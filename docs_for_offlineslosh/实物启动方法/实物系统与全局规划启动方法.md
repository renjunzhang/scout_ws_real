# 实物系统与全局规划启动方法

> 更新日期：2026-08-20
>
> 这份文档整理可重复使用的实物基础启动、全局路径生成和固定路径接入方法。它不是某一批实验的放行文件，也不代表新的 OfflineSlosh 方法已经实现。

下面的命令按 Bash 编写。如果当前终端是 zsh，先运行 `bash`，再执行后续命令。不要在 zsh 里直接 `source setup.bash`。

## 1. 先看结论

新的 offline-slosh 方法建议采用下面的实物链路：

```text
CAN、底盘、雷达、Cartographer、IMU、RealSense
→ 检查 /odom、/scan_front、/map、TF、/imu/data、相机和 /cmd_vel
→ MBF + GlobalPlanner 只生成原始全局几何路径
→ 捕获原始路径
→ 离线清理、平滑、曲率检查和碰撞复核
→ 冻结为 /scout/global_path_fixed 使用的路径文件
→ OfflineSloshOCP 生成离线防晃序列
→ 实验 runner 启动 recorder、控制器和固定路径 replay
→ /cmd_vel 唯一发布给 Scout
```

这是新方法的目标链路，不是当前已经打通的一套命令。现在要分清：

| 内容 | 当前状态 |
|---|---|
| 底盘、雷达、Cartographer、IMU 和 RealSense 基础栈 | 可按本文启动和检查 |
| 已有 S-MPCC 的 development runner | 只能按它对应的带日期协议执行 |
| MBF → 离线平滑 → 冻结路径 | 新方法已选定的路径制作方案，尚未完成工具链验收 |
| OfflineSloshOCP 和 residual S-MPCC 实车运行 | 尚未实现，不可按本文直接跑车 |

这里有两个必须分开的阶段：

1. **路径制作阶段**才会启动 MBF 全局规划器，输出 `/scout/global_path`。这是新方法的未来准备步骤，不属于当前 G3R3 或旧固定路径 trial。
2. **固定路径执行阶段**只重放冻结路径到 `/scout/global_path_fixed`，不需要启动 MBF、move_base 或其他在线全局规划器。

## 3. 启动前检查

开始前先满足下面这些条件：

- Scout 已架设和接线完成，CAN 设备为 `can0`；
- 场地净空，安全员和急停就位；
- 小车处于静止状态；
- 没有键盘遥控、TEB、旧 SPMPC 或其他节点在发布 `/cmd_vel`；
- 不同时启动建图和定位；当前实验使用 Cartographer localization，不是建图；
- 不同时启动 AMCL 和 Cartographer；
- 实物地图、固定路径、相机标定等外部文件已经复制到实物机，而且有可信清单中的预期 hash 可供比对。

当前 Cartographer launch 的默认地图名是：

```text
$(rospack find scout_maps)/maps/map_carto_20260629_R0.pbstream
```

这份地图没有出现在当前 `/home/a/scout_ws` 仓库树中，很可能是实物机外置资产。先从本次 release 或冻结清单中取出这张地图的 64 位 SHA-256，导出为 `EXPECTED_REAL_MAP_SHA256`，再在 `/home/geist` 上运行：

```bash
source /opt/ros/noetic/setup.bash
source /home/geist/scout_ws/devel/setup.bash
set -euo pipefail

: "${EXPECTED_REAL_MAP_SHA256:?请先从冻结清单导出地图的预期 SHA-256}"
[[ "${EXPECTED_REAL_MAP_SHA256}" =~ ^[0-9a-f]{64}$ ]]

REAL_MAP="$(rospack find scout_maps)/maps/map_carto_20260629_R0.pbstream"
test -s "${REAL_MAP}"
REAL_MAP_SHA256="$(sha256sum "${REAL_MAP}" | awk '{print $1}')"
printf 'map=%s\nactual_sha256=%s\nexpected_sha256=%s\n' \
  "${REAL_MAP}" "${REAL_MAP_SHA256}" "${EXPECTED_REAL_MAP_SHA256}"
[[ "${REAL_MAP_SHA256}" == "${EXPECTED_REAL_MAP_SHA256}" ]]
```

文件不存在、没有预期 hash 或 hash 不一致时都要停止。不要临时换成仿真地图，也不要在没有记录的情况下换另一张实物地图。

## 4. 推荐方式：统一启动实物基础栈

终端 A 运行下面的命令，并在整个 batch 中保持运行：

```bash
source /opt/ros/noetic/setup.bash
source /home/geist/scout_ws/devel/setup.bash
set -euo pipefail

export SCOUT_WS=/home/geist/scout_ws
export SENSOR_LOG_DIR="/home/geist/slosh_bags/real/startup_logs/sensor_stack_$(date +%Y%m%d_%H%M%S)"

SCOUT_WS="${SCOUT_WS}" \
LOG_DIR="${SENSOR_LOG_DIR}" \
REALSENSE_COLOR_WIDTH=1920 \
REALSENSE_COLOR_HEIGHT=1080 \
REALSENSE_COLOR_FPS=30 \
REALSENSE_ENABLE_DEPTH=false \
REALSENSE_ENABLE_INFRA=false \
WAIT_FOR_ODOM=true \
WAIT_FOR_LOCALIZATION_MAP=true \
bash "${SCOUT_WS}/src/scout_apps/control/scout_local_planner/scripts/launch_real_sensors_stack.sh"
```

脚本会请求一次 `sudo`，尝试让 `can0` 以 500000 bit/s 启动，然后依次启动：

```text
Scout 底盘
→ 等待 /odom
→ NanoScan3 前雷达
→ 等待 /scan_front
→ Cartographer localization
→ Cartographer 自带的 RViz
→ IMU 和 base_link 到 imu_link 的 TF
→ 等待 /imu/data
→ RealSense 彩色相机
→ 等待彩色图像并检查相机信息
```

它不会启动：

- 全局规划器；
- 固定路径发布器；
- SPMPC；
- 在线液面测量节点；
- rosbag recorder。

不能只看脚本是否还在运行。它当前有几个宽松检查：

- 即使设置 `WAIT_FOR_LOCALIZATION_MAP=true`，`/map` 超时仍只警告并继续；
- 相机信息读取失败或分辨率不符合时只警告；
- IMU 和 RGB 频率检查不会让脚本失败；
- 脚本不检查 `map -> base_link`；
- 如果设置 CAN 速率的命令失败，但 `can0` 已经是 UP，脚本会继续，不能单凭这一点证明速率正确。

所以必须执行下一节的独立检查。

## 5. 基础栈启动后的必做检查

终端 B 运行下面的检查。任何一条失败，整段命令都会停止：

```bash
source /opt/ros/noetic/setup.bash
source /home/geist/scout_ws/devel/setup.bash
set -euo pipefail

# ROS master 必须可连接。
rosnode list >/dev/null

# 确认 CAN 真的是 UP 且 bitrate 为 500000。
CAN_INFO="$(ip -details link show can0)"
printf '%s\n' "${CAN_INFO}"
grep -Fq 'state UP' <<< "${CAN_INFO}"
grep -Eq 'bitrate[[:space:]]+500000' <<< "${CAN_INFO}"

# 这些话题必须能在 10 s 内收到一条消息。
timeout 10s rostopic echo --noarr -n 1 /odom
timeout 10s rostopic echo --noarr -n 1 /scan_front
timeout 10s rostopic echo --noarr -n 1 /map
timeout 10s rostopic echo --noarr -n 1 /imu/data
CAMERA_INFO="$(timeout 10s rostopic echo -n 1 /camera/color/camera_info)"

# tf_echo 会持续运行，timeout 返回 124 是正常的；这里改为检查它的实际输出。
TF_CHECK="$(timeout 5s rosrun tf tf_echo map base_link 2>&1 || true)"
printf '%s\n' "${TF_CHECK}"
grep -Fq 'Translation:' <<< "${TF_CHECK}"
grep -Fq 'Rotation:' <<< "${TF_CHECK}"

# 不只看 timeout 退出码，必须真的统计到 average rate。
check_hz() {
  local topic="$1" output
  output="$(timeout 10s rostopic hz "${topic}" 2>&1 || true)"
  printf '%s\n' "${output}"
  grep -Fq 'average rate:' <<< "${output}"
}

check_hz /odom
check_hz /scan_front
check_hz /imu/data
check_hz /camera/color/image_raw

# 检查 IMU frame 和相机分辨率。
IMU_FRAME="$(timeout 10s rostopic echo -n 1 /imu/data/header/frame_id)"
grep -Fq 'imu_link' <<< "${IMU_FRAME}"
grep -Eq '^width:[[:space:]]+1920$' <<< "${CAMERA_INFO}"
grep -Eq '^height:[[:space:]]+1080$' <<< "${CAMERA_INFO}"

# /cmd_vel 可以有订阅者，但在接入局部控制器前不能有旧发布者。
if rostopic list | grep -Fxq /cmd_vel; then
  CMD_INFO="$(rostopic info /cmd_vel)"
  printf '%s\n' "${CMD_INFO}"
  CMD_PUBLISHERS="$(awk '
    /^Publishers:/ {inside=1; next}
    /^Subscribers:/ {inside=0}
    inside && /^[[:space:]]*\*/ {print}
  ' <<< "${CMD_INFO}")"
  [[ -z "${CMD_PUBLISHERS}" ]]
fi
```

这里只确认了“持续有数据”。各 topic 的最低频率还要以当次实验的冻结协议为准。

最后还要在 RViz 中人工确认：

- 激光与地图对齐；
- 机器人位置和方向正确；
- `map -> base_link` 没有明显跳变；
- 场地和地图与本次路径相符。

当前主要 TF 关系应为：

```text
Cartographer: map → odom
Scout 底盘:   odom → base_link
雷达安装:     base_link → nanoscan3_front
IMU 安装:     base_link → imu_link
```

## 7. 全局规划：只用于未来的路径制作

> 本节是 offline-slosh 新方法的路径制作接口，尚未完成整条工具链的实物验收。它不属于当前 G3R3 或旧固定路径 trial，绝对不能把 MBF 命令插进现有 runner 中。

### 7.1 为什么选 MBF + GlobalPlanner

新方法只需要一个外部工具，从当前机器人位置到目标点生成一条几何路径。设计上选用：

```bash
roslaunch scout_global_planner mbf_global.launch \
  base_global_planner:=global_planner/GlobalPlanner \
  planner_name:=GlobalPlanner \
  replan_frequency:=0.0
```

这个 launch 会启动 MBF `GetPath`，订阅 `/scout/goal`，并把结果发布到 `/scout/global_path`。它的 controller 列表为空，recovery 也关闭，速度接口旁路到 `/scout/move_base_cmd_vel`，不应向 `/cmd_vel` 发布速度。

`replan_frequency=0.0` 的意思是不定时重新规划；但每收到一条 goal 消息，仍会发起一次规划。

还要注意一个重要边界：当前 MBF 的 global costmap 只有 `/map` 静态层和膨胀层，没有把 `/scan_front` 作为全局动态障碍层。所以它只会绕开已经在静态地图上的障碍，不是现场动态避障系统。

几个现有入口的区别是：

| 入口 | 本方案怎样处理 |
|---|---|
| `mbf_global.launch` | 选定为原始几何路径生成器，但尚需实物 smoke |
| `move_base_global.launch mode:=mpc` | 不用；它仍启动完整 move_base 和 DWA 占位局部规划器 |
| `move_base_global.launch mode:=teb` | 禁止与 SPMPC 并行；TEB 会直接发布 `/cmd_vel` |
| `simple_global_planner.launch` | 不用；它是自研实现，路径来源不够通用 |

### 7.2 安全的路径生成和捕获顺序

`/scout/global_path` 是锁存话题。如果 MBF 已经发布过上一个目标的路径，新启动的 capture 会立即拿到那条旧路径。因此不要采用“先规划很多次，最后随便 capture”的顺序。

每制作一条新路径，按下面顺序做。

1. 先停止上一个 MBF 进程，不复用它的锁存消息，并确认 `/scout/global_path` 没有其他发布者。
2. 终端 C 先启动 capture，让它等待第一条新路径。文件名要唯一，已存在时拒绝覆盖：

```bash
source /opt/ros/noetic/setup.bash
source /home/geist/scout_ws/devel/setup.bash
set -euo pipefail

RAW_PATH=/home/geist/fixed_paths/offline_slosh/raw_mbf_path_001.json
test ! -e "${RAW_PATH}"

rosrun scout_local_planner fixed_global_path_runner.py \
  --mode capture \
  --input-topic /scout/global_path \
  --path-file "${RAW_PATH}" \
  --capture-timeout 60
```

3. 终端 D 启动一个全新的 MBF：

```bash
source /opt/ros/noetic/setup.bash
source /home/geist/scout_ws/devel/setup.bash
set -euo pipefail

roslaunch scout_global_planner mbf_global.launch \
  base_global_planner:=global_planner/GlobalPlanner \
  planner_name:=GlobalPlanner \
  replan_frequency:=0.0
```

4. 等终端 D 启动完成，并确认 `rostopic info /scout/goal` 中已经出现 MBF path publisher 订阅者。然后在终端 B 发送一次已在地图上检查过的目标：

```bash
source /opt/ros/noetic/setup.bash
source /home/geist/scout_ws/devel/setup.bash
set -euo pipefail

GOAL_X=3.0
GOAL_Y=0.0
GOAL_YAW=0.0

rosrun scout_local_planner send_fixed_goal.py \
  --goal-topic /scout/goal \
  --frame map \
  --x "${GOAL_X}" \
  --y "${GOAL_Y}" \
  --yaw "${GOAL_YAW}" \
  --repeat-count 1 \
  --repeat-rate 2 \
  --wait-subscriber-timeout 10
```

5. capture 终端保存并退出后，在同一终端检查 JSON：

```bash
test -s "${RAW_PATH}"
python3 - "${RAW_PATH}" <<'PY'
import json
import sys

path_file = sys.argv[1]
with open(path_file, "r", encoding="utf-8") as stream:
    data = json.load(stream)
poses = data.get("poses", [])
assert data.get("frame_id") == "map", data.get("frame_id")
assert len(poses) >= 2, len(poses)
print("pose_count=", len(poses))
print("start=", poses[0]["x"], poses[0]["y"])
print("end=", poses[-1]["x"], poses[-1]["y"])
PY
sha256sum "${RAW_PATH}"
```

还要在 RViz 中使用 `map` 作为 Fixed Frame，显示 `/scout/global_path`，人工核对起点、终点、路径形状和静态障碍距离。确认 capture 完成后，停止终端 D 的 MBF。

这个过程只生成原始路径，不会让车运动。即便如此，MBF 启动前和启动后都要复查 `/cmd_vel` 没有发布者。

## 8. MBF 输出不是最终平滑轨迹

MBF 输出的 `/scout/global_path` 只能叫“原始全局几何路径”。

当前 GlobalPlanner 使用 Dijkstra、二次势函数并关闭栅格中心路径，所以视觉上可能比原始栅格折线圆滑。但是：

- MBF path publisher 只是转发 GlobalPlanner 的结果；
- 没有额外的样条平滑步骤；
- 没有速度、加速度或时间信息；
- 不保证切线连续、曲率连续或曲率变化满足 Scout 和液体优化要求。

现有 `fixed_global_path_runner.py --mode capture` 也只是把路径点保存到 JSON，不会替我们平滑路径。

第 7 节保存的 raw JSON 还不是 OfflineSloshOCP 的最终输入。后面必须完成：

1. 删除重复点和过近点；
2. 按弧长重新采样；
3. 使用 B 样条或三次样条平滑空间形状；
4. 重新计算路径方向；
5. 检查最大曲率和曲率变化；
6. 在平滑后的路径上重新检查障碍物距离；
7. 用新文件名保存最终路径，记录 hash 并写入冻结清单；
8. 完成冻结后取消文件写权限，再确认 hash 没有变化。

上面的“取消写权限”将是新方法 freeze 工具的正式步骤，不是现场随手修改文件权限。这套离线路径处理和 freeze 工具目前还没有在新方案中实现，所以现在不能把 raw capture 重命名成最终冻结路径来绕过这一步。

## 9. 冻结路径执行阶段

完成离线几何处理并生成 OfflineSloshOCP 基准以后，正式执行使用：

```text
冻结 JSON
→ fixed_global_path_runner.py
→ /scout/global_path_fixed
→ 新 residual S-MPCC
```

这一阶段不需要全局规划器。建议停止路径制作阶段的 MBF，避免现场同时存在两条容易混淆的路径。

底层 replay 接口如下。这里的文件名只是未来接口示例；在新方法生成真实冻结文件和预期 hash 之前，这段命令会按预期拒绝运行：

```bash
source /opt/ros/noetic/setup.bash
source /home/geist/scout_ws/devel/setup.bash
set -euo pipefail

PATH_JSON=/home/geist/fixed_paths/offline_slosh/frozen_path.json
: "${PATH_EXPECTED_SHA256:?请先从冻结清单导出路径的预期 SHA-256}"
[[ "${PATH_EXPECTED_SHA256}" =~ ^[0-9a-f]{64}$ ]]
test -s "${PATH_JSON}"
test ! -w "${PATH_JSON}"
PATH_ACTUAL_SHA256="$(sha256sum "${PATH_JSON}" | awk '{print $1}')"
[[ "${PATH_ACTUAL_SHA256}" == "${PATH_EXPECTED_SHA256}" ]]

rosrun scout_local_planner fixed_global_path_runner.py \
  --mode replay \
  --path-file "${PATH_JSON}" \
  --output-topic /scout/global_path_fixed \
  --base-frame base_link \
  --manual-start \
  --start-pos-tol 0.08 \
  --start-yaw-tol 0.15 \
  --start-hold-sec 0.5 \
  --publish-rate 2.0 \
  --publish-count 0
```

这条命令只用于说明接口。真实 development/formal trial 应由配套 runner 启动 replay，这样才能同时检查 path hash、起点门、recorder 和局部控制器状态。

`test ! -w` 是冻结接口的一部分。未来 freeze 工具必须先完成上一节的清单、hash 和取消写权限步骤，否则 replay 拒绝运行是正常结果。

当前旧方法的固定路径局部控制器也使用 `/scout/global_path_fixed`。当前 `fixed_path.yaml` 中障碍和走廊功能均关闭，所以它不会建立用于障碍代价的 `/map` 订阅，也没有在线碰撞代价或避障。路径必须事先确认几何可行。

第一版新方法也不允许在线热切换全局路径。如果 `/scout/global_path` 发生变化，原来的冻结路径和离线防晃序列都应视为失效：先停车，再重新完成平滑、检查和离线规划。

## 10. 局部控制器、录包和当前实验 runner

新的 OfflineSloshOCP 和 residual S-MPCC 尚未实现，所以现在没有可以写入本文件的“新方法实车启动命令”。后续实现时，应新增独立 variant/config 和一键 runner，而不是覆盖旧 solver。

当前 processed-IMU 固定路径 wrapper 的安全顺序是：

```text
确认 reference、/cmd_vel 和 debug topic 没有遗留发布者
→ 启动 recorder
→ 启动 planner，但暂时不给路径，因此只保持零速度
→ 等 processed-IMU 完成静止 bias、滤波预热并进入 READY
→ 启动冻结路径 replay
→ 通过起点位置和航向门
→ 才允许运动
```

新方法 runner 应保留这个基本顺序，并增加：

- 执行模型 artifact hash；
- 平滑冻结路径 hash；
- OfflineSloshOCP nominal artifact hash；
- residual/tube 配置 hash；
- 最终 published `/cmd_vel` 和真实响应记录。

对于现有实验：

- 不要手工拆开 planner、path 和 recorder；
- 使用最新带日期、release ID 和 `VALIDATE_ONLY` 的实验 runner；
- recorder 必须先于有效运动启动；
- `.bag.active` 必须正常闭合成 `.bag`；
- 失败 bag、日志和 postflight 不得删除或覆盖；
- 当前 image-free 协议禁止把 raw RGB、depth 或 debug image 录进 bag。视觉侧只录在线液面标量、质量字段和相机信息；控制、observer、IMU、odom、snapshot、horizon 和 audit 等实验证据仍照常录制。

截至 2026-08-19，最新 G3R3 runner 仍属于旧方法的 development 验证，不是 offline-slosh 新方法。它还要求 `/liquid/measurement` 已经独立启动并正常，而现有 G3R3 指导文件没有给出唯一的在线液面启动命令，这是当前 SOP 的一个缺口。补齐前不要自行猜测 launch 组合。

正式 40/64/88 目前仍是 `NO-GO`。

## 11. 停止方法

真实 trial 要让配套 runner 统一停止，不要人工在多个终端中逐个乱关。当前 processed-IMU runner 有两种情况。

正常到达录包时间边界时：

```text
先看到 .bag.active 已经结束
→ 再通知固定路径 replay 和局部控制器停止
→ 立即发布一次零速度
→ 等待路径和局部控制器真正退出
→ 再发布一次零速度
→ 等待 recorder 完成 bag 后处理
→ 确认 .bag.active 已正常闭合为 .bag
```

注意：这个正常分支是先结束 `.bag.active`，再停路径和局部控制器，所以后面两次零速度不在 bag 里。

在录包仍活跃时收到 `Ctrl-C` 或进入异常 cleanup 时：

```text
先通知等待节点、路径 replay 和局部控制器停止
→ 发布零速度
→ 等待它们退出
→ 再发布零速度
→ 最后停止 recorder
```

这个分支中的停车数据可能进入 bag，但不能把它当作已冻结的尾段记录保证。如果新协议确实要求完整停车尾段，必须先修改并验收 runner，不能靠现场手工控制时序。

所有 trial 完成后，再在终端 A 按 `Ctrl-C` 停止基础传感器栈。

下面的单次零速度只能用于局部控制器已经停止后的补充确认：

```bash
rostopic pub -1 /cmd_vel geometry_msgs/Twist \
  '{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}'
```

如果还有其他节点持续发布非零 `/cmd_vel`，单发一次零速度不能保证停车。

发生人车风险时，不等待正常顺序，立即使用硬件急停。安全处理后仍保留已经产生的数据和日志。

停止基础栈时，在原终端按 `Ctrl-C`。脚本会停止自己启动的子进程。不要使用 broad `killall` 或 `pkill`。

## 12. 关键话题速查

| 话题 | 含义 |
|---|---|
| `/odom` | Scout 底盘的轮式里程计和速度估计，不是 ground truth |
| `/scan_front` | NanoScan3 前向激光 |
| `/map` | Cartographer 占据栅格 |
| `/imu/data` | IMU 原始数据，frame 应为 `imu_link` |
| `/camera/color/image_raw` | RealSense 彩色图像，只作为在线视觉输入或特定调试使用 |
| `/liquid/measurement` | 在线液面标量和质量信息，不是定位源 |
| `/scout/goal` | 路径制作阶段的目标输入 |
| `/scout/global_path` | MBF 输出的原始全局几何路径 |
| `/scout/global_path_fixed` | 冻结路径 replay，固定路径控制器的输入 |
| `/cmd_vel` | 最终实车速度命令，只允许一个有效发布者 |
| `/scout/move_base_cmd_vel` | move_base/MBF 旁路速度接口，不应驱动实车 |

## 13. 当前已知缺口

后续开发前需要处理或明确记录：

1. `launch_real_sensors_stack.sh` 的 `/map`、相机信息、频率和 CAN 检查仍有只警告不停止的情况，而且不检查 `map -> base_link`；
2. 实物默认 `.pbstream`、冻结路径和 RGB calibration 是实物机外置资产，当前仓库不能证明它们存在；
3. MBF 路径制作链还没有完成实物 smoke，原始路径到平滑冻结路径的离线工具也尚未实现；
4. OfflineSloshOCP、nominal artifact 和 residual controller runner 尚未实现；
5. 当前最新 G3R3 文档缺少唯一的在线 `/liquid/measurement` 启动入口；
6. 0717 文档中的 formal 多终端模板仍为 `NO-GO`，不能作为现成正式命令；
7. `change_log.md` 中旧 `Q_slosh`、governor 和旧 recorder 命令不能用于当前 SPMPC；
8. `fixed_global_path_runner.py --mode capture` 自身不会拒绝旧的锁存路径，也不会拒绝覆盖已有 JSON，所以现阶段必须使用第 7.2 节的顺序规避。
