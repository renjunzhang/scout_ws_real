# SPMPC 局部规划器解耦与模块化重构方案

- 日期：2026-08-20
- 审计对象：`src/scout_apps/control/spmpc_local_planner`
- 审计基线：分支 `offline-slosh-plan-online-tracking`，提交 `a156182a`
- 本文性质：重构实施方案；本轮不修改控制算法和业务代码

## 1. 核心结论

一句话重构思路：

> **在控制行为不变的前提下，把一次控制周期收敛为可离线复现的纯 C++ `ControlCycleEngine`，ROS 只负责收发和类型转换，Python 只承担代码生成与离线分析。**

当前代码不是需要推倒重写，而是需要重新建立边界。已经模块化且有测试的 `reference`、`estimation`、`warm_start`、`phase_rejoin` 和液体动力学应保留；主要拆解对象是以下三处：

1. `SpmpcLocalPlannerROS`：同时承担参数、状态、求解、安全、命令和诊断，是当前最大耦合点；
2. `continuous_mpcc_solver_acados.cpp`：把 acados ABI、参数打包、warm start、Phase-Rejoin 和结果解码放在同一文件；
3. 单一 CMake library：目录虽然分开，构建依赖没有分开，任何层都可以越界引用。

建议先在**同一个 ROS 包内拆目录和 C++ library target**，暂时不拆成多个 catkin 包。这样可以先解决代码耦合，又不会立即增加部署、消息和版本管理成本。

## 2. 本次重构的范围

### 2.1 要做

- 将领域状态、执行模型、估计、求解接口、命令仲裁和 ROS 适配分层；
- 把 `controlTimerCallback()` 中的业务流程抽成纯 C++ 控制周期引擎；
- 建立一次且唯一的最终命令仲裁链；
- 使用 typed config，一次加载并集中校验参数；
- 拆分 acados backend，消除 Python codegen 与 C++ wrapper 的手写双真源；
- 在线、实时、fail-closed 和确定性回放逻辑优先使用 C++；
- 整理 Python、Shell、测试和安装内容；
- 用单元测试和固定 bag replay 证明重构前后行为一致。

### 2.2 暂时不做

- 不修改 B0、BSlosh 或 Phase-Rejoining 的数学形式；
- 不重新调权重、延迟、液体模型或 Scout 参数；
- 不改变现有 topic、ROS message、参数 key、artifact schema 和状态码；
- 不同时引入新的避障、恢复集合或实物功能；
- 不立即删除历史实验脚本，也不把全部 Python 强行改写为 C++；
- 不在结构重构提交中混入论文算法改进。

结构变化和算法变化必须分开提交。否则仿真或实物结果改变时，无法判断来自代码回归还是方法变化。

## 3. 当前代码的实际情况

### 3.1 已经做得好的部分

- 唯一可执行入口 `spmpc_local_planner_node.cpp` 很薄，只负责创建 ROS 对象；
- 液体动力学、路径、observer、warm start 和 Phase-Rejoin 大部分已经是纯 C++；
- 现有 CMake 注册了 14 个 C++ gtest target，源码中约有 138 个 `TEST/TEST_F`；
- IMU 使用独立 callback queue，observer 共享状态有互斥保护，并发设计有明确意图；
- Phase-Rejoin 已经有 artifact、候选、gate 和 coordinator 等独立类，可继续细化而不是重写。

### 3.2 主要耦合点

| 位置 | 当前事实 | 直接问题 |
|---|---|---|
| `ros/spmpc_local_planner_ros.cpp` | 2940 行；初始化约 700 行；读取约 215 个参数 | ROS 类同时决定配置、算法和安全策略 |
| `controlTimerCallback()` | 约 570 行 | 一次函数完成状态门控、observer、时间对齐、执行预测、求解、Phase-Rejoin、安全、诊断和发布 |
| `ros/spmpc_local_planner_ros.h` | 同时持有 ROS I/O、TF、solver、observer、governor、phase、history 及大量运行状态 | 类成员成为隐式模块接口，难以独立测试 |
| `core/types.h` | 465 行，并反向包含 Phase-Rejoin 和 warm-start diagnostics | 领域状态、solver I/O 和诊断 DTO 混在同一个总头文件 |
| `continuous_mpcc_solver_acados.cpp` | 1588 行，核心 `solve()` 约 690 行 | ABI、参数布局、约束、warm start、诊断和多种 solver 混合 |
| `diagnostics_publisher.cpp` | 1287 行，约 55 个 publisher | 诊断采集、消息编码和 ROS 发布没有分开 |
| `CMakeLists.txt` | core、solver、ROS 和 diagnostics 编入同一库 | 目录边界无法由编译器约束 |
| `install(DIRECTORY ... scripts)` | 整个 `scripts/` 被安装 | codegen、分析、测试、缓存也进入 runtime share |

另外还有四个重要问题：

- `control_cycle_contract` 和 `delay_phase_types` 本身不依赖 ROS，却放在 `ros/` 目录；
- `CommandHistoryBuffer` 使用 `ros::Time + geometry_msgs::Twist`，把数值执行模型绑定到 ROS；
- 命令决策分散在 `SpmpcProblem::solve()`、ROS callback、安全 gate 和发布 limiter 中，没有单一所有者；
- map-vref 的 CSV、插值和参数读取在 ROS 类中，且控制周期内仍会访问 parameter server。

## 4. 目标架构

### 4.1 单向依赖

```text
spmpc_local_planner_node
          │
          ▼
       spmpc_ros
  参数加载 / TF / 消息转换 / 收发
          │
          ▼
    spmpc_controller
 ControlCycleEngine + CommandPipeline
          │
          ├──────────► spmpc_runtime
          │            状态对齐 / 命令历史 / 执行前沿 / v_ref
          ├──────────► spmpc_estimation
          ├──────────► spmpc_phase_rejoin
          ├──────────► spmpc_solver_api
          │                 │
          │                 ├── spmpc_solver_rollout
          │                 ├── spmpc_solver_acados
          │                 └── spmpc_solver_legacy（可选）
          └──────────► spmpc_safety

下层公共能力：spmpc_domain / spmpc_model / spmpc_reference / spmpc_warm_start
```

依赖只能由外向内。`domain/model/reference/estimation/runtime/phase_rejoin/solver_api/controller` 不得包含：

- `ros::Time`；
- ROS message；
- parameter server；
- topic 名称；
- ROS 日志宏。

核心时间统一为 `std::int64_t stamp_ns`，速度命令统一为纯 C++ `VelocityCommand`。ROS 层只在边界进行转换。

### 4.2 建议目录

```text
include/spmpc_local_planner/
├── domain/             # RobotState、SloshState、VelocityCommand、时间戳
├── config/             # AppConfig、子配置和纯 C++ 合同校验
├── model/              # 液体和车辆数值模型
├── reference/          # path、spline、projection、speed profile
├── estimation/         # odom/IMU excitation、observer、selector
├── runtime/            # state alignment、command history、execution front
├── phase_rejoin/       # phase、candidate、gate、artifact
├── warm_start/         # solver warm start
├── solver/
│   ├── api/            # SolverRequest、SolverResult、Capabilities
│   ├── rollout/        # 采样后端
│   ├── acados/         # 唯一允许接触 generated/acados 的位置
│   └── legacy/         # direct-omega 等旧后端，可选编译
├── safety/             # tracking、terminal、平台硬安全
├── controller/         # ControlCycleEngine、CommandPipeline 和流程编排
├── telemetry/          # ROS 无关的周期诊断快照
└── ros/                # config loader、message adapter、publisher、RosNode

src/                    # 与 include 同结构
tools/
├── codegen/acados/     # 保留的 Python codegen
├── analysis/           # 离线 Python 分析
└── legacy/             # 已封存的旧协议工具

test/
├── cpp/
├── python/
├── fixtures/
└── golden/
```

目录和 library target 不必机械地一一对应，但每个稳定边界必须有独立 target，不能再编成一个总库。

### 4.3 一次控制周期的唯一流程

`ControlCycleEngine::step()` 固定执行以下流程：

```text
输入快照与就绪检查
        ↓
observer 选择与统一时间轴
        ↓
执行延迟期间状态传播
        ↓
v_ref / slosh policy / Phase-Rejoin prepare
        ↓
solver.solve()
        ↓
terminal / recovery / fail-closed 决策
        ↓
tracking 与平台硬安全
        ↓
最终限幅和 command contract
        ↓
唯一 final command + 一份周期诊断快照
```

ROS timer callback 最终只做三件事：获取输入快照、调用 `engine.step()`、发布结果。它不再判断 solver 成败，不再决定恢复动作，也不再修改命令。

建议的最小接口为：

```cpp
struct ControlCycleRequest {
    std::uint64_t cycle_id;
    std::int64_t cycle_start_ns;
    StampedRobotState robot;
    ObserverSnapshot observers;
    ReferenceView reference;
    CostmapView costmap;
};

struct ControlCycleResult {
    VelocityCommand solver_command;
    VelocityCommand final_command;
    CommandDecision decision;
    ControlCycleTelemetry telemetry;
};
```

接口只表达所有权，不要求第一阶段立即采用上述最终命名。

## 6. C++、Python 和 Shell 的边界

“少用 Python”应按运行职责判断，而不是按文件数量判断。目前包内有 47 个 Python 文件，但 3 个 launch 均只启动 C++ `spmpc_local_planner_node`。多数 Python 属于离线分析和实验协议。

当前 `package.xml` 也没有声明这些离线脚本所需的 rosbag、NumPy、PyYAML、CasADi 等依赖；因此将整个 `scripts/` 安装到 runtime share 并不自洽，应改成运行文件白名单。

### 6.1 必须迁到 C++

| 优先级 | 当前脚本/逻辑 | 原因与目标 |
|---|---|---|
| P0 | `validate_realsense_timestamp_health.py` | 它在 G3R2 实物运动前执行 fail-closed 门控；迁为无 ROS `TimestampHealthEvaluator` + 小型 C++ ROS executable |
| P0 | 正式配置、artifact 和 command contract 校验 | 属于运行放行条件，应与实际 C++ schema 使用同一真源 |
| P1 | `analysis/horizon_liquid_replay.py` | 重复液体动力学和 observer replay，应调用共享 C++ model |
| P1 | `generate_phase_rejoin_development_nominal.py` | 重复车辆/液体传播和 artifact schema，迁为 C++ CLI |
| P1 | `prepare_phase_rejoin_development_artifact.py` 的 schema 校验/写入 | rosbag 提取可暂留 Python，领域合同进入 C++ artifact core |
| P1 | `analysis/g4_replay_from_g3.py` | 直接操作 acados 参数和 iterate，长期改成复用真实 backend 的 C++ replay executable |

时间戳门迁移必须保持当前 CLI、退出码、JSON schema、滑窗、settle-until-pass 和 queue 语义。数值 replay 迁移必须先用固定 bag 双跑，逐字段比较输出。

### 6.2 继续保留 Python

- `scripts/acados/` 中 4 个 CasADi/acados codegen 脚本；
- rosbag 提取、统计检验、画图、CSV/JSON 汇总；
- trial 结束后的 postflight 分析；
- 需要 NumPy、SciPy、pandas 或绘图库的探索性工具。

这些工具应移到 `tools/codegen` 或 `tools/analysis`，不安装到机器人 runtime share。

### 6.3 Shell 只做薄编排

Shell 可以保留环境准备、启动、录包和顺序编排，但不能继续承载领域判断。当前 `run_spmpc_short_horizon_matched_trial.sh` 直接执行 Python 单元测试作为运行门，应替换为构建好的 C++ preflight validator。

### 6.4 暂不直接删除的内容

- G2S/G3/G3R/G3R2 的 campaign-specific 脚本：先按 protocol/revision 封存证据，再归档；
- `validate_spmpc_formal_freeze.py` v1.0：不能放行 v2.0，应进入 legacy，而不是假装升级；
- `analysis/estimate_cmd_odom_delay.py`：已被新工具取代，可在确认引用清零后归档；
- `__pycache__` 和 `.pyc`：可直接清理并加入 ignore。

注意：实物链还跨包调用 `scout_local_planner` 的路径/goal Python 工具，以及 `realsense_liquid_measurement` 的在线液面节点。它们不属于本包重构范围，但若最终目标是“整条实物在线链 C++ 化”，需要后续单独审计，不能以本包 Python 数量下降代替整链验收。

## 7. 分阶段实施计划

### R0：冻结现有行为

改动：

- 保存当前参数表、topic、message schema、status code 和命令优先级；
- 选定固定 bag、固定 reference、固定 artifact，建立 golden replay；
- 补 config/backend policy、reference、map-vref、命令优先级的 characterization tests；
- 记录当前测试清单和关键输出容差。

验收门：

- 现有 C++/Python 测试通过；
- golden 数据能逐周期关联 `cycle_id`、solver 输入、solver 命令和最终发布命令；
- 明确浮点严格相等项与允许容差项。

此阶段不过，不开始移动核心代码。

### R1：拆领域类型和 CMake target

改动：

- 新增 `domain`、`runtime`、`solver_api`、`controller`、`ros` 等 target；
- 拆分 `core/types.h`，暂留兼容头和 type alias；
- 为非 ROS target 设置独立 include/link 依赖。

验收门：

- 仅移动和拆库，不改变运行结果；
- 非 ROS target 可以在不链接 catkin/acados 的情况下编译；
- 静态检查确认核心目录没有 ROS include。

### R2：执行模型彻底去 ROS

改动：

- 迁移 state alignment、command history、delay types 和 execution predictor；
- 使用 `stamp_ns + VelocityCommand`；
- ROS adapter 只负责转换输入输出。

验收门：

- 现有 history/predictor/contract 测试逐值一致；
- 补齐时钟回退、历史不足、双通道延迟、timeout 和边界采样测试；
- 固定 replay 的 execution-front 状态与旧实现一致。

### R3：集中配置加载与校验

改动：

- 建立 `AppConfig`、子配置和 `ValidationReport`；
- `RosConfigLoader` 负责参数 key 到 typed config 的映射；
- backend capability、release policy、artifact contract 使用纯 C++ validator；
- `SpeedProfile` 一次加载，不在周期中访问参数服务器或文件。

验收门：

- 当前约 215 个参数读取都有映射、默认值和兼容说明；
- fatal/warn/normalize 行为有表驱动测试；
- 控制周期内无 parameter server 和文件 I/O；
- 相同 YAML 得到相同 effective config。

### R4：抽取控制周期和唯一命令链

改动：

- 建立 `ControlCycleEngine`、`CommandPipeline` 和 `SafetySupervisor`；
- 把 observer 选择、统一时间轴、执行预测、phase prepare/decide/commit、solver 和安全仲裁移出 ROS；
- 统一 solver command、terminal command、recovery command、safety override、limiter 和 published command 的审计。

验收门：

- WAIT、TF/observer 失败、solver 失败、terminal、phase recovery、tracking safety、limiter 和 contract 的优先级均有确定性单测；
- 对同一 golden bag，最终命令、状态码和 intervention 原因逐周期一致；
- ROS timer callback 中不再出现 solver、phase 或安全业务判断。

### R5：拆分 solver backend

改动：

- `SolverApi::configure()` 返回显式结果，`solve()` 改为符合真实状态语义的非 `const` session；
- acados capsule 使用 RAII，消除 raw `void*` 生命周期；
- 拆 parameter builder、warm-start policy、solution decoder；
- B0、BSlosh、Phase-Rejoin 与 legacy backend 通过 capability/manifest 选择；
- generated manifest 成为参数布局和 bounds 的唯一真源。

验收门：

- off/monitor/enforce replay 与旧 backend 的参数、初值、`u0`、horizon、cost 和 status 一致；
- capsule 创建失败在 configure 阶段明确失败；
- 无 acados 时，domain/controller/rollout 仍可构建测试；
- legacy target 关闭时不影响主线。

### R6：拆诊断与工具链

改动：

- controller 只生成 ROS 无关 telemetry snapshot；
- ROS 层按 control-cycle、solver、observer、phase 分组编码和发布；
- Python 测试移入 `test/python`，codegen/analysis 移入 `tools`；
- CMake 改成白名单安装，禁止安装 tests、codegen、legacy 和缓存；
- 完成 P0/P1 C++ 工具迁移。

验收门：

- 现有 topic 和 message schema 不变；
- telemetry encoder 有 golden test；
- install space 中只有运行所需 executable、library、config、launch 和必要资源；
- 实物启动主链在本包内不依赖 Python。

### R7：删除兼容层并重新冻结

只有 R0–R6 全部通过后，才能删除旧总头、旧 ROS 业务函数和兼容 facade。

实验脚本、路径或输出 schema 一旦改变，旧 `FREEZE_ID` 不得继续使用。需要：

1. tag/归档旧执行链；
2. 固定 bag 双跑新旧实现；
3. 比较 JSON/CSV、退出码和 fail-closed 条件；
4. 生成新的 commit、binary/tool hash 和 `FREEZE_ID`。

## 8. 第一批可以直接开始的任务

第一批建议只做到 R0–R2，不碰 solver 数学：

1. 建立一组最小 golden replay fixture，冻结命令仲裁和执行前沿输出；
2. 给 backend policy、map-vref、reference preprocess 和 command priority 补 characterization tests；
3. 新建 `domain/time.h`、`domain/command.h`、`domain/state.h`；
4. 将 `delay_phase_types`、`control_cycle_contract` 移出 `ros/`；
5. 将 `CommandHistoryBuffer` 和 `ExecutionStatePredictor` 改为纯 C++ 类型；
6. 按依赖拆第一版 CMake target，并增加“核心层禁止 ROS include”的检查；
7. 保留旧 include 路径作为临时兼容 facade，所有调用切换后再删除；
8. 单独提交，不顺手修改 B0、权重、gate 或 Scout 执行参数。

建议对应提交顺序：

```text
重构01：冻结控制周期行为并补齐特征测试
重构02：拆分领域类型与构建目标
重构03：执行历史和执行前沿预测去ROS化
重构04：集中参数加载与运行合同校验
重构05：抽取纯C++控制周期和统一命令链
重构06：拆分acados后端与生成合同
重构07：拆分诊断并整理Python/Shell工具
重构08：移除兼容层并建立新冻结版本
```

每个提交都必须可编译、可测试、可单独回退。禁止积累一个跨阶段的大提交。

## 9. 最终完成标准

满足以下条件才算重构完成：

- ROS 依赖只存在于 `spmpc_ros` 和明确的 ROS executable；
- `ControlCycleEngine` 可以用普通 C++ fixture 或 bag replay 独立运行；
- 控制周期内没有 parameter server、磁盘 I/O 和 Python 调用；
- 最终命令只有一个所有者，优先级和 intervention 原因可测试、可审计；
- solver API 不暴露 acados C ABI，生成参数合同只有一个真源；
- Python 仅用于 codegen、离线数据处理、统计和绘图；
- runtime install 不再包含测试、分析、codegen、legacy 或缓存；
- 重构前后 golden replay 在规定容差内一致；
- 新功能和算法修改从新的独立提交开始。

## 10. 与后续仿真和实物工作的关系

这次重构应当位于大规模实物标定和正式实验之前，因为后续需要反复辨识 Scout 双通道执行模型、验证液体 observer、运行 Phase-Rejoin 和比较基线。若控制周期仍集中在 ROS 巨型类中，任何实物异常都会很难定位。

但重构不能代替标定，也不能改变当前证据边界：

- Scout 的延迟、惯性、IMU/RGB 时间偏差仍需在实物阶段辨识；
- 这些结果应成为 config/artifact 数据，而不是硬编码进 controller；
- B0 或防晃性能修正必须在结构等价通过后另开提交；
- 只要正式二进制、工具或冻结合同变化，确认实验就应使用新的 `FREEZE_ID`。

因此推荐顺序为：

```text
行为冻结
→ 结构重构与等价 replay
→ Scout/IMU/RGB 标定
→ 模型保真度实验
→ 控制算法修改与仿真
→ 固定版本实物确认
```

这能让后续每个实验结果都回答一个明确问题，而不是同时验证架构、实现、模型和算法。
