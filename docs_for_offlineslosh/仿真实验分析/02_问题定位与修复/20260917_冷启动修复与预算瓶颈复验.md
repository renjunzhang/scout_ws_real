## 仿真与实物延迟的关系

实物不应为了匹配控制器再人为加入延迟。`common.yaml` 的 FOPDT 参数来自
[20260902 底盘阶跃辨识](../../../docs/实物实验注意事项/对比试验/实物对比试验分析/20260902_底盘速度阶跃与执行器能力辨识分析.md)：
在 0.15 m/s、0.30 rad/s 工作点，拟合延迟约 155/330 ms，tau 为 112/119 ms，
增益为 1.018/1.096；生成模型将延迟量化为 30 Hz 下的 5/10 拍，即约 167/333 ms。
这些是工作点相关的候选值，不是全速度范围通用的实测常数。

当前 Gazebo 的 planar drive + acceleration guard 没有复现该执行模型。
正式比较需要让仿真执行链匹配经验证的实物响应，或另行生成匹配仿真执行链的预测模型。
旧的 `delay_phase=off` 不会关闭显式 FIFO。

但上一批静止时的预测失败不能只归因于这个失配：直接从 bag 提取首个求解快照，
不运行 Gazebo，在相同生成求解器中恢复参数、边界、初值和迭代次数，
可得到与录包 **逐状态完全相同** 的结果（B0 与 Full 的最大状态差均为 0）。
入口为 `scripts/diagnose_trajectory_solver_startup.py`，证据为
`raw_cold_baseline.json`、`full_cold_baseline.json`。快照只有 primal 初值，
因此该工具只用于冷启动；不能据此声称恢复了后续周期的 dual/internal history。
最终脚本再次复现的结果与脚本哈希另存于 `raw_cold_verified.json`、`full_cold_verified.json`。

## 根因与本轮修复

1. **热启动状态与控制不一致。** 旧实现截断 `v_cmd/omega_cmd`，保留原 `a/alpha`，
   在饱和点造成动力学缺陷。B0 录包初值最大缺陷为 0.012965872，出现在命令速度及 FIFO 尾部。
   修复为先限制控制增量，再积分状态；状态和控制在整段传播成功后一起替换。
   同时保留真实初始实际速度，并保持连续 yaw，避免跨 ±π 产生 2π 跳变。
   离线修正初值的缺陷降至 0，但首轮优化后的缺陷仍约 0.02209，说明它只是其中一个缺陷。

2. **被拒绝的迭代进展丢失。** 旧实现只有已接纳解可用于下一周期，启动拒绝后总是重建 flatness/plan 初值。
   新实现只对“有限值且 acados 返回成功、但动力学检查未通过”的结果保留数值初值。
   下一周期从真实反馈和真实命令 FIFO 重新积分，不把未执行控制向前移一拍，
   不更新已接纳解标记或命令历史，不放行失败输出。诊断来源为 `RETRY_NUMERICAL_ITERATE`。
   配置/任务重置会清空该初值，其他失败仍按原策略处理。

3. **已满足接纳所需可行性的迭代仍消耗预算。** 有在线 deadline 时，每次 RTI 后计算真实非线性残差，
   dynamics ≤ 原 `1e-4` 且所有生成不等式残差 ≤ `1e-6` 时停止继续迭代。
   随后的独立动力学重放、区域、液体、jerk、命令和发布时间检查仍执行。
   残差计算本身计入迭代墙钟估计。无 deadline 的 native 回归仍执行原固定次数。
   这不是最优性收敛证书，也没有取消既有停车接管。

离线试过 condensing 数量、QP 热启动和裁减蕴含边界，没有得到足以支持生产变更的收益，
因此均未修改生产参数或边界。部分 Full QP 达到 50 次迭代上限；
acados SQP_RTI 可以将 QP MAXITER 映射为 NLP success，仍需依赖实际非线性接纳检查。
诊断候选及负结果保留在 `*_qp_hot.json`、`*_implied_bounds.json` 等文件。

| 最终结果 | FAIL，`TASK_DEADLINE_MISSED` |

cycle 29/30 被拒绝，cycle 31 使用 `RETRY_NUMERICAL_ITERATE` 后通过并首次发布非零命令。
cycle 130 在求解开始前已经过去 20 ms 仿真时间，0 次 RTI，触发
`SOLVER_FAILURE_STOPPING: SOLVE_BUDGET_EXHAUSTED`，之后保持既有停车所有权。
本轮已经消除了“每拍重新从头启动”的现象，但没有完成整段运输。

TF 录包线索（`raw_r01/tf_timing_diagnosis.json`）：cycle 130 开始于 43.128 s，
原始里程计 epoch 为 43.127 s，而开始前最新 map→odom 与 odom→base_footprint TF 只有 43.124 s。
到求解开始的 43.148 s，更新的 TF 已到达；与 `robotStateAtEpoch()` 等待同 epoch TF 的路径吻合。
bag 到达顺序不是 planner 的实际 TF buffer 到达时刻，因此尚不能把全部 20 ms 精确归因于 TF 等待。
需要分段 steady-clock 计时，而不是延长发布时效或绕过停车策略。

上述 P95 都来自 ROS/仿真时间，不能替代控制器实际使用的 steady-clock 预算；
全窗还包括大量停车周期，不可拿全窗 P95 宣称 30 Hz 运输通过。

## Full 的诊断计划来源

正确区域下的上层重算未在本轮限时内完成：一次冷启动超过五分钟后显式中止，
一次使用旧解初值的单 BLAS 线程重算达到 6 分钟 timeout，均没有产生可执行的新优化结果。
这不是证明任务不可行；两个日志和中止记录均保留。

为独立验证下层启动，使用 `reanchor_feasible_seed.py` 将旧控制序列在本轮 **同一 task**
的真实声明初值上完整重新积分，虚拟进度按新路线长度重标定。
直接重放因 yaw 超容差而被 validator 拒绝（`feasible_seed.log`）；
之后在 10–20 s 加入很小的平滑角命令脉冲，末端命令和 FIFO 仍清空，
重新积分全部车体、执行器和液体状态，再通过完整 Python 和 C++ 检查。
没有放宽任何 validator 容差，也没有只修饰输出轨迹。

最终 `feasible_seed_plan.json` 明确标记 `REPLAYED_FEASIBLE_SEED_NOT_REOPTIMIZED`，
保留原优化来源、SHA256 和脉冲大小。模型重放缺陷为 0，区域最小余量 1.3033 m，
密集内部液面峰值约 0.37487 mm。它是可行诊断计划，不能称为新任务的最优解，
也不能用本轮 B0/Full 数值计算防晃收益。

## Full fresh Gazebo：full_r01

使用上述诊断计划与 raw_r01 **同一份冻结 task**。新 Gazebo 定位初始值与 task 声明初值
存在约 7.6 mm 的位置差，求解器仍从本 case 的实际反馈重建初始状态；没有把计划初值当观测。

| 指标 | 本轮 full_r01 |
|---|---:|
| 启动动力学拒绝 | 2 次 |
| 成功求解并接纳 OCP 命令 | 2 次 |
| 成功解最大动力学缺陷 | 8.8516e-6，门槛仍为 1e-4 |
| 已执行求解的 RTI 次数 | 四个周期均为 1 |
| 非零 `/cmd_vel` 数 | 6，包含停车尾段 |
| 两次成功求解耗时 | 15/28 ms，ROS/仿真时间 |
| 最终结果 | FAIL，`TASK_DEADLINE_MISSED` |

cycle 26/27 被拒绝，28/29 通过并发布；30 为 0 次 RTI 的 `SOLVE_BUDGET_EXHAUSTED`，
进入持续停车接管。与 B0 的 TF 等待线索不同，该周期求解前只有 2 ms 仿真时间，
上一周期求解达 28 ms；预算逻辑同时考虑上一轮迭代墙钟估计，仍需墙钟分段数据区分
求解变慢、线程调度和预算估计保守程度。不能只把这一例归因于 TF。
停车期间还出现两次 `STATE_TIME_ALIGNMENT_FAILED_EXTRAPOLATION_LIMIT`（716/788），
不是本例最早的失败触发点，也未被剔除。

两例均有闭合 bag，前后 ROS 11892 / Gazebo 11926 端口为空，`valid_fresh_lifecycle=true`，
`passed=false`。Full 只出现很短的小速度启动，定位变化量不宜解释为有效运输距离。
本轮精简机器记录见[结果与身份 JSON](20260917_冷启动修复与预算瓶颈复验.json)。
