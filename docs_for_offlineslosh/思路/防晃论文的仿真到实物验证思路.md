## 1. 为什么要分成两条线路

仿真和实物面对的“被控制对象”本来就不同：

| 内容           | 仿真线路                | 实物线路                     |
| -------------- | ----------------------- | ---------------------------- |
| 控制器内部代码 | 同一套 C++ 代码         | 同一套 C++ 代码              |
| 内部模型形式   | 同一套线/角双通道模型   | 同一套线/角双通道模型        |
| 内部模型参数   | 仿真版本参数            | 用实车数据辨识的参数         |
| 外部被控对象   | 独立的仿真 Scout 和液体 | 真实 Scout 和真实液体        |
| 离线防晃轨迹   | 按仿真参数生成          | 按实车参数重新生成           |
| 恢复判定规则   | 用独立仿真数据验证      | 用实车参数和独立数据重新验证 |
| 最终结论       | 方法在仿真中有效        | 真实液面是否降低             |

控制器内部模型要保持同一种含义，但参数不必相同。仿真中的“假 Scout＋假液体”反而不能与控制器内部模型完全一样，否则相当于控制器自己出题、自己判卷。

这说明旧约束只保证“命令刚进入队尾时兼容”，没有保证它在后续预测阶段逐格前移时仍兼容。最终 OCP 因此在每个 path stage 对 14 个 execution state 全部施加与该 stage 参数图像绑定的双边 B_exec，共 28 项；发布 envelope/residual authority 仍为原 6 项，stage 总约束数 34，terminal 为 empirical 1 项加 B_exec 28 项。参数 schema/hash、beta、V3、residual authority、cost、recovery、Plant 和成功定义均未改变；solver config hash/ID 因求解器语义变化而更新。

最终只读 development 证据目录：

`/data/a/spmpc_exec_identification/phase_rejoin_seed8601_stage3_closed_dev_20260822.ShBSbL`

两次 seed 8601 结果完全一致（仅真实 wall-time 列不同）：

- 每次 1061 次 Full SQP，原始状态全部为 `DELAY_AUGMENTED_ACADOS_OK`；
- `solver_failures=0`、`controlled_stops=0`、`recovery_actions=0`；
- `sequence_completed=true`、`task_success=true`，完成原因为 `PHASE_TAIL_RELEASED`；

- 每次最大 KKT 残差均为 stationarity `9.9978e-7`、equality `4.1775e-9`、inequality `0`、complementarity `9.9421e-10`，最大 SQP/QP 迭代数为 4/13；
- 两次合并 2122 个完整 backend wall-time 样本：P50 `2.2207 ms`、P95 `3.0568 ms`、P99 `5.3270 ms`、max `9.8945 ms`，相对 30 Hz 的 `33.333 ms` 预算零超期。

因此仿真第 3 阶段的 seed 8601 development gate 为 **GO**，严格 C3 消融定义、C4 development readiness 和 C1 公平配置均已形成。当前补丁完成后只需一次 clean build/freeze/readiness 和人工确认。正式 C0--C4/IS 未执行，planar_r03 仍不是实车参数，也没有论文级正式正向防晃结论。

### 仿真4：完成C0–C4正式仿真

这是当前下一阶段。补丁提交后的 clean build/freeze/readiness 通过并获得人工确认后，即开始 seeds 3101--3116 的正式矩阵；此后不再回调方法或统计规则。

名义路径比较：

- C0 普通 MPCC；
- C1 独立用 task/tracking/time/accel/jerk 冻结的平滑普通控制器；不预设其完成时间或平滑程度与 C4 相近；
- C2 只回放离线防晃轨迹；
- C4 完整方法。

受控偏离比较：

- C3 使用与 C4 相同的 22D residual MPC、完整预测域 B_exec、冻结恢复反馈和发布事务，但 9D empirical gate 只监测、不参与优化或监督器 admission；
- C4 在同一控制链上强制执行 9D empirical gate。

同时改变延迟、液体频率和阻尼，检查结果是否稳定。**独立仿真液面必须下降**；控制器内部计算的液面只用于解释原因，并检查变化趋势是否一致。还要报告完成时间、路径误差、动作平滑性，以及控制器能否每秒运行 30 次且不超时。

### 仿真线路完成后得到什么

仿真线路完成后，至少留下一个完整、可复现的仿真研究：

> 考虑线/角差分执行延迟的相位重接控制，在独立底盘和液体仿真中降低了晃动，并减少了破坏离线防晃尾段的在线修正。

如果实物最终没有成功，这套结果可以独立整理成一般应用型控制或机器人论文。但只能声称“仿真中有效”，不能声称真实液面已经降低。

## 4. 线路二：仿真通过后再做实物

### 实物1：标定 Scout 和测量时间轴

使用最终容器、液位和载荷，记录最终发布命令、Nokov、odom、IMU 和 RGB，辨识：

- 线速度和角速度延迟；
- 响应惯性和增益；
- 死区、饱和和可能的方向差异；
- ROS、Nokov、IMU 和 RGB 的时间偏差。

### 实物2：完成实车基础验证

详细技术文档把这一步叫 `G0`。人话就是检查：

1. Scout 的执行延迟是否稳定；
2. 从读取状态到预测终点的整段预测是否足够准确；
3. 第一拍在线修正在实车上是否真的高于噪声；
4. IMU 和 RGB 的时间、幅值和相位是否可信。

四项全部通过，才是“可以继续”；任一项不通过就停止，先修正延迟、模型或传感器。这一步通过不代表防晃性能已经成功。

### 实物3：重新生成实物专用资产

实物线路继续使用相同控制器代码，但必须替换为实车参数，并重新生成：

- 实物专用离线防晃轨迹；
- 执行状态匹配条件；
- 恢复判定规则；
- 实物实验配置和版本记录。

仿真线路的轨迹和恢复规则不能直接拿来上车。

### 实物4：重跑仿真，再做只观察、不控制的检查

先用实车标定参数配置控制器，再重跑仿真，确认代码修改后仍然正向。外部仿真 Scout 和液体仍要保留独立的参数偏差与未建模误差，不能与控制器内部模型完全相同。随后在实车上只观察控制器判断、不让它实际控制车辆，确认接回尾段的判断、时间索引和最终命令记录正确。

这两项通过后，才允许正式实物实验。

### 实物5：正式实物对比

名义主实验：

- C0、C1、C2、C4；
- 使用同一路径、容器、液位、起始条件和安全限制；
- 主要比较独立 RGB 液面高度，同时检查完成时间和路径误差。

恢复实验：

- C3、C4；
- 只做预先审查过的小幅、可重复偏离；
- 大量危险或明显不可恢复的情况留在仿真和录包回放中。

最终防晃结论只由独立 RGB 实物结果给出，控制器内部液面只能解释原因。

## 5. 两条线路共用什么，必须分开什么

### 共用

- 控制器 C++ 代码和双通道模型形式；
- 最终命令出口和记录方式；
- C0–C4 的定义；
- 分析指标和失败统计原则；
- “异常时停止，不偷偷放宽规则”的原则。

### 分开

- 执行和液体参数；
- 离线防晃轨迹；
- 执行状态匹配条件和恢复规则；
- 仿真冻结版本与实物冻结版本；
- 用于调参、独立验证和最终结论的数据。

任何一条线路只要根据验证结果改了模型或阈值，就必须生成新版本，并重新采集独立验证数据。

### 仿真无法代替实物的部分

以下内容不在仿真里伪造“已对齐”：

- RGB、Nokov、IMU 和 ROS 的多时钟偏差；
- Scout 在不同电量、载荷和地面下的真实延迟、死区和方向差异；
- 相机观察平面的有符号液面相位与 max-LCR 标定；
- 驱动器/CAN 的真实执行回执和现场安全边界。

仿真只复用它们的**数据结构、时间含义、双通道模型形式和失败关闭逻辑**。具体数值与正式结论必须留到实物重新标定和验证。

## 6. 暂时不做什么

- DualSPHysics/CFD；
- 动态障碍和在线重规划；
- 第二容器和大量路径；
- 鲁棒不变集、递归可行性等重理论扩展；
- 无法公平复现的外部防晃基线。

核心仿真和第一条实物路径通过后，再考虑第二冻结路径或可信的 input-shaping/fixed-profile 对照。
