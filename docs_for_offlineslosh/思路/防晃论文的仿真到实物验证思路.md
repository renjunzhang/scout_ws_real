## 0. 一眼看懂整个路线

```text
仿真和实物共用的准备工作
✅ 第1阶段  冻结可复现基线
   ↓
✅ 第2阶段  统一最终命令出口
   ↓
△  第3阶段  预计发布时间和双通道执行模型代码已完成，正式实车参数待标定
   ↓
✅ 第4阶段  在线周期显式选择时实际调用22维求解器，默认旧行为不变
   ↓
线路一：仿真，先完成
✅ 仿真1  建立最小独立C++“假Scout＋假液体”并通过smoke/pilot
△ 仿真2  已冻结开发参数候选v1；正式session仍未冻结
▶ 仿真3  生成仿真专用离线轨迹和接回尾段的held-out判断规则
○ 仿真4  完成C0–C4正式仿真
   ↓
仿真完成点
   ├→ 保留一篇只声称“仿真有效”的备用论文
   └→ 若继续冲击RA-L：进入实物线路
                    ↓
线路二：实物
○ 实物1  标定Scout、IMU和RGB
○ 实物2  完成实车基础验证
○ 实物3  重新生成实物专用轨迹和接回尾段的判断规则
○ 实物4  用实车参数重跑仿真，再做只观察、不控制的检查
○ 实物5  完成正式实物对比
   ↓
   ├→ 实物通过：形成带真实液面证据的RA-L稿件
   └→ 实物未通过：使用仿真备用稿，不声称真实液面降低
```

这里的核心关系是：

> **控制器代码和模型形式共用；仿真参数、实车参数、离线轨迹、恢复规则和正式数据分别冻结，不能混用。**

两条线路分别保留参数、轨迹和数据，但不是同时开工：**先完整做通仿真，再开始实物。**本文所说的“冻结”，就是把代码、参数和规则固定并记录下来，之后不能根据正式结果随意改动。

## 1. 为什么要分成两条线路

仿真和实物面对的“被控制对象”本来就不同：

| 内容           | 仿真线路                | 实物线路                     |
| -------------- | ----------------------- | ---------------------------- |
| 控制器内部代码 | 同一套 C++ 代码         | 同一套 C++ 代码              |
| 内部模型形式   | 同一套线/角双通道模型   | 同一套线/角双通道模型        |
| 内部模型参数   | 仿真版本参数            | 用实车数据辨识的参数         |
| 外部被控对象   | 独立的仿真 Scout 和液体 | 真实 Scout 和真实液体        |
| 离线防晃轨迹   | 按仿真参数生成          | 按实车参数重新生成           |
| 恢复判定规则   | 用独立仿真数据验证      | 用实车参数和独立数据重新验证 |
| 最终结论       | 方法在仿真中有效        | 真实液面是否降低             |

控制器内部模型要保持同一种含义，但参数不必相同。仿真中的“假 Scout＋假液体”反而不能与控制器内部模型完全一样，否则相当于控制器自己出题、自己判卷。

## 2. 共用准备第4阶段已经完成，但仍是正式 NO-GO

当前问题可以用一句话说明：

> 22维执行增广求解器已经由显式配置进入真实在线周期；当前缺口已经转为正式仿真资产，而不是在线 factory 接线。

本工作树已经闭合五件事：

1. 在线控制器能够选择并启动新的执行增广求解器；
2. 使用当前机器人状态、最终发布命令历史和两路命令队列构造每周期初态；
3. 补齐相对离线轨迹的正式目标、参数和在线修正边界；
4. 接入终端“能否重新接回防晃尾段”的判断，以及当前执行状态匹配条件；
5. 保持唯一最终命令出口和异常停止规则，完成在线闭环回归。

第 4 阶段完成条件：

- [x] 在线控制周期实际调用新求解器，而不是只在独立测试中运行；
- [x] 第一拍新命令按线、角各自延迟影响联合终点预测；
- [x] 命令历史不完整、时间异常或配置不匹配时拒绝正常控制；
- [x] 在线求解结果、终端判断、保存动作和最终发布命令可以完整追溯；
- [x] 受影响回归和 30 Hz 求解性能检查通过，并形成阶段记录。

新的 backend 仍是严格 opt-in：默认 `continuous_mpcc_acados`、`delay_augmented_phase/enabled=false`，且默认 recovery hash 为空，所以旧行为不变、误开启会被拒绝。独立 plant 与开发参数 v1 也已经建立，但正式 OfflineSloshOCP nominal/tail、held-out recovery artifact 和 C0--C4/IS 条件 runner 尚不存在，因此现在仍不能运行或宣称正式 C0--C4 结果。

## 3. 线路一：先把仿真完整做通

### 仿真1：建立独立的仿真 Scout 和液体

控制器发出最终命令后，仿真对象再独立模拟：

```text
最终命令
→ 线/角两路延迟
→ 响应惯性、增益、死区和饱和
→ Scout真实运动
→ 液体响应
```

仿真对象至少要允许参数偏差、噪声和时间抖动。液体仿真最好比控制器内部的低阶模型更复杂；如果暂时做不到，也必须改变参数并加入未建模误差，不能使用完全相同的方程和参数自证。

### 仿真2：冻结一次仿真实验

把一次仿真需要的内容固定下来：

- 代码版本；
- 仿真地图和路径；
- 控制器参数；
- 仿真 Scout 和液体参数；
- 启动、录包和分析程序；
- 失败规则和结果指标。

以后看到结果再调参数，就必须生成新的仿真版本，旧结果不能与新结果混在一起。

### 仿真3：生成仿真专用轨迹和恢复规则

根据仿真版本的执行参数生成完整离线防晃轨迹：

```text
运动 → 减速 → 抵消余晃 → 静置保持
```

恢复规则也只用仿真线路的数据建立，并用另一批完全没参与调参的数据检验。它只说明“在当前仿真范围内是否还能接回尾段”，不叫安全保证。

### 仿真4：完成C0–C4正式仿真

名义路径比较：

- C0 普通 MPCC；
- C1 与完整方法完成时间和平滑程度相近的普通控制器；
- C2 只回放离线防晃轨迹；
- C4 完整方法。

受控偏离比较：

- C3 允许在线修正，但不检查能否接回离线尾段；
- C4 完整方法。

同时改变延迟、液体频率和阻尼，检查结果是否稳定。**独立仿真液面必须下降**；控制器内部计算的液面只用于解释原因，并检查变化趋势是否一致。还要报告完成时间、路径误差、动作平滑性，以及控制器能否每秒运行 30 次且不超时。

### 仿真线路完成后得到什么

仿真线路完成后，至少留下一个完整、可复现的仿真研究：

> 考虑线/角差分执行延迟的相位重接控制，在独立底盘和液体仿真中降低了晃动，并减少了破坏离线防晃尾段的在线修正。

如果实物最终没有成功，这套结果可以独立整理成一般应用型控制或机器人论文。但只能声称“仿真中有效”，不能声称真实液面已经降低。

## 4. 线路二：仿真通过后再做实物

### 实物1：标定 Scout 和测量时间轴

使用最终容器、液位和载荷，记录最终发布命令、Nokov、odom、IMU 和 RGB，辨识：

- 线速度和角速度延迟；
- 响应惯性和增益；
- 死区、饱和和可能的方向差异；
- ROS、Nokov、IMU 和 RGB 的时间偏差。

### 实物2：完成实车基础验证

详细技术文档把这一步叫 `G0`。人话就是检查：

1. Scout 的执行延迟是否稳定；
2. 从读取状态到预测终点的整段预测是否足够准确；
3. 第一拍在线修正在实车上是否真的高于噪声；
4. IMU 和 RGB 的时间、幅值和相位是否可信。

四项全部通过，才是“可以继续”；任一项不通过就停止，先修正延迟、模型或传感器。这一步通过不代表防晃性能已经成功。

### 实物3：重新生成实物专用资产

实物线路继续使用相同控制器代码，但必须替换为实车参数，并重新生成：

- 实物专用离线防晃轨迹；
- 执行状态匹配条件；
- 恢复判定规则；
- 实物实验配置和版本记录。

仿真线路的轨迹和恢复规则不能直接拿来上车。

### 实物4：重跑仿真，再做只观察、不控制的检查

先用实车标定参数配置控制器，再重跑仿真，确认代码修改后仍然正向。外部仿真 Scout 和液体仍要保留独立的参数偏差与未建模误差，不能与控制器内部模型完全相同。随后在实车上只观察控制器判断、不让它实际控制车辆，确认接回尾段的判断、时间索引和最终命令记录正确。

这两项通过后，才允许正式实物实验。

### 实物5：正式实物对比

名义主实验：

- C0、C1、C2、C4；
- 使用同一路径、容器、液位、起始条件和安全限制；
- 主要比较独立 RGB 液面高度，同时检查完成时间和路径误差。

恢复实验：

- C3、C4；
- 只做预先审查过的小幅、可重复偏离；
- 大量危险或明显不可恢复的情况留在仿真和录包回放中。

最终防晃结论只由独立 RGB 实物结果给出，控制器内部液面只能解释原因。

## 5. 两条线路共用什么，必须分开什么

### 共用

- 控制器 C++ 代码和双通道模型形式；
- 最终命令出口和记录方式；
- C0–C4 的定义；
- 分析指标和失败统计原则；
- “异常时停止，不偷偷放宽规则”的原则。

### 分开

- 执行和液体参数；
- 离线防晃轨迹；
- 执行状态匹配条件和恢复规则；
- 仿真冻结版本与实物冻结版本；
- 用于调参、独立验证和最终结论的数据。

任何一条线路只要根据验证结果改了模型或阈值，就必须生成新版本，并重新采集独立验证数据。

## 6. 暂时不做什么

- DualSPHysics/CFD；
- 动态障碍和在线重规划；
- 第二容器和大量路径；
- 鲁棒不变集、递归可行性等重理论扩展；
- 无法公平复现的外部防晃基线。

核心仿真和第一条实物路径通过后，再考虑第二冻结路径或可信的 input-shaping/fixed-profile 对照。

## 7. 代码中几个英文词的人话解释

| 代码中的词                 | 人话解释                                         |
| -------------------------- | ------------------------------------------------ |
| `plant`                  | 仿真中的“假 Scout＋假液体”                     |
| `delay-augmented solver` | 考虑真实执行延迟的在线优化器                     |
| `session`                | 一次实验的完整配置单                             |
| `runner`                 | 按配置单启动控制器、传感器和录包的程序           |
| `B_exec`                 | 当前命令队列和底盘响应能否接回离线轨迹的条件     |
| `held-out gate`          | 用完全独立的数据检验过的恢复判定规则             |
| `release`                | 代码、参数、轨迹和分析方法都固定的实验版本       |
| `G0=GO`                  | 实车基础验证通过，允许继续；不是防晃效果已经成功 |
