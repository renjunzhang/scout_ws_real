\section{Release Status and Freeze Rule}

This fragment records configuration, validation, and analysis fields for the
target \PRSMPCC{} release. It contains no formal performance result. A
\Pending{} entry is neither a pass nor permission to acquire confirmation data.
The current physical \texttt{enforce} status is \NoGo{} because the unequal-delay
causal-front blocker B0 remains open and G3 lacks a formal execution-compatibility
set and an independent held-out gate test.

One release identifier binds the Git commit, build products, runner, controller
configuration, path and frame hashes, execution and liquid models,
\OfflineSloshOCP{} artifact, gate objects, measurement chain, condition
definitions, randomization, and analysis specification:
\begin{align}
  \text{release ID} &= \text{\Pending},\\
  \text{freeze-manifest SHA-256} &= \text{\Pending}.
\end{align}
Changing any bound object creates a new release. Data from releases with
different contracted objects are not pooled.

\section{Gate Construction, Compatibility, and Data Separation}

The 9-D gate is evaluated only inside the execution-compatibility set. For the
diagonal empirical representation used by the target formulation,
\begin{equation}
  m_i(e)=\sum_r\left(\frac{e_r}{\rho_{r,i}}\right)^2,
  \qquad
  m_i(e)\leq1,
\end{equation}
with phase radii $\rho_{r,i}=\text{\Pending}$. The joint online terminal condition also
requires $e^{\mathrm{exec}}\in\mathcal B_i^{\mathrm{exec}}$. Samples outside
$\mathcal B_i^{\mathrm{exec}}$ are contract rejections and are not silently
counted as 9-D classifier errors.

The primary held-out gate diagnostic is the conditional false-safe fraction
\begin{equation}
  r_{\mathrm{FS}|\mathrm{A}}
  =\frac{N(\mathrm{gate\ accept}\cap\mathrm{recovery\ fail})}
  {N(\mathrm{gate\ accept})},
\end{equation}
which estimates $P(\mathrm{recovery\ fail}\mid\mathrm{gate\ accept})$ and is
undefined when no sample is accepted; zero coverage is then reported explicitly.
Its estimate and interval are \Pending. False rejection, normal-operation coverage,
compatibility-set rejection, and the worst phase are reported alongside it.

\section{Development Provenance and Claim Boundary}

Development simulations, branch-coverage tests, no-motion trials, parameter
selection, gate construction, and pilots are archived with their data role,
release/configuration hash, date, path, container/fill, measurement version,
selection decision, and rejection reason. They do not contribute observations
to $D_{\mathrm{main,confirm}}$ or $D_{\mathrm{recovery,confirm}}$.

The final evidence remains limited to frozen-path tracking in a static,
obstacle-clear workspace, the contracted Scout execution range, the reported
container/fill and low-order liquid-model range, and the observed empirical-gate
coverage. Independent RGB determines physical anti-slosh performance. Internal
liquid states, IMU and an online slosh monitor are supporting signals only. The
stored action is phase indexed rather than a feedback recovery law, and no
recursive-feasibility, robust-recovery, spill-free, online-obstacle-avoidance, or
true signed-liquid-phase claim is made.
