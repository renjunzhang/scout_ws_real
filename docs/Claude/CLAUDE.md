# CLAUDE.md

## 1. 编码前先思考

**不要假设。不要掩盖困惑。明确指出取舍。**

在实现之前：

- 明确说明你的假设。如果不确定，就提问。
- 如果存在多种理解，列出来——不要默默选择其中一种。
- 如果存在更简单的方法，要说明。必要时应提出反对意见。
- 如果某件事不清楚，就停下来。说明哪里令人困惑，并提问。

## 2. 简洁优先

**用能解决问题的最少代码。不要做推测性实现。**

- 不添加超出需求的功能。
- 不为一次性代码设计抽象。
- 不添加未被要求的“灵活性”或“可配置性”。
- 不为不可能出现的场景编写错误处理。
- 如果你写了 200 行，但本可以用 50 行完成，就重写。

问问自己：“一位资深工程师会不会认为这过度复杂？”如果答案是会，就简化。

## 3. 外科手术式修改

**只改必须改的地方。只清理你自己造成的问题。**

编辑已有代码时：

- 不要“顺手改进”相邻代码、注释或格式。
- 不要重构没有坏掉的东西。
- 遵循现有风格，即使你会用不同方式实现。
- 如果发现无关的死代码，可以提出来——不要删除它。

当你的修改产生孤立代码时：

- 删除因你的修改而变得未使用的 import、变量或函数。
- 不要删除原本就存在的死代码，除非被要求这样做。

检验标准：每一行被修改的代码，都应该能直接追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。完成与改动风险相称的验证。**

将任务转化为可验证的目标：

- “添加校验” → “为非法输入编写测试，然后让测试通过”
- “修复 bug” → “编写能复现该 bug 的测试，然后让测试通过”
- “重构 X” → “确保重构前后测试都通过”

对于多步骤任务，给出简短计划：

```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强成功标准能让你独立循环推进。弱成功标准（如“让它能用”）则需要不断澄清。若实物、设备或现场条件暂时不可用，清楚记录“尚未验证”和缺少的证据即可，不要把它误写成实现失败。

## 5. 数学公式格式

**面向 Obsidian 编写数学公式。块级公式使用独占行 `$$`。**

- 数学公式、推导、变量定义优先使用 Obsidian 原生块级 LaTeX。
- `$$` 必须独占一行，公式内容放在中间，不要写成行内 `$$...$$`。
- 不要把块级公式放进 Markdown 表格；表格中用反引号文本表示公式。
- 简单变量名可以用反引号，例如 `eta_bar`、`Q_slosh_eta`。

推荐：

```text
$$
\omega_n=\sqrt{\frac{g\xi}{R}\tanh\left(\frac{\xi h}{R}\right)}
$$
```

避免：

```text
行内 $$\omega_n=...$$
| 指标 | $$\eta_{\lim}$$ |
```

## 6. 实物实验门禁：按风险分级

**门禁用于防止危险和错误归因，不用于追求不现实的“每次数据都完美”。**

实物系统存在定位噪声、网络抖动、液体未完全静止和传感器偶发丢帧。不要把所有阈值都设计成硬阻断，也不要因为单次 postflight 指标不好就把一次安全完成的试验笼统判成“失败”。门禁分为三类：

### 6.1 安全硬门禁

以下条件不满足时禁止启动运动，运行中触发时应停车：

- 操作者未明确解锁运动、急停不可用、场地或终点没有净空；
- 硬限速未生效，或运行参数超出本次确认的安全范围；
- 控制必需的定位、状态或命令链路失效、严重过期；
- 实际加载的路径、地图、算法条件与准备执行的试验明显不一致；
- 已知故障可能造成车辆失控或无法可靠停车。

安全硬门禁不能因为“只是 development”而绕过。

### 6.2 证据有效性门禁

关键 topic 缺失、bag 不完整、试验行号或配置不符、相机/NOKOV 数据不足等问题，通常影响的是“这包数据能否用于回答问题”，不一定意味着车辆不能安全运动。

- 能在运动前发现时先修复；若不影响安全，也可由用户确认后作为诊断试跑继续。
- 运行后才发现时保留 bag，标记为 `development`、`diagnostic_only` 或“不可用于正式统计”，不要自动删除。
- 一个证据通道失效，只否定依赖该通道的结论，不自动否定同包其他有效证据。

### 6.3 质量告警与效果指标

起点存在小误差、频率轻微抖动、RGB 少量异常点、单包 P95/RMS 未达预期、跟踪效果较差等，默认作为告警和分析结果，不作为开发试验的自动停止条件。

- 阈值应来自设备能力、历史数据或明确冻结的方案，不能凭感觉不断收紧。
- 优先使用容差范围、连续超限时长和重复试验统计，避免单帧或瞬时越界触发失败。
- 算法效果差是需要保留的负结果；只要安全和基本证据成立，就应允许完成并进入分析。
- 只有用户明确开始“正式冻结试验”时，才执行方案预注册的严格有效性门和停止规则。

开发试跑、诊断采集和正式验证必须明确区分。开发阶段允许“带告警通过”；正式结果不能用放宽后的 development 标准冒充。

## 7. 项目兼容性红线

以下接口默认保持兼容，不要在无关任务中顺手修改：

- `/mpc/cost_breakdown` 21 字段 layout（analysis 脚本 + RGB 流程依赖）
- `/slosh/*` `/terminal/*` `/reference/*` `/profile_cap/*` topic 名
- `slosh_experiment*.launch` 的 arg 名（验证方案 20+ 处命令引用）
- terminal d200 参数

如果用户的目标确实要求修改这些接口，可以改，但要先列出生产者、消费者和实验脚本，提供兼容或迁移方案，并只运行与修改范围相符的验证。

## 8. 修改后的验证范围

**验证应与改动风险相称，不要求每次修改都通过整套工程和实物门禁。**

- 只改文档：重读修改章节并运行 Markdown/diff 检查。
- 只改离线分析：运行相关脚本的语法检查、单元测试或小样本回放。
- 修改 `scout_local_planner` 编译代码：运行 `catkin_make --pkg scout_local_planner` 和直接相关测试。
- 修改路径、goal、terminal 或闭环行为：再运行相关 smoke；只有涉及 terminal d200 时才要求重跑对应 terminal smoke。
- 实物运动验证：由用户明确启动，在安全硬门禁通过后执行；非安全告警不应擅自升级为禁止运动。
- 阶段性完成或用户要求时，再记录到 `docs/Claude/修改日志-时间/<日期>.md`；不要求每个微小编辑都新建日志。

若某项验证受设备、ROS 进程或现场条件限制，应明确写成“尚未验证”和原因，不要把它混写成代码失败，也不要为了凑齐门禁擅自启动实物。

- 仿真笔记：`docs/重要文档/仿真笔记.md`
