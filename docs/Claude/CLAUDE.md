# CLAUDE.md

## 1. 编码前先思考

**不要假设。不要掩盖困惑。明确指出取舍。**

在实现之前：
- 明确说明你的假设。如果不确定，就提问。
- 如果存在多种理解，列出来——不要默默选择其中一种。
- 如果存在更简单的方法，要说明。必要时应提出反对意见。
- 如果某件事不清楚，就停下来。说明哪里令人困惑，并提问。

## 2. 简洁优先

**用能解决问题的最少代码。不要做推测性实现。**

- 不添加超出需求的功能。
- 不为一次性代码设计抽象。
- 不添加未被要求的“灵活性”或“可配置性”。
- 不为不可能出现的场景编写错误处理。
- 如果你写了 200 行，但本可以用 50 行完成，就重写。

问问自己：“一位资深工程师会不会认为这过度复杂？”如果答案是会，就简化。

## 3. 外科手术式修改

**只改必须改的地方。只清理你自己造成的问题。**

编辑已有代码时：
- 不要“顺手改进”相邻代码、注释或格式。
- 不要重构没有坏掉的东西。
- 遵循现有风格，即使你会用不同方式实现。
- 如果发现无关的死代码，可以提出来——不要删除它。

当你的修改产生孤立代码时：
- 删除因你的修改而变得未使用的 import、变量或函数。
- 不要删除原本就存在的死代码，除非被要求这样做。

检验标准：每一行被修改的代码，都应该能直接追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环推进，直到验证通过。**

将任务转化为可验证的目标：
- “添加校验” → “为非法输入编写测试，然后让测试通过”
- “修复 bug” → “编写能复现该 bug 的测试，然后让测试通过”
- “重构 X” → “确保重构前后测试都通过”

对于多步骤任务，给出简短计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强成功标准能让你独立循环推进。弱成功标准（如“让它能用”）则需要不断澄清。

## 5. 数学公式格式

**面向 Obsidian 编写数学公式。块级公式使用独占行 `$$`。**

- 数学公式、推导、变量定义优先使用 Obsidian 原生块级 LaTeX。
- `$$` 必须独占一行，公式内容放在中间，不要写成行内 `$$...$$`。
- 不要把块级公式放进 Markdown 表格；表格中用反引号文本表示公式。
- 简单变量名可以用反引号，例如 `eta_bar`、`Q_slosh_eta`。

推荐：

```text
$$
\omega_n=\sqrt{\frac{g\xi}{R}\tanh\left(\frac{\xi h}{R}\right)}
$$
```

避免：

```text
行内 $$\omega_n=...$$
| 指标 | $$\eta_{\lim}$$ |
```
