> 时间范围：2026-04-17 ~ 2026-04-18

## 0. 这段时间干了什么

简单说：发现 MPC 大部分时间在爬行，而且液体晃动抑制几乎没有起作用，然后把根因一层层扒开修掉了。

问题链条不是一开始就全看清的，是跑了七八条 bag 才逐步拼出来的。最终定位到两个根本性问题：

1. **MPC 频繁 OSQP -3（不可行）**，原因是局部几何送进了病态数据，以及 u_prev 冻结导致约束结构性矛盾。

2. **速度剖面被执行层限速反复重算**，导致全局规划的速度从来没真正生效，机器人长期以 v < 0.15 m/s 爬行，横向加速度几乎为零，liquid anti-slosh cost 基本没有进入有效工作区。

下面把这两件事分开讲。

---

## 1. MPC 可行性修复链

### 1.1 病态局部几何

**现象**：日志里大量 `fitLocalSpline failed: pathological geometry rejected`，或者 MPC 送进去的 `kappa=27.79, omega_ref = v × kappa = 4.6 rad/s >> omega_max`。

**根因**：`PathHandler` 从 `global_points_map_` 取局部窗口，该缓存是原始清洗版（sanitize + resample），没有平滑。路径在 resample spacing 尺度下的正常弯道仍然会给出过大的 kappa 估计，localSpline 拟合后经 cubic 导数放大，最终送进 MPC 的几何数据直接超出约束可行域。

**修复**：

1. `updateGlobalPath()` 时额外生成一份平滑缓存 `global_points_map_smooth_`（最多 4 轮迭代 bspline→resample→sanitize→去单点尖刺）。

2. `getReferencePoints()` 的取点来源从 `global_points_map_` 切换到 `global_points_map_smooth_`（当 `global_smooth_valid_` 时）。

3. 局部窗口不再重复做 B-spline 平滑（smooth cache 已经做过了，双重平滑会再次放大）。

4. `fitLocalSpline()` 改为先降采样到较稳的拟合间距（约 0.08~0.12 m），再做 cubic spline 拟合，避免稠密点列放大曲率。

**阈值调整**：`fitLocalSpline` 的病态拒绝阈值从 `kappa>20 || dkappa>200` 放宽到 `kappa>30 || dkappa>500`。原阈值是针对原始路径（kappa~68, dkappa~2380）设计的，smooth cache 输出（kappa~17, dkappa~339）会被误判为病态。

---

### 1.2 omega_max 约束缺失

**现象**：日志 `kappa=10.26, v_des=0.25, omega_ref=0.25×10.26=2.57 rad/s > omega_max=2.0`，OSQP 直接报 PRIMAL INFEASIBLE。

**根因**：原来的曲率限速只考虑横向加速度约束：

$$v_{\text{cap,kappa}} = \sqrt{\frac{a_{\text{lat,max}}}{\kappa}}$$

没有把 $\omega_{\max}$ 硬约束也纳进来：

$$v_{\text{cap,omega}} = \frac{\omega_{\max}}{\kappa}$$

两个 cap 都要满足才能保证 MPC 约束可行，但代码只有第一个，第二个缺失了。而且即使第一个 cap 存在，它还有一个 `min_speed` 下限兜底（当时设为 0.25 m/s），在高曲率段会把 cap 架空。

**修复**（`local_planner_ros.cpp`）：

```cpp
const double v_cap_kappa = sqrt(max(0.0, max_lat_accel / kappa));
const double v_cap_omega = omega_max / kappa;          // 新增
const double v_cap_geom  = min(v_cap_kappa, v_cap_omega);
// 若几何限速本身低于 min_speed，降速优先，不再兜底
const double v_floor = min(tracking_curvature_min_speed_, v_cap_geom);
v_curve_cap = min(v_curve_cap, max(v_floor, v_cap_geom));
```

dkappa 限速同样有 `min_speed` 下限把实际 cap 架空的问题，也一并修掉：允许 dkappa cap 结果低于 min_speed。

---

### 1.3 u_prev 冻结

**现象**：参考路径几何已经完全正常（`/mpc/reference_path max_kappa = 0.73`），但 OSQP -3 仍然持续 140 拍，日志：

```
fail_streak=0,  u_prev=(-0.444, 0.552)
fail_streak=10, u_prev=(-0.444, 0.552)
fail_streak=140,u_prev=(-0.444, 0.552)   ← 一直没动
实际机器人: omega ≈ 0（已停止转向）
```

**根因**：MPC 失败时，代码发布 fallback 速度（v→0, omega→0），但 `last_control_` 不更新，停留在最后一次成功解的值。

alpha 约束是：

$$|\omega_k - \omega_{\text{prev}}| \le \alpha_{\max} \cdot \Delta t$$

`omega_prev` 被冻结在 0.552，而机器人已经停转，实际 omega 接近 0。这迫使 MPC 的 $\omega_0$ 下界为：

$$\omega_0 \ge 0.552 - 4.0 \times 0.1 = 0.152 \text{ rad/s}$$

但参考值 $\omega_{\text{ref},0} = v \times \kappa = 0.038 \times 0.741 = 0.028$ rad/s，两者差距过大，QP 结构性不可行。

**修复**（`local_planner_ros.cpp`）：MPC 失败后同步更新 `last_control_`：

```cpp
publishCmdVel(v, omega);
last_control_(A) = abs(current_v_) > 1e-3 ? (v - current_v_) / dt : 0.0;
last_control_(OMEGA) = omega;   // fallback omega，随失败次数逐步衰减到 0
```

这样每次 fail 后 `omega_prev` 随 fallback 逐步下降，alpha 约束的下界也随之回落，MPC 恢复可行。

---

### 1.4 可行性保护层（Feasibility Guard）

上面 1.1~1.3 处理的都是"几何或约束结构本身导致的不可行"。除此之外，还加了一层外层保护，防止 v 过高时 QP 本身就进入危险区：

- `fail_streak ≥ 3`：`v_des_cmd` 限到 0.5 m/s
- `fail_streak ≥ 6`：`v_des_cmd` 限到 0.3 m/s
- 连续成功 5 次后释放

另外，路径切换或 `TRACKING` 重进入时，加 10 步（起点曲率过高时翻倍到 20 步）的低速爬升 ramp，避免一拍恢复高速再次触发不可行。

## 2. 速度剖面重构

这是当前这段时间里改动最大、影响最深的部分。

### 2.1 问题：全局速度剖面从来没真正生效

**现象**：bag 诊断显示 `v < 0.15 m/s` 占 70.7% 时间，`v < 0.30 m/s` 占 90%。而全局速度剖面计算出的 `v_geom_min = 0.386 m/s`，全局 `v_profile` 均值 = 0.810 m/s。两者严重矛盾。

**根因**：`getReferencePoints()` 内部有如下触发逻辑：

```cpp
if (params_.time_parameterize &&
    (!speed_profile_valid_ || std::abs(v_des - speed_profile_v_des_) > 1e-3)) {
    updateSpeedProfile(v_des);  // v_des 就是 v_des_cmd
}
```

而 `v_des_cmd` 在进入 `getReferencePoints()` 之前，已经被局部 reactive cap 压低到 0.07~0.10 m/s。

执行链条：

```
① v_nominal = 1.6 m/s
② v_des_cmd = min(v_nominal, v_cap_kappa_local) ≈ 0.07~0.10 m/s
③ getReferencePoints(v_des_cmd=0.10)
④ |v_des - v_stored| > 0.001 → updateSpeedProfile(v_des=0.10)
⑤ 全局速度剖面按 v_des=0.10 重新规划，所有 v_ref 截断到 ≤0.10 m/s
⑥ MPC 收到 v_ref=0.10，忠实跟踪
```

实质：每次局部 cap 改变 v_des_cmd，就会触发全局速度剖面重算，规划层名义速度从未稳定主导整条路径。

### 2.2 修复：规划速度与执行速度分层

`getReferencePoints()` 接口从：

```cpp
getReferencePoints(..., v_des, ref_points)
```

改为：

```cpp
getReferencePoints(..., v_exec, v_plan, ref_points)
```

- **`v_plan`**：只用于 `updateSpeedProfile(v_plan)`，始终取 `v_nominal`，不随局部 cap 变化。
- **`v_exec`**：只用于当前周期 v_ref 的执行层上界裁剪，取 `v_des_cmd`。

内部逻辑变为：

```cpp
// 仅在路径实质变化时重算速度剖面
if (!speed_profile_valid_ || abs(v_plan - speed_profile_v_des_) > 1e-3) {
    updateSpeedProfile(v_plan);   // 始终用 nominal
}
// 取剖面速度，但不超过执行层上界
double v_ref = getSpeedAtS(s_progress);
v_ref = min(v_ref, v_exec);      // 执行层 cap 仍生效
```

这样，局部 cap 只影响当前周期参考速度的上界，不会反向把整条 v(s) 重写成低速版本。

### 2.3 速度剖面几何来源的问题

速度剖面计算 `v_geom(s)` 需要 $\kappa(s)$ 和 $\kappa'(s)$。原来的做法是从 `global_spline_.evaluateKappa(s)` 取 cubic spline 的一阶、二阶导数。

实测发现，cubic spline 对曲率变化率有约 4 倍的放大效应：

| 来源 | kappa | dkappa |
|---|---|---|
| smooth cache 窗口点估计 | ~13 | ~253 |
| cubic spline 输出（`/mpc/reference_path`） | ~18 | ~807 |

这意味着速度剖面在计算 alpha 约束限速 $v \le \sqrt{\alpha_{\max}/\kappa'}$ 时，用的 $\kappa'$ 比真实路径几何大了好几倍，整条速度剖面被系统性压低。

**修复**：`updateSpeedProfile()` 改为从 `global_points_map_smooth_` 取离散几何，用相邻点有限差分估计 $\kappa$ 和 $\kappa'$，不再用 cubic spline 导数。

同时，速度剖面的几何采样进一步粗化：先重采样到 `profile_geom_spacing = max(0.10, 2 × speed_profile_ds)`（约 0.10~0.15 m），再在这条更粗的规划几何上计算曲率。速度规划不应对 5cm 级的局部微小波动敏感，否则 alpha 限速长期主导。

### 2.4 速度剖面三约束结构

当前 `updateSpeedProfile()` 的几何速度 $v_{\text{geom}}(s)$ 综合三个来源：

$$v_{\text{geom}}(s) = \min\left(v_{\text{nom}},\ \sqrt{\frac{a_{\text{lat,max}}}{\kappa}},\ \frac{\omega_{\max}}{\kappa},\ \sqrt{\frac{\alpha_{\max}}{|\kappa'|}}\right)$$

其中后三项分别对应：

- **横向加速度约束**：$v^2 \kappa \le a_{\text{lat,max}}$
- **角速度约束**：$v \kappa \le \omega_{\max}$（新增）
- **角加速度约束**：$v^2 |\kappa'| \le \alpha_{\max}$（几何来源修复后量级正常）

在 $v_{\text{geom}}(s)$ 基础上，再做前向/后向梯形遍历：

$$v_{\text{back}}(s) = \min\left(v_{\text{geom}}(s),\ \sqrt{v_{\text{back}}^2(s+\Delta s) + 2 a_{\max} \Delta s}\right)$$

$$v_{\text{final}}(s) = \min\left(v_{\text{back}}(s),\ \sqrt{v_{\text{final}}^2(s-\Delta s) + 2 a_{\max} \Delta s}\right)$$

最终得到在弯前充分减速、弯后梯形加速的 v(s) 剖面。

### 2.5 实验结果对比（仿真）

修复前（reactive cap 主导，v_plan 从未生效）：

- `v < 0.15 m/s` 占 70.7%
- `v < 0.30 m/s` 占 90%
- `a_lat = v · |ω|`：均值约 0.048 m/s²

修复后（test7 基线，v_plan 解耦，几何来源修复）：

- 速度剖面 `kappa_max ≈ 4.8~6.1`（原来 26~54）
- 速度剖面 `dkappa_max ≈ 18.9~25.3`（原来 275~523）
- `v_geom_min ≈ 0.33~0.42 m/s`（弯道段理论下界）
- 近终点/terminal recovery 段仍偏慢（see §4）

## 3. 当前系统速度剖面流程（test7 基线）

完整的速度参考生成链条，从上游路径到 MPC 输入：

```
① /scout/global_path 接收

② updateGlobalPath()：
   - sanitize + resample + spike removal → global_points_map_（原始清洗版）
   - 4 轮迭代 bspline → global_points_map_smooth_（平滑缓存）
   - global_spline_ 优先使用 smooth cache 几何

③ 控制周期内：
   v_exec = min(v_nominal, v_cap_feas_guard, v_cap_omega_local, ...)
   v_plan = v_nominal（固定，不随 cap 变化）

④ getReferencePoints(v_exec, v_plan)：
   - 仅在 |v_plan - v_stored| > 1e-3 时重算 updateSpeedProfile(v_plan)
   - updateSpeedProfile：
       从 smooth cache 取离散几何，粗化采样（~0.10 m）
       计算三约束 v_geom(s)：a_lat / omega / alpha
       前向/后向梯形遍历
   - v_ref[i] = min(getSpeedAtS(s_i), v_exec)

⑤ MPC 收到 ref_points[i]（含 v_ref, kappa, x, y, theta_path）
   求解 OSQP QP，输出 a, omega
```

局部 reactive cap（`v_cap_omega_local`）当前角色：应急安全哨兵，正常弯道由全局剖面保证，极端几何突变时才介入。

## 4. 当前残余问题

### 4.1 near-goal / TERMINAL_LATCHED 偏保守

**现象**：仿真中，短路径任务（终点占比高）的整体速度被 near-goal 阶段拖慢，`TERMINAL_LATCHED` 进入后速度明显偏低，持续时间偏长。

**当前判断**：这更像 terminal recovery 设计偏保守，而不是 tracking MPC 主约束问题。

**当前决策**：不在仿真中继续修，等实物测试结论：
- 若实物中不复现 → 归类为仿真侧偏保守现象
- 若实物中同样复现 → 优先检查 `terminal_enter_distance / terminal_v_max` 参数，先做参数级修正

### 4.2 slosh cost 实际有效区间仍需验证

修复后弯道段 `v_geom_min ≈ 0.39 m/s`，预期 `a_lat = v² × κ ≈ 0.39² × 5.18 ≈ 0.79 m/s²`，slosh cost 才真正进入有效工作区（修复前均值约 0.048 m/s²，差距约 16 倍）。

但这个结论来自仿真速度剖面分析，实物上速度是否真的能维持在这个水平，还需要实物 bag 验证。

### 4.3 实物 sim-to-real gap 未知

当前所有结论都基于仿真。实物上可能有：

- 地面摩擦导致速度响应与模型不符
- IMU ay bias 行为与仿真不同
- 路径几何在实物导航下的实际曲率分布与仿真不同

新增或改进的诊断脚本：

- `scripts/diagnose_speed_profile.py`：对单条 bag 输出全局平滑路径的曲率统计、几何约束下各项 `v_geom_min`、实际 cmd_vel 速度分布、局部 cap 是否仍在主导的判断。

### 速度剖面相关（path_handler）

| 参数 | 当前值 | 语义 |
|---|---|---|
| `speed_profile_omega_max` | 取 `vehicle/omega_max = 2.0 rad/s` | 速度剖面规划用 ω 约束（独立，可覆盖） |
| `speed_profile_alpha_max` | 取 `vehicle/alpha_max = 4.0 rad/s²` | 速度剖面规划用 α 约束（独立，可覆盖） |

| `max_tan_decel` | 2.0 m/s² × 0.8（内部折减） | 后向遍历减速约束 |

`speed_profile_omega_max` / `speed_profile_alpha_max` 可在 YAML 中显式配置（`path_handler/speed_profile_omega_max`），不配置时退回 `vehicle/*`。配置存在时，规划层与 MPC 内层的 alpha 约束可独立设置，避免双重保守。
