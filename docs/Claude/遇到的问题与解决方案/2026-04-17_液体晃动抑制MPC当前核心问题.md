# 2026-04-17 液体晃动抑制 MPC 当前核心问题与对应解决方案

## 1. 对应问题摘要

对应问题文件：

- `/home/a/scout_ws/docs/Claude/遇到的问题与解决方案/2026-04-17_液体晃动抑制MPC当前核心问题.md`

当前系统的核心问题，不是“液体晃动抑制有没有接上”，而是：

**在带有 slosh 增广状态的 tracking MPC 中，高曲率路径、较高参考速度、路径切换/重进入，以及输入变化率硬约束共同作用时，TRACKING 阶段的 QP 可行性仍不够稳定，尤其体现在 S 弯和狭窄路段。**

补充判断：

- 当前 `Q_slosh_eta * (eta_x^2 + eta_y^2)` 属于 **soft cost**，它会改变优化偏好，但不会直接把“约束系统”变成无解。
- `OSQP status = -3` 在当前语境下应优先理解为：**当前 tracking 阶段的硬约束系统失去可行性**，而不是“soft slosh cost 太大”。
- `REACHED / IDLE` 段 stale `status_val` 污染问题已经识别并修复，因此当前主要矛盾已经进一步收敛到 `TRACKING` 阶段。
- 当前实验还暴露出一个新的结构问题：**局部 reactive curvature cap 正在压制全局速度剖面 `v(s)`**。  
  其结果是：弯道阶段长期低速爬行，`omega` 约束、横向激励与 slosh cost 在大部分时段没有进入有效工作区。

因此，对应解决方案不能继续停留在：

- `Q_slosh`
- `gamma`
- `rho_0`
- `beta`
- `settling_tol`

这类单参数微调上，而应从控制结构上处理。

## 2. 结合当前 MPC 结构的理解

根据 `/home/a/scout_ws/docs/重要文档/mpc_数学化架构总结.md`，当前控制器不是普通的路径跟踪器，而是一个 **8 维增广 tracking MPC**：

- Frenet 跟踪子系统：`e_l, e_c, e_theta, v`
- 液体晃动子系统：`eta_x, eta_dot_x, eta_y, eta_dot_y`

控制量为：

- `a`
- `omega`

当前每个周期求解的是 successive linearization 后得到的 **affine time-varying QP**。  
QP 内同时耦合了：

### 目标函数层

- 路径跟踪误差代价
- 速度跟踪误差代价
- 控制量代价
- 控制变化率代价
- liquid anti-slosh 软代价 `Q_slosh_eta * (eta_x^2 + eta_y^2)`

### 约束层

- 动力学等式约束
- `v / a / omega` 边界
- `Δa / Δomega` 硬约束
- 可选 slosh modal proxy 盒约束

因此当前系统已经不是“导航 + 一个液面观测量”，而是：

**路径跟踪目标、控制平滑目标、液体晃动抑制目标共同耦合在一个 tracking QP 中的控制器。**

这也是为什么一旦路径几何变激烈，系统会表现出：

- 既要快走
- 又要平滑
- 还要少晃

最终在某些工况下把 QP 推到不可行。

## 3. 当前问题的工程本质

当前问题的本质可以概括为：

**液体晃动抑制主线已经接入，但它尚未建立在一个对复杂路径足够鲁棒的 tracking MPC 底座之上。**

更具体地说，当前主要矛盾不是：

- slosh 模型没接上
- risk scheduler 没工作
- settling 判据没写出来

而是：

- 在高曲率路径、S 弯、狭窄路段、replan 后路径重进入这些场景里，
- tracking 参考仍可能偏激进，
- 与 `Δa / Δomega` 等硬约束叠加后，
- QP 的硬可行域被压没，
- 进而导致连续 `OSQP -3`。

所以当前阶段最应该先解决的，不是“如何进一步增强 anti-slosh 强度”，而是：

**如何先让 tracking 底座在复杂路径下仍然稳定有解。**

只有在这个前提下，liquid anti-slosh 的收益才可能稳定体现出来。

需要补充一条当前阶段的工程判断：

**如果局部 reactive cap 长期压住全局速度剖面，那么即使 MPC 每拍都求解成功，系统也可能只是在大部分时间里低速爬行，无法让弯道阶段本应生效的 `omega` 约束、横向激励和 slosh 代价真正起作用。**

## 4. 解决思路总览

总体策略改为：

**把“可行性保障”从单个 QP 的内部优化偏好中剥离出来，变成外层显式保护；内层增广 MPC 则在较保守的参考下继续做 tracking 与 liquid anti-slosh 优化。**

即系统从：

**所有目标直接耦合在一个 QP 中**

调整为：

1. 外层可行性层先处理：
   - 高曲率
   - 连续 solve fail
   - 路径切换 / 重进入
2. 外层风险层再基于 slosh 风险调低参考速度
3. 内层增广 MPC 在更可跟踪的参考下继续做：
   - 路径跟踪
   - 控制平滑
   - 液体晃动抑制

这不是取消 liquid anti-slosh，而是把它建立在一个更鲁棒的 tracking 底座上。

当前系统本来就是 tracking MPC，不是 MPCC；参考路径和 `v_ref` 由 `PathHandler` 内部生成。因此从结构上优先修改：

- 参考层
- 可行性保护层
- 重进入/切换层

需要补充一个当前实现判断：

**继续单纯扩大 `PathHandler` 前段窗口补丁范围，不是合理主路。**

原因是已经观察到：

- 一开始失败在 `start=0`
- 补丁扩展后，失败被推迟到 `start=7/9`
- 再往后又被推迟到 `start=21/25`

这说明问题不是“补丁范围还不够大”，而是：

- 上游长路径前段本身存在一段持续的高曲率 / 高曲率变化率区域
- 同时 `REACHED -> TRACKING` 入口速度也偏激

因此，前段窗口补丁只能作为定位和短期止血手段，不能继续作为长期主方案。

比继续给同一个 QP 堆目标更合理。

## 5. 结构性解决方案

### 5.1 第一层：TRACKING 可行性保护层

这是第一优先级。

它的目标不是“让液面更稳”，而是先保证：

**在路径几何复杂、参考速度偏高、硬约束偏紧时，tracking MPC 仍能持续给出可行解。**

#### 5.1.1 连续 solve fail 降速保护（Feasibility Governor）

在 `TRACKING` 阶段增加显式的可行性保护逻辑。

触发条件：

- 当前状态为 `TRACKING`
- 连续出现 `OSQP primal infeasible` / 连续 `status_val=0`
- 连续失败次数达到阈值，例如 `3~5` 次

触发动作：

- 临时降低 `v_des_cmd`
- 例如先降到 `0.5 m/s`
- 若继续失败，再降到 `0.3 m/s`
- 并重新生成 `ref_points`
- 而不是只在输出端缩放 `/cmd_vel`

退出条件：

- 连续求解成功若干次，例如 `5~10` 次
- 且当前路径曲率、tracking 误差恢复到正常范围

释放方式：

- 不一步恢复到原始 `v_des_cmd`
- 而是线性或指数缓慢释放
- 防止刚恢复成功后一拍又被推回 infeasible 区

这一步的本质是给 tracking 层增加一个 **feasibility governor**，解决当前最明显的不合理现象：

- 小车已经接近不动
- 但 `v_des` 仍维持在 `1.4~1.5 m/s`
- 控制器还在硬解一个已经不可行的 tracking QP

#### 5.1.2 曲率相关参考速度上限（Curvature-Aware Reference Cap）

当前高曲率/狭窄段下的关键问题之一，是 `v_ref` 仍偏高。

因此，参考速度约束应更早进入参考生成层，而不是等 QP 内部被动承受。

建议在 `PathHandler` 生成 `v_ref` 时就加入更强的路径几何约束：

- 按 `|kappa|` 限速
- 同时按 `|Δkappa|` 或“曲率翻转强度”限速

需要特别强调：

**S 弯的问题不只是“大曲率”，更是“曲率快速翻转”。**

这会带来：

- `omega_ref = v_ref * kappa` 快速反向
- `Δomega` 硬约束更容易与参考冲突
- tracking QP 更容易 infeasible

因此，速度帽建议从：

- 仅依赖 `|kappa|`

升级为：

- 同时依赖 `|kappa| + |Δkappa|`

作用是：

**先让参考本身更可跟踪，再谈液体抑制。**

需要补充一条当前实现修正：

**局部 reactive cap 不能长期作为主导限速器。**

当前 bag 和日志已经表明：

- 全局速度剖面 `v(s)` 可能已经给出合理的弯中最低速度
- 但进入 `getReferencePoints()` 之前，`v_des_cmd` 仍可能被局部 `kappa_local_spline` 派生的 `v_cap_omega_local` 压到极低值
- 结果是全局剖面失效，系统在弯道阶段进入长期低速爬行

因此更合理的角色分工应为：

- **全局速度剖面 `v(s)` 作为主导速度参考**
- **局部 reactive cap 仅作为最后安全阀 / 异常兜底**

当前建议的收敛顺序是：

1. 先诊断 `updateSpeedProfile()` 使用的 `global_spline_.evaluateKappa(s)` 是否给出了合理的 `kappa_max / kappa_p95 / v_geom_min`
2. 若全局剖面几何合理，再在仿真实验中做一次“禁用局部 reactive cap”的 A/B 对比
3. 若全局剖面本身也存在曲率放大，再先修全局平滑缓存，再谈 local cap 的角色

#### 5.1.3 路径切换 / 重进入速度爬升（Re-entry Ramp）

当前另一类高危时刻，不是 steady tracking 本身，而是：

- 新路径显著变化
- replan
- `REACHED / IDLE -> TRACKING`

当前控制流程中，收到新路径后会：

- `updateGlobalPath()`
- 必要时 `resetWarmStart(true)`
- 再重新进入 `TRACKING`

如果这时 `v_des_cmd` 直接恢复到 nominal 值，就容易出现：

- 当前速度很低
- 路径局部曲率又高
- 但参考层一拍恢复到高速

这会显著增加 infeasible 风险。

因此建议：

在以下事件发生后：

- 显著路径切换
- replan
- `REACHED / IDLE -> TRACKING`

统一进入一个短暂的 **re-entry ramp**：

- 前 `0.5~1.0 s`
- 或前 `0.3~0.5 m` 路径进度
- `v_des_cmd` 从较低值逐步抬升
- 不允许瞬间恢复到 nominal cruise speed

### 5.2 第二层：把 liquid anti-slosh 从“强耦合硬施压”改成“风险优先调参考，QP 内辅助细化”

这一层的核心不是削弱 liquid anti-slosh，而是重新分配职责：

- 第一层先保可行性
- 第二层再保液面风险
- 第三层才由 QP 内软代价做细化优化

当前 liquid anti-slosh 的主要耦合点有三类：

- `Q_slosh_eta` 软代价
- `risk_scheduler` 输出的 `Q_eta_k / eta_bar / v_ref_eff`
- 可选 `slosh box constraint`

#### 5.2.1 风险优先调参考速度（Risk Governor）

让以下量优先作用于 `v_ref / v_des`：

- `rho_k`
- `u_k`
- IMU `a_y`
- `/slosh/height_pred_max`

也就是：

- 先降低未来激励
- 再让 MPC 在较低激励下优化

而不是一开始就把 `Q_slosh_eta` 抬很高，逼 QP 同时满足：

- 高速度 tracking
- 强 anti-slosh

从物理上看，这也更合理：

- 速度越高
- 转弯越急
- 横向激励越大

液体晃动就越大。

所以先调低参考速度，本身就是 anti-slosh 手段。

#### 5.2.2 QP 内保留 slosh 软代价，但回到辅助地位

这意味着：

- slosh 增广状态保留
- `Q_slosh_eta * (eta_x^2 + eta_y^2)` 保留
- 可选 slosh box constraint 保留
- 但第一层风险控制不再主要依赖 QP 内大权重硬压

这样调整后，系统的 anti-slosh 逻辑变成：

- 外层 governor：优先减激励
- 内层 MPC：在可行前提下做细化抑晃和平滑 tracking

这样做的好处是：

- 不会取消 liquid anti-slosh
- 不会退化成纯限速器
- 但能明显减少“tracking 和 anti-slosh 在一个 QP 里抢自由度”

#### 5.2.3 明确区分 Feasibility Governor 与 Risk Governor

这两层不应混写成同一个“大 governor”。

建议严格区分：

**A. Feasibility Governor**

输入：

- `solve_fail_count`
- 曲率
- 路径切换事件
- re-entry 状态

目标：

- 先保证 tracking MPC 有解

**B. Risk Governor**

输入：

- `rho_k`
- `height_pred_max`
- IMU `a_y`
- 风险预估量

目标：

- 在可行前提下进一步降低液体激励

这样分层后：

- 工程调试更清楚
- 消融更清楚
- 论文表达也更清楚

---

### 5.3 第三层：柔化 near-goal / settling 切换

当前 `SETTLING` 切换里，会同时发生：

- 跟踪误差权重清零
- `v_des = 0`
- `Q_v` 提高
- `Q_slosh / Q_slosh_eta` 提高
- `slosh_eta_bar` 改为 settling 口径

这会使 `SETTLING` 第一拍天然更硬，容易出现切换冲击。

建议：

- 在 `TRACKING -> SETTLING` 之间增加一个更平滑的过渡层，例如：
  - `GOAL_SLOWDOWN`
  - 或 `SOFT_SETTLING`
- 若不新增状态，也至少让以下量做渐进切换，而不是一步切满：
  1. `v_des`
  2. `Q_v`
  3. `Q_slosh_eta`
  4. `eta_bar`

这个顺序也表示危险等级：

- `v_des` 突变最容易直接打到可行性
- `Q_v` 次之
- `Q_slosh_eta` 主要改变优化偏好
- `eta_bar` 若为 hard 限制，则最危险，应该最后再谨慎调整

优先级说明：

- 这一层重要
- 但优先级低于前两层
- 因为当前主战场已经收敛到 `TRACKING`

所以顺序应是：

- 先修 tracking feasibility
- 再柔化 settling

## 6. 对当前 MPC 结构的影响

调整前，当前系统更接近：

- 上游路径
- `PathHandler` 生成参考
- 增广 MPC QP 同时处理：
  - tracking
  - 速度跟踪
  - 控制平滑
  - liquid anti-slosh
  - near-goal 切换

调整后，更准确的结构应为：

### 6.1 外层可行性层（Feasibility Layer）

负责：

- 曲率速度帽
- `|Δkappa|` 速度帽
- 连续 solve fail 降速
- re-entry ramp

输出：

- 更保守的 `v_ref / v_des`

### 6.2 外层风险层（Risk Layer）

负责：

- `rho_k`
- `height_pred_max`
- IMU `a_y`
- 风险相关参考调整

输出：

- `v_ref_eff / v_des_eff`

### 6.3 内层增广 MPC

仍然求解当前这套：

- 8 维增广 tracking MPC
- affine time-varying QP
- tracking cost
- control / control-rate cost
- slosh soft cost
- 可选 slosh box constraint

也就是说：

本方案不是把 liquid anti-slosh 从 MPC 中拿掉，而是把系统从：

**单层强耦合优化器**

改成：

**外层先保 tracking 可行性，外层再做风险感知参考整形，内层再做 liquid anti-slosh 细化优化**

## 7. 对 liquid anti-slosh 效果的影响

### 7.1 正面影响

#### 1. 抑晃收益更稳定

当前最大问题不是“liquid anti-slosh 不够强”，而是：

- tracking QP 有时直接不可行
- 一旦不可行，控制输出失去连续性
- liquid anti-slosh 收益也无法稳定兑现

先保可行性后，liquid anti-slosh 才能真正稳定发挥。

#### 2. 更符合液体晃动的物理逻辑

液体晃动主要由激励产生：

- 速度越高
- 转弯越急
- 横向加速度越大

因此：

- 先调低 `v_ref / v_des`
- 再在 QP 内细化抑晃

在物理上比“单纯靠大 `Q_slosh` 硬压”更合理。

#### 3. 减少“防晃和导航打架”

当前看起来像是：

- tracking 目标要求快走、紧跟
- anti-slosh 目标要求少晃、少激励
- 两者同时压进一个 QP 后，在复杂路径里互相抢自由度

分层后，这种冲突会明显减轻。

### 7.2 可能代价

#### 1. 速度会更慢

尤其在：

- S 弯
- 狭窄路段
- replan 后高曲率路径

这是用速度换可行性和更稳的液面响应。

#### 2. QP 内部 slosh 权重的“存在感”会减弱

因为很多 anti-slosh 收益，会先由参考降速获得。

但这不是坏事，而是把 liquid anti-slosh 从：

- 强行硬压

改成：

- 更稳定地发挥作用

## 8. 当前 liquid anti-slosh 约束的性质

### 8.1 当前主线仍是 soft

当前最核心的 liquid anti-slosh 机制是：

- `Q_slosh_eta * (eta_x^2 + eta_y^2)`

这本质上是 **soft penalty**：

- 不禁止晃动
- 只是让优化器不愿意产生大晃动

更严谨地说：

- soft cost 不会直接制造“约束系统无解”
- 但它会改变最优解偏好
- 在与高参考速度、硬输入边界、硬变化率边界、线性化误差共同作用时，可能把系统推到更容易触发 infeasible 的 operating region

### 8.2 当前另有一个可选 hard 约束

即：

- `enable_slosh_box_constraint`

但它约束的是：

- `eta_x`
- `eta_y`

也就是 modal proxy box constraint，而不是对总液面真实高度直接加 hard bound。

因此准确说法应为：

- 当前 liquid anti-slosh 主线是 **soft 为主**
- hard constraint 是 **可选增强**
- 且当前 hard constraint 约束的是模态代理量，不是总液面真实高度

## 9. 为什么当前应优先做结构改造，而不是继续大范围调参数

因为当前问题更像：

- 某些路径几何下参考速度过高
- QP 硬可行域被压没
- 控制器缺少 solve fail 后的退让机制
- 路径切换 / re-entry 过猛

这类问题只靠继续调：

- `Q_slosh`
- `gamma`
- `rho_0`
- `beta`
- `settling_eta_tol`

通常只能改善一部分工况，无法稳定解决。

而从 MPC 的一般经验看：

- 硬输入边界和硬输入变化率边界可能互相冲突
- 若这种冲突在当前时刻无法同时满足，QP 会直接 infeasible
- 参考整形、速度保护、事件过渡层，通常比直接继续抬/降代价更稳

需要特别强调：

**第一阶段不优先软化物理硬约束。**

原因是：

- 物理边界和变化率边界仍然有明确工程语义
- 过早软化容易让控制器短期“更容易有解”，但代价是物理语义变弱、激励变大
- 当前最终目标是液体晃动抑制，不宜一上来就通过软化硬约束换取表面可行性

因此当前更合理的顺序是：

1. 先做结构保护
2. 再做参数微调
3. 若仍不够，再谨慎考虑 slack / softening

---

## 10. 当前推荐的实施顺序

### 第一优先级：先保 tracking 可行性

优先实现：

- `TRACKING` 连续 solve fail 降速保护
- 曲率 + 曲率变化率相关参考速度上限
- 路径切换 / re-entry ramp

当前应补充一条实施修正：

- 不继续沿“扩大前段窗口局部补丁”这条路推进
- 将路径平滑前移到更上游的全局路径层
- 同时加强 `REACHED -> TRACKING` 入口限速

也就是：

1. 用更干净的全局平滑路径缓存供 `PathHandler` 取局部窗口
2. `PathHandler` 只保留轻量 sanitize / reject，不再承担越来越重的“修坏路径”职责
3. 在 re-entry 初段根据 `e_theta`、当前速度、前段几何继续压低 `v_des_cmd`
4. 对“全局速度剖面 vs 局部 reactive cap”的主从关系做一次明确收敛：
   - 先诊断 `updateSpeedProfile()` 的 `kappa_max / kappa_p95 / v_geom_min`
   - 再在仿真中做一次禁用局部 reactive cap 的 A/B
   - 若验证通过，再把 local cap 调整为兜底逻辑，而不是主导限速器

验收标准：

- S 弯 / 狭窄路段连续 `status=-3` 次数明显下降
- `TRACKING` 段连续 `status_val=0` 的区段明显缩短
- `REACHED -> TRACKING` 后不再一拍恢复到高 `v_des`

### 第二优先级：让 liquid risk 更多前移到参考层

优先实现：

- `rho_k / height_pred_max / IMU a_y` 优先调 `v_ref / v_des`
- QP 内 `Q_slosh_eta` 保持中等，不继续硬抬
- 保留 slosh 增广状态和软代价，不移除

验收标准：

- 在不显著恶化完成时间和 tracking error 的前提下
- `/slosh/height`、视觉液面高度、风险暴露指标呈下降趋势
- 同时 `status_val` 稳定性不劣化

### 第三优先级：柔化 settling / near-goal

优先实现：

- soft settling / goal slowdown 过渡层
- `Q_v / Q_slosh_eta / eta_bar / v_des` 渐进切换
- 若仍不够，再考虑 `Δu` 软化或 slack

验收标准：

- `SETTLING` 第一拍不再出现明显切换冲击
- near-goal 阶段 solve fail 不再集中爆发
- 终点附近液体残余晃动与 tracking 误差同时保持可接受

## 12. 当前代码诊断所支持的判断

目前代码和日志已经支持以下结论：

1. `REACHED / IDLE` stale `status_val` 污染已识别并修复  
   修复后不再重复刷上一帧求解结果。

2. `TRACKING` 是当前连续 infeasible 的主战场  
   当前主问题不再是 `REACHED / IDLE` 的统计表象，而是高曲率路径下 tracking QP 本身的硬可行性不足。

3. `relaxed_settling` 改动的 `eta_tol / eta_dot_tol / timeout_s` 只作用于 `SETTLING` 退出条件  
   它们不直接进入 `SETTLING` 内部 MPC 的代价或约束切换，因此不能把 `SETTLING success=0` 简单归因于 relaxed settling 本身。

4. 当前 liquid anti-slosh 已接入，但仍建立在一个对复杂路径不够鲁棒的 tracking 底座之上  
   因此当前阶段继续往同一个 QP 里叠更多 anti-slosh 目标，并不能优先解决主问题。

5. 当前通过扩展 `PathHandler` 前段窗口修复范围，已经证明该补丁方向只能“把失败往后推”，不能根治  
   因此当前更合理的实现路径应转为：
   - 上游全局路径平滑缓存
   - 更保守的 `REACHED -> TRACKING` 入口限速
   而不是继续扩大局部窗口补丁覆盖范围。

6. 当前弯道阶段的另一个关键问题，不再只是“会不会 infeasible”，而是“局部 reactive cap 是否把全局速度剖面长期压死”。  
   如果局部 cap 长期主导，则系统虽然看起来求解稳定，但 liquid anti-slosh 相关代价与约束在大部分阶段都不会进入有效工作区。

---

## 13. 一句话总结

**该问题的解决方案，不是继续把更多 liquid anti-slosh 目标压进同一个 QP，而是把系统改成”外层先保 tracking 可行性，外层再做风险感知参考整形，内层再在可行前提下做 liquid anti-slosh 优化”的分层结构。当前 liquid anti-slosh 主线仍保留在 MPC 内部，但其实际收益将更多建立在一个在复杂路径下仍可稳定求解的 tracking 控制底座之上。**

## 14. 2026-04-18 Bag 诊断结论与具体改进方案

### 14.1 诊断脚本与 Bag 结论

诊断脚本：`scripts/diagnose_speed_profile.py`

对 `slosh_Q5_20260418_181443_analyze_tracking_smooth_cache7.bag` 的分析结论：

```
[全局平滑路径] 总弧长: 4.35 m，n_poses=80

曲率统计（scipy CubicSpline，ds=0.05m）：
  kappa_max = 5.18 1/m（min_radius = 0.193 m）
  dkappa_max = 7.5 1/m²（含 kappa 平滑窗口=10 pt≈0.5m）

几何约束下各项 v_geom_min：
  √(a_lat/κ_max) = 0.440 m/s   ← 横向加速度约束
  ω_max/κ_max    = 0.386 m/s   ← 角速度约束（最紧）★
  √(α/dκ_max)   = 0.731 m/s   ← 角加速度约束

全局速度剖面：v_geom_min = 0.386 m/s，v_profile 均值 = 0.810 m/s

实际 cmd_vel：
  v 均值 = 0.183 m/s，v 中位数 = 0.113 m/s
  v < 0.15 m/s 占 70.7%，v < 0.30 m/s 占 90.2%
```

**诊断结论：**

| 候选根因 | 结论 |
|----------|------|
| A：global_spline kappa 放大（>10 1/m） | ✗ 不成立，kappa_max=5.18 在合理范围 |
| B：dkappa 有限差分噪声放大 | ✗ 不成立，dkappa_max 仅 7.5 1/m² |
| C：局部 reactive cap 覆盖全局速度剖面 | **✓ 成立** |

全局速度剖面计算正确（v_geom_min = 0.386 m/s），但实际执行中 70.7% 时间 v < 0.15 m/s，说明局部 reactive cap 仍在主导。

---

### 14.2 根因机制：速度剖面被 v_des_cmd 重触发重算

**问题不只是”局部 cap 覆盖”，机制更隐蔽：**

`getReferencePoints(N, dt, v_des_cmd, ...)` 内部有如下触发逻辑（`path_handler.cpp` 约第 644 行）：

```cpp
if (params_.time_parameterize &&
    (!speed_profile_valid_ || std::abs(v_des - speed_profile_v_des_) > 1e-3)) {
    updateSpeedProfile(v_des);   // ← v_des 就是 v_des_cmd（已被局部 cap 压低）
}
```

执行链条：

```
① local_planner_ros.cpp:
     v_des_cmd = min(v_nominal=1.6, v_cap_omega_local)
               ≈ ω_max / kappa_local_spline ≈ 0.07~0.10 m/s

② getReferencePoints(N, dt, v_des_cmd=0.10, ...)

③ path_handler.cpp 内部检测到 |v_des - v_des_stored| > 0.001
   → updateSpeedProfile(v_des=0.10)
   → 速度剖面以 v_des=0.10 重新规划，所有 v_ref 截断到 0.10 m/s

④ getSpeedAtS(s) 返回 ≤ 0.10 m/s
⑤ v_ref = min(0.10, v_des_cap=0.10) = 0.10 m/s
⑥ MPC 收到 v_ref=0.10，忠实跟踪 → 机器人爬行
```

**本质：全局速度剖面从未以 v_nominal=1.6 m/s 稳定生效，每次局部 cap 改变 v_des_cmd 都会触发重算，剖面被以低速重新初始化。**

---

### 14.3 具体改进方案

改进方向：**分离”规划速度”与”执行速度”**，让速度剖面始终以 v_nominal 规划，局部 cap 仅在读取剖面后作为最终裁剪。

#### 方案 A（推荐，改动最小）：禁用局部 reactive cap

在仿真 yaml 中设置：

```yaml
tracking_curvature_speed_cap_enable: false
```

效果：`v_des_cmd = v_nominal = 1.6 m/s` 保持稳定，速度剖面以正确的 v_des=1.6 规划。`getSpeedAtS(s)` 在弯道处返回 0.39~0.51 m/s，MPC 收到有意义的弯道参考速度。

验收标准：
- 弯道 v_cmd ≈ ω_max/κ ≈ 0.38~0.51 m/s
- 弯道 a_lat = v²·κ ≈ 0.39²×5.18 ≈ 0.79 m/s²（晃动被激励）
- rho_k 在弯道段明显上升（当前几乎恒为 0）
- MPC OSQP 成功率保持 ≥ 99%

#### 方案 B（更彻底，推荐中期实现）：隔离规划 v_des 与执行 v_des_cmd

在 `path_handler.cpp` 的 `updateSpeedProfile` 触发逻辑中，始终使用 `v_des_stored_nominal_`（仅在路径更新时设置，不随 v_des_cmd 变动）：

```cpp
// 路径更新时设置（updateGlobalPath 调用处）：
speed_profile_v_nominal_ = v_des;   // v_max * 0.8，与局部 cap 无关

// getReferencePoints 内触发条件改为：
if (params_.time_parameterize &&
    (!speed_profile_valid_)) {
    updateSpeedProfile(speed_profile_v_nominal_);  // 始终用 nominal
}
```

然后在 `v_ref` 取值处保留外部上界裁剪：

```cpp
double v_ref = speed_profile_valid_ ? getSpeedAtS(s_progress) : v_des_cap;
v_ref = std::min(v_ref, v_des_cap);   // 执行级 cap 仍生效
```

效果：速度剖面作为稳定的”路径级规划”，局部 cap 作为”执行级安全阀”，两者不互相污染。

#### 方案 C（配合 B，中期）：将局部 reactive cap 阈值放宽为兜底

```yaml
# 局部 cap 仅在极端情况触发，不影响正常弯道
tracking_curvature_preview_distance: 0.5   # 从大范围预见缩到近距离
tracking_curvature_min_speed: 0.3          # 放宽下限
```

### 14.4 实施优先级

| 优先级 | 动作 | 目标 |
|--------|------|------|
| P0（立即） | 禁用 `tracking_curvature_speed_cap_enable_`（方案A） | 验证全局速度剖面能独立工作，弯道 v 恢复到 0.38 m/s |
| P1（P0验证后） | 实现方案B，隔离规划/执行 v_des | 根治重触发机制，局部 cap 可重新启用作兜底 |

## 15. 当前阶段结论（2026-04-19）

### 15.1 当前状态：阶段性基本解决

截至当前版本，仿真中的主结构问题已经基本定位并完成收敛：

1. 已修正规划速度与执行速度耦合问题  
   - `v_plan` 与 `v_exec` 已分离  
   - 速度剖面不再因执行层临时限速被反复低速重算

2. 已修正速度剖面的几何来源过硬问题  
   - `updateSpeedProfile()` 不再使用 cubic spline 导数直接生成 `kappa / dkappa`
   - 改为基于 smooth cache 的离散几何，并使用更粗的规划几何尺度

3. 正常巡航段的速度能力已验证基本正常  
   - 在几乎无弯道样本中，`TRACKING + terminal_mode=NONE` 的速度分布已正常
   - 说明当前“整体慢”并不再是全程巡航问题

4. `OSQP -3` 已不再是主矛盾  
   - 当前 solver 成功率整体稳定
   - tracking 主流程已不再表现为大面积不可行

### 15.2 尚未完全收口的问题

当前剩余问题主要集中在 near-goal / terminal recovery 段：

1. `TERMINAL_LATCHED` 进入后速度上限明显偏低  
2. 在短任务、近直线、终点占比较高的仿真样本中，会显著拉低整包速度统计  
3. 该现象目前更像 terminal recovery 设计偏保守，而不是巡航层或 MPC 主约束问题

### 15.3 当前决策

当前不继续在仿真中扩大修改范围，先以当前版本作为阶段性基线进入实物测试。

决策如下：

1. 暂停继续修改 terminal recovery  
2. 暂停继续修改 MPC 主约束  
3. 保持当前已验证有效的结构修正版本不变  
4. 后续是否继续优化 near-goal / terminal recovery，等待实物测试结果再决定

### 15.4 实物测试后的判定原则

1. 若实物中不复现 near-goal 长时间低速问题  
   - 则将该问题归类为仿真侧偏保守现象  
   - 不再继续投入修改

2. 若实物中同样复现 `TERMINAL_LATCHED` 过早进入、持续过久、整体速度被拖慢  
   - 则优先检查：
     - `terminal_enter_distance`
     - `terminal_release_distance`
     - `terminal_v_max`
   - 优先做参数级修正，不先改 MPC 主体

### 15.5 当前版本的定位

当前版本建议作为：

- 仿真阶段的收敛基线版本
- 后续实物测试的基线版本

不将当前状态表述为“彻底解决”，而表述为：

**仿真主问题已阶段性基本解决，剩余 near-goal 保守行为待实物测试后再决定是否继续优化。**
