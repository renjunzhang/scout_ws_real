> 背景：基于 2026-04-22 首批 10 个实物红色液体 bag，需要判断 MPC 控制行为是否存在 bug，而不仅仅是参数调整问题。

>
> MPC 架构参考：`src/scout_apps/control/scout_local_planner/README.md`

## 1. 问题定义

当前 10 个 bag 的诊断摘要（`diagnose_real_tuning.py`）已给出聚合统计，但聚合统计不足以识别 bug——它只能给出"整包有问题"而不能说"哪个时刻/哪个机制出了什么错"。

需要区分的两类问题：

| 类型 | 特征 | 处理方式 |
|---|---|---|
| **参数整定问题** | 行为方向正确、量级偏差 | 调参 |
| **代码 bug** | 行为不符合设计意图、有规律性异常 | 代码修复 |

## 2. 已知 bug 风险点（来自 README §9/§12）

### Bug A：u_prev desync（已有修复记录，需验证是否真正消除）

**机制**：MPC 求解失败后，若 `last_control_` 未及时更新，下一周期 Δu 约束的基准是错误的历史值。  
**表现**：solve failure 后的下一帧出现反常大的 `|Δcmd_v|` 或 `|Δcmd_ω|`。  
**检测方法**：对每个 status_val=0 帧，提取相邻帧的 `cmd_vel` 差分，统计 Δ 分布。

### Bug B：v_plan/v_exec 耦合（P1 修复，需验证没有回退）

**机制**：执行层降速若触发 `updateSpeedProfile` 重算，整条速度剖面按低速压缩，系统性减速。  
**表现**：odom_v 下降后，`v_des_eff` 跟着同步下降（而不是保持相对稳定）。  
**检测方法**：时序对齐 odom_v 与 v_des_eff，看是否存在 odom 下降 → v_des_eff 跟降的级联模式。

### Bug C：speed_governor 与 risk_scheduler 双重叠加（设计问题或参数问题）

**机制**：`slosh_speed_governor` 和 `RiskScheduler` 各自独立压制 v_des。PROP2 包里两者同时激活，实际速度可能被过度压制。  
**表现**：PROP2 包中 `speed_governor_active=1` 与 `rho_k>0` 的时间高度重叠。  
**检测方法**：统计两者同时激活的帧比例；对比 PROP2 与 FAS 包的 v_des_eff 分布。

### Bug D：SETTLING 停留时长不合理

**机制**：SETTLING 阶段 MPC 等待 `|η| < eta_tol AND |η̇| < eta_dot_tol`（或 timeout）后才进入 REACHED。若停留时长远小于晃动衰减周期 `2π/ω_n`，说明约束过松；若 timeout 过早触发，说明约束过紧。  
**表现**：SETTLING 时长 < 1 个自然周期（通常约 1-3s），或各包 SETTLING 时长差异极大。  
**检测方法**：从 `/mpc_status` 提取每次 TRACKING→SETTLING→REACHED 的时间戳，统计 SETTLING 段时长。

**注**：当前 0422 实物 compare 实验不验证 SETTLING（`mpc_params.yaml: settling/enable: false`）。SETTLING 属于 T2 终点晃动衰减验证，需单独开启。本批 10 包 `TRACKING → REACHED` 是预期行为，D 检查不适用于此次实验。

### Bug E：tracking_reentry_ramp 过紧

**机制**：每次进入 TRACKING 触发 10 步（0.5s @ 20Hz）爬坡，期间速度上限被限制在 0.6 m/s 以内。  
**表现**：TRACKING 开始后前 0.5s 的 cmd_vel 明显低于中段，且低于 v_des_eff。  
**检测方法**：对每次 IDLE→TRACKING 转换，提取前 10 帧 cmd_vel 与稳态 cmd_vel 对比。

### Bug F：QP 失败位置聚集（几何引发的系统性不可行）

**机制**：路径高曲率段或曲率突变段会引发 Frenet 线性化误差放大，导致 QP 约束冲突。  
**表现**：solve failure 在时序上聚集，且聚集位置对应 `/mpc/reference_path` 的高 kappa 时刻。  
**检测方法**：对每个 failure 帧读 reference_path 的 max_kappa，画 failure 时序与 kappa 时序的重叠图。

## 3. 已有数据的可疑异常

### 3.1 dist p95 量级异常（需优先解释）

| 条件 | dist p95 (m) | heading p95 (deg) |
|---|---:|---:|
| NOM | 4.961 | 93.12 |
| ISR | 5.232 | 83.66 |
| PROP1(Q=5) | 5.761 | 101.90 |
| block2 Q5 | 2.824 | 27.14 |

正常差速机器人的横向跟踪误差 p95 应该 < 0.3m。**4-5m 的数值说明诊断脚本的距离度量本身有问题**，或者路径几何（U 形/来回）使得"最近点"不是当前跟踪段而是对向段。

block2 明显更低，可能是路径更简单（直行段更多）而非控制器更好。

**需优先验证**：打印某帧 odom 坐标和 `/mpc/reference_path` 坐标，确认是否同 frame。

### 3.2 block2 三包 rho_k = 0

block2 Q5/Q10 开了 `Q_slosh=5/10`，但 `rho_k msgs = 0`，说明 risk_scheduler 没有运行。需确认这三包是否本就按"固定 Q_slosh、无 scheduler"设计的对照组。若否，则 scheduler 没触发是 bug。

## 4. 分析方案

### 4.1 新脚本：`mpc_bug_analysis.py`

输入：10 个 bag 路径列表  
输出：
1. **状态机时序图**：每包 IDLE/TRACKING/SETTLING/REACHED 时间段的甘特图
2. **failure 聚集分析**：failure 帧时序 + 对应 kappa（直方图 + 散点图）
3. **Δcmd after failure 分布**：failure 后下一帧的 `|Δcmd_v|` 和 `|Δcmd_ω|` 分布（验证 u_prev fix）
4. **v_des_eff vs odom_v 时序对比**：检测级联降速
5. **governor + scheduler 重叠率**：PROP2 包专项
6. **SETTLING 时长表**：各包各次 SETTLING 时长（对比 ω_n 估计值）
7. **tracking_reentry 速度曲线**：TRACKING 开始后前 20 帧 cmd_vel
8. **dist/heading 坐标系验证**：打印某帧 ref_path 点 vs odom 坐标

### 4.2 分析优先级

| 优先级 | 检查项 | 原因 |
|---|---|---|
| P0 | dist/heading 坐标系验证 | 当前诊断数据可能不可信，先验证 |
| P0 | failure 聚集 + kappa 相关性 | 直接影响求解可靠性 |
| P1 | u_prev desync 验证 | 已有修复，需确认不回退 |
| P1 | SETTLING 时长 | 影响实验是否"等待晃动衰减"的结论 |
| P2 | governor + scheduler 重叠 | 影响 PROP2 vs FAS 对比公平性 |
| P2 | v_plan/v_exec 级联降速 | P1 修复后的回归验证 |
| P3 | tracking_reentry ramp | 影响实验开始阶段数据的可用性 |

## 5. 预期输出与决策节点

每个检查的预期结论形式：

- **dist/heading 验证**：确认是坐标系问题 → 修复诊断脚本的 frame 处理
- **failure 聚集**：若 failure 集中在 kappa > 2 的段 → 说明路径几何引发 QP 不可行，非 bug；若随机 → 可能 u_prev desync 残留
- **u_prev desync**：若 failure 后 `|Δcmd|` 分布与 non-failure 帧无显著差异 → 修复已生效；若有明显长尾 → 仍存在
- **SETTLING 时长**：若 < 1s 且各包差异小 → timeout 在主导（不是 η 收敛），需调整 timeout 或 eta_tol
- **governor + scheduler**：若重叠 > 50% → 双重压速是 PROP2 速度低的主要原因，非纯 scheduler 收益
