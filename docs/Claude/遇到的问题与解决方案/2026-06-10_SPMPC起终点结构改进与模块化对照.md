# 2026-06-10 SPMPC 起点/终点结构改进与模块化对照

## 1. 当前判断

针对实物 `B_slosh` bag：

```text
/data/a/slosh_bags/real/0610/20260610_spmpc_mainline_ground/spmpc_B_slosh_acados_ground_smoke.bag
```

当前结论是：

```text
SPMPC B_slosh 实物 smoke 的好跟踪效果不是主要由起点/终点污染造成。
中段 tracking 本身成立。
但 reached tail 会显著污染整包均值，正式定量评估必须切窗口。
```

分段复核结果：

| 窗口 | 时长/占比 | 现象 | 结论 |
|---|---:|---|---|
| start | `≈5.17s / 9.8%` | 低速 ramp；`monotonic_clip` 比例较高 | 有起步 transient，但不是主要污染源 |
| middle/tracking | `≈29.03s / 55.4%` | `cmd_v≈0.341m/s`，`odom_v≈0.338m/s`，projector mean `≈0.0465m`，contour RMS `≈0.054m`，yaw RMS `≈0.101rad` | 最干净、最能说明真实跟踪效果 |
| terminal | `≈6.83s / 13.0%` | slowdown/capture，仍有非零命令与非零误差 | 合法终点控制段，不适合混入 cruise tracking 均值 |
| reached | `≈11.47s / 21.8%` | `cmd_vel`、速度、projector、slosh summary、cost 近零 | 会把整包均值美化约 20%+，必须剔除 |

因此：

```text
短期：B_slosh smoke 可以认为主线通了，但 B_ours 仍需单独验证。
中期：SPMPC 需要改进起点/终点结构，但不是因为这次结果作假，而是为了 formal Gate、论文统计与复现鲁棒性。
```

## 2. 为什么还需要改起点/终点结构

当前 SPMPC 已有基础门控：

- `SpmpcProblem::setReferencePath()` 避免同一路径重复 reset progress/terminal/start-lock：`src/scout_apps/control/spmpc_local_planner/src/core/spmpc_problem.cpp:53`
- `SpmpcProblem::solve()` 用 projector 得到 `proj.s`，并用终点欧氏距离做 terminal reached：`src/scout_apps/control/spmpc_local_planner/src/core/spmpc_problem.cpp:111`、`src/scout_apps/control/spmpc_local_planner/src/core/spmpc_problem.cpp:120`
- `TerminalController` 已有 `TRACKING / TERMINAL_SLOWDOWN / TERMINAL_CAPTURE_STOP / REACHED` 模式与 terminal clamp：`src/scout_apps/control/spmpc_local_planner/src/core/terminal_controller.cpp:33`、`src/scout_apps/control/spmpc_local_planner/src/core/terminal_controller.cpp:93`
- ROS wrapper 已有 tracking safety 与 terminal spin fail：`src/scout_apps/control/spmpc_local_planner/src/ros/spmpc_local_planner_ros.cpp:375`、`src/scout_apps/control/spmpc_local_planner/src/ros/spmpc_local_planner_ros.cpp:404`
- wrapper 中 `controlTimerCallback()` 在 solve 后、发命令前统一过 safety gate：`src/scout_apps/control/spmpc_local_planner/src/ros/spmpc_local_planner_ros.cpp:524`

这些已经解决了“false PASS”和“危险继续跑”的问题。现在的问题更偏结构层：

```text
1. 起点段、常规 tracking 段、terminal 段、reached 段虽然有诊断，但还没有形成清晰的 supervisor / module 边界。
2. start transient 仍能出现较高 monotonic_clip，说明 start/projection/progress 仍应独立管理。
3. terminal/reached 样本容易污染整包统计，需要正式输出窗口标签或分析脚本统一切窗。
4. 当前 terminal 控制已经在 core 内，但 goal reached / safety / zero command / latch 等策略仍分散在 problem + terminal_controller + ROS wrapper。
5. 后续 B_ours、formal Gate、多轮实物对比需要更稳定的结构，而不是靠脚本临时解释。
```

## 3. TEB 的起点/终点结构

### 3.1 起点段

TEB 的 ROS wrapper 会把 transformed local plan 的第一点替换为当前机器人 pose；如果 plan 只剩 goal，还会插入当前 pose 作为 start：

```text
src/scout_apps/control/teb_local_planner/src/teb_local_planner_ros.cpp:335
```

TEB 内部 `TimedElasticBand` 将第一点作为固定边界：

```text
src/scout_apps/control/teb_local_planner/src/timed_elastic_band.cpp:329
src/scout_apps/control/teb_local_planner/src/timed_elastic_band.cpp:397
```

同时，TEB 把当前起始速度注入优化器：

```text
src/scout_apps/control/teb_local_planner/src/optimal_planner.cpp:233
src/scout_apps/control/teb_local_planner/src/optimal_planner.cpp:271
```

对 SPMPC 的启发：

```text
起点不是“路径的第一个点”这么简单；应明确建模为：
当前 pose + 当前速度 + 当前 progress/projection 共同构成 horizon start boundary。
```

### 3.2 终点段

TEB 的 local goal 不总是 global goal，而是 transformed lookahead window 的末端；near real goal 时才退回真实 goal orientation：

```text
src/scout_apps/control/teb_local_planner/src/teb_local_planner_ros.cpp:318
src/scout_apps/control/teb_local_planner/src/teb_local_planner_ros.cpp:701
src/scout_apps/control/teb_local_planner/src/teb_local_planner_ros.cpp:827
```

TEB 还显式处理 terminal velocity，默认终点速度为零，也可配置 `free_goal_vel`：

```text
src/scout_apps/control/teb_local_planner/src/optimal_planner.cpp:273
src/scout_apps/control/teb_local_planner/src/optimal_planner.cpp:313
```

goal reached 由 wrapper 做 supervisory 判断，而不是由优化器自己宣布：

```text
src/scout_apps/control/teb_local_planner/src/teb_local_planner_ros.cpp:290
src/scout_apps/control/teb_local_planner/src/teb_local_planner_ros.cpp:465
```

对 SPMPC 的启发：

```text
terminal cost、terminal slowdown、goal reached 判定应该解耦。
优化器可以负责生成轨迹，但“到没到、该不该停、是否成功”应由 supervisor 判定。
```

### 3.3 震荡与可行性

TEB 的 oscillation 检测是独立 `FailureDetector`，根据执行命令历史判断，而不是只看当前 OCP horizon：

```text
src/scout_apps/control/teb_local_planner/src/recovery_behaviors.cpp:51
src/scout_apps/control/teb_local_planner/src/teb_local_planner_ros.cpp:980
```

TEB 优化后还会做 trajectory feasibility check，且会对稀疏轨迹做插值检查：

```text
src/scout_apps/control/teb_local_planner/src/teb_local_planner_ros.cpp:388
src/scout_apps/control/teb_local_planner/src/optimal_planner.cpp:1250
src/scout_apps/control/teb_local_planner/src/optimal_planner.cpp:1266
```

对 SPMPC 的启发：

```text
solver success != trajectory executable。
SPMPC 的 tracking_safety 已经是第一步，后续应扩展成独立 FeasibilitySupervisor。
```

## 4. DWA 的起点/终点结构

### 4.1 起点段

DWA 没有显式 start-segment 对象。它依赖 wrapper 每周期获取由当前 pose 转换/裁剪后的 local plan：

```text
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner_ros.cpp:264
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner_ros.cpp:283
```

DWA core 只负责采样与评分：

```text
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner.cpp:216
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner.cpp:319
```

对 SPMPC 的启发：

```text
路径裁剪 / 当前局部窗口 / 起点定义属于 wrapper 或 reference module，不应散落在 solver backend。
```

### 4.2 终点段

DWA 终点结构非常清楚：

```text
未到 position tolerance -> 正常 DWA
到 position tolerance -> LatchedStopRotateController 接管 stop/rotate
```

关键位置：

```text
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner_ros.cpp:286
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner_ros.cpp:293
```

`isGoalReached()` 也由 `LatchedStopRotateController` 统一判断：

```text
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner_ros.cpp:154
```

DWA 还会在接近终点时关闭 alignment cost，避免强行贴路径朝向导致终点旋转不稳定：

```text
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner.cpp:268
```

对 SPMPC 的启发：

```text
终点行为可以是一个单独 controller/supervisor mode。
不要让中段 path-tracking cost 原样支配终点方向对齐。
```

### 4.3 可行性复用

DWA 的 stop/rotate 虽由终点 controller 接管，但仍通过 `checkTrajectory()` 复用 DWA core 的轨迹合法性检查：

```text
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner_ros.cpp:293
src/scout_apps/control/navigation/dwa_local_planner/src/dwa_planner.cpp:216
```

对 SPMPC 的启发：

```text
不同 mode 可以共用一个 motion validity oracle。
SPMPC 不应让 terminal mode 完全绕过 feasibility/safety gate。
```

## 5. mpc_planner 的起点/终点结构

### 5.1 起点与 rolling local window

`mpc_planner` 的 start/local progress 由 closest-point projection 决定，并写入共享 `ModuleData`：

```text
src/mpc_planner/mpc_planner_modules/src/contouring.cpp:35
src/mpc_planner/mpc_planner_types/include/mpc_planner_types/module_data.h:21
```

几何窗口、道路边界、速度 profile 都以同一个 `current_path_segment` 为索引：

```text
src/mpc_planner/mpc_planner_modules/src/contouring.cpp:94
src/mpc_planner/mpc_planner_modules/src/contouring_constraints.cpp:79
src/mpc_planner/mpc_planner_modules/src/path_reference_velocity.cpp:62
```

对 SPMPC 的启发：

```text
当前 progress/projection 应成为共享 runtime context，供 reference、cost、bounds、warm-start、diagnostics 共用。
不要让每个模块各算各的局部路径起点。
```

### 5.2 终点与 goal reached

`mpc_planner` 的 goal reached 是模块组合式：`Planner::isObjectiveReached()` 对所有模块做 AND：

```text
src/mpc_planner/mpc_planner/src/planner.cpp:247
src/mpc_planner/mpc_planner_modules/include/mpc_planner_modules/controller_module.h:83
```

实际路径终点主要由 contouring module 以欧氏距离判断 spline endpoint：

```text
src/mpc_planner/mpc_planner_modules/src/contouring.cpp:167
```

ROS navigation wrapper 把完成作为 one-shot event，置 `done_` 并 reset planner：

```text
src/mpc_planner/mpc_planner_rosnavigation/src/ros1_rosnavigation.cpp:225
```

对 SPMPC 的启发：

```text
goal reached 可以模块化，但路径终点语义必须有唯一 owner。
SPMPC 目前由 TerminalController + SpmpcProblem 共同承担，后续可以收敛成 TerminalSupervisor。
```

### 5.3 warm-start 与 infeasibility fallback

`mpc_planner` 用上一周期是否 feasible 选择 warmstart；如果不可行，进入 braking 初始化：

```text
src/mpc_planner/mpc_planner/src/planner.cpp:77
src/mpc_planner/mpc_planner_solver/src/acados_solver_interface.cpp:303
```

对 SPMPC 的启发：

```text
当 solver/local basin 不可信时，braking fallback 比重复上一状态更安全。
这比仅输出 hard-zero 更适合作为 OCP 初值层的恢复策略。
```

## 6. 对 SPMPC 的建议结构

建议不是把 TEB/DWA/MPC 照搬，而是吸收它们的边界设计。推荐 SPMPC 后续拆成以下 supervisor/module：

```text
SpmpcLocalPlannerROS
  ├── 只负责 ROS I/O、TF、topic、param、publish、bag diagnostics
  └── 不直接写复杂 start/terminal 策略

SpmpcProblem / SpmpcControllerCore
  ├── 组织 reference context、solver、terminal supervisor、safety supervisor
  └── 不把所有策略塞进 solver backend

ReferenceProgressManager
  ├── 输入：ReferencePath + RobotState + previous_progress
  ├── 输出：projection、guarded_s、local window、start-window flag、monotonic clip diagnostics
  └── 统一供 warm-start、OCP reference、diagnostics、start supervisor 使用

StartSegmentSupervisor
  ├── 识别 current-pose path 起步 transient
  ├── 检测 progress stall / monotonic clip burst / low-v high-omega
  ├── 可先只诊断，不直接接管控制
  └── 后续必要时提供 start ramp / progress nudge / fallback seed

TerminalSupervisor
  ├── 统一管理 TRACKING / SLOWDOWN / CAPTURE_STOP / REACHED
  ├── 欧氏距离 + heading/speed/omega gate
  ├── terminal command clamp
  ├── reached latch / release hysteresis
  └── 输出 terminal window label，供 bag 分析剔除 reached tail

FeasibilitySafetySupervisor
  ├── solver success 后检查 projection distance、spin、trajectory feasibility、stale TF/odom
  ├── 负责 hard-zero / fail status
  └── 与 solver backend 解耦

WarmStartFallbackManager
  ├── previous solution shift
  ├── flatness seed
  ├── braking fallback
  └── 必要时支持 multi-hypothesis seed
```

## 7. 最小改进优先级

### P0：先规范评估窗口，不改控制行为

这是最小且最应该先做的：

```text
1. 所有 B0 / B_slosh / B_ours 实物 bag 统一切 start / middle / terminal / reached。
2. 论文主表优先报告 middle/tracking window。
3. terminal/reached 另表报告，不混入 tracking/slosh 对比均值。
4. reached tail 必须剔除。
```

原因：当前 `B_slosh` 已经表明中段 tracking 好，但 whole-bag average 会被 reached tail 美化。

2026-06-11 已落实第一版离线切窗：`extract_fixed_path_paper_metrics.py` 支持 `start/tracking/terminal/reached/motion/core/safety_abort/solver_fail` 窗口，并用已有 B0/B_slosh 实物 bag 输出 `/data/a/slosh_bags/real/0610/spmpc_eval_windows_metrics.csv`。该实现只改离线评估脚本，不改变控制行为。

2026-06-11 进一步补齐速度统计与实验矩阵口径：fixed-path metrics 增加 `cmd_v_mean/p95/max` 与 `odom_v_abs_mean/p95/max`，matrix 默认用窗口化 `windows` 输出；`mpc_local_planner` standalone config 对齐到 `0.8/1.2/0.6/1.2` fair-common 限幅。已有实物 B0/B_slosh 表明硬 `v_max=0.8` 已配置，但 tracking 实际均速只有约 `0.32–0.35m/s`，所以提速应先诊断 `v_ref`/速度 profile/terminal window，而不是盲目提高 `v_max`。

### P1：修 goal-boundary bounce

当前 `B_slosh` 有很短的：

```text
GOAL_REACHED -> B_slosh_ACADOS_OK -> GOAL_REACHED
REACHED -> TERMINAL_CAPTURE_STOP -> REACHED
```

建议后续在 `TerminalSupervisor` 中做 reached latch / release hysteresis：

```text
1. reached 后保持 reached latch；
2. 只有实际 reference signature 改变，或距离超过 release_distance，才释放；
3. 避免终点边界几帧跳变污染状态机。
```

2026-06-11 已先做最小版本：在现有 `TerminalController` 内增加 `reached_latched_`，真正满足 `position_reached + low speed + low omega` 后保持 `REACHED`，并依赖已有 `reset()` / reference path 变化释放；未立即展开 `TerminalSupervisor` 大重构。

### P2：把 start/progress/projection 结构化

实物 `B_slosh` start 窗口虽然不污染结论，但仍有：

```text
monotonic_clip: 32 / 155 ≈ 20.6%
```

建议把当前散落的 `last_progress_s_`、projector、start_lock 统一成 `ReferenceProgressManager + StartSegmentSupervisor`。

短期先只输出更清晰的 diagnostics，不急着接管命令。

### P3：terminal 从 controller 升级为 supervisor

当前 `TerminalController` 已经有效，但长期建议职责更清楚：

```text
TerminalController: 只计算 terminal plan / clamp。
TerminalSupervisor: 管理状态机、latch、release、window label、status。
```

### P4：增加 feasibility-aware warm-start fallback

参考 `mpc_planner`，当上一周期不可行或出现 start lock，可考虑：

```text
previous feasible solution -> shifted warm-start
flatness seed -> normal seed
failure/stall -> braking fallback seed
```

但这属于后续工程，不应在当前实物 smoke 成功后马上大改。

## 8. 不建议做的事

```text
1. 不要为了 B_slosh 实物成功就删除 tracking_safety / terminal gates。
2. 不要把 terminal reached 样本混进论文 tracking 均值。
3. 不要把 DWA 的 stop-rotate 机械照搬到 SPMPC；SPMPC 可以有 terminal supervisor，但不一定要独立 rotate controller。
4. 不要把 start recovery 直接做成会覆盖 /cmd_vel 的大控制器；应先诊断，再最小化引导。
5. 不要把 start/projection/terminal 逻辑塞进 acados backend；solver backend 应保持数值优化职责。
```

## 9. 一句话结论

```text
SPMPC 的起点/终点结构需要改进，但不是因为这次 B_slosh 实物结果被污染；
而是为了让 formal Gate、论文指标、多轮实物对比和异常恢复更可靠。

最优先改的是评估窗口与状态机边界，其次才是 start/progress 引导和 warm-start fallback。
```
