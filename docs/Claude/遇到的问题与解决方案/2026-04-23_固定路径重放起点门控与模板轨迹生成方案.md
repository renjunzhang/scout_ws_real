# 2026-04-23 固定路径重放起点门控与模板轨迹生成方案

## 背景

当前实物有效性验证依赖：

- `fixed_global_path_runner.py` 重放固定路径到 `/scout/global_path_fixed`
- `slosh_experiment.launch` 让 local planner 订阅固定路径

但现场出现两个实际问题：

1. **起点门控过严，不适合实物**
   - 现有 replay 模式默认要求机器人重新进入捕获路径的起点容差区（`start-pos-tol / start-yaw-tol / start-hold-sec`）后才开始发布固定路径
   - 仿真中这个逻辑合理，实物中很难精确回到同一位置和朝向
   - 结果是：固定路径重放本身变成了实验阻塞项，而不是帮助实验稳定化的工具

2. **路径模板准备成本高**
   - 当前 `P0/P1/P2/P3` 路径需要先手工录制或先跑一次全局规划再 capture
   - 对空旷场地实验来说，研究者更需要的是：
     - 站在起点
     - 点击一个终点
     - 自动生成标准化的 `straight / single_turn / s_curve / mixed` 路径

---

## 问题 1：固定路径 replay 的起点等待如何改

## 当前代码现状

文件：

- `src/scout_apps/control/scout_local_planner/scripts/fixed_global_path_runner.py`

已有能力：

- `--skip-start-wait`
  - 直接跳过起点门控，立即 replay
- `--publish-start-goal`
  - 将固定路径起点以 `PoseStamped` 形式发布到 goal topic

现状不足：

- `--skip-start-wait` 过于激进，启动后立即发路径，不适合“人工微调后再开始”
- `--publish-start-goal` 只是辅助把起点发成 goal，不等于“到位后我再手动开始”

## 方案判断

不建议继续强化自动回起点逻辑，也不建议只靠放宽 `start-pos-tol / start-yaw-tol`。

原因：

- 实物场景下，路径重放的核心目标是 **重复同一条路径几何**
- 不是验证机器人是否能自动回到完全相同的起始姿态
- 过度依赖起点门控会把实验流程卡死在一个不重要的前置条件上

## 方案

### 方案 A（优先实施）：新增 `--manual-start`

在 `fixed_global_path_runner.py` 中新增一个手动启动模式：

行为：

1. 读取固定路径
2. 可选先执行 `--publish-start-goal`
3. 不立即 replay
4. 等待人工确认后再开始 replay

可选触发方式：

- 终端回车触发
- 或单独订阅一个空消息话题，例如 `/fixed_path/start`

建议第一版先做最简单的：

- `--manual-start`
- 终端打印：`Press Enter to start replay`

优点：

- 最符合实物实验习惯
- 不改变现有 replay 发布逻辑
- 比 `--skip-start-wait` 更稳

### 方案 B（保留）：继续支持 `--skip-start-wait`

保留现有参数，用于极简场景或快速 debug。

但在正式实物验证方案中，不建议把它作为默认推荐口径。

## 实施建议

优先级：

1. 新增 `--manual-start`
2. 文档中将 replay 推荐命令改为 `--manual-start`
3. 继续保留 `--skip-start-wait` 作为调试选项

## 问题 2：点击终点自动生成模板轨迹

## 目标

在空旷场地内，研究者只需：

1. 机器人位于起点
2. 点击一个终点
3. 自动生成标准化模板路径

路径类型包括：

- `P0_straight`
- `P1_single_turn`
- `P2_s_curve`
- `P3_mixed`

并直接发布到：

- `/scout/global_path_fixed`

同时可选保存为 JSON，供后续重复 replay。

## 方案判断

这个需求不适合继续塞进 `fixed_global_path_runner.py`。

原因：

- `fixed_global_path_runner.py` 的职责是 capture / replay 固定路径
- 模板轨迹生成是另一类能力：**从起终点构造路径几何**
- 两者混在一个脚本里会让 CLI 语义变乱

## 方案

新增独立脚本：

- `template_fixed_path_generator.py`

### 输入

- 当前机器人位姿（TF，通常 `map -> base_link`）
- 用户点击终点（例如 `/move_base_simple/goal` 或 `/scout/goal`）
- 模板类型：
  - `straight`
  - `single_turn`
  - `s_curve`
  - `mixed`

### 输出

- `nav_msgs/Path` 到 `/scout/global_path_fixed`
- 可选保存到 `/data/a/fixed_paths/*.json`

### 几何思路

使用“起点局部坐标系下的标准化模板”：

1. 将起点作为局部坐标原点，朝向为 x 轴
2. 将终点投影为模板长度 `L`
3. 在局部坐标系内生成模板曲线 `y(s)`
4. 再旋转、平移回全局坐标系

建议模板：

- `straight`
  - `y(s)=0`

- `single_turn`
  - 单峰偏移样条，产生一次明显方向改变后再回到终点

- `s_curve`
  - 双峰或正弦模板，例如 `y(s)=A \sin(2\pi s/L)`

- `mixed`
  - 前段直线 + 中段单峰 + 后段 S 弯

### 参数建议

第一版允许只暴露少量参数：

- `--template {straight,single_turn,s_curve,mixed}`
- `--length-scale auto`
- `--amplitude-scale auto`
- `--save-path-file /data/a/fixed_paths/P2_s_curve.json`

让工具默认根据起终点距离自动缩放。

## 当前判断

1. 固定路径 replay 的主要问题不是算法，而是 **实物实验流程与仿真假设不匹配**
2. 最优先不是增强自动回起点，而是提供 **人工确认后再开始 replay** 的能力
3. 模板轨迹生成值得做，而且比手工 capture 更适合后续重复实验
4. 两个需求应拆成两个工具层修改：
   - `fixed_global_path_runner.py`：补 `manual-start`
   - `template_fixed_path_generator.py`：新建模板轨迹生成器

## 2026-04-23 实施结果

今天已按上述方案完成第一版实现：

### 1. `fixed_global_path_runner.py`

- 新增 `--manual-start`
- 行为：
  1. 加载路径
  2. 可选发布起点 goal
  3. 等待终端回车
  4. 再进入原有起点门控 / replay

特点：

- 默认行为不变，不加该参数时语义与旧版一致
- 与 `--skip-start-wait` 可组合：
  - 若同时传入，则回车后直接 replay
  - 若不传 `--skip-start-wait`，则回车后仍走原有起点门控

### 2. `template_fixed_path_generator.py`

新增独立脚本，当前支持：

- `straight`
- `single_turn`
- `s_curve`
- `multi_s`
- `sharp_turn`

实现方式：

- 当前机器人位姿作为起点
- 点击终点作为终点
- 在起终点连线局部坐标系内生成标准化控制点
- 通过 Chaikin 平滑和定间距重采样生成 `nav_msgs/Path`
- 发布到 `/scout/global_path_fixed`
- 可选保存 JSON

当前设计刻意保持简单：

- 不改现有 fixed replay 默认逻辑
- 不往 `fixed_global_path_runner.py` 混入模板生成逻辑
- 模板参数先采用自动缩放，不引入复杂交互状态机
