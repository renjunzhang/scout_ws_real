# 2026-04-21 实物 MPC 未来状态估计与调参方案

> 背景：实物 `Q_slosh=0` 基线在关闭 `tracking_curvature_speed_cap_enable` 后，速度恢复，但弯道出现明显不贴路径、切弯和姿态滞后。需要回答两个问题：
>
> 1. 当前是否应该直接引入“未来状态估计 / 状态前瞻”？
> 2. 在状态前瞻之前，实物参数整定应优先做什么？

---

## 1. 当前判断

### 1.1 结论先行

当前**不建议立刻把“未来状态估计”作为第一优先级实现**。

原因不是它没价值，而是当前实物 bag 暴露出来的主矛盾仍更像：

1. `lookahead_distance` 偏大，弯道容易切弯  
2. `alpha_max` 偏保守，转向建立不够快  
3. `R_domega` 偏大，角速度变化受到额外抑制  
4. 输出链路的速度/角速度迟滞尚未完全排除  

也就是说，当前更像是**响应链整定问题**，而不是“模型主体都已对，只差时间对齐补偿”的问题。

---

## 2. 为什么会提出“未来状态估计”

### 2.1 当前代码里已有的只是“控制前瞻”，不是“状态前瞻”

当前 `scout_local_planner` 已有：

- `cmd_vel_lead_time`
- midpoint extraction

其作用是：从 MPC 最优控制序列中提取一个更适合当前底盘的控制输出时刻。

它解决的是：

> `u_k` 应该取第一个控制量，还是取半步/一步后的控制量更合理？

但它**没有解决**：

> 当前用于构造 `x0` 的里程计状态，是否已经滞后于真正底盘状态？

### 2.2 真正的“未来状态估计”是什么

这里说的未来状态估计，严格来说是：

**state latency compensation / x0 prediction**

即：在进入 MPC solve 前，不直接使用当前 odom 位姿和速度，而是按一个小延迟 `τ` 预测一个未来状态：

```text
x_hat(t+τ), y_hat(t+τ), yaw_hat(t+τ), v_hat(t+τ)
```

然后：

1. 用预测位姿重新计算 Frenet 误差  
2. 用预测速度构造 `current_state`  
3. 再把这个预测后的 `x0` 送入 MPC

---

## 3. 为什么当前不是第一优先级

### 3.1 从实物 bag 现象看，主问题仍是弯道响应链

在当前实物 `Q0` bag 中，典型现象是：

- `v_des_eff` 已经放开，不再像早期那样被压到 `0.2~0.25 m/s`
- `cmd_vel.angular.z` 已经频繁打到较大值甚至接近上限
- 弯道 `heading error` 和贴合误差仍显著偏大

这更像：

- 前视太远，控制器在几何上就容易抄近路
- 转向加速度上限偏小，姿态建立晚
- `R_domega` 偏大，导致控制器不愿意快速建立转角

这种问题下，如果直接加状态前瞻，可能会有帮助，但**不会替代基本响应整定**。

### 3.2 若基础响应链没整定好，状态前瞻容易掩盖问题

如果现在就上状态前瞻：

- 可能会让“晚半拍”看起来稍微变好
- 但无法解决 `lookahead_distance` 太大、`alpha_max` 太小、`R_domega` 太大的根因

结果是：

- 参数之间的因果关系会变混
- 后续论文里也更难解释“到底是补偿起作用，还是本体整定没做好”

因此当前更合理的顺序是：

1. 先整定 `lookahead_distance / alpha_max / R_domega`
2. 再判断是否仍存在稳定、可重复的“固定相位滞后”
3. 若仍存在，再引入未来状态估计

---

## 4. 当前推荐的调参优先级

### 4.1 第一优先级

1. `path_handler/lookahead_distance`
   - 方向：下调
   - 作用：减少切弯、缩短几何前视导致的“抄近路”

2. `vehicle/alpha_max`
   - 方向：上调
   - 作用：让角速度建立更快，减少弯中姿态滞后

3. `mpc/R_domega`
   - 方向：小步下调
   - 作用：减少对角速度变化的过强惩罚

### 4.2 第二优先级

1. `vehicle/omega_max`
   - 仅在确认已经不是 `lookahead` / `alpha_max` / `R_domega` 的问题后，再小步上调

2. `Q_contour / Q_ec / Q_etheta`
   - 不建议先动
   - 应放在“响应已经跟上，但仍不够贴路径”之后再调

---

## 5. 什么现象说明应该开始做未来状态估计

在以下条件同时满足时，未来状态估计才应进入实现优先级：

1. `lookahead_distance / alpha_max / R_domega` 已经调过一轮  
2. 输出 EMA 等执行层额外迟滞已关闭或确认不是主因  
3. `cmd_vel` 看起来已经足够激进  
4. 但车体轨迹仍持续、稳定地“晚半拍”  
5. 这种滞后在多条 bag、不同路径上都能重复出现

简化判断：

> 如果现象是“总是整体晚转一点”，适合做状态前瞻；  
> 如果现象是“有时切弯、有时甩尾、有时来不及收”，更像基础响应链还没调顺。

## 6. 如果后续要实现，正确的落点是什么

### 6.1 不只是改 `cmd_vel_lead_time`

`cmd_vel_lead_time` 只影响**控制输出提取**，不影响 MPC 初始状态 `x0`。

因此，如果要做未来状态估计，不能只改控制提取；应改的是：

1. 当前 odom 状态读取  
2. Frenet 误差计算  
3. `current_state` 构造

### 6.2 推荐的最小实现路径

在 `LocalPlannerROS` 中引入一个小的状态前瞻时间 `state_prediction_lead_time`，例如：

```text
τ = odom_latency + 0.5*dt
```

按当前速度和角速度做一阶预测：

```text
x_hat   = x + v * cos(yaw) * τ
y_hat   = y + v * sin(yaw) * τ
yaw_hat = yaw + omega * τ
v_hat   = v + a_prev * τ
```

然后：

1. 用 `(x_hat, y_hat, yaw_hat)` 重新计算 FrenetState  
2. 用 `v_hat` 构造 `current_state(StateIndex::V)`  
3. 再进入后续 MPC solve

### 6.3 第一版不要做太复杂

第一版不建议：

- 引入复杂 observer
- 额外估计高阶状态
- 同时耦合 IMU 和 wheel odom 做融合补偿

第一版只做：

- pose 一阶前推
- speed 一阶前推

先验证是否能显著减少“稳定相位滞后”。

---

## 7. 当前阶段的执行建议

### 7.1 现在先做什么

当前建议保持：

1. 优先继续用 bag 调 `lookahead_distance / alpha_max / R_domega`
2. 使用离线脚本 `diagnose_real_tuning.py` 辅助判断下一轮优先调哪项
3. 暂不立即实现状态前瞻

### 7.2 什么时候切换到代码实现阶段

只有当：

- 速度已经正常
- 求解成功率正常
- near-goal / governor / risk fallback 不是主因
- 但实物仍表现出稳定的“时间滞后型跟踪误差”

才进入“状态前瞻补偿”的实现阶段。

---

## 8. 一句话结论

**未来状态估计是合理方向，但当前不是第一优先级。**

当前实物 MPC 更需要先把：

- `lookahead_distance`
- `alpha_max`
- `R_domega`

这三类“弯道响应链”参数调顺；若之后仍存在稳定、可重复的固定相位滞后，再实现状态前瞻补偿。
