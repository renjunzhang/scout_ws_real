# 2026-05-12 OSCRS GFRS 模块化拆分 (L2.5)

## 概要

将 `anti_slosh_path_post_processor.py`（原 927 行单体）按 G/F/R/S/diagnostics/ROS adapter 职责拆分为 `oscrs/` 子包。纯算法逻辑迁入无 ROS 依赖的模块，ROS adapter 保留在 post_processor 作为薄调用层。

## 最终目录结构

```
scripts/
  anti_slosh_path_post_processor.py   # ROS adapter (517 行, -44%)
  candidate_generators.py             # 旧 G 接口，保持不变
  generate_anti_slosh_path_candidates.py  # 几何工具，未改动
  oscrs/
    __init__.py                       # 模块说明
    types.py                          # dataclass 类型文档 (CandidateEval, FeasibilityResult, SloshMetrics, SelectionResult, AntiSloshParams)
    path_utils.py                     # 纯几何工具: sanitize_points, endpoint_error, direction_preserved, safe_ratio, clamp, yaw_to_quat
    generators/
      __init__.py
      georef.py                       # G wrapper: 委托 candidate_generators.generate_georef_candidates，附带 level meta
    feasibility.py                    # F 层: 几何/碰撞/ay gate, geometry score, check_collision_on_grid (纯函数)
    slosh_rollout.py                  # R 层: forward_profile, rollout_slosh_metrics, predicted_lateral_profile, apply_slosh_scores (纯函数)
    selector.py                       # S 层: evaluate_oscrs_hard_gate, apply_oscrs_score, select_oscrs_candidate, resolve_fixed_candidate (纯函数)
    diagnostics.py                    # 纯字符串/数值格式化: format_report, format_safety_alarm, build_metrics_array, compute_fb_codes
```

## 每层职责与归属

| 层 | 文件 | 核心函数 | 说明 |
|---|---|---|---|
| G | `candidate_generators.py` | `generate_georef_candidates()` | 旧接口，未改动。外部调用方不受影响 |
| G | `oscrs/generators/georef.py` | `generate_georef_candidates_with_meta()` | 薄 wrapper，保持候选点列、顺序、数量等价 |
| F | `oscrs/feasibility.py` | `evaluate_geometry_feasibility()`, `check_collision_on_grid()` | 几何 gate + collision grid 纯函数。collision 的 ROS 部分（frame check/logging）留在 adapter |
| R | `oscrs/slosh_rollout.py` | `forward_profile()`, `rollout_slosh_metrics()`, `predicted_lateral_profile()`, `apply_slosh_scores()` | 速度剖面预测 + 2阶 ODE slosh 仿真，纯 Python |
| S | `oscrs/selector.py` | `evaluate_oscrs_hard_gate()`, `apply_oscrs_score()`, `select_oscrs_candidate()` | hard gate + batch-norm score + S_full 选择，纯 Python |
| diagnostics | `oscrs/diagnostics.py` | `format_report()`, `format_safety_alarm()`, `build_metrics_array()`, `compute_fb_codes()` | 字符串/数值格式化，纯函数。输出格式与 `validate_georef_oscrs_bag.py` 严格兼容 |
| ROS adapter | `anti_slosh_path_post_processor.py` | 所有方法变为 3-10 行委托调用 | 参数读取、topic 订阅/发布、ROS 日志。算法决策全部委托给 oscrs/ |

## 行为兼容性

- **候选顺序**: 不改变。`original, mild, medium, mid, strong` 顺序由 `candidate_specs` 保持，G wrapper 逐点等价
- **candidate_report 格式**: 不改变。`format_report()` 逐字符重现旧 `publish_candidate_report()` 输出。`validate_georef_oscrs_bag.py` 的 `SUMMARY_RE` / `ROW_RE` 仍可解析
- **fb 语义**: 不改变。`compute_fb_codes()` 逻辑逐行等价于旧代码：-1/0/1/2/3 和 takeover 语义不变
- **safety_alarm 格式**: 不改变。`format_safety_alarm()` 逐字符等价
- **slosh rollout 物理**: 不改变。`forward_profile()` 和 `rollout_slosh_metrics()` 逐行等价，含 B7 note 的 `slosh_terminal_E` 语义
- **path_to_msg 首尾 orientation**: 不改变。该逻辑停留在 ROS adapter 中，未移动
- **GEOREF_TUNED / GEOREF_FIXED_MILD / GEOREF_OSCRS_ACTIVE**: 现有行为不改变。参数读取和选择逻辑路径不变
- **MPC 控制器**: 未触碰
- **实物验证 SOP 参数语义**: 未改变

## 未迁移的内容

以下逻辑因 ROS 依赖或其他原因留在 adapter 中：

- `check_candidate_collision()` 的 ROS 日志（`rospy.logwarn_throttle`）和 costmap 订阅 — 纯 grid 逻辑已迁到 `check_collision_on_grid()`
- `publish_safety_alarm()` 的 ROS 频率限制和 `rospy.logwarn` — 消息格式化已迁到 `format_safety_alarm()`
- `publish_outputs()` 的 publisher 调用和 debug path 发布
- `publish_candidate_report()` 和 `publish_metrics()` 的 ROS publisher 调用
- `path_callback()` 的整体编排：G→F→R→S 的顺序和条件分支仍在 adapter 中，未抽象为 pipeline.py

后续可继续拆分（按方案 commit 6：pipeline.py + tail protection），但当前所有模块边界已经清晰，每个模块可独立单元测试。

## 接入第二个 Generator 的步骤

若需新增非 GeoRef 的候选生成器（如 MPC solver 内参候选、fixed path 模板等），应按以下步骤：

1. 在 `oscrs/generators/` 下新增 `new_generator.py`，实现 `generate_xxx_candidates(base, ...)` → `list[(name, points)]`
2. 在 `oscrs/generators/georef.py` 同层或新文件实现 G wrapper
3. 在 `path_callback()` 中新增 G 调用分支（替换 `generate_georef_candidates` 调用点）
4. 确认新候选 `name` 不与现有 `original/mild/medium/mid/strong` 冲突
5. F/R/S 层不需要修改（它们只消费 `list[(name, points)]` 和统一的 row dict 接口）
6. diagnostics 层不需要修改（它只消费 row dict 的字段名）

## 第三轮 (同日): pipeline.py + path_callback 薄化

### 新增: oscrs/pipeline.py

将 `path_callback()` 中除 ROS I/O 外的全部决策逻辑提纯为 `run_pipeline()`：

- `_evaluate_one()` — 对一条候选执行 F→R→S 纯计算链，接受 duck-typed params 对象
- `run_pipeline()` — 编排：候选评估 → slosh score → geometry best → fixed/OSCRS 选择 → alarm 判断
- `PipelineResult` — 承载 `rows/best/geometry_best/oscrs_best/alarm_triggered/best_fallback/fixed_*` 信号

### 改造: path_callback 成为 thin adapter

原 75 行决策逻辑缩减为 ~55 行 ROS I/O：
1. sanitize + resample (adapter)
2. G 候选生成 (adapter，通过 G wrapper)
3. 预计算碰撞结果 (adapter，需要 ROS costmap)
4. `run_pipeline()` (纯编排)
5. ROS logger 消耗 `best_fallback` / `fixed_not_found` / `fixed_rejected` 信号
6. `publish_safety_alarm()` + `publish_outputs()`

### 统一: resolve_fixed_candidate 接入 pipeline

返回值从 `item | None` 改为 `(item, status)` 三元态：
`"found_accepted"` / `"found_rejected"` / `"not_found"`。
adapter 不再手写 `next(...)` 查找；pipeline 统一处理固定候选解析，
通过 `PipelineResult` 信号让 adapter 负责 ROS 日志。
