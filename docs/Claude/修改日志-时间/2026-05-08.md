## open_goal_c 目标发布鲁棒性修正

现象：

用户运行：

```bash
SCENARIO=open_goal_c CONDITION=RAW_TUNED RUN_ID=smoke01 START_DELAY=10 RECORD_DURATION=0 \
rosrun scout_local_planner run_sim_fixed_path_bag.sh
```

检查：

```text
run_sim_fixed_path_bag.sh 的 SCENARIO 分支会正确读取 scenarios.yaml；
open_goal_c 会设置 PATH_MODE=global_goal；
global_goal 分支会启动 MPC 后调用 send_fixed_goal.py 发布 /scout/goal。
```

判断：

问题更可能是 /scout/goal 的订阅端启动慢或 action bridge 尚未 ready，
原默认 wait_sub=5s、repeat=10 对较慢启动不够保守。

修正：

```text
TEMPLATE_GOAL_WAIT_SUBSCRIBER_TIMEOUT: 5 -> 20
TEMPLATE_GOAL_REPEAT_COUNT: 10 -> 30
TEMPLATE_GOAL_REPEAT_RATE: 保持 5Hz
```

影响：

只增强 global/template goal 发布鲁棒性，不改变 RAW / GEOREF / OSCRS 控制逻辑。

后续复查：

```text
open_goal_c 仍不动时，检查 world 边界发现 open_walled.world 东墙在 x=6；
scenarios.yaml 中 open_goal_c 原目标为 x=6.0, y=-3.0，
目标点落在墙/膨胀区边界，MBF 很可能无法生成 /scout/global_path。
```

修正：

```text
open_goal_c goal: x=6.0,y=-3.0 -> x=4.5,y=-3.0
expected_path_length_m: ~7.0 -> ~8.9
```

结论：

本次不是目标发布函数失效；
脚本已发布 /scout/goal，但场景目标配置不可达/贴墙。

## run_sim_fixed_path_bag 防误用：显式目标参数自动切 global_goal

现象：

用户后续运行脚本时只传了 TEMPLATE_GOAL_X/Y/QZ/QW，
但没有传 PATH_MODE=global_goal。
脚本默认 PATH_MODE=replay，因此仍走默认 PATH_ID=P2_s_curve 固定路径，
导致 bag 名为 P2_s_curve，且没有使用用户给定目标点。

修正：

```text
启动时记录 PATH_MODE 与 TEMPLATE_GOAL_* 是否由环境变量显式设置；
若 PATH_MODE 未显式设置、SCENARIO 为空、且用户显式传了 TEMPLATE_GOAL_X/Y/QZ/QW 任一项，
则自动设置 PATH_MODE=global_goal，并打印：
  PATH_MODE not set but TEMPLATE_GOAL_* was provided; using PATH_MODE=global_goal
```

影响：

```text
1. 旧 fixed-path replay 不受影响：不传 TEMPLATE_GOAL_* 时仍默认 replay。
2. SCENARIO 不受影响：SCENARIO 分支仍显式设置 PATH_MODE=global_goal。
3. 用户用 run_sim 脚本发布自定义目标时，不再因漏写 PATH_MODE 而误录固定路径。
```

## OSCRS Step-0 离线判据与在线诊断字段对齐

背景：

```text
用户指出 analyze_oscrs_candidates.py 的 violation 漏掉方案 §4.4 中的时间超限项；
同时 offline collision_pass=1 写死、线上 candidate_report 缺 fallback_code，容易和 §4.4 五分支判据混淆。
```

修改内容：

```text
1. analyze_oscrs_candidates.py:
   violation 增加 0.2 * max(0, time_proxy/(1.15*t_proxy_raw)-1)
   CSV 增加 time_violation
   CSV 增加 collision_check_mode=not_evaluated_offline，明确 Step-0 离线不做碰撞检查
   CSV 增加 offline_oscrs_selected / fallback_code

2. fallback_code 离线语义：
   0 = non-original candidate 同时通过 geometry / height / residual
   1 = fallback original，且 original height/residual 安全
   2 = fallback geometry-pass candidate
   3 = 无完整可行候选，选 violation 最小项用于诊断

3. anti_slosh_path_post_processor.py:
   candidate_report summary 增加 fb 字段
   fb=-1 表示 OSCRS shadow/active 未启用，该字段无意义
   fb=0 表示当前在线 OSCRS feasible candidate 存在
   fb=3 表示当前简化在线 OSCRS 未找到 feasible candidate
```

边界说明：

```text
当前在线节点仍保持最小行为：OSCRS active 只在 feasible candidate 存在时接管，否则回退 geometry best。
尚未实现方案 §4.4 的完整在线 0/1/2/3/4/5 五分支 fallback 行为。
原因是完整 fallback 会改变运行时选路策略，实物前不应和已跑通的 active smoke 混在一起改。
```
