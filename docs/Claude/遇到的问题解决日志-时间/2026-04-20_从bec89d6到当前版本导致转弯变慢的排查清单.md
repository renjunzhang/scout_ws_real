# 2026-04-20 从 `bec89d6` 到当前版本导致转弯变慢的排查清单

> 目的：明确从 `bec89d6499a31b6c9135df43a3458a66d5fe19e8` 到当前版本，哪些参数和代码变更最可能直接导致"转弯明显变慢"。

---

## 0. 结论先行

`bec89d6` 这个提交本身**没有修改 MPC 代码**，主要是实验方案文档、脚本、记录。

当前版本"转弯慢"有两类原因：

| 类型 | 来源 | 实物 | 仿真 |
|---|---|---|---|
| **新增逻辑**（bec89d6 前不存在） | `speed_profile_omega_max` 桥接 + tracking 曲率预览限速 | ✓ | ✓ |
| **参数调紧**（bec89d6 到当前 yaml 改动） | `omega_max` 3.5→2.0、`alpha_max` 7.0→4.0、`max_lat_accel` 2.0→1.2 | — | ✓ |

**实物最主要的新约束**：`speed_profile_omega_max` 此前不存在，现在自动桥接到 `vehicle/omega_max=1.0`，弯道速度从原来仅受 `max_lat_accel` 约束，现在叠加了 `omega_max/κ` 约束：

```
κ=0.5 rad/m：旧上限 √(2.0/0.5)=2.0 m/s → 新上限 min(2.0, 1.0/0.5)=2.0 m/s（不变）
κ=1.0 rad/m：旧上限 √(2.0/1.0)=1.41 m/s → 新上限 min(1.41, 1.0/1.0)=1.0 m/s ← 变慢
κ=1.5 rad/m：旧上限 √(2.0/1.5)=1.15 m/s → 新上限 min(1.15, 1.0/1.5)=0.67 m/s ← 变慢
κ=2.0 rad/m：旧上限 1.0 m/s → 新上限 0.5 m/s ← 减半
```

---

## 1. 第一优先级：新增的两层几何约束（bec89d6 前不存在）

### 1.1 `speed_profile_omega_max` 在 v(s) 剖面中新增桥接

**文件**：`local_planner_ros.cpp:432`、`path_handler.cpp:1404`

```cpp
// local_planner_ros.cpp:432（参数初始化时）
if (path_params_.speed_profile_omega_max <= 1e-6)
    path_params_.speed_profile_omega_max = vehicle_params_.omega_max;  // ← 实物=1.0

// path_handler.cpp:1404（v(s) 剖面计算时，bec89d6 前不存在这段）
if (params_.speed_profile_omega_max > 1e-3 && kappa_abs > 1e-4) {
    const double v_cap = params_.speed_profile_omega_max / kappa_abs;
    v = std::min(v, v_cap);   // ← 对每个路径点都执行
}
```

**实物配置**：`mpc_params.yaml` 无显式 `speed_profile_omega_max`，自动回退 `vehicle/omega_max=1.0`。

**排查**：看 `[SpeedProfile]` 日志，`dom(omega)` 计数是否频繁主导。

---

### 1.2 TRACKING 循环新增曲率预览"二次压速"

**文件**：`local_planner_ros.cpp:874`（默认 `tracking_curvature_speed_cap_enable_=true`）

```cpp
kappa_preview = getMaxCurvatureAhead(lookahead_dist, tracking_curvature_preview_distance_=1.5m)
v_cap_kappa   = sqrt(max_lat_accel / kappa_preview)
v_cap_omega   = vehicle_params_.omega_max / kappa_preview    // ← 实物=1.0/κ
v_cap_geom    = min(v_cap_kappa, v_cap_omega)
v_des_cmd     = min(v_des_cmd, v_cap_geom)
```

这是**双重限速**：v(s) 剖面已经用 `omega_max/κ` 压过一次，控制循环每 50ms 还要再压一次。这层在 bec89d6 前完全不存在。

`kappa_preview_dbg` 和 `dkappa_preview_dbg` 仅在 MPC **求解失败**时出现在 `ROS_WARN [SolveFail]` 日志里，正常求解时不单独发布话题。要在正常行驶中观察，需手动对 `/cmd_vel` 和 `slosh/v_des_eff` 做比值分析，或临时在成功路径加日志。

---

### 1.3 `speed_profile_alpha_max` 在 v(s) 剖面新增 dκ 约束

**文件**：`path_handler.cpp:1410`

```cpp
// bec89d6 前不存在这段
if (params_.speed_profile_alpha_max > 1e-6) {
    v_cap = sqrt(speed_profile_alpha_max / dkappa_abs);
    v = std::min(v, v_cap);   // ← 对每个路径点都执行
}
```

实物 `speed_profile_alpha_max` 未显式配置，自动桥接到 `vehicle/alpha_max=2.5`。

弯道**入口**处 `dkappa` 最大，因此车速会在弯前提前降低，产生"入弯慢"的感觉。

**排查**：`[SpeedProfile]` 日志 `dom(alpha)` 计数、`dkappa_max`。

## 2. 第二优先级：`max_lat_accel` 的 v(s) 约束（原有，但仍是关键参数）

**文件**：`mpc_params.yaml`、`path_handler.cpp:1398`

```cpp
v <= sqrt(max_lat_accel / kappa)   // path_handler v(s) 剖面
```

这条约束在 bec89d6 前就有，不是新增。但它仍然是最物理直观的弯道限速，且现在被 `omega_max/κ` 在高曲率时超越（1.3 节的表格说明了两者的相对强弱）。

**实物当前值**：`max_lat_accel=2.0 m/s²`（未改变）。

**排查**：`[SpeedProfile]` 日志 `dom(lat)` 计数主导时说明 `max_lat_accel` 是主因；`dom(omega)` 主导时说明 1.1 节的桥接是主因。

---

## 3. 第三优先级：仿真专用参数调紧（实物不受影响）

仅影响 `mpc_params_sim.yaml`，实物 `mpc_params.yaml` 这三项未改动：

| 参数 | bec89d6 | 当前 | 影响 |
|---|---|---|---|
| `vehicle/omega_max` | 3.5 rad/s | **2.0 rad/s** | 直接限制 ω 硬约束；同时拉低 1.1 节桥接值 |
| `vehicle/alpha_max` | 7.0 rad/s²  | **4.0 rad/s²** | 桥接到 `speed_profile_alpha_max`，入弯更保守 |
| `path_handler/max_lat_accel` | 2.0 m/s² | **1.2 m/s²** | 弯道速度上限进一步下降 |

仿真还改了：

- `Q_contour`: 15→45（横向误差权重增大，MPC 更激进贴线，有时反而触发减速）
- `lookahead_distance`: 0.6→0.35 m（前视缩短，弯前预热距离变短）
- `use_bspline_smoothing`: true→false（路径不再平滑，kappa 峰值更高，进一步触发限速）

## 4. 第四优先级：RiskScheduler 的速度折减

**启用条件**：`risk_scheduler_enable=true`（默认 false，slosh_experiment.launch 可覆盖）

```cpp
v_ref_eff_k = v_ref * (1.0 - beta * s_rho)    // beta=0.3, s_rho ∈ [0,1]
```

弯道本身会拉高 `r_k`（液面预测风险），在 scheduler 开启时会进一步折减速度，最多降低 30%。

**仿真已发现问题**：`u_k` 在仿真中虚高（mean≈0.41），导致 `rho_k≈0.13`，`Q_eta_desired≈3` 低于 FAS 固定 Q=5，PROP 在仿真中反而比 FAS 晃动更大。实物待验证。

**排查话题**：`/risk_scheduler/rho_k`、`/risk_scheduler/u_k`、`/risk_scheduler/r_k`

## 5. 第五优先级：near-goal / terminal / settling 逻辑带来的"假性慢"

| 机制 | 代码 | 速度 |
|---|---|---|
| `terminal_recovery` 接管 | `terminal_v_max=0.18 m/s` | 极低 |
| `goal_stop_pending` | `v_des_cmd_raw=0.0` | 归零 |
| `settling/enable` | `Q_v=30, Q_eta=10` 收敛 | 极低 |
| `tracking_reentry_ramp` | 进入 TRACKING 后 10 步内 | 从 0.6 m/s 爬坡 |

**典型误判**：短路径实验里弯道后很快进入 near-goal，`TERMINAL_LATCHED` 接管，被误认为"弯中慢"。

**排查**：`/scout_local_planner/status` 里的 `planner_state`、`terminal_mode`；`/slosh/speed_governor_active`。

## 6. 第六优先级：路径几何本身偏"硬"

如果全局路径 `kappa` 峰值偏高，上述所有限速都会被频繁触发。

- **话题**：`/scout/global_path_smooth`、`/mpc/reference_path`
- **日志**：`[SpeedProfile] kappa_max / dkappa_max / v_geom_min`
- **启发**：若 `v_geom_min` 已经很低（如 <0.5 m/s），说明路径几何就是主因，调参收益有限，需要改路径规划端。

## 7. 推荐排查顺序

### Step 1：看 `[SpeedProfile]` 日志（rosout 或 rqt_console）

```
[SpeedProfile] n=XX kappa_max=? dkappa_max=? v_geom_min=? dom(nom/lat/omega/alpha)=?/?/?/?
```

- `dom(omega)` 高 → 1.1 节的 `omega_max/κ` 桥接是主因
- `dom(alpha)` 高 → 1.3 节的 `dkappa` 约束是主因
- `dom(lat)` 高 → 2 节的 `max_lat_accel` 是主因
- `v_geom_min` 很低 → 路径几何本身太硬

### Step 2：看 local preview cap 是否二次压速

```bash
# 临时方法：rostopic echo /cmd_vel 同时看日志
# 正式方法：比较 /slosh/v_des_eff 与 v_max*0.8 的差距
```

在**求解失败**场景下，`ROS_WARN [SolveFail]` 日志末尾会直接输出 `kappa=? dkappa=?`，可以观察二次压速的幅度。

若想在正常运行中持续观察，需在 `local_planner_ros.cpp:916` 附近添加一行 `ROS_INFO_THROTTLE` 或新发布一个 `Float32` 话题。

### Step 3：区分仿真 vs 实物

- 仿真：3 节的参数调紧是额外主因，先考虑恢复 `omega_max`
- 实物：1.1 节的 `omega_max/κ` 桥接是主要新增约束，考虑显式配置 `speed_profile_omega_max` 或临时设 `tracking_curvature_speed_cap_enable: false`

### Step 4：排除 near-goal 污染

若转弯慢只在靠近终点时发生，先确认 `planner_state` 不是 `TERMINAL_LATCHED` 或 `SETTLING`。

### Step 5：RiskScheduler 开启时检查折减

```bash
rostopic echo /risk_scheduler/rho_k
rostopic echo /risk_scheduler/u_k
```

若 `rho_k > 0.3` 且 `beta=0.3`，弯道速度最多再降 30%。

## 8. 快速验证方案

### 验证"是否新增逻辑导致慢"

临时关闭 TRACKING 曲率预览：

```bash
roslaunch scout_local_planner slosh_experiment.launch \
    # 在 mpc_params.yaml 或 launch 里临时添加：
    # safety/tracking_curvature_speed_cap_enable: false
```

若关闭后转弯速度明显回升，确认 1.2 节是主因。

### 验证"omega_max 桥接是否过紧"

显式配置一个更大的 `speed_profile_omega_max`（比如 2.0），绕过桥接：

```yaml
# mpc_params.yaml path_handler 段加入：
path_handler:
  speed_profile_omega_max: 2.0   # 显式覆盖，绕过桥接（vehicle.omega_max=1.0 不再作用于 v(s) 剖面）
```

若弯道速度回升，确认 1.1 节是主因；此时 `omega_max=1.0` 仍作用于 MPC 硬约束和实时 tracking cap（L888），只是 v(s) 剖面不再受限。

## 9. 一句话总结

从 `bec89d6` 到当前版本，**实物最主要的新约束是 `speed_profile_omega_max` 自动桥接到 `vehicle/omega_max=1.0`，叠加 TRACKING 曲率预览的二次压速**，在 κ≥1.0 的弯道上弯中速度上限下降 30%~50%；仿真额外还有 3 条参数调紧。排查应先看 `[SpeedProfile]` 日志里 `dom(omega)` 是否主导，再决定是调参还是关闭新逻辑。

## 10.MPC 相对 bec89d6 的改进与风险自适应说明（2026-04-20）

### 1) 先澄清 bec89d6 的基准含义

`bec89d6` 这个提交本身没有修改 MPC 主体代码，主要是文档、脚本和实验启动链路变化。因此这里的“相对 bec89d6”应理解为：从 `bec89d6..HEAD` 这段开发期间，`scout_local_planner` 的 MPC 架构新增了哪些能力。

### 2) 结构性改进（核心）

1. 引入独立风险调度模块 `RiskScheduler`，由预测晃动高度、晃动能量、终点距离和 IMU/模型不确定性计算风险量 `r_k/u_k/rho_k`。  
2. `RiskScheduler` 已接入 `LocalPlannerROS` 的 MPC solve 前 outer loop，可在线输出 `Q_eta_k`、`eta_bar_k`、`v_ref_eff_k`，并带变化率限制，避免参数突变。  
3. 增加 fallback 触发逻辑：IMU 超时、bias 未就绪、不确定性长期过高时，回退到保守固定参数。  
4. 增加风险调度调试话题：`/risk_scheduler/rho_k`、`/risk_scheduler/r_k`、`/risk_scheduler/u_k`、`/risk_scheduler/Q_eta_k`、`/risk_scheduler/fallback_active`。  
5. 新增可配置的终点 `SETTLING` 阶段，用于到达目标后继续做残余晃动收敛判定；是否实际生效取决于 settling 参数。  
6. 增加 tracking 可行性保护与恢复机制，包括失败计数、速度封顶、重入 ramp。  
7. 增加全局平滑缓存、速度剖面几何约束和 `v_plan/v_exec` 分离，减少局部限速反复污染全局速度剖面。  
8. 增加 input shaping（ZV）参考整形，主要作为 ISR 经典对比算法，不属于 PROP 风险自适应 MPC 的核心链路。  

### 3) 风险自适应：已实现，但是否生效取决于启动方式

- 风险自适应不是只有参数占位，而是已有 `risk_scheduler.cpp/h` 实现，并已接入 MPC solve 前的运行时参数更新流程。  
- `mpc_params.yaml` 和 `slosh_experiment.launch` 默认不强制打开 `risk_scheduler_enable`，因此普通启动可能仍是固定参数 FAS。  
- Day4 profile 或手动 launch 可以显式设置 `risk_scheduler_enable:=true`，此时才是 PROP 风险自适应链路。  
- FAS vs PROP 的关键差异应定义为：`Q_slosh=5` 且 `risk_scheduler_enable=false` 对比 `Q_slosh=5` 且 `risk_scheduler_enable=true`。  

### 4) 当前必须保留的限定

- `Q_eta_k` 会通过高度系数换算后注入 `runtime_mpc_params.Q_slosh_eta`，这是当前风险调度最直接生效的项。  
- `v_ref_eff_k` 会作为风险折减后的参考速度进入速度剖面/参考生成链路，这是当前风险调度影响速度的主要入口。  
- `eta_bar_k` 只有在 `enable_slosh_box_constraint=true` 时才真正进入 MPC 盒约束；如果当前实物配置关闭盒约束，则它主要是调度输出和后续约束实验接口，不能写成当前一定在约束中生效。  
- ISR/ZV input shaping 是论文对比 baseline，不能和 PROP 主方法混写；PROP 主链路仍应是 slosh-aware MPC + risk-adaptive scheduling。  

### 5) 与基线相比的结论

- **架构能力明显增强**：从固定 slosh-aware MPC 扩展为可选的风险自适应 MPC，可在线调节 slosh 权重、参考速度和安全边界接口。  
- **风险自适应已工程落地，但不是所有启动方式默认启用**：需要 `risk_scheduler_enable:=true` 或对应 profile。  
- **实验效果还需要 FAS vs PROP 实物 bag 验证**：目前可以说“结构已完成”，但不宜提前写成“效果已证明”。  

### 6) 启用建议（最小可行）

1. 固定路径和固定目标下先跑 FAS：`Q_slosh=5`、`risk_scheduler_enable=false`。  
2. 同一路径再跑 PROP：`Q_slosh=5`、`risk_scheduler_enable=true`。  
3. 对比 `/risk_scheduler/rho_k`、`/risk_scheduler/fallback_active`、`/slosh/eta`、`/cmd_vel`、完成时间和液面峰值，确认风险调度是否带来实际收益。  
4. 若长期 fallback 或速度显著变慢，优先调 `beta`、`Q_eta_max`、`rate_limit_per_step`，不要先打开 slosh box constraint。
