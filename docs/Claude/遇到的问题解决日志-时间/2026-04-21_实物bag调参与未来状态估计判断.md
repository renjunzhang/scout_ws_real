# 2026-04-21 实物 bag 调参与未来状态估计判断

## 1. 背景

今天围绕实物 `Q_slosh=0` 基线继续调参与诊断，重点关注两个问题：

1. 关闭 `tracking_curvature_speed_cap_enable` 后，速度恢复，但弯道不贴路径  
2. 是否需要立刻给实物 MPC 加“未来状态估计 / 状态前瞻补偿”

同时，为了减少“工控机端 bag 不方便拷贝回开发机”带来的往返成本，新增了一份**可直接在实物工控机上运行的离线调参脚本**。

---

## 2. 关键诊断结论

### 2.1 第一条实物 bag：速度慢的根因不是 risk scheduler，也不是 OSQP

对实物 `Q0` bag 的诊断结论：

- `risk_scheduler` 未启用，不是主因  
- `terminal_recovery` 未长时间介入，不是主因  
- `OSQP` 求解成功率高，不是主因  
- 真正的问题是：`/slosh/v_des_eff` 本身就被压得很低，速度在进 MPC 之前已经慢了

进一步结合路径几何分析，判断：

- 主压速项来自 TRACKING 局部预览里的 `dkappa` 限速  
- 关闭 `tracking_curvature_speed_cap_enable` 后速度明显恢复

### 2.2 第二条实物 bag：速度起来后，主矛盾切换成“弯道响应链”

后续实物 bag 表现为：

- `v_des_eff` 已经放开，不再是参考速度先天过低  
- `cmd_vel` 仍追不上 `v_des_eff`  
- 航向误差和贴合误差显著偏大  
- `local_path` 几何明显比 `reference_path` 更尖

因此当前主问题不再是“慢”，而是：

> 速度放开后，实物弯道闭环响应还没整顺。

当前更像是：

- `lookahead_distance` 偏大
- `alpha_max` 偏小
- `R_domega` 偏大
- 执行响应链存在迟滞

---

## 3. 对“是否立刻做未来状态估计”的判断

今天明确结论：

**不建议把未来状态估计作为当前第一优先级实现。**

理由：

1. 当前 bag 暴露出来的主矛盾仍是基础响应链  
2. 直接引入状态前瞻可能掩盖 `lookahead / alpha_max / R_domega` 的根因  
3. 当前更像“弯道控制还没调顺”，不是“模型都对，只差时间对齐”

当前推荐优先级：

1. `lookahead_distance`
2. `alpha_max`
3. `R_domega`
4. 最后再考虑 `Q_contour / Q_etheta`

只有在上述参数调过后，仍出现稳定、可重复的“整体晚半拍”现象，才进入未来状态估计实现阶段。

## 4. 今天新增脚本

新增：

- `src/scout_apps/control/scout_local_planner/scripts/diagnose_real_tuning.py`

用途：

- 直接对实物 rosbag 输出“下一轮优先调哪些参数”
- 区分：
  - `v_des_eff` 本身太低
  - `cmd_vel` 跟不上 `v_des_eff`
  - terminal / governor / risk fallback 是否在主导
  - 弯道贴合差更像前视、角加速度、角速度变化率权重，还是误差权重问题

支持：

- 完整模式
- `--brief` 简短模式，直接输出 `Top Next Changes`

这一步的意义是：后续在工控机上不必先把 bag 拷回开发机，也能快速判断下一轮该动哪些参数。

## 6. 当前阶段结论

当前阶段不继续扩大 MPC 结构修改范围，先坚持以下策略：

1. 用 `diagnose_real_tuning.py` 辅助看 bag  
2. 优先调顺实物弯道响应链  
3. 暂不立刻实现未来状态估计  
4. 若后续 bag 证明存在稳定的固定相位滞后，再单独启动状态前瞻实现

一句话总结：

> 当前实物问题的第一优先级仍是“响应链整定”，不是“状态前瞻补偿实现”。
