### 6. 参考层加入曲率 / 曲率变化率速度帽

本轮继续落地方案中的 `Curvature-Aware Reference Cap`。

新增内容：

- `PathHandler::getMaxCurvatureRateAhead()`
- `LocalPlannerROS` 在 `v_des_cmd -> getReferencePoints()` 之间加入：
  - 基于 `|kappa|` 的速度上界
  - 基于 `|dκ/ds|` 的速度上界

新增参数：

- `safety/tracking_curvature_speed_cap_enable`
- `safety/tracking_curvature_preview_distance`
- `safety/tracking_curvature_rate_preview_distance`
- `safety/tracking_curvature_min_speed`
- `safety/tracking_curvature_rate_min_speed`
- `safety/tracking_curvature_rate_gain`

当前默认值：

- curvature speed cap enable = `true`
- curvature preview distance = `1.5 m`
- curvature rate preview distance = `1.0 m`
- curvature min speed = `0.25 m/s`
- curvature rate min speed = `0.25 m/s`
- curvature rate gain = `1.0`

实现方式：

1. `|kappa|` 速度帽：

- 依据 `path_params_.max_lat_accel`
- 使用 `v <= sqrt(a_y_max / |kappa|)`

2. `|dκ/ds|` 速度帽：

- 依据 `vehicle_params_.alpha_max`
- 使用近似关系 `dot(omega_ref) ≈ v^2 * dκ/ds`
- 得到 `v <= sqrt(alpha_max / |dκ/ds|)`

这层速度帽发生在 `getReferencePoints()` 之前，因此属于参考层保护，而不是在求解失败后再被动缩放输出。

### 13. 基于前段窗口分析的进一步根因修复：单点折返尖刺清洗

基于 `analyze_global_path_prefix_window.py` 对远 goal bag 的检查，已经观察到：

- 路径前段并非由大量极短段导致
- 主要问题是局部存在单点折返尖刺
- 典型表现为相邻段长度正常，但 heading 在单个点附近突然大幅反向，再立刻回到原主方向

典型例子：

- `31->32 heading ≈ 0.618`
- `32->33 heading ≈ -1.194`
- `33->34 heading ≈ 0.416`

这类单点尖刺会把前段局部窗口的 `kappa / dkappa` 瞬间拉爆，导致：

- `fitLocalSpline failed: pathological geometry rejected`

因此本轮新增：

- `removeSinglePointSpikes()`

接入位置：

1. `updateGlobalPath()`
   - `sanitizePolyline()` 之后
   - `resamplePath()` 之后再做一次
2. 全局速度曲线样条拟合前
3. `getReferencePoints()` 的局部窗口清洗后
4. `fitLocalSpline()` 内部最终入口

当前启发式规则：

- 若某个中间点的前后两段长度都正常
- 但该点处航向跳变过大（当前阈值 `> 1.2 rad`）
- 且移除该点后前后点可以直接更平滑连接
- 则将该点视为单点折返尖刺并去除

为什么这样做：

- 这不是临时“放宽几何阈值”
- 而是针对已定位到的上游路径异常形态做数据质量修复
- 仍然符合“先收敛、后扩展”和“追根因”的原则

## 新增：P1 结构修复，解耦规划速度与执行速度

根据后续 bag 与代码诊断，当前更隐蔽的根因不是单纯“local curvature cap 覆盖 global speed profile”，而是：

- `LocalPlannerROS` 先计算运行时执行速度上限 `v_des_cmd`
- 再将该值直接传入 `PathHandler::getReferencePoints()`
- `getReferencePoints()` 内部若发现 `|v_des - speed_profile_v_des_| > 1e-3`
  就会重新调用 `updateSpeedProfile(v_des)`

结果是：

- 全局速度剖面 `v(s)` 会被按执行层限速值重新规划
- 规划层名义速度 `v_nominal` 从未真正稳定地主导整条路径速度剖面

这会导致：

- 弯道长期低速爬行
- `omega` 约束、横向激励、slosh cost 在大部分阶段无法进入有效工作区

本轮修改将两层职责拆开：

1. **规划速度 `v_plan`**
   - 只用于 `updateSpeedProfile(v_plan)`
   - 当前取 `v_nominal`

2. **执行速度 `v_exec`**
   - 只用于当前周期参考速度硬上界
   - 当前取 `v_des_cmd / last_v_des_eff_`

代码改动：

- `PathHandler::getReferencePoints()` 接口从
  - `getReferencePoints(..., v_des, ref_points)`
  改为
  - `getReferencePoints(..., v_exec, v_plan, ref_points)`

- `getReferencePoints()` 内部：
  - 仅在 `|v_plan - speed_profile_v_des_| > 1e-3` 时重算 `updateSpeedProfile(v_plan)`
  - `speed_profile_valid_ ? getSpeedAtS(s_progress) : v_plan`
  - 最终 `v_ref` 仍会被 `v_exec` 作为执行层上界裁剪

- `LocalPlannerROS` 两次调用改为：
  - 执行层传 `v_des_cmd` 或 `last_v_des_eff_`
  - 规划层固定传 `v_nominal`

目的：

- 让全局速度剖面真正按规划层速度工作
- 执行层限速只影响当前周期，不再反向重写整条 `v(s)`

本轮未改动：

- MPC 数学结构
- 代价权重
- 物理硬约束
- local cap 开关逻辑本身

## 根因结构修复：全局平滑缓存 + 重进入曲率自适应 ramp

### 根因分析（2026-04-18）

经过代码审查，发现前段窗口补丁不断扩大的根本原因是：

**`global_points_map_`（局部窗口取点来源）没有 B-spline 平滑，只有去重/去尖刺**

具体问题：

- `updateGlobalPath()` 中 `bsplineSmooth()` 只作用于临时变量 `global_points`，结果送入 `global_spline_`（速度曲线专用）
- `global_points_map_` 始终是原始清洗版（sanitize + resample + spike_removal），未经平滑
- `getReferencePoints()` 从 `global_points_map_` 切局部窗口，遇到路径锐角（正常弯道，非尖刺）时，在 `resample_spacing` 尺度下估算曲率仍超 `kappa > 20` 阈值，触发 `fitLocalSpline` 拒绝

因此，单纯靠 `removeSinglePointSpikes` 和前段窗口 B-spline 修复只能延缓，不能根治。

### 本轮结构改动

**不继续扩大前段窗口补丁范围；改为在全局路径接收时生成独立平滑缓存，供局部窗口直接使用。**

#### 1. `path_handler.h`：新增平滑缓存成员

```cpp

std::vector<Eigen::Vector2d> global_points_map_smooth_;
std::vector<double>          global_path_s_smooth_;
bool                         global_smooth_valid_ = false;
```

`global_points_map_`（原始清洗版）保留不变，仍用于路径相似性检测（`path_similar` 逻辑）和诊断。

#### 2. `path_handler.cpp`：`updateGlobalPath()` 构建平滑缓存

在 `global_path_s_` 构建完成后，追加：

```cpp

if (params_.use_bspline_smoothing && global_points_map_.size() >= 4) {
    sm = bsplineSmooth(global_points_map_, ...);
    sm = resamplePath(sm, rs);

}
```

与 `global_spline_`（速度曲线用的全局样条）分离：两条缓存职责明确，互不覆盖。

#### 3. `path_handler.cpp`：`getReferencePoints()` 切换取点来源

```cpp

const std::vector<double>& path_s = global_path_s_;

// 改为
const std::vector<Eigen::Vector2d>& path_points_map =
    global_smooth_valid_ ? global_points_map_smooth_ : global_points_map_;
const std::vector<double>& path_s =
    global_smooth_valid_ ? global_path_s_smooth_ : global_path_s_;
```

弧长数组与点集一一对应，不存在 s 坐标不一致问题。

#### 4. `local_planner_ros.cpp`：重进入 ramp 基于起点曲率自适应

`transitionTo(TRACKING)` 和 `consumeResetHint()` 两处统一改为：

```cpp
int ramp = std::max(0, tracking_reentry_ramp_steps_);
if (tracking_curvature_speed_cap_enable_ && path_params_.max_lat_accel > 0.0) {
    const double kappa_start = path_handler_.getMaxCurvatureAhead(
        0.0, tracking_curvature_preview_distance_);

        sqrt(max_lat_accel / kappa_start) < tracking_reentry_v_cap_) {
        ramp *= 2;  // 起点曲率过高时加倍保守

}

```

逻辑：若匀速以 `tracking_reentry_v_cap_` 行驶就超出横向加速度限制，说明起点几何已经偏激，加倍 ramp 步数（0.5s → 1.0s）。不修改 `last_control_`（`a_prev` 语义侵入性强，证据不足）。

## cubic spline dkappa 放大问题 → 窗口迭代修复推广到全局

## 2026-04-18 追加：omega_max 硬约束速度限制

### 背景

第 4 次远 goal bag（Bag 4）显示车辆卡在 s≈5.2 m 处，日志：

```
kappa=10.2631 dkappa=400.5191
v_des=0.250 v_des_raw=1.455
ref0=(v=0.250 k=-3.320)
fail_streak=0...59+
```

分析：
- `v_cap_kappa = sqrt(1.0/10.26) = 0.31 m/s`
- 旧限速：`max(min_speed=0.25, 0.31) = 0.31`，但 `v_des_cmd` 被 `tracking_curvature_min_speed_=0.25` 下限兜底
- 实际 `v_des = 0.25`，则 `omega_ref = 0.25 × 10.26 = 2.57 rad/s > omega_max=2.0 rad/s`
- OSQP 约束本身不可行（PRIMAL INFEASIBLE），不是局部极值问题

### 根因

曲率限速只考虑了横向加速度约束 `v ≤ sqrt(a_lat/kappa)`，未考虑角速度约束 `v × kappa ≤ omega_max`，即缺少 `v_cap_omega = omega_max / kappa` 这一项。

### 修改

文件：`src/local_planner_ros.cpp`，曲率限速段（原 L857-864）：

```cpp
// 旧代码
const double v_cap_kappa = std::sqrt(std::max(0.0, path_params_.max_lat_accel / (kappa_preview_dbg + 1e-9)));
v_curve_cap = std::min(v_curve_cap, std::max(tracking_curvature_min_speed_, v_cap_kappa));

// 新代码
const double v_cap_kappa = std::sqrt(std::max(0.0, path_params_.max_lat_accel / (kappa_preview_dbg + 1e-9)));
// omega_max 硬约束：v × kappa ≤ omega_max
const double v_cap_omega =
    (vehicle_params_.omega_max > 1e-3)
        ? vehicle_params_.omega_max / (kappa_preview_dbg + 1e-9)
        : v_cap_kappa;
// 几何综合限速：取两者较小值
const double v_cap_geom = std::min(v_cap_kappa, v_cap_omega);
// 若几何限速低于 min_speed，说明路径确实无法以 min_speed 行驶，降速优先
const double v_floor = std::min(tracking_curvature_min_speed_, v_cap_geom);
v_curve_cap = std::min(v_curve_cap, std::max(v_floor, v_cap_geom));
// 等价于：v_curve_cap = std::min(v_curve_cap, v_cap_geom)
```

对 kappa=10.26 的效果：
- `v_cap_kappa = 0.31 m/s`
- `v_cap_omega = 2.0 / 10.26 = 0.195 m/s`
- `v_cap_geom = 0.195 m/s`（omega_max 约束更紧）
- `v_des_cmd` 被限制到 ≤0.195 → `omega_ref = 0.195 × 10.26 ≈ 2.0 rad/s = omega_max` → MPC 可行

## 2026-04-18 追加：u_prev 冻结导致 MPC 永久不可行

Bag 6 在大弯道处仍然出现 OSQP -3，但分析发现参考路径几何已完全正常：

- `/mpc/reference_path` max_kappa=0.733（1/m），max_dkappa=5.98（1/m²）→ **无几何问题**
- window repair 正常工作：kappa 22.4→5.59，dkappa 449→69
- 所有 fail 事件 ref(max_k=0.733, max_dk=5.98) 保持不变

### 根因：u_prev.omega 冻结 + alpha 约束

MPC 失败时，代码仅发布 fallback 速度（v→0, omega→0），但 **`last_control_` 不更新**，停留在最后一次成功解的值。

```
第一次 fail：u_prev=(-0.444, 0.552)
fail_streak=10：u_prev=(-0.444, 0.552)   ← 完全没变
fail_streak=140：u_prev=(-0.444, 0.552)  ← 永久冻结
实际机器人：omega≈0（已停止）
```

alpha 约束（`|omega_0 - u_prev.omega| ≤ alpha_max × dt`）因此强制：
```
|omega_0 - 0.552| ≤ 4.0 × 0.1 = 0.4
→ omega_0 ≥ 0.152
```

而参考值 `omega_ref_0 = v_des × kappa_ref = 0.038 × 0.741 = 0.028`。
MPC 不得不从 omega_0=0.152 出发，与已停止的实际状态严重不符，引发 QP 结构性不可行。

### 修改

文件：`src/local_planner_ros.cpp`，MPC 失败 fallback 发布后同步更新 `last_control_`：

```cpp
// 旧代码（失败后不更新 last_control_）
publishCmdVel(v, omega);
last_solve_time_ms_ = 0.0;

// 新代码
publishCmdVel(v, omega);
// 同步更新 last_control_，使下一周期的 alpha 约束基于实际命令值
last_control_(ControlIndex::A) =
    std::abs(current_v_) > 1e-3
        ? (v - current_v_) / dt
        : 0.0;
last_control_(ControlIndex::OMEGA) = omega;
last_solve_time_ms_ = 0.0;
```

效果：每次 fail 后，`last_control_.omega` 随 fallback omega 逐步衰减到 0，alpha 约束的 omega_0 下限也随之回落，MPC 恢复可行。

## 2026-04-18 追加：全局运动学速度剖面（结构性修复）

### 背景与动机（Bag 7 分析 + 用户反馈）

Bag 7 已基本消除 MPC infeasible，但用户指出当前**局部反应式限速**（v_cap_omega、v_cap_dkappa 在控制循环内实时截断速度）存在三个根本缺陷：

1. **效率差**：直道也因 lookahead 窗口捕获到远处弯道曲率而降速，轨迹整体拖慢。
2. **运动学违约**：从高速突然切入低速，切换过程本身可能超出 MPC 的加速度约束（|Δv|/dt > a_max），反而引发新的 infeasible。
3. **晃动抑制无效**：当 v≈0.10 m/s 时横向加速度几乎为零，液体不晃动，抑制效果无从体现。

正确做法：在路径接收时**一次性生成全局 v(s)** 剖面，通过梯形前向/后向遍历确保加减速平滑，局部 cap 仅作应急安全兜底。

### 算法：三步梯形剖面

```
①  v_geom(s) = min(v_des,
                   ω_max / κ(s),              # 角速度硬约束
                   √(α_max / |κ'(s)|),        # 角加速度硬约束
                   √(a_lat_max / κ(s)))        # 横向加速度（旧）
②  后向遍历（刹车可行性）:
     v_back(s) = min(v_geom(s), √(v_back(s+ds)² + 2·a_max·ds))
③  前向遍历（加速可行性）:
     v_final(s) = min(v_back(s), √(v_final(s-ds)² + 2·a_max·ds))
```

对于 dκ'(s)，采用相邻采样点的中心差分（边界点用单侧差分）：

```cpp
dkappa_abs = |κ[i+1] - κ[i-1]| / (2·ds)   // 内部点
dkappa_abs = |κ[1] - κ[0]| / ds             // 左端点
dkappa_abs = |κ[n-1] - κ[n-2]| / ds         // 右端点
```

### 修改文件与位置

#### 1. `types.h`：PathHandlerParams 新增两字段

```cpp
double speed_profile_omega_max = 0.0; // v(s) 规划用 ω_max (rad/s)，<=0 不限制
double speed_profile_alpha_max = 0.0; // v(s) 规划用 α_max (rad/s²)，<=0 不限制
```

#### 2. `local_planner_ros.cpp`：loadParameters() 中桥接运动学约束

在 `path_params_.base_frame = base_frame_;` 之后追加：

```cpp

path_params_.speed_profile_omega_max = vehicle_params_.omega_max;
path_params_.speed_profile_alpha_max = vehicle_params_.alpha_max;
```

#### 3. `path_handler.cpp`：updateSpeedProfile() 采样循环替换

**Before**（仅有横向加速度约束）：
```cpp
for (int i = 0; i < n; ++i) {
    const double s = std::min(total_len, i * ds);
    speed_profile_s_.push_back(s);
    double v = v_des;
    if (params_.max_lat_accel > 0.0) {
        double kappa_abs = std::abs(global_spline_.evaluateKappa(s));
        if (kappa_abs > 1e-4) {
            v = std::min(v, std::sqrt(params_.max_lat_accel / kappa_abs));
        }
    }
    speed_profile_v_.push_back(v);
}
```

**After**（三约束 v_geom，dkappa 由有限差分估计）：
```cpp
// 第一步：采样曲率，计算 v_geom(s) = min(v_des, ω_max/κ, √(α_max/|κ'|))
std::vector<double> kappa_arr(static_cast<size_t>(n));
for (int i = 0; i < n; ++i) {
    const double s = std::min(total_len, i * ds);
    kappa_arr[static_cast<size_t>(i)] = global_spline_.evaluateKappa(s);
}

for (int i = 0; i < n; ++i) {
    const double s = std::min(total_len, i * ds);
    speed_profile_s_.push_back(s);
    double v = v_des;
    const double kappa_abs = std::abs(kappa_arr[static_cast<size_t>(i)]);

    // 横向加速度约束：v² × κ ≤ a_lat_max
    if (params_.max_lat_accel > 0.0 && kappa_abs > 1e-4) {
        v = std::min(v, std::sqrt(params_.max_lat_accel / kappa_abs));
    }
    // 角速度约束：v × κ ≤ ω_max  →  v ≤ ω_max / κ
    if (params_.speed_profile_omega_max > 1e-3 && kappa_abs > 1e-4) {
        v = std::min(v, params_.speed_profile_omega_max / kappa_abs);
    }
    // 角加速度约束：v² × |κ'| ≤ α_max  →  v ≤ √(α_max / |κ'|)
    if (params_.speed_profile_alpha_max > 1e-6) {
        double dkappa_abs = 0.0;
        if (i == 0) {
            dkappa_abs = std::abs(kappa_arr[1] - kappa_arr[0]) / ds;
        } else if (i == n - 1) {
            dkappa_abs = std::abs(kappa_arr[n-1] - kappa_arr[n-2]) / ds;
        } else {
            dkappa_abs = std::abs(kappa_arr[i+1] - kappa_arr[i-1]) / (2.0 * ds);
        }
        if (dkappa_abs > 1e-4) {
            v = std::min(v, std::sqrt(params_.speed_profile_alpha_max / dkappa_abs));
        }
    }
    speed_profile_v_.push_back(v);
}
```

后续前向/后向遍历（步骤②③）逻辑不变，由原有代码完成。

- `<= 0.3 m/s` 占比从 `test7` 的 `90.8%` 回升到 `92.7%`

因此本改动已回退，恢复到 `test7` 对应的基线：

- 保留前面已验证有效的结构修正
- 不保留“去掉 0.8 减速折减”这一步

## 2026-04-18 规划层 alpha 预算与 MPC 硬约束解耦

### 判断

在 `test7` 的 `[SpeedProfile]` 中：

- `dom(alpha)` 仍占较大比例
- `v_geom_min ≈ 0.33~0.42`

而当前代码里存在一个结构问题：

```cpp
path_params_.speed_profile_alpha_max = vehicle_params_.alpha_max;
```

这意味着：

- 速度剖面规划层的 `alpha` 预算
- MPC 求解时的 `omega` 变化率硬约束

被强行绑定为同一个值。

这会造成双重保守：

1. 规划层先用 `v² * |dkappa| <= alpha_max` 压低 `v(s)`
2. MPC 内层再用 `|Δomega| <= alpha_max * dt` 做硬约束

### 修改

文件：

- `src/scout_apps/control/scout_local_planner/src/local_planner_ros.cpp`
- `src/scout_apps/control/scout_local_planner/config/mpc_params_sim.yaml`

1. `local_planner_ros.cpp`
   - 新增参数读取：
     - `path_handler/speed_profile_omega_max`
     - `path_handler/speed_profile_alpha_max`
   - 只在未显式配置时，才退回到 `vehicle/omega_max` 和 `vehicle/alpha_max`

2. `mpc_params_sim.yaml`
   - 明确配置：

```yaml
path_handler:
  speed_profile_omega_max: 2.0
  speed_profile_alpha_max: 8.0
```

其中：

- `speed_profile_omega_max` 仍与车辆一致
- `speed_profile_alpha_max` 在仿真里先放宽到 `8.0`
  - 仅作用于速度剖面规划
  - 不改变 MPC 内部的硬约束 `vehicle/alpha_max = 4.0`

### 原因

这不是补丁，而是把“规划预算”和“执行硬约束”拆开：

- 规划层可以更积极地给出弯道速度参考
- MPC 内层仍然保留真实 `omega` 变化率硬约束

这样不会破坏“符合 MPC 代价与约束”的目标，只是避免规划层提前双重限速。

## 2026-04-18 全局平滑缓存改为主几何来源

### 判断

`test2` 之后，`reference_path` 的几何尖峰已经明显下降，但速度仍偏慢。  
这说明主矛盾继续收敛到：**全局平滑路径本身仍然偏硬**，而不是 MPC 约束太严格。

当前代码里还存在一个结构问题：

- `global_points_map_smooth_` 仅作为局部窗口点源
- `global_spline_`（速度剖面用）和局部窗口修复链并未完全与这条平滑缓存统一

结果是：

- 局部窗口与速度剖面并不总是基于同一条几何
- smooth cache 的平滑强度也还不够高

### 修改

文件：

- `src/scout_apps/control/scout_local_planner/src/path_handler.cpp`

本次不再加局部补丁，而是把全局 smooth cache 本身做成更适合 tracking 的几何主来源。

1. 新增 `buildTrackingFriendlySmoothPath()`
   - 对 `global_points_map_` 进行最多 4 轮迭代平滑
   - 每轮执行：
     - `bsplineSmooth`
     - `resamplePath`
     - `sanitizePolyline`
     - `removeSinglePointSpikes`
   - 目标阈值：
     - `kappa <= 3.8`
     - `dkappa <= 45.0`
   - 只要几何仍有改善就继续，不再改善就停止

2. `global_points_map_smooth_` 改用上述函数生成

3. `global_spline_` 改为优先直接使用 `global_points_map_smooth_`
   - 这样速度剖面和局部窗口共享同一条平滑几何
   - 仅当 smooth cache 不可用时，才退回原始缓存 + 单次 B-spline

### 原因

这一步是结构收敛，不是新补丁。

目标是把“路径几何过硬”尽量在全局层解决，而不是：

- 先让全局缓存偏硬
- 再到局部窗口反复修补

也就是说：

- smooth cache 负责主要几何平滑
- local window 只负责局部取样和连续参数化
- speed profile 与 reference path 共享同一条平滑几何
