## 审查边界与核心判断

基于我能直接核对到的证据，你在 `experiment/georef-mpc-hybrid` 分支上的 OSCRS，已经不是“什么都没有”的状态，而是**`G` 已抽出、`F/R/S` 已经存在但仍然内嵌在一个单体 `post_processor` 中**。更准确地说：当前工程形态是 `G + monolithic S`，其中 `S` 这个“大块”实际上同时承担了执行可行性过滤、slosh rollout、slosh hard gate、score、selector、fallback、diagnostics 和 ROS 发布。`scripts/README.md` 也把当前主线明确写成 “MBF global path → Online GeoRef / OSCRS path post-processor → normal MPC tracking → bag / offline analysis”，而阶段性总结则把当前方法定位为 `OSCRS = G + S`，并指出 `post_processor` 仍然是 1000+ 行的大文件。fileciteturn8file0L1-L1 fileciteturn25file0L1-L1

我能直接确认的代码事实是：`candidate_generators.py` 现在只做一件事——调用 `smooth_path` 生成 GeoRef 候选，并以 `candidate_specs` 的顺序返回 `list[(name, points)]`；它已经把“候选生成”这个最小 G 层从主循环中抽了出来，而且文档和测试都把“同分时依赖候选顺序”视为必须保留的行为。fileciteturn6file0L1-L1 fileciteturn9file0L1-L1 fileciteturn26file0L1-L1

因此，当前实际还缺的不是“是否用了这些思想”，而是四件非常具体的工程缺口：

第一，**执行可行性层没有独立边界**。几何 gate、collision gate、`ay_ratio_limit` 和候选级 reject reason 仍混在 `evaluate_candidate()` 的一个大流程里，导致“为什么实物 fallback / 为什么没 takeover”很难做结构化诊断。阶段性总结也明确把这一块列为未来 `F` 层，要输出 `reject_stage / reject_reason`。fileciteturn25file0L1-L1

## 当前 OSCRS 的真实结构与 G/F/R/S 归类

如果把你现在的实现拆成方法层，而不是按文件看，它其实已经非常接近你想要的 `G → F → R → S → diagnostics`，只是边界没有落在代码模块上。

当前可直接认定为 `G` 的部分只有一个：`scripts/candidate_generators.py::generate_georef_candidates()`。它对 `base` 路径按 `candidate_specs` 顺序生成 `original / mild / medium / mid / strong` 等候选；其中 `original` 直接复用 `base`，其它项走 `smooth_path + sanitize_fn`。这部分已经是“候选生成器当前实例 = GeoRef smoothing”的一个干净最小实现。fileciteturn6file0L1-L1

当前应该归为 `F` 的部分，散落在 `anti_slosh_path_post_processor.py` 的 `evaluate_candidate()` 和 `check_candidate_collision()` 相关逻辑里：长度比、漂移、端点误差、方向保持、短段、曲率、point-cost 碰撞检查，以及 `ay_ratio_limit` 这类动态代理门限。阶段性总结也明确把这一组列成“geometry gate + safety gate”，并指出 `max_candidate_level` 这个 cap 目前也还寄生在 `S` 侧。fileciteturn17file0L1-L1 fileciteturn25file0L1-L1

当前应该归为 `R` 的部分，是 `forward_profile()` 与 `rollout_slosh_metrics()`。前者做基于曲率/横向加速度/切向加速度预算的前向速度剖面，后者用二阶模态模型滚动出 `slosh_h_p95`、`slosh_h_max`、`slosh_h_residual_max`、`slosh_eta_dot_rms`、`slosh_energy_rms`、`slosh_terminal_E` 等量。它们已经是完整的“rollout 物理层”，只是输出接口目前仍服务于一体化 row。fileciteturn17file0L1-L1

当前应该归为 `S` 的部分，是 `apply_oscrs_score()`、`select_oscrs_candidate()`、fixed candidate override、`fb` / `takeover` / `fallback` 语义、以及基于 `eta_lim_mm` 和 `residual_ratio` 的 OSCRS hard gate。阶段性总结把这一层的语义说得很清楚：`fb=0` 是 takeover 成功，`fb=1` 是只有 original slosh-safe，`fb=2` 是几何可行但 slosh hard gate 全失败，`fb=3` 是无可用几何候选。fileciteturn25file0L1-L1

当前应该归为 ROS adapter 的部分，是 topic/param 适配、`path_to_msg()`、`path_callback()`、publisher 管理和 debug path 发布。这里还存在一个非常重要的兼容性约束：`path_to_msg()` 已经被修成“保留 raw MBF path 首尾 orientation，只对中间点按候选切线赋 yaw”，因此你后续的 terminal 修复应放在**候选几何**而不是 message orientation 层。fileciteturn17file0L1-L1 fileciteturn25file0L1-L1

从这个角度看，你当前最合适的目标不是 full plugin OSCRS，而是一个非常克制的 “L2.5 结构”：

## 与 mpc_planner、T‑MPC++、SH‑MPC 的对照关系

你现在最该对齐的，不是把 urlmpc_planner upstream repositoryturn5search0 的 solver 或 C++ core 搬进来，而是对齐它的**架构骨架**。按照 urlT‑MPC++ paper pageturn5search0 和 AMR Lab 的官方说明，T‑MPC++ 的关键结构是：高层先生成多个拓扑不同的 guidance trajectory；每个 guidance 约束一个局部优化器去求对应行为的局部最优；然后在并行得到的局部轨迹里，执行**可行且总代价最低**的一条，并以 receding-horizon 方式循环。citeturn5search0turn6search1

你要做的 OSCRS `G → F → R → S`，和它最一致的地方在于：

多候选并行这件事是一致的。T‑MPC++ 是“多个拓扑 distinct 的 guidance / local-optimization candidate”；你这里是“多个 GeoRef path-shape candidate”。在方法论上，它们都属于“单次 replanning 里不只看一条候选”。citeturn5search0

“先排除不可行，再在可行集里选最优”也是一致的。T‑MPC++ 的不可行性主要来自碰撞/优化失败/局部约束；你这里的不可行性会拆成两层：`F` 负责几何/碰撞/执行代理可行性，`S` 再基于 slosh rollout 做 OSCRS hard gate 与 score 选择。这个“先形成 feasible set，再做 lowest-cost selection”的骨架是一致的。citeturn5search0

真正不一致的地方也要说清楚：你**不是**在做 T‑MPC++ 的 solver 级复现。你没有同伦类 guidance planner、没有并行局部优化器、没有把 tracking MPC 本体替换成 T‑MPC solver。你的 OSCRS 仍然是一个**reference-layer post-processor**，下游执行器仍然是你现有的 OSQP tracking MPC。也正因为如此，我不建议你追求“直接复用 mpc_planner 代码”，而是只复用它的“模块边界思想”。这个结论也和你自己的设计纪律一致：不引新 solver、不大改底层 C++ MPC、不为了论文强行引入强候选或 full plugin。fileciteturn25file0L1-L1

而在 `F` 层扩展上，与其说你该看 T‑MPC++，不如说你该看 urlSafe Horizon MPC paperturn4search2 与其前身的 scenario-based planning 思想。SH‑MPC 的核心不是“多 candidate”，而是把不确定障碍物的联合碰撞概率，用 scenario optimization 的方式转成整个 planning horizon 上的可验证安全约束；AMR Lab 的项目页也把 2021 的 Scenario-Based Trajectory Optimization 描述成“通过采样把不确定性转成确定性约束，并可对场景做几何裁剪/过滤”。这正好对应你将来要在 `F` 层预留的 localization fluctuation / uncertainty-aware feasibility hook。citeturn4search2turn6search0

所以，和你当前 OSCRS **最一致的论文结构**是这样的：

| 参考来源 | 你应借鉴的层次 | 不应借鉴的层次 |
|---|---|---|
| T‑MPC++ | 多候选、可行集过滤、最低代价选择、ROS adapter 与核心逻辑分离 | solver 生成、并行局部优化器、拓扑 guidance planner 本体 |
| SH‑MPC / Scenario-based planning | 把不确定性视作 feasibility 约束层、把“安全”放在 score 之前 | chance-constrained MPC solver 与 scenario optimizer 直接移植 |

这个对照的关键点是：你的**baseline 不是上游代码库，而是上游架构**。现阶段最接近的“结构基线”是 T‑MPC++；最值得预留给 `F` 层的“安全扩展基线”是 SH‑MPC。citeturn5search0turn4search2turn6search0

## 分阶段修改计划

**Commit 1：引入 `types.py` 与 `diagnostics.py`，但不改算法行为**

修改文件应包括 `scripts/oscrs/types.py`、`scripts/oscrs/diagnostics.py`、`anti_slosh_path_post_processor.py`。

## 关键实现细节的具体判定

`max_candidate_level` 应该怎么从 S 移到 G，同时保持旧行为？

我的建议是：**不要改旧 `generate_georef_candidates()` 的签名**，而是在 `oscrs/generators/georef.py` 里新增一个 wrapper。这个 wrapper 先按当前代码顺序构造 `capped_specs`，再调用旧函数。这样做的好处是，你仍然保留 `test_candidate_generators_equivalence.py` 所在的 legacy exact path，也不会让任何旧 import 失效。与此同时，`post_processor` 对“候选 cap”这个 GeoRef-specific 语义的了解可以消失。阶段性总结已经把“cap 在 S 层”列为 L2 的残留耦合，因此这是当前最值得先搬的那一条。fileciteturn9file0L1-L1 fileciteturn25file0L1-L1

tail protection 第一版应该“直接替换 raw tail”，还是做 blend？

我建议**第一版先做 `replace_raw_tail`，不要先做 blend**。原因不是 blend 不好，而是你当前最急的风险不是上游平滑度，而是 terminal consistency。现在你已经修过 endpoint orientation，但 summary 文档明确说 geometry tail 仍可能被 smoothing 改坏；因此第一版最稳的策略，是直接把最后 `D_tail` 米改回 `base` 路径的尾段，再重新 sanitize 一次。这样可以把 terminal approach 几何钉住，且调参透明。blend 可以作为 `tail_protect_mode=blend` 的第二阶段选项，但不应该先上实物 smoke。fileciteturn17file0L1-L1 fileciteturn25file0L1-L1

`tail_deviation` 和 `tail_heading_error` 怎么定义？

我建议都对着**resampled `base` 尾段**来定义，而不是对着原始 MBF path。因为当前 G/F/R/S 全部都是在 `resample(ds)` 之后的 `base` 上工作的。  
`tail_deviation` 用尾段窗口内的**最大弧长对齐点距离**，即
\[
d_{\text{tail}}=\max_{s\in[s_{\text{end}}-D,s_{\text{end}}]}\|p_c(s)-p_b(s)\|.
\]
`tail_heading_error` 用同一窗口内的**最大切线航向差绝对值**，即
\[
e_{\psi,\text{tail}}=\max_{s\in[s_{\text{end}}-D,s_{\text{end}}]}
|\mathrm{wrap}(\psi_c(s)-\psi_b(s))|.
\]
为了方便调试，可以同时记录 `p95`，但 gate 本身建议先用 `max`。这样它才是一个真正的 terminal consistency 代理，而不是平均效果量。这个设计也与“保留尾段几何而不是只保留 endpoint orientation”相一致。fileciteturn25file0L1-L1

collision gate 现在是 point-cost threshold，不是 footprint polygon，要不要换？

当前阶段**不要换**。`post_processor` 文件头和碰撞逻辑都明确说明，现有碰撞检查依赖 global costmap 的 inflation 层点代价阈值，而不是显式 footprint polygon。把它移入 `F` 层完全合理，但把它改成 footprint polygon 检查，会引入新的运行时语义和更多 frame/footprint-topic 耦合，这跟你现在的目标——“参考层可执行性增强，但不动主 MPC 和 solver”——是冲突的。我的建议是留下来，并在 `diagnostics.py` 里把 `collision_mode=point_cost` 明示到报告中。fileciteturn17file0L1-L1

`ay_ratio_limit` 属于 F 还是 S？

明确属于 **`F_dynamic`**。因为它衡量的是 candidate 相对 baseline 的执行侧横向激励代理，不是液体任务目标本身。放在 `F` 可以把“这条参考路径从车辆执行角度就已经太激进”与“这条路径车辆能跑，但 slosh 不安全”区分开。当前文档也正是把它归在 geometry/safety gate 一组里，而不是 OSCRS hard gate 一组里。fileciteturn11file0L1-L1 fileciteturn25file0L1-L1

`eta_lim / residual_ratio` 属于 F 还是 S？

它们应该留在 **`S`**。原因不是它们不“硬”，而是它们是**slosh-objective-specific hard gate**，依赖的是 rollout 输出，而不是 reference 的一般可执行性。把它们放在 `S_hard_gate`，正好对应你论文里“slosh-constrained selector”的方法主体，也更接近 T‑MPC++ 的“feasible lowest-cost among task-constrained trajectories”的结构表达。fileciteturn12file0L1-L1 fileciteturn25file0L1-L1

我建议**留在 selector**。它本质上是“选择策略 override”，而不是 ROS topic 适配。ROS adapter 负责把参数读进来并交给 selector；selector 决定是 fixed 模式、geometry-only 模式还是 OSCRS active 模式。这样做的好处是：bag-level 选择语义集中在一个模块内，更容易单测和比较 old/new。fileciteturn17file0L1-L1

`original` candidate 应不应该永远保留？要跳过哪些 gate？

应当**永远保留**，而且永远不被 generation cap 删掉。
