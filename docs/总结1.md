## 当前真正参与控制的数据链（先看这个）

当前代码里，真正参与控制/MPC 求解的数据链是：

```text
/scout/goal
    ↓
全局规划器（move_base / simple_global_planner / MBF）
    ↓
/scout/global_path              # 上游输入给 local planner 的几何路径 nav_msgs/Path
    ↓
PathHandler::updateGlobalPath() # 缓存、重采样、累计弧长、全局 v(s) 速度曲线
    ↓
PathHandler::getReferencePoints()
    ↓
ref_points: std::vector<ReferencePoint>
  - x, y
  - theta_path
  - kappa
  - v_path
  - s
  - v_ref
    ↓
MPCSolver::solve(current_state, ref_points)
    ↓
/cmd_vel
```

需要特别区分：

- `/scout/global_path`：**会参与控制**，是 `scout_local_planner` 的上游输入路径。
- `ref_points`：**会参与控制**，但它是 `PathHandler` 在进程内部生成的参考点序列，**不是 ROS 话题**。
- `/scout/global_path_smooth`：**不会参与控制**，只是把局部平滑样条发布出来做**可视化/录包**。
- `/local_path`：**不会作为控制输入回流**，它是 MPC 预测轨迹的**可视化输出**。

## 2. 当前系统的运行定位

### 2.1 从 ROS 角色上看

当前 `scout_local_planner` 是**局部规划器**：

- 上游输入：`/scout/global_path`、`/odom`
- 下游输出：`/cmd_vel`
- 内部周期性滚动求解，驱动底盘执行

### 2.2 从优化本质上看

当前 `scout_local_planner` 更准确的定位是：

**基于全局路径局部参考的 tracking MPC**

而不是：

- MPCC（Model Predictive Contouring Control）
- 自由空间局部轨迹优化器
- 走廊/障碍/进度统一优化器

原因很明确：

- `PathHandler` 先从全局路径生成一串局部参考点 `ref_points`
- `MPCSolver::solve(current_state, ref_points)` 再去跟踪这串参考
- 当前优化变量里**没有**路径进度 `s`
- 当前目标里**没有** progress reward
- 当前几何约束里**没有**统一的走廊/障碍半空间约束主链路

因此当前主范式是：

```text
global_path -> local reference -> MPC tracking
```

而不是：

```text
progress + geometry + obstacle + control 的统一联合优化
```

## 5. 全局路径的信息流

这一部分非常关键。当前全局路径并不是一个“带速度和时间的轨迹”，而是一条**几何路径**。

### 5.1 上游全局规划器提供什么

无论你当前使用：

- `move_base_global.launch`
- `simple_global_planner.launch`
- `mbf_global.launch`

最终给 `scout_local_planner` 的统一输入都是：

- `/scout/global_path`
- 类型：`nav_msgs/Path`

这条路径本质上只提供：

- `x`
- `y`
- pose orientation（姿态）

它**不直接提供**：

- `vx`
- `vy`
- `omega`
- `a`
- 每个点的时间戳轨迹语义 `t_i`

所以：

**上游给的是几何路径，不是时间参数化轨迹。**

### 5.2 MBF 路径链路

以当前主用 MBF 模式为例，信息流是：

```text
/scout/goal
    ↓
mbf_path_publisher_node
    ↓
/scout/mbf_costmap_nav/get_path   (action)
    ↓
GlobalPlanner / NavfnROS 插件在 global_costmap 上规划
    ↓
/scout/mbf_costmap_nav/GlobalPlanner/plan
    ↓
mbf_path_publisher_node 重新发布
    ↓
/scout/global_path
```

当前给 MPC 真正使用的是：

- `/scout/global_path`

而不是：

- `/scout/mbf_costmap_nav/GlobalPlanner/plan`

后者更像内部/调试输出。

### 5.3 `PathHandler` 如何处理这条路径

`PathHandler` 是 `scout_local_planner` 包内部类，代码在：

- `src/scout_apps/control/scout_local_planner/include/scout_local_planner/path_handler.h`
- `src/scout_apps/control/scout_local_planner/src/path_handler.cpp`

它负责把上游几何路径加工成 MPC 可用的局部参考。

#### 第一步：`updateGlobalPath(path, v_des)`

主要做这些事：

1. 检查路径点数是否足够
2. 做路径相似性检测
   - 如果新旧路径足够相似，不重置 `s_global_`
   - 避免 warm-start 和参考推进被频繁打断
3. 缓存原始全局路径
4. 可选重采样：`resample_spacing`
5. 计算累计弧长 `global_path_s_`
6. 构建全局样条 `global_spline_`
7. 生成全局速度曲线 `updateSpeedProfile(v_des)`

注意：

- `updateGlobalPath()` **不会先把路径整体变到 odom**
- 它缓存的是原始路径坐标（通常是 `map`）
- 真正局部窗口变换发生在 `getReferencePoints()` 中

#### 第二步：`updateSpeedProfile(v_des)`

当 `time_parameterize=true` 时，`PathHandler` 会在全局路径上生成一条 `v(s)` 速度曲线。

主要逻辑：

1. 曲率限速
   - `v <= sqrt(max_lat_accel / |kappa|)`
2. 前向加速扫描
   - 限制切向加速度不超过 `max_tan_accel`
3. 反向减速扫描
   - 限制切向减速度不超过 `max_tan_decel`
4. 末端收速
   - 根据 `goal_speed`、剩余弧长做停车收尾
5. 对速度曲线做平滑处理

因此：

- 上游没有给速度
- 速度是 `PathHandler` 在本地按几何曲率和动力学限制生成的

#### 第三步：`getReferencePoints(N, dt, v_des, ref_points)`

这是从全局路径生成 MPC 局部参考点的核心函数。

主要步骤：

1. 通过 TF 查 `base_frame <- global_path.frame_id`
2. 在全局路径上找机器人最近点
3. 用投影更新全局进度 `s_global_`
   - 并限制前进时 `s_global_` 不倒退
4. 截取局部窗口
5. 只把局部窗口变到 `base_link`
6. 局部样条拟合 `fitLocalSpline()`
7. 按 `time_parameterize` 方式生成 **N 个**参考点

当前每个 `ReferencePoint` 的真实字段是：

```cpp
struct ReferencePoint {
  double x;           // base_link 坐标系
  double y;           // base_link 坐标系
  double theta_path;  // 路径切线方向
  double kappa;       // 曲率
  double v_path;      // 路径推进速度
  double s;           // 弧长参数
  double v_ref;       // 代价函数使用的参考速度
};
```

注意：

- `ReferencePoint` **没有** `omega_ref` 字段
- `omega_ref` 是在代价函数里临时按 `v_ref * kappa` 计算
- `ref.x/ref.y` 是 **`base_link` 坐标系**，不是 `odom`

#### 第四步：终点捕获区

当前为了避免“离终点还不够近但参考速度已经掉成 0”的问题，`PathHandler` 做了近终点捕获处理：

- 参数：
  - `goal_capture_distance`
  - `goal_capture_min_speed`
- 当目标距离还没达标但已经进入捕获区时：
  - 强制 `v_ref >= goal_capture_min_speed`

这是为了解决：

- 还在 `TRACKING`
- 但速度提前降为近 0
- 导致看起来“停在终点外面”

#### 第五步：Frenet 误差与终点判定

`PathHandler` 还负责：

- `getFrenetState()`
  - 返回 `e_l`, `e_c`, `e_theta`
- `isGoalReached()`
  - 基于目标点距离 + 路径末端切线方向判定

注意：

- 终点 yaw 判定当前更偏向**路径末端切线方向**
- 不是单纯使用 goal pose 的 orientation

## 6. 当前 MPC 的结构

### 6.1 状态、控制、决策变量

当前增广状态为 8 维：

```text
x = [e_l, e_c, e_theta, v, eta_x, eta_x_dot, eta_y, eta_y_dot]
```

含义：

| 索引 | 名称 | 含义 |
|---|---|---|
| 0 | `E_L` | 纵向误差（lag error） |
| 1 | `E_C` | 横向误差（contour error） |
| 2 | `E_THETA` | 航向误差 |
| 3 | `V` | 线速度 |
| 4 | `ETA_X` | X 向模态位移 |
| 5 | `ETA_X_DOT` | X 向模态速度 |
| 6 | `ETA_Y` | Y 向模态位移 |
| 7 | `ETA_Y_DOT` | Y 向模态速度 |

当前控制量为 2 维：

```text
u = [a, omega]
```

含义：

| 索引 | 名称 | 含义 |
|---|---|---|
| 0 | `A` | 纵向加速度 |
| 1 | `OMEGA` | 角速度 |

注意：

- 当前是**直接控制角速度 `omega`**
- `omega` 不再作为状态量

### 6.2 当前时域和决策变量布局

当前典型参数：

- `N = 40`
- `dt = 0.05`
- `nx = 8`
- `nu = 2`

决策变量布局：

```text
z = [x_0, u_0, x_1, u_1, ..., x_39, u_39, x_40]
```

维度：

```text
nz = N * (nx + nu) + nx = 40 * (8 + 2) + 8 = 408
```

### 6.3 为什么说当前是 tracking MPC

因为：

- 它并不在 QP 里自己决定“沿哪条几何轨迹走”
- 它接收一串由 `PathHandler` 预先生成好的局部参考点
- 然后优化的是“怎么平滑、可行地跟上这些参考点”

所以当前目标不是：

- 最大化 progress
- 在自由空间中重新规划一条轨迹
- 联合决定进度/障碍/走廊/速度

而是：

- 最小化跟踪误差
- 最小化控制代价
- 满足动力学和边界约束
- 在此基础上可选地抑制液体晃动

## 7. 当前动力学模型

动力学模型实现在：

- `src/scout_apps/control/scout_local_planner/src/diff_drive_model.cpp`

### 7.1 基础 Frenet 模型

当前使用的是小角度近似下的差速 Frenet 跟踪模型：

```text
e_l_dot     = v - v_path
e_c_dot     = v * e_theta
e_theta_dot = omega - kappa * v
v_dot       = a
```

离散化方式：

- 欧拉离散化

因此 `predict()` 里对应的是：

```text
e_l(k+1)     = e_l(k) + dt * (v - v_path)
e_c(k+1)     = e_c(k) + dt * v * e_theta
e_theta(k+1) = e_theta(k) + dt * (omega - kappa * v)
v(k+1)       = v(k) + dt * a
```

### 7.2 slosh 子系统耦合

当前还把液体晃动增广进状态：

- `x_slosh = [eta_x, eta_x_dot, eta_y, eta_y_dot]`

在 `predict()` 中，当前 slosh 激励映射是：

- `ax = a`
- `ay = v * omega`

也就是默认把横向激励近似为离心加速度。

注意：

- 这是当前版本的工程近似
- 对四轮差速实物并不一定完全准确
- IMU 接口已预留，但当前实物话题中尚未确认真实 IMU 输入链

### 7.3 线性化方式

在 `linearize()` 中：

- 基础状态部分构建 `A`、`B`
- slosh 子系统使用 `SloshIntegration` 提供的离散矩阵 `A_slosh`, `B_slosh`
- 已补上 `ay = v * omega` 对 `v` 的偏导项：
  - `A(:, V) += B_slosh[:,1] * omega`
- 最终仿射项采用一致性写法：

```text
c = predict(x, u, ref, dt) - A*x - B*u
```

这是为了保证线性化和名义轨迹一致。

## 8. 当前代价函数

代价函数实现在：

- `src/scout_apps/control/scout_local_planner/src/cost_function.cpp`

### 8.1 当前优化目标骨架

当前代价函数本质上仍是 tracking cost：

```text
J = tracking error
  + speed tracking
  + control effort
  + control rate penalty
  + optional omega feedforward
  + optional slosh soft cost
  + terminal ramped tracking cost
```

### 8.2 逐项说明

#### 跟踪误差

基础模式：

- `Q_el * e_l^2`
- `Q_ec * e_c^2`
- `Q_etheta * e_theta^2`

如果开启 contour/lag 结构：

- `Q_lag * e_l^2`
- `Q_contour * e_c^2`

#### 速度跟踪

- `Q_v * (v - v_ref)^2`

这里的 `v_ref` 来自 `PathHandler` 的局部参考点。

#### 控制代价

- `R_a * a^2`
- `R_omega * omega^2`

#### 控制变化率代价

- `R_da * (a_k - a_{k-1})^2`
- `R_domega * (omega_k - omega_{k-1})^2`

#### 曲率前馈角速度

如果启用 `omega_ff`：

- `omega_ref = v_ref * kappa`
- 代价项为：
  - `Q_omega_ff * (omega - omega_ref)^2`

#### slosh 软代价

当前软代价为：

```text
Q_slosh_eta * (eta_x^2 + eta_y^2)
```

其中：

```text
Q_slosh_eta = Q_slosh * height_coeff^2
```

这个换算在 `LocalPlannerROS::initialize()` 中完成。

#### 终端 ramp 权重

当前不是只在最后一步抬权，而是：

- 最后 `terminal_ramp_steps` 步逐步放大
- 当前主要放大的项是：
  - `e_c`
  - `e_theta`
  - `v`

注意：

- 当前还没有单独的 terminal slosh residual 目标
- 当前终端更强调“到点/贴路径/收速度”，不是“液体模态速度归零”

## 9. 当前约束系统

约束管理器在：

- `src/scout_apps/control/scout_local_planner/src/constraint_manager.cpp`

### 9.1 状态约束

当前状态边界主要只约束：

- `v_min <= v <= v_max`

### 9.2 控制约束

- `-a_max <= a <= a_max`
- `-omega_max <= omega <= omega_max`

### 9.3 控制变化率约束

如果启用：

- `|omega_k - omega_{k-1}| <= alpha_max * dt`
- `|a_k - a_{k-1}| <= j_max * dt`

其中：

- `k=0` 使用 `u_prev_` 作为上一时刻输入

### 9.4 slosh 盒约束

当前已实现第一版盒约束代理：

- `|eta_x(k)| <= eta_bar`
- `|eta_y(k)| <= eta_bar`

但注意：

- `eta_bar` **不是**简单 `slosh_height_max / height_coeff`
- 当前实现会：
  1. 先给旋转抛物面项留预算
  2. 再把剩余 modal 高度预算除以 `height_coeff * sqrt(2)`

所以当前它是一个保守的 modal 位移代理约束。

### 9.5 动力学等式约束

QP 中还强制每一步满足：

```text
x_{k+1} = A_k x_k + B_k u_k + c_k
```

这才是 MPC 的核心。

## 10. `LocalPlannerROS` 的控制信息流

这一段是当前系统的主控制流程。

### 10.1 初始化阶段

`LocalPlannerROS::initialize()` 主要做：

1. 读取参数
2. 初始化 TF buffer
3. 初始化 `PathHandler`
4. 初始化 `MPCSolver`
5. 配置并接入 `SloshIntegration`
6. 计算：
   - `Q_slosh_eta`
   - `slosh_eta_bar`
7. 初始化订阅发布
8. 启动控制定时器

### 10.2 订阅输入

#### `globalPathCallback()`

收到 `/scout/global_path` 后：

- 调 `path_handler_.updateGlobalPath(*msg, vehicle_params_.v_max * 0.8)`
- 若成功，设置 `has_path_ = true`
- 如果当前在 `IDLE / REACHED / ERROR`，切到 `TRACKING`

#### `odomCallback()`

收到 `/odom` 后：

- 保存 `current_v_`
- 保存 `current_omega_`
- 保存 `current_odom_time_`
- 保存 `current_pose_`
- 调 `path_handler_.updateRobotState()`

#### `imuCallback()`

如果启用了阶段 7 的 IMU 参数，则会订阅 IMU：

- `linear_acceleration.y`
- `angular_velocity.z`
- 并对这些量做简单 EMA 滤波和差分

但当前根据实物话题清单：

- 尚未确认真实 IMU 输入话题存在
- 当前实物主链路仍主要使用 odom/模型估计

### 10.3 `controlLoop()` 逐周期流程

当前主控制循环顺序如下：

1. `updateState()`
   - 检查 odom/path 是否有效
   - 检查是否到达终点
2. 若 `PathHandler` 提示路径显著变化：
   - `resetWarmStart(true)`
3. `updateSloshEstimate()`
   - 估计 `ax`、`ay`、`alpha`
   - 更新 slosh 内部状态
4. `publishStatus()`
5. 根据状态机执行：
   - `IDLE / ERROR`：发 0 速
   - `REACHED`：发 0 速，并继续输出一段 slosh debug
   - `TRACKING`：执行 MPC 主流程

### 10.4 `TRACKING` 状态下的详细流程

#### 第一步：生成基础参考

先用基础目标速度：

```text
v_des_cmd = vehicle.v_max * 0.8
```

然后：

- `path_handler_.getReferencePoints(N, dt, v_des_cmd, ref_points)`

#### 第二步：speed governor（外环启发式速度治理）

如果启用了当前版本的 anti-slosh 速度治理，则：

- 读取当前 `slosh_height`
- 读取上一周期 `predicted_height_max`
- 读取前方曲率预览 `kappa_preview`
- 结合死区、滞回、最小保持周期，决定是否激活 governor
- 若激活，则计算更保守的 `v_des_eff`
- 再重新调用一次：

```text
getReferencePoints(..., v_des_eff, ref_points_governed)
```

说明：

- governor 不是直接修改现有 `refs[k].v_ref`
- 而是**重新生成一套参考点序列**

#### 第三步：获取 Frenet 误差

- `path_handler_.getFrenetState(frenet)`

得到：

- `e_l`
- `e_c`
- `e_theta`

#### 第四步：起点原地对齐（可选）

如果启用 `heading_align`：

- 只在起点附近生效
- 不在整个路径中都生效

当前实物默认一般不依赖这一项。

#### 第五步：构建当前增广状态 `x0`

```text
x0 = [e_l, e_c, e_theta, v, eta_x, eta_x_dot, eta_y, eta_y_dot]
```

其中：

- 前 4 维来自 Frenet 误差和当前速度
- 后 4 维由 `slosh_integration_.writeToAugmentedState()` 写入

#### 第六步：设置上一步控制量

- `mpc_solver_.setPreviousControl(last_control_)`

用于：

- `Δa`
- `Δomega`
- warm-start 一致性

#### 第七步：求解 MPC

- `solution = mpc_solver_.solve(current_state, ref_points)`

#### 第八步：发布控制与调试量

如果求解成功：

- `publishCmdVel(solution.v_cmd, solution.omega_cmd)`
- 保存 `last_control_`
- 发布 `/local_path`
- 计算并发布：
  - `/slosh/height_pred_max`
  - `/slosh/constraint_active`
  - `/mpc/solve_ms`
  - `/mpc/status_val`

如果求解失败：

- 执行降级控制：
  - 逐步减速
  - 缩放当前角速度
- 同时发布失败状态

## 11. `MPCSolver` 的求解流程

求解器实现位于：

- `src/scout_apps/control/scout_local_planner/src/mpc_solver.cpp`

### 11.1 初始化

初始化时主要做：

- 创建 `DiffDriveModel`
- 初始化 `CostFunction`
- 初始化 `ConstraintManager`
- 设置 slosh 盒约束开关
- 计算 `nz = 408`

### 11.2 每周期求解流程

`solve(current_state, reference_path)` 的流程：

1. `buildQP()`
2. `updateOSQP()`
3. `warmStart()`
4. `osqp_solve()`
5. `extractSolution()`

### 11.3 构建 QP 的关键步骤

#### 代价函数

- `cost_function_.buildQPCost(N, refs, P_, q_)`

#### 约束

- 初始条件约束：`x0 = current_state`
- 动力学等式约束
- 状态/控制/变化率约束
- slosh 盒约束（若启用）

#### 线性化名义轨迹

当前不是只在线性化 `k=0`，而是：

- 从上一轮解中恢复 `u_prev_seq`
- 滚动得到名义轨迹 `x_lin`
- 对每个 `k` 用 `(x_lin[k], u_prev_seq[k])` 做线性化

这比旧版更一致。

### 11.4 解的提取方式

当前输出提取已经不是旧版：

- 不是简单 `v_cmd = x_1(V)`
- 不是简单 `omega_cmd = u_0(OMEGA)`

当前实际提取方式是：

```text
v_cmd     = v0 + 0.5 * a0 * dt
omega_cmd = 0.5 * (omega0 + omega1)
```

这样做是为了让线速度和角速度在时间上更一致地对齐到 `t + 0.5 dt`。

## 12. `/local_path` 与 `/scout/global_path_smooth` 的真实含义

### 12.1 `/scout/global_path_smooth`

这是 `scout_local_planner` 本地发布的：

- 不是 MBF 直接输出

### 12.2 `/local_path`

这是当前 MPC 预测轨迹的可视化。注意几点：

- 起点被强制放在当前 `base_link` 原点
- 可视化恢复时主要使用 `e_c`
- 当前有意忽略 `e_l`
  - 这样弯道上看起来不容易锯齿
  - 但这也意味着它不是“真实底盘历史轨迹”

因此：

- `/local_path` 用来观察 MPC 的预测趋势
- 不是用来精确表示底盘真实行驶轨迹

## 14. 当前实物调参与关键结论

### 14.1 输出 EMA 已被证明会恶化基础跟踪

之前实物测试已经说明：

- 输出端 EMA 会引入预测-执行相位滞后
- 关闭 EMA 后，实物“左摇右晃”明显减轻

因此当前实物配置已经改为：

```yaml
filter:
  alpha_v: 1.0
  alpha_omega: 1.0
  kappa_boost: 0.0
```

这意味着：

- 基础跟踪阶段不再依赖输出低通
- 平滑性主要依靠 MPC 内部代价和约束来实现

### 14.2 当前实物调参顺序

当前推荐顺序是：

1. 先做基础跟踪基线
2. 再调转向平滑：
   - `R_omega`
   - `R_domega`
   - `lookahead_distance`
3. 若仍摆头，再调：
   - `Q_ec`
   - `Q_etheta`
4. 最后才怀疑模型问题

这也是为什么当前不建议立刻大改 MPC 结构。

## 15. 当前系统的整体结论

### 15.1 已经完成的部分

当前项目已经完成并可运行的核心内容包括：

- MPC + slosh 状态注入
- slosh 软代价
- 预测峰值监测
- 第一版盒约束
- 第一版速度治理

- 状态同步
- IMU 最小接口预留
- 离线 bag 分析链路
- 实验入口和文档整理

### 15.2 当前系统的准确定位

当前系统可以准确概括为：

**Scout Mini 差速/四轮差速移动机器人上的参考路径跟踪型 MPC 局部规划器，并已接入初版基于模型估计的液体晃动抑制机制。**

### 15.3 当前最重要的工程判断

- 它是 MPC，但不是 MPCC
- 它是局部规划器，但本质上仍是 tracking MPC
- 全局路径上游只给几何路径，不给速度/时间轨迹
- 局部参考、速度曲线、终点捕获都在 `PathHandler` 内部完成
- 当前 anti-slosh 已具备初版工程可用性
- 下一步不是继续大规模重构，而是：
  - 继续实物调参
  - 等 IMU 接入后做阶段 7 验证
  - 再决定是否做风险自适应 `Q_slosh`、terminal residual slosh 等增强

### 15.4 当前不建议立刻做的事

当前不建议立刻推进：

- 阶段 6 slack 重构
- MPCC 化改造
- 大规模 Frenet 模型结构重写
- 输出端再加回强 EMA

因为当前系统的主要瓶颈已经从“有没有功能”转移到：

- 实物一致性验证
- IMU 接入
- 基础路径跟踪调顺
