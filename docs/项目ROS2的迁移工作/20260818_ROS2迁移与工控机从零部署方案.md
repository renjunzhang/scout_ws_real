# Scout/S-MPCC 项目 ROS 2 迁移与工控机从零部署方案

> 日期：2026-08-18
>
> 当前阶段：迁移设计，尚未开始改代码
>
> 目标：在新工控机上从零建立可复现的 ROS 2 实物实验环境，并尽量保持现有 SPMPC 实物实验的算法、参数和评价口径不变。

## 0. 先给结论

### 0.1 推荐平台

第一阶段推荐使用：

```text
Ubuntu 24.04 LTS
ROS 2 Jazzy
C++17
ament_cmake + colcon
AgileX scout_ros2: Jazzy 代码先固定到已核对提交 48f70cbefa74b94d4442ed1a4ac9237a088abbb7
AgileX ugv_sdk: main 分支，先固定到已核对提交 f2704eacdc90357078cd93ec60aae08bb4baab35
acados: 延续实物验证组合 v0.5.4 / acados_template 0.5.1 / CasADi 3.7.2
```

选择 Jazzy 是因为新工控机从零部署，没有必要再绑定支持周期更短的 Humble；Ubuntu 24.04 和 ROS 2 Jazzy 的支持周期也更适合后续论文实验与维护。代价是当前 ROS 1 实物机验证过的 acados/Python 组合来自 Ubuntu 20.04 + Python 3.8，新机的 Python 3.12 codegen 环境必须单独验收，不能把操作系统升级和求解器升级混在一起。

AgileX 仓库还有一个需要冻结规避的问题：截至本方案核对时，Jazzy 代码实际位于远端 ref `refs/heads/origin/jazzy`，而仓库 README 给出的 `git clone -b jazzy` 与该 ref 不一致。`dependencies.repos` 应直接写上述完整 commit，不依赖分支名。等官方修正分支后，也仍应通过评审再更新锁定版本。

### 0.2 迁移原则

1. 不把当前 ROS 1 工作区原样复制到 ROS 2。
2. 先保证同输入下 SPMPC 数值结果一致，再改导航集成方式。
3. 第一阶段保持 SPMPC 为独立控制节点，不立即改成 Nav2 Controller 插件。
4. 底盘直接采用 AgileX 官方 ROS 2 驱动，自研代码不再维护一份底盘协议实现。
5. 全局导航直接转向 Nav2，不迁移 ROS 1 的 `move_base` 和 MBF。
6. 实物恢复顺序固定为：底盘 → 传感器 → TF → 定位 → 固定路径 → SPMPC shadow → B0 低速闭环 → 防晃组 → Nav2 全局路径。
7. `/cmd_vel` 必须只有一个最终发布者；所有控制器先进入速度仲裁节点。
8. 所有外部仓库、Python 包、求解器生成物和系统配置都必须可锁定、可校验，不能依赖“当前机器刚好能运行”。

### 0.3 本轮应该迁移和暂不迁移的范围

应迁移：

- `spmpc_local_planner` 当前 continuous MPCC 主线；
- `slosh_models` 中被 SPMPC 实际使用的 `LiquidSloshModel`；
- 固定路径和点到点实验入口；
- Scout Mini CAN 底盘、NanoScan3、WIT IMU；
- 地图、定位、全局路径输出；
- RealSense RGB 记录与离线液面评价链；
- SPMPC 自定义诊断消息、rosbag 录制和分析脚本。

第一阶段暂不迁移：

- ROS 1 `move_base_flex`/MBF；
- ROS 1 `move_base`、`nav_core` 插件体系；
- 历史 `scout_local_planner` 的 OSQP 主线；
- 全部 TEB、DWA、LT-DWA、`mpc_local_planner` 历史副本；
- Cartographer 独立 catkin 工作区和它的环境补丁；
- 当前尚未验证稳定的混合 Gazebo 模型链；
- 与当前实物主线无关的 GPU 液体仿真依赖。

对比规划器应在 SPMPC ROS 2 主线稳定后按论文需求逐个恢复，不能让它们阻塞主线迁移。

## 1. 三份 ROS 1 日志梳理

本节依据：

- [change_log.md](../重要文档/change_log.md)
- [change_log2.md](../重要文档/change_log2.md)
- [change_log3.md](../重要文档/change_log3.md)

三份文件同时记录了装机、ROS 环境、算法演进和实验结论。迁移时必须把“机器部署事实”和“某一时期的算法尝试”分开。

### 1.1 旧工控机的基础环境

| 项目 | ROS 1 已验证状态 | ROS 2 迁移含义 |
|---|---|---|
| 操作系统 | Ubuntu 20.04 | 新机使用 Ubuntu 24.04 LTS |
| ROS | ROS Noetic | 改为 ROS 2 Jazzy |
| 构建 | `catkin_make`，部分包用 `catkin_make_isolated` | 统一 `colcon build`，外部普通 CMake 依赖独立安装 |
| 环境 | 多个工作区在 `.bashrc` 中叠加 source | 改为单一项目环境脚本，禁止在 `.bashrc` 叠加多个工作区 |
| 旧 MPC 求解器 | OSQP v0.6.2 + osqp-eigen，Ubuntu 20.04 需源码安装 | 只服务旧 `scout_local_planner`；当前 SPMPC 主线不需要它 |
| 当前 SPMPC 求解器 | acados continuous MPCC | 必须重新编译 acados 并重新 codegen，不能复制旧 `.so` |
| 地图定位 | Gmapping、AMCL、Cartographer 均用过，后期以 Cartographer 纯定位为主 | ROS 2 首先用 Nav2 AMCL + 现有栅格地图；新建图优先 Slam Toolbox |
| 仿真 | Gazebo classic、官方底盘模型、本地传感器 bridge 多次调整 | 不作为第一次实物迁移的前置条件 |

旧环境出现过的典型问题：

- catkin 白名单被缓存，导致修改后的包没有参与编译；
- Cartographer 使用 isolated 安装后，可执行文件路径需要人工符号链接；
- `.bashrc` 中 Conan 的 glog/gflags/ceres 与系统库冲突；
- 多个工作区 source 顺序错误，`rospack` 找到另一套源码；
- 手工 source 主工作区会覆盖 Cartographer overlay；
- 地图 YAML 和脚本中存在 `/home/a`、`/home/geist` 等绝对路径；
- acados 环境变量写在 shell 交互守卫之后，非交互启动时读不到；
- generated acados 求解器没有进入仓库，新机器必须重新生成。

ROS 2 环境设计必须从结构上消除这些问题，而不是逐条复刻旧补丁。

### 1.2 旧底盘和传感器配置事实

| 设备 | 已验证配置 | 迁移时必须保留的合同 |
|---|---|---|
| Scout Mini | CAN `can0`，500000 bit/s | `can0` 名称、500 kbit/s、Scout Mini 型号、差速运动学 |
| NanoScan3 | 传感器 `192.168.50.11`，主机 `192.168.50.1`，UDP 端口可自动选择 | 固定网卡地址、`/scan_front`、`nanoscan3_front` frame |
| 激光外参 | `base_link -> nanoscan3_front`：约 `(0.125, -0.0425, 0.155)` m | 写入 URDF/xacro，只允许一个 TF 发布者 |
| WIT IMU | CH341，USB ID `1a86:7523`，`115200` baud，约 50 Hz | `/dev/imu_usb`、`/imu/data`、`imu_link`、时间戳和 50 Hz |
| IMU 外参 | `base_link -> imu_link`：粗测 `(0.10, -0.045, 0.0)` m，姿态暂为 0 | 保留为名义值，并明确它不是完整标定结果 |
| RealSense | D435，RGB 主实验曾使用 1920×1080 | RGB 是独立评价真值链，不应成为 SPMPC 控制启动硬依赖 |

IMU 日志中的重要结论：

- 厂家默认 udev 规则只覆盖 `10c4:ea60`，实物却是 `1a86:7523`，所以旧机曾退回 `/dev/ttyUSB0`；
- 正式迁移应按设备序列号优先绑定 `/dev/imu_usb`，只有没有序列号时才退回 VID/PID；
- 当前 SPMPC 默认液体观测源仍是 odom；processed-IMU 需要显式开启，并通过 READY、freshness、bias 和 fallback 检查；
- 实物默认保留 IMU yaw rate，横向加速度和完整外参不能在迁移时被“顺便默认开启”。

### 1.3 旧实物 ROS 运行链

旧实物过程可以压缩为下面八层：

```text
1. can0 建链
   -> scout_base 发布 /odom 和底盘状态，接收 /cmd_vel

2. NanoScan3
   -> /scan_front

3. 定位
   -> Cartographer localization 或 AMCL
   -> map -> odom -> base_link

4. IMU（防晃实验需要）
   -> /imu/data，frame_id=imu_link

5. RealSense（独立评价）
   -> /camera/color/image_raw 等

6. 全局规划
   -> move_base/MBF
   -> /scout/global_path 或固定路径 /scout/global_path_fixed

7. SPMPC
   -> 订阅 /odom、/imu/data、参考路径、/map
   -> 30 Hz 求解
   -> /cmd_vel

8. rosbag + RGB 离线分析
   -> 控制、状态、TF、相机和 SPMPC 诊断统一归档
```

当前 `spmpc_local_planner` 的主合同是：

| 类型 | ROS 1 接口 | 当前语义 |
|---|---|---|
| 输入 | `/odom` | 底盘状态和 odom 液体观测输入 |
| 输入 | `/imu/data` | processed-IMU 可选观测输入 |
| 输入 | `/scout/global_path_fixed` | 当前固定路径实物主入口 |
| 输入 | `/map` | 代价地图/地图输入；当前主线 obstacle OCP 尚未正式启用 |
| 输出 | `/cmd_vel` | 最终差速底盘指令 |
| 输出 | `/spmpc/*` | 求解状态、预测时域、液体状态、终点状态、延迟诊断等 |
| TF | `map -> odom -> base_link` | `use_tf_pose=true` 时用于机器人全局位姿 |

### 1.4 当前 SPMPC 与早期 ROS 1 MPC 的区别

早期 `scout_local_planner` 使用 OSQP 和增广状态模型；当前论文主线 `spmpc_local_planner` 已经转为：

- 30 Hz、`dt=0.0333333333 s`；
- 60 步预测时域；
- `continuous_mpcc_acados` 为正式主后端；
- `PARTIAL_CONDENSING_HPIPM` QP；
- B0、B_slosh、B_ours 等消融变体；
- 独立的 processed-IMU、observer selection、延迟相位、warm start、terminal 和 risk governor 模块；
- 大量 typed diagnostics 和实验冻结脚本。

因此，ROS 2 主线迁移不能以旧 OSQP 包是否可运行作为成功标准。OSQP 只在未来确实要恢复旧 baseline 时再装。

### 1.5 旧流程中不应继承的做法

- 不把 Cartographer 编译目录放到项目 `src` 内；
- 不在 `.bashrc` 中无条件 source 多个工作区；
- 不使用绝对用户目录作为地图、标定或 bag 路径；
- 不手工复制老工控机的 acados、HPIPM、BLASFEO 或 generated solver `.so`；
- 不让底盘、Nav2、SPMPC、遥控节点同时直接发布 `/cmd_vel`；
- 不同时由 URDF、静态 TF 节点和传感器 launch 发布同一条外参；
- 不在第一轮把 ROS 1 仿真 workaround 当作 ROS 2 实物依赖；
- 不使用浮动外部分支完成正式实验，所有版本都应写入 lock/manifest。

## 2. ROS 2 目标架构

### 2.1 第一阶段：行为保持架构

```text
NanoScan3 --------------------------> /scan_front ----┐
                                                     |
Scout Mini CAN -> scout_base -> /odom + odom->base --+--> Nav2 AMCL
                                                     |      |
WIT IMU ----------------------------> /imu/data ------+      +--> map->odom
                                                            |
RViz/Nav2 goal -> planner_server -> path adapter ------------+--> /scout/global_path_fixed
                                                                   |
                                                                   v
                                                     spmpc_local_planner
                                                     /cmd_vel_spmpc
                                                                   |
teleop -> /cmd_vel_teleop -----------------------------> twist_mux |
Nav2 emergency/recovery -> /cmd_vel_nav2 --------------------------+
                                                                   |
                                                                   v
                                                               /cmd_vel
                                                                   |
                                                                   v
                                                        AgileX scout_base

RealSense RGB -> rosbag2/离线液面评价，不反馈当前控制器
```

第一阶段不启动 Nav2 `controller_server`，避免它与独立 SPMPC 同时控制底盘。Nav2 只负责地图、定位和路径规划；一个很薄的 path adapter 调用 `ComputePathToPose` 并发布 `nav_msgs/Path` 给 SPMPC。

### 2.2 第二阶段：Nav2 原生集成，可选

只有独立节点版本完成数值和实物等价验证后，才考虑把 SPMPC 封装成 `nav2_core::Controller`：

```text
planner_server -> controller_server(SPMPC plugin) -> velocity_smoother/安全层 -> scout_base
```

这一步会引入 lifecycle、`setPlan()`、`computeVelocityCommands()`、costmap server 和 Nav2 行为树语义，属于第二次架构变更。它不应与 ROS1→ROS2 API 迁移同时进行。

这个树只保留五个自研 ROS 2 包：

1. `scout_bringup`：硬件和整机启动；

3. `spmpc_msgs`：自定义接口；

## 4. ROS 2 接口合同

### 4.1 话题和 TF

| 功能 | ROS 2 目标接口 | 类型/说明 |
|---|---|---|
| 底盘速度输入 | `/cmd_vel` | `geometry_msgs/msg/Twist`，只由 `twist_mux` 输出 |
| SPMPC 候选指令 | `/cmd_vel_spmpc` | `geometry_msgs/msg/Twist` |
| 遥控候选指令 | `/cmd_vel_teleop` | `geometry_msgs/msg/Twist`，优先级高于 SPMPC |
| 底盘里程计 | `/odom` | `nav_msgs/msg/Odometry`，由官方 `scout_base` 发布 |
| 底盘状态 | `/scout_status` | 官方 `scout_msgs/msg/ScoutStatus` |
| IMU | `/imu/data` | `sensor_msgs/msg/Imu`，`frame_id=imu_link` |
| 激光 | `/scan_front` | `sensor_msgs/msg/LaserScan`，`frame_id=nanoscan3_front` |
| 地图 | `/map` | `nav_msgs/msg/OccupancyGrid` |
| 固定/全局路径 | `/scout/global_path_fixed` | `nav_msgs/msg/Path` |
| SPMPC 诊断 | `/spmpc/*` | 保持现有名称和语义，便于实验脚本迁移 |
| 相机 | 通过 launch remap 固定项目话题 | 不假定不同 `realsense-ros` 版本的话题默认值相同 |

目标 TF 只有一棵树：

```text
map -> odom -> base_link -> nanoscan3_front
                         -> imu_link
                         -> camera_link
```

权威来源固定为：

- `map -> odom`：AMCL；
- `odom -> base_link`：第一阶段由 `scout_base`；
- 传感器静态外参：URDF + `robot_state_publisher`；
- 不再额外启动同名 `static_transform_publisher`。

若以后加入 `robot_localization` 融合 IMU，必须把底盘原始里程计改名为 `/wheel/odom`，并关闭底盘的 `odom -> base_link` TF，让 EKF 成为唯一发布者。第一阶段不要加入该变化。

### 4.2 QoS 约定

| 数据 | 推荐 QoS | 原因 |
|---|---|---|
| `/odom`、`/imu/data`、`/scan_front` | Sensor Data，best effort，depth 5～10 | 降低高频传感数据阻塞；与驱动协商后确认 |
| `/map` | reliable + transient local | 新节点启动后仍能取得最近地图 |
| 参考路径 | reliable + transient local，depth 1 | SPMPC 启动或重启后应取得当前路径 |
| `/cmd_vel*` | reliable，depth 1 | 只关心最新控制指令 |
| `/spmpc/*` | reliable，depth 10；大体量预测消息可单独调小 | 保留诊断完整性，同时避免控制回调被阻塞 |

必须为 rosbag2 准备 QoS override 文件。否则 ROS 2 中“话题能看到但 bag 没录到”可能只是 QoS 不匹配。

### 4.3 官方 `scout_ros2` 接入事实

核对的官方仓库：<https://github.com/agilexrobotics/scout_ros2.git>。

已核对 Jazzy 提交 `48f70cbefa74b94d4442ed1a4ac9237a088abbb7` 的 `scout_base`：

- 支持 Scout、Scout Mini、Scout Mini Omni；
- V1/V2 协议均走 CAN；
- `scout_mini_base.launch.py` 默认 `port_name=can0`；
- 订阅绝对话题 `/cmd_vel`；
- 发布 `/odom`、`/scout_status`；Jazzy 版已经移除 Humble 版的 `/rc_status`；
- 发布 `odom -> base_link`；
- 状态循环为 50 Hz；
- 位姿是对底盘速度积分得到的 dead reckoning，不是外部定位真值；
- 源码中没有项目级速度仲裁和明确的上层命令 watchdog。

因此迁移中要增加 `twist_mux` 和停止/超时实测，不应把“官方驱动能收到 Twist”直接等同于整机安全链完成。若旧实验脚本依赖 `/rc_status`，需要删除该依赖或另做适配；电池监控应从 `/scout_status` 的 `battery_voltage` 读取。

## 5. `spmpc_local_planner` 代码迁移方法

### 5.1 保持不动或只做命名调整的部分

下面这些目录应尽量保持数值代码不变：

```text
core/
dynamics/
estimation/
reference/
solvers/
warm_start/
```

先把它们编成一个普通 C++ target，例如 `spmpc_core`，再让 ROS 2 节点链接。核心 target 不应依赖 `rclcpp`、ROS 消息或 ROS 时钟。

当前仍需清理的边界：

- `command_history_buffer`、`execution_state_predictor` 中的 `ros::Time` 改为 `int64_t` 纳秒或 `std::chrono`；
- `imu_shadow_ros_adapter` 继续保持薄适配层，只在边界转换 ROS 2 `sensor_msgs::msg::Imu`；
- `LiquidSloshModel` 并入 `dynamics` 后，去掉对 ROS 1 `slosh_models` 包的依赖。

### 5.2 ROS API 对照

| ROS 1 | ROS 2 |
|---|---|
| `roscpp` | `rclcpp` |
| `ros::NodeHandle` | `rclcpp::Node` |
| `advertise/subscribe` | `create_publisher/create_subscription` |
| `ros::Timer` | `create_wall_timer` 或 ROS clock timer |
| `ros::Time` | `rclcpp::Time`；核心内部统一转纳秒 |
| `pnh.param()` | `declare_parameter()` + `get_parameter()` |
| `tf2_ros::Buffer` | 带 node clock 的 ROS 2 Buffer/Listener |
| `geometry_msgs::Twist` | `geometry_msgs::msg::Twist` |
| `nav_msgs::Path` | `nav_msgs::msg::Path` |
| catkin messages | `rosidl_generate_interfaces` |
| XML launch | Python launch |
| `rosbag record` | `ros2 bag record` |

### 5.3 参数迁移

ROS 2 参数必须全部显式声明。原 ROS 1 YAML 需要包在节点名和 `ros__parameters` 下，例如：

```yaml
spmpc_local_planner:
  ros__parameters:
    control_frequency: 30.0
    dt: 0.0333333333
    horizon_steps: 60
    solver_backend: continuous_mpcc_acados
    topics.odom: /odom
    topics.imu: /imu/data
    topics.reference_path: /scout/global_path_fixed
    topics.cmd_vel: /cmd_vel_spmpc
```

配置分层仍保留：

```text
common -> platform -> container -> variant -> experiment -> launch override
```

但要增加启动时的“有效参数快照”，并随 rosbag2 一起保存。正式实验禁止运行中动态修改求解器权重；ROS 2 parameter callback 只允许修改白名单中的观测或调试项。

### 5.4 回调和时钟

ROS 1 中 IMU 曾使用独立 spinner。ROS 2 推荐：

- 控制定时器放入 mutually-exclusive callback group；
- odom/path/map 放入状态 callback group；
- IMU 放入独立 callback group；
- 使用 `MultiThreadedExecutor`，但所有共享状态通过明确的 mutex 或双缓冲保护；
- 控制周期测量使用 steady clock；
- 消息新鲜度和 TF 使用 ROS clock；
- 所有时间在进入数学核心前统一转为纳秒，避免 ROS 1/ROS 2 类型渗透。

迁移回放必须覆盖时钟回退、future skew、IMU packet gap、接收时间与 header 时间不同等当前已有测试情形。

### 5.5 自定义消息

当前四个消息移动到 `spmpc_msgs`：

```text
PredictedHorizon.msg
PreSolveSnapshot.msg
SloshObserverDebug.msg
SloshObserverSelectionDebug.msg
```

`spmpc_msgs` 使用 `rosidl_default_generators`，运行依赖 `rosidl_default_runtime`。字段含义和单位不得在迁移时修改；若确实要改字段，增加版本字段或新消息，避免旧分析脚本静默误读。

### 5.6 acados 处理

当前仓库的 `generated/acados` 只有忽略规则，正式求解器 `.so` 没有跟踪。新机必须：

1. 按冻结版本编译 acados C 库；
2. 在独立 Python venv 中安装匹配的 `acados_template`、CasADi、NumPy、PyYAML；
3. 重新生成 `spmpc_b0` 和 `spmpc_slosh`；
4. 再执行 colcon/CMake；
5. 检查节点不是 stub；
6. 保存 acados、HPIPM、BLASFEO、generated solver 和配置文件的 SHA-256。

迁移时建议给 CMake 增加：

```text
-DSPMPC_REQUIRE_ACADOS=ON
```

正式构建若找不到 acados 或 b0/slosh 生成物，应直接配置失败，不能悄悄编译成 `ACADOS_NOT_IMPLEMENTED` stub。

Ubuntu 20.04 的 `t_renderer`/GLIBC 2.31 问题在 Ubuntu 24.04 上不应直接照搬，但仍要运行一次模板渲染和求解器创建 smoke。Python 3.12 下若冻结的 acados_template/CasADi 无法正常 codegen，应使用项目锁定的 Python 3.11 codegen 容器或隔离环境生成 C 代码，再在 24.04 上原生编译；不要为迁就系统 Python 直接升级 OCP 工具链，也不要复制旧 `.so`。

### 5.7 Nav2 接入顺序

第一版 `scout_navigation` 只做：

1. map server；
2. AMCL；
3. planner server；
4. `ComputePathToPose` action client；
5. 发布 `/scout/global_path_fixed`；
6. 不启动 controller server。

这样可以保持当前 SPMPC 的 Path 订阅合同。等独立节点版本通过实物等价验证后，再决定是否实现 `nav2_core::Controller`。

### 5.8 rosbag 和分析脚本

ROS 1 `.bag` 与 ROS 2 rosbag2 存储不同。迁移策略为：

- 旧 bag 不要求全部在线转换；先把回放必需的 `/odom`、`/imu/data`、Path、TF、控制指令和四个 custom messages 导出成带时间戳的 CSV/NPZ 基准；
- ROS 2 新实验优先使用 MCAP；如果 Jazzy 环境中 MCAP 插件未验证，则先用默认 SQLite3；
- RGB 仍可能产生约 10 GB/分钟的数据，bag 目录必须放在独立大容量盘；
- 录制脚本保存 metadata、QoS override、有效参数、Git commit、依赖 lock、求解器哈希和设备信息；
- Python 分析脚本把 ROS 1 `rosbag` 读取层与实际算法分离，增加 `rosbag2_py`/MCAP 读取适配器；
- RGB 在线检测仍不作为控制器启动前置条件。

## 6. 新工控机从零部署步骤

### 6.1 部署前冻结旧系统

在重装或停用旧机前先保存：

- 主仓库分支、commit、submodule commit 和 `git status`；
- `/etc/udev/rules.d` 中 CAN、IMU、RealSense 规则；
- 网卡名称、MAC、NanoScan3 IP 配置；
- `ip -details link show can0`；
- ROS 1 topic/type/frame/frequency 清单；
- `tf2_tools view_frames` 结果；
- 当前 SPMPC 全部 YAML 和启动参数；
- acados/HPIPM/BLASFEO/generated solver 哈希；
- 固定路径文件、地图、相机标定和正式实验 bag；
- 一条 B0 和一条当前推荐防晃组的完整基准运行。

建议给最后一个 ROS 1 可运行提交打只读 tag，例如：

```text
ros1-final-real-20260818
```

### 6.2 安装系统和基础工具

1. 安装 Ubuntu 24.04 LTS，记录 ISO 校验值；
2. 主机名、用户、时区统一，时区设为 `Asia/Shanghai`；
3. 启用 NTP/chrony，确认系统时间稳定；
4. 用户加入 `dialout` 等设备组；
5. 安装 Git、build-essential、CMake、Python venv、can-utils、网络和串口诊断工具；
6. 安装 ROS 2 Jazzy、rosdep、vcstool、colcon；
7. 安装 Nav2、Slam Toolbox、RViz2、teleop、twist_mux、robot_state_publisher、xacro；
8. 通过 `rosdep install --from-paths src --ignore-src -r -y` 解决包依赖；
9. 不在 `.bashrc` 中 source 项目工作区，只保留最小 ROS 发行版环境，项目运行统一使用 `scripts/setup_env.bash`。

建议系统包类别：

```text
ros-jazzy-ros-base
ros-dev-tools
python3-colcon-common-extensions
python3-vcstool
python3-rosdep
can-utils
python3-serial
ROS 2 Jazzy 的 navigation2/nav2-bringup/slam-toolbox/twist-mux/teleop-twist-keyboard
```

具体包名以 Jazzy apt 源和 `rosdep` 为准，部署脚本需要做“已安装/不可用”的显式检查。

### 6.3 配置设备

#### CAN

临时检查顺序：

```bash
sudo modprobe gs_usb
sudo ip link set can0 down
sudo ip link set can0 up type can bitrate 500000
ip -details link show can0
candump can0
```

确认适配器稳定后，用 systemd unit 持久化 `can0`，并设置启动失败可见。不要只依赖每次手敲命令。

#### NanoScan3 网口

- 按网卡 MAC 确定物理接口，不在文档中写死 `enpXsY`；
- 主机静态地址 `192.168.50.1/24`；
- 传感器地址 `192.168.50.11`；
- 禁止这张专用网卡走默认路由；
- 先完成 ping/UDP/驱动单节点检查，再启动整机 launch。

#### IMU udev

- 优先按 `idVendor=1a86`、`idProduct=7523` 加序列号绑定 `/dev/imu_usb`；
- 没有序列号且机器只接一个同型 CH341 时，才用 VID/PID；
- 用户加入 `dialout` 后重新登录；
- 验证 `115200` baud、50 Hz、`frame_id=imu_link`；
- 保持机器人静止完成 `[2,10) s` bias 窗口。

#### RealSense

- 安装与 ROS 2 版本匹配的 librealsense udev 规则；
- `realsense-ros` 使用源码或 apt 二选一，不能混装同名包；
- 先独立验证 RGB 分辨率、频率、曝光和相机时间戳；
- 为 `/data/<user>/spmpc_bags` 准备足够空间和写权限。

### 6.4 拉取并锁定源码

使用 `dependencies.repos` 管理：

```text
scout_ros2
ugv_sdk
sick_safetyscanners2
realsense-ros（可选）
```

开发阶段可以跟踪分支，第一次底盘和传感器 smoke 通过后立即把实际 commit 写回 manifest。正式实验只允许按 commit 拉取，不允许 `git pull` 后直接开跑。

### 6.5 安装 acados 和生成求解器

沿用旧机已经实测过的隔离原则：

```text
C/C++ 库：独立目录，例如 /opt/spmpc/acados-v0.5.4 或项目专用目录
Python codegen：独立 venv
运行环境：scripts/setup_env.bash
```

顺序固定为：

```text

-> 初始化全部 submodule
-> 编译并安装 libacados/libhpipm/libblasfeo
-> 建立 codegen venv
-> 固定 CasADi/acados_template/NumPy/PyYAML 版本
-> 生成 b0
-> 生成 slosh
-> 运行 solver create/solve smoke

```

RouteB/direct-omega 只在需要诊断实验时生成，不作为恢复实物主链的门槛。

### 6.6 构建和测试

推荐命令形态：

## 7. 分阶段迁移与放行步骤

### M0：冻结 ROS 1 基准

交付物：

- ROS 1 final tag；
- B0/防晃组基准 bag；
- 输入序列和期望输出；
- 参数、TF、设备和求解器哈希清单。

放行：能在旧机按文档重复启动并得到一致状态。

### M1：建立 ROS 2 骨架，只迁数学核心

动作：

- 创建上面的五包结构；
- 将 core/dynamics/estimation/reference/solvers/warm_start 编成 `spmpc_core` target；
- 吸收 `LiquidSloshModel`；
- 把 ROS 时间从 core 清除；
- 迁移现有 gtest 到 `ament_cmake_gtest`。

放行：不启动 ROS 节点，所有核心测试通过；固定输入下与 ROS 1 核心输出满足约定容差。

### M2：迁移消息和 ROS 2 节点外壳

动作：

- 建立 `spmpc_msgs`；
- 迁移订阅、发布、参数、TF、timer、diagnostics；
- 加 callback groups 和线程安全检查；
- 先令 `publish_cmd_vel=false`。

放行：回放标准输入时节点稳定运行，30 Hz 控制定时器无持续超期，所有诊断可录制。

### M3：底盘驱动独立验收

动作：

- 构建官方 `scout_ros2` + `ugv_sdk`；
- `scout_mini_base.launch.py` 连接 `can0`；
- 检查 `/odom`、`/scout_status` 和 TF；
- 架空轮或清空场地后进行短时 teleop；
- 测量停止指令和上层指令丢失后的实际行为。

放行：

- CAN 无持续 error frame；
- `/odom` 接近 50 Hz；
- `odom -> base_link` 连续且只有一个发布者；
- 速度方向和角速度符号与旧机一致；
- 急停、遥控抢占和指令超时均通过。

### M4：传感器和 TF 验收

动作：

- 启动 NanoScan3 ROS 2 驱动；
- 移植 WIT IMU 到 `rclpy`；
- 用 URDF 发布传感器外参；
- 可选启动 RealSense；
- 录制 60 秒静止数据。

放行：

- `/scan_front` 稳定，frame 正确；
- `/imu/data` 接近 50 Hz，绝大多数相邻 header 间隔小于当前 35 ms epoch-break 阈值；
- IMU 四元数范数、方向和静止 bias 检查通过；
- TF 无重复 authority、无断树；
- rosbag2 能按 QoS 完整录到传感器数据。

### M5：地图和定位

动作：

- 修正现有地图 YAML 为相对 PGM 路径；
- 用 Nav2 map server + AMCL 加载旧栅格地图；
- 若地图质量不足，再用 Slam Toolbox 重建，不先迁 Cartographer；
- 验证 `map -> odom -> base_link`。

放行：静止和低速运动时定位连续，无 TF 跳变；急停和转弯后的漂移不劣于 ROS 1 基准。

### M6：固定路径 SPMPC shadow

动作：

- 发布与旧实验相同的 `/scout/global_path_fixed`；
- SPMPC 使用 `/cmd_vel_spmpc`，但不接入 mux 输出；
- 先跑 B0，再跑当前防晃 variant；
- 同时记录输入、solver status、预测时域和 candidate command。

放行：

- 后端明确为 `continuous_mpcc_acados`；
- 不出现 `ACADOS_NOT_IMPLEMENTED`/`ACADOS_NOT_CREATED`；
- 正常段求解时间显著低于 33.3 ms 控制周期；
- progress、terminal、slosh observer、delay-phase 状态符合旧实验合同；
- 同一输入序列下 ROS 1/ROS 2 candidate command 差异在预先冻结的容差内。

### M7：B0 低速实物闭环

动作：

- 将 `/cmd_vel_spmpc` 接到 `twist_mux`；
- 先直线、再缓弯、再固定 S 曲线；
- 速度上限从低到正式值逐步放开；
- 每一步先做 20 秒 smoke，再做一条完整路线。

放行：无求解失败、无指令抖动、无 TF/定位异常、能安全停车和被 teleop/急停抢占。

### M8：防晃组和 RealSense 评价

动作：

- 保持路径和运动上限不变，只切换 B0/防晃 variant；
- 先用 odom observer 恢复历史可比性；
- processed-IMU 作为独立 A/B，不能在迁移基线中默认开启；
- 启动 RGB 记录但不把在线视觉接入控制；
- 用 ROS 2 分析适配器复跑相同指标。

放行：数据完整、有效参数和哈希完整、视觉和内部模型指标口径与 ROS 1 一致。

### M9：接入 Nav2 全局路径

动作：

- 启动 map server、AMCL、planner server；
- path adapter 调用 `ComputePathToPose`；
- 发布到 SPMPC Path 接口；
- controller server 保持关闭。

放行：点到点路径稳定，SPMPC 不因路径更新、frame、时间戳或 transient-local QoS 出现重置和停滞。

## 8. ROS 1 与 ROS 2 等价验证

### 8.1 核心数值层

对完全相同的状态、路径、参数和 warm start 输入比较：

- slosh dynamics 单步和多步 rollout；
- progress projection；
- reference spline；
- terminal controller；
- processed-IMU pipeline；
- observer selection；
- execution state prediction；
- acados 初值、状态、约束和第一个控制量。

纯 C++ 模块应使用严格浮点容差；acados 在不同编译器和 CPU 上允许小数值差异，但必须保持 solver status、约束活跃方向和控制趋势一致。

### 8.2 ROS 集成层

比较：

- 收到每个输入的时间和 header 时间；
- TF 查询结果；
- 控制定时器 jitter；
- `/cmd_vel_spmpc`；
- `/spmpc/status`、variant、backend；
- predicted horizon；
- slosh state/height；
- observer selection/fallback；
- terminal mode；
- delay compensation 和 command history。

不要用实物最终轨迹完全重合代替数值等价检查。DDS 调度、定位和底盘执行会引入变化，必须先把 core 和 wrapper 分层验证。

### 8.3 实物放行红线

出现以下任意一项，不允许进入正式实验：

- acados stub 或 generated solver 哈希未知；
- `/cmd_vel` 有多个最终发布者；
- TF 同一边存在多个 authority；
- 地图 YAML 仍含旧用户绝对路径；
- IMU 设备名依赖随机 `/dev/ttyUSB*`；
- SPMPC 定时器持续超过 33.3 ms；
- rosbag2 丢失 odom、Path、TF、控制指令或关键 `/spmpc/*`；
- SPMPC 因 QoS 收不到地图或路径；
- teleop/急停不能抢占；
- 控制指令中断后底盘停止行为未实测；
- RGB 评价所需标定、曝光、分辨率或时间戳没有记录。

## 9. 主要风险与处理

| 风险 | 后果 | 处理 |
|---|---|---|
| AgileX Jazzy ref 命名异常 | README 的 `-b jazzy` 可能拉取失败 | `dependencies.repos` 直接锁定 `48f70cb...`，不依赖分支名 |
| Python 3.12 与冻结 acados codegen 组合未实测 | 不能生成相同 OCP，或被迫改变求解器版本 | 先验证冻结组合；必要时只把 codegen 放入锁定的 Python 3.11 容器，运行时仍原生部署 |
| 官方底盘驱动绝对订阅 `/cmd_vel` | 多控制器抢占困难 | 用 `twist_mux` 输出唯一 `/cmd_vel` |
| 官方 odom 为速度积分 | 与实际运动存在漂移 | 第一阶段保持旧行为；依赖 AMCL 修正全局位姿，后续再评估 EKF |
| acados 未被 CMake 检出 | 节点静默成为 stub | `SPMPC_REQUIRE_ACADOS=ON`，构建失败优于运行失败 |
| generated solver ABI 变化 | 创建失败或数值变化 | 新机重新 codegen，保存版本和哈希，做固定输入回归 |
| ROS 2 QoS 不匹配 | 节点或 bag 收不到数据 | 固定 QoS 合同和 rosbag2 override，逐话题检查 offered/requested QoS |
| ROS clock/steady clock 混用 | freshness、延迟估计错误 | core 用纳秒；周期用 steady clock；消息/TF 用 ROS clock |
| MultiThreadedExecutor 竞态 | 状态撕裂、偶发控制异常 | callback group + 锁/双缓冲 + TSAN/高频回放测试 |
| 重复 TF | 定位跳变 | 每条 TF 指定唯一 authority，外参只放 URDF |
| 地图不能直接复用 | Nav2 加载失败 | 使用已有 `.pgm+.yaml`，全部改相对路径；`.pbstream` 不作为 Nav2 必需格式 |
| WIT IMU 设备名漂移 | 启动失败或连错串口 | 以序列号 udev 绑定 `/dev/imu_usb` |
| RGB 数据吞吐过大 | bag 写盘阻塞、磁盘爆满 | 独立高速盘、预留容量、测写速、拆分控制 bag 与全量 RGB bag |
| 迁移时顺便调参 | 无法判断差异来自 ROS 还是算法 | 参数冻结，先等价再调参 |

## 11. 建议的第一批开发任务

建议单独建立迁移分支，例如：

```text
migration/ros2-jazzy
```

第一批提交只做以下内容：

1. 新建 ROS 2 工作区骨架和 `dependencies.repos`；
2. 新建 `spmpc_msgs`；
3. 将 SPMPC core 编译为无 ROS 的 C++17 library；
4. 并入 `LiquidSloshModel`；
5. 迁移现有核心 gtest；
6. 加入 acados 必需性检查和 solver codegen 脚本；
7. 暂不连接底盘、不迁 Nav2、不发 `/cmd_vel`。

第一批通过后再做 ROS 2 wrapper。这样任何数值变化都能在接入 DDS、TF、Nav2 和硬件前发现。

## 12. 当前推荐实施顺序

```text
冻结 ROS 1 实物基准
-> 新机装 Ubuntu 24.04 + Jazzy
-> 固定 scout_ros2/ugv_sdk
-> 独立跑通 CAN 底盘
-> 建立 ROS 2 项目骨架
-> 迁 SPMPC core 和测试
-> 重建 acados/generated solver
-> 迁 ROS 2 wrapper，shadow 回放
-> 迁 NanoScan3 + IMU + TF
-> Nav2 AMCL 加载旧栅格地图
-> 固定路径 B0 shadow
-> B0 低速实物
-> 防晃 variant
-> RealSense/rosbag2 评价链
-> Nav2 planner path adapter
-> 最后再恢复论文所需 baseline
```

这个顺序的核心目标是：先恢复一条最短、可解释、可安全停下的实物闭环，再逐层增加导航和实验功能；每一层都有独立放行条件，避免把驱动、QoS、TF、求解器和防晃效果混成一个问题。
