## 1. 当前结论

当前 `Q=0` 仍然出现：

- 跟踪过程中左右摇摆
- 有些目标点终点不收敛

因此，当前主问题不是 `slosh` 项，也不是 `Q_slosh` 设置，而是：

- base tracking
- terminal logic
- 执行链滞后

换句话说：

- **先把基础 MPC 执行链和终点逻辑修顺**
- **再继续谈 anti-slosh 的实验解释**

## 2. 已有证据支持的根因

### 2.1 `goal_stop_pending_` 当前是“进容差区就硬切零速”

当前 `LocalPlannerROS` 的行为是：

- 一旦 `path_handler_.isGoalReached()` 为真
- 就先把 `goal_stop_pending_ = true`
- `controlLoop()` 在 `TRACKING` 分支里检测到该标志后，直接：
  - `publishCmdVel(0.0, 0.0)`
  - `return`

这意味着当前终点最后一段不是“继续由 MPC 连续减速和纠偏”，而是：

- **先进入容差区**
- **再由外层状态机直接切零速**

这会导致：

- 进容差区时速度如果还大，容易冲过头
- 切零后不再由 MPC 继续末端纠偏

当前证据：

- `bag: slosh_QQ0_1_20260320_163754.bag`
- `goal1` 最近到目标时：
  - `closest_dist ≈ 0.006 m`
  - `closest_yaw_err ≈ 0.012 rad`
  - 同时最近 `odom v ≈ 0.807 m/s`
  - 但最近 `cmd_vel = (0, 0)`

这说明：

- **当前停法确实是“高速进入容差区后外层硬切零”**

### 2.2 `isGoalReached()` 的终点 yaw 判定当前不可靠

当前 `PathHandler::isGoalReached()`：

- 不优先使用 goal pose 自己的 orientation
- 而是用 `global_path` 最后两个点的切线方向做终点 yaw

但当前 bag 里多条 `global_path` 的尾巴已经显示：

- 最后两个点几乎重合
- `tail_ds` 基本在 `1e-7 m` 量级

这会直接导致：

- 终点切线方向退化
- yaw gate 不稳定或物理意义变弱

因此当前终点不收敛里，有一部分不是“MPC 不会停”，而是：

- **终点几何定义本身就不干净**

### 2.3 执行链存在额外滞后

当前有两层会让实际 `omega` 慢于优化器期望：

1. `LocalPlannerROS::publishCmdVel()`
   - 对 `v` / `omega` 做了 EMA 低通
2. `MPCSolver`
   - `omega_cmd` 不是直接取 `u_first(omega)`
   - 而是取首两步均值

这会带来：

- 输出角速度比优化器假设更慢
- 路径误差修正容易过头再反向修
- 外观看起来像左右摇摆

这里的判断是：

- **滞后是强嫌疑项**
- 但应先做最小 A/B，再决定是否永久改成“无滤波 + 直接第一步”

## 3. 第一优先级修改

### 3.1 修改 `PathHandler::isGoalReached()` 的终点 yaw 来源

修改目标：

- 不再把“最后两个 path 点切线”作为唯一终点 yaw 来源

建议顺序：

1. **优先使用 goal pose 自己的 orientation**
2. 如果 goal orientation 不可信，再从路径尾部往前寻找一个**非退化段**
3. 不要直接使用最后两个几乎重合的点

同时建议：

- 在路径更新时，去掉尾部重复点 / 近重复点

涉及文件：

- `src/scout_apps/control/scout_local_planner/src/path_handler.cpp`

修改目标不是“让终点 yaw 更漂亮”，而是：

- **先让终点判定几何口径成立**

### 3.2 去掉 `goal_stop_pending_` 的“进容差就直接零速”

修改目标：

- 不再在进入 goal 容差区后立刻 `publishCmdVel(0,0)`

建议改法：

- 只有在：
  - `goal_pose_reached == true`
  - 且 `speed_low == true`
- 才真正切到 `REACHED`

在这之前：

- 即使已经进了位置/姿态容差
- 也继续让 MPC 工作
- 继续受控减速与纠偏

也就是把当前逻辑：

- “进容差就硬停车”

改成：

- “进容差但还没低速，就继续受控收住”

涉及文件：

- `src/scout_apps/control/scout_local_planner/src/local_planner_ros.cpp`

这一刀的目标是：

- **把终点最后一段重新交回给控制器**

## 4. 第二优先级修改

### 4.1 做执行滞后的最小 A/B

这一阶段先不要大改权重。

先做两个 A/B：

#### A. 关闭输出 EMA

临时改成：

- `filter.alpha_v = 1.0`
- `filter.alpha_omega = 1.0`
- `filter.kappa_boost = 0.0`

目的：

- 验证左右摇摆是不是主要来自输出滤波滞后

#### B. `omega_cmd` 直接取第一步

临时改成：

- `solution.omega_cmd = solution.u_first(ControlIndex::OMEGA)`

而不是：

- 首两步均值

目的：

- 验证 `omega` 额外半步滞后是否是主要摇摆来源

涉及文件：

- `src/scout_apps/control/scout_local_planner/src/local_planner_ros.cpp`
- `src/scout_apps/control/scout_local_planner/src/mpc_solver.cpp`

### 4.2 终点捕获参数收紧

只有在完成 3.1 / 3.2 后，终点仍然经常“往里拱”时，再做这一步。

优先改：

- `goal_capture_min_speed: 0.08 -> 0.0` 或 `0.02`
- `goal_capture_distance: 0.50 -> 0.25 ~ 0.30`

目的：

- 降低 near-goal 阶段“被保底速度继续往前推”的副作用

涉及文件：

- `src/scout_apps/control/scout_local_planner/config/mpc_params.yaml`

## 5. 当前不建议做的修改

下面这些暂时不要和前两刀混在一起：

- 大范围重调 `Q_contour / Q_lag / R_domega / Q_omega_ff`
- 引入 terminal reverse
- 新增 terminal recovery 模式
- 再次大改 `lookahead_distance`
- 同时改 IMU 开关、anti-slosh 参数、终点逻辑

原因：

- 这些修改会把根因混在一起
- 当前还没必要

按第一性原理，当前最短路径是：

1. 修终点几何定义
2. 修终点硬停逻辑
3. 验证执行滞后
4. 最后才调参数

## 6. 修改后验证顺序

每次只改一项或一类，并录新 bag。

建议顺序：

1. 只改 `isGoalReached()` yaw 判定
   - 录一条 `Q=0` bag
2. 再改 `goal_stop_pending_`
   - 再录一条 `Q=0` bag
3. 再做“关闭 EMA / 关闭 omega 两步均值”的 A/B
4. 如果终点仍然常常往里拱，再收 `goal_capture_*`

验证时重点看：

- `/mpc_status`
- `/cmd_vel`
- `/odom`
- `/scout/goal`
- `/scout/mbf_costmap_nav/exe_path/feedback`
- `/scout/mbf_costmap_nav/move_base/feedback`
- `/local_path`
- `/scout/global_path_smooth`

通过标准：

- 左右摇摆明显减弱
- 终点最近距离稳定进入容差区
- 终点最后一段不再表现为“高速进容差后直接砍零”
- `Q=0` 下 base planner 自身先稳定

## 7. 一句话执行建议

当前最值得立即动代码的只有两刀：

1. 修 `PathHandler::isGoalReached()` 的终点 yaw 口径
2. 去掉 `goal_stop_pending_` 的“进容差就直接零速”

这两刀做完，再做“输出 EMA / `omega_cmd` 两步均值”的最小 A/B。  
在这之前，不要再继续大范围扫权重。

## 8. 已完成修改记录

### 2026-03-20 第一优先级两刀已落地

#### 已完成修改 1：终点 yaw 判定优先使用 goal pose orientation

- 修改文件：
  - `src/scout_apps/control/scout_local_planner/src/path_handler.cpp`
- 修改内容：
  - `PathHandler::isGoalReached()` 不再只依赖 `global_path` 最后两个点的切线方向
  - 现在优先使用 goal pose 自身的 quaternion orientation
  - 若 goal orientation 不可用，再回退到路径尾部向前搜索的非退化切线
- 修改目的：
  - 修复尾部重复点导致的终点 yaw 判定退化问题

#### 已完成修改 2：`goal_stop_pending_` 不再直接硬切零速

- 修改文件：
  - `src/scout_apps/control/scout_local_planner/src/local_planner_ros.cpp`
  - `src/scout_apps/control/scout_local_planner/include/scout_local_planner/local_planner_ros.h`
- 修改内容：
  - `TRACKING` 分支中不再因为 `goal_stop_pending_` 直接 `publishCmdVel(0,0)` 并 `return`
  - 现在 `goal_stop_pending_` 只表示：
    - 已进入 goal pose 容差区
    - 但仍需继续由 MPC 将速度收低
  - 进入该状态后，将 `v_des_cmd` 压到 `0.0`，继续让 MPC 负责最后一段减速和纠偏
- 修改目的：
  - 避免“高速进容差区后外层直接砍零”导致的冲过头与滑行

#### 已完成修改 3：`goal_stop_pending_` 下 `v_des_cmd=0` 现在会真正压住参考速度

- 修改文件：
  - `src/scout_apps/control/scout_local_planner/src/path_handler.cpp`
- 修改内容：
  - `PathHandler::getReferencePoints()` 在 `time_parameterize` 分支里，原先会优先使用 `speed_profile`
    生成 `v_ref`
  - 现在将外部传入的 `v_des` 视为**硬上界**
  - 当 `goal_stop_pending_` 触发、上层把 `v_des_cmd` 压到 `0.0` 时，
    `ref.v_ref` 不会再被 `speed_profile` 或 near-goal 下界重新抬回正值
- 修改目的：
  - 修复“上层要求终点减速，但参考速度源头仍然继续给正向速度”的结构错误
  - 让终点最后一段真正具备‘先参考停住，再判断低速切 REACHED’的必要条件

#### 已完成修改 4：`goal_stop_pending_` 增加最小锁存 / 滞回释放

- 修改文件：
  - `src/scout_apps/control/scout_local_planner/src/local_planner_ros.cpp`
- 修改内容：
  - `updateState()` 不再因为 `isGoalReached()` 一帧返回 `false` 就立即清掉
    `goal_stop_pending_`
  - 现在一旦进入 `goal_stop_pending_`，只要机器人还没有明显离开终点区，
    就继续保持 terminal stop 状态
  - 仅当：
    - 收到新的 goal pose 并重新进入别的状态链，或
    - 当前 `goal_dist` 明显大于释放阈值
      `max(goal_capture_distance, goal_tolerance + 0.15)`
    时，才释放 `goal_stop_pending_`
- 修改目的：
  - 消除“进圈一帧开始刹车 -> 因惯性/定位微漂出圈一帧又恢复巡航参考”的
    终点边界震荡（limit cycle）
  - 保持 `REACHED` 判定仍然严格要求：
    - `goal_pose_reached == true`
    - `speed_low == true`
