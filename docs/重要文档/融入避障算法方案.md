## 协作原则

1. 不要假设我清楚自己想要什么。动机或目标不清晰时，停下来讨论。
2. 目标清晰但路径不是最短的，直接告诉我并建议更好的办法。
3. 遇到问题追根因，不打补丁。每个决策都要能回答“为什么”。
4. 输出说重点，砍掉一切不改变决策的信息。
5. 修改日志统一记录在 `融入避障算法方案log.md`。

## 当前判断

- 当前 `scout_local_planner` 还是参考路径跟踪型 MPC，不是 obstacle-aware MPC，也不是 MPCC。
- 当前系统已经有局部障碍感知基础设施：
  - `/scout/mbf_costmap_nav/local_costmap/costmap`
  - `/scan_front`
- 当前 MPC 主体是 `OSQP + successive linearization + affine QP`。
- 当前近终点仍有 `terminal recovery` 外层逻辑，因此避障接入必须尽量避免同时改动：
  - `PathHandler`
  - slosh 子系统
  - near-goal recovery

结论：

- 不应该直接把参考项目整个搬进现有控制链。
- 应该只借鉴它的“障碍几何代理 + 安全约束思路”，保留当前 `PathHandler -> MPCSolver -> OSQP` 主体。

## 当前方案还缺什么

上一版方案已经回答了“参考什么”和“先走哪条路”，但还不够完整，主要缺 5 件事：

- 没把“为什么一定要改”写成工程目标。
- 没把“哪些东西故意不改”写成非目标。
- 没把“改完后整条控制链长什么样”画出来。
- 没把“最可能出问题的地方”提前列成风险清单。
- 没把“文件应该怎么放、为什么这么放”写清楚。

本轮补的就是这 5 件事。

## 修改目的

这次把避障接入当前 MPC，不是为了追求论文形式更漂亮，而是为了解决当前系统已经明确存在的工程缺口。

### 直接目的

- 让当前局部控制器对局部障碍“有机制上的反应”。
- 避免出现“全局路径贴障碍物很近，tracking MPC 仍按参考硬跟，导致实车有撞障机制风险”的情况。
- 在不推翻当前 `tracking MPC + slosh + terminal recovery` 结构的前提下，补上局部安全约束层。

### 间接目的

- 保住当前已经跑通的基础跟踪、终点收敛和 slosh 相关链路。
- 给后续动态障碍、严格 D-CBF、甚至 MPCC 化改造留接口，而不是把代码写死成一次性补丁。
- 让避障问题的排查路径变清楚：
  - 是障碍输入不对
  - 还是障碍代理不对
  - 还是安全约束不对
  - 还是求解器/参数不对

### 非目标

本轮方案明确不追求以下目标：

- 不把当前系统一次性改造成完整 MPCC。
- 不把当前求解器从 `OSQP` 换成 `casadi/ipopt` 或其它 NLP 求解器。
- 不同时重写 `PathHandler`、slosh 子系统、terminal recovery。
- 不在 v1 就把动态障碍预测和严格 D-CBF 全做完。
- 不追求“第一刀就最优绕障”，优先追求“可控、可回滚、可验证”。

## 参考项目结论

参考仓库：`/home/a/scout_ws/src/MPC-D-CBF`

本轮确认到的关键结构：

- `local_map`
  - 点云转局部栅格/梯度图

  - 椭圆障碍拟合
- `obs_param`
  - 对障碍参数做跟踪和预测

可借鉴点：

- 把障碍物先压缩成少量几何代理，再进优化器。
- 障碍约束不直接对原始点云/整张地图求解。

不能照搬的点：

- 它的求解器是 `casadi/ipopt`，你当前是 `OSQP`。
- 它的状态是世界系位姿，你当前是 `Frenet tracking + slosh` 增广状态。
- 它的障碍输入链是 `velodyne/grid_map/DBSCAN/ellipse/KF`，你当前现成可用的是 `local_costmap` 和激光。

结论：

- 参考项目适合拿来学“障碍表达和约束形式”。
- 不适合直接作为你当前 `scout_local_planner` 的代码底座。

## 推荐路线

### 方案目标

在不破坏当前 tracking MPC 主链的前提下，先做一版：

- 保留 `PathHandler` 生成参考路径的职责不变
- 保留 `MPCSolver` 的 OSQP QP 求解框架不变
- 新增一层“障碍代理 + 线性化安全约束”
- 先做静态/准静态障碍
- 动态障碍和严格 D-CBF 放到第二阶段

### 为什么先不用参考项目那套完整 D-CBF

原因不是“它不好”，而是“不适合你现在这套结构”：

- 直接移植会迫使你改求解器或把当前 QP 变成 NLP。
- 直接移植会迫使你把 `Frenet` 状态重写成世界系位姿主状态。
- 直接移植会把现有 slosh、terminal、tracking 回归一次性全部打散。

这条路风险太高，不是当前最短路径。

### 为什么当前推荐路线更短

因为你现在最值钱的东西不是“理论上换成更强的优化器”，而是已经存在的这几条可用链路：

- `global_path -> PathHandler -> ref_points`
- `current_state -> MPCSolver -> OSQP`
- `local_costmap`
- `terminal recovery`
- `slosh` 状态注入和调试链

如果直接迁移参考项目，你会同时失去这几条链路的稳定性。  
如果只新增“障碍代理 + 安全约束层”，当前系统的大部分正确性可以保留。

### v1 推荐接法

#### 1. 障碍输入源

v1 优先使用：

- `/scout/mbf_costmap_nav/local_costmap/costmap`

必要时保留备用源：

- `/scan_front`

原因：

- 这是你现有系统已经跑通的链路。
- 比从参考仓库移植 `velodyne -> grid_map -> ellipse` 短很多。
- 可以先把“控制器接入避障”这个核心问题做出来，再讨论障碍建模精度。

#### 2. 新模块边界

建议新增独立模块，而不是把逻辑塞进 `PathHandler`：

- `ObstacleProxyManager`
  - 输入：`local_costmap` 或 `LaserScan`
  - 输出：少量障碍代理
  - v1 代理优先选“膨胀圆”或“轴对齐/定向椭圆”
- `ObstacleConstraintBuilder`
  - 输入：参考点、名义轨迹、障碍代理
  - 输出：可并入 OSQP 的线性不等式约束

不建议让 `PathHandler` 直接负责避障，因为：

- `PathHandler` 当前职责是“路径窗口化 + 参考生成”
- 一旦把障碍决策塞进去，会把“上游参考”和“下游安全约束”混成一层

#### 3. MPC 接法

v1 不改成 NMPC，不直接引入 `casadi/ipopt`。

v1 做法：

- 继续保留当前 affine time-varying QP
- 在每个预测步对障碍安全函数做一次局部线性化
- 生成可被 OSQP 接收的线性半空间约束
- 必要时给每步约束加 slack，并在 cost 里重罚 slack

这样做的好处：

- 不破坏当前求解器框架
- 可以复用当前 successive linearization 流程
- 更容易和现有速度/角速度/变化率约束并存

#### 4. 控制模式边界

v1 的模式边界建议写死：

- 远场：
  - `tracking MPC + obstacle constraints`
- 近终点但未进入 `REACHED`：
  - 仍保留当前 `terminal recovery`
- 已到达：
  - 维持当前停靠链

这意味着：

- 避障主约束只作用在正常 `TRACKING` 主链上。
- near-goal 不在第一轮强行把 obstacle-aware logic 深耦合进 terminal logic。

原因：

- 你当前 near-goal 逻辑刚稳定，不值得在避障第一刀里再一起打散。
- 终点附近若确实有障碍问题，应该在主链稳定后再单独处理 terminal-aware obstacle handling。

### 关键技术口径

#### 1. 不做“地图全量入优化”

优化器里不直接放整张 costmap。

应该先做：

- costmap/scan -> 障碍代理
- 障碍代理 -> 少量安全约束

否则 QP 尺寸和工程复杂度都会失控。

#### 2. 不做“直接 world-state 改造”

当前 MPC 状态不需要立刻改成世界系 `x, y, theta`。

更稳的做法是：

- 保留当前 `e_l, e_c, e_theta, v, ...`
- 新增一个“Frenet 误差 -> 笛卡尔名义点”的回投工具
- 用回投后的名义点与障碍代理构造约束

这里的核心难点不是写约束，而是先把当前 `e_l/e_c` 的几何意义和符号方向彻底钉死。

#### 3. v1 先做静态障碍

v1 只要求：

- 对静态或低速变化障碍可靠避让

先不要求：

- 动态障碍预测
- 严格复现参考项目里的 D-CBF 时间递推形式

原因：

- 你当前最缺的是“控制器主链开始对障碍有反应”
- 不是“第一版就把动态障碍理论做满”

#### 4. 先约束“车体代理”，再约束“完整 footprint”

v1 建议先把机器人简化成：

- 1 个膨胀圆

稳定后再看是否升级成：

- 2 圆
- 3 圆
- 椭圆车体

原因：

- 车体代理越复杂，约束数量越多，QP 尺寸和调参成本越高。
- 当前第一目标是先建立稳定的障碍反应闭环，不是把碰撞几何一开始就做满。

#### 5. 先做“可线性化安全函数”，不要一上来追求最严格形式

v1 的核心不是“名字一定叫 D-CBF”，而是：

- 安全函数可解释
- 可在线性化
- 能稳定并入当前 OSQP
- 打开后确实改变控制行为

如果第一刀形式过于复杂，最容易出现的结果不是“更安全”，而是“求解不稳 + 不知道哪里错”。

## 修改后的 MPC 架构

### 修改前

```text
/scout/global_path
    ->
PathHandler
    ->
ref_points
    ->
LocalPlannerROS
    ->
x0 + ref_points
    ->
MPCSolver
    ->
OSQP
    ->
/cmd_vel
```

### 修改后 v1

```text
/scout/global_path
    ->
PathHandler
    ->
ref_points
                       /scout/mbf_costmap_nav/local_costmap/costmap
                                  ->
                           ObstacleProxyManager
                                  ->
                           obstacle_proxies
                                       \
                                        \
LocalPlannerROS -> x0 + ref_points + obstacle_proxies
                                        ->
                                   MPCSolver
                                        ->
                       nominal trajectory / linearization points
                                        ->
                           ObstacleConstraintBuilder
                                        ->
                    obstacle linear constraints (+ optional slack)
                                        ->
                                     OSQP
                                        ->
                                     /cmd_vel
```

### 修改后的职责分层

- `PathHandler`
  - 仍只负责路径窗口化、样条、参考速度、`ref_points`
- `ObstacleProxyManager`
  - 负责把 `local_costmap` 或 `scan` 压缩成少量障碍代理
- `ObstacleConstraintBuilder`
  - 负责把障碍代理变成 QP 约束
- `MPCSolver`
  - 负责把新增障碍约束与现有动力学/边界/代价一起组装给 OSQP
- `LocalPlannerROS`
  - 负责调度、订阅、调试输出、开关控制和回退逻辑

### 修改后仍然不变的部分

- `Frenet + slosh` 增广状态定义
- `OSQP` 求解框架
- `PathHandler` 主参考生成逻辑
- `slosh` 状态注入
- `terminal recovery`
- 当前全局路径主入口

结论：

- 这次改造是“在当前 tracking MPC 外围补一层障碍约束能力”
- 不是“重写成全新局部规划器”

## 分阶段实施

### 阶段 A：障碍代理层

目标：

- 从 `local_costmap` 提取少量最近障碍代理
- 在 `base_link` 或统一控制坐标系下输出

输出建议：

- 每帧最多 `M` 个最近障碍
- 每个障碍包含：
  - `cx, cy`
  - `radius` 或 `a, b, theta`
  - `inflated_margin`

新增调试输出建议：

- `/obstacle_proxy/markers`
- `/obstacle_proxy/debug`

阶段 A 的通过标准：

- 能稳定从 `local_costmap` 产出有限个障碍代理。
- 坐标系、障碍膨胀半径、最近障碍选择逻辑都可解释。
- 在没有障碍时输出稳定为空或近空，不抖动。

### 阶段 B：预测位姿回投层

目标：

- 对 horizon 上每个 `k` 得到预测车辆几何中心点或碰撞圆心

建议：

- 先只取一个代表点
- 稳定后再扩成多圆 footprint

新增工具建议：

- `frenet_projection_utils.*`

阶段 B 的通过标准：

- 给定 `x_k` 和 `ref_k`，能稳定得到车辆代理点在局部笛卡尔系的位置。
- 这个回投和当前 `local_path`、`ref_points`、`FrenetState` 的符号方向一致。
- 误差定义不会在左右方向上翻符号。

### 阶段 C：QP 安全约束层

目标：

- 把障碍距离约束并入当前 OSQP

v1 约束形式建议：

- 先做线性化最小距离约束
- 必要时加 slack
- 对 slack 给大权重

不建议第一刀就做：

- 非凸原始距离约束
- 直接把参考项目 D-CBF 原式硬塞进当前代码

阶段 C 的通过标准：

- 障碍约束能稳定进入当前 QP。
- 没障碍时不显著改变原控制输出。
- 有障碍时控制输出出现可解释变化。
- 求解失败率不上升到不可接受水平。

### 阶段 D：速度治理补充

如果仅靠几何约束还不稳，再加一层与 slosh governor 类似的外层治理：

- 障碍近距离时压低 `v_des`
- 但这层只能当补充，不能代替主约束层

阶段 D 的定位：

- 这是鲁棒性增强，不是主安全机制。
- 如果只有外层减速没有主约束层，本质上还是“看到危险就慢一点”，不是机制级避障。

## 可能造成的问题

这部分必须先写，不然后面实现时容易把副作用当成 bug。

### 1. QP 不可行率上升

原因：

- 障碍约束和跟踪约束冲突
- 安全半径过大
- 路径本身穿障
- 不允许倒车而局部空间不足

后果：

- OSQP 失败增多
- 进入退化控制
- 局部停滞

应对：

- v1 支持 slack
- 对最近障碍数量设上限
- 打开/关闭避障时做 A/B 回归

### 2. 控制输出抖动

原因：

- costmap 更新有抖动
- 障碍代理帧间跳变
- 线性化点变化过快

后果：

- `omega_cmd` 抖
- 车在障碍前蛇形

应对：

- 障碍代理做最小稳定化和排序
- 只保留少量最近障碍
- 约束/速度治理加入滞回

### 3. 参考路径跟踪质量下降

原因：

- 安全约束与 tracking 目标竞争

后果：

- `e_c/e_theta` 变大
- 车离路径更远

这不是纯 bug，有时是设计结果。  
真正要判断的是：

- 偏离是否可解释
- 偏离后是否更安全
- 脱离障碍后能否重新收敛

### 4. near-goal 逻辑出现冲突

原因：

- `terminal recovery` 当前是外层显式控制
- 避障主约束如果也想接管 near-goal，会和现有模式切换冲突

后果：

- 终点前犹豫
- 终点前反复切模式

应对：

- v1 先不深改 terminal
- 先把避障主链限制在正常 `TRACKING` 阶段

### 5. 局部最优或卡死

原因：

- 只有局部约束，没有进度变量
- 全局路径若贴障碍太近，局部控制器可能只会停或原地犹豫

后果：

- 不是撞上，就是不走

应对：

- 这类情况不能只怪 MPC
- 需要同时看全局路径质量和局部可行空间
- 必要时后续补“局部参考修正”或“上游重规划触发”

### 6. slosh 与避障目标相互拉扯

原因：

- 避障常常要求更大横摆或更激进减速
- anti-slosh 常常希望更平缓

后果：

- 两套目标打架
- 参数不好调

应对：

- v1 默认不同时推大 `Q_slosh` 和强避障
- 先保证安全，再讨论液体表现

### 7. 坐标系和几何定义错误

原因：

- `base_link`、`map`、`costmap`、Frenet 局部样条之间坐标含义不统一

后果：

- 约束方向错
- 明明有障碍却不避
- 明明没障碍却乱躲

应对：

- 这是实现前必须优先核清的真问题
- 不能靠调参数掩盖

## 当前结论

当前更完整的方案结论是：

1. 这次改造的目标不是“换一套避障控制器”，而是“给当前 tracking MPC 增加局部安全约束能力”。
2. 参考项目的价值在于障碍代理和约束思路，不在于整套控制框架可直接迁移。
3. v1 最合理的工程路线是：
   - 用现有 `local_costmap`
   - 构造少量障碍代理
   - 在线性化后并入当前 OSQP 约束
4. 这条路线的最大风险不是参数，而是：
   - 坐标系不清
   - 障碍代理抖动
   - QP 可行性下降
5. 为了降低破坏性，文件和代码都应该做最小增量接入，不做 package 级重构。

## 当前决策

本轮先冻结以下决策：

1. 参考项目只作为算法参考，不作为底座迁移目标。
2. 你的 v1 避障输入优先接现有 `local_costmap`，不是重建 `grid_map` 管线。
3. 你的 v1 避障求解优先保持 `OSQP + 线性化约束`，不是换 `casadi/ipopt`。
4. 你的 v1 先做静态障碍，再考虑动态障碍和严格 D-CBF。
