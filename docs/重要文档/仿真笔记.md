# 仿真笔记

## 1. 当前目标

当前仿真主线不是完整复刻实物液面视觉，而是建立一条稳定、可重复、可录 bag 的 anti-slosh MPC 验证链路：

1. 使用官方 AgileX Scout Mini Gazebo 底盘。
2. 使用本项目 bridge 层统一 `/scan_front`、`/imu/data`、`/odom`、`/tf`。
3. 使用 Cartographer 建图/定位。
4. 使用 MBF 全局规划 + `scout_local_planner` 局部 MPC。
5. 在开阔场地录制 bag，用 `/slosh/height`、轨迹、MPC 状态分析改进效果。

当前推荐场景是：

- world: `/home/a/scout_ws/src/scout_ros/scout_description/worlds/open_walled.world`
- map: `/home/a/scout_ws/src/scout_apps/scout_maps/maps/map_sim_empty.pbstream`

旧迷宫场景仍可保留用于回归：

## 3. 推荐启动方式

### 3.1 一键启动导航骨架

脚本：

```text
/home/a/scout_ws/src/scout_apps/control/scout_local_planner/scripts/launch_sim_nav_stack.sh
```

脚本会启动：

- Gazebo + 官方 Scout Mini bridge
- Cartographer localization sim
- MBF global planner sim

局部 MPC 仍单独启动。

开阔场地：

```bash
source /home/a/scout_ws/devel/setup.bash
SIM_ENV=open USE_RVIZ=true \
SPAWN_X=0.0 SPAWN_Y=0.0 SPAWN_Z=0.1 SPAWN_YAW=0.0 \
rosrun scout_local_planner launch_sim_nav_stack.sh
```

旧迷宫场地：

```bash
source /home/a/scout_ws/devel/setup.bash
SIM_ENV=maze USE_RVIZ=true \
rosrun scout_local_planner launch_sim_nav_stack.sh
```

手动指定 world 和 map：

```bash
source /home/a/scout_ws/devel/setup.bash
SIM_ENV=custom USE_RVIZ=true \
WORLD_NAME=/home/a/scout_ws/src/scout_ros/scout_description/worlds/open_walled.world \
MAP_FILE=/home/a/scout_ws/src/scout_apps/scout_maps/maps/map_sim_empty.pbstream \
SPAWN_X=0.0 SPAWN_Y=0.0 SPAWN_Z=0.1 SPAWN_YAW=0.0 \
rosrun scout_local_planner launch_sim_nav_stack.sh
```

说明：

- `SIM_ENV=open` 是当前推荐默认。
- `WORLD_NAME` 和 `MAP_FILE` 会覆盖 `SIM_ENV` 默认值。
- 脚本默认 `SPAWN_WHEEL_CONTROLLERS=false`，即关闭四个 wheel velocity controller，只保留 `scout_state_controller`。
- 脚本默认 `ENABLE_ODOM_TF_BRIDGE=false`；定位模式下由 Cartographer 发布 `map -> odom -> base_footprint`，避免重复 TF。
- 保留 `scout_state_controller` 是为了发布 `/joint_states`，否则 RViz RobotModel 会缺轮子关节状态。

### 3.2 启动局部 MPC

`slosh_experiment_sim.launch` 已对齐实物 `slosh_experiment.launch`（2026-05-20），
支持 33 个 arg（MPC 权重 / terminal slowdown / capture stop / v_des rate limit /
risk scheduler / settling / IMU 标定等）。可直接照搬实物命令的全部 arg 跑仿真。

基础固定 Q 仿真：

```bash
roslaunch scout_local_planner slosh_experiment_sim.launch \
  Q_slosh:=5 \
  risk_scheduler_enable:=false \
  input_shaping_enable:=false \
  enable_slosh_box_constraint:=false \
  slosh_speed_governor_enable:=false
```

后续做结构改进验证时，再逐项打开 scheduler、input shaping 或 box constraint，避免多个变量同时变化。

如果只是想验证仿真链路能跑通（smoke test），用一键脚本：

```bash
bash src/scout_apps/control/scout_local_planner/scripts/run_s_curve_smoke_test.sh
```

脚本自动 spawn + MPC + path generator + rosbag + teardown，跑一段 S 曲线后退出。
不用拼命令、不用守 4 个终端。仅用于 smoke test，不为数据精度负责。

## 4. 建图流程

### 4.1 启动开阔世界底盘

```bash
source /home/a/scout_ws/devel/setup.bash

roslaunch scout_description scout_mini_true_empty_bridge.launch \
  world_name:=/home/a/scout_ws/src/scout_ros/scout_description/worlds/open_walled.world \
  gui:=true \
  x:=0.0 y:=0.0 z:=0.1 yaw:=0.0 \
  enable_odom_tf_bridge:=true \
  spawn_wheel_controllers:=false
```

说明：

- `enable_odom_tf_bridge:=true` 只用于建图流程，给 Cartographer 建图提供 `odom -> base_footprint`。
- `spawn_wheel_controllers:=false` 避免四个 wheel velocity controller 和官方 skid-steer 插件抢轮子。
- 关闭 wheel velocity controllers 时仍会启动 `scout_state_controller`，保证 `/joint_states` 和 RobotModel 正常。

### 4.2 启动 Cartographer 建图

```bash
source /home/a/scout_ws/devel/setup.bash
source /home/a/scout_ws/src/scout_apps/sensors/cartographer_ws/install_isolated/setup.bash

roslaunch nanoscan3_mapping scout_nanoscan3_cartographer_sim.launch
```

当前建图配置：

- `scout_2d_sim.lua` 中 `use_odometry = true`
- Cartographer 订阅 `/scan_front`
- `/odom` 先经过 `odom_monotonic_relay.py` 过滤为 `/odom_carto`
- Cartographer 实际订阅 `/odom_carto`

这样既保留 odom 约束，又避免重复时间戳触发：

```text
map_by_time.h:43 Check failed: data.time > std::prev(...)
```

### 4.3 建图运动建议

不要长时间原地高速自转。Scout Mini 是四轮 skid-steer，原地自转必须横向滑移，Gazebo 会有轻微 stick-slip 抖动。

推荐建图运动：

```bash
roslaunch scout_bringup scout_teleop_keyboard.launch
```

或用小半径圆弧：

```bash
rostopic pub -r 20 /cmd_vel geometry_msgs/Twist \
"{linear: {x: 0.12, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.3}}"
```

## 5. 关键话题

当前仿真链关键话题：

- `/scan_front`：2D 激光，由 bridge 从 `/scan` relay。
- `/imu/data_raw`：Gazebo IMU plugin 原始输出。
- `/imu/data`：经 `imu_frame_relay.py` 统一 frame 后输出。
- `/odom`：官方 Gazebo skid-steer 插件输出。
- `/odom_carto`：`odom_monotonic_relay.py` 过滤后的 Cartographer odom 输入。
- `/joint_states`：`scout_state_controller` 输出，RViz RobotModel 需要。
- `/cmd_vel`：底盘速度命令。
- `/risk_scheduler/*`：risk scheduler 状态。
- `/slosh/*`：晃动估计与 anti-slosh 相关信号。

不要再单独启动：

```bash
roslaunch nanoscan3_bringup nanoscan3_front_sim.launch use_rviz:=false
```

原因：`scout_mini_true_empty_bridge.launch` 已经提供 `/scan -> /scan_front` relay 和相关 TF，重复启动会造成话题/TF 混乱。

## 6. 关键 TF

目标 TF 链：

```text
map -> odom -> base_footprint -> base_link -> laser_link -> nanoscan3_front
                                      |
                                      -> imu_link
                                      -> camera_link
```

当前角色：

- Cartographer localization 发布 `map -> odom`。
- `odom_tf_broadcaster.py` 可发布 `odom -> base_footprint`。
- `tf_footprint_base` 发布 `base_footprint -> base_link`。
- `robot_state_publisher` 发布 URDF 固定关节和轮子 link。
- `tf_front_alias` 发布 `laser_link -> nanoscan3_front`。

检查命令：

```bash
rosrun tf tf_echo odom base_link
rosrun tf tf_echo base_link nanoscan3_front
rostopic hz /joint_states
```

如果 RViz RobotModel 报错，优先检查：

```bash
rostopic info /joint_states
rostopic hz /joint_states
rosparam get /robot_description
```

`spawn_wheel_controllers:=false` 时，必须仍有 `scout_state_controller` 发布 `/joint_states`。

## 7. 已确认问题与处理

### 7.1 `/scan_front` 全是 `inf`

原因：

- 初版 `open_walled.world` 是 20m x 20m。
- 雷达 `range_max=8.0m`。
- 小车在中心时看不到墙。

处理：

- `open_walled.world` 改为 12m x 12m，墙在 `x/y = +/-6m`。

### 7.2 Cartographer 使用 `/odom` 会崩溃

典型报错：

```text
map_by_time.h:43 Check failed: data.time > std::prev(trajectory.end())->first
```

处理：

- 不关闭 odom 约束。
- 使用 `odom_monotonic_relay.py` 把 `/odom` 过滤为 `/odom_carto`。
- Cartographer 建图和定位都订阅 `/odom_carto`。

### 7.3 RobotModel 报错

原因：

- 关闭四个 wheel velocity controllers 时，如果连 `scout_state_controller` 也不启动，就没有 `/joint_states`。
- RViz RobotModel 的轮子连续关节需要 `/joint_states`。

处理：

- `spawn_wheel_controllers:=false` 时只启动 `scout_state_controller`。
- 不启动四个 `scout_motor_*_controller`。

### 7.4 自转抖动 + 中心漂移（2026-05-19 部分修复）

历史：首版认为是 Gazebo 接触模型固有限制，建议不修。
2026-05-19 定位到具体缺陷并完成 A 步修复 + B/C bisect。

A 步（已应用，commit `0df008f`）：

```text
src/scout_ros/scout_description/urdf/official_scout_mini_imu_extras.urdf.xacro
  给四个 wheel_link 注入 ODE 接触参数：
    mu1=1.0  mu2=0.5  fdir1="1 0 0"  minDepth=0.001  maxContacts=64
```

原因：upstream `scout_mini.gazebo` 整段摩擦/接触块被注释掉，
`scout_mini_wheel.gazebo` 也只有 `<transmission>`，
四个轮子走 Gazebo 默认 `mu1=mu2=1` 各向同性摩擦。
验证：spin test pose drift peak 从 0.217 m 降到 0.116 m（降 47%，距 50% target 差 3%）。

B/C bisect（已回退）：

- B = 去掉右轮 `wheel_vertical_offset + 0.001` 偏置（4 轮共面）
- C = skid_steer 插件 torque 1000 → 50
- 实测 A 单独最好（+47%），B/C 单独或合并都让 pose 漂更差（ab -14%、ac +8%、abc +4%）
- 归因：upstream `+0.001` 是故意打破 4 点共面避免 ODE 接触过约束；`torque=50` 在原地自转工况下 fmax 不足
- 现状：`launch` 仍指 upstream `mini_abs.xacro`，fork 文件（`mini_abs_fixed.xacro`/`scout_mini_fixed.gazebo`）留作 D / 对角偏置实验基础设施，未被引用

当前结论：

- A v2 是 URDF 接触层局部最优。
- 不再为 URDF 层接触/惯量参数继续投入（B/C/D 试错收益已榨干）。
- 不修改 wheel axis 符号（方向已确认正常）。
- 不使用过重的 ODE 物理参数（实时因子会下降）。
- 避免把"原地自转是否完美"作为 MPC 结论；重点看路径跟踪。

工具（commit `0df008f`）：

```text
scripts/record_spin_test.sh             30s 纯角速度自转录 bag + 自动复位 + meta.json
scripts/analysis/analyze_spin_test.py   before/after 对比，输出 pose drift / IMU 5-20Hz 能量 / PASS/FAIL
```

### 7.5 KDL root inertia warning

启动时可能出现：

```text
The root link base_link has an inertia specified in the URDF, but KDL does not support a root link with an inertia.
```

当前判断：

- 这是 RobotModel/KDL 的常见 warning。
- 不是 Gazebo 速度暴降或转向异常的主因。
- 暂不为这个 warning 改官方模型。

### 7.6 固定路径实验 goal topic 必须用 `/scout/template_goal`

`template_fixed_path_generator.py` 跑固定路径实验时，goal 不能发到默认的 `/scout/goal`：
该 topic 同时被 MBF 全局规划 `/scout/mbf_path_publisher` 订阅，MBF 会用它自己的
global planner 生成一条直线路径并下发，绕过你的 template 路径，2026-05-20 撞墙
事故就是这么来的。

正确做法（已在 `run_s_curve_smoke_test.sh` 与实物流程中固化）：

```bash
rosrun scout_local_planner template_fixed_path_generator.py \
    --goal-topic /scout/template_goal \
    --output-topic /scout/global_path_fixed \
    ...

rostopic pub -1 /scout/template_goal geometry_msgs/PoseStamped \
    "{header: {frame_id: 'map', stamp: now}, pose: {position: {x: ..., y: ..., z: 0.0}, orientation: {x: 0, y: 0, z: 0, w: 1}}}"
```

发 goal 之前必须验证：

```bash
# 1) path_gen 已订阅 goal topic（没超时退出）
rostopic info /scout/template_goal | grep template_fixed_path_generator
# 2) TF 链通，robot 在 map 帧可定位
rosrun tf tf_echo map base_link
```

### 7.7 sim-real 动力学数值差距（承认 + 不再投入）

2026-05-20 跑同款 anti-slosh S 曲线（`Q_slosh=5`）对比实物 D 组 n=3 平均：

```text
                    real D    sim D    sim/real
v_p95   [m/s]       1.14      1.36     1.2x
ax_p95  [m/s^2]     0.28      4.01     14x      <<<
ay_p95              0.30      2.82     9.4x
jerk_p95 [m/s^3]    3.24      506      156x     <<<
slosh_p95   [mm]    0.89      4.32     4.9x
```

实物 summary 来源：
`/data/a/slosh_bags/real/20260518_fixed_path_cost/red_visual_analysis_20260518/fixed_path_cost_effect/fixed_path_cost_effect_summary.csv`

分层归因：

```text
MPC 命令层 ax_p95 = 2.29 m/s^2（已是实物 8x）：
  sim 中 odom = cmd 无打滑，MPC 反馈完美 → 自己敢更激进；
  实物轮胎打滑，MPC 看响应慢 → 自我保守。
底盘层 cmd 2.29 -> 实际 4.01：
  skid_steer 插件 torque=1000 + 无 wheelAcceleration 限幅 → 冲击响应。
两层叠加 = 实物 14x ax，156x jerk，5x slosh。
```

判定：Gazebo classic ODE + 四轮 skid-steer + 完美 odom 反馈，这套底座的天花板就在这。
要让 sim ax 进入实物 ~3x 量级需要写 cmd_vel rate limiter 节点（半天工，但仍不够 paper 用）；
真正数值互通须换 Isaac Sim / MuJoCo（1-2 周）。
2026-05-20 决定不再为此投入。paper 数据继续走实物 bag。

### 7.8 自动调参脚本反复启停仿真导致 RViz/TF 状态混乱（2026-06-06）

现象：

```text
用 launch_sim_nav_stack.sh 启动后，RViz 中 RobotModel 显示异常/看不到。
```

当时触发原因不是修改了仿真 launch 或 RViz 配置，而是自动调参脚本连续执行了多次：

```bash
SIM_ENV=open USE_RVIZ=true \
SPAWN_X=-4.0 SPAWN_Y=0.0 SPAWN_Z=0.1 SPAWN_YAW=0.0 \
rosrun scout_local_planner launch_sim_nav_stack.sh
```

问题点：

```text
1. 自动脚本反复启动/停止 Gazebo、RViz、Cartographer、MBF，容易留下旧进程或旧 TF 状态。
2. 如果旧 gzserver / rviz / roslaunch 没完全退出，再开新仿真，会出现模型、TF、RViz display 状态混乱。
3. 当时使用 SPAWN_X=-4.0，不是本文档推荐的 open 场景标准验证位姿。
4. P2_s_curve 的路径起点约为 x=3.45, y=0.21，SPAWN_X=-4.0 也不是该固定路径起点。
```

已确认：相关文件没有被修改：

```text
launch_sim_nav_stack.sh
cartographer_localization.rviz
scout_mini_true_empty_bridge.launch
```

恢复方式：

```bash
# 先干净关闭残留进程
pkill -f launch_sim_nav_stack.sh
pkill -f scout_mini_true_empty_bridge.launch
pkill -f gzserver
pkill -f gzclient
pkill -f rviz

# 再按标准 open 场景启动
source /home/a/scout_ws/devel/setup.bash
SIM_ENV=open USE_RVIZ=true \
SPAWN_X=0.0 SPAWN_Y=0.0 SPAWN_Z=0.1 SPAWN_YAW=0.0 \
rosrun scout_local_planner launch_sim_nav_stack.sh
```

经验结论：

```text
调参/正式对比时，不要让脚本自动反复启动 Gazebo/RViz。
推荐人工 fresh 启动仿真，等待 30s 定位归位，再单独启动 planner 和录包。
```
