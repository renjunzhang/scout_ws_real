# 仿真笔记

## 1. 当前仿真目标

当前仿真的目标不是复刻实物全部细节，而是先建立一条**稳定、可重复、可用于 anti-slosh MPC / risk scheduler 验证**的仿真链路。  
当前优先级是：

1. 底盘运动稳定
2. `/scan_front`、`/imu/data`、`/odom`、`/tf` 口径与本项目导航链兼容
3. Cartographer 纯定位可用
4. MBF 全局规划可用
5. `scout_local_planner` 局部规划和 anti-slosh 实验可用

结论上，**本地旧 Scout Mini 模型链不再作为主仿真底盘使用**，当前采用：

- 官方 AgileX Scout Mini 模型
- 本项目 bridge 层
- 本项目 `maze_course.world`


## 2. 当前可用仿真链

### 2.1 底盘入口

当前稳定入口：

- `/home/a/scout_ws/src/scout_ros/scout_description/launch/scout_mini_true_empty_bridge.launch`

该 launch 的作用：

- 调用 `/data/a/official_scout_ws` 中的官方 Scout Mini 仿真模型
- 使用本项目 world
- bridge 出本项目需要的话题与 TF

当前 bridge 提供：

- `/scan_front`
- `/imu/data`
- `/odom`
- `nanoscan3_front`
- `imu_link`
- `base_footprint -> base_link`


### 2.2 官方模型来源

官方对照工作区放在：

- `/data/a/official_scout_ws`

之所以单独维护这套工作区，是因为：

- 本地 `scout_description` 与官方 `scout_description` 同名
- 如果直接 overlay 混用，`rviz`、`xacro`、`mesh`、`launch` 很容易串包

因此后来新增了官方绝对路径版本入口，避免 `package://scout_description/...` 解析到错误包。


### 2.3 当前完整导航链

当前顺利启动的顺序是：

1. 启 bridge 底盘
2. 启 Cartographer 纯定位
3. 启 MBF 全局规划
4. 启 `scout_local_planner`

其中，脚本入口是：

- `/home/a/scout_ws/src/scout_apps/control/scout_local_planner/scripts/launch_sim_nav_stack.sh`

该脚本现在会启动：

- 官方 bridge 底盘
- `nanoscan3_localization scout_nanoscan3_cartographer_localization_sim.launch`
- `scout_global_planner mbf_global_sim.launch`

然后只做一个定位刷新动作：

- 后退 `4s`
- 不再原地自转

脚本启动后，局部规划器仍然单独起：

```bash
roslaunch scout_local_planner slosh_experiment_sim.launch risk_scheduler_enable:=true Q_slosh:=5.0
```

## 4. 当前关键话题

当前这条仿真链里，关键输入输出口径为：

- `/scan_front`：2D 激光，当前约 `11 Hz`
- `/imu/data`：由 `/odom` 估计出的仿真 IMU，当前约 `50 Hz`
- `/odom`
- `/odom_carto`：经过单调时间戳过滤后的 Cartographer odom 输入
- `/scout/global_path`
- `/local_path`
- `/cmd_vel`

说明：

- 不再单独启动 `roslaunch nanoscan3_bringup nanoscan3_front_sim.launch`
- 因为 bridge 已经直接提供 `/scan_front`


## 5. 当前关键 TF 结构

最终验证通过的 TF 结构是：

```text
map -> odom -> base_footprint -> base_link
```

这是当前能同时兼容：

- Cartographer
- MBF
- `scout_local_planner`
- RViz RobotModel

的稳定结构。

当前关键配置在：

- `/home/a/scout_ws/src/scout_apps/sensors/nanoscan3_localization/config/scout_2d_localization_sim.lua`

当前关键参数是：

```lua
tracking_frame = "base_link"
published_frame = "base_footprint"
odom_frame = "odom"
provide_odom_frame = true
```

含义：

- Cartographer 负责 `map -> odom` 与 `odom -> base_footprint`
- bridge 提供 `base_footprint -> base_link`


## 6. 关键修改点

### 6.1 world 物理参数

最开始仿真速度表现异常，很大一部分不是控制器问题，而是 world 物理参数问题。

确认结果：

- 本地 `empty.world`
- 本地 `maze_course.world`

最初都缺少官方 world 中的 ODE physics 配置。

后来给 world 补入了：

```xml
<physics type='ode'>
  <max_step_size>0.01</max_step_size>
  <real_time_factor>1</real_time_factor>
  <real_time_update_rate>100</real_time_update_rate>
  <gravity>0 0 -9.8</gravity>
</physics>
```

补完后，官方底盘在仿真中的速度表现恢复正常。


### 6.2 官方模型 + 本地 bridge

本地旧 Scout Mini 模型链存在以下问题：

- 高速易翘头
- wheel / collision / drive 行为不稳定
- 同一个 `maze_course.world` 下，表现明显差于官方模型

对照结论：

- 官方链稳定
- 本地旧链不稳定

因此当前放弃继续修本地旧底盘，改为：

- 官方模型作为底盘
- 本地 bridge 负责接口兼容


### 6.3 绝对路径模型

为了解决官方包与本地包同名冲突，在 `/data/a/official_scout_ws` 内新增了绝对路径版本：

- `mini_abs.xacro`
- `scout_mini_true_empty_abs.launch`

作用：

- 避免 `package://scout_description/...` 指到错误包
- 解决 RViz `RobotModel` mesh 无法显示的问题


### 6.4 雷达视野修正

曾经出现 2D 激光大面积被车身上方结构遮挡。

处理方式：

- 从官方仿真模型中移除了 `box_link`

结果：

- `/scan_front` 恢复正常
- 激光可用于 Cartographer 和 MBF


### 6.5 IMU 接入

这一阶段 IMU 方案经历了两步：

#### 阶段 1：临时桥接

早期为了先打通导航链和 anti-slosh 链，曾临时使用：

- `/home/a/scout_ws/src/scout_apps/sensors/nanoscan3_bringup/scripts/odom_to_imu.py`

它的作用是：

- 订阅 `/odom`
- 估计 `/imu/data`

这个阶段的意义主要是先把：

- `risk_scheduler`
- fallback 逻辑
- anti-slosh 主链路

快速打通。

#### 阶段 2：Gazebo 真 IMU

当前已经切换到 **Gazebo 真 IMU**。

实现方式：

- 在官方底盘模型的本地扩展 `urdf_extras` 中新增 `imu_link`
- IMU 安装位姿按当前实物记录挂载：
  - `x = 0.10`
  - `y = -0.045`
  - `z = 0.0`
  - `rpy = 0 0 0`
- 由 Gazebo `libgazebo_ros_imu.so` 直接发布 IMU 原始话题
- 再经轻量 relay 统一 `header.frame_id`

当前实际结构是：

```text
Gazebo IMU plugin -> /imu/data_raw
imu_frame_relay.py -> /imu/data
```

其中：

- `/imu/data_raw` 来自 Gazebo 真 IMU
- `/imu/data` 是最终供导航与 anti-slosh 使用的话题
- `imu_frame_relay.py` 只负责把 `header.frame_id` 统一成 `imu_link`，不改数值

当前验证结果：

- `/imu/data` 频率约 `50 Hz`
- `header.frame_id = imu_link`
- `base_link -> imu_link = (0.10, -0.045, 0.0)`
- 小运动下角速度与加速度响应正常

因此当前结论更新为：

- 当前仿真链**已经具备独立的 Gazebo 真 IMU**
- 不再使用 `odom -> imu` 作为正式方案
- 旧的 `odom_to_imu.py` 已退出当前仿真主链


### 6.6 Cartographer odom 时间戳过滤

Cartographer 纯定位曾多次因为重复 odom 时间戳崩溃，典型报错是：

```text
map_by_time.h:43 Check failed: data.time > std::prev(trajectory.end())->first
```

处理方式：

- 新增 `odom_monotonic_relay.py`
- 将 `/odom` 过滤为严格递增时间戳的 `/odom_carto`

当前定位 launch 已改为让 Cartographer 使用 `/odom_carto`。


## 7. 过程中遇到的主要问题

### 7.1 本地旧 Scout Mini 模型不稳定

现象：

- 提高速度后容易翘头
- 键盘直接发速度也会翘头
- 有时轮子陷地

结论：

- 不是 MPC 本身导致
- 更像本地模型链的 collision / inertia / drive plugin / wheel geometry 组合不自洽


### 7.2 world 看似一样，速度却不一样

现象：

- 真空世界里速度正常
- 换到 `maze_course.world` 后速度异常

结论：

- 不是“地图墙体影响速度”
- 根因是 world 的 physics 配置不同


### 7.3 官方与本地 `scout_description` 同名包冲突

现象：

- RViz 无法显示车身 mesh
- `roslaunch scout_description ...` 经常落到错误包
- xacro/launch 解析行为不稳定

处理方式：

- 官方工作区独立放到 `/data/a/official_scout_ws`
- 官方模型改为绝对路径入口
- 本地 bridge launch 用绝对路径调用


### 7.4 2D 激光被上层结构遮挡

现象：

- `/scan_front` 数据异常
- Cartographer 难以稳定定位

处理方式：

- 删除官方仿真模型中的 `box_link`


### 7.5 TF 树冲突

这个阶段是整个排查里最容易反复出问题的一段。

出现过两类典型错误：

#### 1) `odom` 不存在

表现：

```text
Timed out waiting for transform from base_link to odom
target_frame odom does not exist
```

原因：

- MBF / costmap 需要 `odom` TF
- 当前链路在某些配置下只有 `/odom` 话题，没有对应 TF

#### 2) `TF_REPEATED_DATA`

表现：

```text
TF_REPEATED_DATA ignoring data with redundant timestamp
```

原因：

- 同一条 TF 有多个 authority
- 或者 Cartographer 的 `published_frame` 选择错误，导致 `base_link` 被挂到错误位置

最后确认的稳定做法是：

- Cartographer 用 `published_frame = base_footprint`
- `provide_odom_frame = true`
- 不再额外启用 `enable_odom_tf_bridge`


### 7.6 Cartographer 直接崩溃

出现过的根因包括：

1. `/odom` 时间戳重复
2. 雷达被上方结构遮挡
3. TF 树配置错误

因此 Cartographer 稳定运行依赖三个条件同时满足：

- `/scan_front` 正常
- `/odom_carto` 时间严格递增
- TF 树为 `map -> odom -> base_footprint -> base_link`


## 8. 当前结论

到目前为止，当前最可靠的仿真结构是：

1. 官方 Scout Mini 模型
2. 本地 bridge 层适配传感器与 TF
3. 本项目 `maze_course.world`
4. Cartographer 纯定位
5. MBF 全局规划
6. `scout_local_planner` 局部规划

也就是说，当前仿真已经不是“本地旧 Gazebo 模型直接跑导航”，而是：

**官方底盘 + 本地接口适配 + 本项目导航链**

这条链已经可以用于继续做：

- anti-slosh MPC 仿真验证
- risk scheduler 仿真验证
- bag 录制与对比实验

并且当前 IMU 已经不再是里程计桥接，而是 Gazebo 真 IMU + 轻量 frame relay。


## 8.1 当前修改对实物的影响边界

当前这批修改对实物运行行为的影响边界如下：

### 不直接影响实物运行逻辑的部分

- 仿真 launch
- 仿真 world
- 仿真 Cartographer 配置
- bridge 层脚本：
  - `odom_to_imu.py`
  - `odom_monotonic_relay.py`
  - `odom_tf_broadcaster.py`

这些内容不会被实物主链自动调用，因此**不直接改变实物算法行为**。

### 需要注意但目前风险可控的部分

有少量修改发生在共享工作区包级文件中，例如：

- `nanoscan3_bringup/CMakeLists.txt`
- `nanoscan3_bringup/package.xml`
- `scout_description/CMakeLists.txt`

这些修改的作用主要是：

- 安装仿真桥接脚本
- 声明额外依赖
- 安装 `worlds/` 目录

它们会进入同一工作区的构建结果，但**不会主动改变实物运行行为**。  
当前可以认为：

- 对实物**运行时主链没有实质影响**
- 对共享工作区的**编译/安装内容有轻微影响**

如果后面要做“仿真与实物彻底隔离”，更稳的做法是把当前 bridge 脚本迁入独立的 `sim_bridge` 包，而不是继续放在 `nanoscan3_bringup` 下。


## 9. 后续建议

后续继续推进时，建议遵守下面几条：

1. 不再回到旧的 `scout_mini_gazebo.launch` 作为主仿真底盘
2. 不再单独启动 `nanoscan3_front_sim.launch`
3. 继续使用当前 bridge 链与 Cartographer / MBF 组合
4. 若后面还出现 TF 异常，优先检查：
   - `published_frame`
   - `provide_odom_frame`
   - 是否多处重复发布同一条 TF
5. anti-slosh 方案验证优先关注控制逻辑，不再把时间浪费在旧底盘模型修补上
