## 0. 先说结论

如果以**当前系统状态**直接冲 `RA-L`，我认为**还不够稳**。最主要的问题不是“Q 还要不要继续调”，而是：

1. **没有真实液面 ground-truth**
   - 现在 `/slosh/height` 本质上还是模型估计值。
   - 这意味着你目前能证明的是“模型预测更保守/更小”，还不能强证明“真实液体晃动被显著压下去”。

2. **IMU 还没真正进入可信闭环**
   - 当前 `ax/alpha` 主要来自 odom 差分，`ay` 主要来自 `v*omega` 近似。
   - 没有 IMU 时，这条激励输入链的可信度有限。

3. **算法创新点还不够凝练**
   - 当前结构是“tracking MPC + slosh soft cost + 盒约束 + 外层 governor”。
   - 这个系统已经工程上很不错，但如果论文主张只是“加了个 Q_slosh 和限速器”，创新性偏弱。

4. **实验设计离 RA-L 还差一层**
   - 现在更像“工程功能打通 + 初步有效性验证”。
   - `RA-L` 需要的是：可信传感、严格基线、可复现实验协议、清晰贡献边界。

所以我的判断很明确：

- **这个项目值得投论文**
- 但**现在不该再发散做太多新功能**
- 应该围绕“液体防晃动控制”这条主线，把**测量链、算法主线、实验协议、论文定位**一次打磨清楚

- `slosh_models` 里的模型是不是和论文一致

### 0.1.2 最关键的三条结论

1. **当前实现的 slosh 子模型本质上是线性的。**
   - 即使 `use_linear_model=false`，当前代码也没有切换到论文完整的 NL 动力学。

2. **当前 MPC 融入方式在默认配置下是自洽的。**
   - 默认 `offset_x=offset_y=0` 时，预测模型和估计模型都以 `[ax, ay] = [a, v*omega]` 为主输入，逻辑是通的。

3. **当前系统里有不少“论文模型之外的工程扩展”。**
   - 例如 `eta_parabola`、盒约束、speed governor、IMU fallback。
   - 这些不是坏事，但论文写法必须清楚区分：
     - 哪些是论文原始模型
     - 哪些是你的工程扩展

### 0.1.3 现阶段最重要的表述原则

如果你现在写论文或文档，最稳妥的说法是：

- **我们采用了源自论文的线性 2D 单模态 MSD 晃动估计模型**
- **并将其以状态增广方式接入 tracking MPC**
- **同时加入了旋转修正、输出高度修正和工程风险治理机制**

不要直接写：

- “我们实现了论文中的 nonlinear sloshing model 并集成进 MPC”

这句话按当前代码状态来说是不严谨的。

## 1. 论文主线应该怎么定

我建议你把论文定位成：

**面向差速/四轮差速移动机器人的在线液体防晃动路径跟踪控制系统**  
核心是：**状态增广的 tracking MPC + 风险感知 anti-slosh 机制 + 实物验证**

更具体一点，论文主线建议定成：

### 推荐主标题方向

**An IMU-Calibrated Slosh-Aware Tracking MPC for Liquid Transport on a Differential-Drive Mobile Robot**

或者更工程一些：

**Risk-Adaptive Slosh-Aware MPC for Liquid Transport on a Mobile Robot with Real-World Validation**

### 论文里真正要卖的贡献

1. **移动机器人场景**
   - 不是机械臂，不是离线路径整形，而是移动平台在线局部控制。

2. **slosh-aware tracking MPC**
   - 在 tracking MPC 中引入晃动状态、软代价、风险治理和约束护栏。

3. **可信观测链**
   - IMU 接入后，激励输入不再完全依赖 odom 差分和 `v*omega` 近似。

4. **真实实验验证**
   - 至少要有一种可信的真实晃动评价方式，而不只是模型内部量。

5. **可复现实验协议**
   - 有统一 launch、统一 bag 录制、统一 episode 管理、统一指标提取。

## 1.1 怎么让项目更有价值，而不是只是“功能更多”

这件事我建议你牢牢记住：

**期刊看重的不是你做了多少模块，而是你是不是把一个问题讲清楚、做扎实、证据给够。**

对你这个项目来说，真正能提高论文价值的，不是“再加几个功能”，而是下面四件事：

1. **把问题定义收紧**
   - 论文要回答的是：`移动机器人在携液路径跟踪时，如何在线抑制晃动风险，同时保持任务效率？`
   - 不是泛化成“更强导航系统”
   - 不是扩成“带避障、带学习、带复杂地图、带多任务调度的全能框架”

2. **把贡献边界封闭**
   - 审稿人最怕看到“这里加一点 heuristic，那里再补一个 governor”。
   - 你需要把现在的系统解释成一个完整方法，而不是一堆工程补丁。
   - 最好的表达方式是：
     - `可信激励估计`
     - `风险感知代价/约束治理`
     - `真实实验验证`

3. **把证据链做硬**
   - 不是只证明“模型预测下降”
   - 而是要尽量证明“真实晃动风险下降，且任务时间没有不可接受地变差”
   - 这决定了论文是“工程演示”，还是“可发表研究”

4. **把方法做成可复现实验对象**
   - 同一路径
   - 同一填充高度
   - 同一容器
   - 同一 launch
   - 同一 metrics pipeline
   - 这样实验结果才有统计意义，论文也更像研究工作，而不是一次 demo

### 1.2 哪些改动会明显提升项目价值

下面这些改动，是真正能提高论文价值的：

1. **加入真实液面测量或可信替代量测**
   - 这是价值提升最大的单项改动。
   - 一旦你有了真实测量，整篇文章就从“模型内优化”升级成“实物 anti-slosh 控制”。

2. **把 anti-slosh 从固定参数调优，升级成风险自适应机制**
   - 固定 `Q_slosh` 太像调参。
   - `Q_slosh = f(risk)`、`v_des = h(risk)` 更像方法贡献。

3. **做完整消融矩阵**
   - baseline / soft-cost / box-constraint / governor / full
   - 这会显著提升说服力。

4. **给出模型可信度分析**
   - 例如预测峰值和实测峰值的相关性。
   - 这能直接回应“你的模型到底靠不靠谱”这个关键质疑。

5. **补参数辨识**
   - 不是为了把模型做得很复杂。
   - 而是为了让“模型预测”和“真实实验”之间不至于脱节。

### 1.3 哪些事情会拉低论文价值

下面这些方向，短期内大概率会拉低命中率：

1. **现在就加避障**
   - 这会把主题从“携液控制”带偏到“导航系统”。
   - 贡献边界会立刻变糊。

2. **现在就大改 MPCC**
   - 改动面太大，风险高，和当前最核心的缺口不匹配。

3. **堆很多学习模块**
   - 如果没有高质量数据和统一基线，学习模块只会让系统更难解释。

4. **没有真实测量就急着写强结论**
   - 这是最危险的点。
   - 没有真实液面或可信 proxy，就不要宣称“显著抑制真实晃动”。

5. **只用单一路径、单次实验、单组截图**
   - 这种证据在 `RA-L` 级别非常弱。

### 1.4 对不同期刊，应该怎么定目标

按当前项目状态，我建议这样看：

1. **`RA-L`**
   - 可以作为主目标。
   - 但前提是你必须补齐：
     - 真实量测或可信 proxy
     - 完整消融
     - 实机多次重复实验
     - 明确的方法主线
   - `RA-L` 可以接受系统型和应用型工作，但证据链必须硬。

2. **`T-RO`**
   - 现在不建议作为第一目标。
   - 它通常更需要：
     - 更强的方法深度
     - 更强的一般性
     - 更充分的理论或跨场景验证
   - 以你当前阶段，直接冲这个目标不划算。

3. **`RAS` / `Control Engineering Practice` 一类**
   - 如果最后真实量测链路没有完全补齐，或者方法创新更多体现为系统集成与工程验证，
     这类期刊会更稳。
   - 它们不是“降级”，而是更匹配“工程系统论文”的表达方式。

### 1.5 我最直接的判断

如果你问我“怎样最有机会被期刊接收”，我给的答案不是“再做更多”，而是：

- **把主题收紧**
- **把证据做硬**
- **把方法讲成一个完整故事**
- **把实验做成标准化协议**

这四件事，比再加一个新模块更重要。

### 1.6 文献应该怎么整理，才不会拖后腿

文献部分不要再写成“大而全综述”，而要服务于你的论文主线。

我建议最终只保留三类相关工作：

1. **机械臂/轨迹优化类 anti-slosh**
   - 用来说明：已有工作更多集中在机械臂、离线轨迹整形、几何优化。

2. **移动机器人/服务机器人携液控制**
   - 用来说明：移动平台上的在线闭环 anti-slosh 研究更少，你的场景有独立价值。

3. **液面传感与状态观测**
   - 用来说明：为什么你需要真实量测链路，而不是只靠模型内估计。

文献整理的原则很简单：

- **只保留能稳定检索到的正式论文**
- **标题、年份、期刊名必须核准**
- **不要保留“疑似存在”的论文**
- **不要为了显得综述很多，塞进不可靠引用**

对这篇稿子来说，related work 的任务不是“显得读了很多”，而是：

- 说明你的问题和别人不一样
- 说明你的方法放在现有文献里是什么位置
- 说明你为什么必须做真实测量和实机验证

如果文献整理得干净，整篇稿子的可信度会明显更高。

### 1.7 推荐的 related work 结构（精简版）

最终论文里的 related work 不要写成散乱的大综述，建议只保留下面四组：

1. **机械臂 / 轨迹整形 / slosh-free transport**

   - [Arrizabalaga et al., 2024, ICRA, “Geometric Slosh-Free Tracking for Robotic Manipulators”](https://doi.org/10.1109/ICRA57147.2024.10610813)
   - 这一组的作用是说明：已有 slosh-free 工作很多集中在机械臂、轨迹整形、几何跟踪或 teleoperation，不是移动机器人在线局部控制。

2. **移动机器人 / 服务机器人携液控制**
   - [Choi et al., 2024, Robotics and Autonomous Systems, “Suppressing Violent Sloshing Flow in Food Serving Robots”](https://www.sciencedirect.com/science/article/pii/S092188902400112X)
   - 这一组的作用是说明：移动平台上已有与携液稳定相关的工作，但方法多数更偏平台稳定、参考整形或简单逻辑，而不是你现在这种“局部路径跟踪 MPC + 晃动状态增广 + 预测风险治理”。

3. **液面传感 / 状态观测 / 测量链路**
   - [Qi et al., 2023, Sensors, “Observing Liquid Sloshing Based on a Multi-Degree-of-Freedom Pendulum Model and Free Surface Fluctuation Sensor”](https://www.mdpi.com/1424-8220/23/21/8831)
   - [Weaver et al., 2024, IEEE Sensors Letters, “Slosh Measuring Sensor System for Liquid-Carrying Robots”](https://doi.org/10.1109/LSENS.2024.3473688)
   - 这一组的作用是说明：真实量测链路是合理且必要的，你的系统不能长期只停留在模型内部量。

4. **局部风险场 / 避障规划（只作为 future work 参考）**
   - [Zhou et al., 2021, IEEE RA-L, “EGO-Planner: An ESDF-Free Gradient-Based Local Planner for Quadrotors”](https://ieeexplore.ieee.org/document/9309347/)
   - [Zhou et al., 2020, ICRA, “Robust Real-time UAV Replanning Using Guided Gradient-Based Optimization and Topological Paths”](https://doi.org/10.1109/ICRA40945.2020.9196996)
   - 这一组不是你当前主线的 related work 核心，只是为后续“局部几何风险场 + 携液风险场”做方法灵感储备。

最终写法建议是：

- 第一段写机械臂与轨迹整形
- 第二段写移动机器人携液控制
- 第三段写液面传感与状态观测
- 最后一段用 3~5 句明确点出你的差异：
  - 你研究的是**移动机器人在线局部路径跟踪**
  - 你用的是**tracking MPC**
  - 你关注的是**晃动风险与任务效率的在线权衡**
  - 你目标是**实机验证**

## 3. 当前最致命的不足

### 3.1 没有真实液面测量

这是当前最关键的问题。

如果没有任何真实液面测量，审稿人很容易质疑：

- 你压下去的是不是真实晃动？
- 还是只是模型内部估计值变小了？
- 如果模型偏了，实验结论是否仍然成立？

### 3.2 当前算法结构还偏工程拼接

当前结构是：

- QP 内：slosh soft cost / 盒约束
- QP 外：speed governor

这在工程上完全合理，但论文上会被问：

- governor 是否只是 heuristic？
- 它与 MPC 的关系是否只是“外挂限速器”？
- 贡献是否足够理论化/系统化？

### 3.3 缺少强基线与消融矩阵

目前必须至少有以下对比：

1. baseline tracking MPC（`Q_slosh=0`, governor off）
2. soft cost only
3. box constraint only
4. governor only
5. full method

如果没有这组对比，论文说服力会不够。

### 3.4 现在不适合再扩题

如果现在把避障、MPCC、复杂地图约束、学习控制一起拉进来，问题会立刻变成：

- 论文问题定义变了
- 变量太多
- 实验难以归因
- 时间被摊薄

这对投稿非常不利。

## 5. 我建议的论文算法主线

我建议你把算法升级成下面这个版本：

## 5.1 主方案：风险自适应的 slosh-aware tracking MPC

保持当前 tracking MPC 主体不变，但做三项增强：

1. **IMU 校准后的激励输入**
   - 用 IMU 替换/校正 `ay`、`omega_z`、`alpha_z`
   - 把当前 odom-based fallback 保留为备份

2. **风险自适应权重/约束**
   - 不再让 `Q_slosh` 是常数
   - 改成 `Q_slosh = f(risk)`
   - 必要时让 `eta_bar = g(risk)` 或 `v_des = h(risk)`

3. **终端残余晃动抑制**
   - 在终端或末端若干步中，对 `eta_x_dot / eta_y_dot` 再给一个 residual damping 项
   - 让系统不是只追求“到点”，还追求“到点时液体别还在明显摆”

这样做的好处是：

- 不改大结构
- 工程上可控
- 论文上能形成比“固定 Q + governor”更完整的故事

### 5.2 为什么这个方向比“单纯加大 Q”更好

### 5.2 一个可直接实现的 risk-adaptive 草案

这里给一个**尽量贴近当前代码结构**、可以直接落地的第一版方案。

#### 5.2.1 risk 用哪些量组成

我建议第一版 risk 只用 4 个量，全部都能从你当前系统里拿到：

1. 当前晃动高度比例
   - `r_now = h_now / h_lim`
   - 其中 `h_now = /slosh/height`
   - `h_lim = mpc/slosh_height_max`

2. 预测晃动高度比例
   - `r_pred = h_pred_max / h_lim`
   - 其中 `h_pred_max = /slosh/height_pred_max`

3. 当前横向激励比例
   - `r_ay = |ay_est| / ay_lim`
   - 其中 `ay_lim` 可以先用 `path_handler/max_lat_accel`

4. 前方曲率风险比例
   - `r_kappa = |kappa_preview| / kappa_ref`
   - `kappa_preview` 可直接来自前方曲率预览
   - `kappa_ref` 取一个经验基准值，用于归一化

第一版不要把量搞太多。先把 risk 做简单、可解释、可调试。

#### 5.2.2 一个简单可用的 risk 公式

第一版我建议直接用加权和，再做饱和：

```text
risk_raw =
    w_now  * clamp(r_now,   0, 2.0) +
    w_pred * clamp(r_pred,  0, 2.0) +
    w_ay   * clamp(r_ay,    0, 2.0) +
    w_k    * clamp(r_kappa, 0, 2.0)

risk = clamp(risk_raw, 0, 1)
```

建议的初始权重：

```text
w_now  = 0.20
w_pred = 0.45
w_ay   = 0.20
w_k    = 0.15
```

这样做的原因是：

- 当前残余晃动重要
- 但**预测峰值**应该占更高权重
- `ay` 和曲率更多是先验激励风险

#### 5.2.3 risk 作用到哪里

第一版不要同时改太多地方。推荐分两步：

**版本 A：论文主实验优先**

只让 risk 调整 `Q_slosh_eta`：

```text
Q_slosh_eta_eff =
    Q_slosh_eta_min +
    (Q_slosh_eta_max - Q_slosh_eta_min) * smoothstep(risk)
```

这样你能更干净地回答：

- 固定 `Q_slosh` 和 risk-adaptive `Q_slosh` 谁更好

**版本 B：工程增强版**

再让 risk 去调参考速度：

```text
v_des_eff = v_des_cmd * (1 - lambda_v * smoothstep(risk))
```

或者只在 `risk > r_enter` 时启动当前 governor。

我的建议是：

- 论文对比时先做 **A**
- 工程最终版本再做 **A + B**

否则你很难在论文里说清楚，到底收益来自 adaptive Q，还是来自外层限速。

#### 5.2.4 一个更稳妥的 smoothstep 形式

为了避免 risk 在阈值附近抖动，建议不要用硬切换，而是用平滑函数：

```text
z = clamp((risk - r0) / (r1 - r0), 0, 1)
smoothstep(z) = 3 z^2 - 2 z^3
```

例如：

```text
r0 = 0.25
r1 = 0.75
```

这样低风险时几乎不介入，高风险时快速增强。

#### 5.2.5 建议新增的话题和日志量

为了让这套方法可解释，建议新增这些调试量：

- `/slosh/risk`
- `/slosh/risk_now_ratio`
- `/slosh/risk_pred_ratio`
- `/slosh/risk_ay_ratio`
- `/slosh/risk_kappa_ratio`
- `/slosh/Q_slosh_eta_eff`

如果后面 governor 也联动，再加：

- `/slosh/risk_v_scale`

没有这些可视化量，后面调参会非常痛苦。

#### 5.2.6 代码落点建议

第一版可以这样拆：

1. `local_planner_ros.cpp`
   - 计算 `risk`
   - 计算 `Q_slosh_eta_eff`
   - 发布 risk 相关调试话题

2. `types.h`
   - 增加 runtime risk-adaptive 配置参数

3. `cost_function.cpp`
   - 支持读取运行时更新后的 `Q_slosh_eta`

更稳妥的做法不是直接反复改全局 `mpc_params_`，而是：

- 保留一份 `base params`
- 每周期生成一份 `runtime params`
- 用 `runtime params` 构建本周期求解

这样逻辑最清楚，也最适合论文描述。

#### 5.2.7 这套草案的优点

- 和当前代码结构兼容
- 不需要改成非线性 MPC
- 可解释性强
- 能直接形成论文对比实验

这会比“试很多固定 Q，然后挑最好一个”更像方法贡献。

### 5.3 为什么这个方向比“单纯加大 Q”更好

因为论文不应该只是说：

- `Q=5` 比 `Q=0` 好

而应该说：

- 系统能根据当前风险自适应地调节 anti-slosh 强度
- 在不显著牺牲任务效率的前提下压制晃动风险

这才更像一个可发表的方法。

### 5.4 备选增强：slack 约束

如果后面发现盒约束经常导致不可行，可以考虑：

- 给 slosh box constraint 引入 slack
- 并在 cost 中惩罚 slack

但我的建议是：

- **把 slack 放到第二优先级**
- 先做 IMU + 真实测量 + 风险自适应权重

### 5.5 如果未来要把避障也融进去，什么方向更值得

这个方向**有价值**，但我建议把它当成**第二篇文章或后续扩展**，不要和当前主线混在一起。

先说清一个关键点：

- **EGO-Planner 不是 ESDF planner**
- 它的核心恰恰是 **ESDF-free**
- 它通过引导路径和碰撞惩罚来拿局部梯度，而不是显式构建全局 ESDF

所以如果你说“像 EGO-Planner 那样算局部 ESDF 场”，这个说法本身不准确。

更准确地说：

- 如果你想走 **ESDF / signed-distance field** 路线，更接近 `Fast-Planner` 这类思路
- 如果你想走 **不用显式 ESDF、直接做局部几何碰撞惩罚**，才更接近 `EGO-Planner`

#### 5.5.1 对你这个差速车，后续更适合什么

对当前项目，我更建议未来做成：

**2D 局部几何风险场 + 携液风险场的联合规划**

而不是生搬硬套四旋翼的整套轨迹优化框架。

原因：

1. 你是地面差速车，不需要 3D B-spline 飞行轨迹那套复杂结构
2. 你已经有 ROS 导航栈和局部路径跟踪器
3. 你真正需要的是：
   - 障碍物距离风险
   - 窄通道风险
   - 急转弯风险
   - 液体晃动风险
   - 它们之间的统一治理

#### 5.5.2 一个更适合你的 future work 方向

后续可以定义一个**联合风险场**：

```text
R_total(p, s, v) =
    w_obs   * R_obs(p) +
    w_turn  * R_turn(s) +
    w_slosh * R_slosh(s, v, eta) +
    w_stop  * R_stop(p, v)
```

其中：

- `R_obs(p)`：来自局部 costmap 或局部距离变换的障碍物接近风险
- `R_turn(s)`：来自路径前方曲率或转角变化
- `R_slosh(s, v, eta)`：来自预测晃动、当前晃动和速度
- `R_stop(p, v)`：来自刹停空间不足或窄通道中的速度风险

然后让这个联合风险场作用于：

- `Q_slosh`
- `v_des`
- 局部路径选择
- 或者障碍物附近的约束收紧

#### 5.5.3 如果真要做“场”，我建议分两条路线

**路线 A：工程上更稳**

- 基于 `local_costmap` 做 2D Euclidean distance transform
- 得到一个局部障碍距离场
- 再叠加一层 slosh risk layer

优点：

- 最贴近你现有 ROS 体系
- 好实现
- 容易做可视化

**路线 B：方法上更新**

- 不显式算完整 ESDF
- 只在候选局部路径 / 参考点序列附近提取必要几何风险
- 类似 `EGO-Planner` 的“只计算需要的局部几何信息”

优点：

- 更新快
- 更有“新方法”味道

缺点：

- 实现与调试难度更高
- 论文故事会立刻从“液体控制”变成“风险感知局部规划”

#### 5.5.4 我的建议

如果是**当前这篇主投稿**：

- 不要把避障正式并入主方法
- 最多在 future work 里写

如果是**后续继续深挖的第二阶段**：

- 我认为“局部几何风险场 + 携液风险场 + risk-adaptive local planning”是很有潜力的方向
- 这条线甚至可能比单纯做 MPCC 更有新意

但这已经不是“把当前稿子补齐”了，而是在开一个新问题定义。

```text
struct RiskAdaptiveParams {
    bool enable;
    std::string mode;
    double q_slosh_min;
    double q_slosh_max;
    double r0;
    double r1;
    double w_now;

    double w_ay;
    double w_kappa;
    double kappa_ref;
    double ay_ref;
    double v_scale_max;

struct RiskAdaptiveState {
    double r_now;
    double r_pred;
    double r_ay;
    double r_kappa;
    double risk;
    double smooth_risk;

```

- 参数和运行态分离

   - 在拿到 `ref_points` 之后、调用 MPC 之前计算 risk
   - 生成 `runtime q_slosh_eta_eff`
   - 如果是 `q_and_speed` 模式，再同步调整 `v_des_eff`

4. `publishDebugTopics()`
   - 发布 risk 调试量

推荐的控制流程是：

```text
原始 v_des_cmd
    ↓
先生成一版 ref_points
    ↓
根据当前/预测状态 + 曲率预览 计算 risk
    ↓
得到 q_slosh_eta_eff
    ↓
如果 mode=q_and_speed，再更新 v_des_eff
    ↓
必要时重新生成 ref_points
    ↓
构建 runtime params
    ↓
MPC 求解
```

这个顺序和你当前 governor 的位置是兼容的。

#### 6.2.5 运行时参数不要怎么改

这里有一个很重要的工程建议：

**不要直接在控制循环里永久改写全局 `mpc_params_`。**

更稳妥的方式是：

```text
const MPCParams runtime_params = buildRuntimeMPCParams();
mpc_solver_.setParams(runtime_params);
```

也就是说：

- `mpc_params_` 保留为“静态基础参数”
- `runtime_params` 是“本周期求解参数”

这样能避免：

- 参数污染
- debug 时看不清当前值
- 后续同时接入 governor/box constraint 时逻辑混乱

#### 6.2.6 一个更具体的运行时计算顺序

每个控制周期建议按下面的顺序执行：

1. 读取当前 `h_now = slosh_height`
2. 读取上一周期 `h_pred_max`
3. 读取 `ay_est_used`
4. 计算 `kappa_preview`
5. 归一化得到 `r_now / r_pred / r_ay / r_kappa`
6. 得到 `risk_raw`
7. 做 saturate 和 smoothstep
8. 计算 `q_slosh_eff`
9. 计算 `q_slosh_eta_eff = q_slosh_eff * height_coeff^2`
10. 若 `mode=q_and_speed`，计算 `v_scale`
11. 发布 risk 相关话题
12. 用本周期 runtime params 求解 MPC

建议先不要把 `eta_bar` 也做成 adaptive。

原因：

- 一次改太多，很难分辨收益来源
- 盒约束可行性本来就更敏感

所以推荐阶段顺序是：

```text
第 1 阶段：adaptive Q
第 2 阶段：adaptive Q + speed scaling
第 3 阶段：必要时再考虑 adaptive eta_bar
```

#### 6.2.7 建议新增的 YAML 示例

可以在 `mpc_params.yaml` 和 `mpc_params_sim.yaml` 里预留：

```yaml
risk_adaptive:
  enable: false
  mode: "q_only"
  q_slosh_min: 0.0
  q_slosh_max: 5.0
  r0: 0.25
  r1: 0.75
  w_now: 0.20
  w_pred: 0.45
  w_ay: 0.20
  w_kappa: 0.15
  kappa_ref: 0.8
  ay_ref: 0.8
  v_scale_max: 0.35
  debug_publish: true
```

后面 `slosh_experiment.launch` 里建议额外暴露：

```text
risk_adaptive_enable
risk_adaptive_mode
risk_adaptive_q_slosh_max
risk_adaptive_r0
risk_adaptive_r1
```

这样做消融实验最方便。

#### 6.2.8 建议增加的实验组

在当前五组 baseline 之外，risk-adaptive 还要单独做：

1. `fixed Q=5`
2. `adaptive Q (0~5)`
3. `adaptive Q + speed scaling`

如果时间够，再补：

4. `fixed Q=10`

这样你就能回答三个关键问题：

- adaptive 是否比固定 `Q=5` 更好
- adaptive 是否比更保守的固定 `Q=10` 更有效率
- 收益来自 adaptive Q，还是来自额外降速

#### 6.2.9 建议的论文图表

如果你真做这部分，论文里至少应该加两张图：

1. `risk / q_slosh_eff / v_des_eff` 的时序图
2. `fixed-Q vs adaptive-Q` 的峰值-时间 tradeoff 图

这是最能体现“不是简单调参，而是在线权衡”的证据。

#### 6.2.10 一个现实的开发顺序

我建议你后面真正开工时按下面顺序做：

1. 先只加 `risk` 计算和调试话题，不改控制逻辑
2. 再加 `adaptive Q`
3. 跑仿真验证是否数值稳定
4. 再加 `adaptive speed scaling`
5. 最后才上实机

这个顺序能最大限度避免“逻辑和实验一起乱掉”。

### 6.3 第三阶段：加入终端残余晃动项

建议改动：

- `cost_function.cpp`

加入末端项，例如：

- `Q_eta_dot_terminal * (eta_x_dot^2 + eta_y_dot^2)`

目的：

- 不只是让液面高度小
- 还让到达时剩余振动速度小

## 7. 实验设计必须怎么做

### 7.1 必须有的任务集合

至少三类：

1. 直线加减速
2. 定半径转弯
3. S 弯/连续曲率变化路径

### 7.2 必须有的基线

至少五组：

1. baseline tracking MPC
2. soft cost only
3. box constraint only
4. governor only
5. full method

### 7.3 必须有的观测来源对比

至少两组：

1. odom-only
2. imu-enabled

### 7.4 必须有的评价指标

#### 跟踪与效率

- tracking time
- goal reached rate
- path tracking error
- `v_des_eff_mean`

#### 求解稳定性

- `/mpc/solve_ms`
- `solve_fail_count`
- `status_val`

#### 液体相关

- `pred_max`
- `pred_rms`
- **measured height max / rms**（必须尽量补）
- spill event / overflow proxy（如果能定义）

#### 一致性诊断

- 预测 vs 实测的相关性
- IMU vs odom fallback 的差异

### 7.5 每组实验次数

- 最低：每组 5 次
- 更稳妥：每组 10 次

没有重复实验，`RA-L` 说服力会很弱。

## 8. 真实液面测量这件事怎么解决

### 8.1 我最推荐的方案

如果你短期做不到复杂传感器，我建议先选一个**低成本可交付方案**：

1. 顶视相机 + 标尺
2. 容器侧视相机 + 轮廓提取
3. 简单 ToF/激光测距方案

论文角度上，哪怕这个量测是：

- 低频
- 离线处理
- 近似指标

也比“完全没有真实 liquid measurement”强得多。

### 8.2 如果短期实在没有液面传感器怎么办

那论文还能不能投？

可以，但风险明显更高。

这时你最多只能把论文定位成：

- **model-based risk suppression**
- 而不是强意义上的 **real slosh suppression**

我不建议把自己放到这么被动的位置。
