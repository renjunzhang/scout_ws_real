## 5. Information-access fairness

新增：

```text
spmpc_experiments/config/benchmark/information_access_policy.yaml
```

### 5.1 原则

主对比中，不同方法允许的信息必须符合其方法类别。

| 方法类别 | 允许输入 | 禁止输入 |
|---|---|---|
| Classical / modern local planner | odom, TF, map/costmap/scan, global/fixed path | `/liquid/height`, RGB 液面, slosh modal state |
| Ordinary MPC local planner | odom, TF, costmap, path | 在线液体反馈、SPMPC 内部 slosh 状态 |
| Hamaguchi / Lim profile baseline | 离线液体模型参数、固定路径、common limits | 在线 RGB 液面反馈、运行中根据液面改 profile |
| SPMPC | odom-derived slosh state, slosh model, path, optional map | 在线 RGB 液面闭环反馈，除非另设实验族 |
| slosh monitor | odom/cmd_vel 与统一 slosh model | 发布结果被任何 planner、profile generator、command gate 在线消费 |
| 评价脚本 | bag 内所有记录 topic，包括 monitor-only topic | 不得把某方法内部私有模型输出当跨方法唯一主指标 |

### 5.2 关键边界

论文主表中，SPMPC 的 `/spmpc/slosh_height` 不能单独作为跨方法主排名指标。推荐优先级：

#### 仿真

1. 统一 monitor-only external slosh observer / replay model；
2. 若仿真有液面真值，则真值优先；
3. SPMPC internal slosh 只作诊断和消融解释。

#### 实物

1. RGB offline / online liquid height，标定与 ROI 统一；
2. external slosh observer 作为补充；
3. SPMPC internal slosh 只作诊断。

## 6. External slosh observer / monitor-only policy

新增：

```text
spmpc_experiments/config/benchmark/external_slosh_observer_policy.yaml
spmpc_experiments/config/benchmark/slosh_model_monitor_policy.yaml
```

### 6.1 目标

为所有 planner 提供统一的液体 proxy 评价，避免“SPMPC 用自己的内部模型评价自己”。

同时，仿真阶段必须能实时检测到 slosh model 高度变化，作为后续实物 RGB 液面结果的对照锚点。这个 slosh monitor **只做监控数据，不参与闭环控制，不参与 planner/OCP/profile 的计算，不改变 `/cmd_vel`**。

### 6.2 Monitor-only 边界

新增一个独立的 `slosh_model_monitor` 监控链，定位是：

```text
/odom 或 /cmd_vel
  -> slosh_models 统一模型 replay/observer
  -> /benchmark/slosh_monitor/*
  -> rosbag / metrics / report
```

禁止链路：

```text
/benchmark/slosh_monitor/*
  -> planner input
  -> SPMPC OCP parameter
  -> profile generator during test
  -> command gate
  -> /cmd_vel
```

也就是说，monitor 可以计算并发布液面高度变化，但这些数据只能用于：

1. 仿真/实物对比记录；
2. 离线指标提取；
3. RViz/plot 实时观察；
4. 调试“某段路径是否激发液体晃动”。

不得用于：

1. 在线调 `v_ref`；
2. 在线调 `w_slosh`；
3. 触发 planner 重新规划；
4. 修改 command gate 输出；
5. 在 test case 中生成或修正 profile。

### 6.3 推荐策略

```yaml
external_slosh_observer:
  source_model: slosh_models
  mode: monitor_only
  inputs:
    odom: /odom
    cmd_vel_executed: /cmd_vel
    cmd_vel_raw: /benchmark/cmd_vel_raw
  outputs:
    height_topic: /benchmark/slosh_monitor/height
    state_topic: /benchmark/slosh_monitor/state
    event_topic: /benchmark/slosh_monitor/event
    debug_topic: /benchmark/slosh_monitor/debug
  control_usage:
    allowed: false
    forbidden_consumers:
      - planner
      - spmpc_ocp
      - profile_generator_during_test
      - command_gate
  use_for_main_metrics:
    sim: true
    real: secondary
  rgb_priority_real: true
  notes:
    - "Monitor output is for observation, bagging, and offline metrics only."
    - "External observer is still a model proxy, not ground truth."
    - "Do not mix SPMPC internal slosh_height with monitor slosh height in the same metric column."
```

### 6.4 Monitor topics

建议所有仿真 case 默认启动 monitor，并记录：

| topic | 类型建议 | 用途 |
|---|---|---|
| `/benchmark/slosh_monitor/height` | `std_msgs/Float64` 或同等数值消息 | 统一 slosh model 高度 proxy，单位建议 mm |
| `/benchmark/slosh_monitor/state` | `Float64MultiArray` / custom msg | `eta_x, eta_x_dot, eta_y, eta_y_dot` 等状态 |
| `/benchmark/slosh_monitor/event` | `std_msgs/String` / diagnostic msg | 高度变化、peak、over-threshold 事件 |
| `/benchmark/slosh_monitor/debug` | diagnostic msg | 输入延迟、dt、ax/ay 估计、模型参数 |

推荐 monitor 同时输出：

```text
height_mm
height_delta_mm
height_abs_delta_mm
height_peak_mm
height_p95_window_mm
over_threshold_flag
```

这些量用于检测“仿真时 slosh model 高度是否真的变化”，以及后续与实物 RGB 液面变化对齐。

### 6.5 指标命名

必须分清：

```text
spmpc_internal_slosh_*      # SPMPC 内部预测/观测，诊断
slosh_monitor_model_*       # 统一 monitor-only 模型 proxy，跨方法仿真主指标之一
rgb_liquid_*                # 实物 RGB 指标，实物主指标
```

### 6.6 启动与录包要求

仿真对比 case 默认启动 monitor；实物 case 建议启动同一个 monitor，但其结果只作为 RGB 的补充解释。

推荐启动顺序：

```text
start sim/localization
  -> start path publisher
  -> start slosh_model_monitor
  -> start planner adapter
  -> start rosbag
  -> run case
```

推荐录包 topic：

```text
/benchmark/slosh_monitor/height
/benchmark/slosh_monitor/state
/benchmark/slosh_monitor/event
/benchmark/slosh_monitor/debug
```

如果 monitor 未启动或 topic 缺失：

- 仿真 strict 主表：标记 `REQUIRED_TOPIC_MISSING`，不进入 slosh 指标主表；
- 仿真 smoke：允许继续，但标记 `monitor_missing: true`；
- 实物：允许继续，以 RGB 为主，monitor 缺失写入 warning。

### 6.7 Monitor 防泄漏检查

为了证明 monitor 没有参与闭环，preflight 和 metadata 需要记录：

```yaml
slosh_monitor:
  enabled: true
  mode: monitor_only
  output_namespace: /benchmark/slosh_monitor
  consumed_by_planner: false
  consumed_by_command_gate: false
  consumed_by_profile_generator_during_test: false
  allowed_consumers:
    - rosbag
    - metrics_extractor
    - rviz_or_plot
```

`bench_preflight.py` 应检查：

1. planner launch 参数中没有订阅 `/benchmark/slosh_monitor/*`；
2. command gate 不订阅 `/benchmark/slosh_monitor/*`；
3. profile generator 只在 case 前离线生成 CSV，不在 test case 运行中读 monitor；
4. bag/metrics 可以订阅 monitor topic。

### 6.8 与实物 RGB 的对齐用途

monitor 的主要价值不是替代 RGB，而是建立仿真到实物的一致对照：

```text
仿真：slosh_monitor_model_height -> 判断模型液面 proxy 是否被路径/控制激发
实物：rgb_liquid_height + slosh_monitor_model_height -> 判断模型 proxy 与真实视觉液面的量级/趋势差异
```

报告中建议同时列：

```text
slosh_monitor_model_peak_mm
slosh_monitor_model_p95_mm
slosh_monitor_model_rms_mm
rgb_liquid_peak_mm           # 实物有 RGB 时
rgb_liquid_p95_mm
rgb_liquid_rms_mm
```

并明确写：monitor 是 **monitor-only model proxy**，不是控制输入，也不是真值。

### 7.1 目标

避免 SPMPC 被充分调参、baseline 只用默认参数导致不公平。

### 7.2 推荐 schema

```yaml
tuning:
  split:
    train_scenarios:
      - s_curve_x5_train
      - straight_x5_train
    validation_scenarios:
      - s_curve_x5_val
    test_scenarios:
      - s_curve_x5_test
      - threshold_s_curve_test

  trials:
    max_performance_tuning_trials_per_planner: 20
    integration_debug_trials: recorded_but_not_counted
    fixed_random_seed: 42

  selection_metric:
    primary: success_rate
    secondary: external_or_rgb_slosh_p95_mm
    tertiary: first_goal_time_s
    quaternary: abs_domegadt_p95

  forbidden:
    - tune_on_test_set
    - manual_parameter_change_after_test_bag_seen
    - compare_default_baseline_against_heavily_tuned_ours_without_disclosure

  freeze:
    require_parameter_freeze_before_test: true
    require_config_hash: true
    require_git_sha: true
```

### 7.3 metadata 要求

每个主表 case 必须记录：

```yaml
tuning:
  phase: test
  parameters_frozen: true
  tuning_trials_used: 12
  tuned_on_scenarios:
    - s_curve_x5_train
    - straight_x5_train
  config_hashes:
    planner_config: ...
    adapter_config: ...
    common_limits: ...
    scenario: ...
```

## 8. Command gate 公平性

v1 的 command gate 设计保留，但需要更严的主表准入阈值。

### 8.1 两级阈值

```yaml
command_gate_policy:
  clamp_ratio_warning: 0.01
  clamp_ratio_main_table_exclusion: 0.05
  raw_limit_violation_warning: true
  record_raw_and_executed_cmd: true
```

### 8.2 主表必须列出的控制字段

```text
cmd_raw_v_max
cmd_raw_omega_max
cmd_raw_abs_dvdt_p95
cmd_raw_abs_domegadt_p95
cmd_exec_v_max
cmd_exec_omega_max
cmd_exec_abs_dvdt_p95
cmd_exec_abs_domegadt_p95
command_gate_clamp_ratio
```

### 8.3 原则

command gate 只能作为安全兜底，不能作为隐式控制器。若一个 planner 需要 command gate 长时间修正输出，说明它没有在内部满足 common-limit，应标为 fairness warning 或排除主表。

## 10. Profile baseline 公平性

Hamaguchi-style 与 Lim-style 不应各自带不同 tracker。它们必须共享同一个 profile tracking layer。

### 10.1 三层拆分

```text
profile_generator
  -> profile_csv
  -> common_profile_tracker
  -> command_gate
  -> metrics
```

| 模块 | Hamaguchi 与 Lim 是否允许不同 |
|---|---:|
| profile generator | 是 |
| profile CSV schema | 否 |
| profile tracker | 否 |
| command gate | 否 |
| metrics analyzer | 否 |

### 10.2 复用现有 CSV schema

优先复用：

```text
scout_local_planner/scripts/analysis/path_profile_utils.py
```

标准字段：

```csv
s_normalized,s_m,t_s,x,y,yaw,v_ref_m_s,a_ref_m_s2,jerk_ref_m_s3,method
```

不要新发明第二套 profile CSV。

### 10.3 `profile_tracking_common.yaml`

```yaml
profile_tracker:
  implementation: scout_local_planner_external_profile
  external_profile_mode: custom_csv
  path_topic: /scout/global_path_fixed
  output_cmd_topic: /benchmark/cmd_vel_raw
  constraints:
    v_max: 0.8
    omega_max: 1.2
    a_max: 0.6
    alpha_max: 1.2
  tracking:
    lookahead_distance_m: fixed
    goal_tolerance_m: common
    yaw_tolerance_rad: common
  execution_cap:
    enabled: true
    accel_limit: 0.6
    decel_limit: 0.6
    jerk_limit: null
```

### 10.4 Hamaguchi-style 生成器

第一版不要完整复刻论文，建议在现有 Biagiotti/profile 工具基础上新增：

```text
spmpc_experiments/scripts/generate_hamaguchi_profile.py
```

输入：fixed path + liquid natural frequency/damping + common limits。  
输出：标准 profile CSV。

### 10.5 Lim-style 生成器

新增：

```text
spmpc_experiments/scripts/generate_lim_style_profile.py
```

第一版只做沿固定路径的离线 `v(s)` 或 `v(t)` 优化，不做完整二维轨迹优化。

## 12. Preflight 与 freshness checker

### 12.1 `bench_preflight.py`

新增统一预检脚本，避免每个 shell 里重复写检查逻辑。

检查内容：

```yaml
preflight:
  common:
    - git_status_recorded
    - required_ros_packages_found
    - common_limits_loadable
    - scenario_loadable
    - path_tool_available
    - metrics_extractor_available
    - slosh_monitor_config_loadable
    - slosh_monitor_launch_available
    - slosh_monitor_not_listed_as_planner_input

  planner_specific:
    spmpc:
      - acados_solver_available
      - generated_bounds_match_or_warn
    baseline_runner:
      - plugin_class_loadable
      - config_yaml_exists
    mpc_planner:
      - src_mpc_planner_exists
      - ros1_mode
      - dependencies_present
      - generated_solver_present
    lt_dwa:
      - package_exists
      - launch_exists
```

### 12.2 `bench_check_freshness.py`

新增 strict fresh-sim 检查器。

职责：

1. case 前检查 ROS/Gazebo 是否干净；
2. case 后检查 ROS/Gazebo 是否残留；
3. 输出 machine-readable YAML；
4. 不负责 broad killall/pkill；
5. 只用于检查和记录。

结果写入：

```yaml
freshness:
  strict_requested: true
  pre_ros_alive: false
  pre_gazebo_alive: false
  post_ros_alive: false
  post_gazebo_alive: false
  passed: true
```

若使用已运行仿真，只能标记：

```yaml
strict_fresh: false
run_type: current_sim_diagnostics
```

不能进入 strict fresh-sim 主表。

## 13. `src/mpc_planner` 接入策略

`src/mpc_planner` 更现代，但依赖重，不应直接承诺进主表。

### 13.1 M0：preflight only

检查：

- 是否在 ROS1/catkin 模式；
- 伴生依赖是否存在；
- solver generation 是否完成；
- wrapper launch 是否可解析；
- 是否能输出 `/cmd_vel` 或 remap 到 `/benchmark/cmd_vel_raw`。

失败状态：

```text
MPC_PLANNER_NOT_READY
```

这不是算法失败。

### 13.2 M1：no-obstacle fixed-path smoke

只接：

```text
/odom
/scout/global_path_fixed
/benchmark/cmd_vel_raw
```

暂不接 pedestrian simulator、dynamic obstacle predictor、roadmap。

### 13.3 M2：common-limit strict fresh-sim

通过 M1 后，再做 common-limit strict fresh-sim。

### 13.4 M3：进入主表

只有满足 main-table inclusion criteria 后，才作为 modern MPC baseline 进入主表。否则作为 related work / advanced skipped baseline 说明。

## 14. LT-DWA 接入策略

当前 LT-DWA 上游源码已作为普通目录 vendored 到 `third_party/LT_DWA/`，但不放入 catkin 扫描的 `src/`，因为上游包含 `local_planner`、`navigation` 等与当前 workspace 冲突的 package 名称。
因此：

1. 文档可以把 LT-DWA 作为目标 modern baseline；
2. preflight/readiness 应检查 `third_party/LT_DWA` source-only vendor；
3. vendor 缺失时标记 `LT_DWA_NOT_INSTALLED`，vendor 存在但 adapter 未完成时标记 `LT_DWA_ADAPTER_NOT_READY`；
4. 不得把 dependency/readiness 状态记为算法失败。

## 15. 实物 git pull 友好约束

实物端只应需要：

```bash
git pull
catkin build <changed packages>
rosrun spmpc_experiments bench_preflight.py --mode real --planner ...
roslaunch ...
```

不应在实物机临时改源码。

### 15.1 提交到 git 的内容

应提交：

- benchmark config；
- preflight/freshness scripts；
- profile generator；
- common profile tracker config；
- report template；
- example local config。

不提交：

- bag；
- 大结果目录；
- 实物机私有 IP/路径；
- 外置盘绝对路径；
- 大型 generated solver artifacts，除非项目明确需要。

### 15.2 local override

```text
spmpc_experiments/config/local/*.local.yaml
```

加入 `.gitignore`，提交 `.example.yaml`。
