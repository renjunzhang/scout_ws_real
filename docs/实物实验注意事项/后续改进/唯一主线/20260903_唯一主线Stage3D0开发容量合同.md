## 1. 本阶段解决的问题

Stage 3 的 solver 固定数组宽度需要明确的延迟队列容量，但这个容量不等于已经辨识并晋级的生产 `delay/tau/gain`。若继续让 development codegen 读取历史 Stage 0/1 的 `PROHIBITED` 状态或等待 validation/final-test bag，就会重新形成“没有 solver 无法验证、没有正式验证又不能生成 solver”的循环。

本阶段建立独立的 `DevelopmentCapacityContract`：只冻结开发 artifact 的整数容量和由它唯一派生的维度。它允许后续生成带 `DEV_UNVALIDATED` 标签的开发 solver，但不授予 production promotion、formal evidence 或实车运动资格。

## 2. 整数是唯一容量权威

容量先冻结在 30 Hz release grid 上的整数 interval：

```text
R_v     = 12
R_omega = 24
dt      = 1/30 s

D_v     = R_v - 1     = 11
D_omega = R_omega - 1 = 23
NQ_v    = R_v + 1     = 13
NQ_omega= R_omega + 1 = 25

NX      = 14 + D_v + D_omega       = 48
NU      = 3
NP_exec = 7 + 3*(NQ_v + NQ_omega) = 121
```

`L_max` 只保存为精确的 `12/30 s`、`24/30 s` 有理表示。loader 不从 `0.40/0.80` 浮点秒数反算 `ceil(L_max/dt)`，因此不会在整数边界因二进制浮点误差改变 codegen 维度。

## 3. 证据与权限边界

`diag/lt-dwa-collision-tracking@d601e313deefcaeaacdf027296d3ba0ce376b62e` 仅作为选择该保守容量的 provenance metadata。capacity loader：

- 不打开或查询该分支；
- 不读取 bag、ROS、git clean、RGB 或 validation/final-test 划分；
- 不导入 `stage1_evidence.py`、`contract_source.py` 或旧 Stage 3a manifest；
- 不把来源 SHA 解释为生产参数 authority。

因此远程 bag 是否在本机可用不会阻塞开发布局和 codegen。正式参数晋级、目标机性能、live arm 和 formal evidence 仍由各自独立门禁裁决。

## 4. 固定字节身份与严格 schema

机器合同位于：

```text
config/mainline/contracts/development_capacity_v1.json
```

loader 对原始 JSON 字节计算并固定 SHA-256：

```text
22b1806e0c78d46cc6bf51b30002b30d2a42f29352f492d018aa11ec3ac5bca4
```

重新排版但语义相同的文件也不是同一个 v1 snapshot。解析和重建采用 fail-closed 规则，拒绝：

- 重复 key、未知字段、缺字段和非 UTF-8/非法 JSON；
- `bool`、浮点整数或字符串冒充整数；
- 非正 `R`、负 `D`、非正 `NQ/NX/NU/NP_exec`；
- `D/NQ/NX/NU/NP_exec` 任一派生值漂移；
- 把 `L_max` 改成小数、约分后的另一种表示或非 `R/30` 值；
- 把状态改写成 production/frozen authority；
- 直接构造或 `replace()` typed contract 绕过 pinned loader。

对外返回冻结 dataclass 和精确 `Fraction`；后续 Stage 3-D1 只接受该 typed contract，不接受散落的 `L_max_sec` 或调用者自报布尔 authority。
