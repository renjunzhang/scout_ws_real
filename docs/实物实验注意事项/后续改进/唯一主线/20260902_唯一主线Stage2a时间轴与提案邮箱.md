## 1. 实施边界

本子阶段只实现两项 ROS-free 基础设施：

- `ReleaseScheduler`：从冻结 `ClockAnchor` 逐拍枚举绝对 `1/30 s` 网格；
- `ProposalMailbox`：planning worker 与 release owner 之间的固定双槽、一次性 proposal 交接。

没有接入 ROS timer、`/cmd_vel`、TF、旧 planner、acados、generated solver、命令历史或权威状态提交。proposal 被 mailbox 接受或取出都不代表命令已经发布；只有后续 `FinalCommandPublisher` 成功后才能提交 emitted history、publisher state、delay queue、warm start 和 `s_commit`。

Stage 1 仍保持：

```text
BLOCKED_PENDING_DEDICATED_IDENTIFICATION_EVIDENCE
```

本实现不写入旧候选 `delay/tau/gain`，也不冻结 `L_max`，因此没有越过 Stage 3 codegen 门禁。

## 2. ReleaseScheduler 合同

`poll(now_steady)` 永远只检查最老的未消费边界：

- 早于 `T_k` 返回 `NotDue`，不推进 cycle；
- 等于 `T_k` 返回 `DueOnTime`；
- 晚于 `T_k` 返回 `DueLate`，仍只消费 `k`；
- 一次唤醒跨过多拍时，调用方必须连续得到 `k,k+1,k+2...`，不存在跳到最新拍的 API；
- `now_steady` 回退立即锁存 fault，不允许原 epoch 内自动重锚；
- 只有更大的 `reset_epoch` 才能显式 reset；
- 时间戳、lateness 或 cycle 溢出均 fail closed，失败时不回绕 cycle ID。

边界继续由 Stage 0 的有理网格直接计算，model time 只通过冻结 anchor 映射。

这里的 scheduler fault 只表示 steady clock regression、时间表示溢出等时间轴已失效。普通 proposal 缺失、solver failure 或 safety fault 不得停止 scheduler；后续 release coordinator 必须继续逐拍取得边界并真实发布安全零。

## 3. ProposalMailbox 合同

mailbox 限定为单 producer、单 consumer/owner，并使用两个固定槽位。每个槽位由一个 lock-free `uint64` 原子同时编码 cycle tag 与状态，避免物理槽复用时的 ABA：

```text
Empty -> Open -> Writing -> Ready -> Claiming -> Claimed
              \-> Rejected -> Claiming -> Claimed
Open -> Closed
Writing -> CloseRequested -> Abandoned
```

关键规则：

1. `arm` 只能按严格连续 cycle ID 进行；两个槽位占满时立即返回 busy。
2. proposal 必须精确匹配 cycle、steady/model 边界、reset epoch、history generation 以及 config/model/artifact/path 四类 hash。
3. `ready_time <= cutoff` 合法，晚 `1 ns` 即拒绝；错误 identity 或 late proposal 会毒化本拍，后来的“正确” proposal 不能替换它。
4. `closeAndTakeExact` 将“关闭本拍”和“读取 proposal”合成一次原子状态裁决；若 producer 正在写，release 立即得到 missing，producer 最终只能进入 abandoned。
5. `k` 的迟到写入不能污染复用同一物理槽的 `k+2`；`k+1` 也不能替代缺失的 `k`。
6. payload 必须是固定大小且 trivially copyable；release 侧不分配内存、不取锁、不等待 solver。
7. 若目标平台的 tagged atomic 不是 lock-free，mailbox 构造直接失败。目标机仍需在后续性能阶段复核该条件和 release jitter。
8. 一个 mailbox 实例只绑定一个 `reset_epoch`，没有 in-place reset API。进入新 epoch 前必须先让旧 producer 停止访问旧实例，再构造绑定新 epoch 的 mailbox；旧 epoch proposal 即使 cycle ID 相同也会被拒绝并毒化该拍。Stage 4 接入线程生命周期时必须证明这条 quiesce 边界。
9. release 先进入不可复用的 `Claiming` 状态，复制完 payload/拒绝原因后才发布 `Claimed`；因此 `k+2` 不能在旧数据读取完成前覆写同一物理槽。

## 4. 当前测试

纯 C++14 测试覆盖：

- 3001 个绝对边界及双时钟映射；
- 早到、准时、迟到、多拍积压但无跳拍；
- steady clock 回退锁存、提高 epoch 后显式 reset；
- 时间戳与 cycle 溢出；
- cutoff 等号与晚 `1 ns`；
- 所有 identity/hash/generation 不匹配；
- duplicate、missing、late、双槽容量及旧 cycle 污染；
- publish/close 并发竞态的线性化结果；
- 10,000 个 cycle 的双槽反复复用与 tag 隔离。

本子阶段只证明 request 枚举与候选交接，不宣称已经满足“每拍恰好一个 emitted event”。该性质仍需后续 `ReleaseCoordinator + FinalCommandPublisher + PublishedCommandHistory` 集成测试证明。
