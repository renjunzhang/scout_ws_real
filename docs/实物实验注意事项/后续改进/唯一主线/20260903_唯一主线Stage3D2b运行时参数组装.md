## 2. 强类型参数输入

[`parameter_values.py`](../../../../src/scout_apps/control/spmpc_local_planner/scripts/acados/mainline/parameter_values.py) 将已经加载的数值拆成六个职责单一的 block：

- actuator：显式 `tau/gain`，唯一派生 `inv_tau`；
- reference：一个 horizon-static normalized cubic，以及 61 个显式 `ref_speed[k]`；
- slosh：显式 `omega_n/zeta/kappa/eta_ref/r_dot`，唯一派生 `2*zeta*omega_n` 与 `omega_n^2`；
- normalization：9 个可用作除数的严格正尺度；
- running weights：9 个有限非负权重；
- terminal weights：4 个有限非负权重。

该层只验证数值，不决定 production 参数。所有 public dataclass 都没有数值默认值；bool、int 数值别名、NaN/Inf、非法符号、派生量溢出或下溢、不可表示的 normalization 倒数都会失败。

reference 的有效域固定为：

```text
xi = (s-ref_s_origin)/ref_s_scale
xi in [0,1]
```

切向检查不是只看端点，而是求 `||d(x,y)/ds||^2` 四次多项式在完整有效域内的 stationary candidates。最小切向阈值是显式 validation policy，参与输入语义身份，但不伪装成第 163 个 solver 参数。

`ref_speed[60]` 不由 assembler 静默改写成零。停车或 terminal slowdown 必须由后续 `TerminalReferencePolicy` 在 solve 前显式形成 reference，再作为同一 typed snapshot 输入。

## 3. 固定宽度运行时延迟日程

[`runtime_schedule.py`](../../../../src/scout_apps/control/spmpc_local_planner/scripts/acados/mainline/runtime_schedule.py) 的唯一 builder 为：

```python
build_runtime_fractional_delay_schedule(
    capacity,
    delay_v_sec,
    delay_omega_sec,
    integer_snap_tolerance_sec,
    duration_tolerance_sec,
)
```

它只接受 D0 pinned typed capacity：

- `dt`、`NQ_v`、`NQ_omega` 和最大 delay 来自 capacity；
- 不再执行浮点 `ceil(L_max/dt)`，也不接受 caller 自报 selector width；
- 精确 `delay=0`、整数拍和 `delay=L_max` 都落到合法整数 tap；
- 单通道先按 `delay/dt=m+beta` 规范化，再对线/角切换时刻取精确并集；
- 最多三个 active slot，最后一个 active duration 用 `dt-前段累计值` 构造；
- active selector 必须 one-hot，未使用槽也使用合法 `Q(0)` one-hot；
- integer snap 要求 `0 <= tolerance < 0.5*dt`；
- duration tolerance 与 C++ 合同一致，要求 `0 <= tolerance < dt`。

输出保存输入 delay、规范化后的 `m/beta`、三个 duration 和两组固定宽度 selector。`to_dict()` 是唯一规范文档，`sha256` 只对该文档计算；严格 `from_dict/require` 会重建 builder 结果，不能让修改后的派生字段继续进入参数装配。

## 4. 完整 `61 x 162` 参数装配

[`runtime_parameter_assembler.py`](../../../../src/scout_apps/control/spmpc_local_planner/scripts/acados/mainline/runtime_parameter_assembler.py) 内部从 D0/D1 重建 D2a `SolverParameterLayout`，不接受调用者传入 `NP`、offset、block range、`dt`、`L_max` 或直接 coefficient vector。

对每个 `k=0..60`，装配器都重新建立 162 个空槽，并按 typed block range 一次性写入：

```text
actuator scalars + duration/selectors
+ reference cubic + ref_speed[k]
+ derived slosh values
+ normalization
+ running weights
+ terminal weights
+ liquid schedule[k]
```

任一 block 名称错序、长度不符、重复写入、空槽、非有限值都会失败。不存在“先沿用 solver 内存，再改几个 stage 字段”的路径。

`p[60]` 使用同一个 row builder，因此 execution、reference、slosh、normalization 和全部 weights 仍是完整合法值；只有 `liquid_run_coeff[60]` 与 `liquid_boundary_coeff[60]` 按 D2a terminal 合同显式为零。

最终不可变 snapshot 保存：

- D0 capacity 原始字节 hash；
- D1 layout、D2a parameter layout 的语义 hash；
- runtime delay schedule、parameter values、liquid schedule 的语义 hash；
- condition、完整 parameter order 和全部 `61 x 162` 数值。

该 horizon snapshot 的 canonical hash 可以直接进入 trial effective config、每周期 snapshot 和 bag meta。它不进入 codegen artifact manifest，因为合法 runtime delay、tau/gain、reference 或实验条件变化不应触发重新 codegen。

## 5. B0/Bslosh 公平配对

`build_matched_runtime_parameter_pair()` 要求：

- 第一个 condition 必须是 B0，第二个必须是 Bslosh；
- 两臂共用同一个 capacity/layout/runtime schedule/parameter values；
- `K_liquid`、`W_run`、`W_boundary` 完全一致；
- 逐 stage、逐 offset 比较完整参数矩阵。

差异白名单不写死 `160/161`，而是从 typed layout 中的：

```text
liquid_run_coeff
liquid_boundary_coeff
```

反查 offset。任一其他字段变化都会失败。零权重时允许两臂没有实际数值差异，但白名单仍只包含这两个字段。

这证明的是 runtime parameter 公平性。B0 下改变液体初值不影响机器人 horizon/首拍命令，仍需等统一 symbolic graph 建立后用数值不变量验证。
