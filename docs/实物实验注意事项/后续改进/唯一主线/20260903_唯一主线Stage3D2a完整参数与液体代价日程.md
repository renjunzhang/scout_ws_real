## 1. 本阶段解决的问题

Stage 3-D1 只冻结了 state、control 和 execution parameter prefix，尚不能确定 solver 每个 stage 的完整 `p[k]` 宽度，也没有把 `K_liquid` 与实验条件编译为固定宽度的液体代价系数。

本阶段拆出两个 ROS-free、CasADi-free 的纯合同模块：

1. `solver_parameter_layout.py`：从 D0 typed capacity 和 D1 typed layout 唯一展开完整参数顺序；
2. `cost_schedule.py`：把调用方已选择的 `condition/K_liquid/W_run/W_boundary` 编译为 `N+1` 组右端液体代价系数。

两者只冻结结构和数值日程，不创建 symbolic graph、acados OCP、generated header、动态库或 artifact manifest。

## 2. 完整参数布局

每个 `p[k]` 使用相同的 162 维顺序，`k=0..N` 共 61 个参数向量：

| block | 半开 offset | 数量 | 内容 |
|---|---:|---:|---|
| execution prefix | `[0,121)` | 121 | D1 的 FOPDT 标量、三槽 duration 和双通道 selector |
| reference | `[121,132)` | 11 | 归一化局部 XY 三次曲线 10 项，加独立 `ref_speed` |
| slosh | `[132,138)` | 6 | 阻尼、刚度、双向耦合、`eta_ref` 和 running `r_dot` |
| normalization | `[138,147)` | 9 | tracking、actual、issue acceleration 和 jerk 尺度 |
| running weight | `[147,156)` | 9 | tracking、progress、speed、issue acceleration 和 jerk 权重 |
| terminal weight | `[156,160)` | 4 | contour、lag、`v_actual-ref_speed`、`omega_actual` |
| stage cost | `[160,162)` | 2 | `liquid_run_coeff`、`liquid_boundary_coeff` |

因此：

```text
NP = 121 + 11 + 6 + 9 + 9 + 4 + 2 = 162
```

完整 layout identity 绑定 D0 capacity 原始字节 SHA-256 和 D1 完整语义 SHA-256。ordered names、offsets、block order、连续 block range、`N=60`、`N+1=61` 及 terminal 全字段显式赋值策略都进入严格序列化合同。

## 3. Reference 与代价语义

reference schema 固定为 `normalized_local_cubic_xy_v1`：

```text
xi = (s - ref_s_origin) / ref_s_scale
coord_ref = c0 + c1*xi + c2*xi^2 + c3*xi^3
dcoord_ref/ds = (c1 + 2*c2*xi + 3*c3*xi^2) / ref_s_scale
psi_ref = atan2(dy_ref/ds, dx_ref/ds)
```

未来 assembler 必须要求 `ref_s_scale>0`，在完整有效域 `xi∈[0,1]` 验证切向非退化；超域不得 clamp 或静默外推。`ref_speed` 是每个 stage 都显式赋值的非几何速度参考，不是第 11 个几何系数。

running 的九项顺序明确不含 `omega_actual` 幅值惩罚：角速度由 hard bound、路径 tracking 和 terminal `omega_actual→0` 管理，避免额外幅值项在弯道与必要转向竞争。若未来改变该决定，必须升级参数 schema 和 artifact identity，不能偷换现有 weight 含义。

`slosh_running_eta_dot_ratio` 是方案中 `r_dot` 的唯一参数绑定，只进入预测右端液体 running cost。boundary 使用独立固定的模态速度系数 `1`，不得复用 running `r_dot`。terminal 四项只读取 `x_N`，不访问不存在的 `u_N`，且全局液体 terminal cost 恒为零。

## 4. 固定右端液体日程

唯一构造入口要求调用方显式提供全部参数：

```python
build_liquid_cost_schedule(condition, K_liquid, W_run, W_boundary)
```

它固定执行：

```text
condition B0     -> objective_scale = 0
condition Bslosh -> objective_scale = 1

liquid_run_coeff[k]
  = 1{k<K_liquid} * objective_scale * W_run / K_liquid

liquid_boundary_coeff[k]
  = 1{k=K_liquid} * objective_scale * W_boundary
```

输出是两个不可变、长度为 `N+1=61` 的 tuple。running stage `0..K-1` 对应离散 map 的预测右端 `x_{k+1}`；boundary stage `K` 读取 shooting state `x_K`。`K+1..N` 全零，terminal index `N` 两个系数也显式为零。这里不额外乘 `dt`、不除 `N`，也不选择实验窗口或权重。

输入校验强制 `1<=K_liquid<N`、强类型 condition、有限非负权重。正权重若在除以 `K_liquid` 后下溢为零，或系数总和发生不可表示的浮点溢出，会以领域错误 fail closed，不泄漏裸数值异常。实际日程可通过 `to_dict()` 完整写入后续 horizon snapshot。

## 5. B0/Bslosh 公平性边界

完整 layout 的机器合同声明两臂必须共享：

- 同一 dynamics、constraints 和 parameter order；
- 同一 execution/reference/slosh 参数；
- 同一 normalization、robot running 和 terminal weights；
- 同一液体传播。

唯一允许变化的 stage parameter 是：

```text
liquid_run_coeff
liquid_boundary_coeff
```

B0 两组系数严格全零，但不能因此关闭液体状态或切换另一张 solver graph。该不变量目前只冻结为结构合同；“改变 B0 液体初值不改变机器人 horizon/首拍命令”的数值测试要等统一 graph 建立后执行。
