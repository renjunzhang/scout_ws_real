## 1. 本阶段解决的问题

Stage 3-D0 已把开发队列容量冻结为强类型整数合同，但 solver graph 还需要唯一、可复算的 state/control/execution parameter 顺序。继续调用历史 Stage 3a 的 `build_synthetic_layout(L_max_v_sec, L_max_omega_sec)` 会重新引入浮点 `ceil`、synthetic purpose 和旧 `PROHIBITED` 身份语义。

本阶段新建独立 `development_layout.py`。唯一构造入口是：

```python
build_development_layout(capacity: DevelopmentCapacityContract)
```

它只接受 D0 pinned loader 生成的 typed capacity，不接受 raw dict、`L_max_sec`、`dt_sec`、scenario、purpose 或调用者自报的 authority 布尔值。

## 3. 身份和权限边界

序列化 layout 绑定：

- D0 capacity 原始字节 SHA-256；
- 30 Hz 精确有理周期与 `N=60`；
- `R/D/NQ/NX/NU/NP_exec`；
- 完整 ordered names、offsets 和 selector offsets。

scope 固定为：

```text
DEVELOPMENT_STATE_CONTROL_EXECUTION_PREFIX_ONLY
```

该文档故意没有完整 `NP`、reference/slosh/cost 参数、constraints、solver options、artifact SHA、generated 状态或 production gate。D1 只证明固定宽度布局，不声称 CasADi graph 或 solver artifact 已经存在。

## 4. 单向依赖

```text

```

`development_layout.py` 不导入或调用历史 `layout.py/build_synthetic_layout()`、`manifest.py`、`contract_source.py`、`stage1_evidence.py`、ROS 或 bag。隔离子进程还验证了真实 import 后这些旧模块没有通过 package 初始化被间接加载。

旧 Stage 3a scaffold 继续作为当时的历史合同测试存在，但不再处于 development codegen 的依赖路径中。两者不会共享 purpose、manifest 或 artifact 权限。

## 5. Fail-closed 行为

typed round-trip validator 总是用调用方提供的同一 `DevelopmentCapacityContract` 重新构造期望布局，再做严格类型相等比较。以下修改均拒绝：

- raw dict 或额外 positional 参数冒充 typed capacity；
- capacity SHA、`R/D/NQ`、grid 或 horizon 漂移；
- `bool`、浮点整数等 Python 数值别名；
- `NX/NU/NP_exec` 或任一 dimension 漂移；
- state/control/parameter 顺序、名称、offset 或 selector width/offset 漂移；
- 增加未知字段、full parameter、artifact 或 production 字段。

返回对象使用 frozen dataclass、tuple 和只读 mapping；对 layout 或嵌套 selector 的修改均失败，`dataclasses.replace()` 也不能绕过唯一 builder。
