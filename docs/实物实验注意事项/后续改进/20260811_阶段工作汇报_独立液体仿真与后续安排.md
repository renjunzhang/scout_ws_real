## 一、为什么要单独做液体仿真

现有仿真里有两个晃动量：`H_proxy` 和 `H_modal`。前者在控制器外部计算，后者来自
控制器内部，但二者都使用相近的液体模型和同一小车运动输入。因此它们适合说明控制器的
机制，却不适合作为独立的液体评价。

这次引入 DualSPHysics 的目的，是在控制器之外再建立一套粒子液体计算。它不参与控制，
只读取小车已经执行完的运动，重新计算容器里的自由液面。这样可以比较不同方法产生的实际
运动对水体的影响，同时避免评价模型和控制模型完全同源。

这里仍然要注意：DualSPHysics 是数值仿真，不是真实水测量。在通过网格/时间步收敛和
实物 RGB 对照以前，它的输出只能叫 `H_sph`，不能叫 physical truth。

## 二、首版采用离线 two-pass

首版不把液体 solver 塞进 Gazebo，也不做实时 ROS bridge，而是分两遍运行：

```text
第一遍：R8 小车仿真
  -> fresh Gazebo
  -> 记录实际执行运动
  -> 生成 closed bag、manifest 和 postflight

第二遍：独立液体回放
  -> 只读提取容器实际位姿
  -> DualSPHysics 回放同一段运动
  -> Gauge 提取自由液面
  -> 输出 H_sph 和质量检查
```

第二遍不读取 `/cmd_vel` 或 MPC 计划轨迹，不向控制器反馈液位，也不修改第一遍的到点、
超时或方法失败结论。液体计算失败时，只在新的 secondary ledger 中记录，不能回写原来的
attempt。

采用这种方式，主要是为了避免高负载液体计算改变 Gazebo real-time factor 和控制周期，
也避免第三方程序进入实物/仿真控制运行图。

## 三、截至 8 月 6 日已经完成的内容

### 1. 固定 DualSPHysics 源码

已经在独立目录中获取并静态核对以下源码：

```text
repository: https://github.com/DualSPHysics/DualSPHysics

```

源码 commit、Git tree、文件清单、许可证和仓库中的预编译 ELF 都已记录 hash。获取后只做
静态检查，没有构建或执行 GenCase、solver、MeasureTool、预编译 `.so` 或仓库脚本。

### 2. 建立第三方程序的安全门禁

仓库中新增了独立的 safety、dependency、sandbox 和 QEMU gate。它们的作用不是自动
安装或执行程序，而是把每一步能做什么写死：固定目录、固定命令、固定 hash、一次性回执、
失败后保留证据，并禁止 `sudo`、系统安装、广域进程清理和越界写盘。

QEMU 安装状态已完成只读审计，当前 boot 也只运行过一次固定版本探针：

```text
/usr/bin/qemu-system-x86_64 -no-user-config -version
```

该探针 PASS 只说明 QEMU binary 可以加载。没有运行 machine、没有创建 image/VM，也没有
执行 DualSPHysics 或 GenCase。

### 3. Ubuntu 20.04 升级路线被安全阻断

为了继续 machine-none 隔离测试，原计划评估更新到 ESM HWE 5.15.0-186。宿主显卡基线
正常：RTX 3060、NVIDIA 570.133.07、CUDA interface 12.8。

但 `apt-get -s` 模拟发现，名称看似 570 的候选元包实际会删除现有 570 组件并安装 580
模块：

```text
5 upgraded, 11 newly installed, 2 removed
remove nvidia-driver-570 / libnvidia-encode-570
install NVIDIA 580 kernel modules
```

这不符合“保留现有驱动大版本、不得删除现有包”的边界，所以原升级路线已经 NO-GO。
没有下载、安装、删除、修改 GRUB 或重启。冻结 570.133 后改走 DKMS 仍需要单独验证
NVIDIA 和 RealSense 能否同时为新内核构建，目前也没有放行。

### 4. 形成 Ubuntu 24.04 独立工作站方案

考虑到原 Ubuntu 20.04 电脑还承担 ROS、Gazebo、实物设备和 NVIDIA 任务，继续在这台机器
上试第三方液体构建风险较高。因此已经准备把液体计算移到一台独立的 Ubuntu 24.04 / ROS 2
电脑。

两台电脑只交换普通文件：原电脑导出 `motion.csv` 和 JSON manifest，24.04 电脑返回
Gauge CSV、H_sph summary 和 QC。它不读取原 ROS 1 工作区，也不把二进制传回原电脑执行。

## 五、正式液体 case 还需要补充的物理信息

软件 smoke 可以先做，但要让 C1/C2 具有物理意义，还需要确认：

1. 容器内径、总内高、壁厚、底部形状以及是否开口；
2. 容器相对小车 `base_link` 的安装位置和姿态；
3. 实际水量或液深、误差和温度；
4. 内壁材料以及可用的接触角/润湿信息；
5. 实物 RGB 液面标定、采样率和可作为 reference 的实验；
6. 最终主指标采用 crest、absolute height 还是 peak-to-peak；
7. 单个液体 case 可接受的最长运行时间和 GPU 预算。

目前使用的 C1 直径 37 mm、C2 直径 95 mm、液深/高度候选 58 mm 都还是
`SIM_ONLY_UNVALIDATED`，不能写成正式物理条件。

| --- | --- |
| `R8` | 与实物源码分开的新一代仿真控制器和实验运行身份。 |

| `Gazebo` | 小车和场地的机器人仿真环境；第一遍小车运动在这里完成。 |
| `H0` | 开阔场地开发路径，只用于验证运行和液体回放流程，不属于正式 H1/L1。 |

## 七、目前可以给出的结论

独立液体仿真的路线已经明确，固定源码和安全门禁也已建立，但目前还没有产生任何
DualSPHysics 液体结果。原 Ubuntu 20.04 升级方案因会迁移 NVIDIA 580 已经停止，下一步
优先在独立 Ubuntu 24.04 电脑完成环境基线、隔离构建和 C1 静水 smoke。

在数值收敛、实际运动回放和实物 RGB 保真验证完成前，H_sph 只能作为开发评价量；R8
正式 40/64/88、实时液体 bridge、液体力反馈和 physical-primary 结论都不在当前放行范围内。
