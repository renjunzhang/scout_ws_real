## 0.1 目标最终状态

本方案最终要交付的不是一个单点 trick，而是一套**可关闭、可影子验证、可受控闭环、可离线复核**的实物延迟与相位补偿链路。完成后的系统应达到以下状态：

```text
默认状态：delay_phase 关闭，SPMPC 行为与当前版本一致。
P0 monitor：只测量延迟/时间戳/solver/command 周期，不改变控制。
P1 shadow：实时预测 execution state，但只发布诊断，不进入 solver。
P1 fixed_closed_loop：使用同日 P0 标定的固定 delay，把预测 execution state 输入 solver。
P1 adaptive_closed_loop：在安全 gate 允许时慢速在线修正 delay，默认关闭。
P2 solver-aware：只有 P1 仍无法解决相位问题时，才考虑输入延迟队列/RTI/MHE。
```

最终代码层面应形成 4 个解耦模块：

| 模块                              | 作用                                                              | 是否影响控制                            |
| --------------------------------- | ----------------------------------------------------------------- | --------------------------------------- |
| `CommandHistoryBuffer`          | 保存 post-gate`/cmd_vel` 历史，供预测器使用                     | 否                                      |
| `DelayPhaseEstimator`           | 给出`linear_delay_s` / `angular_delay_s` / confidence         | monitor/shadow 否，closed-loop 间接影响 |
| `ExecutionStatePredictor`       | 用 raw odom + cmd history 前向预测`RobotState` / `SloshState` | shadow 否，closed-loop 是               |
| `ExecutionAlignmentDiagnostics` | 发布 raw/predicted/error/mode/status，支持 bag 复核               | 否                                      |

最终实验层面，每个实物 run 的 bag 必须能回答：

```text
1. 本 run 的 delay_phase_mode 是 off / monitor / shadow / fixed_closed_loop / adaptive_closed_loop？
2. 使用的 linear_delay_s、angular_delay_s 分别是多少？来源是 fixed 还是 online？
3. raw state 与 predicted execution state 差多少？
4. predicted state 是否比 ZOH 更接近后续 odom？
5. compensation 是否降低 cmd->odom 相位滞后或 projection tail？
6. compensation 是否增加 command limiter、terminal gate、tracking safety 介入？
7. RGB offline max-LCR / tracking / 到点率 是否有正向收益或至少不恶化？
```

核心原则：**不使用未来下一帧真值，不把 acados 预测 `x1` 当实车当前状态，不用 raw solver `u0` 做执行预测；只使用当前已知 odom、当前内部 slosh state、已经发布过的 post-gate command history 和显式 delay 模型。**

## 0.2 结论先行

经过当前代码审查，**延迟/相位补偿不应该先改 acados/OCP/codegen**。最合适的方案是在 ROS wrapper 和 solver 之间新增一个模块化的“执行状态对齐层”：

```text
odom / TF / cmd history
    -> TimingDiagnostics / DelayPhaseEstimator
    -> ExecutionStatePredictor
    -> SolverInput(raw + predicted)
    -> SpmpcProblem / existing solver
    -> existing terminal gate / tracking safety / command limiter
    -> diagnostics / recorder / offline analyzer
```

近期目标不是一次性完成 P2/RTI/MHE，而是：

1. **P0：测量与审计**，不改变控制行为；
2. **P1-shadow：预测状态影子模式**，只发布诊断，不进闭环；
3. **P1-guarded：固定延迟的受控闭环补偿**，通过开关启用；
4. **P2：solver-aware 输入延迟/RTI/MHE** 仅在 P1 证据不足时再做。

当前历史实物 bag 已经说明 P0 问题真实存在：

```text
20260610 / 20260611 SPMPC 实物 bag：
  v    cmd -> odom lag ≈ 0.14 ~ 0.16 s
  omega cmd -> odom lag ≈ 0.18 ~ 0.28 s
  solver p95 ≈ 2.6 ~ 4.8 ms
```

因此主要延迟不在 acados 求解，而更像是：

```text
/cmd_vel publish -> 底盘执行 -> odom 反馈
```

## 2. 最终完成状态定义

本方案的最终完成状态不是“强行上高级算法”，而是一个可开关、可审计、可回退的执行状态对齐模块。

### 2.1 软件功能状态

完成后应支持：

```yaml
delay_phase:
  enable: true
  mode: monitor | shadow | fixed_closed_loop | adaptive_closed_loop
```

四种模式含义：

| mode                     | 控制行为                      | 用途                  |
| ------------------------ | ----------------------------- | --------------------- |
| `monitor`              | 不改变控制                    | P0 延迟测量、bag 审计 |
| `shadow`               | 不改变控制，只预测并发布误差  | P1 影子验证           |
| `fixed_closed_loop`    | 使用固定延迟预测状态进 solver | 低风险闭环补偿        |
| `adaptive_closed_loop` | 在线估计延迟并慢速更新        | 后续增强，默认关闭    |

### 2.2 工程边界状态

最终应满足：

1. P0/P1 不改 acados codegen；
2. P0/P1 不改 OCP 状态维度；
3. predictor 是独立模块，可单元测试；
4. command history 是独立模块，可单元测试；
5. diagnostics 是新增 topic，不破坏旧 topic；
6. recorder 默认记录所有新增 topic；
7. compensation 默认关闭，正式实验必须记录 mode/status；
8. 所有补偿都能通过 rosparam/launch 关闭，回到原始行为。

### 2.3 实验验收状态

完成后每个实物 run 至少能回答：

```text
1. 本 run 是否启用 delay compensation？
2. 使用固定延迟还是在线估计延迟？
3. 使用的 v/omega delay 分别是多少？
4. raw state 与 predicted execution state 差多少？
5. prediction 是否比 ZOH 更接近下一帧 odom？
6. compensation 是否降低 tracking projection tail？
7. compensation 是否增加 command clamp / safety gate 介入？
8. 对 RGB offline max-LCR 是否有正面或负面影响？
```

## P1-shadow：影子预测，不进闭环

### 目标

验证 predictor 是否比 ZOH 更接近后续 odom。

### 行为

```text
raw input 仍进入 solver
predicted state 只发布 diagnostics
```

### 插入点

在 `controlTimerCallback()` 中：

```text
1. robotStateFromLatest(raw_robot)
2. predictor.predict(raw_robot, current_slosh, command_history, delay_estimate)
3. input.robot = raw_robot       # shadow 阶段保持原行为
4. publish raw_vs_predicted diagnostics
5. problem_.solve(input, output)
```

### 验收

```text
1. shadow mode 与 off mode 控制输出一致或近似一致；
2. predicted state 对下一帧 odom 的误差 < ZOH；
3. prediction 不出现 yaw/v/omega spike；
4. diagnostics 可离线复核。
```

---

## P1-fixed-closed-loop：固定延迟闭环补偿

### 目标

用同日 P0 bag 得到的固定 delay 预测 execution state，并把 predicted state 输入 solver。

### 行为

```text
input.raw_robot = raw_robot
input.robot = predicted_robot
input.slosh = predicted_slosh
problem_.solve(input, output)
```

### 安全要求

即使 solver 使用 predicted state，安全 gate 也必须能看到 raw state：

```text
tracking safety: raw + predicted 均要诊断
terminal gate: 不允许 predicted 使终点误判提前
start-lock: raw progress 与 predicted progress 都记录
```

如果设计复杂，第一版 fixed closed-loop 只允许在非 terminal phase 使用 predicted state；terminal phase 回退 raw state。

### 验收

```text
1. mode 可一键回退 off/shadow；
2. 到点率不下降；
3. projection distance p95 不恶化；
4. command limiter 介入比例不显著增加；
5. RGB offline max-LCR 不恶化；
6. solver failure 不增加。
```

---

## P1-adaptive-closed-loop：在线估计延迟，慢速更新

### 目标

在固定 delay 方案稳定后，允许 delay 估计慢速在线更新。

### 冻结条件

以下情况不更新 delay：

```text
terminal phase
tracking unsafe
start-lock active
低速/低激励
odom stale
estimator confidence 低
```

### 参数

```yaml
online_update_enable: false
update_alpha: 0.05
confidence_threshold: 0.60
max_step_change_s: 0.01
fallback_to_fixed_delay_on_stale: true
```

默认关闭。

## P2：solver-aware 输入延迟 / RTI / MHE

### 触发条件

只有当 P1 已经证明：

```text
1. predictor 比 ZOH 准；
2. 但闭环控制仍存在相位主导问题；
3. 问题无法通过 ROS 层 execution-state alignment 解决；
```

才进入 P2。

### P2 优先顺序

```text

2. 仍不够，再考虑输入延迟队列；
3. 最后才考虑 RTI 分相 / AS-RTI / MHE。
```

P2 不作为当前 R0/R1/R2 前置条件。

## 8. 风险与约束

### 8.1 混合时间源风险

当前 solver 用固定 `dt_`，command limiter 用 wall-clock dt：

```text
spmpc_local_planner_ros.cpp:832
spmpc_local_planner_ros.cpp:585
```

predictor 必须明确：

```text
预测步长用 wall-clock/history time；
solver horizon 仍用配置 dt；
两者不要混淆。
```

### 8.2 TF pose 与 odom twist 混合风险

当前 `robotStateFromLatest()` 可用 TF 替代 x/y/yaw，但 v/omega 仍来自 odom：

```text
spmpc_local_planner_ros.cpp:890
```

因此 diagnostics 必须记录 odom age 和 TF pose 使用状态。第一版 predictor 仍以当前 `RobotState` 为 raw state，不额外改变 TF 逻辑。

### 8.3 不能用未来真值

prediction error 可离线用下一帧 odom 评估，但闭环 predictor 不能读取未来 odom。

### 8.4 不能用 Map-vref 掩盖相位问题

delay compensation 与 Map-vref 是独立模块：

```text
Map-vref 改 v_ref；
delay_phase 改 solver 初始 execution state；
```

R0/R1/R2 实验必须分别记录 `map_vref_status` 与 `delay_phase_mode`。
