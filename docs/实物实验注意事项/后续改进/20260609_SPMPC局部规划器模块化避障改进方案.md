# 20260609 SPMPC 局部规划器模块化避障改进方案

## 1. 当前结论

SPMPC 后续应该继续朝“完整一点的局部规划器”发展，而不是只定位成固定路径跟踪器。

更准确的目标口径是：

```text
reference / global path 是局部规划的 guidance，
不是必须逐点硬跟踪的固定执行轨迹。

SPMPC local planner 应在局部 horizon 内同时优化：
  1. 局部轨迹几何；
  2. 路径进度；
  3. 底盘动力学与控制平滑；
  4. slosh 模态预测与晃动代价；
  5. corridor / obstacle 约束或代价；
  6. terminal 收敛。
```

因此，避障能力值得做，并且应该做成模块化、解耦合、可开关的结构。但当前阶段不建议直接复刻 `src/mpc_planner` 的全部功能。推荐路线是：

```text
借鉴 mpc_planner 的模块生命周期与能力声明思想，
保留 SPMPC 自己的 slosh-aware continuous MPCC 主线，
先补 corridor 与静态障碍基础模块，
再逐步扩展 dynamic obstacle / homotopy / navigation plugin。
```

## 2. 当前缺口

和 `src/mpc_planner` 相比，当前 `spmpc_local_planner` 主要缺口是：

```text
1. continuous MPCC 后端不是完整 obstacle-aware OCP；
2. obstacle_enable / homotopy_enable 等参数目前主要在 primitive 后端有效；
3. continuous 后端没有真正的 costmap obstacle constraint；
4. continuous 后端没有 topology-driven multi-homotopy 求解；
5. 缺少模块级 feature capability 声明，容易出现“开关打开但后端静默忽略”；
6. ROS 集成仍是 standalone node，不是 nav_core / move_base plugin。
```

其中最需要先处理的是第 2 和第 5 点：

```text
不能让 obstacle_enable=true / homotopy_enable=true 在 continuous backend 下看起来可用，
但实际没有进入 OCP。
```

这会影响后续实验解释和论文方法口径。

## 3. 设计原则

### 3.1 不照搬 `mpc_planner` 全量框架

`mpc_planner` 具备 ellipsoid / gaussian / linearized / decomp / topology-driven MPC 等完整能力，适合作为强通用 MPC baseline 或 appendix 参考。

但 SPMPC 的核心创新是：

```text
slosh dynamics + local MPCC + planning-control integrated execution
```

所以第一阶段不追求完整 chance-constrained / topology-driven framework，而是先补齐 SPMPC 自己需要的最小局部规划能力。

### 3.2 acados 用 superset OCP，而不是运行时动态增删符号结构

acados codegen 的 OCP 结构需要提前固定。模块化不应理解成运行时任意添加/删除 CasADi symbolic term，而应理解成：

```text
1. codegen 一个包含可选模块 slot 的 superset OCP；
2. C++ 模块在运行时更新参数、权重、enable flag、障碍 slot；
3. 关闭模块时将对应 weight 置零或 slot 填 dummy；
4. 打开模块时填入真实参数。
```

这比运行时改 OCP 结构更适合 acados，也更利于实车稳定性。

### 3.3 参考路径是 guidance，不是死跟踪

后续口径建议写成：

```text
global/reference path provides a nominal guidance corridor.
The local SPMPC may deviate within the corridor to satisfy dynamics,
avoid obstacles, and reduce slosh excitation.
```

也就是说，SPMPC 可以保留 contour / lag / progress 的 MPCC 结构，但 obstacle/corridor 模块应允许局部轨迹主动调整。

### 3.4 不破坏现有实验红线

后续实现时仍需遵守当前项目红线：

```text
1. 不修改 /mpc/cost_breakdown 既有字段 layout；
2. 不改 /slosh/* /terminal/* /reference/* /profile_cap/* 话题名；
3. fixed-path fresh-sim 仍遵守一 case 一 fresh sim、30s 定位等待、关闭后 30s 等待；
4. 不把 obstacle 模块引入 slosh 主消融，除非专门设计 obstacle-aware 实验块。
```

## 4. 推荐总体架构

建议把 SPMPC 拆成下面几层。

### 4.1 ROS / 输入适配层

职责：

```text
/odom
/global_path 或 /scout/global_path_fixed
/costmap
/obstacle_array optional
/tf
/slosh observer state
```

统一转换为内部结构：

```text
PlannerInput
ReferencePath
CostmapGrid
ObstacleSet
RobotState
SloshState
```

ROS 层只做 I/O 和消息转换，不直接决定某个 obstacle term 如何进入 OCP。

### 4.2 模块层

建议新增轻量模块接口，先不要做得和 `mpc_planner::ControllerModule` 一样复杂。

概念接口：

```cpp
class SpmpcModule {
public:
    virtual void configure(...);
    virtual void update(const ModuleContext& ctx, ModuleOutput& out);
    virtual SolverFeatureFlags requiredFeatures() const;
    virtual void appendDiagnostics(...);
};
```

第一批模块建议：

```text
ReferenceTrackingModule
CorridorModule
StaticObstacleModule
SloshModule
SmoothnessModule
TerminalModule
HomotopyBiasModule   # 后续再做
```

模块的职责不是直接操作 acados capsule，而是输出 solver 参数、权重、障碍摘要和 diagnostics。

### 4.3 Solver 参数装配层

新增或扩展 `SolverInput` / `SolverParams`，承载模块输出。例如：

```text
SolverInput
  robot
  slosh
  reference
  corridor_data
  obstacle_set
  enabled_features
```

continuous acados wrapper 负责把这些模块输出写入参数向量。

### 4.4 Backend capability 声明

每个 solver backend 应显式声明支持哪些功能。

示例能力矩阵：

| backend | reference MPCC | slosh | corridor soft | corridor hard | costmap obstacle | homotopy | dynamic obstacle |
|---|---:|---:|---:|---:|---:|---:|---:|
| `primitive` | yes | yes | yes | yes | yes | simple bias | no |
| `continuous_mpcc_acados` | yes | yes | planned | planned | planned | no | no |
| `continuous_mpcc_direct_omega_legacy` | yes | partial / diagnostic | planned | no | planned | no | no |

规则：

```text
如果用户开启了某个 backend 不支持的 feature，必须 WARN 或 FATAL，不能静默忽略。
```

## 5. continuous MPCC superset OCP 建议

第一版 obstacle-aware continuous OCP 可包含以下代价结构：

$$
J = J_{track} + J_{progress} + J_{speed} + J_{control} + J_{smooth}
  + J_{slosh} + J_{corridor} + J_{obs} + J_{slack}
$$

其中当前已有：

```text
J_track
J_progress
J_speed
J_control
J_smooth
J_slosh
```

后续新增：

```text
J_corridor
J_obs
J_slack
```

### 5.1 Corridor soft cost

建议第一步做 soft corridor，不急着做 hard constraint。

定义横向误差 `e_c`，corridor 半宽 `b_c`：

$$
J_{corridor,k}
= w_{corridor}
  \left(\frac{\max(0, |e_{c,k}| - b_c)}{b_c}\right)^2
$$

优点：

```text
1. 与 MPCC contour error 天然兼容；
2. 不需要复杂 costmap；
3. 适合 global path 已避障、local planner 只需保持安全走廊的场景；
4. 对 slosh-aware 局部轨迹调整较友好。
```

后续如需 hard corridor，可增加 slack：

$$
|e_{c,k}| \le b_c + s_{c,k}
$$

$$
s_{c,k} \ge 0
$$

$$
J_{slack,c} = w_{slack,c} s_{c,k}^2
$$

### 5.2 Static obstacle soft cost

从 costmap 中提取最多 `M` 个局部障碍 primitive，建议第一版用 circle obstacle slot：

```text
obs_i = (x_i, y_i, r_i, enable_i, weight_i)
```

每个 stage / obstacle 的距离：

$$
d_{i,k}^2 = (x_k - x_i)^2 + (y_k - y_i)^2
$$

安全半径：

$$
r_{safe,i} = r_i + r_{robot} + margin
$$

soft penalty：

$$
J_{obs,k}
= \sum_i w_{obs,i}
  \left(\frac{\max(0, r_{safe,i}^2 - d_{i,k}^2)}{r_{safe,i}^2}\right)^2
$$

实现注意：

```text
1. CasADi 中可先用 fmax；若 RTI 不稳定，再换 smooth hinge / softplus 近似；
2. obstacle_enable=false 时 w_obs=0 或 enable_i=0；
3. 空 costmap 时所有 obstacle slot 填 dummy，不改变当前行为；
4. 第一版不要直接上 hard nonconvex obstacle constraint，避免初值差导致 infeasible。
```

### 5.3 Dynamic obstacle 后置

动态障碍会引入 stage-dependent 参数：

```text
x_obs[i, k]
y_obs[i, k]
r_obs[i, k]
```

参数量随 `N * M` 增长，且对预测输入质量敏感。建议在 static obstacle soft cost 稳定后再做。

### 5.4 Homotopy 后置

轻量 homotopy 可先做多 candidate：

```text
center guidance
left-biased guidance
right-biased guidance
```

每个 candidate 解一次 OCP，选择 lowest feasible cost。该功能会增加算力和调参复杂度，建议放在 corridor / static obstacle 稳定之后。

## 6. 分阶段实施计划

### Stage 0：能力声明与 unsupported feature guard

目标：

```text
消除“开关打开但 continuous backend 静默忽略”的问题。
```

建议改动：

```text
1. 为每个 solver backend 增加 FeatureFlags；
2. 初始化时检查 obstacle_enable / homotopy_enable / corridor_hard_bound_enable；
3. unsupported feature 打 WARN 或 FATAL；
4. diagnostics 发布 active / unsupported feature 状态。
```

验证：

```text
1. continuous + obstacle_enable=true 时有明确 WARN/FATAL；
2. primitive + obstacle_enable=true 保持当前行为；
3. fixed-path obstacle_enable=false 不受影响；
4. 不需要重新生成 acados solver。
```

优先级：最高，风险最低。

### Stage 1：CorridorModule soft cost

目标：

```text
让 continuous MPCC 真正支持 corridor soft penalty。
```

建议改动：

```text
1. 在 acados cost 中加入 J_corridor；
2. 参数向量加入 corridor_enable / corridor_width / w_corridor；
3. C++ wrapper 填参数；
4. diagnostics 发布 max_contour_error / max_violation / J_corridor；
5. 保持 obstacle_enable=false 时当前主线行为尽量不变。
```

验证：

```text
1. generate_spmpc_acados.py --check --model b0/slosh 通过；
2. catkin_make --pkg spmpc_local_planner 通过；
3. 单元或离线 smoke：轨迹偏离 corridor 时 J_corridor 增大；
4. fixed-path B0 fresh-sim 对比确认不引入明显退化。
```

### Stage 2：StaticObstacleModule soft obstacle cost

目标：

```text
从 costmap 提取局部静态障碍，并让 continuous OCP 产生绕避趋势。
```

建议改动：

```text
1. 新增 ObstacleExtractor：CostmapGrid -> ObstacleSet；
2. 固定 M 个 obstacle slot；
3. acados 参数向量加入 obstacle slot；
4. cost 中加入 J_obs；
5. diagnostics 发布 obstacle_count / nearest_obstacle_distance / J_obstacle；
6. obstacle_enable=false 或 obstacle_count=0 时行为等价当前。
```

验证：

```text
1. 空 costmap：输出与当前差异很小；
2. 单障碍 synthetic map：local trajectory 有绕避趋势；
3. solver_time_ms 仍满足 30 Hz；
4. ACADOS_SOLVE_FAILED 不显著增加。
```

### Stage 3：Obstacle slack / hard-ish safety

目标：

```text
在 soft obstacle cost 基础上，引入 slack 约束增强安全性。
```

建议先做 soft slack，不直接做无 slack hard nonconvex constraint。

验证重点：

```text
1. 初值差时不轻易 infeasible；
2. 近障时 slack 有诊断输出；
3. 对比只用 soft cost 的绕避效果。
```

### Stage 4：DynamicObstacleModule

目标：

```text
支持简单动态障碍预测。
```

输入可以先用常速度预测：

```text
obs_i(k) = obs_i(0) + v_i * k * dt
```

该阶段应作为附录或后续扩展，不建议混入当前 slosh 主实验。

### Stage 5：Homotopy / multi-candidate SPMPC

目标：

```text
局部多候选 guidance，选择最低可行代价。
```

可先实现：

```text
left / center / right lateral bias
```

后续再考虑类似 `mpc_planner` 的 topology-driven MPC。

## 7. 实验与论文口径建议

### 7.1 当前主实验不混入避障变量

在 obstacle 模块稳定前，主实验仍建议围绕：

```text
B0
B_smooth
B_slosh
B_ours
```

比较：

```text
success
duration
tracking error
cmd smoothness / omega_rate
model slosh proxy
RGB true slosh height
```

不要把 obstacle-aware 结果混入 slosh 因果消融，否则难以解释 `slosh` 改善来自避障轨迹改变还是液体模型代价。

### 7.2 避障作为后续实验块

当 Stage 1/2 稳定后，可单独设计：

```text
Obstacle-aware Local Planning Supplement
```

对比：

```text
SPMPC no obstacle module
SPMPC corridor only
SPMPC corridor + static obstacle
TEB / DWA / mpc_planner baseline
```

指标：

```text
collision / min distance
success
tracking deviation
slosh peak / p95
duration
solver time
```

### 7.3 和 `mpc_planner` 的关系

论文中建议这样表述：

```text
mpc_planner is a full-featured obstacle-aware and topology-driven MPC framework.
Our SPMPC focuses on slosh-aware local MPCC and introduces obstacle handling
through modular corridor/obstacle terms in the local OCP. The two systems are
not identical in scope; mpc_planner can serve as a strong external MPC baseline.
```

## 8. 当前建议的近期动作

近期不建议马上重构整个 planner。推荐最小动作：

```text
1. 先保留刚跑通的 RouteB/direct-omega 结果，不改主线算法；
2. 新增 backend feature capability / unsupported feature guard；
3. 在文档和 diagnostics 中明确 continuous backend 当前 obstacle 支持状态；
4. 等 fixed-path / real-robot 主实验链路稳定后，再进入 CorridorModule；
5. CorridorModule 稳定后，再进入 StaticObstacleModule。
```

一句话路线：

```text
先防误用，再补 corridor，再补静态障碍，最后再考虑 dynamic/homotopy。
不要一口气复刻 mpc_planner 全部功能。
```
