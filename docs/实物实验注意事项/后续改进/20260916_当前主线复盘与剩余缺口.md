## 1. 主线现在是什么

**原路线提供方向和进度坐标，显式区域提供几何自由度；上层安排全程几何、速度、液体响应和停车，下层 MPCC 按当前状态自主调整局部运动。** 跟踪误差只作诊断，主要成绩是任务完成、区域可行性、实际运动曲率、耗时和液体响应。

```text
原路线 + 有序凸区域 + 完整初态 + 目标/期限
  → 离线全任务优化 → 独立重新传播校验 → 完整计划

ROS 观测 + 真实最终命令历史
  → 同时刻状态对齐与前推
  → 持续任务时钟、连续进度投影、当前区域/停车尾段检查
  → N+1 阶段参考与约束 → 在线 MPCC → 预测核验
  → 候选首命令后的停车余量检查 / 必要时持续制动接管
  → 发布合同与安全门 → 最终命令及审计

完整预测末端 → 离线名义后缀/重优化诊断
```

最后一条仍是离线诊断，没有反馈在线目标或命令。当前两层通过完整参考、共同动力学和状态预测协同，尚无在线剩余代价、可接续终端条件或递归可行性保证。下层可改变上层几何与时序，因此上层计划的低晃动不能自动转移到闭环执行。

论文机制沿用[9月15日框架梳理](../对比试验/解决问题的思路/20260915_轨迹层与MPCC协同框架思路.md)，本轮核对实现，没有重新阅读论文全文：R32对应全任务液体优化，D19/D20对应区域内几何决策，R13/R19启发剩余运动检查；这些参考不构成当前软件继承其理论保证的证明。

四组仍为 `raw_mpcc / geometry_mpcc / planned_mpcc / planned_slosh`。主比较是原路线直接给普通 MPCC 与完整方法；planned两组共用同一个上层液体计划，只隔离下层液体项。共同 deadline约束最长允许时间，不能据此声称实际运输时间已经匹配。

## 3. 首轮确认的三类遗漏

### 3.1 停车尾段缺少全段速度边界检查：优先修复

[TaskStopManager](../../../src/scout_apps/control/spmpc_local_planner/src/core/task_stop_manager.cpp)的配置接收加速度、角加速度和jerk上限，没有接收 `actual_v_min / v_max / omega_max`。尾段核验区域、传播和quiet条件；[SpmpcProblem](../../../src/scout_apps/control/spmpc_local_planner/src/core/spmpc_problem.cpp)只额外检查尾段**第一条**命令的速度上界。在线OCP的整段运动边界检查没有覆盖停车接管尾段。

用生产 `TaskStopManager::predict()`、`makeJerkLimitedStopCommand()`和实际运动传播器复现，设上界0.8 m/s、`dt=1/30`、`a_max=0.6`、`alpha_max=1.2`、`jerk=1`、线执行器 `tau=0.112 s / gain=1.018`，角状态/队列为零，无区域约束：

| 初始实际速度 / 最新命令 / 加速度记忆 | 首命令（m/s） | 全尾段最大命令 / 实际速度（m/s） | 当前返回 |
| --- | --- | --- | --- |
| 0.79 / 0.8 / 0 | 0.798889 | 0.8（含初始命令）/ 0.810272 | `valid=true, STOP_TAIL_QUIET` |
| 0.79 / 0.76 / 0.4 | 0.772222 | 0.833333 / 0.842631 | `valid=true, STOP_TAIL_QUIET` |

第一例线FIFO全部为0.8；第二例为 `[0.7066666666667, 0.72, 0.7333333333333, 0.7466666666667, 0.76]`，末两条命令差分与0.4 m/s²加速度记忆一致，`delayed_v_cmd`分别与FIFO首条一致。第一例在第2个传播节点已超过0.8，是现有FIFO造成的不可改变前缀。第二例在jerk限制下仍需先释放正加速度记忆，后续命令也越界。问题在于尾段仍被标为通过，并非认定当前状态一定存在能满足全部约束的补救动作。上述最大值按固定制动序列完整传播所得，没有模拟ROS故障门后续接管，不能用来预言故障接管后的实车峰值。

[SpeedSafetyContract](../../../src/scout_apps/control/spmpc_local_planner/src/core/speed_safety_contract.cpp)检查solver、后处理和待发布的三个命令标量，不检查实际速度或完整FIFO预测；它不能补齐这个前瞻检查。当前24组数据没有报告该反例触发，不代表边界已被覆盖。

最小修改方向：把现有运动限制传入共享停车核验，逐节点检查actual/command/FIFO及初始状态，区分不可改变的前缀越界与候选制动不通过。复用当前配置和停车控制器，不再增加一套限速参数；不能靠截断命令破坏jerk后仍报告原预测有效。

### 3.2 普通参考的末端几何退化：影响自主几何与对照可靠性

这里有两处相关但独立的错误：

1. [continuous solver](../../../src/scout_apps/control/spmpc_local_planner/src/solvers/continuous_mpcc_solver_acados.cpp)的 `fitReferencePolynomials()` 在 `s0==route.length()` 时仍强制拟合宽度至少0.001；12个采样都被截到同一个端点，随后在绝对progress坐标上拟合三次式。导数仅剩浮点残差，参考朝向失去可靠切向。符号OCP的[参考代价](../../../src/scout_apps/control/spmpc_local_planner/scripts/acados/spmpc_acados_cost.py)同样对这些导数求 `atan2`，因此影响contour/lag方向及数值性质，范围不止诊断显示。
2. [ReferenceSpline::sample()](../../../src/scout_apps/control/spmpc_local_planner/src/reference/reference_spline.cpp)在端点的前向差分长度为零，却把 `atan2(0,0)`作为前向方向；末段朝向非零时会产生假曲率。该曲率进入保守/flatness热启动，可能带来错误角速度或限速。

路线 `(0,0)→(1,0)→(1,1)` 在 `s=2` 的临时反例输出：

```text
fitted yaw = -2.3561944901923448 rad
spline yaw =  1.5707963267948966 rad
spline kappa = -15.707963267948966 1/m
```

末段是竖直直线，端点切向应约为π/2、曲率应为0。当前两组失败CSV在 `t=10 s / projected_s=2` 也记录 `ref_yaw=-2.35619449`。已确认错误与失败共现，尚未通过隔离修复证明它是 `ACADOS_SOLVE_FAILED_4` 的唯一根因。

主影响范围是raw/geometry使用的cruise参考；planned阶段使用[adapter的归一化拟合](../../../src/scout_apps/control/spmpc_local_planner/src/planning/ocp_planning_adapter.cpp)，属于另一条几何入口。此前方法README把全部局部几何都写为归一化拟合，本轮纠正该表述。

最小修改方向：在参考模块统一有效端点切向和单侧曲率差分，处理短窗口/重复点/零导数；普通拟合也使用稳定局部坐标。须同时核对符号代价、热启动和诊断坐标，不能只修显示或把异常yaw硬置零。之后定向复跑两组失败，再判断是否还有期限终点约束的独立数值问题。

### 3.3 外部命令回放的launch与录制配置不一致：影响可复用入口

[trajectory_mpcc.launch](../../../src/scout_apps/control/spmpc_local_planner/launch/trajectory_mpcc.launch)最后用显式参数覆盖 `command_history/source` 和 `external_audit_topic`；[recorder](../../../src/scout_apps/control/spmpc_local_planner/scripts/record_trajectory_mpcc_comparison.sh)只暴露了 `PUBLISH_CMD_VEL`，manifest仍从YAML合并这两个history字段。

- 只在launch选择 `external_audit`：manifest默认仍期望published，`verify-live`保护性拒绝录制。
- 只在planner overlay选择external：launch默认published覆盖它，节点无输出且不接外部audit，无法建立完整命令历史。

纯文件 `VALIDATE_ONLY=true` + `verify-live --live-file`复现了 `command_history.source: expected 'published', live 'external_audit'`。目前可用方式是：launch显式传source/topic，recorder同时加载包含相同值的planner overlay，并设 `PUBLISH_CMD_VEL=false`；对应模拟live配置核对通过。具体操作只维护在[脚本README](../../../src/scout_apps/control/spmpc_local_planner/scripts/README.md#无运动回放)。普通published录制不受此触发影响；这里的拒绝说明核对门有效，不是静默放过错误配置。

最小修改方向：让recorder暴露与launch对应的两个参数，并把最终覆盖顺序放入现有 `recording_contract.py`。不新增回放runner或平行manifest格式。

### 4.1 新反例及解释边界

- **发布改写**：前命令0.1 m/s、加速度记忆0.6 m/s²，按30 Hz得到本拍命令0.12；发布间隔10 ms时，shared limiter改为0.106。按OCP网格重建的新加速度为0.18，变化0.42远超J1允许的0.0333 m/s²。记录改写后的历史只能保证下一拍知道它，不能使本拍旧预测继续有效。
- **IMU恢复**：合成激励后高度4.382452 mm，缺口重置为0；距最后旧帧0.26 s后返回 `NOMINAL_PROCESSED_IMU`，仍为0；未断流同模型对照为0.757909 mm。滤波器热身不表示物理液体已经沉降。
- **odom恢复**：缺口前3.194723 mm；恢复后报告0.122549 mm，同模型在缺口内零激励连续传播为0.621783 mm。ROS推进差分基准由源码确认，bank未核对传播区间与上次有效epoch的一致性。
