## 1. 核心结论

本轮 15 条 bag 不支持“二阶 ODE 模态只在初值注入，后续停止传播”这一猜想。

可确认：

```text
1. planner raw observer 在整个 trial 内持续传播 eta/eta_dot；
2. fixed_closed_loop predictor 每个控制周期从最新 raw state 复制，再向前传播 0.22s；
3. W1/W2/W5 使用的 10D acados horizon 持续传播四个模态状态；
4. generated solver 中确实包含完整二阶 ODE，当前 planner 也实际链接了该 .so；
5. W5 的低 /spmpc/slosh_height 主要出现在 raw -> 0.22s delay prediction 这一层，
   不是 raw observer 幅值同比例降低。
```

因此，原先“W5 已明确是最佳降晃权重”的强结论必须收窄为：

> W5 是当前最强的 **delay-predicted solver-input 相位/终端消振候选**；但 W2 与 W5 在 odom-driven raw 模态响应上没有可靠拉开。

当前决策：

```text
W1：可淘汰。
W2/W5：raw 层未决，暂不冻结 W5。
G3：暂不直接进入。
新实物数据：暂时不需要补跑，先用现有 bag/snapshot 完成离线审计。
```

## 3. 分析边界与统计窗口

### 3.1 “内部模型”必须分两层

#### A. Raw observer

topic：

```text
/spmpc/debug/raw_state
```

其 slosh 状态由最新 odometry 驱动：

```text
ax = (v - v_prev) / dt_odom
ay = v * omega
x_l_next = Ad(dt_odom) * x_l + Bd(dt_odom) * [ax, ay]
```

本文将 raw observer 用于描述“当前执行运动在同一 planner 内部模型上产生的响应”。

#### B. Delay-predicted solver input

topics：

```text
/spmpc/debug/predicted_state
/spmpc/debug/solver_input_state
/spmpc/slosh_height
```

在本轮 `fixed_closed_loop` 中，三者使用的 slosh 状态一致：

```text
raw state at t
  -> replay published command history over 0.22s
  -> predicted state
  -> solve_input.slosh
  -> /spmpc/slosh_height
```

因此 `/spmpc/slosh_height` 不是当前 raw observer，也不是 horizon peak，而是 solver 初值采用的 delay-predicted modal height。

`B0/Bsmooth` 的 ROS observer/predictor 仍在运行，所以可记录同模型 proxy；但它们的 OCP 是 6D 非 slosh horizon，不使用 eta 参与优化。

### 3.2 共同窗口

由于前 13 条 run 没有完整覆盖起步段，为保持 15 条的共同支持域，统一使用：

```text
progress_s in [0.23, 0.95]
```

这里的 `progress_s` 是 planner 记录口径，仅用于 development 对齐；它不替代 formal 所需的 odometry-independent `s_proj/L` extractor。

### 3.3 聚合规则

主表先在每个 bag 内统计 mean/P95/max，再对同条件三个 block 指标取均值。因此表中 max 是“三个 per-run max 的均值”，不是将三条样本池化后的单一 max。

## 7. 排序分歧的主要原因

### 7.1 Delay prediction 是首要原因

```text
omega_n = 31.246 rad/s
f_n     = 4.97 Hz
T_mode  = 0.2011 s
delay   = 0.22 s = 1.094 * T_mode
```

0.22s 几乎跨过一个完整模态周期，小量时序差就会显著改变 eta/eta_dot 合成相位。当前 predictor 还存在：

```text
duration = max(0.15, 0.22) = 0.22s；
v 和 omega 都按同一个 0.22s 窗口传播，没有分别落实线/角 delay；
当前实测 raw v 在第一步接入 now-0.22s 历史 command，存在边界加速度脉冲风险。
```

W5 的快速 future alignment：

```text
predicted(t) vs raw(t+0.22s)
state correlation  = 0.411-0.430
height correlation = 0.308-0.342
q-RMSE              = 0.433-0.446 mm-equivalent
```

相对 raw-hold 基线，eta RMSE 只改善约 `13%-17%`。因此 solver-input 低值尚不能解释为未来 raw 幅值同样低。

### 7.2 OCP 离散分辨率不足以直接冻结

```text
integrator = ERK4
dt / steps = 0.0333333333s / 1
N / Tf     = 60 / 2.0s
samples per modal period = about 6.04
```

对自由模态估算，60 步相对 exact ZOH 会产生：

```text
约 31% 额外数值衰减
约 -0.519 rad 相位差
```

raw observer、delay predictor 和 warm start 使用 exact discrete matrices，而 acados horizon 使用 33.3ms ERK4 单子步，三条内部链路的离散口径并不一致。

### 7.3 Stage/terminal cost 强调 2s 端点

```text
Python stage cost = (...) / N
acados stage scaling = dt = 0.0333333333
terminal scaling = 1，且 terminal 不除 N
```

等幅情况下，running coefficient 总和为 `0.0333`，terminal coefficient 为 `1`，结构上 terminal share 约 `96.8%`。这不是实际 objective 的固定占比，但明确说明当前代价强烈偏向 2s 端点相消。

bag 中也可见：

| 条件 | terminal `h_modal` mean（b01/b02/b03） | horizon peak mean（b01/b02/b03） |
|---|---:|---:|
| `W2` | `0.00191 / 0.00219 / 0.00184 mm` | `0.486 / 0.464 / 0.455 mm` |
| `W5` | `0.000817 / 0.000777 / 0.000694 mm` | `0.337 / 0.352 / 0.344 mm` |

求解器确实在传播 eta，并且 W5 更强地做了 2s 端点消振。问题是该端点相位是否代表需要的全程响应。

C++ 报告的 slosh cost 占比约 `W2=1.76%`、`W5=3.05%`，但没有复现 acados 的 stage `dt` scaling 和 terminal cost，不能解释为求解器真实 objective 占比。

### 7.4 其他边界

- W5 比 W2 慢约 `5.87%`，低 proxy 含整体减速贡献。
- planner raw 使用 actual odom dt、未滤波；standalone 使用固定 `0.02s` 和 `alpha=0.3` 加速度低通，两者不是同一滤波器。
- 当前 mainline 按既定选择不采用 rotation-consistent transport；这不会停止模态，但会影响 S 形反向弯的局部方向/相位解释。
- 当前 `mode_index=1` 只包含第一空间模态。第一模态的时间传播没有停止；第二、第三空间模态则本来就未建模。

## 8. Runtime 与 artifact 风险

predictor 每个 0.02s 子步都复制并重新 configure 模型，一个控制周期约 11 次，同时产生大量 INFO 日志。W5 b03：

```text
configure log count       = about 15,795
planner log               = about 8.7 MB / 110,867 lines
control interval P95      = 39.02 ms
fraction over 40 ms       = about 3.5%
published solver P95      = 13.95 ms
```

状态外置，因此 configure 不会重置 eta；但 `/spmpc/solver_time_ms` 漏掉 predictor/configure/logging 开销，后续 runtime gate 应记录 end-to-end control period。

当前 generated C/JSON 与 Python ODE、cost、维度一致，实际链接 `.so` 的非零 eta 导数测试最大误差为 `0`，所以本次不是 stale/missing propagation。风险在于 generated 目录未版本化且 CMake 不自动重生成，formal release 必须保存生成命令、revision 和哈希。
