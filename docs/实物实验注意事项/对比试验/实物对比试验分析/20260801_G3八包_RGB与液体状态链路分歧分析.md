## 1. 结论

这八包尚不支持“W5 能降低真实液面高度”：

1. 八条 planned rows 均有 bag/postflight，但只有 6 条 individually eligible；Row 06 和 Row 08 FAIL，因此只有 Block 01/02 形成严格有效配对，完整 G3 所需的 `4/4` eligible pairs 已不成立。
2. 前两个严格有效配对的 RGB 主指标平均差为 `Bsmooth-W5=-0.0566 mm`，只有 `1/2` block 为正；负值表示 W5 平均更差。
3. 描述性纳入全部四个 block 后，RGB 平均差为 `-0.0681 mm`，只有 Block 02 支持 W5，即 `1/4` block 为正。
4. 延迟补偿后的 solver-input slosh P95 在四个 block 中都认为 W5 更低，描述性平均 `Bsmooth-W5=+0.1876 mm`。
5. 延迟补偿前的 processed-IMU observer P95 在四个 block 中都认为 W5 更高，描述性平均 `Bsmooth-W5=-0.1732 mm`。严格有效的 6 条 row 中，raw observer 与 RGB 的中位零延迟相关为 `0.706`，legacy predicted state 仅为 `0.582`，raw 优势为 `0.124`。
6. Rows 01--07 的 processed-IMU observer 均无 reset；Row 08 因一次输入 gap 触发 reset，随后 740 个运动样本使用 odom fallback，source contract coverage 仅 `33.57%`。因此不能把八包整体分歧解释为“二阶 ODE 停止传播”，但 Row 08 本身不能作为正常 processed-IMU W5 样本。
7. Row 06 的控制、tracking、solver 和 IMU 均正常，postflight 仅因 RealSense source stamp 出现最大 `0.726 s` future skew 而失败；Row 08 则因 observer reset/fallback 失败。两行均只能保留为描述性或故障诊断证据。

因此，当前 release 的 G3 不能签 `PASS`，也不能据此进入正式 Stage I 40 条。

## 5. 当前输入链解释

W5 实际输入链为：

```text
/imu/data
  -> 去重力、偏置、滤波和杠臂补偿
  -> processed-IMU 二阶 observer，得到当前 eta / eta_dot
  -> fixed_closed_loop delay predictor
  -> 补偿后的 robot + slosh initial state
  -> MPC solver
```

当前冻结的 nominal delay 为线速度 `0.15 s`、角速度 `0.22 s`。延迟补偿的初衷是：用历史命令把测量时刻的机器人和液体状态传播到新命令预计生效的时刻，避免振荡系统因执行延迟而使用错误相位。

但八包数据说明，当前 delay-transformed state 不能被直接当作真实液面改善证据。它在所有 block 中给出 W5 更优排序，而独立 RGB 与 delay 前 observer 均不支持该排序。现阶段只能提出以下待验证假设，不能仅从方法效果表宣称唯一根因：

1. 线/角执行延迟或其组合方式不准确；
2. observer measurement stamp、state stamp、bag time 与 solver tick 的相位没有统一；
3. delay rollout 使用的历史命令激励与 IMU observer 使用的实测加速度激励不一致；
4. 前向传播中的阻尼、积分步长或坐标旋转使模态幅值产生过度衰减或相位抵消；
5. W5 改变了完成时间和命令频谱，P95 排序可能混合控制策略与状态传播口径。

## 7. 调试顺序

开始新的实车采集前，优先做只读离线调试：

1. 在同一时间轴叠加 RGB、raw processed-IMU observer、predicted/solver-input state，检查峰值方向、相位差和每次转向段；
2. 核对 `source_stamp / measurement_stamp / state_stamp / receive_stamp / solver tick`，单独量化传感、observer、planner 和执行延迟；
3. 从 `/cmd_vel` 与 `/odom` 分别估计线、角响应延迟，并检查 Bsmooth 与 W5 是否相同；
4. 做不发布 `/cmd_vel` 的 replay ablation：raw current state、现有 fixed-closed-loop、不同线/角 delay、shadow-only；
5. 检查 rollout 的激励是否与 IMU observer 的实测加速度定义一致，以及液体状态是否按机器人转动正确变换；
6. 另录短原始 RGB 标定包，只做 v2/v3 几何与重复性比较，不用方法结果调 HSV/标尺；
7. 若修改 delay、observer、模型、权重或 RGB 标定，建立新的 development release，重新完成最小 G2C 和完整 G3，旧八包永久保留为诊断证据。

在上述问题关闭前，不应通过增加 `w_slosh`、修改 Bsmooth 权重或选择性补录来追求 RGB 正向结果。
