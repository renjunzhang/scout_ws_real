# SPMPC 论文对比实验设计建议

## 1. 主实验：固定路径跟踪 Fixed-path Tracking

用于证明 SPMPC 的主体液体晃动抑制能力。

### 内部消融

| 方法 | 目的 |
|---|---|
| B0 | non-slosh continuous MPCC baseline |
| B_smooth | 验证控制平滑项作用 |
| B_slosh | 验证 slosh-aware 模型/代价作用 |
| B_ours | 验证 slosh-aware + smooth 的完整方法 |

注意：B0 只能称为内部 non-slosh MPCC baseline，不应直接等同于 de Groot 2025 / mpc_planner 的完整复现。

### 外部 baseline

| 方法 | 目的 |
|---|---|
| TEB | 传统优化式局部规划 baseline |
| DWA | 传统速度采样局部规划 baseline |
| mpc_local_planner / mpc_planner | 需要补齐的权威 optimization baseline；只有依赖和仿真跑通后再加入正式表格 |

## 2. 扩展实验：点到点导航 Point-to-point Navigation

用于展示真实导航入口下的可用性，不建议作为最核心结论。

建议方法：

```text
B0
B_ours
TEB
DWA
```

若 DWA 或 mpc_local_planner 仍不稳定，应标注为诊断性结果，不要强行作为正式公平对比。

## 3. 当前补强优先级

```text
1. 先把 TEB + DWA + SPMPC 内部消融做扎实，保证参数、路径、终点策略和统计窗口公平。
2. 同时补一个 mpc_planner / mpc_local_planner，作为权威 optimization baseline。
3. mpc_planner / mpc_local_planner 跑通前，不把 B0 冒充为 de Groot 2025 / mpc_planner 完整复现。
```

公平性要求：

```text
- B0 / B_smooth / B_slosh / B_ours 使用同一套 terminal policy。
- TEB / DWA 使用相同场景、路径/目标、速度限制和评价指标。
- 主体抑晃指标优先统计 terminal 前的 pre_terminal_phase。
```

## 4. TEB / DWA 公平性处理

TEB / DWA 要作为强 baseline，需要认真调到稳定、平滑、可复现，但不应加入液体晃动模型或 slosh-aware cost。

### 应该做

```text
- 使用同一起点、目标、地图、路径/目标输入和记录时长。
- 使用统一或可解释的速度、角速度、加速度限制。
- 调参到能稳定跟踪/到达，避免明显震荡、暴冲、NO_VALID_CMD 或 transformed plan 为空。
- 使用相同评价指标和统计窗口。
- terminal 前主体段统一统计；若 TEB/DWA 没有 /spmpc/terminal/debug，可用相同终点距离阈值切分 terminal 区。
```

### 不应该做

```text
- 不给 TEB / DWA 加 slosh dynamics。
- 不给 TEB / DWA 加液体高度代价、eta/eta_dot 代价或 slosh-aware optimization。
- 不把魔改后的 slosh-aware TEB/DWA 当作标准 TEB/DWA baseline。
```

### 可以做的“液体友好”普通调参

```text
- 降低最大速度和最大角速度。
- 限制线加速度和角加速度。
- 提高轨迹/速度平滑性。
- 减少急转、急停和终点震荡。
```

论文表述建议：

```text
TEB and DWA are tuned conservatively for stable and smooth liquid-transport navigation, but they do not use the proposed slosh dynamics or slosh-aware cost.
```

## 5. 正式实验公平性 checklist

正式实验前必须先确认下面这些条件，避免 baseline 不公平或按结果调参。

### 5.1 TEB / DWA baseline 调参原则

TEB / DWA 不能直接拿默认参数就说它们差。正式实验前应按固定流程处理：

```text
1. 先调到能稳定完成 fixed-path / P2P 任务。
2. 再在统一或可比的速度、角速度、线加速度、角加速度限制下调平滑性。
3. 不允许为某一个 run 单独调参。
4. 所有正式 run 使用冻结后的固定参数。
5. 所有失败 run 必须记录并进入统计，不能删失败样本。
```

论文表述建议：

```text
TEB and DWA were first tuned to reliably complete the task under comparable physical constraints. Their smoothness-related parameters were then tuned conservatively. All baseline parameters were frozen before formal evaluation and were not adjusted per run.
```

### 5.2 正式 run 前检查项

| 项目 | 要求 |
|---|---|
| 同一起点 | 是。fixed-path 主实验尽量使用同一 spawn pose；允许厘米级/小分米级定位误差，不允许米级偏差 |
| 同一目标 | 是。fixed-path 使用同一路径终点；P2P 使用同一目标点 |
| 同一地图 | 是 |
| 同一 fixed path / global path | fixed-path 使用同一条 `/scout/global_path_fixed`；P2P 使用同一 goal / global path 输入 |
| 同一 `v_max / omega_max` | 是，至少物理上限一致或可比 |
| 同一 acc limits | 是，线加速度和角加速度限制一致或可解释 |
| 同一 footprint | 是 |
| 同一 goal tolerance | 尽量一致；最终成功判定使用统一几何阈值 |
| 同一 controller frequency | 尽量一致；若 planner 内部频率不同，必须记录实际频率 |
| 同一统计窗口 | 是，主指标统计 `pre_terminal`，terminal 停车段单独统计 |
| 同一 RGB 后处理脚本 | 是，实物实验中所有方法使用同一 RGB 后处理脚本和同一阈值 |
| 所有失败 run 是否记录 | 必须记录，不能只保留成功样本 |
| TEB/DWA 是否未加入 slosh model | 必须确认没有 slosh dynamics / slosh-aware cost / eta 或 eta_dot 代价 |
| SPMPC warm-start 是否只用在线信息 | 必须确认不使用未来真值、离线 oracle 或某次 run 的回放结果 |

### 5.3 SPMPC warm-start 公平性

SPMPC warm-start 可以使用在线可获得的信息：

```text
- 当前机器人状态
- 当前 reference path / fixed path
- 车辆运动学和约束
- SPMPC 自身使用的 slosh state
```

不能使用：

```text
- 未来真实轨迹
- 人工挑出来的最优控制序列
- 某一次 run 的结果回放
- TEB / DWA / mpc_local_planner 的结果
- 离线 oracle
```

论文表述建议：

```text
The SPMPC warm-start uses only online available information, including the current robot state, the given reference path, vehicle constraints, and the internal slosh state used by SPMPC. It does not use future ground-truth trajectories, run-specific offline optimization results, or the outputs of other planners.
```

## 6. TEB / DWA 的 slosh 数值监控口径

可以在 TEB / DWA / mpc_local_planner 实验中运行 `src/scout_apps/control/slosh_models` 里的 slosh 数值监控，用来辅助统计液面高度和液体状态。

但口径必须写清楚：

```text
slosh model / slosh monitor 只作为评价模块运行；
TEB / DWA / mpc_local_planner 不能读取该状态；
该状态不能进入它们的控制输入、代价函数或调参逻辑。
```

也就是说：

```text
允许：用同一个 slosh monitor 对所有方法记录 slosh height / eta / eta_dot。
不允许：让 TEB / DWA 根据 slosh height 改速度、改轨迹或改 cost。
```

这样做是公平的，因为液体状态只是离线评价信号，不是外部 baseline 的控制信息。正式 bag 中建议对所有方法统一记录：

```text
/slosh/height
/slosh/state
/slosh/debug
```

如果仿真侧已经由 SPMPC 发布 `/spmpc/slosh_height` 和 `/spmpc/debug/slosh_state`，外部 baseline 仍建议额外跑独立 monitor，并在指标脚本中统一映射 topic alias，避免只有 SPMPC 有 slosh 指标、TEB/DWA 是 NaN。

当前 standalone monitor 接口固定为：

```text
输入：/odom，/cmd_vel 仅 debug
输出：/slosh/height，单位 m
输出：/slosh/state，[x_m, vx_mps, y_m, vy_mps]
输出：/slosh/debug，记录 dt、速度、加速度估计、height、计数器
reset：/slosh/reset
```

注意：`/slosh/height` 使用 SI 单位 m，指标脚本会统一换算成 mm；`/spmpc/slosh_height` 是 SPMPC 内部 debug，单位 mm。

fixed-path suite 中显式设置：

```bash
SLOSH_MONITOR_ENABLE=true
```

## 7. 指标建议

主体 tracking 指标只统计 terminal 前：

```text
pre_terminal_phase = 1
```

建议报告：

```text
tracking error
slosh height peak
eta_dot peak
control smoothness
solver time
failure count
```

terminal 停车段单独报告：

```text
stop distance
cmd_v jump / deceleration
terminal slosh peak
whether final stop is stable
```

## 8. 推荐论文结构

建议按下面口径组织实验，不把所有方法混在一张表里：

```text
Experiment 1: fixed-path 内部消融
  B0 / B_smooth / B_slosh / B_ours

Experiment 2: fixed-path 外部 baseline 对比
  B_ours / TEB / DWA / mpc_local_planner

Experiment 3: point-to-point navigation 补充实验
  B0 / B_ours / TEB / DWA

Experiment 4: 附加模型/求解器分析
  primitive linear / anti / continuous MPCC
```

结论：fixed-path 内部消融证明方法组成；fixed-path 外部 baseline 证明相对普通局部规划器/优化式规划器的优势；P2P 只作为导航可用性补充；primitive / anti / continuous MPCC 只做附加分析，不抢主线。

所有 SPMPC variants 使用同一套 terminal policy，正式抑晃指标优先看 terminal 前的主体路径段。

## 9. 仿真实施落地计划

当前按下面顺序推进，先全部在仿真中跑通，bag/log/统计结果放 `/data/a`：

```text
1. SPMPC 内部消融 fixed-path tracking：B0 / B_smooth / B_slosh / B_ours。
2. TEB / DWA fixed-path baseline：使用同一个 /scout/global_path_fixed，不允许 goal-only straight-line fallback。
3. 统一指标脚本：主指标统计 pre_terminal，terminal 停车段单独统计。
4. 尝试 mpc_local_planner / mpc_planner 作为权威 optimization baseline；不稳定时只作为 diagnostic。
5. 最后做 point-to-point navigation 补充实验。
```

### 9.1 fixed-path 仿真启动原则

不要在同一个 Gazebo session 里连续用 `/gazebo/set_model_state` reset 后跑多个方法。这样容易残留定位、odom、TF、costmap 或 planner 内部状态，导致后续方法看起来“没完成”。

正式或半正式对比建议采用：

```text
一个方法 / 一组方法跑完 -> 关仿真 -> 重新 fresh 启动仿真 -> 再跑下一个方法。
```

仿真启动后先等约 30s，让定位/TF/costmap 稳定，再发布 `/scout/global_path_fixed`。脚本中用：

```bash
PRE_PATH_WAIT_SEC=30
```

### 9.2 启动 fixed-path 对齐仿真

终端 1：启动仿真。这里用当前 `P2_s_curve` 路径起点附近的 spawn pose。

```bash
source /opt/ros/noetic/setup.bash
source /home/a/scout_ws/devel/setup.bash
cd /home/a/scout_ws

SIM_ENV=open \
USE_RVIZ=false \
SPAWN_X=3.4484412831971465 \
SPAWN_Y=0.2053595972008268 \
SPAWN_Z=0.1 \
SPAWN_YAW=-3.0815575130115853 \
rosrun scout_local_planner launch_sim_nav_stack.sh
```

终端 2：确认仿真 ready。

```bash
source /opt/ros/noetic/setup.bash
source /home/a/scout_ws/devel/setup.bash

rostopic echo -n 1 /odom
rostopic echo -n 1 /map
```

### 9.3 SPMPC 内部消融 fixed-path 命令

每次跑前先 fresh 启动仿真。输出统一放 `/data/a`。

```bash
source /opt/ros/noetic/setup.bash
source /home/a/scout_ws/devel/setup.bash
cd /home/a/scout_ws

OUT_ROOT=/data/a/spmpc_paper_compare/fixed_path_manual_$(date +%Y%m%d_%H%M%S)
PATH_FILE=/data/a/fixed_paths/sim/P2_s_curve.json
PATH_ID=P2_s_curve

SLOSH_MONITOR_ENABLE=true \
OUT_ROOT=${OUT_ROOT} \
PATH_FILE=${PATH_FILE} \
PATH_ID=${PATH_ID} \
VARIANTS="B0 B_smooth B_slosh B_ours" \
RUNS=1 \
RECORD_SEC=60 \
PRE_PATH_WAIT_SEC=30 \
SPMPC_SOLVER_BACKEND=continuous_mpcc_acados \
SPMPC_W_SLOSH=-1.0 \
bash src/scout_apps/control/spmpc_experiments/scripts/run_fixed_path_spmpc_suite.sh
```

如果只想单独验证 `B_ours` 已知可到终点的权重，先单跑：

```bash
SLOSH_MONITOR_ENABLE=true \
OUT_ROOT=${OUT_ROOT} \
PATH_FILE=${PATH_FILE} \
PATH_ID=${PATH_ID} \
VARIANTS="B_ours" \
RUNS=1 \
RECORD_SEC=70 \
PRE_PATH_WAIT_SEC=30 \
SPMPC_SOLVER_BACKEND=continuous_mpcc_acados \
SPMPC_W_SLOSH=2.0 \
bash src/scout_apps/control/spmpc_experiments/scripts/run_fixed_path_spmpc_suite.sh
```

注意：如果把 `VARIANTS="B0 B_smooth B_slosh B_ours"` 连续跑在同一个仿真里，仍可能受 reset/状态残留影响。更稳做法是一个 variant 跑完后关仿真，重新启动仿真，再跑下一个 variant。
