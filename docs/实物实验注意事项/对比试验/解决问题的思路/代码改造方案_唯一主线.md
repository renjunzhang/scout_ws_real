## 0. 结论

这次不在现有代码上继续增加 variant、delay mode 和 solver 分支，而是在新分支中做一次**有验收门的破坏性重构**，最终线上只保留：

```text
一个 processed-IMU I0 输入合同
+ 一个共同状态时刻合同
+ 一个显式执行器模型
+ 一个 actuator-aware acados solver artifact
+ 一个规划编排器与一个独立发布编排器
+ 一个最终 /cmd_vel 发布入口
```

新主线中的 `B0` 和 `Bslosh` 不再对应两套动力学或两套 solver：

```text
B0：     同一完整模型，liquid objective scale = 0
Bslosh： 同一完整模型，liquid objective scale = 1
```

两者都传播液体状态、都使用 processed-IMU I0、都要求 `fail_closed`、都使用相同的执行器参数、warm start、约束、时间轴和命令发布链。唯一预注册差异是液体运行代价与液体边界能量是否生效。

这意味着新分支中的 `B0` 是“统一模型上的零液体代价基线”，不是历史 6D literal B0。新实验必须使用新的 protocol/release ID，不能与旧 B0、`matched0/5` 或 legacy bag 混合续跑。

历史行为由 Git 提交、旧分支、bag 和文档保存，不再靠新主线中的兼容开关保存。最终生产代码中不保留：

```text
fixed_closed_loop
fixed_robot_only
instantaneous actuator backend
direct-omega legacy backend
primitive online fallback
6D/10D solver 运行时切换
B_accel/B_smooth/B_ours/... 多变体分叉
measured_v + a0*dt 命令出口
```

## 1. 唯一目标、工程目标与非目标

### 1.1 唯一效果目标

在速度、到点时间、跟踪、安全介入和数据质量可比的条件下：

```text
Bslosh 的实物 RGB P95/RMS 低于 B0
```

solver 内部液体高度、boundary energy 和 predicted state 只用于解释机制，不能替代 RGB 外部真值宣布成功。

### 1.2 工程目标

1. 让 MPC 中“新命令何时能影响实车”的控制权与真实底盘一致。
2. 区分命令状态与实际状态，位姿和液体统一使用预测实际运动。
3. 用命令加速度状态与 jerk 控制保证完整 horizon 和跨重规划周期的命令平滑。
4. 将液体运行代价限制在有证据支持的可信窗口，并在窗口边界加入独立残余能量。
5. 让 B0/Bslosh 共享同一个二进制、状态维度、参数布局和执行链。
6. 把 ROS、时间对齐、命令历史、执行器动力学、OCP、命令提取、安全仲裁和诊断拆成单一职责模块。
7. 所有配置 fail-fast、可追踪、不可在 trial 运动中静默改变。

### 1.3 本次非目标

- 不回退或复刻 0705 代码。
- 不继续调 legacy `0.15/0.22 s fixed_closed_loop`。
- 不把角速度约 `1.5～1.6 s` 的 90% 建立时间当成纯延迟。
- 第一版不同时加入死区、迟滞、左右不对称等全部非线性；先完成分通道 FOPDT。
- 不用输出 limiter 代替 OCP 内的平滑和物理约束。
- 原方案编写阶段不创建 `spmpc-mainline`、不修改源码；实际实施必须按 Stage 0 合同开始。

## 2. 证据边界与第一版候选

| 项目 | 当前证据 | 本方案如何使用 |
|---|---|---|
| 液体初值 | processed-IMU I0 相对 O0 更好；额外约 28 ms 前推反而平均退化 | I0 是唯一测量权威；只允许新联合模型的已知前缀传播，不叠加独立 I1/L22 |
| 线速度响应 | 约 80 ms 后开始响应，约 0.26～0.29 s 到 90% | 分离 `L_v/tau_v/K_v`，不把 0.29 s 全写成延迟 |
| 角速度响应 | 纯等待约 40～80 ms，约 1.52～1.63 s 到 90% | 与线通道独立建模，车体 horizon 保持 2 s |
| 液体预测可信度 | 0～100 ms 中等；100～167 ms 衰减；167～333 ms 较弱；333 ms 后当前不可信 | `267 ms` 为 development 首候选，`333 ms` 只作上界检查 |
| short100 实车 | legacy 组合中 Bslosh 明显差于 B0，并出现命令加速度饱和和正负翻转 | 不继续只调 `w_slosh`，先修正执行器控制权和命令平滑 |

因此第一版候选是：

```text
车体/执行器/液体传播 horizon = 2.0 s
液体运行代价首候选          = 267 ms
液体边界候选                = x_{K_liquid}，K_liquid=8
333 ms                      = K_liquid=10 边界检查
100/167 ms                  = 离线诊断对照
```

`267 ms` 不是已经验证的最优或正式真值。显式执行器模型完成后，必须用互斥的 development/validation/final-test bag 重新选择窗口并验证“真实 emitted command 驱动的”执行器与液体预测 fidelity；未实际执行的 solver candidate 不能直接拿未来 RGB 做离线真值比较。

## 4. 唯一在线数据流

```text
绝对 30 Hz ReleaseScheduler（steady clock）
          |
          +-- CycleRequest{k, T_k^steady, T_k^model, config/model/reset epoch}
          |
          +----------- PlanPhase(k)，必须在 T_k^steady 前完成 -------------+
          |                                                               |
          |  processed-IMU I0 + odom/TF + 已提交 emitted history           |
          |          -> CommonEpochInputBuilder                            |
          |          -> KnownPrefixPropagator（只传播物理/queue/publisher） |
          |          -> ReferenceProgressProjector（重建 s(T_k)）          |
          |          -> TerminalReferencePolicy                            |
          |          -> MainlineAcadosSolver                               |
          |          -> CommandExtractionPolicy                            |
          |          -> immutable PendingRelease{k,T_k^steady/model,...}   |
          |          -> 单槽/双缓冲 ProposalMailbox                        |
          |                                                               |
          +---------------- ReleasePhase(k)，独立固定周期线程 --------------+
                                      |
                      T_k^steady 原子读取同 ID proposal
                                      |

                                      |

                                      |

                                      |
```

线上不得存在第二条 observer、第二条延迟补偿、第二个 solver fallback 或第二个命令发布入口。

## 5. 时间合同

### 5.1 固定发布调度器

新主线使用由 monotonic/steady clock 驱动的绝对 30 Hz 发布网格，并把每个边界映射到传感器所在的 model/ROS 时间域：

```text
T_k^steady = 第 k 个线程唤醒/发布 deadline
T_k^model  = 与 t0 同时间域的模型边界；下文无上标 T_k 默认指它

nominal dt = 1/30 s
```

`1/30 s` 不能用整数纳秒逐拍累加而不产生漂移。domain 中保存有理周期 `period_num/period_den=1/30`，第 k 拍始终由锚点直接计算：

```text
T_k_ns = T_0_ns + round_nearest(k * 1e9 / 30)
```

因此相邻整数时间戳允许相差 `33,333,333/33,333,334 ns`，但绝不做 `T_{k+1}=T_k+33,333,333 ns` 的累计近似。OCP 数学 `dt` 固定为 `1.0/30.0`；时间戳量化误差单列测试，不进入 delay tap 的拍索引。

`ReleaseScheduler` 逐个枚举全部 `T_k`，绝不选择性跳到“下一个仍有完整预算的边界”。在 production live 且 publish 已启用后，每个 `T_k` 必须恰好对应一个最终 emitted event；计算不足时的合法行为是在该边界发布并记录安全零，然后锁存故障，而不是跳拍、临时改期或继续沿用旧远期解。offline replay/dry-run 只能产生明确标记的 audit event，不计作 emitted event。

一次周期明确拆成两个并发隔离的阶段：

```text
PlanPhase(k):
  在 proposal_cutoff^steady=T_k^steady-handoff_margin 之前，
  由 solver worker 基于最后一次已提交 release 状态求解
  产出 immutable PendingRelease{k,T_k^steady,T_k^model,config_hash,model_hash,
                               reset_epoch,path_hash,history_generation,
                               q_issue,a_issue,solver_result,warm_start_candidate}
  原子提交到按 cycle_id 标识的单槽/双缓冲 mailbox

ReleasePhase(k):
  独立固定周期 release 线程在 T_k^steady 读取已截止的该 cycle mailbox
  只读取完全匹配 k/T_k^steady/T_k^model/hash/epoch/generation 的 ready proposal
  做 deadline 与 hard-safety 最终裁决
  发布 proposal 或安全零，并提交唯一权威 emitted event
```

release 线程不得调用 solver、等待 solver mutex、做 TF 查询或执行大块诊断序列化。`ready_time^steady > proposal_cutoff^steady`、ID 错误、proposal 未 ready，或在 cycle 已关闭后才写入的结果一律丢弃；它们不得污染下一周期 mailbox。`handoff_margin` 必须在目标实车计算机上预冻结并进入 effective hash。

```text
T_{k-1}: 发布上一条已提交命令 q_{k-1}
          |
          +-- PlanPhase(k)：获取 I0/odom/history，求解 q_k
          |
T_k:     ReleasePhase(k)
         同 ID proposal 已完成 -> 最终裁决并发布 q_k
         未完成/不匹配/迟到     -> 发布安全零并锁存故障
```

因此 `t_pub_plan=T_k^model` 不是求解结束后的 `now()`，对应的真实 release deadline 是求解开始前冻结的 `T_k^steady`。这明确引入一个可建模的计算/发布前缀，不再假定“算完立即发布”。

proposal 完成不等于命令已经发生。`PublishedCommandHistory`、`AuthoritativePublisherState`、delay queue generation、`s_commit` 和下一周期 warm start 只能在 ReleasePhase 实际发布之后提交：

- nominal proposal 原样发布时，提交其 `q_issue/a_issue`、`s(T_k)` 和附带的 warm-start candidate；
- hard safety、deadline miss 或 solver failure 发布零时，提交实际零命令、把 publisher acceleration state 重置为零并丢弃 candidate；
- 迟到 proposal 不得更新 solver 的跨周期 warm start；下一周期从实际 emitted 历史重新 rollout；
- fault 锁存后仍在每个后续 `T_k` 真实发布并记录零，直到显式结束 trial/reset epoch，不允许停止产生网格事件。

### 5.2 双时钟映射与权威时刻

```text
C_steady0/C_model0     = trial 启动时有界夹取并冻结的时钟锚点
t0                     = selector 接纳的 processed-IMU I0 model/ROS stamp
t_pub_plan             = T_k^model
t_pub_plan^steady      = T_k^steady
t_pub_actual^steady    = 紧邻 cmd_pub.publish() 的 monotonic 时间
t_pub_actual^model     = 同一边界采样的 model/ROS 时间，仅作审计
```

两个系统时钟通常不能真正原子读取。锚点和后续 drift 审计统一使用 bracket sample：

```text
s_before = steady_now()
m_sample = model_now()
s_after  = steady_now()

要求 s_after-s_before <= epsilon_clock_sample
C_steady = midpoint(s_before,s_after)
C_model  = m_sample
```

映射合同固定为：

```text
T_k^model = C_model0 + (T_k^steady - C_steady0)
```

steady clock 只负责唤醒、handoff 和发布 deadline，不与 `t0` 直接相减；model clock 只负责 common epoch、prefix、delay queue 和 OCP。运行中持续审计两时钟相对偏移，clock regression、ROS epoch 切换或映射漂移超过 `epsilon_clock_map` 时立即发布零并升级 `reset_epoch`，不能在原 epoch 内重新锚定后继续 trial。

- `t0` 不是 `ros::Time::now()`，下游不得再次减传感器或滤波延迟。
- `robot(t0)` 由 odom/TF 历史重建，`liquid(t0)` 直接取 I0。
- B0 也必须等待同一 I0 并使用同一个 `t0`，不能使用 latest robot state。
- 发布调用不得早于 steady 计划边界，并强制 `0 <= t_pub_actual^steady-t_pub_plan^steady <= epsilon_pub`；超限时本拍改发安全零、记录真实偏差并锁存，不能继续假装 proposal 按计划时刻生效。
- `t_pub_actual^steady/model` 只证明 planner 的本地 publish 调用边界；没有底盘 ACK/echo 时不得表述为“底盘已收到时刻”。

模型时间与物理审计时间必须分开：

```text
delay queue / KnownPrefix / OCP 的权威 event stamp = T_k^model
t_pub_actual^steady - T_k^steady                  = 本地发布抖动审计
```

history 同时保存 model/steady 的计划与实际时刻，但等间隔 tap 只按 `T_k^model` 构造。所谓“精确 ZOH 分段”只表示相对这个固定模型网格和冻结 delay 精确；真实 publish jitter 是受 `epsilon_pub` 约束的未建模误差。新 `delay_sec` 应在专用辨识中相对 `T_k^model` 拟合为端到端有效延迟；同时另报相对 `t_pub_actual^model` 的物理 onset 指标，不能把两种时间原点混成一个数。

### 5.3 历史覆盖与未来保持

历史合同分成两部分，不能把未来 ZOH 保持写成“已有历史”：

```text
1. 存在一条 event，其 model stamp <= t0 - L_max
2. 在 t_snapshot^steady 原子取得 immutable history generation，
   且 t_hist_cut^model <= map(t_snapshot^steady)
3. (t_hist_cut^model, T_k^model) 没有第二发布入口，显式保持最后 emitted command
```

历史必须：

- 包含查询左边界之前的前驱事件；
- 检查相邻事件最大 gap，而不只是总 span；
- 保存最终 emitted `q`、权威 `a_cmd/alpha_cmd`、cycle ID、`T_k^steady/model`、`t_pub_actual^steady/model`、发布原因和 reset epoch；
- 对重复/倒退时间戳、ROS clock epoch 变化和 publisher 污染 fail closed。

历史不足时，节点持续真实发布并记录零命令完成 warm-up；覆盖完整后才允许运动。不得在内存中补一段从未发布过的假零历史。

live 与 offline replay 的权威历史来源必须互斥：

```text
production live:
  LiveEmittedCommandSource = FinalCommandPublisher 实际调用后提交的事件

offline replay/test target:
  ReplayCommandEventSource = bag 中已记录的真实最终命令事件
```

`ReplayCommandEventSource` 只存在于 replay/test target，不链接进 production node；它必须保留 bag 原始 event stamp/value/reason，不能读取本次 solver proposal 伪造历史。`publish_cmd_vel=false` 的 production dry-run 只能审计 “would publish” proposal，不能向 live history 提交事件，也不能基于这些虚拟事件连续宣称闭环 fidelity。实车静止/正式启动阶段必须由唯一 publisher 真实逐拍发布零来完成 history warm-up。

### 5.4 固定联合前缀传播

`t0` 通常不在发布网格上。为避免“非均匀 prefix + 固定 dt OCP”的矛盾，非均匀部分不进入 acados horizon：

```text
robot/liquid @ t0
  + emitted command events
  + 分通道 ZOH delay/FOPDT
  --KnownPrefixPropagator-->
pose/actual/liquid/delay queue/publisher state @ T_k^-
```

这个传播：

- 只使用已经 emitted 或已由单一发布调度器冻结为 hold 的命令；
- 不包含当前优化变量，不泄漏未来信息；
- 使用与 OCP 完全相同的 ZOH delay、FOPDT、位姿和液体积分核；
- 同时传播 pose、actual、liquid、delay queue 和 publisher state，不是 legacy L22，也不把命令直接当 actual；
- 不传播虚拟进度 `s`；历史中没有已 emitted 的 `v_s`，不得把上周期未来计划伪装成物理历史；
- 结束后 OCP 从 `T_k^-` 开始，后续全部使用均匀 `dt=1/30 s`。

这一步本质上仍是模型传播，必须在 validation 选型后再由未参与选择的 final-test 数据单独证明。此前约 28 ms I1 前推退化是明确风险；若新联合前缀传播不能通过 fidelity 门，主线在这里停止，不能带着错误初值上车。

### 5.5 `s(T_k)` 的唯一重建合同

`s` 由 OCP 优化变量 `v_s` 驱动，不是传感器状态或已发布的物理命令。`KnownPrefixPropagator` 得到 `pose(T_k^-)` 后，`ReferenceProgressProjector` 才在本次 solve 冻结的同一条路径上组装 OCP 的 `s(T_k)`：

```text
I_k = [s_commit,
       min(s_path_end,
           s_commit + v_progress_bound*(T_k-T_commit) + delta_s_guard)]

s(T_k) = local_project(pose(T_k^-), path_id/path_hash, I_k)
```

其中 `s_commit/T_commit` 只来自上一周期成功的 nominal release。首周期只能在预冻结的起点区间内初始化。投影必须同时满足：

- `s(T_k) >= s_commit`，不允许虚拟进度倒退；
- 前进量、横向距离和航向差不超过预冻结 guard；
- 候选在 ambiguity tolerance 下唯一，禁止在交叉路径间跳支；
- path hash、reset epoch 或任一 guard 不匹配时 fail closed，禁止静默全局重投影或 clamp 到远处路径段。

所有搜索窗、guard 和容差进入 effective config/hash。换路径必须升级 `reset_epoch` 并重新完成零历史 warm-up。

`x0.s` 必须使用本次投影值，不能使用 shifted warm-start 的旧 `s`。warm start 只能移位上一轮已经 nominal release 的控制序列；stage-0 全状态由本次 common state 覆盖，并从该 `x0` 用统一离散模型重新 rollout。投影失败、path/reset 变化、上一轮未 nominal release或 proposal 最终未释放时，不接受旧 warm start。

### 5.6 pre-issue 离散状态语义

OCP stage `x[k]` 定义为发布边界 `T_{k+i}^-`、新命令入队之前的状态：

```text
x[k] 包含：
  actual/liquid/pose @ T_{k+i}^-
  上一条 emitted q_{i-1} 与 a_{i-1}
  新命令入队前的历史 delay taps

u[k] = [j_v,i, j_omega,i, v_s,i]
```

同一 stage 内固定顺序：

```text
1. issue map: 由上一 publisher state 和 j[k] 计算 a_i、q_i
2. q_i 在边界 T_{k+i} emitted，并进入 delay line
3. 对 [T_{k+i}, T_{k+i+1}) 做精确 ZOH delay + actual/liquid 离散传播
4. shift delay history，得到下一 pre-issue state x[k+1]
```

本周期命令不是 `x[0]`、不是 `x[1]`，而是明确的代数输出：

```text
(q_issue, a_issue) = issue_map(x[0], u[0])
```

`CommandExtractionPolicy` 只发布 `q_issue`。这消除了 stage-0/stage-1 的一拍歧义，也彻底删除 `measured+u0*dt` 语义。

## 6. 唯一 OCP 模型

### 6.1 状态与控制

采用一个始终包含液体状态的离散模型。定义：

```text
D_c = max(0, ceil(L_max,c / dt) - 1)

x_robot_progress = [px, py, theta, s, v_actual, omega_actual]
x_publisher    = [q_prev_v, q_prev_omega, a_prev, alpha_prev]
x_delay_older  = [older_v[0:D_v-1], older_omega[0:D_omega-1]]
x_liquid       = [eta_x, eta_x_dot, eta_y, eta_y_dot]

x = [x_robot_progress, x_publisher, x_delay_older, x_liquid]
u = [j_issue_v, j_issue_omega, v_s]

NX = 14 + D_v + D_omega
NU = 3
```

其中：

```text
q_prev_c       = 边界前最后一条 emitted command，即 q_{c,i-1}
older_c[r]     = q_{c,i-2-r}
a_prev/alpha_prev = 最后一次 release 按 nominal/安全重置规则提交的权威 publisher acceleration state
```

这里 `px/py/theta/v_actual/omega_actual` 是物理预测状态，`s` 是第 5.5 节单独投影重建的虚拟进度；`x_robot_progress` 这个分组不表示 prefix 可以用历史 `v_s` 传播 `s`。

`D_v/D_omega` 和支持的 `L_max` 是 codegen 合同，必须在专用辨识给出合理范围后冻结。运行时 delay 可以在声明范围内变化，超出 `L_max` 必须 fatal，不能截断。

这是“单个 `14 + delay taps` artifact”，不是严格 14D。不得为了维度数字好看而隐藏 delay 状态或重新引入错时刻转录。

### 6.2 命令状态与 jerk

在 pre-issue state `x[k]` 上，stage 控制先生成本边界要 emitted 的命令：

```text
a_issue[k] = a_prev[k] + dt * j_issue_v[k]
q_issue_v[k] = q_prev_v[k] + dt * a_prev[k]
               + 0.5 * dt^2 * j_issue_v[k]

alpha_issue[k] = alpha_prev[k] + dt * j_issue_omega[k]
q_issue_omega[k] = q_prev_omega[k] + dt * alpha_prev[k]
                   + 0.5 * dt^2 * j_issue_omega[k]
```

必须同时具备：

```text
|q_issue_v|、|q_issue_omega|       命令幅值边界
|a_issue|、|alpha_issue|           命令加速度边界
|j_issue_v|、|j_issue_omega|       jerk 边界
j_issue_v^2、j_issue_omega^2       完整 horizon 平滑代价
```

这样不再需要用 stage cost 访问 `u[k-1]` 来伪造完整 horizon 的 `Delta a/Delta alpha`。跨重规划周期的 stage-0 命令和加速度状态来自权威 publisher state，而不是实测速度或上一条未执行的远期计划。

最终发布状态必须保存：

```text
q_emitted、a_authoritative、cycle_id、stamp、reason、reset_epoch
```

正常情况下，`q_emitted/a_authoritative` 就是 `issue_map(x0,u0)` 的输出。若 hard safety 或 solver failure 改写了 `q`：

- 实际 emitted 值仍按真实顺序进入 delay 历史，旧命令不能被清空，否则会绕过物理纯延迟；
- 下一 publisher state 的 `q_prev` 设为实际 emitted 值，`a_prev/alpha_prev` 按合同重置为零；
- 锁存 trial 无效，不在同一 trial 中恢复 nominal 运行；
- 新 trial 必须以连续零命令完成 history warm-up。

已发生的任意历史序列只作为 `KnownPrefixPropagator` 的外生输入，不要求它重新满足新 jerk dynamics 或 decision bounds，因此不会把历史 prefix 和新命令模型过约束在同一个 OCP 中。

### 6.3 分通道纯延迟

对通道 `c`，设：

```text
delay_c / dt = m_c + beta_c,  0 <= beta_c < 1
```

在边界 `T_i` 生成 `q_issue,i` 后，定义固定展开的命令访问器：

```text
Q_c(0)     = q_issue,c,i
Q_c(1)     = q_prev,c = q_{c,i-1}
Q_c(r>=2)  = older_c[r-2] = q_{c,i-r}
```

ZOH 纯延迟在一个控制周期内精确分成两段：

```text
[T_i, T_i + beta_c*dt):       actuator target = Q_c(m_c+1)
[T_i + beta_c*dt, T_{i+1}):   actuator target = Q_c(m_c)
```

当 `beta_c=0` 时第一段为空：

```text
delay=0       -> 整段使用 q_issue,i
delay=dt      -> 整段使用 q_{i-1}
delay=M*dt    -> 整段使用 q_{i-M}
```

线、角 `beta` 不同时，将两个切换时刻取并集，一个 stage 最多形成三个常值目标子段。`FractionalDelaySchedule` 在启动时生成：

```text
subsegment_duration[0:2]
linear_target_selector[0:2]
angular_target_selector[0:2]
```

selector 是对全部固定 tap 的展开权重，由 CasADi 做固定维度点积；不得用运行时整数 `m` 直接索引符号状态。delay 在单个 trial 中不可动态改变，schedule、delay 和 effective hash 必须一致。

为保证“运行时参数改变不重新 codegen”具有唯一实现，固定以下 codegen 维度：

```text
S_seg = 3
R_c   = ceil(L_max,c / dt)
D_c   = max(0, R_c - 1)
NQ_c  = R_c + 1                 # Q_c(0..R_c) 的 selector 宽度

NP_exec = 7 + S_seg*(NQ_v + NQ_omega)
```

每个 shooting stage 的 OCP 参数 `p` 都包含同一固定顺序的 execution 子向量：

```text
act_inv_tau_v, act_gain_v
act_inv_tau_omega, act_gain_omega
act_seg_dt[0..2]
act_sel_v[0..2][0..NQ_v-1]
act_sel_omega[0..2][0..NQ_omega-1]
```

对每个 slot `r`：

```text
delta_r          = act_seg_dt[r]
q_target_v,r     = dot(act_sel_v[r], Q_v)
q_target_omega,r = dot(act_sel_omega[r], Q_omega)
```

三个 slot 按物理时间顺序依次执行解析 FOPDT、中点位姿和 RK4 液体传播。wrapper 在 trial 启动时把 `delay/m/beta` 编译成上述固定宽度数值，并对全部未来 stage 注入；CasADi 图内不存在运行时整数索引或变长循环。强校验包括：

- `act_seg_dt[r] >= 0`，三段和在冻结容差内严格等于 `dt`；最后一段用 `dt-前两段` 构造，避免累计漂移；
- active slot 的 selector 只能是合法 one-hot；零时长 slot 也使用 `Q(0)` 的合法 one-hot，不允许越界、全零或 NaN；
- `beta` 接近 `0/1` 时按冻结的 integer-snap tolerance 规范化；artifact manifest 只记录 tolerance 与 schedule schema，实际 `delay/m/beta/seg_dt/selectors/runtime_schedule_hash` 只记录在 trial effective config 和每周期 snapshot；
- `tau/gain` 由强类型配置校验，wrapper 只向图中注入有限正数 `inv_tau/gain`；不额外注入一套 `rho` 真值。

`dt/S_seg/L_max/R_c/D_c/NQ_c`、参数顺序和离散公式属于 artifact 合同，改变它们必须升级 `model_id` 并重新 codegen。`delay_c` 在 `[0,L_max,c]` 内只改变 `act_seg_dt/selector` 数值，`tau_c/gain_c` 只改变四个标量，因此不改变 CasADi graph、`NX/NU/NP` 或约束维度，无需 codegen；这些值只允许在 trial 启动前冻结，运动中变化立即 fatal。

每个 stage 结束时：

```text
q_prev_next       = q_issue
older_next[0]     = q_prev
older_next[r>=1]  = older[r-1]
a_prev_next       = a_issue
```

`D_c=max(0,ceil(L_max,c/dt)-1)` 配合 `q_prev` 足以保存到 `q_{i-ceil(L_max/dt)}`。当 delay 恰好等于上界整数拍时，零长度旧子段不得访问边界外 tap。

这不是命令凸插值，也不会在固定网格模型的 `T_i+delay_c` 之前泄漏新命令。队列 shift 是离散复制，新 solver 使用明确的 `DISCRETE` dynamics；Python、C++ replay 和 generated solver 使用同一 schedule 与 golden vectors。相对 `t_pub_actual^model` 的物理泄漏/起效检查属于独立 jitter 与 fidelity 审计，不能用这条模型不变量替代。

### 6.4 执行器渐进响应

对每个 ZOH 常值目标子段、通道 `c in {v, omega}`：

```text
rho_c(delta) = exp(-delta / tau_c)

actual_c[k+1]
  = rho_c(delta) * actual_c[k]
  + (1-rho_c(delta)) * gain_c * q_target_c
```

第一版至少暴露并冻结：

```text
linear:  delay_sec, tau_sec, gain
angular: delay_sec, tau_sec, gain
```

候选 preset 可从 `20260831` 同包辨识值开始，但只能用于实现和离线验证：

```text
linear:  delay≈0.080 s, tau≈0.086 s, gain≈1.050
angular: delay≈0.070 s, tau≈0.677 s, gain≈0.990
```

这些旧候选未记录新合同的 `T_k^model/T_k^steady`，其 delay 时间原点并不完全匹配，只能帮助设置专用辨识激励和初始搜索范围，不能直接写入正式 preset。最终参数必须经过专用辨识 bag 的 development 拟合、validation 选择和 final-test 一次性验证，不能由旧 `0.15/0.22 s` 拼接得到。执行器稳态增益统一命名为 `gain_v/gain_omega`，液体可信窗口统一命名为 `K_liquid`，不得都简写成 `K`。

### 6.5 位姿与液体激励

新 artifact 的离散化 schema 冻结为：

```text
discretization_schema = zoh_fopdt_piecewise_midpoint_pose_rk4_slosh_v1
```

一个名义 stage 内按线/角 delay 切换时刻的并集依次传播。对每个子段 `delta`：

1. `v_actual/omega_actual` 用上一节的指数解析式更新；
2. 解析计算子段中点的 `v_actual_mid/omega_actual_mid`；
3. 位姿使用中点公式：

```text
theta_next = theta + delta * omega_actual_mid
theta_mid  = theta + 0.5 * delta * omega_actual_mid
px_next    = px + delta * v_actual_mid * cos(theta_mid)
py_next    = py + delta * v_actual_mid * sin(theta_mid)
s_next     = s + delta * v_s
```

4. 液体在该子段使用固定 RK4；RK4 节点的实际激励由解析 actual 轨迹计算：

```text
a_x(t) = (gain_v*q_target_v - v_actual(t)) / tau_v
a_y(t) = v_actual(t) * omega_actual(t)
```

5. 子段结束状态作为下一子段初值；stage 末尾再执行 publisher/delay history 的离散 shift。

因此位姿和液体只使用 actual，不保留连续式与离散 map 两套含混真值。Python codegen、C++ prefix/replay 和 warm start 必须逐子段复用同一个公式/测试向量。

概念上的连续关系仍是：

```text
px_dot    = v_actual * cos(theta)
py_dot    = v_actual * sin(theta)
theta_dot = omega_actual
```

但 generated solver 的唯一数值合同是上述离散 schema。严禁液体直接使用 `a_cmd`、`alpha_cmd` 或尚未实现的命令状态作为 actual 激励。

### 6.6 一个 solver、两种实验条件

液体到车体保持单向耦合。B0 时：

```text
liquid_objective_scale = 0
```

第一版两个实验臂都不设置 condition-dependent liquid hard constraint；Bslosh 只通过同一个 `liquid_objective_scale` 使 running/window-boundary objective 生效。否则“两臂只差 scale”的合同会被破坏。若未来需要液体安全约束，必须另立协议，不能混入本次 B0/Bslosh 效果对比。

因此液体状态虽被传播，但不应影响机器人最优解。必须增加数值不变量测试：在 B0 条件下改变 I0 液体初值，首拍命令和机器人 horizon 应在冻结容差内不变。若不满足，说明存在隐藏耦合或数值合同问题。

## 7. Horizon 与代价合同

### 7.1 时域

```text
OCP origin        = t_pub_plan = T_k^-
N                 = 60
dt                = 1/30 s
robot horizon     = 2.0 s from T_k
```

`t0 -> T_k` 已由固定联合前缀传播完成，不计入这 2 s OCP。车体、命令、执行器和液体状态都传播到末端。液体可信窗口从 `T_k` 起算，只控制代价 schedule，不改变状态维度、动力学或 solver artifact。

这改变了旧 short100 的 epoch 语义，因此 `267 ms` 必须在新时间轴下重新验证，不能直接继承旧结论。

### 7.2 可信窗口的精确定义

`K_liquid` 表示受罚的未来 interval 数，并在启动时强制：

```text
1 <= K_liquid < N
```

`K_liquid=0` 会使 running 归一化除零；`K_liquid=N` 会使当前 window-boundary 不落在任何普通 stage，而全局液体 terminal 又被明确关闭。两者都必须 fatal，不能静默改写。首轮候选含义如下：

```text
K_liquid=8:
  running liquid cost = intervals 0..7 的预测右端液体状态 x_1..x_8
  boundary energy     = x_8
  nominal time        = 266.7 ms

K_liquid=10:
  running liquid cost = intervals 0..9 的预测右端液体状态 x_1..x_10
  boundary energy     = x_10
  nominal time        = 333.3 ms
```

running expression 在 stage `k` 内用同一个 `f_discrete(x_k,u_k,p)` 计算预测右端液体状态，不直接访问相邻 shooting node。multiple-shooting dynamics 保证该预测值与 `x_{k+1}` 一致。这样不会用固定的 `x_0` 常数项占掉一份 nominal running 权重。

`K_liquid` 后：

```text
liquid running cost = 0
liquid hard constraint = disabled（两个实验臂、全部 stage 均如此）
liquid state propagation = continue to x_N for diagnostics
```

全局 `x_N` terminal 只保留机器人 terminal，液体 terminal 权重必须为零。

### 7.3 液体运行代价

建议使用预测右端的归一化模态量：

```text
Lq_plus[k] = ||eta_plus(x_k,u_k)||^2 / eta_ref^2
           + r_dot * ||eta_dot_plus(x_k,u_k)||^2
                     / (omega_n^2 * eta_ref^2)
```

`r_dot` 是 running cost 的设计参数，可以从当前 `0.3` 候选开始，但必须写入 effective config。

为了先隔离“窗口长度”而不是把窗口和总增益混在一起，冻结新的代价 schema：

```text
J_liquid_run
  = liquid_objective_scale
  * (W_run / K_liquid)
  * sum_{k=0}^{K_liquid-1} Lq_plus[k]
```

这样比较 `100/167/267/333 ms` 时，`K_liquid` 个未来 interval 的离散 running 权重和固定为 `W_run`。比较窗口期间 `W_boundary` 和其他 robot/command 权重也必须固定。它隔离的是 nominal 离散权重总和；由于纯延迟会让早期 interval 对当前命令不可控，不能进一步宣称各候选的“可控梯度质量”完全相等。必须另行诊断每个窗口中实际可控节点和梯度范数。选定 `K_liquid` 后，再单独调整 `W_run/W_boundary`。

旧 `w_slosh=5` 属于不同的 `/N` 和 active-node 语义，不能直接继承为新 `W_run=5`。必须先计算等效初值，再离线重调并记录新的 cost schema ID。

### 7.4 窗口边界能量

在 `x_{K_liquid}` 单独加入：

```text
E_boundary = ||eta_{K_liquid}||^2 / eta_ref^2
           + ||eta_dot_{K_liquid}||^2
             / (omega_n^2 * eta_ref^2)

J_boundary
  = liquid_objective_scale * W_boundary * E_boundary
```

boundary 的模态速度系数默认按物理自由响应能量取 `1`，不复用 running 的 `r_dot=0.3`。`W_boundary` 必须独立配置、离线冻结，不得隐藏在 running scale 中。

它的准确表述是“减轻可信窗口的截止端效应”，不能写成“保证不会把晃动推到窗口外”。必须同时诊断：

```text
boundary E_boundary
tail eta peak / eta_dot peak
tail energy peak 及其 stage
```

若 `E_boundary` 降低但 tail peak 增大，只能说明当前 boundary 代理不足，不能宣布解决窗口外转移。

### 7.5 代价分项必须可重建

acados 层唯一公式冻结为：

```text
for k = 0..N-1:
  J_stage[k]
    = J_robot_and_command[k] / N
    + 1{k < K_liquid}
      * liquid_objective_scale
      * W_run / K_liquid
      * Lq_plus[k]
    + 1{k = K_liquid}
      * liquid_objective_scale
      * W_boundary
      * E_boundary(x_k)

J_terminal_at_xN = J_robot_terminal(x_N)
```

CasADi 图中不保留对运行时整数 `K_liquid` 的条件分支。wrapper 在每个 stage 注入两个固定宽度 cost 参数：

```text
liquid_run_coeff[k]
  = 1{k<K_liquid} * liquid_objective_scale * W_run/K_liquid

liquid_boundary_coeff[k]
  = 1{k=K_liquid} * liquid_objective_scale * W_boundary
```

它们与第 6.3 节的 execution 子向量、reference/slosh 参数共同组成生成 manifest 中唯一的 `p[k]` 布局。这样 `K_liquid=8/10` 和 B0/Bslosh 只改变参数值，不改变图、维度或 artifact；每个 stage 的实际系数必须写入 horizon snapshot 并参与 cost 重算。

实现要求：

```text
acados cost_scaling[0:N] = 1
stage expression 内不再对整个 cost 二次 /N 或乘 dt
x_N 的 liquid terminal 权重 = 0
```

`J_robot_and_command` 包含 tracking、进度、命令加速度和 jerk 等主线运行项；其 `/N` 语义单独冻结。液体 running 和 boundary 使用各自归一化，不能跟随 robot `/N` 再缩放。

在线诊断至少拆分：

```text
J_robot_run
J_command_accel
J_jerk
J_slosh_run
J_slosh_boundary
J_robot_terminal
J_total_from_acados
J_total_recomputed
```

重算总值必须与 acados 实际目标在冻结容差内一致。不能继续出现 terminal 未赋值、stage N 被当 running `/N` 累计等诊断与真实目标不一致的问题。

## 8. 模块化代码结构

| 模块 | 只负责 | 明确不负责 |

| `ActuatorDiscreteModel` | issue、delay schedule、调用 plant integrator、queue shift | 不选择 observer、不发布命令 |
| `MainlineWarmStart` | 从新 `x0` 用同一模型 rollout 全状态可行候选 | 不沿用旧 6D/10D 布局、不提前提交未 release 结果 |

| `CommandExtractionPolicy` | 计算并提取 `issue_map(x0,u0)` | 不从 measured actual 积分命令 |
| `TerminalReferencePolicy` | 在 solve 前生成唯一 terminal envelope/stop 参考与约束 | 不在 solve 后改命令 |
| `ProposalMailbox` | 按 cycle ID 一次性发布/原子读取 immutable proposal，关闭后拒绝迟到写入 | 不排队复用旧解、不修改 proposal |

## 9. 配置与 generated solver 合同

### 9.1 配置原则

新主线删除以下运行时模式开关：

```text

primitive_mode
solver_backend
delay_phase.mode
execution_model.mode
observer source/fallback mode
```

这些能力在唯一主线中都是固定事实，而不是可选模式：

```text
observer          = processed_imu
failure policy    = fail_closed
common epoch      = required
execution model   = explicit discrete actuator
solver backend    = mainline actuator-aware acados
```

实验只允许一个条件字段：

```yaml
experiment:
  condition: B0       # B0 | Bslosh
```

映射关系：

```yaml
arms:
  B0:
    liquid_objective_scale: 0.0
  Bslosh:
    liquid_objective_scale: 1.0
```

所有其他参数来自同一份 `controller.yaml`。程序启动时逐字段证明两臂除 condition/scale 外完全一致。

```text

  = 排除 experiment.condition/liquid_objective_scale 后的规范化配置 hash

trial_effective_config_hash
  = 包含 condition/scale 在内的完整实际生效配置 hash
```

两臂的 `common_controller_hash` 必须相同；完整 trial hash 必然不同，validator 必须证明结构化 diff 白名单只有 condition/scale，不能错误要求完整 hash 相同。

### 9.3 codegen manifest

生成器必须同时生成：

```text

generated solver library
```

manifest 至少包含：

```text

生成命令
Python/CasADi/acados 版本
source/config SHA256
NX/NU/NP/N/dt
state/control/parameter 顺序
D_v/D_omega/L_max
exact ZOH fractional schedule schema
integer-snap tolerance
dynamics discretization schema
cost schema
artifact SHA256
```

C++ wrapper 使用生成 header，不再手工维护 Python parameter name 列表和 C++ enum 两份合同；对 `NX/NU/NP/N` 使用 `static_assert`。实车启动时 manifest、动态库和编译期 hash 任一不一致都必须 fatal。

codegen manifest 是 artifact 的不可变身份，不包含某次 trial 的实际 runtime schedule hash。`runtime_schedule_hash` 由 wrapper 对冻结后的 `delay/m/beta/seg_dt/selectors` 规范化计算，写入 trial effective config、每周期 snapshot 和 bag meta；它必须匹配实际注入的 `p[k]`，但改变合法 runtime schedule 不得改写 artifact manifest/header/hash。

trial 启动前改变声明范围内的 `delay/tau/gain`、合法的 `K_liquid` 或 B0/Bslosh condition 不应重新 codegen：前者通过固定宽度 `NP_exec` 注入，后两者通过每 stage 的 cost coefficient 注入。所有 stage 都必须显式赋值，不允许依赖 solver 内存中的上次参数；运动中改变任一参数立即 fatal。若这些值的合法改变仍需要重新 codegen，说明模块边界设计失败。

## 10. 命令发布与安全合同

terminal slowdown/capture/stop 必须在 solve 前形成 OCP reference、cost 或 constraint，使正常到点时的 solver proposal 本身就是 nominal 最终命令。不得保留一个常态 post-solver terminal controller 改写命令，否则命令状态和 OCP 预测再次分离。

一次控制周期固定拆为以下两个 phase，求解顺序不能再写在 `ReleaseScheduler(T_k)` 之后：

```text
ReleasePhase(k-1) 成功 commit
  -> 生成 PlanTicket(k,T_k^steady,T_k^model,committed_generation)

PlanPhase(k)，在 proposal_cutoff^steady=T_k^steady-handoff_margin 前：
  -> 获取 committed immutable snapshot
  -> common epoch / known prefix / s projection
  -> TerminalReferencePolicy
  -> solver 与 q_issue/a_issue proposal 校验
  -> publish_once immutable PendingRelease(k)

ReleasePhase(k)，独立线程在 T_k^steady：
  -> try_take_exact(k)，不得等待 solver
  -> 校验 cycle/双时钟边界/reset/path/config/artifact/generation/ready_time
  -> release-time physical hard safety contract（只处理异常）
  -> proposal 合法则发布 proposal；否则发布零并锁存
  -> 在 T_k^steady 前禁止 publish
  -> 紧邻 publish 记录 t_pub_actual^steady/model
  -> cmd_pub.publish(final command)
  -> 成功调用后原子 commit exactly that value/event
```

`PendingRelease` 至少携带 `cycle_id/T_k^steady/T_k^model/reset_epoch/path/config/artifact hash/input generation/q_issue/a_issue/solver status/ready_time^steady/完整 warm-start candidate`，发布到 mailbox 后不可修改。mailbox 对每个 cycle 只接受一次写入；`ready_time^steady > proposal_cutoff^steady`、cycle 已关闭或 ID 不匹配的结果直接丢弃，旧 proposal 不得跨周期复用。

release-time hard safety 只能读取预分配、lock-free 的 immutable `SafetySnapshot`。snapshot 必须携带 steady stamp/reset epoch/source health；缺失、stale、epoch 不符或读取不一致都按安全零处理。ROS callback/TF 查询、动态内存分配和常态 terminal/速度调节不得藏在 `HardSafetyArbiter` 中。

只有 `ReleasePhase` 是下列权威状态的写入者。`cmd_pub.publish(final_command)` 实际调用后，才以同一个 release generation 原子提交：

1. 最终 emitted command history；
2. authoritative publisher state；
3. 保留旧 taps 并注入最终 emitted 值的 delay queue/history generation；
4. 本周期消费状态与 release audit；
5. nominal proposal 对应的 warm start 和 `s_commit`。

只有 final command 与 solver proposal 完全一致的 nominal release 才接受 warm-start candidate 并推进 `s_commit`。hard-safety 改写、deadline zero、solver failure、发布抖动超限或 `publish_cmd_vel=false` 均丢弃候选；在 live publish 已启用时，实际发布的零仍必须提交到 command history、publisher state 和 delay queue。dry-run 只能记录“would publish”诊断，不能伪造 live emitted history。PlanPhase 只能读取已完整 commit 的 snapshot，求解成功本身不得修改任何权威状态。

要求：

1. 全节点只有一个 `/cmd_vel` publisher；检测到其他 publisher 启动失败。
2. terminal reference/constraint、solver proposal、safety command、final emitted command 分字段记录。
3. nominal tracking 和正常到点都不应有 post-solver 改写；任何 hard-safety 改写使 formal trial 无效，但安全上仍发布最终安全值。
4. production live 中，安全零和 solver failure zero 必须进入历史；旧 delay taps 仍按模型网格排出，不能把队列瞬间清零。
5. `publish_cmd_vel=false` 时，每个 `T_k` 恰好记录一个 `would_publish_audit_event`，并强制 `emitted_event_count=0`；不得伪造“已经发布”的历史事件。
6. production live 中 solver failure/non-finite/overrun 时发布并记录零，锁存故障状态，不使用旧远期解。
7. production live 且 publish enabled 时，每个计划 `T_k` 的 emitted event count 必须严格为一；即使 fault 已锁存，也继续逐拍发布并记录零直到 trial/reset 结束。
8. warm start、`s_commit`、publisher command state 和 delay queue 必须服从上述 nominal/安全提交规则，不能在 solver 返回时提前更新。

- effective config 必须同时记录“意图值”和“实际生效值”。

## 15. 分阶段验收门

### 15.0 数据集、统计单元与阈值冻结

在读取 validation/final-test 或开始实车前，必须生成一份 machine-readable gate config，记录 bag 路径、SHA256、互斥的 development/validation/final-test 划分、运动窗口、指标公式、阈值和代码 commit：

- development 只用于拟合参数和形成候选；
- validation 用于选择执行器结构、`K_liquid` 和权重；
- 全部选择冻结并重新 hash 后，final-test 只解封一次用于晋级。

若 final-test 后修改模型、窗口、权重或阈值，该批数据自动降为 development 证据，必须另找未查看数据重新冻结 final-test，不能继续称为独立测试。以下是第一版预注册口径；若 development 噪声表明需调整，必须在解封 validation/final-test 前修改并重新 hash。

执行器 fidelity 以“一条独立 trial”为统计单元，线、角分别报告：

```text
速度 RMSE / MAE
命令变化到 actual 起效的 onset error
t90 relative error
steady-state gain error
phase/cross-correlation lag error
```

第一版晋级门：

```text
final-test median RMSE_new <= 0.90 * min(RMSE_instantaneous, RMSE_legacy)
每条 final-test RMSE_new  <= 1.05 * min(two baselines)
abs(onset error)        <= 1 nominal dt
t90 relative error      <= 15%
```

以上各门对线、角分别成立；不得把两通道平均后掩盖角通道失败。

液体窗口以 horizon 对齐的独立 trial 为统计单元。每个预测 origin 必须是 causal prefix：I0、robot state、history 和参数只能使用 origin 当时已知的数据。离线 fidelity rollout 的未来外生输入使用 bag 中随后**真实 emitted** 的命令；它验证的是“命令→执行器→液体”模型，不是未执行 solver candidate 的反事实效果。

不能只报告 `0～T` 聚合误差掩盖后段退化。至少按冻结的未来 bins（首版边界 `0/100/167/267/333 ms`）逐 bin 定义：

```text
skill(bin) = 1 - MAE_model(bin) / MAE_free_response(bin)
```

这里的 MAE 必须对齐到冻结的未来 RGB/外部液面目标，不能拿内部模态预测与自身比较；free-response 从同一 I0 出发且不使用未来真实输入。若某个 `trial × bin` 的 free-response MAE 低于预注册噪声底，只把该 cell 标记为 `UNINFORMATIVE_BIN`，不得用接近零的分母制造 skill；其他 bin 仍按各自信息量保留。整条 trial 只有在预注册的 RGB 缺失、时间对齐失败等 run-level 数据质量规则触发时才标为 `INVALID_TRIAL`。

`K_liquid` 先在 validation 中选择；对覆盖到候选边界的每个 bin，令 `N_info_bin` 为未标记 `UNINFORMATIVE_BIN` 的有效 trial 数，至少要求 median skill > 0、`ceil(2*N_info_bin/3)` 个 trial 的 skill 为正，并同时报告 `N_info_bin`、最差 trial、可控梯度节点数和 tail peak。冻结候选后，final-test 必须按同一逐-bin 门一次性复核。`K_liquid=8` 仍只是首候选，未过门时退回较短窗口；`K_liquid=10` 只作为上界压力检查。

在线周期集合固定为：

- solver 性能/成功率：observer READY 后至首次 goal/fault 的全部 scheduled solve，每条 run 单独裁决，不跨 run 稀释；
- 命令连续性/饱和：路径进度 `10%～90%` 的 nominal tracking cycles；
- 饱和率：每个 `a_issue/alpha_issue/j_v/j_omega` 通道分别以该通道周期数为分母，`abs(value) >= 0.99*limit` 计饱和；
- 强翻转：相邻周期符号相反，且两侧绝对值均不小于对应加速度上限的 `50%`；线、角分别报告；
- terminal、warm-up、fault-latched cycle 不进入命令效果分母，但必须单独完整报告，不能删除。

## 16. 启动与运行时 fail-closed

### 16.1 启动 fatal

- 非 processed-IMU/fail-closed/common-epoch 合同；
- 发现任何 legacy fixed/delay/backend 参数；
- 六个执行器参数非有限、越界或 delay 超出 codegen `L_max`；
- `K_liquid` 不满足 `1 <= K_liquid < N`，或任一 stage cost/execution 参数未显式赋值；
- `handoff_margin/epsilon_pub` 非有限、越界，或固定三槽 schedule/selector 校验失败；
- steady/model clock bracket 超过 `epsilon_clock_sample`、`epsilon_clock_map` 缺失，或 ROS/model clock 当前无效；
- path/projection guard 缺失、path hash 不一致或起点区间无法唯一投影；
- model/manifest/artifact/schema/hash 不一致；
- command history 时长小于 `state_age_max + L_max + publish_margin`，或缺少左边界前驱 event；
- `/cmd_vel` 存在其他 publisher；
- final command topic 不是已冻结的底盘命令入口，或启动连接合同失败；
- B0/Bslosh 除 condition/scale 外有任何配置差异；
- formal run 启用了未纳入合同的 post-solver limiter/governor/recovery。

### 16.2 运行时发布零并锁存状态码

- I0 stale/reset/future skew；
- odom/TF 无法重建到 `t0`；
- progress projection 歧义、越 guard 或 path/reset generation 不一致；
- 历史缺少前驱、内部 gap 超限、重复/倒退时间戳；
- solver failure、non-finite、proposal cutoff miss 或 mailbox ID/hash/generation 不匹配；
- `t_pub_actual^steady-t_pub_plan^steady` 不在 `[0,epsilon_pub]`，或 clock-map drift 超限；
- final emitted 与 command state 不一致；
- 安全干预或外部 publisher 污染。

零命令本身必须进入历史，该 trial 同时标记无效，不能只依赖 postflight 后验发现。

## 17. 主要风险与停止条件

| 风险 | 处理与停止条件 |
|---|---|
| delay queue 增维导致求解变慢 | target P95 达不到 25 ms 时停止上车；先优化稀疏性和 tap 上界，不回退 legacy |
| solver 阻塞 release 或 proposal 跨周期串线 | planning/release 独立执行上下文和一次性 mailbox 压力测试未通过前禁止接管；每个 `T_k` 缺 proposal 就发布零 |
| 实际发布抖动破坏等间隔 tap 假设 | 禁止早发并冻结 `epsilon_pub`；超限即锁存，逐 trial 报告 jitter；若抖动无法压住则停止上车并升级为显式事件年龄模型 |
| 分数延迟/发布节点错一拍 | exact ZOH 子段、pre-issue issue map 和 release deadline 测试未通过前禁止接管命令 |
| `s` 用旧 `v_s` 前推或投影跳支 | prefix 禁止传播 `s`；局部 forward-only projector 与 stage-0 重锚定合同未通过前禁止求解 |
| 历史命令跳变污染模型 | 历史只走外生联合传播；权威 publisher state 缺失则 fail closed |
| B0 因始终要求 I0 而可用性降低 | 这是公平比较的主动选择；observer 无效时两臂都停车 |
| `K_liquid` 变长同时改变总代价 | 使用 `W_run/K_liquid` 固定离散权重和，并单列可控梯度节点；先选窗口再调权重 |
| boundary 只把峰值推到 tail | 强制发布 tail peak/energy；出现该现象时不晋级 |
| terminal/safety 改写命令 | terminal 进入 OCP；只有 hard safety 可在 solve 后改写，触发即 trial 无效 |
| generated/C++ schema 漂移 | 自动生成 manifest/header、static_assert 和启动 hash gate |
| 删除 legacy 后难以复现实验 | 用旧 Git SHA/worktree 和 bag 复现，不在新代码保留兼容分支 |
| 单一 14+tap 状态模型仍无 RGB 收益 | 记录为有效科学负结果，停止只调 `W_run`，回到模型 fidelity/液体可控性分析 |
