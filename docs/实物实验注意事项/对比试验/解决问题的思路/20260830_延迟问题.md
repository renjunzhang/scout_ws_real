## 1. 目标与证据边界

本文按以下四个问题检查“计划动作 → 最终命令 → 实际运动 → 液体预测”执行链：

本文不重复建立 NOKOV 延迟的另一套数据口径。命令到 NOKOV 动作响应、NOKOV/Windows/Wi-Fi 时间戳边界、bag 身份和逐包拟合的原始记录统一见：

## 2. 控制器计划的动作与最终发布命令是否一致

先分清两种“计划一致”：

1. **本周期首拍是否被后续软件链改动。** `D02/a01`、`D03/a02`、`D04/a01` 的正常跟踪周期分别为 `975/970/981`，三包的 `solver_cmd - published_cmd` 线速度和角速度 P95/最大绝对差均为 `0`，safety intervention 均为 `0`。因此，**正常跟踪段中首拍命令与最终发布命令一致**，当前滞后不是 solver 出口后的 limiter/safety 把命令改坏。
2. **前一周期计划的未来动作是否真成为下一周期首拍。** `ControlCycleAudit` 已记录 `previous_shifted_plan_*` 和 `replanned_minus_shifted_*`，但当前提交文档没有冻结 `D02～D04` 的这组数值。所以还不能宣称“整条 2 s horizon 计划能稳定保留”。这项对液体预测很重要：即使每个周期的首拍都原样发布，较远期减晃动作仍可能在下一次 30 Hz 重规划时被覆盖。

终点附近分别有 `66/70/64` 个 terminal intervention 周期。因此“首拍与发布完全一致”只适用于已排除 terminal 的正常跟踪段，全程报告必须继续分开 solver/terminal/post-gate/published 四层。

## 3. 最终命令发布后，实际速度和转动多久开始响应

本轮可观测的边界是“最终 ROS `/cmd_vel` 发布 → Ubuntu 收到的 NOKOV 动作响应”，不是底盘硬件内部的“收包时刻 → 电机起动”。NOKOV 物理延迟、Windows 解算、Wi-Fi/VRPN 传输和 `use_server_time=false` 的解释边界，以 `20260829_配合动捕测动作延迟.md` 为准。

三包数据的一阶动态加纯延迟拟合为：

| 通道 | 纯延迟 | 时间常数 | 10% 响应时刻 | 50% 响应时刻 | 90% 响应时刻 |
|---|---:|---:|---:|---:|---:|
| 线速度（三包中位模型） | `90 ms` | `74 ms` | `98 ms` | `141 ms` | `260 ms` |
| 角速度（三包中位模型） | `80 ms` | `623 ms` | `146 ms` | `512 ms` | `1.515 s` |

表中阈值时刻由同一拟合模型 `t_p=L-τ ln(1-p)` 派生，不是另一次起步阈值检测。逐包范围为：线速度 90% 响应约 `0.240～0.299 s`，角速度 90% 响应约 `1.515～1.545 s`。

因此若问“什么时候刚开始动”，当前答案是观测纯延迟约 `80～110 ms`；若问“什么时候基本跟上”，线速度约需 `0.24～0.30 s`，角速度则需约 `1.5 s`。只报一个 `80～110 ms` 会严重低估转向建立过程。

## 4. 实际运动相对计划动作的幅值和相位差异

幅值与动态必须分开：

- **稳态幅值没有明显丢失。** 线速度增益为 `1.032～1.034`，角速度增益为 `0.984～0.990`。在当前 Tracker 外参和杠杆臂尚未独立标定的边界下，这不支持“底盘根本做不到命令幅值”。
- **相位/带宽差异明显，角向尤其严重。** 按角速度中位模型，一个命令变化后 `100/167/220/333/500 ms` 时只建立约 `3%/13%/20%/33%/49%` 的最终响应；线速度对应约为 `13%/65%/83%/96%/100%`。所以“最终幅值能跟上”不能用来否定转弯换向期间的大相位滞后。

当前还缺少 `D02～D04` 原始 bag 上的分频互谱/相干性和换向事件分布，因此本节先报时域拟合和阶跃派生量，不伪造一个“全频段固定相位角”。

## 5. 这些差异是否足以解释液体预测随时间迅速失真

当前结论是：**差异的量级足以构成主要解释，且与旧实物证据的方向一致；但尚未在同一包数据上排除液体参数和 RGB 映射误差，所以不称为唯一根因。**

机制链如下：

```text
OCP 计划液体激励：ax = a，ay = v·omega
                  ↓
当前车体模型：v_dot = a，omega_dot = alpha
                  ↓
实车：/cmd_vel 后还有 80～110 ms 纯延迟
      + 线速度约 74 ms、角速度约 623 ms 建立动态
                  ↓
实际 ax 与 v·omega 的峰值时刻、换向时刻和短时幅值与计划不同
                  ↓
低阻尼液体模型对激励相位和历史有记忆
                  ↓
越往远期，planned-input 液体轨迹与 realized-input 轨迹越容易分离
```

当前容器名义一阶液体频率约为 `4.973 Hz`，周期约 `0.201 s`。`80～110 ms` 纯延迟相当于该周期的约 `40%～55%`；若车体激励在该模态附近确有足够能量，单这一项就对应约 `143～197 deg` 的输入相位差。这与“真正 causal lead 约 `100 ms` 后 planned horizon/RGB 对应开始明显衰减”的旧证据在量级上一致。但这是相位敏感性论证，还需用实测输入频谱证明模态附近确有足够激励，不将其当成已完成的频域辨识。

代码语义也支持这个风险：当前 `ExecutionStatePredictor` 用 `max(0.15,0.22)=0.22 s` 的共同窗口，将历史 `/cmd_vel` 直接当作已实现的 `v/omega` 做 ZOH 积分；如果滚动液体，还直接用 `Δcmd_v/Δt` 和 `cmd_v·cmd_omega` 作激励。它尚未表达本轮观测到的线/角分通道纯延迟与一阶建立动态。`fixed_robot_only` 在 B0 中只应用车体结果，所以本轮不会把错误液体 rollout 送入 B0；但这也意味着它不能证明未来 `fixed_closed_loop` 的液体时间对齐是正确的。

还有一条跨批次支持证据：旧 G3R2 中，planned horizon 与 native RGB 的对应约 `100 ms` 后明显变弱，`333 ms` 后不宜当作可靠物理预测；而 actual-IMU retrospective replay 与 RGB 仍保持中等稳定对应。这使“未来车体激励没有按计划实现”比“液体 ODE 软件接线完全错误”更符合现有证据。

## 7. NOKOV、IMU 与真实运动时刻的数学关系

先定义事件：

```text
t_cmd    最终 /cmd_vel 发布
t_phys   真实刚体开始响应
t_nokov  NOKOV 曲线看到响应
t_imu    /imu/data 曲线看到响应
```

再定义：

```text
d_act = t_phys  - t_cmd       底盘接收和物理执行延迟
d_N   = t_nokov - t_phys      NOKOV 测量链延迟
d_I   = t_imu   - t_phys      IMU 测量链延迟

L_cmd_nokov = d_act + d_N
L_cmd_imu   = d_act + d_I
Delta_N_I   = t_nokov - t_imu = d_N - d_I
```

当前直接测得 `L_cmd_nokov≈80～110 ms`，并测得 `Delta_N_I≈-10～-15 ms`。负号表示 NOKOV 更早，或等价地说 `/imu/data` 更晚。

但 `d_act`、`d_N`、`d_I` 三个绝对量仍不能由这两类软件观测唯一解出。因此：

- `80～110 ms` 只能叫“最终 `/cmd_vel` 到 Ubuntu 收到的 NOKOV 动作响应的观测纯延迟”；
- `-10～-15 ms` 只能叫“NOKOV 相对 `/imu/data` 的观测时差”；
- 若要单独得到 NOKOV 的绝对曝光—解算—Wi-Fi 延迟，仍需要硬件触发或统一硬件时钟。

## 8. NOKOV 和 IMU 延迟的当前数据

### 8.1 NOKOV 相对 IMU

`N02～N04` 的符号约定是负值表示 NOKOV 更早：

| bag | 全局时差 | 峰值相关系数 | 有效局部窗口 | 局部范围 |
|---|---:|---:|---:|---:|
| `N02/a01` | `-15 ms` | `0.9925` | `9` | `-15～-10 ms` |
| `N03/a01` | `-15 ms` | `0.9921` | `9` | `-15～-15 ms` |
| `N04/a01` | `-15 ms` | `0.9931` | `9` | `-15～-10 ms` |

27 个有效局部窗口中，24 个为 `-15 ms`，3 个为 `-10 ms`。但 `/imu/data` 原生频率只有约 `50.1 Hz`，即约 `20 ms/样本`；零时差处的相关系数又已经达到 `0.9898～0.9916`。所以正式口径是“两路在 `±20 ms` 内基本同步”，而不是“精确测得 15.0 ms”。

当前 VRPN 为 `use_server_time=false`。`D02～D04` 中 NOKOV 的 bag-arrival 减 header 中位数只有 `0.081～0.110 ms`，这只表示 Ubuntu 收包后很快写入 rosbag，不能解释为 NOKOV 物理延迟约 `0.1 ms`。

### 8.2 raw `/imu/data`

当前 WIT 驱动在串口数据解码完成、收到姿态包后才执行：

```python
stamp = rospy.get_rostime()
imu_msg.header.stamp = stamp
```

所以 `/imu/data.header.stamp` 是 ROS 端解码/发布时刻，不是 IMU 硬件原始采样时刻。设备内部滤波、串口帧周期和解码延迟均已隐含在数值中，不能用 `arrival-header≈0.2 ms` 代替。

只对 gyro-z 做跨实验粗略合成：

```text
L_cmd_imu ≈ L_cmd_nokov - Delta_N_I
          ≈ (80, 80, 110) ms + 15 ms
          ≈ (95, 95, 125) ms
```

这不是同 bag 直接测量，不确定性至少约一个 IMU 周期 `±20 ms`，也不能外推为 accelerometer 延迟。

本机已有的旧 `20260729 planar_r03` 实物 bag 提供了方向性交叉检查（`Verification Status: ANALYZED / 未冻结`）：同一角运动段的一阶加纯延迟模型得到 `/cmd_vel→NOKOV omega` 的 `L≈60 ms`、`/cmd_vel→IMU omega` 的 `L≈80 ms`，相差 `20 ms`。这与当前 N 组结果方向一致，但旧工况不能替代 `D02～D04`。

### 8.3 processed-IMU

当前配置：

```yaml
sensor_delay_sec: 0.015
accel_phase_delay_sec: 0.006834
gyro_phase_delay_sec: 0.005020
alpha_phase_delay_sec: 0.015001
observer_dt_sec: 0.020
```

代码已经计算：

```text
measurement_stamp = source_stamp - 15.000 ms
accel_effective   = source_stamp - 21.834 ms
gyro_effective    = source_stamp - 20.020 ms
alpha_effective   = source_stamp - 30.001 ms
```

其中 `15 ms` 来自 gyro-z 与动捕的相对对齐；后三项是因果滤波和差分的设计值，不是传感器绝对延迟的三次实测。时间戳回拨只是在记录“该数值代表过去哪个时刻”，不会让数据在墙钟时间上提前到达。

当前 observer 的组合 `state_stamp` 使用 `measurement_stamp=source-15 ms`；accel、gyro、alpha 的三个 effective stamp 只被保留为诊断，还没有显式分量重对齐。因此 processed-IMU 后续进入求解器前，必须检查这约 `5～15 ms` 的分量时差，并避免再次减一遍上述配置。

## 9. 当前补偿决策

当前不应简单执行以下任何一种操作：

- 把 `80～110 ms` 与 `10～15 ms` 直接相加后写入 MPC；
- 从 `0.15/0.22 s` 中直接减去 `15 ms`；
- 把角速度 `t90≈1.5 s` 当作角延迟；
- 因为 `/cmd_vel→NOKOV` 的纯延迟小于 `0.15/0.22 s`，就立即覆盖当前配置。

原因是当前配置和本轮模型估计的量不同：

- 历史 `/cmd_vel→odom` 互相关为线速度 `0.14～0.16 s`、角速度 `0.18～0.28 s`，与 `0.15/0.22 s` 接近；
- 本轮 `80～110 ms` 是一阶模型拆出的纯时移 `L`；
- 时间常数 `tau` 还会形成频率相关的相位滞后。

按当前中位模型，线速度在 `150 ms` 时约建立 `56%`，角速度在 `220 ms` 时只建立约 `20%`。因此 `0.15/0.22 s` 更像与 odom、状态传播和信号带宽耦合的有效窗口，而不是纯硬件死时间。

明日可用于离线对照、但今天不写入正式配置的初始模型为：

```text
linear:  L=0.090 s, tau=0.074 s, K=1.033
angular: L=0.080 s, tau=0.623 s, K=0.989
```

目标实现形式应是分通道执行器状态模型，而不是把 `tau` 塞进纯延迟：

```text
dv_real/dt     = (K_v * v_cmd(t-L_v)         - v_real)     / tau_v
domega_real/dt = (K_w * omega_cmd(t-L_omega) - omega_real) / tau_omega
```

今天的决定是：保持 `0.15/0.22 s` 为 provisional tested baseline，等待明日原始 bag 的同包验证后再选模型。

```text
abs(y-y0) >= max(3 * baseline_sigma, 0.05 * abs(delta_y_steady))

```

### 10.4 D：同包计算 NOKOV/IMU 相对时差
