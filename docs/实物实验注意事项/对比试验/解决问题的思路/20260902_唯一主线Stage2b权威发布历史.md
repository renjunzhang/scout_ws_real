## 1. 实施边界

本子阶段实现 ROS-free 的最终命令事件、权威 publisher state 和固定容量历史。它只接受已经跨过唯一 publisher 边界的 `PublicationReceipt::kPublished` 事实，不接受 solver proposal，也不从 mailbox 的 ready/take 状态推断“已经发布”。

尚未接入：

- ROS `/cmd_vel` publisher；
- `ReleaseCoordinator` 与 hard-safety；
- delay queue、FOPDT、known-prefix、warm start 或 `s_commit`；
- offline replay event source；
- 旧 `ros/command_history_buffer.*` 的迁移或删除。

因此当前测试证明的是“若唯一 publisher 返回成功 receipt，权威事实如何被一致提交”，不宣称生产节点已经满足每个 `T_k` 恰好一次发布。

Stage 1 继续保持：

```text
BLOCKED_PENDING_DEDICATED_IDENTIFICATION_EVIDENCE
```

本实现不引入候选 `delay/tau/gain/L_max`，也不进入 Stage 3 codegen。

## 2. 唯一提交语义

每条 `EmittedCommandCommit` 必须同时携带：

- scheduler 冻结的 `cycle_id/T_k^steady/T_k^model/reset_epoch`；
- release 决策读取的 `expected_history_generation`；
- publisher 返回的、重新绑定同一 cycle 与 exact command 的 actual steady/model 双时钟 receipt；
- 最终真实命令、权威加速度与发布原因。

只有 `PublicationStatus::kPublished` 可以提交。`kWouldPublish` 不写 live history、不推进 generation；publisher failure 也不伪造事件，并锁存历史合同故障。

成功提交后，单个不可分割 generation 同时给出：

```text
最终 q_emitted
权威 q_prev/a_prev publisher state
cycle 与 planned/actual 双时钟
reason/publish_late/reset_epoch
release_generation == history_generation
```

权威状态不由调用方另行写入，而是由最终事件派生：nominal 保存实际 `q/a`；warm-up、deadline、solver failure、jitter 和 clock fault 零命令将加速度清零；hard-safety 改写保留实际 emitted `q`，但同样把权威加速度清零。

## 3. 顺序与时间门禁

history 实例绑定一个 `ClockAnchor/reset_epoch/first_cycle_id`：

1. cycle 必须严格连续，禁止重复、倒退或跳拍；
2. `T_k^steady/model` 必须等于绝对 `round(k*1e9/30)` 网格及冻结 anchor 映射；
3. expected history generation 必须等于最后一次完整提交；
4. receipt 内的 cycle/epoch/boundary/command 必须与本次 commit 精确一致，旧 receipt 不能套用到新命令；
5. final command、nominal acceleration 必须有限；要求零命令的 reason 不得夹带非零值；
6. actual steady/model 均不得早于各自计划边界，且 actual steady/model 序列必须严格递增；
7. nominal event 超过 `epsilon_pub` 拒绝；非 nominal 事件可记录真实超限并置 `publish_late=true`；
8. 任一 history-integrity 错误锁存 fault；solver/safety/deadline fault 所产生的合法安全事件不触发该锁，仍可逐拍提交；history-integrity fault 则必须结束当前 epoch。跨 epoch 恢复必须先 quiesce 旧 writer/reader，再新建实例。

模型 tap 与 ZOH 查询只使用 planned `T_k^model`。actual publish 时间只作审计，不能改变 delay tap 时刻。

## 4. 固定容量不可变快照

实现限定一个 release writer 和一个并发 snapshot reader，使用三个启动时预分配的固定容量 buffer：

- active buffer 永不被 writer 原地修改；
- reader 先 pin active buffer，再复制为调用方持有的不可变 snapshot；
- writer 只写既非 active、也未被 reader pin 的 buffer；
- 三缓冲保证单 reader 被 pin 时仍有一个 writer 目标；
- commit 不分配、不取 mutex、不等待 reader，但会复制固定上限的 history storage；
- 第二个并发 reader立即得到 `ReaderBusy`，诊断必须消费 planning 已复制的 snapshot，不得另占 release RCU reader；
- 容量满后只保留最新固定数量的真实事件；若查询左边界前驱已被 prune，coverage 明确返回 insufficient。

`L_max` 尚未由专用辨识冻结，因此容量仍是编译期模板参数。接入生产前必须按 `state_age_max + L_max + publish_margin` 推导容量，并在目标机测量 bounded-copy 的 release jitter。

## 5. 历史查询合同

`sampleAt(model_time)` 是 planned model grid 上的 ZOH：

- 精确命中返回该事件；
- 两事件之间返回前驱；
- 最新事件之后返回明确标记的 future hold；
- 最老事件之前不补假零，返回历史不足。

`coverage(left,right,max_gap)` 必须找到 `stamp <= left` 的真实前驱，并分别报告内部最大相邻 gap 与末端 future-hold 时长。任一超过门限即 fail closed；actual publish jitter 不参与这些 tap 间隔。

## 6. 后续接入门禁

后续 `FinalCommandPublisher + ReleaseCoordinator` 必须保证：

```text
pre-validate final command/reason/generation
-> 唯一真实 publish 调用
-> 获得 kPublished receipt
-> commitEmitted(exactly that command)
-> 同 generation 再提交 delay queue/warm start/s_commit
```

在该集成完成前，旧 ROS 发布路径仍是 legacy，且其“publish 前 record”顺序明确不满足新主线合同，不能包装成这里的 receipt。
