## 0. 先给出结论

未来含 slosh 的正式配置方向是：

```text
processed-IMU 的 I0 液体状态
        +
processed_imu 失效时 fail_closed
        +
slosh_enable = true
        +
车体与液体使用同一物理时刻
        +
MPC 内显式执行器响应模型
        +
旧 delay_phase 只保留 shadow 诊断，或完全 off
```

**不是**：

```text
processed_imu + fail_closed + slosh_enable=true + fixed_closed_loop
```

原因是当前 `fixed_closed_loop` 使用历史 `/cmd_vel` 同时开环推进车体和液体，其液体分支等价于本轮影子实验中的 L22 思路。当前数据并不支持让 L22 进入求解器。

| 配置项 | 未来目标 | 当前边界 |
|---|---|---|
| 液体观察来源 | `processed_imu` 的 I0 | 不是把 raw IMU 数值直接填入 MPC |
| 观察失效策略 | `fail_closed` | IMU 未 READY、过旧或时间契约失败时停车，不静默切换 odom |
| slosh 求解器 | `slosh_enable=true` | B0 仅用于车体回归和对照 |
| 初始状态时刻 | `require_common_epoch=true` | 车体和液体必须属于同一时刻 |
| 液体外部 nowcast | I0，不额外前推 | I1 和 L22 保持 `applied_to_solver=false` |
| 车体执行延迟 | 放入 MPC 执行器模型 | 不再用预测初始车体状态绕过执行器 |
| 执行器参数 | 线/角 `delay_sec`、`tau_sec`、`gain` 全部启动时可配置 | 不得硬编码在 CasADi、generated C 或 C++ wrapper 内 |
| 旧 `delay_phase` | 过渡期 `shadow`，最终可 `off` | 不得用 `fixed_robot_only` 或 `fixed_closed_loop` 与新模型双重补偿 |

## 1. 为什么做这个选择

### 1.1 液体来源已有的证据

2026-08-31 的 N01～N03 三包同包对比目前支持：

- processed-IMU I0 相对 odom O0 的平均 MAE 降低 `27.69%`；
- 平均约 `28 ms` 的 I1 短时前推在 `3/3` 包中都更差，平均退化 `11.95%`；
- L22 的某些幅值误差虽然较小，但相关性较差，且它事先定义为 legacy 诊断分支，不是放行候选。

因此，下一版求解器的液体初值使用 I0，不再于求解器外把它前推 `28 ms`、`0.15 s` 或 `0.22 s`。

### 1.2 车体延迟已有的证据

当前 B0 实物 A/B 已证明“考虑延迟”对跟踪有用：同路径的 `shadow` 未到终点，3 次 `fixed_robot_only` 均到达终点。但底盘并不是“等待一段时间后立即完全跟上”，而是：

- 线速度纯等待约 `80 ms`，之后以约 `79～93 ms` 的时间常数逐渐建立；
- 角速度纯等待约 `40～80 ms`，之后建立很慢，时间常数约 `625～677 ms`；
- 角速度模型到达 90% 变化量需要约 `1.52～1.63 s`，这不是可直接写入补偿参数的“纯延迟”。

所以，旧 `0.15/0.22 s` 仍可作为 B0 的已验证工程基线，但不能直接当成新执行器模型的纯延迟参数。

## 2. 当前两种闭环延迟模式为什么都不是正式答案

| 模式 | 当前做法 | 合适用途 | 不适合含 slosh 正式闭环的原因 |
|---|---|---|---|
| `fixed_robot_only` | 只用预测结果替换 robot，液体保留当前 observer 值 | B0 延迟敏捷排查和历史基线 | 形成“预测车体 + 当前液体”，两者不是同一物理时刻 |
| `fixed_closed_loop` | 用历史 `/cmd_vel` 同时推进 robot 和 slosh | legacy 诊断和历史实验复现 | 把已发布命令近似当成已实现运动，无法表达转向缓慢建立；液体分支是未放行的 L22 |

当前代码已明确禁止：

```text
slosh_enable=true
+ require_common_epoch=true
+ fixed_robot_only
```

这个 fail-fast 应保留。未来加入执行器模型后，还应增加“新执行器模型已开启时，禁止任何旧 closed-loop delay mode”的启动契约。

## 3. 正式时间轴

### 3.1 共同初始时刻

定义：

```text
t0 = 本周期被 observer selector 接纳的 processed-IMU I0 state_stamp
```

然后构造：

```text
liquid(t0) = processed-IMU observer 的 eta_x/eta_x_dot/eta_y/eta_y_dot
robot(t0)  = odom 历史插值到 t0，位姿需要时查询 TF(t0)
```

`t0` 不是 `ros::Time::now()`，不是 bag 到达时间，也不应人工再减一次 `15/20/30 ms`。processed-IMU 管线已经记录 sensor/filter 的有效时间语义，重复减去会造成二次补偿。

当前代码已有 odom 历史插值、短外推和 `TF(t0)` 查询能力。后续应把这一部分收口为单独的 common-epoch input builder，不在 runner、observer 和 solver wrapper 内各算一套时间。

正式 B0/Bslosh 成对比较时，B0 虽然不消费液体状态，也应使用同一个 I0 `t0` 构造 `robot(t0)`。否则 B0 使用最新车体状态、Bslosh 使用较早的共同时刻，仍然会在对比中混入时间口径差异。当前代码只在 slosh solver 消费液体时强制这个对齐，这是后续 formal comparator 契约需要补齐的地方。

### 3.2 从状态时刻到命令真正生效

求解在 `t_now` 发生，新命令要到 `t_apply` 附近才开始影响车体。因此，MPC 不能把刚优化出来的命令虚构为从 `t0` 就已经生效。

```text
processed-IMU I0 ------------------------------+
  liquid(t0), state_stamp=t0                   |
                                                +--> common x0(t0)
odom history + TF(t0) -------------------------+           |
  robot(t0)                                                |
                                                           v
/cmd_vel 已发布历史 ---> 已知、不可重新优化的执行前缀
                                                           |
当前及未来优化命令 ---> 纯等待 + 逐渐响应的执行器模型
                                                           |
                                                           v
                         predicted actual v / omega / a / alpha
                                  |                  |
                                  |                  +--> 路径跟踪动力学
                                  +-----------------------> 液体未来激励
```

这里会在 MPC 时域内继续传播液体状态，因为这本来就是 SPMPC 的核心。禁止的是在进入 MPC 前，再用 I1/L22 单独替换 I0 初值；两者不能混为一件事。

## 4. 执行器模型怎么加

### 4.1 当前 OCP 缺少的部分

当前 alpha-state OCP 直接使用：

```text
v_dot     = a
omega_dot = alpha
liquid ax = a
liquid ay = v * omega
```

这等价于把规划的 `a/alpha` 立即当成实车已实现的运动。对当前转向逐渐建立的底盘，这个假设不成立。

### 4.2 建议的第一版结构

建议在 OCP 内明确区分：

- 优化出的命令状态 `v_cmd/omega_cmd`；
- 车体真正实现的状态 `v/omega`；
- 命令到实际运动之间分通道的等待和建立过程。

概念上可以先用两个独立通道表达：

```text
v_dot     = (K_v     * delayed(v_cmd,     L_v)     - v)     / tau_v
omega_dot = (K_omega * delayed(omega_cmd, L_omega) - omega) / tau_omega

a_actual     = v_dot
alpha_actual = omega_dot
```

其中延迟部分可以使用有界命令队列、离散 delay-chain 状态，或已知历史命令前缀实现。在专用辨识 bag 和 replay 完成前，不冻结具体实现和状态维度。

如果继续保留 alpha-state 控制语义，可把 `a_cmd/alpha_cmd` 理解为命令状态的变化率，而不是已实现的车体加速度。底盘位姿与液体动力学都必须使用 `v/omega/a_actual`，不能使用未执行的原始命令。

`v_cmd/omega_cmd` 的初值和延迟队列必须来自 `t0` 之前真正发布的 `/cmd_vel` 历史，不能来自 solver 出口前的中间值或上一周期未执行的远期计划。历史不足时应 fail closed，不默认补零后继续正式运行。

### 4.3 线向和角向必须分开

线速度和角速度的纯等待、建立速度和可能的死区都不一样，不得复用一个共同时间常数。第一版可以先用线性分通道模型；如果 held-out replay 还有明显起步/停车不对称残差，再单独增加死区或分段参数，不要在第一次修改中同时加入所有非线性。

### 4.4 执行器参数必须暴露为配置

为了能够快速做不同延迟参数的 A/B 与 sweep，第一版至少暴露以下六个参数：

| 通道 | 纯等待 | 建立时间常数 | 稳态增益 |
|---|---:|---:|---:|
| 线速度 | `linear.delay_sec` | `linear.tau_sec` | `linear.gain` |
| 角速度 | `angular.delay_sec` | `angular.tau_sec` | `angular.gain` |

2026-08-31 同包中位模型可以作为第一个开发 preset：

```text
preset_id = actuator_fopdt_20260831_same_bag_v1

linear:  delay=0.080 s, tau=0.086 s, gain=1.050
angular: delay=0.070 s, tau=0.677 s, gain=0.990
```

这是可用于实现、离线 replay 和低速 B0 测试的候选 preset，不是最终实车标定。历史 B0 的 `fixed_robot_only 0.15/0.22 s` 应保留为另一个 legacy baseline，不得把两组数字拼成新 preset。

参数链应固定为：

```text
YAML/preset
  -> 强类型 ActuatorResponseParams
  -> 有限值、单位和范围校验
  -> solver 每周期参数 / replay 同口径参数
  -> effective config + trial meta + bag 诊断
```

测试 runner 可以通过明确的 launch arg 或环境变量覆盖 preset，但必须在小车开始运动前打印“意图值”和“实际生效值”并做一致性检查。实车运动中不接受未记录的动态改参；需要换参时结束当前 trial，以新的 test/attempt 重新启动。

`tau/gain` 应作为运行时 OCP 参数传入。`delay_sec` 的实现也必须保证在预先声明的有界范围内改参不改变 OCP 状态维度，例如使用固定最大长度的 delay buffer/chain 加分数延迟插值。不能因为把 `80 ms` 改成 `70 ms` 就需要手工修改状态维度或重写 generated solver。

## 5. 模块边界

后续实现建议拆成以下单一职责模块：

| 模块 | 只负责 | 不应负责 |
|---|---|---|
| `CommonEpochInputBuilder` | 选择 `t0`，把 odom/TF 重建到 I0 时刻，检查时间契约 | 不前推液体，不做控制 |
| `ActuatorResponseParams` | 加载 preset/覆盖值，校验单位和范围，生成唯一生效参数 | 不做动力学积分，不暗藏 fallback 默认值 |
| `ActuatorResponseModel` | 计算命令经等待和一阶响应后的实际 `v/omega/a` | 不选液体观察器，不做路径投影 |
| `ActuatorHistoryPrefix` | 保存最终已发布 `/cmd_vel`，构造 `t0` 之后的已知执行前缀 | 不使用 solver 出口前的中间命令 |
| OCP 模型/codegen | 在 B0/Bslosh 中消费同一执行器模型契约 | 不再内部暗藏第二套延迟参数 |
| `ExecutionContract` | 检查模型、命令历史、共同时刻和最终发布是否一致 | 不在诊断层修改命令 |
| 跟踪/液面验证脚本 | 判断车跑得好不好、液面是否真的变小 | 不参与在线状态选择 |

当前 `robotStateAtEpoch()` 和 `alignRobotStateToEpoch()` 已提供共同时刻的基础，应优先抽取和补齐测试，不需要推倒重写。

Python/CasADi 和 C++/replay 中难免需要两份实现时，参数顺序、单位、离散化方法和命令前缀语义必须由一份契约清单约束，并用同一组 golden vectors 做跨实现数值对照。不能只靠注释声称两边一致。

## 6. 目标配置示意

下面只表示最终参数契约，`actuator_response` 是待实现的新模块，**当前不能把这段直接复制到 launch 中运行**：

```yaml
planner_variant: <validated_slosh_variant>  # 该 variant 内 slosh_enable=true

slosh_observer:
  source: processed_imu
  fallback_policy: fail_closed

state_timing:
  require_common_epoch: true

# 过渡/正式审计期可保留 shadow；它不得替换 solver input。
# 新执行器诊断完全取代旧诊断后可设为 off。
delay_phase:
  mode: shadow

# 新模块：名称和具体参数尚未进入当前代码。
actuator_response:
  enable: true
  preset_id: actuator_fopdt_20260831_same_bag_v1
  # 首个开发候选；实现时可由 runner 显式覆盖。
  linear:  {delay_sec: 0.080, tau_sec: 0.086, gain: 1.050}
  angular: {delay_sec: 0.070, tau_sec: 0.677, gain: 0.990}

speed_safety:
  enable: true
  v_safe_max: 0.15

execution_contract:
  fail_closed_on_post_limit_change: true
```

正式启动时还必须自动检查：

```text
observer source             = processed_imu
observer fallback policy    = fail_closed
processed-IMU state         = READY and fresh
solver consumes liquid      = true
robot/liquid epoch skew     = 0 within numerical tolerance
I1 applied_to_solver        = false
L22 applied_to_solver       = false
legacy delay applied        = false
actuator response enabled   = true
actuator preset id          = intended preset id
all six actuator params     = intended finite values
solver/published speed      <= v_safe_max
```

任意一项不满足时，本次含 slosh 运行不应自动降级为 odom observer、旧瞬时车体模型或 `fixed_closed_loop`，而应停车并给出可定位的状态码。

## 7. 分阶段实施与提交

每个阶段单独 commit，通过本阶段门槛后才进入下一阶段。

### Stage A：冻结契约和基线

- 为当前 B0/Bslosh 状态维度、参数布局、命令语义和 common-epoch 行为增加契约测试；
- 冻结当前 B0 `fixed_robot_only 0.15/0.22 s` 实物跟踪基线；
- 冻结 I0/O0/I1/L22 三包结果与分析代码 SHA-256；
- 不改变控制行为。

### Stage B：专用执行器辨识

- 采集能分辨纯等待、建立过程、起步/停车差异和左右换向的专用 bag；
- 开发集拟合，held-out bag 只验证；
- 分别冻结 `L_v/tau_v/K_v` 和 `L_omega/tau_omega/K_omega`；
- 若参数近优区仍触及搜索边界，不允许进入在线模型。

### Stage C：独立执行器模型与离线 replay

- 先实现不依赖 ROS/acados 的 `ActuatorResponseModel`；
- 实现强类型参数加载与校验，为六个参数增加非有限值、负值、越界和单位错误测试；
- 单元测试零输入、常值输入、正负换向、不规则时间步长和历史不足；
- 用同一 bag 同时输出“旧纯延迟”与“新执行器模型”，但两者都不进入求解器；
- 用 NOKOV 求导速度、odom 和 IMU gyro-z 交叉检查，不使用 `/mocap/scout_odom.twist`。

### Stage D：同步修改 B0/Bslosh OCP

- B0 和 Bslosh 同时加入完全相同的 robot/actuator 状态和方程；
- Bslosh 只在此共同车体模型上追加液体状态、液体动力学和代价；
- 液体纵向激励改用 `a_actual`，横向激励使用预测实际 `v*omega`；
- 同步修改 Python CasADi 模型、C++ wrapper、warm start、边界、诊断和两套 generated solver；
- 六个执行器参数由同一强类型配置注入 B0/Bslosh，并发布到 effective config 与控制周期审计；
- 生成新的 model/release 名称，不静默覆盖历史 generated solver。

虽然此阶段同时涉及 B0/Bslosh，但这是同一状态维度和参数布局契约的原子更新，不应拆成“B0 已换模型、Bslosh 还在用旧模型”的中间状态。

### Stage E：无运动与 B0 回归

- 先用 `publish_cmd_vel=false` 和录制 bag 验证时间、命令前缀、状态维度、warm start 和求解器输出；
- 再做低速 B0 smoke，与旧 `fixed_robot_only` 基线使用相同路径、起点、`v_ref`、安全上限和终点判定；
- 新模型运行时 `delay_phase=shadow|off`，旧闭环延迟应用率必须为 0；
- B0 未到终点、大曲率转弯退化或命令契约失败时，不进入含 slosh 实车。

### Stage F：含 slosh 的小步放行

1. 无运动 replay；
2. 架空/轮离地的命令链检查；
3. `v_safe_max=0.15 m/s` 的短路径 smoke；
4. processed-IMU 故障、过旧、时间跳变和历史缺失的 fail-closed 注入测试；
5. 最后才进行同参数 B0/Bslosh 实物对比。

## 8. B0 与 Bslosh 怎么保持公平

两者必须共享：

- 同一 robot/actuator 动力学和同一组辨识参数；
- 同一 common-epoch 规则；
- 同一路径、起点、容器、液体量、`v_ref`、边界和终点控制；
- 同一最终命令契约与安全上限；
- 同一录包与 postflight 口径。

B0 不消费液体状态，但仍应并行记录 processed-IMU I0 和 RGB 液面，并使用该 I0 的 `t0` 构造同时刻车体初值；Bslosh 才将 I0 的液体数值放入求解器。如果要更严格地隔离“有无 slosh 代价”，应再使用状态维度和执行器模型完全一致的 matched0/matched5 对照。

主评价仍然是：

- NOKOV 位姿求导得到的车体跟踪和运动；
- RGB 外部液面高度/晃动指标；
- 求解器内部 slosh 高度只用于解释机制，不得用来自证减晃成功。

## 9. 不可违反的红线

1. 不得在新执行器模型上再开 `fixed_robot_only` 或 `fixed_closed_loop`。
2. 不得把角向 `1.52～1.63 s` 的 90% 建立时间写成纯延迟。
3. 不得把 I0 人工前推 `0.15/0.22 s`，也不得重复减 processed-IMU 已编码的滤波/传感时间。
4. 不得让液体模型直接使用“已发布但底盘尚未实现”的 `/cmd_vel` 作为实际加速度。
5. 不得只更新 B0 或只更新 Bslosh 的 generated solver。
6. 不得在 processed-IMU 失效时静默切到 odom 并继续把运行标成正式样本。
7. 不得修改了状态布局却遗漏 warm start、C++ 包装层、诊断 schema 或离线解析器。
8. 不得用内部 slosh 预测高度代替 RGB 外部真值。
9. 不得在正式 B0/Bslosh 对比中让 B0 使用 latest robot state、Bslosh 却使用 I0 时刻的 robot state。
10. 不得把执行器参数只写在代码常量中，或允许 runner 覆盖后不写入 meta/effective config。
11. 不得在同一实车 trial 运动中改参后继续当成同一样本。

## 10. 与 `README_METHOD.md` 的关系

这个方向不改变项目核心贡献：

- 仍然是 alpha-state MPCC；
- 仍然显式传播液体模态位移和模态速度；
- 仍然在同一滚动时域内联合处理路径跟踪、进度、车体可执行性和预测晃液；
- 液体未来运动仍由预测车体运动激励。

执行器模型是对“车体可执行性”的物理完善，不会把方法变成另一种核心算法。但实施成功后，`README_METHOD.md` 中的以下细节必须按实际代码适配：

- B0/Bslosh 的状态维度和控制语义；
- `v_dot=a`、`omega_dot=alpha` 的瞬时执行假设；
- 液体纵向激励 `a_x=a` 的描述；
- 在线数据流中 delay-phase 模块的位置与作用。

在新模型通过 held-out replay、B0 回归和含 slosh 实物对照之前，暂不改论文方法文档的具体公式和维度。
