## 结论

当前最直接的最小可用修复定为：

> **放弃 `O0 + L22` 作为新主线，仅保留为历史基线；采用 `processed-IMU I0 + fail_closed + common_epoch + explicit actuator OCP`。**

目标不是一次建立完美底盘模型，而是先消除“命令速度等于实际速度”的结构错误，使 MPC 能有效降低执行延迟对 slosh 的影响。

## 显式执行器结构的实现状态

截至 2026-09-03，显式执行器结构已由提交 `5993ffa` 实现：

- 主线 acados 模型改为显式 command/actual 状态；B0 为 `23` 维、Bslosh 为 `27` 维。
- 30 Hz 下线速度和角速度分别使用 `5` 拍、`10` 拍 FIFO；两通道独立使用 `L/tau/K`。
- common epoch 到求解时刻由同一执行器模型和最终已发布命令历史前推。
- 车体与液体只使用 actual 状态；液体纵向激励直接使用执行器方程给出的 `a_actual`。
- `/cmd_vel` 取 horizon 的 `x1.v_cmd/x1.omega_cmd`，不再由 actual 状态重建。
- `explicit_actuator` 与 legacy `fixed_closed_loop/fixed_robot_only` 同时启用时启动失败。
- 新 ABBA 入口只选择新 profile，录制、现场门和分析继续复用已有公共 engine。

## 判断依据

已确认：

- 三包离线结果中，I0 相对 O0 的平均 MAE 下降 `27.69%`，因此保留 processed-IMU I0。
- short100 实物结果中，solver 首拍加速度 P95 达到 `0.600 m/s²`，强正负翻转 `76` 次；顿挫由 solver 命令产生，不是发布链或底盘自行停顿。
- 底盘同时存在启动滞后和渐进建立，且响应随命令幅值变化；legacy `0.15/0.22 s` 纯平移不能表达这段动态。

尚未证明：一组固定执行器参数能够覆盖全部速度范围，也尚未证明执行器失配是 slosh 误差的唯一原因。因此首版结构验证阶段只在主要工作速度附近验证模型，当时不先调 `w_slosh` 掩盖问题。该结构和运行时阶段现已通过单包验收；后续权重 smoke 属于下一层控制连续性修正。

## MVP 只做四项修改

### 1. 完全关闭 legacy L22

关闭整个 `fixed_closed_loop/L22`，机器人状态和液体状态都不再按“命令速度等于实际速度”前推。

关闭 L22 不等于放弃时间补偿：从 common epoch 到 OCP 起点，仍使用最终已发布的 `/cmd_vel` 历史和同一套显式执行器模型前推。显式模型与 legacy L22 必须互斥，同时启用时直接启动失败。

### 2. OCP 区分 command 与 actual

命令状态由优化动作推进：

$$
\dot v_{\rm cmd}=a_{\rm cmd},\qquad
\dot\omega_{\rm cmd}=\alpha_{\rm cmd}
$$

线、角通道分别使用固定延迟、一阶惯性和增益：

$$
\dot v_{\rm actual}
=\frac{K_v v_{\rm cmd}(t-L_v)-v_{\rm actual}}{\tau_v}
$$

$$
\dot\omega_{\rm actual}
=\frac{K_\omega\omega_{\rm cmd}(t-L_\omega)-\omega_{\rm actual}}{\tau_\omega}
$$

不得再把线、角延迟统一取为 $\max(L_v,L_\omega)$。

### 3. 车体和液体统一使用 actual

车体位姿使用预测实际速度：

$$
\dot x=v_{\rm actual}\cos\theta,\qquad
\dot y=v_{\rm actual}\sin\theta,\qquad
\dot\theta=\omega_{\rm actual}
$$

液体激励使用：

$$
a_x=a_{\rm actual}=\dot v_{\rm actual},\qquad
a_y=v_{\rm actual}\omega_{\rm actual}
$$

其中 $a_{\rm actual}$ 直接由执行器方程计算，不再使用 $\Delta v_{\rm cmd}/\Delta t$，也不使用带噪声的 odom 速度差分。

### 4. 发布 command，而不是 actual

`/cmd_vel` 发布 `v_cmd/omega_cmd`。第一拍命令来自：

$$
v_{{\rm cmd},1}=v_{{\rm cmd},0}+a_{{\rm cmd},0}\Delta t
$$

角速度同理，不能再从 $v_{{\rm actual},0}+a_{{\rm cmd},0}\Delta t$ 生成命令。命令初态和延迟队列只由最终 emitted `/cmd_vel` 历史初始化；安全仲裁产生的零命令也必须回写历史。

## 完整闭环

```text
processed-IMU I0 ─┐
                  ├→ common epoch
odom/TF actual ───┘
                        ↓
最终 /cmd_vel 历史 + 显式执行器模型前推
                        ↓
command / actual / delay queue / liquid @ OCP 起点
                        ↓
explicit actuator OCP
   ├→ actual → 车体位姿预测
   ├→ actual → 液体激励与状态预测
   └→ command → 安全仲裁 → 最终 /cmd_vel
                                  ↓
                              回写命令历史
```

## 首版边界与验证顺序

- 在主要工作速度附近先冻结一组 `L_v/L_omega/tau_v/tau_omega/K_v/K_omega`，暂不做幅值调度。
- MVP 可先保留 `a_cmd/alpha_cmd` 为控制量；结构修正后若仍有跨周期翻转，再加入完整时域的 `Delta a_cmd/Delta alpha_cmd` 约束或 jerk 平滑。
- `short100` 只作诊断。模型验证通过后再比较 `167/267/333 ms` 液体代价窗口。

按当前实物证据更新后的验证顺序：

1. literal `B0/Bslosh` Block 1 已完成到 Row02；Row02 暴露运行时硬停车后停止，不补跑 Row03/Row04。
2. 固定 `L/tau/K` 的显式执行器结构保持不变；`190310` smoke 已验证运行时硬停车消除。
3. `192948` 已验证 `w_accel=0.3` 能降低饱和，但不能消除约 `5 Hz` 主动翻转。

## Block 1 后的最小运行时修复

总体顺序固定为：

```text
先消除运行时硬停车
    ↓
再处理 MPC 主动输出的速度锯齿
```

继续冻结以下主线，不回退到 legacy L22：

```text
processed-IMU I0 + fail_closed + common_epoch + explicit actuator OCP
legacy fixed_closed_loop/L22 = off
```

### 第一阶段：只修运行时

1. 将 `/odom` 放入独立 callback queue 和单线程 spinner，subscriber queue 深度设为 `10`。这样 acados 求解超期时，原始 odom 仍可持续进入 planner 历史。
2. 对 `last_odom`、odom history、接收时间和 timing 快照统一加锁；控制周期只复制短快照，不在持锁期间求解或等待 TF。`prev_odom` 只属于单线程 odom spinner，不与控制线程共享。
3. 缓存显式执行器 prefix rollout 的固定子步液体离散模型，避免每个 `10 ms` 子步重复构造矩阵和输出配置日志；非整步尾段仍按实际时长精确传播。
4. 对 acados 部分凝聚参数先做本机软件比较。候选为 `qp_solver_cond_N=5/10/15`，只在无新增求解失败且耗时更低的情况下冻结；生成脚本和 B0/Bslosh solver 必须使用同一取值。

### 第一阶段实现结果

提交 `be8f1ef` 已实现以上四项：

- `/odom` 使用独立 callback queue、单线程 `AsyncSpinner`、队列深度 `10` 和 `tcpNoDelay`；控制线程只读取受锁保护的快照。
- 显式执行器 prefix 的固定 `10 ms` 液体离散模型在启动时缓存；不足 `10 ms` 的尾段使用实际时长精确 ZOH 传播。
- 生成器新增 `--qp-cond-n`，默认读取 `common.yaml`；B0 和 Bslosh 当前生成 JSON 均为 `N=60`、`qp_solver_cond_N=10`。
- ABBA validate-only 会检查两个 solver JSON 和 odom 队列合同，避免配置已改但仍误用旧生成物。

### 最新配对后的限制判断

当前证据不支持“速度或加速度限制太低”是本次负结果的原因：

- B0 与 Bslosh 使用相同的 `v_ref=0.20 m/s`、`v_safe_max=0.25 m/s` 和 `a_max=0.6 m/s²`，但 B0 明显更平稳。
- Bslosh 的 `|a_0|` P95 只有 `0.1674 m/s²`，远低于 `a_max`；两包均无 limiter 或速度安全门介入。
- Bslosh/B0 到点时间比为 `1.0323`，低于 `1.05` 的减速混杂门，不存在明显受限速拖慢的问题。

更可能的机制是：当前液体代价仍驱动约 `5 Hz` 的短周期修正，而完整预测时域内对 `Delta a_cmd`/jerk 的约束不足；执行器或液体模型的相位误差可能进一步放大该现象，但尚未证明为唯一原因。提高速度或加速度上限不能解决这一结构问题，反而可能放大液体激励。下一步应保持现有限制，先增加完整时域控制连续性，再做低速 smoke。
