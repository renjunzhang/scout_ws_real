# 20260901 加速度平滑思路

> 日期：2026-09-01
>
> 性质：失败后的更改路线，不代表相关代码已经实施
>
> 状态：历史过渡记录，已由[唯一主线代码改造方案](../../后续改进/唯一主线/代码改造方案_唯一主线.md)取代；本文保留用于追踪失败原因和决策演变，不作为当前实施入口。
>
> 目标：最终只判断一件事——在速度和到点时间可比的前提下，`Bslosh` 的实物 RGB 晃动是否低于 `B0`。

## 1. 当前判断

本次问题不能简单表述为“把 MPC 从速度控制改成加速度控制”，因为当前 continuous MPCC 已经以加速度为控制量：

```text
状态包含：v、omega
控制量：u = [a, alpha, v_s]

v_dot     = a
omega_dot = alpha
```

控制器当前根据首拍解生成速度命令：

```text
cmd_v     = measured_v     + a0     * dt
cmd_omega = measured_omega + alpha0 * dt
```

因此，当前缺少的不是“加速度控制”，而是以下两部分：

1. **加速度变化率约束**：限制相邻时刻的 `a/alpha` 突变，即 jerk；
2. **实际执行器动态**：区分 MPC 规划的命令状态与底盘延迟、渐进响应后的实际状态。

一句话概括：**OCP 内部的速度状态连续、单拍理想增量受 `a_max·dt` 限制，但每个控制周期又从可能滞后的实测速度重新积分，因此发布命令的跨周期连续性并没有被严格保证；加速度连续性和底盘实际响应也都没有被建模。**

## 2. 本次失败暴露的问题

对应分析：

- [20260901_I0_fail_closed_fixed_closed_loop_B0_Bslosh_Block1分析.md](../实物对比试验分析/20260901_I0_fail_closed_fixed_closed_loop_B0_Bslosh_Block1分析.md)

short100 v2 在路径进度 `10%～90%` 区间内有以下直接证据：

| 指标 | B0 | Bslosh-short100 |
|---|---:|---:|
| `|Δv|` P95 | `0.000218 m/s` | `0.0200 m/s` |
| `|Δv| >= 0.015 m/s` | `0` | `211` 个周期 |
| 首拍 `|a|` P95 | `0.00653 m/s²` | `0.600 m/s²` |
| 首拍加速度饱和占比 | `0` | `31.4%` |
| 强正负加速度翻转 | `0` | `76` 次 |

当前线加速度上限为 `0.6 m/s²`，控制频率约 `30 Hz`，因此饱和加速度对应的单拍速度变化正好是：

```text
0.6 / 30 = 0.020 m/s
```

这与 bag 中的 `|Δv| P95=0.020 m/s` 一致。该 bag 已经把 short100 的发布命令脉冲定位到 solver 输出，并排除了所记录区间内的命令丢帧、solver 超时、输出 limiter 和安全门停车。它能解释现场观察到的命令顿挫，但不能据此断言所有车体实际 jerk 或 RGB 恶化都只有这一个原因。

如果 solver 的相邻重规划首拍 `a0` 从 `+0.6` 翻到 `-0.6 m/s²`，命令侧等效离散 jerk 可达到：

```text
(0.6 - (-0.6)) / 0.0333 ≈ 36 m/s³
```

这个 `36 m/s³` 是由 solver 首拍命令计算出的诊断量，不是车体实测 jerk。它说明优化器允许速度斜率快速翻转，并与锯齿命令和顿挫现象一致。

## 3. 为什么现有平滑项没有阻止翻转

当前 `w_du_a` 只约束本次求解 stage 0 的 `a0` 与上一次求解首拍 `a0` 的差；stage 1 到末端没有完整的 horizon 内 `Δa` 代价，也没有硬 jerk 约束。

因此它只能较弱地抑制“本周期首拍相对上一周期首拍”的变化，不能保证整条预测控制序列满足：

```text
a[k+1] - a[k] 足够小
alpha[k+1] - alpha[k] 足够小
```

本次失败配置中：

```text
w_slosh = 5
w_control、w_smooth、w_du_a ≈ 0.1
```

现象与以下机制假设一致：短时液体目标影响了相邻周期的加减速选择，而现有平滑代价不足以抑制翻转。但当前数据不能唯一排除状态错相、执行器动态缺失等因素，因此这里不把 short100 代价写成唯一根因。

### 3.1 short100 与执行器控制权的结构矛盾

short100 实际计入液体代价的未来节点约为：

```text
33 ms / 67 ms / 100 ms
```

而已测实物响应为：

```text
线速度：纯等待约 80 ms，约 0.26～0.29 s 建立到 90%
角速度：纯等待约 40～80 ms，约 1.52～1.63 s 建立到 90%
```

legacy `fixed_closed_loop` 做的是把**过去已发布命令** rollout 到 L22 初值；它没有在 OCP 中为**本次新优化命令**加入未来执行器响应。solver 仍按 `a/alpha` 立即改变车体和液体激励来优化。

因此，在 solver 眼中，本次决策能立刻影响 33～100 ms 的液体状态；在实车中，线速度新动作到窗口末端附近才开始明显生效，角速度更不可能在 100 ms 内充分建立。这是“共同状态时刻 + 显式执行器模型”成为主路线的强机制依据，但两包数据仍不足以把它证明为唯一根因。

显式执行器模型上线后，不能机械保留 short100 并直接开始效果实验。若新决策在可信的 100 ms 内几乎没有控制权，需要在冻结方案前比较三种处理：

1. 用新实物数据验证更长时间内的液体预测，能验证到哪里就把有效代价窗口延长到哪里；
2. 在预测中保留已知命令/执行器 delay prefix，并在可信窗口末端加入可解释的 terminal cost；
3. 如果两者都做不到，承认 short100 只能用于状态诊断，不能承担主要闭环抑晃目标。

## 4. 0705 正向结果应如何借鉴

不建议直接回退到 0705 代码或原样复现 0705 的 `B_ours`。可以借鉴的是它的**强平滑机制**，不能把其正向结果直接归因于液体状态反馈。

0705 的 `B_ours` 大致采用：

```text
w_control = 0.3
w_smooth / w_alpha / w_du_a ≈ 1.0
w_slosh = 5
```

其 RGB 在路径进度 `10%～90%` 内相对 B0 改善约 `29%`，但到点时间慢约 `12.8%`。0705 的 literal `B_slosh` 虽有约 `10.7%` 的 RGB P95 改善，RMS 只改善约 `0.6%`，同时到点慢约 `9.2%`。

按照当前“到点时间比不超过 `1.05`”的可比性门槛，这些结果都存在减速混杂。

0706 当天的直接对照显示：

```text
B_ours 相比 B_smooth：
RGB P95 / max / RMS 分别约高 3.1% / 3.8% / 2.4%
```

这说明 0706 当天 `B_ours` 的 RGB 没有优于 smooth-only，因而削弱了“0705 的改善主要来自液体反馈”的解释。但 0705 到 0706 的同方法 RGB P95/RMS 变化可达约 `85%/70%`，不能用跨日数据直接证明 0705 的收益主要来自哪一项。严谨结论仍是：0705 是平滑、减速、液体反馈和旧链路的组合结果，必须用同日 matched 对照重新拆分。

此外，0705 的控制侧同时包含旧 odom observer、旧代码链和 legacy `fixed_closed_loop`；测量侧还使用旧 RGB 流程。前者改变控制行为，后者改变评价口径，两类变量都妨碍直接回退后的因果解释。

## 5. 近期最小筛查：先止住控制振荡

### 5.1 先明确现有 matched 合同

仓库已有 development 配置：

```text
B_slosh_matched0
B_slosh_matched5
```

两者公共权重为：

```text
w_control = 0.3
w_smooth = 1.0
w_alpha = 1.0
w_du_a = 1.0
w_du_vs = 1.0
```

液体代价只作用于 short100 的 state stages `0..3`。两者使用同一 10D solver，唯一代价差异是 `w_slosh=0/5`。

必须注意：当前 C++ release contract 强制 matched 变体使用：

```text
processed_imu + fail_closed + common_epoch + delay_phase=shadow
```

如果把 matched0/matched5 与 `fixed_closed_loop` 组合，程序会 fail-fast。这个保护不能为了快速试验而拆除。因此它们不是刚失败的 legacy L22 方案的“强平滑换权重版”，而是关闭 legacy 闭环前推后的另一条 development 链路。

### 5.2 同 snapshot 只做点态安全门

近期先不修改正式默认值，也不直接上实车。利用本次 v2 的输入 snapshot，离线比较三组：

| 组别 | solver | 强平滑 | `w_slosh` | 回答的问题 |
|---|---|---:|---:|---|
| literal B0 | 6D | 否 | 0 | 当前点态基线 |
| matched0 | 10D | 是 | 0 | 10D/强平滑在相同输入上的点态影响 |
| matched5 | 10D | 是 | 5 | 加入 slosh 代价后是否立即产生危险首拍 |

离线筛查首先看：

1. solver 成功率、非有限值和求解时间；
2. 首拍加速度饱和占比；
3. 相对当前实测状态的首拍命令增量；
4. matched0 与 matched5 在相同 snapshot 上的首拍控制差异。

在做反事实比较前，必须先用 bag 的原配置回放，并在明确容差内复现在线的 solver input、首拍控制和预测 horizon。若这一步不一致，说明 replay 合同不完整，后续候选比较无效。

建议在运行前冻结一个保守的 development 入口门：

```text
solver success                 = 100%
non-finite                     = 0
solver time P95                < 25 ms（30 Hz 周期的约 75%）
首拍 |a0| 达 ±0.6 饱和的占比  <= 5%
首拍 |a0| P95                  <= 0.30 m/s²
```

这些阈值只是避免把明显激进的候选送上车，不是 RGB 效果阈值。

固定 snapshot 没有按新策略更新下一时刻车体和液体状态，因此不能评估新闭环的 tracking、到点或 RGB。单点独立求解也不能评估跨周期翻转。

如果按时间顺序 replay，并为 B0、matched0、matched5 各自独立保留 `u_prev`，可以再加一层保守的“外生状态序列连续性门”：

```text
路径 10%～90% 的 |Δv| P95      <= 0.005 m/s
|Δv| >= 0.015 m/s 的周期数     = 0
强正负首拍加速度翻转次数       = 0
首拍加速度饱和占比             <= 5%
```

即便通过，这些相邻量仍来自原轨迹的外生状态，不是候选策略生成的新闭环轨迹，只能作为上车前告警门。

判定原则：

- 如果 matched0 已在点态入口门失败，不上车；
- 如果 matched0 通过、matched5 失败，只能说明当前 slosh 候选仍过于激进，不上车；
- 两者通过只代表具备后续 smoke 的必要条件，不代表闭环已经稳定。

### 5.3 执行器模型前只做 matched0 低速 smoke

下一次实车最多先运行一次现有 `matched0`：

```text
variant          = B_slosh_matched0
w_slosh          = 0
v_ref            = 0.10 m/s
delay_phase      = shadow
experiment type  = development smoke
```

它只验证 10D solver、common epoch、processed IMU 链和强平滑命令能否安全闭环，不测试液体反馈效果。建议冻结以下 smoke 门：

```text
solver failure / non-finite                = 0
安全停车、发布后 limiter 污染              = 0
路径 10%～90% 的 |Δv| P95                  <= 0.005 m/s
|Δv| >= 0.015 m/s 的周期数                 = 0
首拍加速度饱和占比                         <= 5%
强正负首拍加速度翻转次数                   = 0
tracking / 到点                            通过现有 C02 postflight 门
```

这些阈值由失败 v2 的 `0.020 m/s`、`31.4%` 和 `76` 次翻转向下收紧，用作安全 go/no-go；如果实际噪声底证明阈值不合理，应先用数据修订并重新冻结，不能跑完后为保留结果而改门。

在显式执行器模型完成前，不建议直接运行 matched5 的 RGB 效果比较。因为 legacy L22 已处于 shadow，而新的底盘响应模型尚未进入 OCP，液体未来激励与实车实际动作的时间关系仍未闭合。此时 matched5 即使正向或负向，也仍是难以解释的组合结果。

### 5.4 matched 对照应怎样解释

显式执行器模型完成后再运行 matched0/matched5：

- 同一执行器模型下的 `matched0 vs matched5`，配合平衡顺序，才用于估计 slosh 代价的增量作用；
- 共用命令与执行器模型的 `B0 vs matched5` 回答完整 Bslosh 系统相对 B0 的效果；
- 单次固定顺序的三臂运行只可作 development go/no-go，不能声称因果隔离；
- 只有 RGB P95 和 RMS 同向降低、到点时间比不超过 `1.05`、tracking 与命令连续性均过门，才进入正式 ABBA。

matched pair 可复用既有 G3R3 平衡顺序，而不是重新设计固定三臂因果协议：

```text
Block 1: M0, M5
Block 2: M5, M0
Block 3: M0, M5
```

但显式执行器模型会形成新的代码 release 和协议 ID，不能让新数据冒充旧 G3R3 数据续跑。

实车资格门可复用既有 G3R3：

```text
每条到点时间       <= 42 s
contour P95         <= 0.05 m
yaw P95             <= 0.15 rad
solver time P95     < 25 ms
solver failure、fallback/reset、安全门、limiter 污染 = 0
候选/B0 到点时间比 <= 1.05
```

RGB 晋级门同样复用既有 development 标准：

```text
mean(Delta_P95_block) >= 0.10 mm
至少 2/3 block 的 Delta_P95 > 0
Delta_P95 中位数 > 0
删除任一 block 后剩余均值仍 > 0
mean(Delta_RMS_block) >= 0
```

命令连续性是安全和机制门，最终是否正向仍由同日 RGB 裁决。

强平滑权重属于短期止血措施。它可以避免再次上车验证一个明显 bang-bang 的控制器，但不能修复计划动作与实际动作的错相，也不能替代执行器建模。

## 6. 正式修改：共同状态时刻与执行器模型

长期修改应与以下方案合并推进：

- [20260831_共同状态时刻与执行器延迟模型实施思路.md](20260831_共同状态时刻与执行器延迟模型实施思路.md)

### 6.1 区分命令状态和实际状态

建议将模型明确拆成两层：

```text
命令层：
v_cmd_dot     = a_cmd
omega_cmd_dot = alpha_cmd

执行器层：
v_actual_dot =
    (K_v * delayed(v_cmd, L_v) - v_actual) / tau_v

omega_actual_dot =
    (K_omega * delayed(omega_cmd, L_omega) - omega_actual) / tau_omega
```

参数含义：

- `L_v / L_omega`：线速度、角速度的纯延迟；
- `tau_v / tau_omega`：延迟后的渐进响应时间常数；
- `K_v / K_omega`：稳态增益；
- 线速度和角速度分别建模，不把角速度约 `1.5～1.6 s` 的慢建立过程全部误认为纯延迟。

命令状态必须有明确的时间合同，例如：

```text
v_cmd(t0) / omega_cmd(t0) = 本次发布、时间戳为 t0 的命令
执行器 delay line         = 只预测该命令何时影响 actual state
```

离散实现到底发布 stage 0 还是首个积分后的 stage 1，必须在编码前冻结，并用单元测试验证时间戳、首拍和 delay prefix 的对应关系。核心是 `/cmd_vel` 来自定义清楚的命令状态，不再隐含使用：

```text
measured_v + a * dt
```

这种把实测实际状态与理想命令增量混在一起、且命令时刻不清楚的表达。

液体未来激励则应使用执行器模型预测的实际运动：

```text
纵向激励：v_actual_dot
横向激励：v_actual * omega_actual
```

而不是直接假设理想 `a_cmd/alpha_cmd` 已经被底盘瞬时实现。

### 6.2 引入真正的 jerk 约束

执行器模型解决“计划动作与实际动作错相”的问题，但它本身不保证命令不在相邻周期 bang-bang。要保证命令平滑，还需要把命令加速度作为状态、jerk 作为新控制量：

```text
a_cmd_dot     = j_v
alpha_cmd_dot = j_omega

|j_v|     <= j_v_max
|j_omega| <= j_omega_max
```

这里保留两个候选，不在数据不足时预先指定唯一实现：

1. 完整 horizon 的 `Δa/Δalpha` 软代价，改动较小，适合先检查求解稳定性；
2. `a_cmd/alpha_cmd` 状态加 `j_v/j_omega` 软/硬约束，物理意义更清楚，但会增加状态和控制维度。

先用离线闭环、求解时间和实车噪声底决定采用哪一级；若软代价不能可靠通过命令连续性门，再升级为显式 jerk 状态和界限。

### 6.3 时间基准与 legacy 链路

状态时刻统一后：

- processed IMU 的 I0 作为共同 `t0` 的液体初值；
- 机器人状态、液体状态和执行器历史均对齐到同一 `t0`；
- 不再在 solver 外把 I0 额外前推为 L22 后又在 solver 内使用执行器延迟模型；
- legacy `fixed_closed_loop/L22` 只保留 `shadow/off` 用于审计，避免双重补偿；
- B0 与 Bslosh 必须使用相同执行器模型和相同命令生成链，唯一核心差异仍是 slosh 反馈/代价。

### 6.4 模块边界

正式实现应按职责拆分，避免把补偿、命令生成和液体预测继续堆在 solver wrapper 中：

```text
StateTimeAligner
  统一机器人、IMU、液体初值和命令历史的 t0

ActuatorDynamicsModel
  负责 L、tau、K 和命令状态到实际状态的预测

CommandSmoothnessModel
  负责 a_cmd/alpha_cmd 状态与 jerk 约束

SloshExcitationAdapter
  只从预测的实际运动生成液体模型激励

CommandPublisher
  发布 solver 的命令状态；输出 limiter 只作为最后安全层
```

输出 limiter 不能作为主要平滑手段，否则会再次出现：

```text
solver 以为执行的是 solver_cmd
实车实际执行的是 limited_cmd
```

这会扩大模型与实物之间的偏差。若安全层触发，必须有独立诊断话题并在实验有效性检查中标记。

## 7. 推荐实施顺序

### Stage 0：冻结失败证据

- 保留 v1、v2 的 bag、配置快照和自动判定；
- 不修改或选择性替换失败配对；
- 将加速度翻转指标作为后续版本的回归基线。

### Stage 1：同 snapshot 强平滑筛查

- 离线运行 B0、matched0、matched5；
- 先排除非有限值、求解超时和点态饱和风险；跨周期翻转留给闭环 smoke 判断；
- 该阶段原则上只增加 development 配置和分析，不修改正式默认值。

### Stage 2：低速 10D matched0 smoke

- 只运行 `matched0 + shadow + v_ref=0.10 m/s`，确认 10D solver、命令连续性、跟踪和到点；
- `w_slosh=0` 可避免把液体代价问题与 10D/控制链问题混在一起；
- 出现顿挫、solver failure 或任何非预期 limiter 触发立即停止；
- 此阶段不运行 matched5，不判断 RGB 效果。

若本阶段因命令翻转失败，停止后续实车，把 Stage 4 的 horizon 平滑/jerk 工作前移，完成后重新通过 Stage 1/2。Stage 3 的执行器模型可以作为独立模块继续离线开发，但不能用它跳过命令连续性门，更不能直接上 matched5。

### Stage 3：共同 `t0` 与分通道执行器模型

- 使用已测得的纯延迟和渐进响应分别辨识 `L、tau、K`；
- 统一机器人、液体和命令历史的状态时刻；
- 关闭 solver 外的 legacy L22 主路径，保持 `shadow/off` 审计；
- 先用命令阶跃与冻结数据验证 predicted actual 是否优于当前模型；
- 重新评估 short100 内的实际可控性，再冻结液体代价窗口或 terminal cost，不能默认沿用 100 ms。

### Stage 4：完整 horizon 平滑或显式 jerk

- 先实现完整 horizon 的 `Δa/Δalpha` 候选并检查求解条件；
- 如果仍不能稳定通过连续性门，再新增 `a_cmd/alpha_cmd` 状态和 `j_v/j_omega` 控制；
- 离线验证 horizon 内连续性和闭环重规划连续性；
- B0、matched0、matched5 同步使用同一命令/执行器模型。

### Stage 5：matched0 / matched5 development 配对

- 在相同 10D solver、强平滑和显式执行器模型下只改变 `w_slosh`；
- 采用配对和反序，避免把固定顺序当作因果证据；
- 先看 RGB P95/RMS 方向、到点时间、tracking 和命令连续性；
- 若 matched5 不优于 matched0，不继续只调 `w_slosh`。

### Stage 6：回归与正式实验

- B0、10D `w=0`、Bslosh 共用同一执行器模型；
- 完成静止、无运动、低速跟踪和故障回退测试；
- development 结果正向后，再执行预注册 ABBA；
- 最终以 RGB P95/RMS、到点时间、tracking 和命令连续性共同判定。

## 8. 决策边界

当前建议是：

1. **不直接回退 0705**：变量过多，且存在明显减速混杂；
2. **不把任务称为“改成加速度控制”**：当前已经是加速度控制；
3. **先离线验证强平滑**：它只是一道点态安全门，不代表新闭环已稳定；
4. **执行器模型前只做 matched0 低速 smoke**：不提前用 matched5 声明液体反馈效果；
5. **正式路线是执行器模型 + horizon 平滑/jerk**：两者分别解决错相和命令突变，不能互相替代；
6. **唯一成功标准不变**：Bslosh 必须在运行时间可比、跟踪正常且无安全层污染的条件下，使实物 RGB 优于 B0。
