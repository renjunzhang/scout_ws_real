# Full 首弯停滞与预算停车定位修复（2026-09-18）

本轮承接 `feat/spmpc-liquid-control` 的 `577e4c47`。用户授权用两小时排查；仅本地中文提交，不 push，不录新视频，不改隔离仿真的 world/map/launch/scripts。实验输出写入 `/data/a/scout_sim_replacement/results/`。

## 1. 结论与保留修改

**原 Full 首弯停滞的主因是低速曲率变化代价过强；N60 还有独立的在线计算预算问题。** 不是“slosh 算不出来”，也不能简单归结为仿真不需要延迟补偿。

本轮保留四项小修改：

1. `planned_slosh` 的 `curvature_rate_weight`：`0.01 → 0.0001`。保留非零平滑代价、贴线权重 1、slosh 权重 5 和末端目标权重 2，全程终点吸引仍为 0。
2. 默认 `horizon_steps`：`60 → 40`，控制仍为 30 Hz，即 1.33 s 窗口。YAML、C++ 默认、生成 solver 与代价归一化、ROS/native 运行物一致；**本轮不再恢复 N60**。
3. 参考构建中只跳过相邻且进度值完全相等的重复查询，不改计划、时间选择或插值误差门限。
4. TF 精确查询失败、随后最新 TF 已超过目标时刻时，再进行一次非阻塞精确查询；失败诊断记录实际锚点时间差。10 ms 外推限值与拒绝规则保留。

Full 始终是原 `planned_slosh`：完整可行诊断计划、progress 参考、28 维车辆/执行器/液体模型。没有改为此前的“raw B0 框架加 slosh”。当前已有到点证据，仍不能称为实物验收或正式防晃效果验证。

## 2. 首弯为什么会不动

原 N40 失败例的 20～43 s 共 690 周期均正常求解，无预算耗尽，却持续低速旋转。43.667 s 时，45 s 硬截止进入 1.33 s 预测窗口，机器人还距终点约 4.16 m，才出现到点约束不可行。因此，后面的求解失败是长期停滞的后果。

瞬态回看：3～5 s 实际航向落后计划，6～8 s 转过头并减速，约 10 s 后线速度接近零，但角速度仍约 0.05 rad/s。30 s 时实际 yaw 约 2.334 rad，计划切线约 0.585 rad。计划拟合切线与计划记录 yaw 一致，没有发现插值把路线方向算反。

`planning_terms.py::geometry_terms()` 用正则化速度定义曲率变化。静止附近，该项的角加速度平方系数在 running cost 除 N 之前约为：

```text
curvature_rate_weight / (v_scale × speed_regularization³)
原值：0.01   / (0.8 × 0.05³) = 100
新值：0.0001 / (0.8 × 0.05³) = 1
```

原设置让低速转向纠偏过于昂贵，配合 progress 参考的隐式位置跟踪，进入低速局部停滞。关闭液体代价或增加 RTI 次数的冻结状态试算没有恢复前进；**只关闭曲率变化项，就在相同计划、任务和 N40 运行库下完成闭环；随后改为非零 0.0001 也完成**。这是保留小权重而非继续盲目加算力的依据。

冻结状态试验只恢复了 snapshot 中的 primal 状态，未恢复 dual/求解器全部内部量，属于方向性诊断；单因素闭环是更强的证据。

## 3. 为什么还会预算停车

### 3.1 N60 的在线余量不足

将权重改为 0.0001 后，N60 能通过首弯并接近终点，但一次复验出现 19 次预算耗尽、9 次命令过期，最终位置误差 3.37 cm、朝向误差 13.85°，45 s 内未到点。预测更长并不自动意味着该机在 30 Hz 下更稳定。

因此将已通过闭环的 N40 设为默认。该 N60 试验发生在下面的参考查询优化之前；本轮未再测优化后的 N60，不能声称 N60 必然无法运行。

### 3.2 N40 的尾段准备耗时有无效重复

首次切默认 N40 并重编后，43.664 s 到点，但末段出现两次预算停车：

| cycle | setup | 剩余预算 | 最近 RTI 估计 | 本轮 RTI 次数 |
| --- | ---: | ---: | ---: | ---: |
| 1129 | 9.737 ms | 15.134 ms | 15.759 ms | 0 |
| 1188 | 11.456 ms | 14.578 ms | 19.971 ms | 0 |

完整计划 1501 行，其中末尾 301 行的 progress 完全相同。`HorizonReferenceBuilder` 校验插值误差时对同一个 `(progress, time)` 重复查询，查询内部还扫描停车平台段。

现在每个插值窗口只检查不同的进度值，保留末段按时钟选择实际剩余速度的行为：

- 7 个真实录制状态、每个 41 节点，mode、nominal_time、phase、s/x/y/v/vs knots 共 287 条记录，十六进制浮点逐值完全一致。
- 末端参考构建 P50 从约 2.95～2.98 ms 降到 0.388～0.395 ms，约 7.5 倍；前段本来只需约 0.25～0.34 ms，没有加速收益。
- 增加长重复尾段测试，核对同一 progress 在不同 elapsed 时仍选择正确速度和节点时刻。

后续一次 Full 无预算耗尽或命令过期，但仍捕获一次 TF 对齐拒绝，见下一节。

## 4. TF 对齐急停及验证边界

参考查询优化后，任务 13.417 s 的 cycle 427 因 `TF_POSE_PROPAGATION_LIMIT` 拒绝，随后一次 `STOP_JERK_HISTORY_INFEASIBLE`。发布速度从 0.1563 m/s 清零，13.507 s 恢复 OCP；模型液面在 13.673 s 达 3.178 mm。不能将这个成功到点例描述为全程无急停。

该周期目标时刻 52.986 s，控制起始 52.990 s；对齐只耗时 0.070 ms，尚未求解 OCP。旧代码在传播失败时未记录锚点年龄，bag 的 TF 接收时序也不等于节点内 buffer 更新时序，**无法从该包证明锚点究竟过旧还是已晚于目标**。

代码中确认存在一个可复现竞态：第一次精确查询因目标稍晚而失败；TF listener 随后更新；第二次 Time(0) 返回晚于目标的锚点。旧代码仍调用只能向前传播的函数，因此因负 age 拒绝。

修复后，新于目标的 TF 只用来触发再次精确查询，不把其位姿冒充目标位姿；目标仍无历史时继续拒绝。恰好等于目标或全静态链可直接使用。失败时记录有符号锚点年龄，便于后续区分真正断流。

受控回归直接提取前后两个生产 `robotStateAtEpoch()` 函数体，使用真实 `tf2::BufferCore`，只在 exact/latest 查询间注入新 TF。7 种场景覆盖正常精确、5 ms 可传播、15 ms 超限、新 TF 竞态、恰好目标、静态链、目标早于全部 TF。旧版本复现竞态拒绝；新版本返回正确目标位姿，且过旧/无历史仍拒绝。测试代码与前后输出归档于 `20260918_full_tf_epoch_retry/`，未为测试引入新的生产抽象。

这消除了确定存在的代码竞态，但不等于证明此前那一次急停必由它引起；真实输入过旧依然会安全拒绝。

## 6. B0、Full、仿真与实物的解释

- B0 `raw_mpcc`：原路线和巡航速度参考，24 维车辆/显式执行器状态，不含下层液体决策及新增几何目标。
- Full `planned_slosh`：消费完整诊断计划和随进度变化的速度参考，28 维，再加几何/液体目标。两者都经过时间对齐、预测约束、停车尾段核验和发布门。
- Full 最终例对蓝色计划的移动段距离 P95 为 2.51 cm（前两到点例约 2.3 cm）；对绿色原任务路线为 19.06 cm，是计划本身缓弯后的几何差异，不应混称为约 2.5 cm 原路线跟踪误差。
- 当前模拟使用辨识执行器适配器，延迟/FIFO 本轮没有关闭。此前 legacy 的 `DELAY_PHASE_MODE=off` 不能直接等同于去掉当前显式执行器模型。权重单因素试验在同一执行链下就能恢复运动，因此本次首弯停滞不支持“先去掉延迟补偿”这个解释。
- B0 R03 约 31.41 s、模型液面峰值 1.00 mm；Full 约 41～44 s，路线、速度策略和耗时不同。不能仅用峰值宣称 slosh 权重带来了百分比收益。
- 当前 `planned_mpcc` 仍保留旧 contour=.02、rate=.01、全程 goal=2；与 Full 已不只是液体项不同。已同步配置说明，未擅自把未验证 profile 改成另一套参数。
