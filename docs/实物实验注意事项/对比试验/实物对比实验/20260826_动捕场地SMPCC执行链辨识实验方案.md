## 0. 一眼看懂

本实验不在动捕场地复现大场地 G3R3，也不直接证明减晃有效。它只利用一条紧凑、可重复的 S 路径，把 S-MPCC 从“计划”到“实车运动”的执行链测清楚。

```text
第一次人工点击终点，选择安全的紧凑 S 路径
                    ↓
              保存并冻结该路径
                    ↓
       同一配置、同一路径重复运行 3～5 次
                    ↓
同步记录 MPC horizon、控制审计、/cmd_vel、odom、IMU、动捕 pose
                    ↓
  分析计划覆盖 → 软件改命令 → 底盘执行延迟 → 传感器误差
                    ↓
为大场地 G3R3 提供执行链模型和可解释的误差边界
```

三层核心证据：

```text
上一周期计划 k=1 → 当前周期重新规划 k=0
        当前 solver command → 最终发布 /cmd_vel
                 最终 /cmd_vel → 动捕真实 v / omega
```

| 要回答的问题 | 主要数据 | 得到的结论 |
| --- | --- | --- |
| 原计划动作是否被下一周期覆盖 | previous `k=1`、current `k=0` | 滚动重规划替换量 |
| 控制器输出是否被软件层修改 | solver、terminal、post-gate、published command | terminal、安全门、限幅器介入量 |
| 最终命令是否被底盘及时实现 | published `/cmd_vel`、动捕 pose | 线/角通道延迟、增益和时间常数 |
| odom/IMU 能否在大场地代替动捕做诊断 | 动捕、odom、IMU | odom/IMU 的偏差、相位和可信边界 |

## 1. 为什么单独在动捕场地做

动捕场地不足以容纳 G3R3 的完整 H0 路径，但执行链辨识不要求复现大场地起终点。它只要求：

1. 路径在动捕有效区域内；
2. 同时包含左转和右转，使角速度出现正负变化；
3. 包含起步、正常跟踪和减速，使线速度有足够变化；
4. 路径、控制配置和载荷能够重复；
5. 动捕、控制、odom 和 IMU 的时间戳可追溯。

因此可以在 RViz 中人工点击一个终点，让 S-MPCC 跟踪紧凑 S 路径。终点的绝对坐标不是研究变量，但正式记录时不能每条随意选择不同终点。

本实验与 G3R3 的分工为：

| 实验 | 场地 | 回答的问题 |
| --- | --- | --- |
| 本协议 | 小型动捕场地 | 命令是否被修改、底盘是否迟滞、odom/IMU 是否可信 |
| G3R3 | 正常实物场地 | 短可信时域液体代价是否真实降低 RGB 液面响应 |

## 2. 实验边界

### 2.1 本实验负责

- 测量上一周期 `k=1` 计划与当前周期 `k=0` 动作的一致性；
- 测量 solver command 到最终 `/cmd_vel` 的软件层改变量；
- 测量最终 `/cmd_vel` 到动捕真实线速度、角速度的响应；
- 分别估计线速度与角速度通道的延迟、稳态增益和一阶时间常数；
- 用动捕校验 odom 与 IMU 的幅值、符号、时间偏移和相位；
- 给大场地 G3R3 的离线解释提供执行链参数及不确定性。

### 2.2 本实验不负责

- 不把动捕接入 S-MPCC 控制闭环；
- 不用动捕替换 `/odom`，也不发布控制用 TF；
- 不比较 Matched0/Matched5 的真实液面效果；
- 不把小场地数据计入 G3R3 的 6 条 development trial；
- 不用 IMU 加速度积分得到线速度真值；
- 不因一次运行的单个峰值就宣布延迟参数已经冻结；
- 不把 Wi-Fi 网络传输延迟全部误认为底盘执行延迟。

若后续把本实验辨识出的执行器模型接入 S-MPCC，必须建立新的代码 release 和协议 ID，不能继续沿用原 G3R3 release。

### 3.1 路径选择规则

第一次人工点击终点只用于选择路径，不计入正式数据。候选路径必须满足：

- 全程位于动捕可靠覆盖区，并给停止距离和定位误差留出余量；
- 机器人、容器和 Marker 不会进入遮挡区；
- 至少包含一个左转段和一个右转段；
- 中间存在明确的角速度换向；
- 起步和停止之外，至少有一段正常 tracking；
- 不贴墙、不穿障碍、不要求临场人工修正；
- 试跑后保存实际 reference/global path，记录目标 pose 与路径哈希。

如果无法保存路径，最低要求是保存每条实际 global/reference path，并设置几何一致性门。路径不一致的 trial 只能作为探索数据，不能合并辨识。

## 7. 离线分析

### 7.1 先统一坐标与时间

1. 使用冻结的动捕刚体到 `base_link` 静态外参；
2. 将动捕位置和姿态统一到车体 `x` 前、`y` 左、`z` 上；
3. 以原始 VRPN pose 为可追溯真值输入；
4. 记录 raw pose 到 bridge pose 的时间差与网络帧间抖动；
5. 先估计 IMU—动捕时间偏移，再估计 command—真实运动延迟；
6. 禁止用 bag arrival order 代替消息时间戳对齐。

Wi-Fi VRPN 默认可能使用接收端 ROS 时间，因此动捕链路包含网络和调度延迟。本协议最终报告必须把以下两项分开：

```text
cmd → received mocap response 的观测延迟
Wi-Fi/VRPN 时间不确定性
```

只有时间同步和时间戳语义通过验证后，才能进一步解释为底盘物理执行延迟。

### 7.2 第一层：滚动计划是否被覆盖

对相邻有效 control cycle 比较：

```text
previous horizon k=1  ↔  current solver u0
```

报告：

- `a` 与 `alpha` 的替换量分布、RMSE 和 P95；
- 符号一致率；
- 左转、右转、角速度换向和直线段的分段结果；
- 计划更新时间与 control period；
- 禁止跨 solver failure、安全门或 terminal cycle 配对。

替换量大说明远期动作在真正到达第一控制步之前已被重新规划覆盖。这是滚动计划一致性问题，不是底盘延迟。

### 7.3 第二层：软件是否修改命令

逐周期比较：

```text
solver_cmd
  → terminal_cmd
  → post_gate_cmd
  → published_cmd
```

分别计算：

```text
Delta_v_terminal / Delta_omega_terminal
Delta_v_gate     / Delta_omega_gate
Delta_v_publish  / Delta_omega_publish
```

报告每一层介入率、最大改变量、P95 和发生阶段。正常 tracking 段与 terminal 段必须分开：接近终点时 terminal controller 可能有意接管，不能把该行为误判为 solver 输出错误。

### 7.4 第三层：底盘是否实现最终命令

从动捕 pose 使用固定平滑器导出：

```text
v_mocap(t)      = 车体纵向速度
omega_mocap(t)  = yaw rate
```

优先比较：

```text
published v_cmd      → v_mocap
published omega_cmd  → omega_mocap
```

第一候选模型为：

```text
tau_v     * d(v_mocap)/dt     + v_mocap     = K_v     * v_cmd(t - d_v)
tau_omega * d(omega_mocap)/dt + omega_mocap = K_omega * omega_cmd(t - d_omega)
```

至少比较：

- 纯延迟；
- 一阶；
- 一阶加纯延迟；
- 数据明确支持时，再考虑死区或饱和。

不能只用一次互相关峰值。每个方向至少保留命令变化时刻、首次明显响应、过零点、峰值和稳态段，并报告各重复 trial 的参数稳定性。

使用 `R01～R03` 拟合，`R04～R05` 做 held-out 验证。只有验证集上的时域误差、相位和参数稳定性通过，才能冻结执行器模型。

### 7.5 第四层：校验 odom 与 IMU

分别比较：

```text
odom v             ↔ v_mocap
odom omega         ↔ omega_mocap
IMU omega_z        ↔ omega_mocap
IMU a_x / a_y      ↔ 动捕导出的 IMU 点加速度
```

结论边界：

- 线速度以动捕导出速度为真值，odom 为待校验量；
- 角速度由动捕与 IMU `omega_z` 交叉验证；
- IMU acceleration 是 specific force，必须处理坐标、重力、零偏和杠臂；
- 不将 IMU 加速度积分为线速度真值；
- 主场地无动捕时，只能把校验后的 odom/IMU 作为迁移诊断量，并携带本实验给出的误差范围。

| 观察结果 | 解释与下一步 |
| --- | --- |
| previous `k=1` 与 current `k=0` 差异大 | 滚动计划被覆盖；先处理计划一致性，不归因于底盘 |
| solver 与 published command 不一致 | 查 terminal、安全门、限幅器或发布链；不进入执行器辨识结论 |
| published command 与动捕响应有稳定延迟 | 支持辨识 `M_actuator`，用 held-out trial 验证 |
| 延迟随 trial 或方向剧烈变化 | 检查地面、轮胎、负载、网络时间、死区和饱和；暂不冻结单一延迟 |
| odom 与动捕稳定一致 | 大场地可把 odom 作为线/角速度主要诊断量，但仍报告校准误差 |
| IMU `omega_z` 与动捕一致 | 大场地可用 IMU 辅助判断角通道动态 |
| IMU 加速度与动捕不一致 | 先修 frame、重力、bias、杠臂或时间对齐，不直接修改液体模型 |
| Wi-Fi 时间抖动过大 | 延迟结论 `INCONCLUSIVE`；改用有线或可靠服务端时间同步 |

### 8.1 本协议完成条件

同时满足以下条件，才可写成“执行链辨识完成”：

1. 至少 `3` 条有效重复 trial，推荐 `5` 条；
2. 同一路径、同一 variant 和同一公共配置；
3. 三层命令链均能按 cycle/time stamp 联结；
4. 动捕数据连续，坐标、刚体和时间戳语义有记录；
5. software command intervention 已明确解释；
6. 线/角执行模型在 held-out trial 上仍有效；
7. odom/IMU 相对动捕的误差边界已报告；
8. 已明确哪些参数可以迁移到大场地，哪些只适用于当前地面和速度范围。
