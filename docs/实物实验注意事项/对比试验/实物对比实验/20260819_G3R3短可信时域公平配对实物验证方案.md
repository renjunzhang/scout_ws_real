## 1. 本次要回答的问题

本次只回答一个主问题：

> 在同一 10D liquid solver、同一 processed-IMU 状态源、同一路径、同一参考速度和完全相同公共控制权重下，仅开启短可信时域内的液体代价，是否能让 `Matched5` 相对 `Matched0` 稳定降低真实 RGB 液面响应，同时不破坏跟踪、安全和实时性？

主物理指标是在线 RGB 标量得到的 `H_vis`，内部模型指标只能作为机制解释，不能作为效果自证。还要利用本轮新增的逐周期审计回答三个诊断问题：

1. 上一周期计划的 `k=1` 与下一周期实际重新规划的 `k=0` 有多一致；
2. raw OCP command 到最终发布命令之间是否仍被软件层修改；
3. 最终发布命令到实际 processed-IMU 激励之间有多大延迟、幅值误差和相位误差。

每条执行前：人工回起点并对齐，保持液体静稳至少 `10 s`，确认在线 RGB 已稳定锁零至少 `2 s`，急停保持在手边。然后只修改 `MATCHED_ROW`：


按表依次运行 `01 → 02 → 03 → 04 → 05 → 06`。正常情况下不要提前 `Ctrl+C`；脚本最长录制 `70 s`，应覆盖启动、完整运动以及到达后的液面衰减段。出现人车风险时安全优先，立即急停或停止命令，但仍保留已产生的失败数据。

每条结束后必须确认：

1. `.bag.active` 已闭包为 `.bag`；
2. 同名 `_short_horizon_postflight.json` 已生成；
3. postflight 中 `"pass": true` 且脚本返回码为 `0`；
4. 没有 image topic、solver failure、state epoch 失败、fallback、命令合同违反或安全门拒绝。

未满足任一项时不要启动下一 row。

## 7. 单条数据有效性

runner 后的自动 postflight 负责检查采集和软件合同，至少包括：

- `cycle_id` 唯一且严格递增，audit、snapshot 和 horizon 可联结；
- 至少 `30` 个 audit cycle、`10` 个 solve cycle，并有足够有效 snapshot/horizon；
- variant、processed-IMU source、公共权重和本 row 的 `w_slosh` 身份正确；
- solver 成功、processed-IMU excitation audit 有效、命令确实发布；
- robot/liquid 对齐到同一 solver epoch，raw skew 不超过 `80 ms`；
- stage `0..3` 的液体权重正确，stage `4..60` 严格为 `0`；
- shared limiter 未介入，发布前命令合同无违反；
- terminal controller 如有介入，只能发生在 terminal phase 且必须被显式标注；
- bag 内 image 类型消息为 `0`。

自动 postflight `PASS` 只说明“这条数据满足采集与实现合同”，不说明 `Matched5` 已经减晃。到达、RGB outcome、跟踪、完成时间和执行链效果必须在 6 条完成后按下节统一分析。

## 8. 六条完成后的分析

### 8.1 真实液面主结果

每条使用从 first effective motion 到 first arrival 后 `5 s` 的共同窗口；对有效 `height_max_lcr_mm` 使用冻结的因果 5 点 rolling median，计算：

- `H_vis P95`（主指标）；
- `H_vis RMS`、peak、tail RMS 和 settling；
- RGB valid/zero-lock/status 覆盖率、频率、最大间隔、source lag 和 future skew。

每个 block 定义：

```text
Delta_P95_b = P95(Matched0, b) - P95(Matched5, b)
Delta_RMS_b = RMS(Matched0, b) - RMS(Matched5, b)
```

正值表示 `Matched5` 更好。必须报告 3 个原始 block 差值、均值、中位数、方向计数和 leave-one-block-out 结果，不能只报 6 条 trial 的 pooled frame 均值。

### 8.2 跟踪、安全与实时性

每条同时报告：

- `GOAL_REACHED`、first-motion 到 arrival 的完成时间；
- contour/yaw 的 RMS、P95 和最大值；
- solver time 的 median/P95/max、失败和控制周期超期；
- fallback/reset、安全门、terminal intervention 和人工干预；
- 两条件的 paired completion/tracking 差值。

基本资格门沿用 development gate：每条到达时间不超过 `42 s`，contour P95 不超过 `0.05 m`，yaw P95 不超过 `0.15 rad`，solver P95 小于 `25 ms`，并且没有 solver failure、tracking-safety stop 或 observer fallback/reset。

### 8.3 执行链与模型诊断

新增审计量按显式时间戳分五层分析：

1. **控制作用是否足够**：比较 Matched0/Matched5 的 raw first action、短可信窗口计划激励和 per-node liquid cost sensitivity。若两条件的动作差小于执行噪声或量化分辨率，则“RGB 无差异”只能说明本次控制作用太弱，不能直接证明液体模型或在线架构无效；
2. **滚动计划是否被覆盖**：对 `previous k=1 → current k=0` 统计相邻有效 cycle 的 `a/alpha` 替换量、RMSE、符号一致率和频谱差异，禁止跨失败或安全门周期比较；
3. **软件执行链是否改命令**：对 raw OCP、terminal controller、安全门、shared limiter 和 published `/cmd_vel` 分层统计介入率及改变量；
4. **Scout 是否实现发布命令**：优先辨识 published `v_cmd/omega_cmd → realized v_r/omega_r`，而不是直接假定“加速度命令到加速度”的一阶模型；
5. **actual-input model 是否解释 RGB**：用对齐到容器中心的实际 `a_x=dot(v_r)` 和 `a_y=v_r*omega_r` 重放液体模型，只在可信短 lead 内检查幅值、主频、相位、相关性和误差，并与 planned-input replay 明确区分。

Scout 执行链的第一候选辨识形式为：

```text
tau_v     * d(v_r)/dt     + v_r     = v_cmd(t - d_v)
tau_omega * d(omega_r)/dt + omega_r = omega_cmd(t - d_omega)
```

这只是待比较的最小候选，不是预先认定的真实模型。必须用 held-out trial 比较纯延迟、一阶加纯延迟以及必要的饱和/死区模型，并报告参数稳定性、残差白化和跨 block 泛化。若相同 S 路径的 6 条数据缺少持续激励、参数不可辨识，则只能生成初步估计，后续另建短小、安全、预注册的执行链辨识数据，不能在这 6 条上过拟合后宣称模型已冻结。

延迟至少拆成三层报告：底盘/驱动器动态延迟、processed-IMU 滤波群延迟、时间戳/通信延迟。IMU 加速度还必须由安装点变换到容器参考点，处理重力补偿、坐标符号以及 `dot(omega) × r`、`omega × (omega × r)` 杠杆臂项。command-to-IMU 的同周期样本不是刚发布命令的响应，不能做无延迟逐点相关。

## 9. 预声明判定

### 9.1 `PROMOTE_FOR_NEXT_GATE`

只有同时满足以下条件，才能把 `Matched5` 作为新的 development 候选继续：

1. 6/6 planned rows 均完成且 postflight `PASS`，形成 3/3 eligible blocks；
2. `mean(Delta_P95_b) >= 0.10 mm`；该门槛高于旧数据约 `0.076923 mm` 的主要量化梯级，不再沿用过低的 `0.05 mm`；
3. 至少 2/3 block 的 `Delta_P95_b > 0`，中位数为正，且删除任一 block 后剩余均值仍为正；
4. 配对平均 `Delta_RMS_b >= 0`，即 RGB RMS 不恶化；
5. 6 条均通过到达、跟踪、安全、observer、common-epoch 和 solver 实时门；
6. 改善不能只出现在一条异常 trial，且必须同时报告其与计划覆盖、软件介入和 command-to-IMU mismatch 的关系。

即使满足以上条件，结论也只能写成“小样本 development 配对支持继续验证”，不能写成正式统计显著，也不能直接开始 Stage I 40 条。

### 9.2 `INCONCLUSIVE`

出现以下任一情况应记为不可判定：RGB 窗口/时间戳/有效率不足、效果小于 `0.10 mm` 测量门、block 方向不稳定、执行 mismatch 过大、只有部分 block 可用，或 Matched0/Matched5 的 raw first-action 分离小于执行噪声。不可判定不能被解释为 Matched0/Matched5 等效，也不能自动触发完整 phase-funnel 实现。

### 9.3 `STOP_OR_REDESIGN`

- 内部模型下降但 RGB 不下降：不能宣布实物正向，也不要继续简单增大 `w_slosh`；优先检查 first-action sensitivity、模型、视觉投影和 actual-input replay。
- planned-input 预测差，但 actual-input replay 能在 held-out 数据解释 RGB：支持“计划没有被实车实现”，进入 Scout 执行模型和 OfflineSloshOCP 门，而不是直接上线完整 funnel。
- `Matched5` 只在低 command-to-IMU mismatch 的 trial 中正向：先辨识 `v/omega` 层的底盘延迟/内环，建立包含执行器模型的新 release，再重新配对。
- actual-input model 仍不能稳定解释 RGB：转向液体模型参数、坐标/投影、observer 或更高阶模型辨识，phase-funnel 路线暂时 `NO-GO`。
- 跟踪、安全或实时性失败：当前 release 停止，不以液面指标正向抵消工程失败。

### 9.4 后备路线的进入门

进入 phase-funnel residual S-MPCC 的理想证据链必须是：

```text
actual-input liquid model 在 held-out bag 有效
→ 含冻结 Scout 执行模型的 OfflineSloshOCP 在 matched-task 实物 RGB 上正向
→ 完整离线抵消序列有效，但当前滚动在线 MPC 未复现
→ 才实现固定 N_s=3 的 residual S-MPCC 和 empirical recoverability tube
```

| G3R3/后续诊断结果 | 决策 |
| --- | --- |
| G3R3 RGB 正向且所有门通过 | 保留当前短时域候选，继续下一 development gate，不切换架构 |
| 动作分离过弱 | 先做冻结 snapshot/first-action sensitivity；结果为 `INCONCLUSIVE` |
| planned-input 差、actual-input replay 有效 | 可以进入执行器辨识和 OfflineSloshOCP |
| actual-input replay 仍不能解释 RGB | 暂停新控制器，先修模型、坐标、observer 或 RGB 投影 |
| OfflineSloshOCP 实物正向、滚动 MPC 不正向 | 最支持 residual + recoverability tube 路线 |
| OfflineSloshOCP 也不优于 Bsmooth | 不做 funnel；nominal 抵消序列没有实物基础 |

后备路线第一版固定 `N_s=3`，不启用逐周期自适应 confidence horizon。只有固定时域 residual/tube 已经正向，并且独立数据证明可信时域确实随状态变化，才允许在新 release 中加入离散 `N_s`、滞回和最小驻留周期。

## 10. 本批结束后的边界

本批完成后先生成完整的 block-level RGB、tracking、runtime、first-action sensitivity、Scout 执行链和 actual-input replay 分析记录，再决定保留当前候选、补执行链辨识还是进入后备路线。任何后备路线数据都使用新的协议 ID，不与 G3R3 或正式样本池化。

G3R3 的成功不会自动关闭 G4–G6、FixedProfile/SmoothMatch 公平性、正式随机表、failure/retry 规则或 `FREEZE_ID`；这些前门禁未完成前，正式 `40/64/88` 始终保持 `NO-GO`。
