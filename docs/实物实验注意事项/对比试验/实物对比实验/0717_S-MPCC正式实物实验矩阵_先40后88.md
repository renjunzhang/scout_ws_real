## 1. 任务边界与证据结构

本实验只研究沿预先给定、已经检查几何可行性的路径进行在线轨迹生成与控制。它不检验全局选路、动态避障或通用局部规划。

必须始终区分：

- `s_ocp`：OCP 内部有限时域虚拟进度；
- `s_proj`：由 odometry 独立投影得到的实际执行进度；
- `t(σ)`：以 `σ=s_proj/L` 重建的实际 motion timing；
- `H_modal`：模型传播的内部非负响应；
- `H_vis`：冻结视觉链给出的物理实验参考量，不是无条件真值。

S-MPCC 使用的是 odometry 驱动、模型传播的内部液体模态状态，不是真实带符号液体相位观测。

| RQ | 正式物理数据 | 计算/审计数据 | 能支持的结论 |
| --- | --- | --- | --- |
| RQ1：物理效果与轨迹重分配 | Stage I | `t(σ)`、Z1–Z5、执行激励 | 高风险路径上的液面响应、任务代价和局部轨迹变化 |
| RQ2：竞争性 timing 解释 | Stage I | reference/prediction/execution 分层 | 排除整体减速；检验 fixed timing 是否已足够 |
| RQ3：模型状态相关 online generation | Stage I 的 S-MPCC 日志 | 四相位、online-input/zero-state replay、执行链、runtime | 内部模型状态是否改变完整 horizon 和第一动作 |
| RQ4：路径选择性与有限迁移 | Stage II-A；条件性 II-B | 分层 effect-difference/参数 replay | 所报告路径上的选择性；满足门槛时的有限跨容器迁移 |

轨迹变化是机制证据，`H_vis` 是物理效果证据；二者不能相互替代。

## 2. 五个比较条件

### 2.1 条件定义

| 条件 ID | 论文名称 | 执行 backend | 液体参数 | runtime 内部模态状态 | 作用 |
| --- | --- | --- | ---: | ---: | --- |
| `B0` | Baseline MPCC | online MPCC，variant `B0` | 否 | 否 | 普通 MPCC 锚点 |
| `Bsmooth` | Smooth-only MPCC | online MPCC，variant `B_smooth` | 否 | 否 | 检验通用平滑 |
| `SmoothMatch` | Smooth-match MPCC | `B_smooth` + 冻结 `v_ref` | 否 | 否 | 检验等完成时间整体减速 |
| `FixedProfile` | Model-informed fixed-profile | 离线 profile + 冻结 tracker | 是 | 否 | 检验 physics-aware fixed timing |
| `Bslosh` | S-MPCC | online MPCC，variant `B_slosh` | 是 | 模型传播 | 本文方法 |

`B0`、`Bsmooth`、`Bslosh` 是共同 OCP 的三个内部 variants。`SmoothMatch` 是独立冻结的完成时间 comparator。`FixedProfile` 是另一套 timing-generation/tracking system，不是 OCP 开关，也不是单因素 memory 消融。

### 2.2 Fixed-profile 的唯一候选定义

v2.0 默认候选是 Hamaguchi-inspired two-impulse ZV fixed-path timing：

- 读取相同冻结路径、$\omega_1$、$\zeta$ 和共同硬限制；
- ZV 脉冲幅值和 $\Delta T$ 由 $\omega_1,\zeta$ 决定并保持固定；
- 只允许调一个预声明的 **unshaped base-profile timing 参数**；
- 每个候选必须从 base profile 重新生成、整形、积分并检查硬约束；
- 显式处理纵向激励和固定路径上的 $a_y\simeq v^2\kappa=v\omega$；
- 从与正式静稳门一致的零/近零名义液体初态生成，并记录该假设；
- 禁止对已经生成的 shaped profile 做 time-warp；
- 正式 trial 只能加载冻结 profile，禁止现场重生成；
- 记录 profile reference、tracker error/latency、method-native raw command、共享执行层输出和实际 odometry；
- 只称 prior-art-inspired end-to-end comparator，不称 Hamaguchi/Lim 的忠实复现。

仓库已有候选生成器：

- `src/scout_apps/control/scout_profile_baselines/scripts/hamaguchi/generate_profile.py`
- `src/scout_apps/control/spmpc_experiments/config/profile_baselines/hamaguchi_profile.yaml`
- `src/scout_apps/control/spmpc_experiments/scripts/run_fixed_path_profile_baseline_suite.sh`

但现有 suite 明确是 current-sim/development 链，并调用 simulation launch；它不是正式实物 runner。当前生成器还需要审计 base-profile 参数与 hard `v_max` 是否分离，以及 endpoint distance scaling 是否改变固定脉冲 timing。完成这些审计和实物集成前，`FixedProfile` formal condition 为 `NO-GO`。

## 3. 正式矩阵：40 → 64 → 条件性 88

### 3.1 分阶段矩阵

下表中的 `n=8` 是当前资源提案，不是统计保证。只有样本量计算冻结后，40/64/88 才成为正式名称。

| 阶段 | 配置 | 每个 randomized block 的条件 | block 数 | 新增 | 累计 | 主要作用 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| Stage I / `S1_CORE` | `C1 + H1` | `B0`、`Bsmooth`、`SmoothMatch`、`FixedProfile`、`Bslosh` | 8 | 40 | 40 | RQ1–RQ3 核心证据 |
| Stage II-A / `S2A_SELECTIVITY` | `C1 + L1` | `Bsmooth`、`FixedProfile`、`Bslosh` | 8 | 24 | 64 | RQ4 路径特征选择性 |
| Stage II-B / `S2B_TRANSFER`，条件性 | `C2 + H1` | `Bsmooth`、`FixedProfile`、`Bslosh` | 8 | 24 | 88 | RQ4 有限配置迁移 |

Stage I 每个 block 包含五个**不同条件**，每个恰好一次。旧 v1.0 中第二次 `Bslosh` 已由 `FixedProfile` 替代；不存在 E2/E3 子组，也不存在可复用的旧五次顺序。

Stage II 不包含 `B0` 和 `SmoothMatch`。因此 Stage II 只解释为 liquid-response–efficiency–tracking 联合结果，不声称严格等完成时间因果效应。若希望在 Stage II 继续做严格时间匹配，必须增加 `SmoothMatch` 并重新计算矩阵，不能继续使用 64/88 计数。

不定义 96 或 104 个正式单元。物理参数 mismatch、长时传播和额外 planner 比较只能另立 exploratory protocol，不得追加到本矩阵。

### 3.2 样本量冻结

正式 `n` 必须根据以下量计算并归档：

- 最小有意义 `H_vis` 效应 $\delta_H$；
- 独立 development block 的 paired variability；
- 目标区间宽度或 power；
- 方法失败和视觉无效率余量；
- Stage II 等价/非劣界所需精度。

如果冻结结果不是 `n=8`，所有表、随机表、目录说明和 40/64/88 名称必须同步改为 `5n / 8n / 11n`，不能只在现场多跑或少跑。

### 3.3 随机化

v2.0 不在本文内嵌临时顺序。正式前必须在 `n`、五条件身份和 Stage II 是否保留后生成并 hash：

```text
freeze/randomization/
├── stage1_five_condition_order.csv
├── stage2a_three_condition_order.csv
├── stage2b_three_condition_order.csv
├── generation_record.yaml
└── sha256.txt
```

要求：

- Stage I 使用位置尽可能平衡的五条件 complete-block 表；
- Stage II-A/B 分别生成独立三条件表；
- 不把不同路径、容器或日期的同编号 block 强行配对；
- actual randomization/permutation inference 必须复现这些真实 assignment；
- paired sign-flip 若保留，只作对称性假设下的敏感性，不能称设计的 exact test；
- 随机表不存在或未通过 validator 时 formal `NO-GO`。

## 4. 平台、路径、容器和 trial 准入

### 4.1 公共平台

| 项目 | 候选口径 | 正式前冻结要求 |
| --- | --- | --- |
| 底盘 | AgileX Scout Mini 2.0 | 设备 ID、payload、质心、构建日志 |
| 控制频率 | 30 Hz | solve-time budget 与实际频率规则 |
| 定位 | NanoScan3/Cartographer，`map -> base_link` | odom/TF/map smoke |
| 相机 | RealSense D435，1920×1080@30 Hz | 序列号、固定姿态、手动曝光/增益/白平衡、camera-to-mode bandwidth 准入 |
| 共同限制 | `v≤0.8`、`|ω|≤1.2`、`|a|≤0.6`、`|α|≤1.2` | online 与 FixedProfile hard-limit audit |
| 路径接口 | frozen JSON replay | 每个 stratum 的 path/profile hash |
| 共享执行层 | terminal、gate、limiter、fallback | raw/post/published command 可分层记录 |

Reference Governor、modal hard cap、Map-vref 和 obstacle cost 在 core comparison 中关闭。若启用，必须对全部适用条件公平处理并建立新 release。

### 4.2 路径

`H1` 必须包含：

- 起步加速；
- 持续曲率；
- 曲率符号反转；
- 退出后的再加速；
- 终端制动。

`L1` 保持相同任务接口，但显著降低最大曲率、曲率变化率和激励。它是 selectivity condition，不是依靠“不显著”即可通过的负对照。

H0/H0b development 路径不得与 held-out H1 正式路径混用。H0/H0b、H1、L1 均保存 JSON、长度、曲率、Z1–Z5、图和 SHA-256。

### 4.3 容器

`C1` 是名义容器。若保留 Stage II-B，`C2` 的实物、几何、液深、freeboard、液体、安装、视觉准入和派生参数必须在第一条 Stage I trial 前冻结。

Stage II-B 中：

- S-MPCC 只更新预声明物理模型参数；
- FixedProfile 用同一 C2 参数重新生成并预冻结 profile；
- controller weights、$\zeta$、horizon、solver、硬限制、H1、执行层和视觉链保持不变；
- 主要比较在 C2 内部完成；
- 不把跨日期 C1/C2 结果写成严格配对或强 interaction。

### 4.4 trial 准入

每次 trial 使用相同、方法无关的准入：

1. 起点位置与航向进入冻结门限；
2. `/cmd_vel` 为零且只有计划中的 publisher；
3. 容器固定、液深、泄漏和相机状态合格；
4. 适用 backend 的内部方法状态 reset 成功，公共 monitor 独立 reset；
5. 等待 ring-down 验证的 `T_SETTLE`，且不超过冻结的最大 admission wait；
6. 可选方法无关 monitor 合格；
7. recorder 已覆盖运动前 raw RGB；
8. 离线 visual-start QC 使用冻结规则；
9. 超过最大等待或在线可判定无法静稳时，在运动前阻断并按方法无关 acquisition failure 归档；
10. 采集后离线 visual-start QC 不合格时保留原 attempt，并按 acquisition-failure/retry 规则处理；若导致跨时段恢复，则按 split-block 规则处理。

运动前 2 s RGB 只是名义采集窗口，不单独证明液体已经静稳；recorder-ready/首个有效 RGB 与 first effective motion timestamp 必须留证，并在 bag 后验证覆盖不少于冻结的 2 s 门槛。

## 5. Formal 前的 development gates

### 5.1 G0–G6

| Gate | 目的 | 必须归档的证据 |
| --- | --- | --- |
| G0 | 主张与 comparator | prescribed-path 边界、五条件身份、fairness variables |
| G1 | rotation release | current 与 rotation-consistent candidate 的 modal propagation、first action、`t(σ)/v(σ)` relevance replay；差异可辨识时的 rotation-only RGB pilot；阈值和唯一选择 |
| G2 | candidate screening | 小候选集的安全、局部 timing、tracking、runtime；内部模型量不当物理真值 |
| G3 | 独立 RGB efficacy | 最终候选 vs `Bsmooth`，精确 `n_dev`、调试预算、$\delta_{H,dev}$、success/single-block-dominance gate、禁止提前停止 |
| G4 | trajectory/replay 工具 | `s_proj` extractor、Z1–Z5、纵/横向四相位、完整 horizon、online-input branch reproduction |
| G5 | comparator fairness | SmoothMatch 与 FixedProfile 的调试预算、完成时间、tracker/constraint/profile audit |
| G6 | measurement/analysis freeze | RGB、同步、failure、estimand、sample size、随机表、软件/config hash |

任一 gate 失败，不得通过增加正式路径、容器或诊断掩盖。

### 5.2 G2：候选筛选

旧 v1.0 的 15 个 no-RGB 权重单元可保留为 G2 development screen，但不能单独授权 formal。它只能用于：

- 排除不安全、tracking/runtime 不合格候选；
- 检查 Z2/Z3 局部 horizon 和 first-action 是否发生变化；
- 形成一个最终 candidate release；
- 记录全部候选和 rejection reason。

B0/Bsmooth 的缺失或零 online modal state 不能当作更优物理结果。`H_modal` 排序不能替代 G3 的真实 RGB 方向。

### 5.3 G3：独立 RGB efficacy pilot

在未进入正式主表的 H0/H0b development 路径上，比较一个最终 `Bslosh` candidate 与 `Bsmooth`：

- 精确 block 数在第一条 RGB trial 前冻结；当前默认建议 `n_dev=4`，不是既成决定；
- final candidate 与两条件的调试/调参预算在第一条 RGB trial 前冻结；
- complete blocks、固定随机表、无提前停止；
- 记录 RGB、completion、tracking、success、执行干预和 runtime；
- 预冻结 $\delta_{H,dev}$、区间/方向门槛和单-block dominance 检查；
- 只有 `H_vis` 方向与门槛均通过，才可进入 G6；
- 若修改 candidate 或 gate，建立新 development release 并重新做完整 pilot；
- 这些数据永久标记 development，不并入 formal `n`。

### 5.4 G4：trajectory 与 model-state replay

正式前必须冻结 longitudinal 与 lateral 两个 mechanism checkpoint、构造相位幅值 $A$、数值容差和输出字段。每个方向的四相位 solve 必须使完整 horizon 或 first action 的差异超过预冻结数值容差；否则不能声称 phase-sensitive online generation。online-input/zero-state replay 只用于 `Bslosh`，并必须从同一个不可变 pre-solve snapshot 克隆，online-input branch 在冻结容差内复现在线 status、first action 和 raw command。

### 5.5 SmoothMatch

只允许通过 `B_smooth` 的一个 speed-reference 参数匹配 development-set、odometry-derived completion time。正式前冻结：

- 最终 `v_ref`；
- 安全区间和 tuning 数据；
- first-arrival/terminal completion 规则；
- 容许误差 $\delta_T$，默认候选 ±5%；
- 正式样本即使实际时间漂移也保留。

不得查看正式 RGB 后重调。

### 5.6 FixedProfile

对每个计划 stratum `(C1,H1)`、`(C1,L1)` 和条件性 `(C2,H1)`，在独立 development 数据上冻结：

- generator/version/hash；
- $\omega_1,\zeta,\Delta T$ 和脉冲幅值；
- 唯一 base-profile timing 参数；
- 生成后的 CSV、plot、constraint report 和 SHA-256；
- tracker config/hash、raw command topic、共享执行层 contract；共同 tracker 仅在技术上适用且预先声明时采用；
- completion-time target/tolerance；
- offline generation time 与 online tracking cost。

正式 profile 不得现场重生成。现有 sim suite、`slosh_experiment_sim.launch` 或 current-sim metadata 不能作为实物 formal runner。

## 6. 记录、trajectory extraction 和 outcomes

### 6.1 每个 trial 的公共记录

| 层 | 必须记录 |
| --- | --- |
| 身份 | protocol、`FREEZE_ID`、condition/backend、stage/block/position、config/profile/path hashes |
| 路径 | frozen path、$\kappa(s)$、online conditions 的 `s_ocp`、odometry-derived `s_proj`、Z1–Z5 |
| 机器人 | timestamped $(x,y,\theta,v,\omega)$ odometry、tracking/cross-track |
| reference | FixedProfile `s_fp,ref(t)`、`v_fp,ref(s)`、`ω_fp,ref(s)`；online reference |
| OCP | online conditions 的 pre-solve input、完整 horizon、first action、solver/runtime |
| 执行 | method-native raw、post-gate、published command、intervention/fallback |
| 液体模型 | Bslosh 的内部 modal state 与 `H_modal`；standalone monitor 仅作支持 |
| 视觉 | raw RGB、camera_info、质量/同步 sidecar；离线 `H_vis` |
| FixedProfile | profile ID/hash、tracker status/error/latency、reference index/progress |
| 结果 | arrival、success/failure、timeout、安全终止、操作员说明 |

FixedProfile 的 raw layer 是 tracker 原生命令，不得误称 solver command。

### 6.2 实际轨迹

actual timing 只能由 `s_proj` 得到。正式前冻结：

- 连续/最近点投影；
- monotonic guard、backtracking、jump、stall；
- first-arrival、interpolation、cross-track 和 terminal 规则；
- `t(σ)` 与 Z1–Z5 traversal time；
- braking、entry/reversal speed、re-acceleration features；
- 单一 constant speed scaling residual；
- 同步、滤波和微分规则；
- executed $a_x\simeq\dot v_{odom}$ 的 RMS 与 $|a_y|\simeq|v_{odom}\omega_{odom}|$ 的 p95。

由于每周期初始化满足 `s_ocp,0|j=s_proj(t_j)`，当前节点之差恒为零，不能作为结果。若保留 forecast diagnostic，只比较 `k>0` 的

$$
e_s(k|j)=s^\star_{ocp,k|j}-s_{proj}(t_j+k\Delta t)
$$

并冻结未来 odometry 插值、有效 horizon 和汇总规则。

### 6.3 outcomes

- Primary physical outcome：`H_vis,p95(full motion)`，窗口从 first effective motion 到统一 arrival；
- 关键 sensitivity：10%–90% progress-window p95；
- Secondary：full/post-arrival RMS、completion、tracking p95、success；
- Trajectory/mechanism：`t(σ)`、Z1–Z5、局部制动/再加速、constant-scaling residual、`a_x/a_y`、`H_modal`、`r_int`；
- Runtime：median/p95/max、budget overrun、failure、fallback、achieved frequency。

一次完整 trial 是统计样本；RGB frame、control cycle 和 path point 不是独立样本。

### 6.4 K6-style supporting diagnostic

完整 modal–vision fidelity 只是 supporting diagnostic。可用 S-MPCC planned units 为：

- Stage I 后 8；
- Stage II-A 后累计 16；
- 条件性 Stage II-B 后累计 24。

K6 必须使用单一冻结脚本、同步规则、lag policy 和 failure denominator，只比较非负幅值包络。不得再使用旧 K6=32 分母；B0、Bsmooth、SmoothMatch、FixedProfile 的缺失/零内部状态不能充作 K6 样本；K6 不能验证 signed phase 或 rotation consistency。视觉 measurement admission 即使不做完整 K6 也必须通过。

## 7. 分阶段执行与 claim gates

### 7.1 Stage I：40 个单元

每个 block 按新的五条件随机表连续执行：

```text
S1_CORE_H1_C1_<CONDITION>_b<BB>_r01
```

`<CONDITION>` 只允许 `B0`、`Bsmooth`、`SmoothMatch`、`FixedProfile`、`Bslosh`。

四个与 Bslosh 相关的 contrasts 共享同一个 block-level Bslosh observation。不得重复采集第二个 Bslosh，也不得把旧 E2/E3 trial 拼入。

确认性顺序固定为：

1. `Bslosh - Bsmooth`：第一物理主比较；
2. 第一步通过后，`Bslosh - FixedProfile`：关键 novelty comparison；
3. 完整主张还要求 SmoothMatch completion-time gate 和 success tolerance 成立；
4. `Bslosh - B0` 为关键次比较，`Bsmooth - B0` 为机制诊断。

SmoothMatch、Baseline 和其他次比较必须使用预声明层级或 Holm 调整，不能根据结果临时提升为主比较。

FixedProfile 比较是 end-to-end system comparison，不单独证明动态 memory 的物理因果必要性。

### 7.2 Stage I 后的扩展 gate

只有预注册 gate 全部满足，才进入 Stage II：

- 40 个 planned units 和全部额外尝试均可追溯；
- RGB/同步/visual-start QC 达到冻结有效率；
- `Bslosh - Bsmooth` 达到 $\delta_H$、区间和 randomization 规则；
- SmoothMatch 完成时间门与物理方向成立；
- `Bslosh - FixedProfile` 按固定层级达到预声明 novelty 准则；
- success、tracking、runtime 和 `r_int` 不超过冻结容限；
- 结果不由单一 block 独占，leave-one-block-out 方向稳定；
- trajectory extractor、纵横向四相位、`Bslosh` online-input replay 和 execution-chain audit 可运行。

未通过时停止扩展并按冻结分析报告，不通过增加 L1/C2 包装核心失败。任何方法、权重、路径、视觉处理或分析修改都会结束当前 release；新版本从 formal block 01 重新开始。

### 7.3 Stage II-A：累计 64

`C1+L1` 每个 block 运行 `Bsmooth`、`FixedProfile`、`Bslosh`：

```text
S2A_SELECTIVITY_L1_C1_<CONDITION>_b<BB>_r01
```

“选择性”必须依据预冻结的 completion、tracking、success、intervention 等价/非劣界，以及 H1→L1 effect-difference 规则；普通不显著不能证明等价。

- `stage2b_enabled=true`；

run label：

```text
S2B_TRANSFER_H1_C2_<CONDITION>_b<BB>_r01
```

结果只支持所报告配置间的有限迁移。参数 correct/incorrect replay 只能证明 optimizer sensitivity。物理响应同时报告原始物理单位与按冻结 freeboard 定义归一化的单位。

## 8. 随机分析、失败和 retry

### 8.1 统计单位与推断

对 trial-level outcome `Y`，block difference 为

$$
\Delta_b^{m-m'}=Y_{m,b}-Y_{m',b}.
$$

报告 raw points、paired lines、mean paired difference、relative change、whole-block bootstrap interval 和 leave-one-block-out。

exact/randomization inference 必须复现实际随机表允许的 assignments。不能把 control cycles 当样本，也不能根据显著性重排主次。

### 8.2 固定分母

所有 planned units 和有效 formal attempts 保留在固定分母。每个 contrast 报告：

- `n_pair/n`；
- success-conditional continuous effect；
- success/noninferiority margin；
- failure-penalized worst-rank 或 composite win–loss sensitivity；
- 全部额外物理尝试和 exclusion log。

### 8.3 允许 retry 的 acquisition failure

只允许与方法无关的采集故障使用 `r02`，例如相机/rosbag 未启动、视频不可恢复、采集后离线 visual-start QC 不合格、正式开始前加载错误路径/配置、方法无关现场侵入。

要求：

- 原 bag、sidecar 和原因永久保留；
- retry 使用相同 condition、backend、profile/config hash；
- 在原 `block_segment_id` 和冻结环境内完成才保留主配对资格；
- 跨时段标记 `split_block=true`，不与另一 segment 强行配对。

solver、tracker、profile execution、tracking、timeout、安全终止和方法相关命令异常均为方法失败，不得用成功重跑替换。fallback 是必须保留的方法相关事件；它是否使整条 trial 判失败、或按事件率/容限判定，必须在首条 formal trial 前冻结，不能现场决定。
