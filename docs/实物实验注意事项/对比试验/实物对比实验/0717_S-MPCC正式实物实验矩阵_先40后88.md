## 1. 总体策略

实验分两次决策：

| 阶段 | 正式物理实验 | 累计次数 | 主要目的 | 决策 |
| --- | --- | ---: | --- | --- |
| 阶段 0：参数冻结 pilot | C1、高风险 pilot 路径，B0、B_smooth、`w_slosh=1/2/5` 各 3 次；`10` 条件性增加 3 次 | **0** | 无 RGB 地完成模型侧权重筛选，并随后冻结 Smooth-match | 全部冻结门槛通过后才允许开始正式 40 次 |
| 阶段 I：核心机制包 | 高风险路径、名义容器三方法 24 次；等完成时间 16 次 | **40** | 检查真实液面是否改善，并排除普通平滑和整体减速解释 | 40 次通过阶段门槛后才扩展 |
| 阶段 II-A：双路径扩展 | 名义容器、低风险路径三方法 24 次 | **64** | 检查效果是否只存在于高风险 S 弯 | 阶段 I 通过后执行 |
| 阶段 II-B：跨容器扩展 | 第二容器、高风险路径三方法 24 次 | **88** | 检查只更新容器模型参数、不重调权重时的有限迁移 | C2 和视觉采样门槛通过后执行 |

权重 pilot、开发 smoke、相机标定、路径冻结、Smooth-match 调速 pilot、C2 选型和 replay 工具验证均不计入 40/88 次。

旧 0705/0706 的 N=3 数据只作为 development-only/pilot，不并入新的正式 `n=8`。

## 4. 权威跟踪路径

### 4.1 正式路径冻结原则

历史脚本采用“固定终点、每次从当前起点重新生成路径”。该方式适合调试，但不同 run 的几何路径会随起点误差改变，不适合新的正式 paired comparison。

正式实验改为：

1. 在地面起点位置和航向标记处生成候选路径；
2. 验收路径长度、曲率、起终点和安全走廊；
3. 保存权威 JSON、路径图、曲率图和 SHA-256；
4. 正式 run 使用 `fixed_global_path_runner.py --mode replay` 发布同一 JSON；
5. replay 前执行 `0.05 m/0.10 rad` 起点门控；
6. bag 中继续记录实际 `/scout/global_path_fixed`，分析时核对其 hash/几何是否与权威文件一致。

建议 freeze artifact 目录：

```text
docs/实物实验注意事项/对比试验/实物对比实验/freeze/
├── paths/
│   ├── H0_weight_pilot.json          # 可选：与正式 H1 分离的同类高激励开发路径
│   ├── H1_P2_s_curve.json
│   ├── H1_P2_s_curve_geometry.csv
│   ├── L1_gentle.json
│   └── L1_gentle_geometry.csv
├── configs/
├── randomization/
└── calibration/
```

正式 runner 在采集前必须支持 replay 已冻结路径；不得在正式 run 中静默退回 template regeneration。

权重 pilot 优先使用与 H1 曲率激励相似但不进入正式主表的 `H0_weight_pilot`。现场工作文件固定为 `/home/geist/fixed_paths/real/<DATE>_spmpc_parameter_pilot/H0_weight_pilot.json`；验收后再把只读副本和 SHA-256 归档到上述仓库 `freeze/paths/`。资源不足时也可直接使用 H1，但所有权重候选 bag 必须标为 `PF`，且正式 S1 仍从新的 block 01 独立开始。

### 4.2 高风险路径 `H1`

沿用已在实物上验证的 P2 fixed S-curve 作为候选：

| 字段 | 候选冻结值 |
| --- | --- |
| 路径 ID | `H1_P2_s_curve` |
| frame | `map` |
| 起点 | 现场地面起点标记的 map 位姿，待冻结 |
| 终点 | `x=-5.424, y=-4.736`；yaw 只作记录，不由模板几何强制 |
| template | `s_curve` |
| start heading | `current`，生成时车体必须对齐起点航向标记 |
| amplitude ratio | `0.18` |
| min/max amplitude | `0.25/1.20 m` |
| side | `left` |
| smoothing | Chaikin `3` 次 |
| spacing | `0.05 m` |

该路径用于全部 40 次核心机制包和 C2 跨容器扩展。

路径区段在查看正式 RGB 结果前，根据冻结路径的曲率图确定：

| 区段 | 物理含义 | 初始建议边界；最终以曲率图冻结 |
| --- | --- | --- |
| `Z1` | 起步直线加速 | `σ≈0–0.15` |
| `Z2` | 第一持续曲率转弯 | `σ≈0.15–0.40` |
| `Z3` | S 弯曲率符号反转 | `σ≈0.40–0.65` |
| `Z4` | 退出转弯并重新加速 | `σ≈0.65–0.85` |
| `Z5` | 终点减速、制动和到达后观察 | `σ≈0.85–1.00`，另加到达后 `5 s` |

最终区段边界只能根据路径几何和控制逻辑调整，不能根据哪一段 RGB 差异最大来选择。

### 4.3 低风险路径 `L1`

完整 88 次方案增加一条低风险路径：

| 字段 | 设计 |
| --- | --- |
| 路径 ID | `L1_gentle` |
| 起终点 | 与 `H1` 使用相同起点标记和终点，控制总位移和 terminal 条件 |
| 候选模板 | `straight`；若当前起点航向与终点弦线不完全一致，生成器的 cubic blend 形成缓慢转向 |
| spacing | `0.05 m` |
| 目标特征 | 无曲率符号反转；最大曲率和曲率变化率显著低于 `H1` |
| 用途 | 检查 S-MPCC 在简单路径上是否造成不必要的时间或跟踪损失 |

`L1` 必须和 `H1` 一样保存权威 JSON、曲率统计和 hash。若 `straight` 候选仍出现过大初始弯折，应移动终点或调整起点航向标记后重新冻结，而不是在正式数据中临时换路径。

### 5.2 参数冻结 pilot 的 15 次矩阵

默认候选为 `w_slosh={1,2,5}`。每个 block 包含 B0、B_smooth 和三个 S-MPCC 权重候选：

| Pilot block | 交错顺序 |
| ---: | --- |
| 01 | B0 → W1 → B_smooth → W2 → W5 |
| 02 | W2 → B0 → W5 → W1 → B_smooth |
| 03 | B_smooth → W5 → W2 → B0 → W1 |

共 `5×3=15` 次。若在查看新实物内部模型筛选结果前已经预注册加入 W10，则将 W10 平衡插入三个 block，总计 18 次；不得看到 W5 的模型侧排序后临时增加一个更有利的权重。

建议命名：

```text
PF_WS_H1_C1_B0_b01_r01
PF_WS_H1_C1_Bsmooth_b01_r01
PF_WS_H1_C1_W1_b01_r01
PF_WS_H1_C1_W2_b01_r01
PF_WS_H1_C1_W5_b01_r01
```

如果使用与正式 H1 分离但曲率激励相似的开发路径，将命名中的 `H1` 替换为 `H0`。如果直接使用 H1，本批仍全部标记为 `PF`，不得进入正式 `n=8`。

### 5.3 权重选择规则

在查看候选排序前，先用 B0/B_smooth 重复 run 确定并冻结 tracking、完成时间、实时性、执行层干预阈值及内部模型实用等价容差 `delta_model` 的计算规则。随后按四层决策：

1. **准入：** success、tracking、solve time、deadline、fallback、执行层和数据完整性全部合格；
2. **机制：** Z2/Z3 中完整 horizon、optimized first action 或局部速度/激励分配发生稳定变化，不能只是全程统一降速；
3. **模型响应：** block-paired 内部 `H_modal`/horizon peak、RMS 和 post-arrival RMS 改善方向稳定，不由单个 trial 独占；
4. **最小拐点：** 相邻候选的额外模型侧收益低于冻结的 `delta_model` 时选择较小权重；更大权重只有在提供明确额外收益且不恶化任务/执行指标时才能入选。

不得只看 cost breakdown 或单次最小值选权重；必须同时检查内部高度时序、完整预测 horizon、第一控制动作、tracking、完成时间和执行层干预。该步骤得到的是 `model-side frozen weight`，不是对真实液面高度改善的独立物理证明。

若现场时间允许，建议在正式 40 次前对最终候选和相邻候选另做少量、独立的 RGB freeze confirmation。若跳过，也可以直接用模型侧冻结值开始预注册的正式 40 次，但之后不得根据正式 RGB 结果重新调权重；否则原正式数据必须整体降级为 pilot。

```text
模型侧 delta_model 与全部准入阈值；若执行 RGB freeze confirmation，再归档相机标定和静止阈值
```

第一条正式 S1 数据开始后，`w_slosh`、B_smooth 权重和 Smooth-match `v_ref` 均不得再调整。若必须修改，已采正式数据全部降级为 pilot，新版本重新冻结并从正式 block 01 开始。

## 6. 阶段 I：40 次核心机制包

### 6.1 总矩阵

| ID | 条件 | 方法 | 每个 block | block 数 | 正式次数 | 研究作用 |
| --- | --- | --- | ---: | ---: | ---: | --- |

E2-C1 和 E3 分别形成配对区组。二者可以共享 `block_id`，但应分别记录自己的随机顺序和开始时间。

### 6.2 预生成顺序

以下顺序使用固定 seed `20260717` 生成，可在正式采集前直接冻结。若需要重新随机，必须在查看任何正式结果前生成整张新表并归档 seed，不能边采集边调整。

| Block | E2-C1 三方法顺序 | E3 等时间顺序 |
| ---: | --- | --- |
| 01 | B0 → B_smooth → B_slosh | B_slosh → Smooth-match |
| 02 | B_smooth → B_slosh → B0 | Smooth-match → B_slosh |
| 03 | B_slosh → B0 → B_smooth | B_slosh → Smooth-match |
| 04 | B_slosh → B_smooth → B0 | Smooth-match → B_slosh |
| 05 | B_smooth → B0 → B_slosh | Smooth-match → B_slosh |
| 06 | B0 → B_slosh → B_smooth | B_slosh → Smooth-match |
| 07 | B0 → B_slosh → B_smooth | Smooth-match → B_slosh |
| 08 | B0 → B_smooth → B_slosh | B_slosh → Smooth-match |

如果一个 block 无法在同一时段完成，应在运行日志中记录中断原因和环境变化。不能根据已看到的 RGB 或 tracking 结果决定剩余方法的顺序。

### 6.3 Run 命名

统一使用：

```text
S1_<group>_<path>_<container>_<method>_b<block>_r01
```

示例：

```text
S1_E2_H1_C1_B0_b01_r01
S1_E2_H1_C1_Bsmooth_b01_r01
S1_E2_H1_C1_Bslosh_b01_r01
S1_E3_H1_C1_SmoothMatch_b01_r01
S1_E3_H1_C1_Bslosh_b01_r01
```

`r02` 只用于与方法无关的采集故障补采；原失败尝试不得删除。方法本身的 solver/tracking/safety failure 保留为正式失败，不允许用 `r02` 替换。

### 6.4 单次正式 run 流程

1. 核对 block、方法、路径 hash、配置 hash 和 Git revision；
2. 检查容器、液深、中心安装、相机固定和安全空间；
3. 机器人回到起点门控范围；
4. 等待液体静稳，并要求 `H_vis` 连续至少 `2 s` 低于冻结静止阈值；
5. recorder 先启动并确认 RGB、odom、TF、路径和诊断正在记录；
6. replay 权威路径，启动随机表指定的方法；
7. 完成路径或记录方法失败；
8. 到达/停止后继续记录 `5 s`；
9. 保存 run metadata、异常说明和结束时电池/环境记录；
10. 快速检查数据完整性，但不查看方法间正式 RGB 排名后改变后续顺序。

## 7. 40 次完成后的扩展门槛

只有下面条件共同满足，才扩展到 64/88 次：

| Gate | 检查内容 | 通过原则 |
| --- | --- | --- |
| G1 协议完整性 | 40 次尝试、随机顺序、配置/path hash、失败和补采记录 | 无未解释配置漂移；旧 pilot 未混入 |
| G2 视觉有效性 | RGB 有效率、同步、静止噪声、缺帧和 ROI | 不存在方法相关的系统缺失；高风险路径信号明显高于噪声 |
| G3 执行一致性 | raw/post-gate/published command 和 `r_int` | 执行层未长期覆盖 OCP 差异；阈值在看结果前冻结 |
| G4 RQ1 核心方向 | B_slosh − B_smooth、B_slosh − B0 的 block-paired `H_vis,p95` | 第一主比较方向与主张一致，且不是由单个 block 独占；同时报告区间和 leave-one-block-out |
| G5 RQ2 减速排除 | Smooth-match 与 B_slosh 完成时间和 RGB | 中位完成时间差满足 `≤5%`，S-MPCC 的液面收益仍有一致方向 |
| G6 任务与实时性 | success、tracking、solve time、deadline miss、fallback | 无不可接受的方法特异失败；30 Hz 下 solve-time p95 应优先低于 `33.33 ms`，超限必须先诊断 |
| G7 RQ4 工具 | 四相位和 actual/zero replay | actual 可复现在线求解；完整 horizon 和 trial-level 汇总可生成 |

`n=8` 不等于自动“显著”。如果效应方向不稳定、RGB 接近噪声、Smooth-match 未匹配或执行层污染严重，应停在 40 次进行诊断，而不是通过增加第二路径或第二容器掩盖核心问题。

40 次后的扩展只允许增加新路径和新容器条件，不允许根据 40 次结果重新调节 B0、B_smooth、B_slosh 的权重、公共限制、H1 路径、primary metric 或 RGB 后处理。如果必须修改这些核心口径，原 40 次应降级为 pilot，修改后的正式矩阵重新开始；不能把修改前后的数据拼成同一个 88 次数据集。

## 9. 阶段 II-B：扩展到 88 次

### 9.1 第二容器 `C2` 的选择与冻结

`C2` 不在 40 次之前强行确定，但在跨容器正式采集前必须冻结：

| 项目 | 规则 |
| --- | --- |
| 几何差异 | 改变半径和/或液深，使第一模态频率相对 C1 改变约 `15%–20%` 或更多 |
| 视觉准入 | 计算 `N_frame/cycle = f_cam/f1`；30 Hz 相机下优先选择更低或适中的 `f1`，避免每周期采样过少 |
| 安装 | 与 C1 一样位于车体旋转中心 |
| 液体 | 同类型、同染料浓度；按统一 freeboard fraction `λ_H` 冻结液位 |

| 禁止更新 | MPCC 权重、阻尼比、horizon、solver、运动约束、路径、共享执行层 |

最终表中填写：容器内半径、液深、freeboard、液体质量、`f1`、每周期相机帧数和派生模型参数。

### 9.2 C2 正式矩阵

## 11. 正式录制矩阵与录制方法

### 11.1 一个 trial 对应一个独立 bag

正式实验不允许把多个方法或多个 block 连续录进同一个 bag。每个表格单元中的一次 trial 必须产生独立的 `.bag` 和完整 sidecar，并使用第 6.3 节的唯一 `RUN_LABEL`。

建议统一目录：

```text
${HOME}/slosh_bags/real/<DATE>_spmpc_formal/
├── S1/E2/H1_C1/<METHOD>/
├── S1/E3/H1_C1/<METHOD>/
├── S2A/E1/L1_C1/<METHOD>/
└── S2B/E2/H1_C2/<METHOD>/
```

录制矩阵如下：

| 阶段/组 | 路径 | 容器 | 方法及 recorder `VARIANT` | Block | bag 数 | `RUN_LABEL` 模式 |
| --- | --- | --- | --- | ---: | ---: | --- |
| S1/E2 | H1 | C1 | B0→`B0`、B_smooth→`B_smooth`、B_slosh→`B_slosh` | 01–08 | 24 | `S1_E2_H1_C1_<METHOD>_b<BB>_r01` |
| S1/E3 | H1 | C1 | Smooth-match→`B_smooth` 加冻结 `v_ref`；S-MPCC→`B_slosh` | 01–08 | 16 | `S1_E3_H1_C1_<METHOD>_b<BB>_r01` |
| S2A/E1 | L1 | C1 | `B0`、`B_smooth`、`B_slosh` | 01–08 | 24 | `S2A_E1_L1_C1_<METHOD>_b<BB>_r01` |
| S2B/E2 | H1 | C2 | `B0`、`B_smooth`、`B_slosh`，统一切换冻结 C2 配置 | 01–08 | 24 | `S2B_E2_H1_C2_<METHOD>_b<BB>_r01` |

其中 `<METHOD>` 只使用 `B0`、`Bsmooth`、`Bslosh`、`SmoothMatch`。`r02` 及以上只用于第 12 节允许的采集故障补采，原始失败 bag 和说明必须保留。

### 11.2 冻结的 recorder 设置

正式录制统一调用：

```text
src/scout_apps/control/spmpc_local_planner/scripts/record_spmpc_full_rgb_bag.sh
```

它只订阅和保存数据，不发送目标、不发布速度、不负责启动 planner。正式设置为：

| 设置 | 正式值 | 说明 |
| --- | --- | --- |
| `RECORD_RGB` | `true` | 原始 RGB 是物理液面 primary outcome 的真源 |
| `RECORD_CAMERA_COMPRESSED` | `false` | 避免压缩伪影进入液面真值 |
| `RECORD_DEPTH` | `false` | 当前主分析不使用深度，降低写盘压力 |
| `RECORD_SCAN` | `true` | 保存现场环境和定位故障证据 |
| `RECORD_STANDALONE_SLOSH` | `true` | 记录统一的 monitor-only `/slosh/*`；monitor 必须另行启动并在每次运动前 reset |
| `RECORD_ONLINE_LIQUID` | `false` | 在线 proxy 不进入控制或 primary outcome；需要调试时另开 pilot |
| `RECORD_ALL_EXISTING_TOPICS` | `false` | 使用确定性 whitelist，避免不同 run 的 topic 集随现场节点漂移 |
| `RECORD_TOPIC_INFO` | `true` | 保存 publisher/subscriber/type sidecar |
| `ROSBAG_BUFFER_SIZE_MB` | `4096` | RGB 正式录制的候选 buffer；现场机内存不足时必须在正式开始前统一冻结新值 |
| `RECORD_SEC` | `90` 或人工提前停止 | 给最长 60 s 运动、planner 启动/检查、运动前预录和到达后 5 s 留出余量；不得在到达瞬间停止 |
| `NAME` | 等于 `RUN_LABEL` | 确保 bag 与全部 sidecar 同名 |

P3 参数冻结 pilot 中 RealSense 随基础栈保持启动，但输出到独立的 `*_spmpc_parameter_pilot` 根目录，并固定 `RECORD_RGB=false`、`RECORD_DEPTH=false`、`RECORD_ONLINE_LIQUID=false`，保留 odom、TF、路径、命令、solver、完整 horizon、内部 `/spmpc/*` slosh 诊断和 standalone `/slosh/*`。planner 启动参数、recorder metadata、run-env sidecar 和 effective config 必须同时记录候选 `W_SLOSH`；任何字段不一致时该 run 不用于权重选择。

正式路径必须从冻结 JSON replay。`run_spmpc_real_fixed_path_trial.sh` 已支持 `PILOT_MODE=true + PATH_SOURCE_MODE=replay`，推荐作为 P3 一键入口，并默认使用 `0.08 m / 0.15 rad` 的 pilot 起点门控；正式 40/88 次仍使用配套启动文档的多终端流程和冻结的更严格门控。`run_continuous_real.sh` 仍按当前起点重新生成路径，只用于 smoke。

### 11.3 每次 run 必须记录的证据

| 层次 | 必须记录 |
| --- | --- |
| 路径 | 权威 path ID/hash、`/scout/global_path_fixed`、`s`、`σ`、曲率和 Z1–Z5 |
| 机器人 | `x,y,theta,v,omega`、contour/lag error、到达和失败状态 |
| OCP 输入 | 实际 solver robot state、传播液体状态、`s_min`、有效 `v_ref` |
| OCP 输出 | 第一 `a,alpha,v_s`、solver status、solve time、完整配置诊断 |
| 执行层 | raw solver command、post-gate command、published command、limiter/fallback 标志 |
| 液体模型 | `eta_x,eta_x_dot,eta_y,eta_y_dot,H_modal` |
| 物理液面 | 原始 RGB、camera_info、标定 ID、`H_vis`、缺帧和同步状态 |
| 平台 | Git revision、配置 hash、节点/话题快照、电池、温湿度、操作员说明 |
| Replay | pre-solve solver/warm-start/previous-solution 快照和完整预测 horizon |

当前代码已提供并由正式 S-MPCC recorder 显式录制：

- `/spmpc/debug/predicted_horizon`：完整 61 状态、60 控制预测时域；
- `/spmpc/debug/pre_solve_snapshot`：solve 前 robot/slosh 输入、参考曲线、有效 `v_ref`、边界、61 阶段参数、上一解和完整原始变量初值。

这两个接口当前由论文主线 `continuous_mpcc_acados` 完整填充。pre-solve 消息明确标记 `primal_guess_only=true`，尚不包含对偶变量和 acados 内部 SQP memory。因此 K3 的 actual/zero replay 在进入正式分析前必须先通过冻结的复现门槛：actual 分支复现在线 solver status、第一控制量和 raw command；不能仅因快照已经录下就认定 exact replay 成立。若 actual 分支超过容差，先补充求解器内部状态，再开展 zero 或 phase-flip 分叉。

### 11.4 录制生命周期

每次 trial 严格按下面顺序执行：

1. 根据随机表填写 `RUN_LABEL`、方法、block、路径、容器和输出目录；
2. 核对冻结路径 JSON 的 SHA-256，并把 hash 写入本次 sidecar；
3. 启动或核对 standalone slosh monitor，调用 `/slosh/reset`；
4. 启动 frozen-path replay，但停在 `--manual-start` 的 Enter 门；
5. 启动 recorder，使节点启动、首个求解周期和全部运动前静止段进入 bag；
6. 启动指定 planner；在尚未发布路径时核对 backend、variant、公共约束、诊断话题和唯一 `/cmd_vel` publisher；
7. 液体达到静稳门槛后，在 replay 终端按 Enter；起点位置/航向门控通过后开始发布路径和运动；
8. 到达、方法失败或安全终止后继续录制 5 s；
9. 先安全停止 recorder 使 bag 正常闭合，再停止 planner 和 path replay；
10. 立即核对 bag、recorded-topics sidecar、路径/config hash、关键 replay 话题和异常记录。

不得在同一 planner 进程中连续切换方法录制多个 trial。每次 trial 都重新启动 planner，使内部历史解、上一控制、delay 状态和 terminal 状态从统一初始条件开始。

论文 primary outcome 固定为首次有效运动到统一到达时刻的全运动窗口 RGB p95：

```text
H_vis,p95(full motion)
```

同时报告：10%–90% 路径进度 RGB p95、full-motion RGB RMS、到达后 5 s RMS、completion time、path error p95、success/failure、运动激励、执行层干预和实时性。

一次完整 trial 才是统计样本；RGB 帧、控制周期和路径采样点不能当作独立样本。

## 12. 失败、补采与数据使用规则

允许排除并在相同 block 补采的情况仅限与方法无关的采集故障：

- 相机或 rosbag 从未启动；
- 视频不可恢复损坏；
- 正式开始前发布了错误路径或错误配置；
- 与方法无关的现场人员/障碍侵入。

以下情况保留为方法失败，不得删除后补一个“成功 run”替换：

- solver failure 或 timeout；
- tracking failure；
- safety termination；
- fallback；
- 方法相关的命令异常；
- 未在最长时间内到达。

所有有效尝试进入 success rate 分母。连续液面和 tracking 指标只对完成 trial 计算时，必须同时报告完成数量/总尝试数量。
