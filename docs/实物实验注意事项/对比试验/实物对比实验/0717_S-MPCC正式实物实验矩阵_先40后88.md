## 1. 任务边界与证据结构

本实验只研究沿预先给定、已经检查几何可行性的路径进行在线轨迹生成与控制。它不检验全局选路、动态避障或通用局部规划。

必须始终区分：

- `s_ocp`：OCP 内部有限时域虚拟进度；
- `s_proj`：由 odometry 独立投影得到的实际执行进度；
- `t(σ)`：以 `σ=s_proj/L` 重建的实际 motion timing；
- `H_modal`：模型传播的内部非负响应；
- `H_vis`：冻结视觉链给出的物理实验参考量，不是无条件真值。

当前已冻结候选的 S-MPCC 使用 odometry 驱动、模型传播的内部液体模态状态，不是真实带符号液体相位观测。HEAD `a2fe0c2` 的 processed-IMU 只生成并行 shadow 状态，`SolverInput.slosh` 强制来自 odom；2026-07-31 未提交 working tree 的 selector 只算 implementation candidate，不改变冻结身份。formal 前必须通过 `G2S` 二选一：

- 若 processed-IMU 相对冻结 RGB 参考没有达到预声明的实质改善门槛，保留 odom；
- 若 processed-IMU 达到门槛，当前 v2.0 候选不能直接切换开关继续，必须建立新的 method release、实现正式输入选择，生成绑定原 G2S 决策与新 revision 的 `IMU_IMPLEMENTATION_VALIDATION` report/hash，重做 G2C/G3，并同步论文与 freeze；
- 同一个 formal release 只允许一个冻结的 **nominal observer source**，也不允许在 Stage I 中途由操作者切换；
- 未来 IMU release 必须为安全性实现 `IMU -> odom` 自动 fallback，并预冻结 fallback source、触发条件和状态码。发生 fallback 的 trial 保留在原 `Bslosh/IMU-release` 分母中并计为 method failure，不得重标为 odom trial、不得用重跑替换，也不得与 nominal-odom release 池化。

| RQ                                  | 正式物理数据            | 计算/审计数据                                           | 能支持的结论                                                                     |
| ----------------------------------- | ----------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------- |
| RQ1：物理效果与轨迹重分配           | Stage I                 | `t(σ)`、Z1–Z5、执行激励                             | 高风险路径上的液面响应、任务代价和局部轨迹变化                                   |
| RQ2：竞争性 timing 解释             | Stage I                 | reference/prediction/execution 分层                     | 排除整体减速；检验 fixed timing 是否已足够                                       |
| RQ3：模型状态相关 online generation | Stage I 的 S-MPCC 日志  | 四相位、online-input/zero-state replay、执行链、runtime | 内部模型状态是否改变完整 horizon 和第一动作                                      |
| RQ4：条件性路径差异与有限迁移       | Stage II-A；条件性 II-B | batch-restricted effect-difference/参数 replay          | 经 Stage I gate 选择后的路径差异 supporting evidence；满足门槛时的有限跨容器迁移 |

轨迹变化是机制证据，`H_vis` 是物理效果证据；二者不能相互替代。

### 1.1 在线 RGB 与无视频录包政策（2026-07-31 冻结方向）

从 G2S 开始，G3 和后续 formal trial 均采用 **在线 RGB 检测、只录派生数值** 的存储政策。RealSense 原始图像仍在运行时输入检测节点，但不得写入实验 bag：

- 在线节点必须使用冻结 calibration、ROI/三标尺、HSV、零点帧数、处理频率及手动曝光/增益/白平衡；`publish_debug=false`；
- 主证据为 `/liquid/measurement`：每条消息复制源图像 `header.stamp`，并记录 max-LCR、三列高度、置信度、裁剪、零点锁定、零点原始样本及其时间窗、无效原因、源图尺寸和处理延迟；`/liquid/height*` 只用于现场画曲线；
- bag 可记录 `/camera/color/camera_info`、ROS 参数快照、calibration/config/algorithm/message SHA-256 和在线派生标量；
- bag 中 `/camera/color/image_raw`、compressed RGB、depth、`/liquid/debug_image`、`/liquid_measurement/debug_image` 及任何 `sensor_msgs/Image`/`CompressedImage` 必须为 **0 条**；recorder 和 postflight 都须 fail closed；
- 运动前必须现场确认 ROI/容器姿态仍匹配，并等待在线量达到 `zero_locked + valid + status=OK`；运动段及冻结 tail 内须达到预声明的时间覆盖、频率、有效率、NaN/裁剪和 timestamp-lag 门；
- 因为不保存原视频，采集后不能换 HSV、重画 ROI 或重新跑视觉算法。在线质量门失败的 attempt 必须原样归档并按冻结 failure/retry 规则处理，不能把缺失图像事后“补算”为有效结果。

该政策去掉 1920×1080@30 Hz 原始 BGR 约 `16.8 GB/90 s` 的理论图像负载；节省的是视频流，控制、IMU、observer、solver、TF、在线视觉标量和 sidecar 仍须完整保留。正式第一条前还要以 smoke 实测在线节点最低频率和 CPU 占用，再冻结最终门限。

## 2. 五个比较条件

### 2.1 条件定义

| 条件 ID          | 论文名称                     | 执行 backend                     | 液体参数 | runtime 内部模态状态 | 作用                            |
| ---------------- | ---------------------------- | -------------------------------- | -------: | -------------------: | ------------------------------- |
| `B0`           | Baseline MPCC                | online MPCC，variant`B0`       |       否 |                   否 | 普通 MPCC 锚点                  |
| `Bsmooth`      | Smooth-only MPCC             | online MPCC，variant`B_smooth` |       否 |                   否 | 检验通用平滑                    |
| `SmoothMatch`  | Smooth-match MPCC            | `B_smooth` + 冻结 `v_ref`    |       否 |                   否 | 检验等完成时间整体减速          |
| `FixedProfile` | Model-informed fixed-profile | 离线 profile + 冻结 tracker      |       是 |                   否 | 检验 physics-aware fixed timing |
| `Bslosh`       | S-MPCC                       | online MPCC，variant`B_slosh`  |       是 |             模型传播 | 本文方法                        |

`B0`、`Bsmooth`、`Bslosh` 是共同 OCP 的三个内部 variants。`SmoothMatch` 是独立冻结的完成时间 comparator。`FixedProfile` 是另一套 timing-generation/tracking system，不是 OCP 开关，也不是单因素 memory 消融。

odom/IMU 是 `Bslosh` 当前状态 observer 的**输入语义选择**，不是新的比较条件。IMU shadow 的有无也不能改变上表五条件身份。若 formal 保留 odom，默认关闭在线 IMU shadow，仅记录 raw IMU 供冻结后的离线 supporting analysis；若希望 formal 在线保留 shadow，必须预先证明其 CPU/回调开销不改变条件公平性，并在所有技术上适用的条件中采用同一冻结政策。

### 2.2 MPC 代价权重：当前执行值与待冻结边界

以下数值来自当前 `config/planner/variants.yaml` 和 runner 实际覆盖，是 G2S/G2C 唯一允许的候选集合口径；`W1` 已淘汰，`W2/W5` 尚未由 G2C 冻结为唯一正式 `Bslosh`。

所有列出的 MPCC 条件共同使用：

```text
w_contour=1.0, w_lag=0.2, w_progress=0.2
w_v=1.0, w_vs=0.3, w_accel=0.0
```

| 用途/条件 | `w_control` | `w_smooth` | effective `w_alpha=w_du_a=w_du_vs` | `w_slosh` | effective `w_eta` | effective `w_eta_dot` | `v_ref` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `B0` | 0.1 | 0.1 | 0.1 | 0 | 0 | 0 | YAML 默认 0.25 |
| G2S `Bsmooth` | 0.3 | 1.0 | 1.0 | 0 | 0 | 0 | **runner 覆盖 0.20** |
| G2C `W2` (`B_slosh`) | 0.1 | 0.1 | 0.1 | 2 | 2 | 0.6 | G2C prereg 待冻结 |
| G2C `W5` (`B_slosh`) | 0.1 | 0.1 | 0.1 | 5 | 5 | 1.5 | G2C prereg 待冻结；当前 YAML 默认候选 |

`w_alpha/w_du_a/w_du_vs` 未在 YAML 单独赋值时由 `w_smooth` 继承；`w_eta=w_slosh`，`w_eta_dot=0.3 w_slosh`，其中 `0.3` 来自当前 C1/tube `slosh_eta_dot_ratio`。G2C 必须显式覆盖 W2，不能因 YAML 的 `B_slosh=5` 默认值把 W2 错跑成 W5。最终 formal 的 `Bslosh` 权重、`v_ref`、容器参数和 effective-config hash 只允许由 G2C/freeze 决定；当前表不是提前宣布 W5 获胜。

`SmoothMatch` 继承冻结后的 `Bsmooth` 代价，只允许改变已预声明的一个 `v_ref` 以匹配完成时间。`FixedProfile` 不使用这组在线 MPCC OCP 权重。

### 2.3 Fixed-profile 的唯一候选定义

v2.0 默认候选是 Hamaguchi-inspired two-impulse ZV fixed-path timing：

- 读取相同冻结路径、$\omega_1$、$\zeta$ 和共同硬限制；
- ZV 脉冲幅值和 $\Delta T$ 由 $\omega_1,\zeta$ 决定并保持固定；
- 只允许调一个预声明的 **unshaped base-profile timing 参数**；
- 每个候选必须从 base profile 重新生成、整形、积分并检查硬约束；
- 显式处理纵向激励和固定路径上的 $a_y\simeq v^2\kappa=v\omega$；
- 从与正式静稳门一致的零/近零名义液体初态生成，并记录该假设；
- 禁止对已经生成的 shaped profile 做 time-warp；
- 正式 trial 只能加载冻结 profile，禁止现场重生成；
- 记录 profile reference、tracker error/latency、method-native raw command、共享执行层输出和实际 odometry；
- 只称 prior-art-inspired end-to-end comparator，不称 Hamaguchi/Lim 的忠实复现。

仓库已有候选生成器：

- `src/scout_apps/control/scout_profile_baselines/scripts/hamaguchi/generate_profile.py`
- `src/scout_apps/control/spmpc_experiments/config/profile_baselines/hamaguchi_profile.yaml`
- `src/scout_apps/control/spmpc_experiments/scripts/run_fixed_path_profile_baseline_suite.sh`

但现有 suite 明确是 current-sim/development 链，并调用 simulation launch；它不是正式实物 runner。当前生成器还需要审计 base-profile 参数与 hard `v_max` 是否分离，以及 endpoint distance scaling 是否改变固定脉冲 timing。完成这些审计和实物集成前，`FixedProfile` formal condition 为 `NO-GO`。

## 3. 正式矩阵：40 → 64 → 条件性 88

### 3.1 分阶段矩阵

下表中的 `n=8` 是当前资源提案，不是统计保证。只有样本量计算冻结后，40/64/88 才成为正式名称。40/64/88 始终计 **planned units**；允许的 acquisition retry 会使实际 physical attempts/bags 多于该数字，但不会扩大确认性样本量。

| 阶段                                 | 配置        | 每个 randomized block 的条件                                       | block 数 | 新增 | 累计 | 主要作用                                                  |
| ------------------------------------ | ----------- | ------------------------------------------------------------------ | -------: | ---: | ---: | --------------------------------------------------------- |
| Stage I /`S1_CORE`                 | `C1 + H1` | `B0`、`Bsmooth`、`SmoothMatch`、`FixedProfile`、`Bslosh` |        8 |   40 |   40 | RQ1–RQ3 核心证据                                         |
| Stage II-A /`S2A_SELECTIVITY`      | `C1 + L1` | `Bsmooth`、`FixedProfile`、`Bslosh`                          |        8 |   24 |   64 | RQ4 条件性、batch-restricted 路径差异 supporting analysis |
| Stage II-B /`S2B_TRANSFER`，条件性 | `C2 + H1` | `Bsmooth`、`FixedProfile`、`Bslosh`                          |        8 |   24 |   88 | RQ4 有限配置迁移                                          |

Stage I 每个 block 包含五个**不同条件**，每个恰好一次。旧 v1.0 中第二次 `Bslosh` 已由 `FixedProfile` 替代；不存在 E2/E3 子组，也不存在可复用的旧五次顺序。

Stage II 不包含 `B0` 和 `SmoothMatch`。因此 Stage II 只解释为 liquid-response–efficiency–tracking 联合结果，不声称严格等完成时间因果效应。若希望在 Stage II 继续做严格时间匹配，必须增加 `SmoothMatch` 并重新计算矩阵，不能继续使用 64/88 计数。

不定义 96 或 104 个正式单元。物理参数 mismatch、长时传播和额外 planner 比较只能另立 exploratory protocol，不得追加到本矩阵。

### 3.2 Formal 前输入源试验不计入 40/64/88

`G2S` 使用同一条 development trial 同时得到 odom observer、processed-IMU observer 和 RGB，因此它不是 odom/IMU 两个控制条件，也不进入 formal 分母。`n_src` 表示预冻结的 planned paired units，不因 acquisition retry 增加；每次物理 attempt 仍须独立编号并进入完整 attempt/reliability 分母。为避免反馈选择偏差，输入源比较默认使用不消费液体状态的 `Bsmooth` 产生代表性运动，并使用专门保留的 `H0s` development 路径；不得占用 H1/L1，也不得把 `G2S` RGB 用于正式效果检验。

如果 `G2S` 最终保留 odom，正式矩阵保持不变。如果 `G2S` 触发 IMU 新 release，则 40/64/88 在新 release 完成全部前置门禁前继续 `NO-GO`，旧 odom 与新 IMU trial 不得拼接。

### 3.3 样本量冻结

正式 `n` 必须根据以下量计算并归档：

- 最小有意义 `H_vis` 效应 $\delta_H$；
- 独立 development block 的 paired variability；
- 目标区间宽度或 power；
- 方法失败和视觉无效率余量；
- Stage II 等价/非劣界所需精度。

如果冻结结果不是 `n=8`，所有表、随机表、目录说明和 40/64/88 名称必须同步改为 `5n / 8n / 11n`，不能只在现场多跑或少跑。

特别是二元 success 的等价/非劣结论不能只沿用连续 `H_vis` 的样本量。若 `n=8` 无法使 success 差值区间达到预声明界限所需精度，只能报告 success 比例、区间和**操作性容限**，不得称统计非劣；是否扩大 `n` 必须在第一条 formal trial 前决定。

### 3.4 随机化

v2.0 不在本文内嵌临时顺序。正式前必须在 `n`、五条件身份和 Stage II 是否保留后生成并 hash：

```text
freeze/randomization/
├── stage1_five_condition_order.csv
├── stage2a_three_condition_order.csv
├── stage2b_three_condition_order.csv
├── generation_record.yaml
└── sha256.txt
```

要求：

- Stage I 使用位置尽可能平衡的五条件 complete-block 表；
- Stage II-A/B 分别生成独立三条件表；
- 每条 formal row 冻结 `PLANNED_BLOCK_SEGMENT_ID`；每次 attempt 的 `ACTUAL_BLOCK_SEGMENT_ID/SPLIT_BLOCK` 只能由 append-only execution evidence 提供，且必须满足 `SPLIT_BLOCK == (ACTUAL != PLANNED)`；
- 不把不同路径、容器或日期的同编号 block 强行配对；
- actual randomization/permutation inference 必须复现这些真实 assignment，且只能用于第 8.1 节对每个 planned row 都有定义的冻结 failure-inclusive estimand；
- paired sign-flip 若保留，只作对称性假设下的敏感性，不能称设计的 exact test；
- 随机表不存在或未通过 validator 时 formal `NO-GO`。

### 4.2 路径

`H1` 必须包含：

- 起步加速；
- 持续曲率；
- 曲率符号反转；
- 退出后的再加速；
- 终端制动。

`L1` 保持相同任务接口，但显著降低最大曲率、曲率变化率和激励。它是 selectivity condition，不是依靠“不显著”即可通过的负对照。

H0/H0b/H0s development 路径不得与 held-out H1 正式路径混用。H0/H0b/H0s、H1、L1 均保存 JSON、长度、曲率、Z1–Z5、图和 SHA-256。`H0s` 专用于输入源选择；一旦查看其 RGB 后不得改滤波或对齐参数并继续称同批数据 held-out。

### 4.4 trial 准入

每次 trial 使用相同、方法无关的准入：

1. 起点位置与航向进入冻结门限；
2. `/cmd_vel` 为零且只有计划中的 publisher；
3. 容器固定、液深、泄漏和相机状态合格；
4. 适用 backend 的内部方法状态 reset 成功，公共 monitor 独立 reset；
5. 等待 ring-down 验证的 `T_SETTLE`，且不超过冻结的最大 admission wait；
6. 可选方法无关 monitor 合格；
7. recorder 已收到带源图时间戳的 `/liquid/measurement`，并确认 bag 选择表不含任何图像流；
8. 在线 visual-start QC 使用冻结规则，满足 `zero_locked + valid + status=OK`、分辨率、手动相机参数和最短连续有效窗口；
9. 超过最大等待或在线可判定无法静稳时，在运动前阻断并按方法无关 acquisition failure 归档；
10. postflight 发现在线 visual-start/motion/tail 覆盖、有效率或时间戳门不合格时保留原 attempt，并按冻结 acquisition/method-failure 规则处理；若导致跨时段恢复，则按 split-block 规则处理。

`G2S` development 若启用 IMU shadow，还必须采用更严格的自动顺序：replay 模式先确认 reference/cmd/IMU-debug 无残留 publisher（generate 模式另含 goal），启动 recorder 并确认 `.bag.active`，再启动 planner；车辆保持静止直至 `/spmpc/debug/slosh_observer_imu` 同时满足 `READY + valid + bias_ready + filter_ready`，之后才允许启动 path/start gate。超时、bias motion、frame mismatch、sample gap 或 recorder 提前停止均在运动前 fail closed。

runner 退出 0 不等于 G2S trial 合格。闭包后还必须独立验证 bag 可读、无 `.bag.active`、required-topic message count、完整有效运动/在线 RGB 标量/tail、图像话题计数为零，以及 planner READY 后的最终参数快照；缺任一证据时保留 bag，不进入 paired continuous-error 的 eligible denominator。attempt-level acquisition/readiness/postflight 状态进入完整可靠性账本，source-ready 与 method-success/failure 则以固定 planned-row 分母报告，不能混用。

运动前 2 s 在线 RGB 有效标量只是名义采集窗口，不单独证明液体已经静稳；recorder-ready/首个 `zero_locked+valid` 源图时间戳与 first effective motion timestamp 必须留证，并在 bag 后验证覆盖不少于冻结的 2 s 门槛。

### 5.2 G2A：既有候选筛选与内部审计

当前 G2S/G2C/G3 development wrappers 有意采用更严格合同：不支持 `SPLIT_BLOCK` recovery。跨 segment 如仍需采集，只能另立 `RECOVERY_OBSERVATION` 并进入 reliability ledger；它不能占用该 gate 的 `r02+` slot、替代 planned row、恢复 paired eligibility 或参与 gate PASS。只有 future wrapper 同步实现 planned/actual segment、postflight 和 verifier 字段后，才可修改此边界。

### 6.2 实际轨迹

actual timing 只能由 `s_proj` 得到。正式前冻结：

- 连续/最近点投影；
- monotonic guard、backtracking、jump、stall；
- first-arrival、interpolation、cross-track 和 terminal 规则；
- `t(σ)` 与 Z1–Z5 traversal time；
- braking、entry/reversal speed、re-acceleration features；
- 单一 constant speed scaling residual；
- 同步、滤波和微分规则；
- executed $a_x\simeq\dot v_{odom}$ 的 RMS 与 $|a_y|\simeq|v_{odom}\omega_{odom}|$ 的 p95。

由于每周期初始化满足 `s_ocp,0|j=s_proj(t_j)`，当前节点之差恒为零，不能作为结果。若保留 forecast diagnostic，只比较 `k>0` 的

$$
e_s(k|j)=s^\star_{ocp,k|j}-s_{proj}(t_j+k\Delta t)
$$

并冻结未来 odometry 插值、有效 horizon 和汇总规则。

### 6.3 outcomes

- Primary physical outcome：`H_vis,p95(motion+tail)`，成功 trial 的窗口从 first effective motion 到 first arrival 后统一冻结的 `T_HVIS_TAIL`；当前候选为 5 s，canonical 数值与窗口规则必须在首条 G3 trial 前冻结，并由 G6/formal 原样继承，且 `T_POST_RECORD >= T_HVIS_TAIL`；
- 关键 sensitivity：10%–90% progress-window p95；
- Secondary：motion-window p95、统一 tail RMS、completion、tracking p95、success；
- Trajectory/mechanism：`t(σ)`、Z1–Z5、局部制动/再加速、constant-scaling residual、`a_x/a_y`、`H_modal`、`r_int`；
- Runtime：median/p95/max、budget overrun、failure、fallback、achieved frequency。

failure/timeout trial 没有 first arrival 时，在线 RGB 标量仍按预冻结规则覆盖至 first effective motion 后 `T_MOTION_MAX + T_HVIS_TAIL`；安全停止后保持零命令并继续记录，不得再次激励液体。若安全要求立即断电或 tail 不完整，该 row 的 continuous `H_vis` 标记 ineligible，但其 method-failure planned-row outcome 仍进入第 8.1 节的 failure-inclusive estimand，不能用成功补跑替换。

planned unit 是统计单位；每个 planned row 按冻结规则最多贡献一个 eligible trial-level outcome。physical attempt 是 acquisition/readiness/postflight reliability ledger 单位，retry 不产生第二个统计样本；在线 RGB measurement frame、control cycle 和 path point 也不是独立样本。

### 6.4 K6-style supporting diagnostic

完整 modal–vision fidelity 只是 supporting diagnostic。可用 S-MPCC planned units 为：

- Stage I 后 8；
- Stage II-A 后累计 16；
- 条件性 Stage II-B 后累计 24。

K6 必须使用单一冻结脚本、同步规则、lag policy、solver 实际输入源和固定的 S-MPCC planned-unit 分母，同时另报 eligible count 与全部 acquisition/method failure。不得再使用旧 K6=32 分母；B0、Bsmooth、SmoothMatch、FixedProfile 的缺失/零内部状态不能充作 K6 样本；未被 solver 使用的 IMU shadow 不能替代 Bslosh 的正式 `H_modal`。K6 不能验证 signed phase 或 rotation consistency。视觉 measurement admission 即使不做完整 K6 也必须通过。

## 7. 分阶段执行与 claim gates

### 7.1 Stage I：40 个单元

每个 block 按新的五条件随机表连续执行：

```text
S1_CORE_H1_C1_<CONDITION>_b<BB>_r<AA>
```

`<CONDITION>` 只允许 `B0`、`Bsmooth`、`SmoothMatch`、`FixedProfile`、`Bslosh`。

四个与 Bslosh 相关的 contrasts 共享同一个 block-level Bslosh observation。不得重复采集第二个 Bslosh，也不得把旧 E2/E3 trial 拼入。

确认性顺序固定为：

1. `Bslosh - Bsmooth`：第一物理主比较；
2. 第一步通过后，`Bslosh - FixedProfile`：关键 novelty comparison；
3. 完整主张还要求 SmoothMatch completion-time gate 和 success tolerance 成立；
4. `Bslosh - B0` 为关键次比较，`Bsmooth - B0` 为机制诊断。

SmoothMatch、Baseline 和其他次比较必须使用预声明层级或 Holm 调整，不能根据结果临时提升为主比较。

FixedProfile 比较是 end-to-end system comparison，不单独证明动态 memory 的物理因果必要性。

### 7.2 Stage I 后的扩展 gate

只有预注册 gate 全部满足，才进入 Stage II：

- 40 个 planned units 和全部额外尝试均可追溯；
- 在线 RGB stamped-quality/同步/visual-start/motion/tail QC 达到冻结有效率，且 bag 的 image-stream audit 为 0；
- `Bslosh - Bsmooth` 达到 $\delta_H$、区间和 randomization 规则；
- SmoothMatch 完成时间门与物理方向成立；
- `Bslosh - FixedProfile` 按固定层级达到预声明 novelty 准则；
- success、tracking、runtime 和 `r_int` 不超过冻结容限；
- 结果不由单一 block 独占，leave-one-block-out 方向稳定；
- trajectory extractor、纵横向四相位、`Bslosh` online-input replay 和 execution-chain audit 可运行。

未通过时停止扩展并按冻结分析报告，不通过增加 L1/C2 包装核心失败。任何方法、权重、路径、视觉处理或分析修改都会结束当前 release；新版本从 formal block 01 重新开始。

### 7.3 Stage II-A：累计 64

`C1+L1` 每个 block 运行 `Bsmooth`、`FixedProfile`、`Bslosh`：

```text
S2A_SELECTIVITY_L1_C1_<CONDITION>_b<BB>_r<AA>
```

只有第 7.2 节的 Stage I extension gate 已形成不可变 `PASS` report/hash，才可启动 Stage II-A；口头判断或单独的布尔变量不能放行。

“选择性”必须依据预冻结的 completion、tracking、success、intervention 等价/非劣界，以及 H1→L1 effect-difference 规则；普通不显著不能证明等价。由于 L1 仅在 Stage I extension gate 通过后采集，复用 Stage I H1 的 H1→L1 结果只能称为 **batch-restricted supporting analysis**，不能写成无条件路径因果 interaction；更强主张需要同期、预注册且随机/平衡的 H1/L1 复现，或预声明的选择后推断。

`S2A_SELECTIVITY_ANALYSIS_RULE_SHA256` 必须在 Stage I 前冻结。对 primary comparator（默认候选 `Bsmooth`，最终以该 rule 为准）和预声明的 `FixedProfile` 次比较，先在各自路径内部定义

$$
I_{p,b}^{(m)}=Y_{m,p,b}-Y_{Bslosh,p,b},\qquad p\in\{H1,L1\},
$$

主公式中的 $Y$ 固定为 lower-is-better 的 `H_vis,p95(motion+tail)`，因此正值表示 `Bslosh` 降低液面响应；再报告 batch-restricted effect difference

$$
D^{(m)}=\overline I_{H1}^{(m)}-\overline I_{L1}^{(m)}.
$$

H1 与 L1 使用各自 complete blocks，禁止按相同 block 编号跨 batch 强配对。completion/tracking 等其他连续 outcomes 若进入 effect-difference，必须在 rule 中先做明确的方向变换；success 与 intervention 使用各自冻结的二元/等级 estimand，不得直接套用上述符号。rule 还必须冻结最小差异/区间门槛、L1 completion/tracking/success/intervention 的等价或非劣界、multiplicity 和缺失/failure sensitivity。`S2A_COMPLETION` 的 `PASS` 只表示 24 个 planned units 与全部 attempts 已闭包，不等于科学结论成立；另行生成 `S2A_SELECTIVITY_ANALYSIS` report/hash，`selectivity_status` 只允许 `SUPPORTED/NOT_SUPPORTED/INCONCLUSIVE`，并绑定 Stage I/S2A dataset indices、两阶段 per-contrast denominator indices 和该 rule hash。每个 H1/L1 comparator 必须分别给出 `N_block_plan/minimum_N_pair/N_pair/valid_unpaired/method_failure/unresolved_acquisition`，不能只报 aggregate partition。

### 7.4 Stage II-B：条件性累计 88

以下资格和规则必须在 Stage I 前写入 manifest；其中 `stage2b_enabled=true` 只表示该条件分支已预注册，不等于已经触发：

- `stage2b_enabled=true`；
- C2 实物和全部参数；
- C2 profile/hash；
- 独立三条件随机表；
- within-C2 `H_vis` 最小效应、任务代价、success 容限；
- primary comparator 和 transfer pass rule；
- 预声明 trigger/stop rule。

实际进入 Stage II-B 还必须在 Stage II-A 全部 24 个 planned units 及所有额外 attempts 可追溯后，归档不可变的 Stage II-A completion `PASS` report/hash 和独立的 `S2A_SELECTIVITY_ANALYSIS` report/hash，再用预声明规则生成绑定二者的 Stage II-B trigger `PASS` report/hash。trigger rule 必须预先声明三种 `selectivity_status` 中哪些允许扩展。缺任一报告、报告 hash 不匹配或 trigger 未通过，都停在累计 64，不得从 Stage I 直接跳到 Stage II-B，也不得为凑到 88 临时改 trigger。

run label：

```text
S2B_TRANSFER_H1_C2_<CONDITION>_b<BB>_r<AA>
```

结果只支持所报告配置间的有限迁移。参数 correct/incorrect replay 只能证明 optimizer sensitivity。物理响应同时报告原始物理单位与按冻结 freeboard 定义归一化的单位。

## 8. 随机分析、失败和 retry

### 8.1 统计单位与推断

对 eligible、method-success trial 的连续 outcome `Y_succ`，block difference 为

$$
\Delta_{b,succ}^{m-m'}=Y_{m,b}-Y_{m',b}.
$$

报告 raw points、paired lines、mean paired difference、relative change、whole-block bootstrap interval 和 leave-one-block-out；这些是明确标注的 **success-conditional** 估计与区间。

G6 还必须冻结唯一的 failure-inclusive hierarchical win–loss estimand `Y_plan`，并使每个 planned row 都有确定贡献：method success 优先于 method failure；两者都 success 时先按 `H_vis,p95(motion+tail)` 与冻结的 $\delta_H$ 判 win/loss/tie，再按预声明 completion/tracking tie-breaker；两者都 method failure 时按冻结 severity 或 tie 规则；方法无关 acquisition failure 在耗尽授权 retry 后按预声明 no-information tie 编码，并同时报告 best/worst missingness sensitivity。不得查看结果后改层级、tie rule 或改用另一种 worst-rank 分析。

exact/randomization inference 只允许用于上述对所有 planned rows 都有定义的 `Y_plan`，并必须复现实际随机表允许的 assignments。由 method failure、fallback、运动后 RGB QC 或其他 post-treatment 事件筛出的 eligible pairs 不能称设计意义的 exact test；其 `Y_succ` 只报告条件性效应、区间与敏感性。不能把 control cycles 当样本，也不能根据显著性重排主次。

### 8.2 固定分母

所有 planned units 和**每一次** physical attempt 都保留在 dataset index 与 exclusion log，但不得共享一个模糊的 “failure denominator”。每个 stage/condition/contrast 固定并同时报告：

- `N_plan`：planned rows；确认性样本量，以及 method success/failure 的唯一分母；
- `N_attempt`：所有 physical attempts；只用于 acquisition/readiness/postflight 可靠性，例如 `N_acquisition_failure_attempt/N_attempt`，retry 会增加它；
- `N_method_success/N_plan` 与 `N_method_failure/N_plan`：每个 planned row 只计一次，retry 不得稀释方法失败率；
- `N_pair/N_block_plan`：满足冻结 continuous eligibility 的 complete block pairs，只用于 `Y_succ` 条件性连续效应，不能代替前述分母。

每个 contrast 还必须报告 `Y_plan` hierarchical win–loss、success 比例及区间、全部额外 attempts 和 exclusion log。只有样本量/区间达到冻结界限时才使用“统计非劣”；否则 success gate 只称操作性容限。

这些逐 contrast 字段必须进入不可变 CSV index，最小 schema 为 `stage,contrast_id,path_id,n_block_plan,minimum_n_pair,n_pair,valid_unpaired_planned_row_count,method_failure_planned_row_count,unresolved_acquisition_planned_row_count`。首条 formal trial 前另冻结 contrast registry CSV/hash，其最小 schema 为 `stage,contrast_id,path_id,n_block_plan,minimum_n_pair`。每份 denominator index 的 contrast set 必须与对应 stage/path 的 registry 子集完全相等，`n_block_plan/minimum_n_pair` 逐行相同；在本 40→64→88 协议中 S1/H1 与 S2A/L1 均固定为 `n_block_plan=8`。还必须满足 method failure + unresolved acquisition 不超过 `2*n_block_plan`，以及 `2*n_pair + valid_unpaired_planned_row_count` 不超过由 planned-row partition 推得的 method-success rows。冻结 verifier 不得信任 CSV 自报计数，必须从完整 dataset index、chosen-attempt/retry chain、segment/split、continuous eligibility 与 failure 分类重新推导；进入下一 stage 前，适用 contrast 还必须满足 `n_pair>=minimum_n_pair`。index 必须与 `DENOMINATOR_SCHEMA_SHA256` 一致；Stage I extension report、S2A completion/analysis report 分别绑定适用 index/hash 和 verifier hash，S2A analysis 同时绑定 H1 与 L1 两份 index。S2A completion 可在未达 minimum 时仅报告数据闭包与 `INCONCLUSIVE`，但不得触发 Stage II-B。

### 8.3 development/formal 允许 retry 的 acquisition failure

`r<AA>` 中首次 attempt 固定为 `r01`。只有冻结且对 condition label 盲化的 classifier 能证明故障发生在方法作用之外、并且与 assignment 无关时，才可授权 `r02+`。允许候选仅包括：运动前相机/rosbag/在线检测未启动；运动前时间段按冻结规则判定的 visual-start QC 不合格；可由独立日志证明的外部存储/相机硬件中断；方法无关现场侵入。运动后在线视觉无效或 tail 不完整不能仅凭结果归为 acquisition failure；由于协议明确不录原视频，这类数据也不得事后换算法恢复。

condition-specific runner/profile/config 拒绝或不匹配、冻结 assignment/environment 配置错误、backend/topic/CPU 压力造成的丢帧，以及由车辆运动引起的遮挡、clipping、振动或相机失效，均不得授权替代性 retry：前两类按冻结 protocol/readiness 规则停止并审计，后两类按 method/measurement failure 进入 planned-row 结果。最大 repeat 次数和超限后的缺失处理必须在首条对应 gate/stage trial 前冻结，runner 不得自动 retry。

要求：

- 已产生的原 bag、sidecar、启动日志和原因永久保留；若故障本身导致 bag/postflight 不存在，failure record 必须显式记录 `artifact_missing` 及可验证的启动日志，不能伪造空 bag；
- 外部冻结 verifier 必须在新 attempt 前签署唯一 retry-authorization report，绑定 planned row、失败 `ATTEMPT_ID`、失败证据 hash、failure class、release/revision、`PLANNED_BLOCK_SEGMENT_ID` 和前后 attempt 的 `ACTUAL_BLOCK_SEGMENT_ID`；仅靠操作者设置 `ACQUISITION_RETRY=true` 不构成授权；
- 新 attempt 记录唯一 `ATTEMPT_ID`、`DEV_REPEAT/REPEAT`、`RETRY_OF_ATTEMPT_ID`、`RETRY_REASON_FILE` 及其 hash，形成不可断裂的 retry chain；
- retry 使用相同 condition、backend、profile/config hash；
- formal 中，只有 `ACTUAL_BLOCK_SEGMENT_ID == PLANNED_BLOCK_SEGMENT_ID`、且与失败 attempt 同 segment/冻结环境内完成的授权 retry 才能保留主配对资格；预分配的跨 segment recovery 必须标记 `SPLIT_BLOCK=true` 并进入 reliability ledger，不能替代该 row、恢复主配对或与另一 segment 强行配对；当前 development wrappers 则按第 5.3 节明确不消费 split-recovery slot；
- 每个 planned row 最多贡献一个 eligible outcome；全部失败和额外 attempts 仍进入相应 `N_plan`/`N_attempt` 账本，不得从 G2S、G2C、G3 或 formal dataset index 删除。

solver、tracker、profile execution、tracking、timeout、安全终止和方法相关命令异常均为方法失败，不得用成功重跑替换。observer-source fallback 按第 1 节固定计为 method failure；其他 execution/fallback 也是必须保留的方法相关事件，其 trial/event-level 判定必须在首条 formal trial 前冻结，不能现场决定。

冻结身份采用两层：首条 formal trial 前的静态 `FREEZE_ID` 覆盖协议、代码/config、随机表、failure/retry 规则、最大 repeat 和预分配 run slots；采集后才出现的 retry authorization、stage-entry report、dataset index 与 chain head 进入引用同一 `FREEZE_ID` 的 append-only execution-evidence ledger，不反向重算 `FREEZE_ID`。由 `FREEZE_ID` 派生且内部引用它的 validation report、`RUN_ENV` 和 index 只能作为 anchored outputs 登记，其自身 hash 不得反向作为 `FREEZE_ID` 输入，避免自引用。动态证据只能放行既有 slot，不能覆盖 condition/backend/path/config/profile/source 或分析规则。
