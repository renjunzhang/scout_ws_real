## 1. 目的与非目的

本次升级的唯一目的，是在未来首次使用 unprivileged user/network namespace 作为液体工具
隔离边界之前，使宿主运行 Canonical 当前提供的 ESM 安全内核。

本次操作不是：

- Ubuntu 20.04 到 22.04 的发行版升级；
- ROS Noetic、Gazebo、CUDA 或 NVIDIA 驱动大版本升级；
- 全量 `apt upgrade`、`full-upgrade` 或 `dist-upgrade`；
- 清理旧内核、执行 `autoremove`；
- 放行 QEMU machine-none、镜像、VM、GenCase 或 DualSPHysics；
- 修改 `/home/a/scout_ws` 或 `/data/a` 中的实验数据。

## 3. 总体安全原则

1. **目标安装**：只安装 HWE kernel meta、image、headers及 NVIDIA 570 对应的预编译
   kernel modules，不做系统全量升级。
2. **旧内核不可删除**：保留 `5.15.0-139` 和它的 NVIDIA 570 模块作为第一回退路径。
3. **先下载、后安装**：先模拟，再只下载并核验 transaction，最后离线使用缓存安装，避免
   dpkg 事务中途依赖网络。
4. **先模块、后重启**：新内核的 NVIDIA 和 RealSense 模块全部验证通过后才可重启。
5. **不自动修复**：任何 DKMS、dpkg、initramfs 或 GRUB 异常都停止并审查，不自动 purge、
   autoremove、改 GRUB 或执行来源不明的修复命令。
6. **不并行运行仿真**：升级、重启和验证期间停止 ROS、Gazebo、QEMU、CUDA计算、GenCase。
7. **不扩大液体权限**：内核升级成功不自动放行 machine-none；重启后仍要生成全新的
   boot-bound admission 并独立审查。

2026-08-06 的 APT 模拟已经证明第 1 条所设想的“新内核 + 570 预编译模块”在当前仓库候选中
不可实现：名称带 570 的 HWE 元包会迁移到 580。因此原方案不得直接进入下载或安装阶段。

### 阶段 C：只下载，不安装

模拟完全通过并经人工复核后，才允许把同一组精确版本下载到 APT cache：

```bash
sudo apt-get --download-only install --no-install-recommends \
  <阶段B冻结的精确包=版本列表>
```

下载后重新检查包来源、版本和 transaction；不得执行手工下载的未知 `.deb`，不得使用
第三方脚本安装内核或 NVIDIA 驱动。

### 阶段 D：受控安装

用户再次批准后，从已下载缓存安装同一组精确版本：

```bash
sudo apt-get --no-download install --no-install-recommends \
  <阶段B冻结的精确包=版本列表>
```

禁止同时运行其他 APT/dpkg 进程。安装期间不得强制中断、关机或重启。

如果出现以下任一情况，安装阶段停止为 `NO-GO`：

- dpkg 返回非零；
- initramfs 或 GRUB生成失败；
- NVIDIA kernel module package 配置失败；
- RealSense DKMS编译失败；
- 磁盘空间低于安全阈值；
- transaction 与模拟结果不一致。

失败后不自动执行 `dpkg --configure -a`、purge或修复；先保留日志并单独审查。

### 阶段 E：重启前硬验证

假设新候选仍为 `5.15.0-186-generic`，至少要求：

```bash
test -r /boot/vmlinuz-5.15.0-186-generic
test -r /boot/initrd.img-5.15.0-186-generic

modinfo -k 5.15.0-186-generic -F filename nvidia
modinfo -k 5.15.0-186-generic -F version nvidia
dkms status
```

必须满足：

- 新 kernel 与 initrd存在；
- 新内核的 NVIDIA module来自 Canonical `nvidia-570` 路径；
- NVIDIA module版本仍为 `570.133.07`，除非另有单独批准；
- 新内核 `linux-modules-nvidia-570-*` 和 signatures package状态为 installed；
- RealSense DKMS显示对新内核 `installed`；
- old kernel `5.15.0-139` 的 kernel、initrd和 NVIDIA modules仍完整；
- GRUB同时含新旧两个入口；
- `apt-mark showhold` 与升级前一致；
- 没有 dpkg pending/broken package。

任一失败：**禁止重启进入新内核**。

### 阶段 F：人工重启

重启是单独的用户批准点。重启前关闭并保存所有实验；不与 Gazebo/QEMU/GenCase 同时运行。

首次启动新内核后只做宿主验证，不立即运行液体或原 Gazebo 对比实验。

#### G1. 内核与启动状态

#### G2. NVIDIA

```bash

```

要求：RTX 3060仍绑定 `nvidia`，模块版本和用户态库一致。由于升级前真实宿主基线为

随后再按需检查 OpenGL renderer、CUDA和 Gazebo渲染。不能一开始就启动完整仿真实验。

#### G3. RealSense及其他硬件

```bash

```

#### G4. ROS/Gazebo

宿主、显卡和传感器基线全部通过后，才按原仿真启动指南做最小 ROS/Gazebo smoke。

- 新 kernel/package状态；
- 当前桌面不可读进程 allowlist；
- policy/schema/gate/tests哈希；

- 新的 create-new singleton attempt/receipt名称。

重新独立审查通过后，才讨论非 QEMU ELF canary和一次性 machine-none live smoke。

## 6. 回退方案

### 6.1 新内核启动失败或显卡不可用

1. 重启进入 GRUB；Lenovo设备通常在启动时按住/连续按 `Shift` 或 `Esc` 显示菜单。
2. 进入 `Advanced options for Ubuntu`。
3. 选择 `Ubuntu, with Linux 5.15.0-139-generic`。
4. 启动后确认：

```bash
uname -r
modinfo -F version nvidia
nvidia-smi
dkms status
```

5. 将新内核标记为 `NO-GO`，保留全部包和日志供审查。

不要自动删除新内核，不要修改默认 GRUB项，不要运行 `autoremove`。如果需要固定旧内核为
默认启动项，必须另行审查并获得批准。

### 6.2 安装失败但尚未重启

- 不重启；
- 保存 `/var/log/apt/`、`/var/log/dpkg.log` 和 `/var/lib/dkms/.../make.log` 的相关片段；
- 检查旧内核文件是否仍完整；
- 停止自动处理，单独制定 dpkg恢复方案。

### 6.3 新内核可启动但某个设备失败

仍优先从 GRUB回到 `5.15.0-139`。不得为了让一个设备工作而在未审查情况下升级 NVIDIA
大版本、删除 RealSense holds、加载第三方模块或修改 Secure Boot。

## 7. 风险矩阵

| 风险 | 预防 | 失败处理 |
|---|---|---|
| NVIDIA新内核模块缺失 | 显式安装匹配的 `linux-modules-nvidia-570`；重启前 `modinfo -k` | 不重启；保留旧内核 |
| Codex沙箱无法访问 NVIDIA设备 | 显卡验收由用户在真实宿主终端执行并保存摘要 | 不修改 `/dev`、udev或驱动以适配沙箱 |
| RealSense DKMS失败 | 新内核重启前要求 `dkms status ... installed` | 不重启；审查 make.log |
| Secure Boot拒绝模块 | 当前为 disabled；重启前复核 | 回退旧内核，不修改 Secure Boot |
| APT候选漂移 | 模拟后冻结精确包版本；下载与安装分离 | 重新模拟，不沿用旧批准 |
| Intel源超时 | 记录并保持 holds；不静默改源 | 停止并单独处理源策略 |
| 磁盘不足 | preflight + 模拟下载大小；禁止 autoremove旧内核 | 不安装 |
| 新内核影响ROS/Gazebo | 不升级ROS包；宿主/显卡通过后才最小 smoke | GRUB回退旧内核 |
| QEMU隔离误放行 | 重启使旧 boot policy天然失效；新 admission另审 | 保持 NO-GO |

## 8. 执行批准点

升级不能用一句“继续”跨越所有状态变化。至少分成以下批准点：

1. NVIDIA宿主基线确认：已完成，用户终端 `nvidia-smi` PASS；
2. 批准 transaction模拟：已完成，原计划结果为 `NO-GO`；本轮未执行 `apt-get update`；
3. 重新设计并审查 570 DKMS 路线；只有另行批准且审查通过后，才可考虑只下载；
4. 审查下载包后，批准安装；
