## 1. 这台电脑要完成什么

这台 Ubuntu 24.04 电脑作为**独立液体计算工作站**，只负责：

1. 独立构建和审查 DualSPHysics、GenCase 及必需工具；
2. 建立容器静水 case，生成可重复使用的静水初态；
3. 读取另一台 Gazebo 电脑导出的容器实际运动文件，离线回放该运动；
4. 计算容器内物理水的自由液面；
5. 提取晃动高度、峰值、频率、衰减和质量守恒等指标；
6. 将小型 CSV/JSON 报告返回原 Gazebo 电脑。

它**不负责**运行小车控制器，不参与 Gazebo case 成败判定，也不向控制器反馈液体力或
液位。首版是单向、离线、two-pass 计算：先完成小车运动，再计算同一运动下的水。

```text
GAZEBO_HOST（操作系统以每个 transfer manifest 为准）
  └── 已关闭的 case → 不可变 motion/metadata 输入包
                              │
                              ▼
LIQUID_ZRJ_MSI_U2404
  └── 静水初态 → 运动回放 → 液面 Gauge → 结果包/接收回执
                              │
                              ▼
GAZEBO_HOST 只导入已核验的小型报告，进行算法间结果对比
```

ROS 1 与 ROS 2 的差异不影响首版流程，因为两台电脑只交换普通文件，不交换 ROS topic，
也不要求 Ubuntu 24.04 电脑打开原 ROS 1 bag。

## 2. 最终目标和当前限制

### 2.1 最终目标

对每个已经结束的小车仿真 run，得到以下独立液体评价量：

- `H_crest(t)`：液面高于静态液深的最大 crest 高度，作为晃动高度 primary candidate；
- `H_peak`：完整有效窗口内的最大 `H_crest`；
- `H_p95`、RMS、峰值时刻；
- 圆周液位差 `H_peak_to_peak(t)`；
- 主频和停止激励后的衰减/阻尼；
- 每个液位 probe 的原始 `zsurf`；
- 粒子质量、泄漏、NaN、无效 probe 和飞溅等质量检查。

### 2.2 当前结果身份

在数值收敛和实物液位验证完成前，所有输出必须带有：

```text
development_only = true
formal = false
fidelity_validation_status = UNVALIDATED
physical_primary_eligible = false
```

液体仿真结果不能冒充真实水测量，也不能覆盖原来的 `H_proxy`、`H_modal` 或 Gazebo run
结论。

## 4. 两台电脑的协作协议（文件 ABI）

### 4.1 身份、版本与状态机

每个跨机文件都必须是 `R8-LIQUID-HANDOFF-ABI-v2` 的显式实例，而不是依据目录名、文件
修改时间或“最新结果”推断身份。`transfer_id` 和 `replay_id` 均使用 ASCII、无空格、不可
复用的格式，例如：

```text
transfer_id = R8L_<source_attempt_id>_<UTC-YYYYMMDDTHHMMSSZ>_v1
replay_id   = R8L_<transfer_id>_<settled_state_short_hash>_<profile_id>_v1
```

`source_attempt_id` 不可包含本机绝对路径、用户名、密码、token、IP 或 ROS 参数 dump。
所有时间戳同时写 RFC 3339 UTC 和 `Asia/Shanghai` 展示值；数值对齐只使用
`motion.csv.t_s`（从 0 开始），不依赖两台电脑的时钟偏差。

```text
GAZEBO_HOST: CLOSED → PACKAGE_STAGED → PACKAGE_READY
                                          │ immutable file transfer
                                          ▼
LIQUID host: STAGED → VERIFIED_ACCEPTED → REPLAY_PENDING → REPLAY_FINALIZED
                                          │                         │
                                          └── REJECTED               ▼
GAZEBO_HOST:                       receipt only              RESULT_READY → IMPORTED
```

允许的状态名称为 `PACKAGE_READY`、`RECEIVED`、`VERIFIED_ACCEPTED`、`REJECTED`、
`REPLAY_PENDING`、`REPLAY_FINALIZED`、`RUN_NOT_AUTHORIZED`、`INFRASTRUCTURE_NO_GO` 和
`RESULT_READY`。`REJECTED`、`NO_GO` 和 `.partial` 都是有效证据，绝不删除后重新命名为
PASS。

### 4.2 源电脑的出站包和传输方式

源电脑只能为已关闭、postflight 已完成的 attempt 生成包。它先在自己的临时目录写
`<transfer_id>.partial/`，完成文件关闭、清单和 SHA-256 后，以原子 rename 得到
`<transfer_id>/`；在此之前不得传输。包内所有文件必须是普通文件，拒绝 symlink、硬链接、
FIFO、socket、可执行程序、压缩炸弹和未列入清单的大文件。

可使用人工拷贝、受控 USB、SFTP 或无删除语义的 `rsync` 运输，但运输层不改变 ABI：

- 不挂载对方工作区，不使用 `rsync --delete`、`--remove-source-files` 或“同步整个目录”；
- 不传私钥、SSH 配置、ROS 环境、APT 配置、二进制、容器镜像或完整 bag；
- 传输到本机时先落在 `$LIQUID_ROOT/incoming/<transfer_id>.partial/`；校验通过前不得
  打开给 solver、解析器或 GUI；
- 传输完成后，本机逐项重算 hash、文件大小、类型和 manifest 约束；全部通过才原子 rename
  为 `$LIQUID_ROOT/incoming/<transfer_id>/` 并设为只读；
- 任何一项不符都保留 staging 与拒绝原因到 `quarantine/`/`audits/`，不覆盖已验收输入。

`transfer_manifest.json` 是验收事实源，至少应列出 `handoff_abi`、`transfer_id`、
`source_host_id`、`source_repo_commit`、`source_attempt_id`、创建时间、`source_status`、
`postflight_complete=true`、每个相对文件路径/字节数/SHA-256、以及本包引用的
`attempt_manifest`、`postflight`、source bag 的 hash。`checksums.sha256` 是同一普通文件集
的可机读复核表；清单与实际集合不一致即拒绝。清单不能用源电脑的绝对路径代替这些身份
字段。

### 4.3 本机验收回执和结果回传

本机对每个输入包生成一个 create-new 的小型
`coordination/receipts/<transfer_id>_receipt.json`，返回给 `GAZEBO_HOST`。它至少包含：

```text
handoff_abi / transfer_id / liquid_host_id / receipt_created_at
accepted | rejected status and machine-readable reasons
observed file list, byte counts and SHA-256
source identifiers/hashes echoed from transfer_manifest
LIQUID_ROOT filesystem/device identity (not a source-host path)
target host profile/document/source-revision hashes
next_allowed_stage = NONE | REPLAY_PENDING
```
