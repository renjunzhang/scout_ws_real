# Ubuntu 24.04 液体仿真电脑任务与数据交接说明

> 日期：2026-08-06（Asia/Shanghai）
>
> 接收电脑：独立的 Ubuntu 24.04 / ROS 2 电脑
>
> 状态：`HANDOFF DESIGN / NOT EXECUTED ON TARGET`
>
> 首选液体后端：[DualSPHysics](https://github.com/DualSPHysics/DualSPHysics)

## 1. 这台电脑要完成什么

这台 Ubuntu 24.04 电脑作为**独立液体计算工作站**，只负责：

1. 独立构建和审查 DualSPHysics、GenCase 及必需工具；
2. 建立容器静水 case，生成可重复使用的静水初态；
3. 读取另一台 Gazebo 电脑导出的容器实际运动文件，离线回放该运动；
4. 计算容器内物理水的自由液面；
5. 提取晃动高度、峰值、频率、衰减和质量守恒等指标；
6. 将小型 CSV/JSON 报告返回原 Gazebo 电脑。

它**不负责**运行小车控制器，不参与 Gazebo case 成败判定，也不向控制器反馈液体力或
液位。首版是单向、离线、two-pass 计算：先完成小车运动，再计算同一运动下的水。

```text
原 Ubuntu 20.04 Gazebo 电脑
  └── 已结束的 case → 容器实际运动 CSV/JSON
                              │
                              ▼
Ubuntu 24.04 液体电脑
  └── 静水初态 → 运动回放 → 液面 Gauge → 晃动高度 CSV/JSON
                              │
                              ▼
原电脑只导入报告，进行算法间结果对比
```

ROS 1 与 ROS 2 的差异不影响首版流程，因为两台电脑只交换普通文件，不交换 ROS topic，
也不要求 Ubuntu 24.04 电脑打开原 ROS 1 bag。

## 2. 最终目标和当前限制

### 2.1 最终目标

对每个已经结束的小车仿真 run，得到以下独立液体评价量：

- `H_crest(t)`：液面高于静态液深的最大 crest 高度，作为晃动高度 primary candidate；
- `H_peak`：完整有效窗口内的最大 `H_crest`；
- `H_p95`、RMS、峰值时刻；
- 圆周液位差 `H_peak_to_peak(t)`；
- 主频和停止激励后的衰减/阻尼；
- 每个液位 probe 的原始 `zsurf`；
- 粒子质量、泄漏、NaN、无效 probe 和飞溅等质量检查。

### 2.2 当前结果身份

在数值收敛和实物液位验证完成前，所有输出必须带有：

```text
development_only = true
formal = false
fidelity_validation_status = UNVALIDATED
physical_primary_eligible = false
```

液体仿真结果不能冒充真实水测量，也不能覆盖原来的 `H_proxy`、`H_modal` 或 Gazebo run
结论。

## 3. Ubuntu 24.04 电脑的工作阶段

### 阶段 U0：只读环境基线

先记录并返回以下信息，不安装任何东西：

- Ubuntu、内核版本和安全更新状态；
- CPU 型号、核心数、内存和 swap；
- 数据盘文件系统、可用空间和挂载选项；
- GPU、`nvidia-smi`、驱动版本、显存和 CUDA 工具链；
- GCC/G++、CMake、Git、Python 版本；
- Docker/Podman/bubblewrap 等现有隔离能力；
- ROS 2 发行版和工作区位置，仅用于避让，不作为液体依赖；
- 是否有正在运行的 ROS 2、Gazebo、CUDA 或其他 GPU 任务。

如果缺少依赖，先给出精确的 APT transaction 模拟；未批准前不得执行安装、全量升级、
驱动升级、内核升级或 CUDA 变更。

### 阶段 U1：建立独立工作根

优先在专用数据盘建立：

```text
/data/a/scout_liquid_lab/
├── incoming/       # 从 Gazebo 电脑收到的只读数据包
├── dependency/     # 固定源码、清单和哈希
├── build/          # 本地构建产物
├── sandbox/        # 首次工具执行和 smoke
├── cases/          # 静水和运动回放 case
├── results/        # 原始 Gauge、粒子输出和日志
├── outgoing/       # 允许传回原电脑的小型结果包
├── audits/         # 环境、构建、运行和哈希证据
└── quarantine/     # 未准入的预编译文件
```

如果目标电脑没有 `/data/a`，可以选择一个新的专用数据盘目录，但必须把绝对路径写入
manifest。不要把它放进 ROS 2 工作区，不要覆盖已有目录，不使用指向其他目录的软链接。

建议 P0 至少预留 `50 GB`，推荐 `100 GB` 以上；内存建议至少 `16 GB`、优先 `32 GB`。
C2/`dp=0.5 mm` 和高频全粒子输出可能远超此预算，未经实测不得承诺。

### 阶段 U2：固定依赖并隔离构建

主候选固定为：

```text
repository: https://github.com/DualSPHysics/DualSPHysics
candidate_commit: ef3721a861fda961f0e2f9ec4cd317b19de99086
observed_git_tree: cef458cb358712f4694b9d2148f638440418e9dc
```

该 commit 是现有方案中的开发候选，不代表已通过作者签名认证。目标电脑需要重新记录：

- remote URL、commit、Git tree 和源码清单 SHA-256；
- license、submodule、脚本、预编译 ELF/`.so` 清单；
- 编译器、CUDA、CMake 参数和最终二进制哈希；
- 构建前后源码是否保持 clean；
- 所有实际使用的 GenCase、solver 和后处理工具来源。

安全要求：

- 使用普通用户和新建目录，不执行 `sudo make install`，不写 `/usr/local`；
- 不修改 ROS 2、Gazebo、NVIDIA 驱动、内核或系统 CUDA；
- 优先从固定源码构建；仓库自带预编译 ELF 先放入 `quarantine`，不能直接执行；
- GenCase 首次执行前，单独完成 SHA-256、`file`、动态依赖、读写路径和网络能力审查；
- 首次执行使用已审查的非特权隔离，关闭网络并限制 CPU、内存、文件数、运行时间和输出量；
- 若目标机没有可接受的隔离能力，停在审查阶段，不降低规则强行运行。

Ubuntu 24.04 是受支持系统，但这不等于未知二进制可以不经审查直接执行。

### 阶段 U3：静水最小 case

先不接收小车运动，只做完全静止的圆柱容器：

1. 构建 C1 development 容器；
2. 使用 `dp=2.0 mm` 做低成本 smoke；
3. 生成水粒子并执行 hydrostatic settle；
4. 至少重复两次冷启动，比较粒子数、质量、液位和最终状态；
5. 检查 NaN、泄漏、质量损失和液面漂移；
6. 固定 `settled_state` 及其完整配置/hash；
7. 验证每次动态 replay 都从该只读初态的 fresh clone 开始。

当前仅有两个未验证的 development 尺寸：

| 条件 | 圆柱内径 | 静态液深 | 估算水量 | 状态 |
|---|---:|---:|---:|---|
| C1 | `37 mm` | `58 mm` | 约 `62.4 mL` | `SIM_ONLY_UNVALIDATED` |
| C2 | `95 mm` | `58 mm` | 约 `411.1 mL` | `SIM_ONLY_UNVALIDATED` |

在收到容器总内高、freeboard、底部形状、壁面材料和真实水量前，只能做软件 smoke，不能
冻结正式物理 case。

### 阶段 U4：合成运动回放

静水通过后，先使用目标电脑自行生成并明确标记为 `SYNTHETIC` 的小幅运动：

- 单轴正弦平移；
- 正弦 yaw；
- 激励停止后的自由衰减；
- 零运动 replay。

这一步验证时间、方向、坐标系、Gauge 和高度提取器，不用于比较控制算法。应报告理论/数值
主频差异、重复性以及 `dp=2.0/1.0 mm` 的初步敏感性。

### 阶段 U5：小车实际运动回放

只有收到完整、hash 正确的数据包后才运行：

1. 校验 transfer manifest 和每个输入文件 SHA-256；
2. 拒绝时间倒退、重复、断点、非法四元数或单位不明的数据；
3. 从冻结的静水初态创建 fresh replay；
4. 用容器位姿驱动容器边界，禁止使用 `/cmd_vel` 代替实际运动；
5. 运行完整运动窗口和冻结 tail；
6. 生成 Gauge、晃动高度和 QC 输出；
7. 原始输入保持只读，结果写入新的 `replay_id` 目录。

每个 Gazebo attempt 的实际运动不同，因此每个 attempt 必须单独 replay；只能复用相同配置
下的静水初态，不能复用某次动态液体结果。

## 4. 原 Gazebo 电脑需要提供的输入

另一台液体电脑不直接读取原始 ROS 1 工作区，也不扫描“最新 bag”。原电脑应为每个已关闭
且 postflight 完成的 attempt 制作一个只读传输包：

```text
incoming/<transfer_id>/
├── transfer_manifest.json
├── motion.csv
├── motion_manifest.json
├── container_spec.json
├── fluid_spec.json
├── run_spec.json
└── checksums.sha256
```

### 4.1 `motion.csv`

首版推荐列：

```text
t_s,x_m,y_m,z_m,qx,qy,qz,qw
```

语义必须固定为：

- `t_s`：相对第一有效样本的秒数，从 `0` 开始并严格递增；
- 平移单位：m；角度隐含在四元数中；全部使用 SI；
- 四元数顺序：`x,y,z,w`，每行归一化且符号连续；
- 每行表示 `T_odom_container(t)`，不是 `base_link`，也不是计划轨迹；
- `T_odom_container = T_odom_base × T_base_container`；
- 坐标轴方向、右手系、插值规则和采样周期写入 manifest；
- 优先由实际 `/odom`、`/tf`、`/tf_static` 离线导出。

速度、角速度、加速度可作为 QC 附加列，但首版不得对噪声位姿盲目二次差分后作为唯一驱动。
禁止把 `/cmd_vel`、计划路径、`H_proxy` 或 `H_modal` 当作液体运动输入。

### 4.2 `motion_manifest.json`

至少包含：

```text
schema_version
transfer_id / source_attempt_id
source_bag_sha256 / attempt_manifest_sha256 / postflight_sha256
source_status / GOAL_REACHED_or_timeout
time_start / duration_s / sample_period_s / row_count
parent_frame=odom / child_frame=container
T_base_container and its source
interpolation translation=linear / rotation=SLERP
first_effective_motion_s / motion_end_s / tail_end_s
discarded_DOF policy, if any
motion_csv_sha256
```

### 4.3 `container_spec.json`

至少包含：

- shape 和全部内表面尺寸，不能只给外径；
- 总内高、初始液深、freeboard、底部圆角/锥度；
- 开口、盖体和溢出规则；
- 壁厚、壁面材料、接触角/润湿信息；
- 容器坐标系原点和轴方向；
- `T_base_container`；
- 几何来源、测量误差、版本和 SHA-256。

### 4.4 `fluid_spec.json`

至少包含液体类型、温度、密度、动力/运动黏度、表面张力、初始体积/液深、重力方向和
测量误差。未知字段必须明确为 `UNKNOWN`，不能悄悄使用默认值后冒充实物参数。

### 4.5 `run_spec.json`

至少包含 case 身份、`dp`、Gauge 数量与位置、输出频率、tail 时长、solver 数值参数、
期望的指标版本和资源上限。

## 5. 液体电脑必须返回的输出

只把小型、可审查的数据包返回原电脑：

```text
outgoing/<replay_id>/
├── result_manifest.json
├── gauge_zsurf.csv
├── slosh_height.csv
├── summary.json
├── qc_report.json
├── build_and_runtime.txt
├── solver.log
└── checksums.sha256
```

### 5.1 `gauge_zsurf.csv`

推荐使用 long format：

```text
t_s,probe_id,theta_deg,radius_m,z_surface_m,valid
```

圆周至少使用 16 个等角度 vertical probes；后续评估 32 个。probe 位置和液面高度都必须
转换回容器坐标系。单个最高飞溅粒子的 `maxz` 只作 QC，不作 primary 晃动高度。

### 5.2 `slosh_height.csv`

```text
t_s,h0_m,h_crest_m,h_abs_m,h_peak_to_peak_m,valid_probe_count,maxz_qc_m
```

其中：

```text
eta_i(t)            = h_i(t) - h0
H_crest(t)          = max_i eta_i(t)
H_abs(t)            = max_i |eta_i(t)|
H_peak_to_peak(t)   = max_i h_i(t) - min_i h_i(t)
```

### 5.3 `summary.json` 和 `qc_report.json`

至少返回：

- `H_peak`、`H_p95`、RMS、峰值时刻；
- first 15 s、完整运动窗口和 tail 的分段结果；
- 主频、衰减率/阻尼及其计算方法；
- missing/invalid probe 比例；
- 粒子初末数量、质量误差、泄漏、NaN、越界和 splash 数；
- 静水偏置/漂移；
- 输入、配置、源码、构建产物、solver 和结果文件的 SHA-256；
- Ubuntu/kernel、CPU/GPU、驱动/CUDA、运行时间和峰值内存/显存；
- `development_only/formal/fidelity_validation_status` 标签。

BI4、VTK、全粒子 snapshot 等大文件先留在液体电脑，不默认复制到原电脑。只有复核需要时
才按明确文件清单传输；不得为了省空间自动删除首次结果。

## 6. 安全边界

1. 不改 Ubuntu 24.04 电脑已有 ROS 2 工作区、ROS 2 包或 Gazebo 环境。
2. 液体构建和运行时不 source ROS 2 环境，除非以后另立 ROS 2 集成项目。
3. 不在原 Ubuntu 20.04 电脑执行 GenCase/DualSPHysics，不把二进制传回原电脑运行。
4. 两台电脑只交换显式清单内的 CSV/JSON/TXT；所有文件先核验 SHA-256。
5. 输入目录只读，输出使用新的 `replay_id`，禁止覆盖或硬链接回输入。
6. 不把液体程序接入 Gazebo world、控制节点、`/cmd_vel` 或小车底盘。
7. 首次构建/运行不与 ROS 2、Gazebo 或其他 GPU 工作负载并发。
8. 不执行全量 APT upgrade、驱动/内核/CUDA 更换或来源不明的安装脚本。
9. 若任何工具试图访问工作根外路径、联网、提权、写入系统目录或加载未登记动态库，立即
   停止并保留日志。
10. 不通过修改门禁或删除失败证据把 `NO-GO` 强行改成 `PASS`。

## 7. 第一轮最小交付顺序

目标电脑收到本文后，按以下顺序工作，每一步完成后先返回报告：

1. **U0 基线报告**：只读环境、资源、已有工具和风险；
2. **U1 存储方案**：选择专用根，给出可用空间和预计配额，不运行上游工具；
3. **U2 构建/GenCase 审查方案**：列出 exact commit、依赖、预编译文件和隔离方式；
4. **C1/`dp=2 mm` 静水 smoke**：只有前三步审查通过后执行；
5. **零运动 + 小幅正弦回放**：验证坐标、Gauge 和高度提取；
6. **一个 development motion 包**：从原电脑接收一个已结束 H0 attempt；
7. **返回结果包**：`H_crest(t)`、peak、p95、频率、衰减和 QC；
8. 再决定是否进入 `dp=1.0/0.75/0.5 mm` 收敛、C2 或实物保真验证。

第一轮明确不做：40/64/88 正式矩阵、实时 ROS bridge、双向流固耦合、液体力反馈、修改
控制器、替换原有 plant 或宣称 physical-primary。

## 9. 尚需用户提供的物理信息

软件 smoke 可以先做，但正式液体 case 前仍需要：

1. 容器内径、总内高、壁厚、底部形状、开口/盖体状态；
2. 容器在 Scout 上相对 `base_link` 的安装位姿；
3. 实际水量或液深及误差、液体温度；
4. 内壁材料和可用的润湿/接触角信息；
5. 实物液位图像/传感器的采样率、标定和参考 case；
6. 最终报告采用 crest、absolute 还是 peak-to-peak 作为主指标；
7. 单 case 可接受的最大离线时间和目标电脑可使用的 GPU。

主方案的完整技术依据见同目录：

```text
20260805_DualSPHysics物理液体接入SIM-R8方案.md
```
