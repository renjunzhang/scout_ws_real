# 实物实验通用启动指南

更新日期：2026-08-28

状态：`COMMON_FIELD_GUIDE`。本文是所有实物实验共用的启动底座，不绑定某一种算法、路径、场地、trial 编号或当前研究主线。

本文只负责把系统带到 `STACK_READY`：

~~~text
工作区与现场参数明确
  → 选择“无定位 / 定位 / 建图”启动模式
  → 底盘与所需传感器就绪
  → 可选外部数据源就绪
  → 地图、TF 与 /cmd_vel 所有权正确
  → 无运动检查或静态 smoke 通过
  → 交给具体实验协议
~~~

路径、控制器、variant、速度、权重、相机标定、录制 topic、trial 顺序、重试规则和统计判定必须由具体实验协议定义，不在本指南中写死。

## 0. 公共部分与实验专属部分

| 层级 | 本指南负责 | 具体实验协议负责 |
| --- | --- | --- |
| 安全 | 急停、`/cmd_vel` 唯一发布者、无运动门、停止顺序 | 本实验额外风险和中止条件 |
| 硬件 | CAN、底盘、雷达、IMU、RealSense 的启动与基础健康 | 哪些传感器必须启用 |
| 地图 | 无定位、建图、显式冻结地图定位三种公共模式 | 使用哪张地图及其预注册 SHA |
| TF | 每条控制 TF 只有一个 authority | 自定义 frame 与外参 |
| 可选数据源 | NOKOV、在线液面等接入边界 | 是否必需、标定文件和质量阈值 |
| 证据 | Git、环境、地图身份、日志、bag 闭包和失败保留 | recorder 白名单、postflight 和统计门 |
| 运动 | 只规定必须显式授权且先过静态门 | 路径、目标、算法、参数、trial 和 runner |

任何新实验都应先引用本指南，再单独写一份实验协议。不要把新的算法矩阵或临时目标点不断追加回公共指南。

## 1. 不随实验变化的安全红线

1. 任一时刻只允许一个节点发布最终 `/cmd_vel`。
2. 静态 smoke、地图冻结和静止定位验收期间，`/cmd_vel` 必须没有 publisher。
3. 建图与纯定位不能同时运行；同一时刻只允许一个 `cartographer_node`。
4. 不重复启动底盘、雷达、IMU 或相机驱动。切换启动模式前先停止旧栈。
5. 只有具体实验的专用 runner 明确要求时，才输入 `ARM_MOTION=YES`。
6. 通用 launch、地图工具、路径生成器和 recorder 本身不构成运动授权。
7. 急停必须在操作者手边，场地保持净空，运动前确认停止距离。
8. 失败 bag、日志、metadata 和 postflight 一律保留，不用成功重跑覆盖。
9. 不使用 broad `killall` 或 `pkill`。按终端及脚本自身的 `Ctrl+C`/cleanup 停止。
10. 正式采集前记录 Git revision、工作树状态、参数文件和所有冻结资产身份。

公共只读检查：

~~~bash
rostopic info /cmd_vel
rosnode list
git -C /home/geist/scout_ws rev-parse HEAD
git -C /home/geist/scout_ws status --short
~~~

看到 `/cmd_vel` publisher 时，先找到对应节点和终端；不要在未知发布者仍存在时启动 planner 或 teleop。

## 2. 每次实验都要准备的环境

### 2.1 ROS 工作区

除一键启动脚本外，其余 ROS 终端统一执行：

~~~bash
source /opt/ros/noetic/setup.bash
source /home/geist/scout_ws/devel/setup.bash
cd /home/geist/scout_ws
~~~

Cartographer 建图终端还要追加：

~~~bash
export CATKIN_SETUP_UTIL_ARGS=--extend
source /home/geist/scout_ws/src/scout_apps/sensors/cartographer_ws/install_isolated/setup.bash
~~~

`launch_real_sensors_stack.sh` 会在内部完成这些 source；手工启动的其他终端仍需自行执行。

### 2.2 实验环境文件

每个实验应在仓库外维护自己的环境文件，例如：

~~~bash
export EXPERIMENT_ID="20260828_example"
export EXPERIMENT_OUT_DIR="/home/geist/slosh_bags/real/${EXPERIMENT_ID}"
export START_IMU=true
export START_REALSENSE=true
~~~

环境文件至少记录：

~~~text
实验 ID 与协议 ID
输出目录
需要的启动模式
是否启用 IMU / RealSense / NOKOV / 在线观测
地图绝对路径与预注册 SHA（需要定位时）
传感器 topic 与 frame
具体实验协议路径
~~~

实验专属的路径、控制参数和判定阈值也可以放在同一文件，但必须由实验协议解释。`ARM_MOTION`、地图冻结授权和 trial 编号不应长期写入环境文件。

## 3. 先选择唯一的启动模式

| 模式 | 用途 | 公共入口 | 是否有 `/map` |
| --- | --- | --- | --- |
| S0 无定位传感器栈 | 传感器 smoke、重新建图、无需地图的诊断 | `launch_real_sensors_no_localization.sh` | 否 |
| S1 显式地图定位栈 | 导航、路径跟踪、控制器和需要 map frame 的实验 | `launch_real_sensors_stack.sh` + 地图路径/SHA | 是 |
| S2 建图 | S0 保持运行，再单独启动 Cartographer mapping | S0 + mapping launch | 是，但属于在线建图 |

不要先启动 S0，再在同一批底盘/雷达进程旁边启动完整 S1。S0 切换到 S1 时，应先停止 S0，再由 S1 重新启动整套进程。

### 3.1 S0：CAN、底盘和传感器，不启动定位

这是重新建图或只做传感器检查时的公共入口：

~~~bash
START_REALSENSE=true \
  bash /home/geist/scout_ws/src/scout_apps/control/scout_local_planner/scripts/launch_real_sensors_no_localization.sh
~~~

默认负责：

- 检查 `can0` 并配置 500000 bitrate；
- 启动 Scout 底盘及 `/odom`；
- 启动 NanoScan3 及 `/scan_front`；
- 启动 IMU 及 `/imu/data`；
- 启动 RealSense 彩色流并检查分辨率、频率；
- 等待关键 topic；
- 在 `Ctrl+C` 时只清理它自己启动的进程。

它强制不启动：

- Cartographer 定位；
- Cartographer 建图；
- AMCL 或 map server；
- planner、teleop、NOKOV 和在线液面节点。

即使当前 shell 残留 `START_LOCALIZATION=true`，该入口也会覆盖为 `false`。应看到：

~~~text
Localization is disabled; no Cartographer/AMCL/map server will be started.
~~~

S0 下不要求 `/map` 或 `map -> base_link`。该脚本不会替操作者启动建图。

### 3.2 S1：使用已冻结地图启动定位

正式或可复现的定位实验必须由实验协议提供：

~~~text
LOCALIZATION_MAP_FILE                 冻结 pbstream 的绝对路径
LOCALIZATION_MAP_EXPECTED_SHA256      预注册的 64 位 SHA-256
LOCALIZATION_OCCUPANCY_GRID_RESOLUTION
LOCALIZATION_GLOBAL_FRAME
LOCALIZATION_BASE_FRAME
~~~

环境文件 source 完成后，先做只读检查：

~~~bash
: "${LOCALIZATION_MAP_FILE:?set an absolute frozen pbstream path}"
: "${LOCALIZATION_MAP_EXPECTED_SHA256:?set the preregistered map SHA-256}"

test -s "$LOCALIZATION_MAP_FILE"
printf '%s\n' "$LOCALIZATION_MAP_EXPECTED_SHA256" \
  | grep -Eq '^[0-9a-fA-F]{64}$'
~~~

然后启动：

~~~bash
export REQUIRE_LOCALIZATION_MAP_HASH=true
export WAIT_FOR_LOCALIZATION_MAP=true
export WAIT_FOR_LOCALIZATION_TF=true
export SENSOR_STACK_LOG_DIR="/tmp/${EXPERIMENT_ID}_localized_$(date +%Y%m%d_%H%M%S)"

LOG_DIR="$SENSOR_STACK_LOG_DIR" \
START_LOCALIZATION=true \
START_REALSENSE=true \
  bash /home/geist/scout_ws/src/scout_apps/control/scout_local_planner/scripts/launch_real_sensors_stack.sh
~~~

显式地图模式会校验实际文件 SHA，并把 `/map` 和 `map -> base_link` 升级为致命就绪门。日志目录中的 `localization_map_identity.env` 保存：

~~~text
地图绝对路径
预期 SHA
实际 SHA
是否强制哈希
occupancy-grid resolution
global/base frame
~~~

正式实验禁止依赖 localization launch 中的历史默认地图。也禁止在 SHA 不符后把“实际 SHA”临时复制成新的预期值来强行启动。

### 3.3 底盘已由其他终端启动时

只有明确知道底盘 launch 的所有权时才使用。外部底盘 + S0：

~~~bash
START_BASE=false \
WAIT_FOR_ODOM=true \
START_REALSENSE=true \
  bash /home/geist/scout_ws/src/scout_apps/control/scout_local_planner/scripts/launch_real_sensors_no_localization.sh
~~~

外部底盘 + S1 则必须先具备第 3.2 节的显式地图变量，再执行：

~~~bash
START_BASE=false \
WAIT_FOR_ODOM=true \
START_LOCALIZATION=true \
  bash /home/geist/scout_ws/src/scout_apps/control/scout_local_planner/scripts/launch_real_sensors_stack.sh
~~~

`START_BASE=false` 只跳过底盘，不会跳过雷达、定位、IMU 或 RealSense。若这些节点也已在外部运行，不要再启动整套脚本，应由具体实验提供更细粒度入口。

### 3.4 常用公共开关

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `START_BASE` | `true` | 启动 CAN 与 Scout 底盘 |
| `WAIT_FOR_ODOM` | `true` | 要求 `/odom` 就绪 |
| `START_LOCALIZATION` | `true` | 仅完整栈使用；无定位入口会强制关闭 |
| `START_IMU` | `true` | 启动并检查 `/imu/data` |
| `START_REALSENSE` | `true` | 启动并检查 RGB |
| `REALSENSE_ENABLE_DEPTH` | `false` | 是否启动深度流 |
| `REALSENSE_COLOR_WIDTH/HEIGHT/FPS` | `1920/1080/30` | RGB 模式 |
| `LOG_DIR` | `/tmp/...` | 保存启动和健康检查日志 |
| `READY_TIMEOUT` | `45` | topic/TF 等待上限 |

实验环境应显式记录与默认值不同的开关。

## 4. 公共建图与地图切换流程

### 4.1 建图

1. 先按 S0 启动底盘和所需传感器。
2. 确认没有定位、旧建图或 planner 残留。
3. 在另一终端启动 mapping。

~~~bash
rosnode list | grep -E 'cartographer|amcl|map_server' || true

roslaunch nanoscan3_mapping scout_nanoscan3_cartographer.launch \
  scan_topic:=/scan_front \
  odom_topic:=/odom \
  occupancy_grid_resolution:=0.02 \
  use_rviz:=true \
  respawn:=false
~~~

当前 mapping launch 由 Cartographer 独占动态 `map -> odom`，不再额外发布静态同名 TF。

低速建图要求：

- 覆盖实验可行驶区域及停止余量；
- 重复观察结构并形成回环；
- 避免长时间快速原地自旋、打滑和贴墙；
- 避免人员、线缆和动态物体长期进入地图；
- 建图运动只标记为 `MAP_BUILD`，不计入正式实验。

完成后先停止 teleop，并确认 `/cmd_vel` 没有 publisher。

### 4.2 冻结地图

当前仓库提供的 fail-closed 冻结工具为：

~~~text
src/scout_apps/control/spmpc_local_planner/scripts/freeze_spmpc_mocap_field_map.sh
~~~

虽然文件名来自动捕场地任务，它的地图三件套、不可覆盖、服务返回码和 SHA 门可以复用于 Cartographer 场地地图。使用前至少设置：

~~~bash
export MAP_ID="map_carto_20260828_example_v1"
export MAP_OUTPUT_ROOT="/home/geist/scout_maps/real/20260828_example"
export MAP_STEM="$MAP_OUTPUT_ROOT/$MAP_ID"
export MAP_RESOLUTION=0.02
export TRAJECTORY_ID=0
~~~

使用 NOKOV 时保持 `REQUIRE_MOCAP=true`；不使用 NOKOV 的实验必须显式记录：

~~~bash
export REQUIRE_MOCAP=false
~~~

先做无 ROS 写入的检查：

~~~bash
VALIDATE_ONLY=true \
  bash src/scout_apps/control/spmpc_local_planner/scripts/freeze_spmpc_mocap_field_map.sh
~~~

确认输出 stem 正确、teleop 已停止后，才授权一次：

~~~bash
ARM_MAP_FREEZE=YES \
  bash src/scout_apps/control/spmpc_local_planner/scripts/freeze_spmpc_mocap_field_map.sh
~~~

该工具会检查 topic、`/cmd_vel`、Cartographer 服务返回码，导出 pbstream/PGM/YAML，校验分辨率与 PGM/YAML 结构，生成 manifest、validation report 和可 source 的 `freeze.env`。不得再维护一套手工 `finish_trajectory -> write_state -> 转换 -> 临场填 SHA` 的主流程。

人工仍需检查地图预览是否存在重影、断裂、错误墙体或动态障碍残影。不合格资产保留为失败 candidate，使用新的 `MAP_ID` 重建，不覆盖。

### 4.3 从建图切到定位

冻结完成后：

1. 停止 mapping launch；
2. `Ctrl+C` 停止 S0；
3. source 生成的 `${MAP_STEM}_freeze.env`；
4. 按 S1 启动完整定位栈；
5. 检查 `localization_map_identity.env`、`/map` 和 TF；
6. 通过定位验收后才交给实验协议。

不同场地切换时必须停止整套定位进程，再用另一组绝对地图路径和 SHA 重启；不能用覆盖同名文件的方式切场。

## 5. 可选公共数据源

### 5.1 NOKOV / VRPN

只有实验协议声明需要动捕时才启动。先设置并检查：

~~~bash
: "${MOCAP_HOST:?set the XINGYING host IPv4}"
: "${MOCAP_PORT:?set the VRPN port}"
: "${MOCAP_TRACKER:?set the rigid-body name}"

ip route get "$MOCAP_HOST"
ping -c 3 "$MOCAP_HOST"
nc -zv -w 2 "$MOCAP_HOST" "$MOCAP_PORT"
~~~

原始 VRPN：

~~~bash
roslaunch vrpn_client_ros sample.launch server:="$MOCAP_HOST"
~~~

当前安装的 `sample.launch` 只接收 `server`；VRPN 端口固定为 3883 时，不要传入不存在的 `port` launch 参数。

若项目需要桥接和状态门，在另一个终端启动：

~~~bash
roslaunch nokov_mocap_monitor nokov_monitor.launch \
  start_vrpn:=false \
  server:="$MOCAP_HOST" \
  tracker:="$MOCAP_TRACKER"
~~~

检查：

~~~bash
rostopic hz "/vrpn_client_node/$MOCAP_TRACKER/pose"
rostopic echo -n 1 /mocap/status
~~~

NOKOV 默认只提供隔离监测：

- 不 remap 成 `/odom`；
- 不接管 `map/odom/base_link` 控制 TF；
- 不直接作为 `/cmd_vel` 输入；
- 坐标系对齐由具体实验的冻结外参和离线分析负责。

### 5.2 RealSense

基础栈只负责相机驱动和基础 RGB 健康：

~~~bash
rostopic hz /camera/color/image_raw
rostopic echo --noarr -n 1 /camera/color/image_raw
rostopic echo -n 1 /camera/color/camera_info
~~~

曝光、增益、白平衡、ROI、HSV、标尺和液面 calibration 都是实验资产，必须由具体协议冻结。相机正在发布不代表允许把图像录入 bag；image-free 实验仍应由 recorder/postflight 拒绝图像流。

### 5.3 IMU 与处理后状态

基础栈只保证原始公共入口 `/imu/data`。若实验使用 processed IMU、observer 或融合状态，具体协议必须声明：

~~~text
输入与输出 topic
frame 与单位
时间戳来源
READY/fallback 规则
是否允许原始 IMU 回退
必须录制的诊断 topic
~~~

### 5.4 在线液面或其他 observer

这些节点不是基础传感器栈的一部分。具体协议负责启动命令、标定文件、零点锁定、质量状态和 recorder 政策。公共门只要求：

- 节点不会发布最终 `/cmd_vel`；
- 输入传感器已稳定；
- 输出状态在运动前持续有效；
- 标定身份被保存。

## 6. 公共 `STACK_READY` 验收

### 6.1 Topic 健康

按实际启用项检查：

~~~bash
rostopic hz /odom
rostopic hz /scan_front
rostopic hz /imu/data
rostopic hz /camera/color/image_raw

rostopic echo -n 1 /odom
rostopic echo --noarr -n 1 /scan_front
rostopic echo -n 1 /imu/data
rostopic echo --noarr -n 1 /camera/color/image_raw
~~~

未启用的传感器不要求对应 topic。具体实验应给出最低频率、最大断帧和时间戳单调性门，不能只凭 `rostopic hz` 的瞬时输出判断正式数据有效。

### 6.2 TF 与地图

S0 只要求底盘自身 TF；S1/S2 还要求：

~~~bash
rostopic echo -n 1 /map
rosrun tf tf_echo map base_link
rosrun tf tf_monitor map odom
~~~

Cartographer 场景的公共所有权为：

~~~text
Cartographer:      map -> odom
Scout odometry:    odom -> base_link
NOKOV monitor:     独立 mocap frame，仅监测
~~~

同一 TF edge 出现多个 authority、静态/动态混发或持续跳变时，不得进入运动。

使用冻结 Cartographer 地图时还要检查：

~~~bash
rosparam get /cartographer_node/frozen_map_file
rosparam get /cartographer_node/frozen_map_expected_sha256
~~~

它们必须与实验协议及 `localization_map_identity.env` 完全一致。

### 6.3 `/cmd_vel` 所有权

无运动阶段：

~~~bash
rostopic info /cmd_vel
~~~

必须显示无 publisher。运动阶段则必须恰好是当前专用 runner 的控制链，不能同时存在 teleop、旧 planner 或测试 publisher。

### 6.4 静态 smoke

所有会运动的实验，在启动控制器前至少做一次不发布速度的静态 smoke。公共目标是检查：

- 必需 topic 都存在；
- header 时间戳有效且单调；
- 频率和最大断帧满足协议；
- 静止 odom、IMU、动捕或 observer 不异常漂移；
- `/cmd_vel` 全程无 publisher；
- bag 正常闭包；
- 自动 postflight 通过。

本仓库的 NOKOV/odom/IMU 被动 smoke 可复用：

~~~bash
bash src/scout_apps/control/spmpc_local_planner/scripts/record_spmpc_mocap_static_smoke.sh
~~~

只有实验确实需要这些 topic、且其阈值已在协议中冻结时才使用该入口。没有 NOKOV 或需要其他传感器的实验，应提供自己的 passive smoke 和 postflight。

### 6.5 定位验收

需要 map frame 的实验还必须验证：

- 磁盘地图与预注册 SHA 一致；
- 运行时实际加载同一绝对路径和 SHA；
- `/map` frame、resolution 和尺寸合理；
- `map -> base_link` 连续且时间新鲜；
- 激光与地图结构在 RViz 中重合；
- 小范围低速移动后无定位跳变；
- 回到物理起点时重复性满足具体实验的 start gate。

定位验收不通过时，不生成正式路径、不启动 planner，也不把失败地图换名后强行使用。

### 6.6 `STACK_READY` 的定义

只有同时满足以下条件，公共启动阶段才完成：

~~~text
所选启动模式正确
底盘与所需传感器健康
可选数据源健康
地图和 TF 所有权正确
/cmd_vel 当前无 publisher
静态 smoke / 定位验收满足本实验要求
Git、参数、地图和日志身份可追溯
~~~

`STACK_READY` 不是运动授权。下一步必须进入具体实验协议的 validate-only、recorder 和 `ARM_MOTION` 门。

## 7. 具体实验接管时必须声明的合同

每份实物实验协议至少回答：

| 项目 | 必须声明 |
| --- | --- |
| 实验身份 | 协议 ID、Git release、development/formal 边界 |
| 启动依赖 | S0/S1/S2、地图路径/SHA、可选节点 |
| 研究变量 | 算法、variant、唯一允许变化的参数 |
| 固定条件 | 路径、起终点、速度、权重、载荷、外参 |
| 运动门 | 专用 runner、`VALIDATE_ONLY`、`ARM_MOTION`、急停条件 |
| 录制 | topic 白名单、图像政策、时长、输出目录 |
| 单条有效性 | postflight、fallback、安全介入、bag 闭包 |
| 顺序 | trial/block 顺序、复位和静稳时间 |
| 重试 | 失败是否允许重试、命名和停止整批规则 |
| 判定 | 预注册指标、阈值、训练/held-out 或配对统计 |

推荐衔接顺序：

~~~text
本指南完成 STACK_READY
  → 具体协议的无运动 validate-only
  → 启动协议指定 recorder
  → 人工确认起点、净空和急停
  → 专用 runner 显式 ARM_MOTION=YES
  → 自动 postflight
  → 人工决定是否进入下一条
~~~

通用底层脚本即使能直接发布速度，也不能替代具体协议的专用 runner。

## 8. 公共证据与录包原则

正式或需要复现的 development 实验，至少保存：

~~~text
实验协议与环境文件
Git revision、git status，必要时保存实际 diff
传感器栈 LOG_DIR
地图绝对路径、预期/实际 SHA 和 map identity
相机/外参/observer 等标定身份
路径或目标身份
runner protocol metadata
rosbag 与 bag info
postflight 报告
失败原因与人工干预记录
~~~

公共规则：

1. 在任何非零速度输出前 recorder 必须已经工作；可以由专用 runner 内部按正确顺序启动，也可以由操作者预先启动；
2. 正式 recorder 使用协议白名单，不依赖 `-a`；
3. 是否录图像由协议决定，且 postflight 必须能发现违规图像流；
4. 每个输出名唯一，拒绝覆盖和 `.bag.active` 残留；
5. 运动完成后保留协议要求的静止尾段；
6. bag 闭包和 postflight 完成前不要先停底盘/传感器栈；
7. 失败数据和成功数据使用不同身份，不能用成功结果覆盖失败记录。

## 9. 公共停止顺序

正常结束：

1. 等当前 runner 和 recorder 正常结束，确认 bag 闭包；
2. 停止 planner 或 teleop；
3. 确认 `/cmd_vel` 没有 publisher；
4. 若正在建图且要保留 candidate，先使用专用冻结工具；
5. 停止 mapping 或 localization；
6. 停止在线 observer、液面节点或其他实验附加节点；
7. 停止 NOKOV 项目桥和 VRPN client；
8. 最后 `Ctrl+C` 停止基础传感器栈。

异常或人车风险时，安全优先立即急停；随后仍应尽量保留已经产生的 bag、日志和错误状态。

## 10. 常见故障

| 现象 | 公共处理 |
| --- | --- |
| `can0` 不存在 | 检查 USB-CAN，执行 `sudo modprobe gs_usb` 和 `ip -details link show can0` |
| `/odom` 没有数据 | 检查底盘 launch、CAN bitrate、电源和是否重复启动 |
| `/scan_front` 没有数据 | 检查雷达电源、网络、launch 日志和 topic remap |
| RealSense 启动失败 | 检查 USB 带宽、设备占用和所选分辨率/FPS |
| S0 意外出现 `/map` | 有旧定位或建图节点残留，找到对应终端并停止 |
| S1 地图 SHA 不符 | 停止；核对实验协议与 freeze.env，不改写预期值 |
| `/map` 有数据但 TF 跳变 | 检查 `map -> odom` 是否有多个 authority |
| 定位栈启动超时 | 检查 pbstream、雷达/odom、Cartographer overlay、`/map` 和 TF 日志 |
| NOKOV 有 pose 但 status 非 OK | 核对主机、Tracker 名、遮挡和 XINGYING 状态 |
| `/cmd_vel` 有未知 publisher | 不运动；通过 `rostopic info` 找节点并停止其所属终端 |
| bag 留下 `.active` | 视为未正常闭包，保留并按协议判失败 |
| 切场后仍显示旧地图 | 旧定位进程或 shell 环境未清理；全部停止，在新终端显式重启 |

## 11. 通用现场速查

### 启动前

- [ ] 已确认本次实验协议和 `EXPERIMENT_ID`；
- [ ] 已选择 S0、S1 或 S2，未混用；
- [ ] 急停、净空和停止距离已确认；
- [ ] 没有旧底盘、雷达、相机、定位或 planner 节点；
- [ ] Git、环境文件和输出目录已记录。

### 传感器

- [ ] `/odom` 和 `/scan_front` 正常；
- [ ] 启用 IMU 时 `/imu/data` 正常；
- [ ] 启用 RealSense 时 RGB 与 camera_info 正常；
- [ ] 所有必需 topic 的频率、断帧和时间戳门已通过；
- [ ] 启动日志已保存。

### 地图与 TF

- [ ] S0 明确不要求 `/map`；
- [ ] S1 使用显式绝对地图和预注册 SHA；
- [ ] mapping 与 localization 没有同时运行；
- [ ] `map -> odom -> base_link` authority 唯一且连续；
- [ ] 切场时已停止旧栈并重新核对地图身份。

### 运动前

- [ ] `/cmd_vel` 当前无 publisher；
- [ ] 静态 smoke 和需要的定位验收已通过；
- [ ] 具体协议的 validate-only 已通过；
- [ ] recorder 已启动；
- [ ] 路径、参数、载荷、外参和标定符合具体协议；
- [ ] 只有专用 runner 会在显式授权后接管 `/cmd_vel`。

### 结束后

- [ ] bag 已闭包且无 `.active`；
- [ ] postflight 已完成；
- [ ] 失败证据没有被覆盖；
- [ ] planner 先停，基础传感器栈最后停；
- [ ] 地图、日志、metadata 和人工记录可追溯。
