### 1.1 对齐的含义

“对齐实物”指下列身份和统计合同一一对应：

| 实物合同 | 仿真对应 | 是否允许变化 |
| --- | --- | --- |
| `S1_CORE / S2A_SELECTIVITY / S2B_TRANSFER` | `SIM-S1_CORE / SIM-S2A_SELECTIVITY / SIM-S2B_TRANSFER` | 只加 `SIM-` 前缀，阶段含义不变 |
| 五个/三个条件 | 同名 `B0/Bsmooth/SmoothMatch/FixedProfile/Bslosh` | 不增删、不把内部消融另起名称混入 |
| H1/L1 | 同一冻结 JSON 的仿真 replay | 仅允许冻结的刚体坐标变换，不改变曲率/弧长结构 |
| C1/C2 | 同一实物 manifest 派生的 plant/controller 参数 | C2 只改预声明物理参数 |
| complete block | complete block + common-random-number seed bundle | 每个条件仍须 fresh ROS/Gazebo |
| planned row 是样本 | planned simulation row 是样本 | control cycle、Gazebo step、frame 都不是样本 |
| `H_vis` 为独立实物测量 | `H_plant` 为独立 simulator plant state | `/slosh/height`、`H_modal` 不能替代 |
| 实物 method/config release | 同一代码与 effective-config 的仿真 release | 仿真专属 plant/world 配置另行 hash |
| failure/retry/固定分母 | 完全继承 | 只把硬件 acquisition failure 映射为仿真基础设施 failure |

仿真 rows 与实物 rows 是两套数据，不跨域配对、不合并 block，也不把仿真样本加入实物 N。仿真能支持代码、机制和条件迁移论证；最终真实液面 efficacy 仍由实物独立测量决定。

### 1.2 样本量名称

本文件按候选 `n=8` 写成 40/64/88。只有实物样本量冻结也选择 `n=8` 时，协议 ID 才能升为正式版本。

若最终 block 数为 `n ≠ 8`，整个矩阵同步改为：

```text

完整条件分支   = 11n
```

不得只改批跑脚本里的 `N`，却继续沿用 40/64/88 的文件名、随机表或分母。

## 4. 五个条件的不可变身份

| condition | backend | 液体参数 | 在线液体状态 | 唯一允许差异 | 禁止行为 |
| --- | --- | ---: | ---: | --- | --- |
| `B0` | online MPCC | 否 | 否 | 冻结普通 MPCC variant | 读取 plant truth 或 `/slosh/*` 调速 |
| `Bsmooth` | online MPCC | 否 | 否 | 冻结通用平滑代价 | 临场改 `v_ref`、约束或 limiter |
| `SmoothMatch` | online MPCC | 否 | 否 | 相对 `Bsmooth` 只改一个预冻结 `v_ref` | 同时改权重、horizon、solver 或安全层 |
| `FixedProfile` | offline timing + 冻结 tracker | 是，离线 | 否 | 加载对应 stratum 的只读 profile | 每 run 现场重生成、读取 live liquid state |
| `Bslosh` | online S-MPCC | 是 | 冻结 observer 的模型状态 | 继承最终唯一 source-specific release | 使用 simulator ground truth、临场换 W2/W5/source |

### 4.1 `Bslosh` 的当前边界

`Bslosh` 不是“把脚本中的 `B_slosh` 默认值跑起来”。它必须绑定实物最终完成 G2S/G2C/G3 后的：

```text
git revision / build ID
observer nominal source / fallback policy
robot/liquid delay semantics
all cost weights
all limits and safety layers
container/model parameters
effective-config hash
```

尤其必须把 `w_control`、`w_smooth`、`w_alpha`、`w_du_a`、`w_du_vs`、`w_slosh`、`w_eta`、`w_eta_dot` 全部纳入 effective-config diff；只检查 `w_slosh` 和 `v_ref` 不足以证明条件身份。

截至本文日期：

```text
W5_S10 = REJECT_FOR_FORMAL_STAGE
formal Bslosh = UNSELECTED
```

不得把今天 screening 的单次正向、旧 W5 默认值或旧 N=9 仿真最优行直接升格为正式方法。

### 4.2 `SmoothMatch`

在任何正式数据前，用独立 development 数据冻结一个 `v_ref_match`，使完成时间落入预注册的匹配容差。formal 时它相对 `Bsmooth` 只能改变：

```text
v_ref: <Bsmooth frozen value> -> <SmoothMatch frozen value>
```

其余 effective config 必须 byte-for-byte 或 canonical-value 等价。若完成时间 gate 在 `SIM-S1` 失败，不能从 40 条结果反向调 `v_ref` 后保留旧 rows。

### 4.3 `FixedProfile`

唯一候选身份继承实物定义：Hamaguchi-inspired two-impulse ZV fixed-path timing，只称 prior-art-inspired end-to-end comparator，不称对 Hamaguchi/Lim 的忠实复现。生成器候选为：

```text
src/scout_apps/control/scout_profile_baselines/scripts/hamaguchi/generate_profile.py
src/scout_apps/control/spmpc_experiments/config/profile_baselines/hamaguchi_profile.yaml
```

正式 profile 必须在第一条 formal row 前按 stratum 生成并冻结：

```text
H1 × C1
L1 × C1
H1 × C2
```

每份保存 generator revision、输入 path/container hash、输出 CSV/hash、tracker config/hash、约束 audit 和只读权限。一个 stratum 的 8 个 blocks replay 同一冻结 profile；环境 seed 只改变 plant/传感/执行扰动，不重新优化 timing。

若 C2 需要按预声明物理参数生成新 profile，这是 transfer 设计的一部分；不得同时改 tracker、限制、path 或生成算法。

当前 profile suite 的 `freshness_claim=current_sim_only` 且按 case 生成 profile，只能作为 development capability，不能签署此处的正式 `FixedProfile`。

### 4.4 可选 matched-weight 诊断

可另设：

```text
SIM-DEV-MATCHED-WEIGHT
```

使用同一 `B_slosh` solver/state/release 做两行：

```text
Bslosh_w0:     w_slosh = 0
Bslosh_wFinal: w_slosh = <final frozen value>
```

两行都保留相同的 `w_control/w_smooth/v_ref`、液体状态维度、observer、delay、limiter 和 solver，只切换 slosh cost 权重，用于拆分“液体项净贡献”和“整套系统比较”。它不属于五条件主表，不得替换正式 `Bsmooth` 或把样本加入 40/64/88。

## 5. H1/L1 与 C1/C2 的仿真映射

### 5.1 路径

H1 必须继承实物冻结路径并包含：

1. 起步加速；
2. 持续曲率；
3. 曲率反转；
4. 退出弯道后的再加速；
5. 终端制动。

L1 保持相同任务接口，但降低最大曲率、曲率变化率和液体激励。它不是靠“不显著”自动通过的负对照。

仿真应直接 replay 冻结 JSON。若地图坐标不同，只允许预冻结一个刚体变换：

```text
p_sim = R * p_real + t
yaw_sim = yaw_real + yaw_offset
```

必须保存 source JSON/hash、transform/hash、derived JSON/hash，并验证弧长、曲率和 Z1–Z5 分段在数值容差内不变。不得用当前脚本运行时生成的通用 `s_curve` 代替 H1/L1。

derived path 还必须通过 current sim world 的 fit/clearance audit；刚体变换不能让车体、容器或安全 footprint 接近墙体/障碍物后仍声称只改变了坐标系。

H0/H0b/H0s 只用于 development、plant 校准和 runner smoke；看过这些结果后仍不得修改 H1/L1 formal JSON。

### 5.2 容器与 plant 参数

C1/C2 的数值不得在本文件中臆造。它们必须来自实物最终 manifest，包括至少：

```text
container geometry
liquid height / freeboard / density
mounting pose and offset
damping/model calibration version
sensor and actuator properties
```

Stage II-B 中允许变化的只有预注册的 C2 物理参数：

- plant 使用 C2 物理参数；
- `Bslosh` 只更新 release 明确允许更新的物理模型参数；
- `FixedProfile` 用同一 C2 参数预生成冻结 profile；
- weights、阻尼、horizon、solver、硬限制、H1、执行层和测量链保持不变。

C1/C2 是两个 batch，不能按同编号 block 强配对，也不能把其差异写成无条件 interaction。

## 6. 独立液体 plant truth：正式 primary 的前提

### 6.1 为什么当前 `/slosh/height` 不合格

当前代码链是：

```text
Gazebo robot odom
  -> slosh_monitor_node: finite difference/filter 得到 ax, ay=v*omega
  -> LiquidSloshModel 单模态状态更新
  -> /slosh/height
```

实现证据位于：

```text
src/scout_apps/control/slosh_models/src/slosh_monitor_node.cpp
src/scout_apps/control/slosh_models/src/liquid_slosh_model.cpp
src/scout_apps/control/spmpc_local_planner/src/dynamics/slosh_dynamics.cpp
```

而控制器 `SloshDynamics::configure()` 直接实例化 `LiquidSloshModel`，复制其 `Ad/Bd`、固有频率和高度系数，再传播内部模态状态。因此：

- `/slosh/height` 是 controller-external、evaluation-only 的模型 proxy；
- 它对 B0/Bsmooth 等不反馈，仍可用于统一机制诊断；
- 但它与 `Bslosh` 共享模型族、参数和同一机器人运动输入，不是 Gazebo 中独立液体的 plant state；
- 它不能作为“模拟已证明真实液面下降”的 primary outcome。

monitor 的固定 `model_dt` 和加速度低通会让 `/slosh/height` 与 controller `H_modal` 数值不完全相同，但这种旁路差异不能建立物理独立性。当前 Gazebo world/robot 也没有 liquid/free-surface plugin，只有机器人、地面/墙、drive、laser 和 IMU 等模型。

`/spmpc/slosh_height` 更是控制器内部 `H_modal`，只能解释控制器认为自己做了什么。

### 6.2 正式 plant 的最低合同

在解除 formal NO-GO 前，仿真必须新增并冻结 plant-side liquid dynamics，满足：

1. plant state 与 controller state 分离，不能调用控制器 `SloshDynamics` 或直接复用其 observer state；
2. controller 永远不能订阅或读取 plant hidden state；
3. plant 由实际 simulated base motion/acceleration 驱动，而不是由未执行的 raw command 驱动；
4. 优先使用更高保真或至少独立实现/独立参数化的 multi-mode、free-surface surrogate 或 CFD-derived model；
5. 在 H0 development 数据上对实物 RGB 的幅值、频率、阻尼、相位和排序做预注册 fidelity validation；
6. 保存 plant code revision、parameter hash、initial-state rule、integration step 和 output schema；
7. 发布只读 truth，例如 `/sim_truth/liquid_height`，并由 recorder 读取，但通过 namespace/access-policy 验证 controller 没有订阅者。

建议正式指标名：

```text
H_plant(t) = abs(/sim_truth/liquid_height)
```

这里的“truth”只表示 simulator 内部 plant ground truth，不等价于现实真值。若 plant fidelity gate 未通过，88 条即使跑完也只能标为 controller/mechanism validation。

### 6.3 没有独立 plant 时允许的结论

若暂时继续使用 `/slosh/height`，数据集必须改标：

```text
evidence_class = MODEL_PROXY_MECHANISM_ONLY
primary_physical_efficacy_eligible = false
```

允许报告 tracking、runtime、solver stability、内部/外部 proxy、命令频谱和方向一致性；禁止使用 `H_plant`、`physical truth`、`liquid efficacy validated` 等表述，也不能用 proxy PASS 放行实物 formal Stage I。

## 7. delay、observer 与信息访问公平性

### 7.1 observer

仿真 `Bslosh` 必须继承实物最终 nominal source 和 fallback policy：

- 若实物冻结 odom，则仿真从模拟 odom 走同一 observer 语义；
- 若实物冻结 processed-IMU，则仿真必须实现相同采样、坐标、滤波、bias、timestamp 和 fallback；
- 不论哪种 source，未来 horizon 仍由预测机器人状态/控制传播；
- 禁止把 `/sim_truth/liquid_height` 或 plant modal state 注入 controller。

同一 release 中不得按 condition 或 run 临场切 source。发生 nominal-source fallback 时保留在该 `Bslosh` planned row 中并计 method failure，不重标、不用成功补跑覆盖。

### 7.2 delay 二选一

| plant 能力 | primary controller 设置 | 允许的 claim |
| --- | --- | --- |
| plant 已实现并冻结实车 actuator/sensor/transport delay | 继承实物最终 delay predictor 与 source semantics | 可称 hardware-delay-aligned simulation |
| plant 仍为当前零执行延迟 | `DELAY_PHASE_MODE=off`，linear/angular delay 为 `-1.0` | 只能称 sim-native controller/mechanism result |

不能采用第三种做法：plant 零延迟，但只在 controller 开启实车候选 delay，然后把相位错配结果称为实物对齐。

实车 delay 可以在 `SIM-DEV-DELAY-PAIR` 中做同代码、同 seed 的 paired diagnostic：

```text
plant zero delay + controller delay off
plant zero delay + controller candidate delay
```

该诊断用于解释 predictor 相位敏感性，不进入 88，也不替代完整 actuator-delay plant。

## 8. seed、随机化与 block

### 8.1 seed bundle

每个 block 冻结一个 `SEED_BUNDLE_ID`，至少控制：

```text
initial robot pose perturbation
initial liquid plant state / residual phase
actuator disturbance
sensor noise
environment/contact noise
simulator RNG seed
```

同一 block 的所有条件使用相同 seed bundle，以 common random numbers 降低成对方差；每个条件仍须销毁并 fresh 启动 ROS/Gazebo，然后重新加载同一初始状态。不同 block 使用独立 seed bundle。

不能只设置一个会被 method-dependent callback 次数消耗的全局 RNG。每类扰动应使用独立 sub-seed，优先预生成按 simulation time 索引的 disturbance/noise trace；每条 attempt 保存实际 trace hash，避免不同求解时长使随机流错位后失去 block 内配对。

seed 分布必须在 H0/development 上由实物合理范围或明确物理假设冻结。不得看到 H1 结果后挑“有利 seed”。若当前仿真完全确定、所有 block 初态也完全相同，重复 8 次不会产生 8 个独立实验单位；这种情况下只能算 deterministic reproducibility check，不能把相同轨迹的 8 份拷贝当 `n=8`。

### 8.2 三张独立随机表

必须分别生成：

```text
SIM-S1_CORE_randomization.csv
SIM-S2A_SELECTIVITY_randomization.csv
SIM-S2B_TRANSFER_randomization.csv
```

要求：

- Stage I 为五条件 randomized complete blocks，位置出现次数尽可能平衡，任一条件各位置次数差不超过 1；
- Stage II-A/B 各自为三条件 randomized complete blocks，位置同样尽可能平衡；
- 三张表独立生成，不能复用实物的顺序，也不能按 block 号跨 stage/容器配对；
- 保存 generator revision、algorithm、seed/seed commitment、CSV SHA-256 和 validator report/hash；
- 表不存在、行数不等于 40/24/24、condition set 不完整或 validator 不通过即 NO-GO。

每行至少包含：

```text
stage, planned_row_id, block_id, order_position, condition_id,
path_id, container_id, seed_bundle_id, planned_block_segment_id
```

### 8.3 block segment

记录：

```text
PLANNED_BLOCK_SEGMENT_ID
ACTUAL_BLOCK_SEGMENT_ID
SPLIT_BLOCK = (ACTUAL != PLANNED)
```

同一 complete block 尽量在同一软件/主机负载 segment 连续完成。跨 segment 的 recovery 只能进入 reliability ledger；除非未来冻结协议明确支持并验证，否则不能恢复主 paired eligibility。

## 9. strict-fresh 单 case 状态机

每个 planned row/attempt 执行以下不可交换的顺序：

```text
验证 RUN_ENV / randomization row / hashes
  -> preflight: ROS master 与 Gazebo master 均不可达
  -> fresh 启动独立 ROS/Gazebo/world
  -> 验证 map/world/path/plant/sensor topics 与参数
  -> 加载 seed bundle，plant/controller 全状态 reset
  -> 30 s pre-control settle
  -> 启动 recorder，确认 bag/数据文件正在增长
  -> 启动对应 backend，保持 start gate
  -> 释放冻结路径，开始 effective motion
  -> 最长 60 s 等待首次 GOAL_REACHED
  -> 记录冻结 motion+tail 窗口
  -> 正常关闭 recorder
  -> 仅停止本 runner 追踪的 PID
  -> 30 s post-shutdown wait
  -> postflight: ROS/Gazebo 均不可达
  -> 写 attempt manifest、QC、hash 与 dataset index
```

公共硬规则：

- 每个 condition fresh ROS/Gazebo，禁止同 session reset 后计正式结果；
- 显式传 map 和 world，二者都保存 hash，不能依赖脚本默认值；
- recorder 必须早于 planner 运动；
- 60 s 是从 tracking/effective-motion 计的 method timeout，不等于总 recorder budget；
- 到点后仍要保留最终冻结的 `T_HVIS_TAIL`（当前实物候选 5 s，以最终 freeze 为准）；
- 60 s 未到点时记 method failure，停止再次激励并继续记录到 `T_MOTION_MAX + T_HVIS_TAIL`；若安全要求提前关闭或 tail 不完整，continuous outcome 按冻结规则标 ineligible，但 failure-inclusive planned-row outcome 仍保留；
- recorder budget 必须覆盖 startup + 30 s settle + 60 s motion upper bound + tail + buffer；
- pre/post reachability 任一个为 true，该 attempt 不具 strict-fresh 资格；
- planner、FixedProfile tracker 和 liquid plant 每条都重新启动，不能在同一进程里切条件；
- 只停止自己追踪的 PID，不使用 broad `killall/pkill`。

现有 wrapper 中 `RECORD_SEC=60/70` 的含义必须在新 runner 中拆清，不能让 59 s 到点的 trial 因 recorder 同时结束而丢失 tail。

## 10. outcome、窗口与 claim 层级

### 10.1 Primary

仅在第 6 节独立 plant gate PASS 后：

```text
H_plant,p95(motion+tail)
window = first effective motion -> first arrival + frozen tail
unit   = mm
lower is better
```

关键 sensitivity：

```text
H_plant,p95(progress 10%–90%)
```

如果 simulator truth 的尺度与实物 `H_vis` 不能直接互换，必须在 formal 前冻结 `δ_H,sim` 的物理映射；不得跑完 H1 后按效果大小选阈值。只有 plant-vs-RGB 校准支持直接 mm 对齐时，才直接继承实物 `δ_H`。

### 10.2 Secondary

- motion-window `H_plant p95`；
- 统一 tail RMS、peak 和衰减时间；
- completion time、是否到点；
- contour/tracking p95、yaw p95、terminal error；
- collision、安全约束违例、published-zero/intervention；
- success/failure。

### 10.3 Mechanism

- `t(σ)`、`v(σ)`、Z1–Z5；
- 纵/横向四相位和局部制动/再加速；
- `a_x/a_y`、velocity/omega/acceleration/jerk；
- constant-scaling residual、`r_int` 与局部 command intervention；
- plant hidden state 与 `H_plant`；
- standalone `/slosh/height`，名称固定为 `H_proxy`；
- controller `/spmpc/slosh_height`，名称固定为 `H_modal`；
- raw/selected/delay-predicted solver-input state、horizon、cost breakdown；
- FixedProfile reference/index/progress 与 tracker state/error。

`H_proxy/H_modal` 只能解释机制，不能覆盖与 `H_plant` 相反的 primary 排序。

modal–plant fidelity supporting diagnostic 只使用 `Bslosh` planned rows：S1 后 8、S2A 后累计 16、条件性 S2B 后累计 24。不得恢复旧 K6=32 分母，也不得把其他条件缺失/为零的内部状态当样本。

### 10.4 Runtime

每条保存：

```text
solver/tracker runtime median, p95, max
control-loop achieved frequency
budget-overrun count/fraction
solver status and failure
fallback/intervention count/fraction
CPU/memory/sim real-time factor
```

仿真 real-time factor 或 CPU 饱和会同时改变传感采样和控制时序，必须进入 QC；不能把 condition-specific 计算压力造成的丢样简单归为可补跑 acquisition failure。

## 11. failure、retry 与固定分母

### 11.1 方法失败：禁止成功重跑覆盖

以下保留在 planned row 中：

- solver divergence/NaN/status failure；
- planner/tracker/profile execution failure；
- 60 s timeout、未到点、collision、安全终止；
- tracking 超限、method-specific command 异常；
- observer fallback、governor/fallback/intervention；
- controller/planner process crash；
- condition-specific config/profile/topic 错配；
- condition-specific CPU 压力、频率下降或数据缺失。

可另跑 diagnosis，但不能用新的成功 run 替换正式 outcome。

### 11.2 可能授权 retry 的基础设施/acquisition failure

只有冻结且 condition-blind classifier 能证明与方法 assignment 无关时，才可授权相同 row/seed/config 的 `r02+`，例如：

- 运动前 rosbag/结果写入未启动；
- 运动前 Gazebo/ROS 基础环境无法启动，且 planner 尚未消费 assignment；
- 外部存储、宿主机或调度系统中断；
- 方法无关的 world/map 基础设施损坏。

每次 retry 必须：

1. 保留原 artifact、日志和 failure record；
2. 由外部 verifier 生成 authorization ID/reason/hash；
3. 使用同一 planned row、condition、backend、profile、config 和 seed bundle；
4. 写 `RETRY_OF_ATTEMPT_ID`；
5. 每个 planned row 最多贡献一个按预注册规则选定的 eligible outcome。

同一 condition 连续失败超过 3 次时，runner 应自动暂停该 condition/阶段并触发审计。未执行的 planned rows 仍留在 `N_plan` 和 closure ledger 中，不能静默缩小分母；问题关闭后是否继续，只能按预冻结 stop/resume rule 决定。

### 11.3 固定报告分母

每个 stage/condition/contrast 至少报告：

```text
N_plan
N_attempt
N_method_success / N_plan
N_method_failure / N_plan
N_pair / N_block_plan
```

统计单位是 planned row。attempt、control cycle、Gazebo physics step、path point、topic message 都不能充当 n。

同时冻结 failure-inclusive `Y_plan` hierarchical win–loss：先比较 method success/failure；都成功时再按 primary 的 `δ_H` 和 completion/tracking tie-break；都失败时按 severity；授权 retry 用尽后的方法无关 missing 按预注册 no-information rule 和 sensitivity 报告。

## 12. contrasts、分析与 stage gates

### 12.1 Stage I 固定比较顺序

1. `Bslosh - Bsmooth`：第一物理主比较；
2. 第一步 PASS 后，`Bslosh - FixedProfile`：novelty comparison；
3. `SmoothMatch` 完成时间 gate 与 success tolerance；
4. `Bslosh - B0`：关键次比较；
5. `Bsmooth - B0`：机制诊断。

SmoothMatch、baseline 与其他次比较必须使用预声明层级或 Holm 调整，不能看完结果后升格。`Bslosh-FixedProfile` 是 end-to-end system comparison，不单独证明 dynamic memory 的物理因果必要性。

成功 trial 的连续 outcome 用 block 内 paired difference，报告 raw points、paired lines、mean paired difference、relative change、whole-block bootstrap interval 和 leave-one-block-out。必须同时报告 fixed-denominator 的 failure-inclusive `Y_plan`，不能只展示成功条件下的曲线。

actual randomization/permutation inference 必须复现真实 assignment，且只用于每个 planned row 都有定义的 `Y_plan`；paired sign-flip 如保留，只能作为对称性假设下的 sensitivity，不能称设计的 exact test。

### 12.2 `SIM-S1 -> SIM-S2A`

至少全部满足：

- 40 planned rows 和全部 attempts 闭包；
- plant/recording/sync/QC 合格；
- `Bslosh-Bsmooth` 达到预冻结 effect、interval 和 randomization gate；
- SmoothMatch 完成时间匹配且 primary 方向成立；
- FixedProfile novelty gate 成立；
- success、tracking、runtime、intervention 在容限内；
- 结果不由单一 block 独占，LOBO 方向稳定；
- trajectory、Z1–Z5、replay 与 execution audit 可运行。

失败即停在 40。改方法或规则后只能新 release 重开 Stage I。

### 12.3 `SIM-S2A -> SIM-S2B`

Stage II-B 的 C2、profile、随机表、within-C2 comparator、最小效应、trigger 和 stop rule 必须在 `SIM-S1` 第一条前注册。

放行必须同时存在：

1. S2A 24 rows/attempts closure PASS；
2. 不可变 S2A completion report/hash；
3. 独立 selectivity analysis report/hash；
4. 绑定前两者和预注册规则的 S2B trigger PASS。

否则停在 64，不能改 trigger 凑 88。

Stage II 的 primary comparator 默认候选为 `Bsmooth`，但必须以最终 contrast registry 为准。对 lower-is-better outcome 可定义：

```text
I_p,b^(m) = Y_m,p,b - Y_Bslosh,p,b
```

正值表示 `Bslosh` 更低。selectivity supporting quantity：

```text
D^(m) = mean(I_H1^(m)) - mean(I_L1^(m))
```

H1 与 L1 是独立 batch blocks，不能按相同 block number 跨路径配对。只能写 `batch-restricted supporting analysis`，不能写成无条件 path interaction。
