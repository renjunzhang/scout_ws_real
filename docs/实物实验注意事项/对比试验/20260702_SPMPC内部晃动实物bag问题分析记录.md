# 20260702 SPMPC 内部晃动实物 bag 问题分析记录

## 1. 当前问题

仿真中 SPMPC 内部消融结果支持 `B_slosh / B_ours / hard` 相比 `B0` 可降低模型晃动指标；但 2026-07-02 实物录包后观察到相反现象：

- `B0` 实物表现反而更好；
- `B_slosh`、`B_ours` 没有明显降低实物晃动；
- `B_slosh_hard_2p5mm`、`B_ours_hard_2p5mm` 开启 hard 后效果更差，且出现求解失败；
- 所有 bag 录制时都声称开启了相位补偿。

本记录用于固定当前诊断结论，避免后续把这批实物结果误解释为“方法已经被否定”或“2.5mm hard 约束已验证无效”。

## 4. 控制频率与执行链判断

### 4.1 配置与实测频率

当前 SPMPC planner 配置：

```text
control_frequency = 30.0 Hz
dt = 0.0333333333 s
horizon_steps = 60
```

Scout Mini 手册中 CAN 运动控制反馈帧、控制帧周期是 20 ms，即 50 Hz 口径；控制帧接收超时是 500 ms。

bag 中实测：

| topic | 典型频率 |
|---|---:|
| `/cmd_vel` | 约 30 Hz |
| `/odom` | 约 50 Hz |
| `/spmpc/solver_time_ms` | 约 30 Hz |

solver p95 全部低于 `dt=33.3ms`；soft slosh/ours p95 大约 14–15ms，hard p95 大约 4–7ms，B0 大约 4ms。因此当前没有证据表明“planner 30Hz 太高导致算不过来”。

### 4.2 当前判断

控制频率不是这批实物异常的首要嫌疑。更可能的问题是：

1. hard 约束参数没有按预期落地；
2. slosh 模型/observer 与真实液面响应存在相位或幅值失配；
3. phase compensation 虽已开启，但固定延迟值未必等于实物真实延迟；
4. slosh 权重和 eta-dot 权重尺度可能不一致。

后续可以做 30Hz vs 50Hz 对照，但不应优先把当前异常归因于“30Hz 过高”。

## 5. hard 2.5mm 约束的关键疑点

这是当前最可疑的问题。

这批 hard bag 的 sidecar 中可见类似配置：

```yaml
spmpc_local_planner:
  container:
    slosh_height_max: 0.0025
  slosh:
    slosh_height_max: 0.001
```

但代码读取 hard cap 的位置是 `slosh/slosh_height_max`，不是 `container/slosh_height_max`：

- `src/scout_apps/control/spmpc_local_planner/src/ros/spmpc_local_planner_ros.cpp` 中读取 `slosh/slosh_height_max`；
- `src/scout_apps/control/spmpc_local_planner/src/solvers/continuous_mpcc_solver_acados.cpp` 中用 `params_.slosh.slosh_height_max` 注入 hard constraint。

因此，文件名和 sidecar 中的 `container/slosh_height_max=0.0025` 很可能没有进入 solver；实际 solver 使用的仍可能是默认 `slosh/slosh_height_max=0.001`。

这与 hard 组现象一致：

- `B_slosh_hard` 出现 64 次 `ACADOS_SOLVE_FAILED_4`；
- `B_ours_hard` 出现 57 次 `ACADOS_SOLVE_FAILED_4`；
- hard 组首次到达时间变慢到 44–47s；
- `/spmpc/slosh_height` peak 反而升到约 8mm。

所以当前不能把这批 hard bag 解释为“2.5mm hard 约束无效”。更合理的解释是：**2.5mm 参数可能没有真正生效；实际 hard 约束仍接近 1mm，导致求解压力和实物执行变差。**

另外，OCP hard constraint 约束的是 modal-only：

```text
eta_x^2 + eta_y^2 <= eta_max_sq
```

它不是 RGB 真实液面硬约束；`/spmpc/slosh_height` 还可能包含 parabola term。因此论文中不能把该 hard constraint 表述为真实液面高度的严格物理硬约束。

## 6. phase compensation 判断

bag 中 `/spmpc/debug/delay_compensation` 和 `/spmpc/debug/execution_alignment_status` 基本都显示 `FIXED_CLOSED_LOOP_OK`，`shadow_valid` 约为 1.0。因此这批 bag 并不是“相位补偿没有开”。

但这只能说明 fixed closed-loop 逻辑被启用并通过守卫，不说明 `linear_delay_sec=0.15`、`angular_delay_sec=0.22` 一定是实物真实延迟。

如果固定延迟值偏差较大，slosh-aware 控制可能出现相位错误：优化器以为在反相抑制，真实系统却可能在加剧晃动。因此后续需要用 `/cmd_vel` 与 `/odom` 做 cross-correlation 校准，分别估计线速度、角速度执行延迟。

## 7. slosh 权重与方法层面的判断

当前 `w_slosh=5.0` 的 soft slosh/ours 能改变预测 horizon：

- `B_slosh` horizon peak p95 约 0.87mm；
- `B_ours` horizon peak p95 约 1.20mm；
- B0 因关闭 slosh 预测，horizon slosh 为 0。

但 `/spmpc/slosh_height` 观察值没有下降，反而高于 B0。这说明问题不是单纯“权重大一点/小一点”，而是存在以下失配：

1. 优化器压的是内部 modal state，不一定等价于实物液面真值；
2. 实物底盘执行延迟、低层滤波、轮地摩擦和水杯安装等因素会改变相位；
3. slosh observer 的高度代理量与 RGB 真值之间仍需标定；
4. hard 约束当前可能参数口径错误，不能作为有效证据。

之前代码审查中还发现一个需要优先核对的尺度问题：

- Python/codegen 默认口径：`eta_dot_ref = omega_n * eta_ref`；
- C++ runtime 当前口径：`eta_dot_ref = omega_n * h_ref`；
- 而 `eta_ref = h_ref / c_h`。

这会改变 eta-dot penalty 的实际尺度，可能让 slosh velocity 项与设计口径不一致。后续调 `w_slosh` 前，应先修正/统一该口径。

## 8. `v_ref=0.2` 与实际速度的注意事项

bag 中 `/spmpc/debug/v_ref_current` 基本为 0.2m/s，但 `/cmd_vel.linear.x` p95 可到 0.39–0.43m/s，max 可到约 0.46–0.52m/s。

说明当前 `v_ref` 不是硬速度上限；MPCC 的 progress reward 和动态约束仍会使实际命令速度超过 `v_ref`。

如果实物液面敏感，后续不应只调 `v_ref`，还应考虑：

- 降低 `robot/v_max`；
- 降低 `w_progress`；
- 提高速度跟踪/anti-creep 相关权重；
- 或为实物实验增加显式速度 envelope。

## 10. 当前结论

当前更可靠的判断是：

1. `B0` 在这批实物 bag 中确实表现更好；
2. soft slosh/ours 未在模型 observer 指标上带来实物收益；
3. hard 组明显变差并出现 acados solve fail；
4. hard 2.5mm 很可能没有真正写入 solver 使用的 `slosh/slosh_height_max`；
5. 控制频率/计算耗时不是首要问题；
6. fixed_closed_loop phase compensation 已启用，但固定延迟值还未校准；
7. 当前不能据此否定 SPMPC 方法本身，应先修实验口径、参数落地和真实液面指标。

## 13. 2026-07-03 当前问题梳理与优先级更新

本节是在前述 bag 复盘、延迟估计脚本输出、以及后续代码审查基础上的当前状态整理。它用于指导下一轮实物重跑；若与第 10–11 节的旧优先级冲突，以本节为准。

### 13.1 当前最强嫌疑：angular delay 严重过补偿

使用脚本：

```text
src/scout_apps/control/spmpc_local_planner/scripts/analysis/estimate_cmd_odom_delay.py
```

对 2026-07-02 实物 S 形 bag 做 `/cmd_vel` 到 `/odom` 的延迟估计后，当前判断如下：

| 通道 | 当前配置 | 实测估计 | 判断 |
|---|---:|---:|---|
| 线速度延迟 | 150 ms | 50–80 ms | 偏大约 2 倍 |
| 角速度延迟 | 220 ms | 5–10 ms | 严重偏大，约 20 倍 |

最关键的是角速度通道。`fixed_closed_loop` 相位补偿并不是复用上一轮 MPC 预测轨迹的下一刻状态，而是：

1. 读取当前测量的 robot/slosh 状态；
2. 使用最近发布过的 `/cmd_vel` 历史；
3. 按 `linear_delay_sec`、`angular_delay_sec` 和内部动力学模型向前积分；
4. 得到 `predicted_robot`、`predicted_slosh`；
5. 在守卫通过时，用预测状态替换 `solve_input.robot`、`solve_input.slosh`，作为本轮 MPC 的初始状态。

因此，如果 `angular_delay_sec=0.22` 远大于真实底盘角速度响应延迟，转弯时 `predicted_robot.yaw/omega` 会被明显推到未来相位。MPC 在错误初始状态上优化出的“抑制晃动轨迹”，落到真实系统上可能反而激发晃动。`B_slosh`、`B_ours` 对 slosh/turning phase 更敏感，因此会比 `B0` 更容易被错误相位补偿伤害。

限制：这批 S 形轨迹速度剖面较平滑，xcorr 峰值只有约 `0.2–0.4`，不能用于精确标定；它只能支持“`220 ms` 明显过大”的判断。

下一轮短实物重跑前，建议先采用保守欠补偿配置：

```yaml
delay_phase:
  linear_delay_sec: 0.08
  angular_delay_sec: 0.05
```

该配置不是精确标定结果，只是用于避免明显过补偿。精确标定需要单独录制原地左右转的方波角速度 bag。

### 13.2 当前问题分层

| 层级 | 问题 | 当前证据/状态 | 对实验的影响 | 处理优先级 |
|---|---|---|---|---|
| P0 | `angular_delay_sec=0.22` 明显过大 | 延迟估计显示角速度真实响应约 5–10 ms，S 形数据虽不适合精标，但足以说明 220 ms 过大 | fixed_closed_loop 初始状态相位错误，slosh-aware MPC 可能在错误 yaw/omega/slosh 相位上优化 | 最高 |
| P0 | delay 诊断口径可能误导 | 当前诊断曾用 `history_window_sec` 判断 history complete，可能与 predictor 实际 delay horizon 不一致 | bag 可能显示 fixed_closed_loop 未应用，但 solver 实际已经使用预测状态 | 最高 |
| P0 | slosh 诊断 raw/solver-input 语义不稳定 | `/spmpc/debug/slosh_state` 若改为 `solve_input.slosh`，同一 topic 会随 fixed_closed_loop 状态在 raw/predicted 间切换 | 离线脚本可能把控制器内部预测量误当 observer 实测量 | 最高 |
| P0 | `/spmpc/slosh_height` 可能混用状态源 | 若使用 `solve_input.slosh` 但仍使用 raw odom `omega`，在 `use_parabola_term=true` 时标量高度不对应单一状态 | 影响 hard margin、observer 高度和相位补偿效果解释 | 最高 |
| P1 | hard cap namespace 历史错误 | 旧 bag 中 `container/slosh_height_max=0.0025`，但 solver 读取 `slosh/slosh_height_max` | 旧 hard 2.5mm bag 不能证明 2.5mm hard 无效 | 高 |
| P1 | hard constraint 口径是 modal-only | acados 约束 `eta_x^2 + eta_y^2 <= eta_max_sq`，不包含 RGB 真液面，也不包含 parabola 高度项 | 不能把 solver hard cap 直接写成真实液面高度硬约束 | 高 |
| P1 | `eta_dot_ref` 尺度历史不一致 | C++ runtime 曾用 `omega_n * h_ref`，应与 `eta_ref=h_ref/c_h` 同口径改为 `omega_n * eta_ref`；当前已有修改但需要构建和实验验证 | eta-dot 惩罚可能曾被压小，导致 slosh 速度抑制不足 | 高 |
| P1 | `effective_config.v_ref` 诊断仍可能不准 | 若发布顺序在 solve 前，会滞后一拍；primitive/GOAL_REACHED 默认 `v_ref_debug=0` 时可能污染配置 topic | bag 中 effective_config 不能完全代表当前 tick solver 真实速度 | 中高 |
| P2 | shared command limits 只在求解后裁剪 | `platform/shared_constraints/*` 未进入 solver bounds，只在 `/cmd_vel` 下发前 clamp | solver 规划轨迹和实际执行命令可能不一致 | 中 |
| P2 | `v_ref` 不是硬速度上限 | bag 显示 `v_ref_current=0.2`，但 `/cmd_vel.linear.x` p95/max 可超过 0.2 | 不能仅靠调 `v_ref` 控制实物激励，需要看 `v_max`、`w_progress`、后级限幅 | 中 |
| P3 | S 形 bag 不适合精确 delay 标定 | 输入太平滑，xcorr 峰值低 | 只能判断明显过大，不能得出 ±5 ms 级精确延迟 | 中 |

### 13.3 下一轮实验前的最小修正清单

在继续大规模调 `w_slosh`、hard constraint 或做论文对比前，建议先完成以下最小闭环。

1. 修正/确认 delay 相关诊断口径：
   - `history_complete` 应与 `ExecutionStatePredictor` 实际补偿 horizon 一致，而不是简单等于 `history_window_sec` 是否覆盖；
   - `cmd_odom_alignment.fixed_closed_loop_applied` 必须表示本轮 `solve_input` 是否真的被预测状态替换；
   - 保留 raw state 与 solver-input state 的区别，避免一个 topic 同时承担两种语义。

2. 修正/确认 slosh 诊断口径：
   - 若发布 raw observer 状态，则 topic 名和文档保持 observer 语义；
   - 若发布 solver-input slosh，则建议另设 topic 或明确标注，例如 `solver_input_slosh_state`；
   - `slosh_height` 若使用 solver-input slosh，则角速度也应使用同一 `solve_input.robot.omega`，否则会混用 predicted slosh 与 raw odom omega。

3. 使用保守 delay 配置做短实物 smoke：

```yaml
delay_phase:
  mode: fixed_closed_loop
  linear_delay_sec: 0.08
  angular_delay_sec: 0.05
```

建议最小矩阵：

```text
B0
B_slosh_old_delay
B_slosh_new_delay
B_ours_old_delay
B_ours_new_delay
```

目的不是形成最终排行榜，而是验证“过大的 angular delay 是否是 B_slosh/B_ours 变差的主因”。

4. 单独录制原地角速度方波 bag：

```text
0.0 rad/s  1s
+0.25~0.40 rad/s  2s
0.0 rad/s  1s
-0.25~0.40 rad/s  2s
重复 5–8 次
```

至少记录：

```text

/odom
/spmpc/debug/cmd_vel_output
/spmpc/debug/odom_timing
```

用 `estimate_cmd_odom_delay.py` 分别估计 linear/angular delay。只有这类边沿清楚的信号才适合精确标定。

5. hard 组重跑前必须确认：
   - `slosh/slosh_height_max` 是唯一权威路径；
   - 若兼容读取 `container/slosh_height_max`，不能让旧 deprecated key 覆盖显式 canonical key；
   - bag 中 `/spmpc/debug/slosh_hard_constraint_effective` 显示实际 `h_limit_mm=2.5`；
   - hard 约束仍按 modal-only 解释，不写成真实液面/RGB 硬约束。

### 13.4 当前对论文/汇报结论的约束

这批实物 bag 当前只能支持以下保守结论：

1. 在旧配置下，`B0` 的模型 observer 指标和实物观感优于 `B_slosh/B_ours`；
2. 旧 hard 组存在明显求解失败和实物退化，但 hard cap 参数 namespace 曾不一致，因此不能证明 `2.5 mm` hard 本身无效；
3. fixed_closed_loop 虽然开启，但 `angular_delay_sec=0.22` 很可能严重过补偿，是当前最强嫌疑；
4. 在 delay、诊断口径、eta-dot 尺度、hard cap 生效路径稳定前，不能把这批结果作为“SPMPC 方法被实物否定”的证据；
5. 下一轮实验应优先验证 delay 配置修正是否恢复 slosh-aware variant 的效果，再讨论权重、hard constraint 和最终 RGB 指标。

## 14. 2026-07-04 仿真补充：fixed_closed_loop delay 可能反向激励 slosh

本节补充 2026-07-04 在隔离仿真 `/data/a/scout_sim_replacement` 中做的 strict fresh-sim 对照。目的不是形成新排行榜，而是回答一个更具体的问题：**slosh cost 本身是否坏了，还是 fixed_closed_loop delay compensation 把相位带偏了？**

### 14.1 对照口径

统一条件：

```text
MATRIX=spmpc_B0 spmpc_B_slosh
MODE=closed_loop
GOAL_X=5.0, GOAL_Y=0.0, GOAL_YAW=0.0
PATH_TEMPLATE=s_curve
PATH_START_HEADING=current
PATH_AMPLITUDE_RATIO=0.18
PATH_MIN_AMPLITUDE=0.25
PATH_MAX_AMPLITUDE=1.20
PATH_SIDE=left
PATH_SMOOTH_ITERATIONS=3
strict fresh-sim=true
```

只改变 delay-phase：

1. `fixed_closed_loop, linear=0.08, angular=0.05`；
2. `delay off`。

### 14.2 关键结果

`fixed_closed_loop 0.08 / 0.05` 对照中，`B_slosh` 的 slosh 反而显著变大：

| delay 口径 | variant | `/slosh/height` p95 | `/slosh/height` max | internal `/spmpc/slosh_height` p95/max |
|---|---|---:|---:|---:|
| fixed 0.08/0.05 | `B0` | 0.742 mm | 1.555 mm | 0.592 / 1.211 mm |
| fixed 0.08/0.05 | `B_slosh` | 3.309 mm | 3.934 mm | 5.395 / 6.903 mm |

而 `delay off` 对照中，slosh cost 本身仍能压低内部模型 slosh，并且外部 `/slosh/height` 没有恶化：

| delay 口径 | variant | `/slosh/height` all p95/max | `/slosh/height` first15 p95 | internal `/spmpc/slosh_height` p95/max |
|---|---|---:|---:|---:|
| off | `B0` | 0.571 / 1.047 mm | 0.533 mm | 0.737 / 1.338 mm |
| off | `B_slosh` | 0.571 / 0.930 mm | 0.419 mm | 0.476 / 1.233 mm |

对应结果目录：

```text
/data/a/scout_sim_replacement/results/strict_fresh_fair_n3_20260704_confirm_delay_off_B0_Bslosh
/data/a/scout_sim_replacement/bags/strict_fresh_fair_n3_20260704_confirm_delay_off_B0_Bslosh
```

### 14.3 当前解释

上述结果说明：

1. `B_slosh` 的 slosh cost 没有整体失效；在 `delay off` 口径下仍能降低内部 `/spmpc/slosh_height`，并使核心运动窗口的外部 `/slosh/height` p95 下降。
2. 仿真中不应默认开启实车候选 `fixed_closed_loop 0.08/0.05`；隔离仿真没有实车同等 command/odom 执行延迟，强行 forward-predict solver input 会把 slosh/robot state 推到错误相位。
3. 如果相位补偿错误，slosh-aware variant 比 `B0` 更容易被带偏：优化器以为在反相抑制，实际可能在正向激励。
4. 因此，“slosh cost 占比很高但 slosh peak 没降”不能直接解释为权重没用；必须同时检查 `solver_input_state`、`raw_state/predicted_state` 和 `command_intervention`。

### 14.4 对下一轮实物实验的更新
