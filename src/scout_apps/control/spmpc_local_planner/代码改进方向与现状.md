## 实验比较与配置

主比较为原路线直接进入普通 `raw_mpcc`，对比完整 `planned_slosh`。`geometry_mpcc` 检查只有下层自主几何时的变化；`planned_mpcc` 与 `planned_slosh` 共用同一上层液体计划，隔离下层液体项。上层是否考虑液体需另生成目标权重关闭的计划。

四组共同区域、运动限制、目标容差、期限、jerk 和评价窗口。raw 的新几何/目标软代价、全部液体决策关闭；其 contour 为 1，另外三组为 0.02。几何权重 0.05、曲率变化权重 0.01、目标权重 2 和 RTI 上限5次均为软件候选。`trajectory_common.yaml` 开 MPC 停车交接和 jerk，`terminal.complete_stop.enable=false`；此前 `model_v234_development.yaml` 是历史开发覆盖层，不能无条件叠到新四组上。

默认四组使用普通停车，均未开启完整液体稳定等待；raw 的液体决策必须保持关闭，液体组可另用覆盖层启用并单独记录。基础 observer 默认仍为 odom，实物 I0/processed-IMU 来源须用覆盖层明确配置并核对实际 selection。没有新相机融合估计器，内部 modal 高度不等于实测液面。

四组的区域停车尾段检查始终启用，复用 `terminal.complete_stop` 下的预算和quiet参数；`enable=false`仅关闭完整液体稳定等待。连续投影窗口、停车预算和回放来源的参数入口见配置README；不再复制另一套控制参数。

## 本轮收敛修复与后续边界

[前五项修复](../../../../docs_for_offlineslosh/实现与修复/20260916_局部规划器五项修复与回归.md)和[合并审查的原始反例](../../../../docs_for_offlineslosh/实现与修复/20260916_当前主线复盘与剩余缺口.md)保留历史语境。本轮不修改CAN/SDK，不增加规划层，不用调低跟踪误差掩盖问题。

| 收敛项 | 当前实现 |
| --- | --- |
| 发布与求解预算 | RTI最多执行配置次数，按剩余时间决定继续；记录实际次数。发布前检查ROS状态epoch及steady clock耗时，过期结果拒绝 |
| 最终命令 | trajectory四组关闭重复shared limiter，默认改写即拒绝；无输出路径执行相同检查，外部审计更新相同历史命令基线 |
| 状态恢复 | 位姿相对实测运动突跳先拦截，再更新连续进度；液体状态积分必须完整覆盖时间增量，缺口后不靠filter READY自动恢复 |
| 停车 | 复用共同速度/角速度上下界检查全尾段和FIFO；汇总RK4子步峰值，再由已有液面policy按开关核验；普通数值故障可使用本周期可信尾段持续接管 |
| 参考端点 | 真实单侧切向、非零拟合窗口、局部归一化QR及既有绝对progress输出；不改OCP参数维度 |
| B0高度评价 | 独立Python旁路使用同epoch可信液体初态和每stage预测actual/FIFO，持续传播液体；零占位不再作为评价，旁路不反馈控制 |

液体断流后的实物恢复采用“确认静置、重启节点”流程，代码提供显式可信初始化API供有依据的调用，不加入运动中自动清零。定位持续换坐标系也需要明确任务重置/重启。小幅定位漂移、真实液体未知初态及硬件传输延迟并未因软件门而消失。

近期后续按用户[验证思路](../../../../docs_for_offlineslosh/验证与论文/20260916_B0与双层防晃MPCC从仿真到实物的验证思路.md)推进：冻结共同S路线、区域、速度/耗时和初态 → 同核评价与充分预算名义比较 → 有限预算及真实IMU链 → ROS1整编译/发布路径 → 用户实物。RGB不是前置条件，IMU模型重建不称作直接液面实测。

仍需区分的边界：

- 当前尚无相近耗时下相对B0的稳定降晃结论；原有缓弯、更快不能替代高度与残余评价。
- 后缀检查仍是离线诊断；在线非劣候选接受、递归可行保证、动态避障不在本轮实现范围。
- 单次RTI不能抢占；预算与过期拒绝不构成30 Hz验收，ROS1整节点、实际发布和实物仍待验证。
- 实物液面硬上限需要冻结freeboard/margin及模型条件；停车子步采样不是连续时间安全证明。
- 外部回放history参数仍需launch与overlay双传同值，暂不为便捷性扩展入口；现有脚本README给出准确用法。

用户确认当前实物为 `7d17f6c4c3f07259323c4ff38666ef6777ce430a`，已有FIFO、一阶响应和四子步RK4，沿用其正常CAN链路。`81e191d`只标识已归档两包。新默认来源/速度/jerk/权重不能直接套用为当前实物条件，CAN异常断流场景不列近期修复。
