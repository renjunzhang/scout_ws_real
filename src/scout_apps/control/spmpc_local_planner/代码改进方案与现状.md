## 0. 这份文档的用途

这不只是一份“待修 bug 列表”，还是后续修改 SPMPC 时必须遵守的回归保护契约。

任何后续改动都必须：

1. 对应本文一个稳定的问题 ID；
2. 先增加能复现该问题的测试，再改行为；
3. 明确记录修改了 B0/slosh 共用链路还是 slosh 特有链路；
4. 不得靠放宽物理约束、更换路径、隐藏后限幅或调 slosh 权重来掩盖 B0 跟踪问题；
5. 在代码、生成求解器、配置、路径 SHA 和实验证据之间建立可追溯关系。

本文中的状态含义：

- `CONFIRMED`：代码路径已确认，可给出明确触发条件。
- `CONDITIONAL`：代码确实存在风险，是否触发取决于路径、终点位置或运行配置。
- `TO_IMPLEMENT`：改法已定义，但尚未改代码。
- `TO_VALIDATE`：已实现后仍必须通过仿真/延迟工厂/实物门。

## 2. 审查结论

当前确实存在能够解释“入弯转向不及时”和“大曲率弯过不去”的代码/结构问题，不应先归因于 slosh 权重或单纯调参。

当前最有解释力、且同时有代码与 bag 支持的机制组合是：

```text
执行延迟未进入默认闭环
  + cmd_omega 每拍都从滞后 odom_omega 只积分一个 dt
  + objective 没有 yaw / omega=v*kappa 前馈
  + 却惩罚 omega 和 alpha
  + v_ref 只按 omega 上限限速，不管 alpha 可达性
  + 远期路径被单个三次多项式改变
= 车在转弯前缺少建立角速度的动机，等位置误差已出现后才大幅纠正
```

在大曲率或曲率快速变化段，又会叠加：

```text
自己生成的参考速度对 alpha_max 不可达
  -> OCP 只能在减速、外切、滞后或求解失败中取舍
  -> anti-creep 又对进一步减速施加重罚
  -> 偏离后可被 projection/spin safety 锁死
```

### 2.1 与 `931f3d7` 的回归比较结论

**结论：没有证据表明 `931f3d7..9729e80` 把 B0 的 OCP 数学模型改坏了。**

该区间保持不变的 B0 行为核心包括：

- 6 维状态 `[x,y,yaw,v,s,omega]` 和 3 维控制 `[a,alpha,v_s]`；
- `spmpc_acados_model.py` 与 `spmpc_acados_cost.py`；
- B0 权重、参数布局与 generated B0 solver；
- 投影、局部参考拟合和 warm-start 核心；
- `cmd_omega = measured_omega + alpha_0*dt` 的出口语义；
- terminal slowdown/capture/omega clamp 及 tracking spin/projection gate。

`git blame` 反向确认：角速度单步积分来自 2026-06-08/10，terminal `1.20 m` slowdown 和 `0.25/0.10 rad/s` 角速度夹限来自 2026-06-05/10，都早于 `931f3d7`。

`931f3d7` 之后真正可能触及 B0 运行链的改动是：

| commit/变化 | 对 B0 的实际影响 | C02_v2/a02 证据 |
|---|---|---|
| `a2fe0c2` IMU shadow + odom 时间戳/有限值/dt 严格接纳 | odom 重复、乱序或异常 dt 时可拒绝更新，是唯一值得保留的 post-931 行为回归候选 | odom 50 Hz 稳定，`dt_clamped=0`，未观察到拒绝链先于跟踪恶化 |
| `01700fd` observer selector | B0 只发诊断，不消费液体状态 | audit 明确为 `LIQUID_NOT_CONSUMED` |
| `88ca590` `fixed_robot_only` | 新增诊断/消融模式，当前 B0 `shadow` 不走该闭环 | `delay_compensation_applied=false` |
| `6764151` cycle audit/state timing/command contract | 增加审计与安全契约；B0 不需液体 common epoch，默认后限幅不改命令 | 30 Hz 稳定，无 contract violation、shared limiter 或 safety gate 介入 |
| `c5209cf/ce6efd0/8f87a8d` 动捕执行脚本 | 新建了一套实验口径：`V_REF=0.10`、`delay=shadow`、共享后限幅关闭 | 这是当前 run 与旧成功基线最大的行为差异 |
| `9729e80` | 仅验收脚本/测试、NOKOV launch 和文档 | 不修改控制器、OCP、权重或 generated solver |

因此，不能把当前 B0 质量失败简化成“`931f3d7` 之后某个 OCP commit 回归”。更准确的说法是：**post-931 新试验口径和新路径把 pre-931 已存在的跟踪结构缺陷稳定暴露了出来。**

本文所说的“B0 失败”是 **tracking-quality/release failure**，不是 ACADOS 返回失败或没有到点。a01/a02 最终都进入 `GOAL_REACHED`，但中途存在大航向/轮廓误差、长时 alpha 饱和和停滞，因此不能作为可放行的基础 B0。

### 2.2 当前 C02 与旧成功 B0 不是同口径 A/B

当前 C02_v2/B0/a02 实际运行为：

```text
V_REF=0.10
delay_phase=shadow
linear/angular shared limiter=false
alpha_max=1.2
path SHA=1464ef37...
```

`shadow` 只计算并发布预测诊断，不替换 `SolverInput`，所以在控制行为上等价于未做延迟补偿。历史干净 B0 证据是 `fixed_closed_loop 0.15/0.22 s`：2026-07-05 记录的 contour p95/max 约 `0.0257/0.0538 m`、yaw p95/max 约 `0.065/0.155 rad`。同日 delay off + 保守角向权限发生 `TRACKING_UNSAFE_PROJECTION`。

所以要验证是否真有 post-931 行为回归，必须在同一路径 SHA、同一 delay mode、同一速度/角向边界、同一 terminal 口径下对两个 binary/commit 重放；当前证据不满足这个条件。

### 2.3 C02_v2/a02 的转向时序归因

a02 有 `1180` 个连续 `B0_ACADOS_OK` 周期，之后进入 `GOAL_REACHED`；没有 ACADOS 失败、tracking safety 或 command-contract 失败。以第一个 `B0_ACADOS_OK` 为 `t=0`，从 `PreSolveSnapshot.reference_*_coeffs` 重建 OCP **真正使用**的多项式曲率，得到：

| OCP 曲率换向 | `v*kappa_poly` 越过 `0.05 rad/s` | `u0_alpha` 进入同向 | 发布 `omega` 越过 `0.05 rad/s` | `/odom omega` 越过 `0.05 rad/s` |
|---|---:|---:|---:|---:|
| 负向换向 | `5.13 s` | `5.80 s` | `7.53 s` | `9.13 s` |
| 正向换向 | `15.46 s` | `16.53 s` | `17.83 s` | `18.93 s` |
| 最后负向 | `24.76 s` | `24.23 s` | `26.60 s` | `27.93 s` |

换向时 OCP 已经看到正确的前方曲率，但发布角速度换向比几何需求晚约 `1.83~2.40 s`。典型单帧：

```text
s=1.201 m: kappa_poly=-0.815 1/m, v=0.338 m/s
              v*kappa=-0.276 rad/s
              u0_alpha=-1.199 rad/s^2
              published_omega=+0.181, measured_omega=+0.221 rad/s

s=2.997 m: kappa_poly=+0.916 1/m, v=0.338 m/s
              v*kappa=+0.310 rad/s
              published_omega=-0.001, measured_omega=-0.020 rad/s
```

这不是“求解器没看到弯”，而是“看到了，但 objective/出口链没有及时建立角速度”。负弯中还出现了确定的 creep/stall：

```text
t=9.66..11.67 s, s=1.677..1.678 m
median raw_v=0.004 m/s, published_v=0, u0_v_s=0
median u0_alpha=-1.2 rad/s^2
all cycles remain B0_ACADOS_OK
```

物理底盘延迟会叠加，但不能单独解释上述 `1.8~2.4 s` 的软件命令换向滞后：

- 闭环 bag 上的粗略相位拟合给出 published command 到 `/odom` 约 `0.16 s`、到动捕姿态导数约 `0.125 s`；由于 command 本身反馈依赖 odom，这不能替代专用开环延迟辨识；
- 历史独立激励证据给出角通道约 `0.18~0.28 s`；
- Cartographer/TF yaw 与独立 NOKOV yaw 做常数外参对齐后，零延迟的 yaw RMS/p95 仅约 `0.0044/0.0084 rad`；加入平面外参和 tracker-to-base 杠杆臂后，位置 RMS/p95 约 `0.0129/0.0223 m`。没有证据表明大尺度定位滞后是该次失败主因。

### 2.4 当前归因的置信度排序

1. **高置信组合归因：** `shadow` 未进闭环 + 从滞后 `measured_omega` 每拍重锚定 + 无 yaw/`omega=v*kappa` 跟踪收益，共同解释了换向过慢和弯中停滞，是当前首要整改对象；各项的独立贡献仍须用 Stage 0/2/6 受控回归隔离。
2. **高置信：** `V_REF=0.10` 不是硬限速，实际运行仍到约 `0.36 m/s`，“低速路径选择”的安全前提不成立。
3. **高置信：** 参考诊断混用 spline 与 OCP polynomial 两套曲率，过去只根据 `stage0_reference.ref_kappa` 做的转向时序结论可能偏乐观，甚至会判断错换向时刻。
4. **中高置信：** terminal controller 真实覆盖最后 `1.21 m` 弯道并改变命令，会妨碍最后弯的跟踪/恢复，但它不解释更早的非 terminal stall。
5. **低置信：** post-931 odom 拒绝、求解超时、shared limiter、safety gate 或动捕定位质量是 a01/a02 主因；现有 bag 均给出反证。

## 3. 已确认问题清单

### SPD-01：`v_ref` 是软代价参考，却被现场流程误当成低速安全上限

**状态：`CONFIRMED`，优先级 P0。**

C02_v2/B0/a02 设置 `V_REF=0.10 m/s`，但发布线速度 P95/最大约为 `0.350/0.363 m/s`，核心运动段超过 `0.30 m/s` 的比例约 `23.7%`，且没有任何后置线速度 limiter 介入。当前代价同时奖励虚拟进度并惩罚 `v_s-v_ref`；忽略其他耦合项时：

```text
v_s* = v_ref + w_progress*v_s,max/(2*w_vs)
     = 0.10 + 0.2*0.8/(2*0.3)
     = 0.3667 m/s
```

该值与实测速度上沿接近。因此必须拆开两个契约：`v_ref` 继续表示优化软目标，另设可审计的运动安全硬上限，并在 OCP bounds、运行时配置、runner 前门和 postflight 中保持一致。不得再用调低 `V_REF` 代替速度上界。

### VAL-01：postflight 只证明数据完整，不能判定路径跟踪质量

**状态：`CONFIRMED`，优先级 P0。**

C02_v2/B0/a02 的自动 postflight 为 `pass=true`：solver/artifact、topic、时间戳、路径 SHA、B0 不消费液体状态和命令发布契约均完整；但同一 bag 的 contour error P95/最大约为 `0.149/0.159 m`，yaw error P95/最大约为 `0.400/0.410 rad`，全部 solve cycle 中又有 `645/1180=54.7%` 的 `abs(alpha)>=1.19 rad/s^2`。这说明当前 PASS 只能命名为 acquisition/data-integrity pass。

上述 yaw 数字是 non-terminal 口径。若看完整行为链，terminal 阶段在排除路径端点拟合退化样本后的 yaw P95/最大还达到约 `0.505/0.507 rad`。当前 validator 会把 terminal cycle 从 `nominal_audits` 排除，这对数据完整性是合理的，但跟踪质量门不能因此忽略最后弯道。

还有一个分析口径陷阱：该 bag 的 `/mocap/scout_odom.twist` 在运动全程为零，它是 pose bridge 输出，不是可直接使用的动捕速度真值。当前 planner 正确使用 `/odom`；后续不得在未增加有效 twist 估计和契约的情况下把 `topics/odom` 改成 `/mocap/scout_odom`。动捕角速度应从姿态和时间戳另行估计。

正式运动入口必须再增加独立的 tracking-quality gate，至少检查实际速度上界、contour/yaw P95 与最大值、进度连续性、控制饱和占比、delay configured/applied 一致性、终点状态和安全介入。阈值必须在正式 R01 前冻结；质量 gate 未通过时不得仅凭现有 postflight 启动下一条。

### TRK-01：指令从滞后实测状态重新积分，实物入弯角速度建立过慢

**状态：`CONFIRMED`，优先级 P0。**

当前出口：

```cpp
cmd_v     = measured_v     + a_0     * dt;
cmd_omega = measured_omega + alpha_0 * dt;
```

位置：`src/solvers/continuous_mpcc_solver_acados.cpp:1090-1095`。

当 `alpha_max=1.2` 且 `dt=0.0333 s` 时，一拍最多只能让发布命令超前实测角速度约 `0.04 rad/s`。若底盘角通道有 `0.18~0.28 s` 延迟，odom 在多个控制周期内几乎不变，后续命令就会不断从同一个滞后值重新起步。线速度通道也有同样问题，一拍只能超前约 `0.02 m/s`，会让弯前减速也滞后。

C02_v2/a02 对这个机理给出了直接实物证据：

- 非 terminal cycle 中 `published_omega == measured_omega + u0_alpha/30` 在数值精度内恒成立；
- 全部 `1180` 个 solve cycle 中，`645` 个的 `abs(alpha)>=1.19`；
- `t=6.10..11.20 s` 连续约 `5.10 s` 的负向饱和期间，`alpha=-1.2` 每拍只能使命令保持在当前实测值下方约 `0.04 rad/s`，不会按已发布命令继续累积；
- 该段最终在 `s≈1.678 m` 出现约 `2.0 s` 的进度停滞，所有周期仍是 `B0_ACADOS_OK`。

因此“大曲率弯过不去”不一定会表现为 ACADOS failure；当前更常见的表现是 alpha 长时饱和、角速度慢慢追、`v_s/cmd_v` 塌到零，等航向转够后再继续前进。

代码已有延迟状态预测器，但 `config/planner/common.yaml:170-178` 默认为 `off`。历史实物证据与此高度一致：

- `docs/实物实验注意事项/后续改进/20260627_SPMPC实物延迟与相位补偿_模块化修改方案.md:143-156`：`cmd_omega -> odom_omega` 约 `0.18~0.28 s`。
- `docs/实物实验注意事项/对比试验/实物对比实验/0705B0_fixed_path基础跟踪调试指南.md:412-424`：同一 B0，`fixed_closed_loop 0.15/0.22` 干净到点，delay off + 保守角向权限发生 `TRACKING_UNSAFE_PROJECTION`。

**注意：**若某个具体 runner 已显式传入 `fixed_closed_loop`，本问题在该 run 中会被部分缓解；不能只看 `common.yaml`，必须看 `/spmpc/debug/effective_config` 和 delay diagnostics。

### SAFE-01：`spin_fail` 把合法持续转弯也当成原地旋转

**状态：`CONFIRMED`，优先级 P0。**

当前 tracking gate 的判断只是：

```text
tracking phase
AND (abs(measured_omega) > 0.5 OR abs(cmd_omega) > 0.5)
AND duration >= 2.0 s
```

终点阶段对应阈值更低，为 `0.2 rad/s` 和 `2.0 s`。代码没有检查线速度、路径进度、投影是否正常或车是否真的原地打转。

位置：

- `src/ros/spmpc_local_planner_ros.cpp:1292-1318`
- `src/ros/spmpc_local_planner_ros.cpp:1321-1385`
- `config/planner/common.yaml:120-134`

例如 `v=0.25 m/s`、半径 `0.4 m` 的 90° 圆弧需要 `omega=0.625 rad/s`，转弯时间约 `2.51 s`。车即使完全正确地沿路径行驶，也会被当前逻辑置为 `TRACKING_SPIN_FAIL`，之后锁存零命令。

这是一个安全逻辑 bug，但修复时不能直接删掉 safety gate。必须改为“高角速度 + 低平移/低进度 + 持续时间”的组合判定，并保留真正原地自旋时的 fail-closed 能力。

### COST-01：跟踪 objective 没有航向误差和曲率角速度前馈

**状态：`CONFIRMED`，优先级 P1。**

`scripts/acados/spmpc_acados_cost.py:33-46` 的 tracking cost 只有 contour/lag 位置误差，没有：

- `yaw - path_yaw` 误差；
- `omega - v*kappa` 误差；
- 弯前 `alpha` 或 `omega` 前馈。

同时 `scripts/acados/spmpc_acados_cost.py:189-205` 在惩罚 `omega` 幅值和 `alpha` 幅值。因此在车还位于中心线上、contour error 尚小时，提前建立角速度只有控制代价、没有直接跟踪收益。虽然未来位置误差会间接提醒 OCP，但在 SQP-RTI 单步、延迟状态和参考拟合误差同时存在时，这种间接信号不够稳定，容易表现为“误差出现后才转”。

a02 还排除了“多项式没把前方弯告诉 OCP”这一单独解释：在 `s=1.201 m` 时 OCP 多项式曲率已为 `-0.815 1/m`，但发布/实测角速度仍是正的 `+0.181/+0.221 rad/s`；在 `s=2.997 m` 时 OCP 曲率已为 `+0.916 1/m`，发布/实测角速度仍约为 `0/-0.020 rad/s`。该现象与缺少 yaw/omega tracking 收益的机理一致，但其独立贡献仍须通过 Stage 0/6 的代价对照测试确认。

### FEAS-01：曲率限速只管 `omega_max`，不管 `alpha_max`

**状态：`CONFIRMED`，优先级 P1。**

当前只根据：

```text
omega = v*kappa
v <= omega_max/abs(kappa)
```

生成曲率参考速度，见 `scripts/acados/spmpc_acados_cost.py:49-73`。这不足以保证 alpha-state 模型可达。若按弧长跟踪：

```text
omega_ref = v*kappa
alpha_required = d(omega_ref)/dt
               = a*kappa + v^2*d(kappa)/ds
```

因此不仅曲率大小，曲率变化率也决定能否跟踪。当前 OCP 又有 `abs(alpha)<=1.2 rad/s^2` 硬约束。

对现有路径按当前曲率口径做只读量化时：

- `P3_mixed` 的高分位角加速度需求已约为 `1.1~1.2 rad/s^2`，紧贴硬上限；
- `slosh_priority_p2_s` 的 p99 需求约 `4 rad/s^2`，在 `v_ref=0.25 m/s` 下明显不可达。

这不表示几何路径在任何速度下都不可达；它表示“当前系统自己给出的参考速度”对自己的 `alpha_max` 局部不可达。OCP 只能降到参考速度以下或接受几何误差。

该代价又强制 `v_ref >= 0.3*v_cruise`，并用 anti-creep 对低于 `v_ref` 的速度额外重罚，会把“安全减速过弯”变贵，进一步增加外切或滞后的可能。

### REF-01：acados 主线不使用 `lookahead_distance`，并用单个三次多项式拟合整段路径

**状态：`CONFIRMED`，优先级 P1。**

`reference/lookahead_distance=0.6` 被 ROS 参数读取，但只在 primitive backend 中使用：

- `src/solvers/rollout_sampling_solver.cpp:169`

acados 主线实际使用：

```cpp
s_end = s0 + params_.v_max * Tf;
```

见 `src/solvers/continuous_mpcc_solver_acados.cpp:672-680`。fixed-path 默认下是 `1.6 m`，然后用 12 个样本点为 x(s)/y(s) 各拟合一个三次多项式，见同文件 `222-235`。

影响：

1. 调 `lookahead_distance` 对主线完全无效；
2. 在 S 弯、紧凑连续弯或高曲率处，OCP 跟踪的不再是原路径，而是被单个多项式改写后的几何；
3. 拟合区间按 `v_max` 而不是实际 `v_ref/v_s` 可达距离确定，远处几何可以反过来扭曲当前附近的切向；
4. 多项式使用全局 `s`、而不是 `sigma=s-s0`，路径弧长较大时还会增加数值条件问题。

只读拟合复现已在现有紧凑 S 路径上观察到厘米级位置误差和约 `10~20 deg` 量级的局部切向误差。定量结果必须与路径 SHA 绑定，不得对可变的 `/home/geist/fixed_paths/...` 文件只记文件名。

### REF-02：进度投影可以跳到任意远的后方路段，且不可恢复

**状态：`CONFIRMED`，优先级 P1。**

`src/reference/progress_projector.cpp:46-80` 在所有 `s>=last_s` 的线段中搜索全局最近点，没有：

- 局部索引/弧长窗口；
- 单周期最大前跳量；
- 航向一致性；
- 路段连通性；
- 自交/近距离平行段解歧。

`src/core/spmpc_problem.cpp:111-121,154-175` 又使 `last_progress_s_` 只增不减。因此在回头弯、自交、靠得很近的平行段上，一次误跳就可能永久丢失正确路段。现有 projection distance safety 也抓不住“空间距离小、但 s 跳得很远”的情况。

### CFG-01：部分代价归一化与曲率限速常量在 codegen 时写死，可与运行时约束不一致

**状态：`CONFIRMED`，point-to-point/运行时 override 下为高风险，优先级 P1。**

`scripts/acados/generate_spmpc_acados.py:71-110` 在生成时固化 fixed-path 平台值：

```text
v_max=0.8, omega_max=1.2, a_max=0.6, alpha_max=1.2
```

`spmpc_acados_cost.py` 用这些 `cfg` 常量做代价归一化和曲率限速。但 launch 会在运行时再加载 experiment config；`config/experiments/point_to_point.yaml:1-3` 把约束改成 `v_max=0.45, omega_max=0.75`，C++ wrapper 会更新硬约束，但已生成代价里的 `1.2` 不会变。

结果是：OCP 的硬角速度上限可能是 `0.75`，而参考限速仍认为可以用 `1.2`。高曲率下会自己制造参考/约束冲突。同理，任何 `alpha_max` 运行时消融也会改变硬约束，但不会改已生成代价的归一化尺度。

### TERM-01：终点阶段角速度硬夹可以让终点附近的大曲率弯不可跟踪

**状态：`CONFIRMED`（是否恶化取决于尾段曲率），优先级 P1。**

当车进入 terminal phase 后，`src/core/terminal_controller.cpp:153-159` 把 `omega` 夹到：

- 普通终点区：`0.25 rad/s`；
- 目标 `0.35 m` 内：`0.10 rad/s`。

配置见 `config/planner/common.yaml:99-123`。如果高曲率弯放在终点前 `1.2 m` 内，这个后置夹限可能低于 `v*kappa` 所需角速度，且该限幅不在 OCP 内，会破坏求解命令与实际发布命令一致性。

C02_v2/a02 已确认该分支实际触发，不再只是静态推测：

- terminal phase 从 `s=4.216 m` 开始，剩余弧长约 `1.213 m`，正好覆盖最后负弯；
- `1180` 个 `B0_ACADOS_OK` 周期中有 `432` 个属于 terminal phase，`175` 个周期的 terminal controller 真实改变了 solver command；
- 其中 `42` 个周期修改角速度，最大 `abs(delta_omega)=0.0422 rad/s`；`137` 个周期修改线速度，最大 `abs(delta_v)=0.0299 m/s`；两类周期可以重叠，因此不能与前述 `175` 直接相加；
- terminal 早期又在 `s≈4.497 m` 出现两段约 `1.4 s` 的低进度段，yaw error 峰值约 `0.507 rad`。

当前 acquisition validator 只要 terminal 改命令发生在 `terminal_phase=true` 就接受，因此 `execution_contract_fail_closed=true` 不等于“整段 solver-to-published 完全一致”。后续报告必须分开 solver、terminal post-gate 和 published 三层命令。

终点成功判定使用欧式距离是合理且已有测试固化的，不应随意改掉；但 slowdown/capture/clamp 的进入还应同时确认车已在路径尾段，避免路径早期空间靠近终点时过早介入。

## 4. 次级但必须一并防回归的问题

### REF-03：路径首尾曲率有退化向量 bug

`src/reference/reference_spline.cpp:38-50` 在首点使 `p_lo=p`，在尾点使 `p_hi=p`，然后计算 `atan2(0,0)`。这会使直线路径首尾的曲率依赖路径在地图中的绝对朝向，而不是真实几何。主要影响 warm start 限速、终点附近状态和诊断。

a02 在最后 `10` 个 B0 solve cycle 已到 `s=path_length`，但 `stage0_reference.ref_kappa` 仍为约 `+0.1835 1/m`，是该 bug 的实物触发证据。

### REF-04：`max_reference_fit_error` 实际没有检查 OCP 使用的多项式

`src/warm_start/diff_drive_flatness_warm_start.cpp:112-123` 先把 warm-start 位置直接设为 spline 采样点，`192-195` 又用同一 spline 采样点去比较，因此 `reference_fit_error` 基本恒为 0。它没有测量 `fitReferencePolynomials()` 送入 OCP 的三次多项式与原路径的误差。

### CFG-02：`smooth_priority_enable=false` 不代表平滑代价关闭

`B0` 中 `smooth_priority_enable=false`，但 `w_alpha/w_du_a/w_du_vs` 的负值会回退到 `w_smooth=0.1`，且 acados cost 无条件使用它们。`smooth_priority_enable` 目前主要是变体身份/诊断字段，不是行为开关。后续必须在名称和行为中选一个明确契约，不能让开发者根据字面误判。

### REF-05：fixed-path 默认不预处理

`common.yaml` 中 `preprocess_enable=false`。重复点、折线噪声和不连续曲率可直接进入投影、曲率计算和多项式拟合。但不得为了快速修复而全局默认打开平滑：这会静默改变已冻结路径的几何和 SHA 语义。正确做法是先做输入几何验证，再对需要预处理的路径生成新身份。

### REF-06：到达路径端点时局部三次拟合退化

**状态：`CONFIRMED`，优先级 P1（在引入 yaw cost 前必修）。**

`fitReferencePolynomials()` 在 `s0==path_length` 时仍强制 `span>=0.001`，但 `ReferenceSpline::sample()` 把这些超出路径的样本全部夹回同一终点。结果是：拟合矩阵在全局 `s` 坐标下近似秩亏，位置虽可重现，导数和切向却没有定义。

a02 最后 `0.30 s/10` 个 B0 solve cycle 中：

```text
s0=s_end=5.4284537 m
polynomial derivative norm ≈ 2.9e-11
ref_yaw ≈ -3.1412 rad
robot_yaw ≈ +0.02 rad
reported wrapped yaw_error ≈ -3.12 rad
```

当前 cost 没有 yaw tracking，且 terminal controller 已接管，所以这不是中段转弯失败主因。但若跳过 Stage 4、直接按 Stage 6 加 yaw cost，会把终点附近的错误 `pi` 航向正式写入 objective。

### REF-07：路径验证、诊断和 OCP 使用三套不同曲率口径

**状态：`CONFIRMED`，优先级 P1。**

当前同一周期里实际存在：

1. 路径 validator 的相邻点 signed-Menger 曲率；
2. `ReferenceSpline::sample()` 用约 `0.1 m` 有限差分得到的曲率；
3. OCP cost 用 `reference_x/y_coeffs` 三次多项式解析导数得到的曲率。

`stage0_reference` 又在一个 payload 中混用了两套几何：`ref_x/ref_y/ref_yaw` 来自 OCP polynomial，`ref_kappa` 却来自 `ReferenceSpline`。C02_v2/a02 中，在 `abs(kappa_spline)>0.1` 的条件下仍有约 `102/1180` 个周期两者符号不同；例如 `s≈1.0 m` 时 spline 还报正曲率，OCP polynomial 已经报负曲率。

路径级只读量化也证明了差异：

| 路径 | Menger `max|kappa|` | OCP polynomial horizon `max|kappa|` | horizon 最大位置/切向误差 |
|---|---:|---:|---:|
| C02_v1, SHA `eb62d44f...` | `4.9466 1/m` | 约 `1.6925 1/m` | 约 `0.0223 m / 19.0 deg` |
| C02_v2, SHA `1464ef37...` | `0.9007 1/m` | 约 `1.0430 1/m` | 约 `0.00834 m / 7.90 deg` |

这表明 C02_v1 的尖曲率在进入 OCP 前已被大幅低通；同时 C02_v2 的拟合误差较小却仍跟踪失败，所以局部多项式不是 a02 的唯一主因。后续必须用同一个“OCP 实际参考”对象生成曲率限速、诊断和质量报告，不得再把三者混为同一个 `kappa`。

## 5. 改进时必须保持的不变量

### 5.1 机器人基线不变量

1. B0 与 slosh 的 `[x,y,yaw,v,s,omega]` 动力学、`[a,alpha,v_s]` 控制语义必须一致。
2. `v_max/omega_max/a_max/alpha_max`、延迟模式、指令后限幅、参考路径和终点逻辑必须在正式 B0/slosh 对比中相同。
3. 修 B0 不得靠把 `alpha_max` 提高到超出共享物理约束；放宽 alpha 只能是带明确标记的诊断消融。
4. 不得用 terminal clamp、safety zero 或后置 rate limiter 隐藏 OCP 输出问题。任何 solver 后的命令变化都必须有诊断、契约和回归测试。
5. RouteB 只作诊断对照，不得无记录地替换 alpha-state formal 主线。

### 5.2 slosh 公平性不变量

1. 修复跟踪链时先让 B0 通过，不先调 `w_slosh`。
2. 机器人共享修复必须同时进入 B0 和 slosh generated solver/wrapper；不得让 slosh 方独有更好的转向前馈或延迟补偿。
3. slosh solver 要求 robot/liquid 共同 epoch 时，不得为了跟踪表现强行使用 `fixed_robot_only`。
4. `w_slosh=0`、液体初值为 0 的 matched slosh solver 应在允许的数值容差内复现 B0 机器人命令趋势。不一致必须可解释，不得默认归因于求解器噪声。

### 5.3 生成求解器不变量

1. 源头是 `scripts/acados/spmpc_acados_model.py` 和 `spmpc_acados_cost.py`；不得手改 `generated/acados/**`。
2. 参数向量增删/重排时，Python `PARAM_NAMES/PIDX`、C++ enum/wrapper、generated `NP` 必须在同一个原子提交中更新。
3. 任何共享 cost/model 改动都必须重生成 B0 和 slosh；若共享函数也被 legacy 使用，还必须检查两个 direct-omega 诊断模型。
4. 生成物必须记录 acados 版本、生成器 commit、配置 hash、`N/NX/NU/NP/NH`，启动时不匹配应 fail closed，不应只靠维度 `static_assert`。

### 5.4 与 `README_METHOD.md` 的核心贡献边界

按本方案修复后，项目理论上仍符合 `README_METHOD.md` 的核心方法，前提是严格保留：

1. alpha-state MPCC 的机器人状态/控制语义；
2. slosh 模态状态作为预测状态进入滚动 OCP；
3. 跟踪、进度、底盘可执行性、控制平滑和液体响应的联合优化；
4. B0/slosh 使用同一机器人跟踪和执行链，slosh 只追加液体动力学/代价/约束；
5. 可选 risk governor 仅调整进入 MPCC 的参考，不用隐藏的后置命令修剪自证有效。

本方案中的延迟对齐、参考几何、yaw/omega 跟踪、可达 speed profile、projection 和 terminal/safety 修复，属于让共享机器人基线真正可执行的实现修正，不会把“液体动态记忆进入在线 MPCC”这一核心贡献变掉。

以下改法会越过该边界，不得以“修 B0”名义静默执行：

- 用 direct-omega RouteB 替换正式 alpha-state 主线；
- 从 slosh OCP 中移除液体状态传播，只剩平滑权重或后置限速；
- 让 slosh 方独有更好的机器人参考/延迟处理，破坏 B0 消融公平性；
- 用未来真值、RGB 评价真值或 acados 未来解伪装成当前可用状态；
- 为了过单条路径而超出共享平台物理上限。

`README_METHOD.md` 当前的局部三次参考、代价项和执行顺序是“当前代码描述”，不是不可修改的核心贡献。按用户决策，先完成修复和成功验证，再使用最终实现口径适配其具体描述；在此之前不得反过来为迁就旧文字保留已确认 bug。

### 5.5 目标模块边界

“分 Stage”只表示验收顺序，不表示一个 Stage 可以一次性修改完。后续必须以单一模块、单一因果假设为提交粒度；同一 Stage 内的不同模块也必须拆成独立提交和独立回归。

目标边界如下：

| 模块 | 唯一职责/输出 | 明确禁止 |
|---|---|---|
| `ExecutionStatePredictor` | 根据带时间戳的 odom、命令历史和分通道延迟，输出同一 execution epoch 的完整机器人状态及有效性证据 | 不做路径投影、速度规划、代价计算、安全判定或终点限幅 |
| `MotionLimitContract` | 解析并冻结运行时硬约束，核对 generated solver metadata，输出带身份的 effective limits | 不生成控制命令，不用 `v_ref` 代替硬上限，不静默接受 codegen/runtime 分裂 |
| `ReferenceGeometry` | 从冻结路径身份生成 OCP 实际使用的位置、切向、曲率和曲率变化率，并可无损序列化给诊断/Python | 不决定速度，不做 terminal 或 safety，不让 solver/validator 各自再拟合一套几何 |
| `FeasibleSpeedProfile` | 根据统一几何、完整机器人状态和硬约束生成满足 `v/omega/a/alpha` 可达性的速度参考 | 不求解 OCP，不发布命令，不在出口补一个隐藏限幅 |
| `ProgressProjector` | 在拓扑和连续性约束下把机器人位姿映射到路径进度，输出候选、选择和重定位原因 | 不判定终点到达，不修改命令，不兼任 tracking safety |
| `TrackingSafetyGate` | 根据运动、进度和偏离证据判断是否真正失控，输出锁存状态和原因 | 不做普通转弯控制，不负责终点停车，不用单一高角速度判失败 |
| `TerminalController` | 在确认进入路径尾段后负责减速、捕获和停车，并完整报告 solver 后命令变化 | 不做全程路径投影，不兼任普通 tracking safety，不掩盖未完成尾弯的误差 |
| `TrackingQualityValidator` | 离线判断路径跑得是否足够好，独立输出 quality pass/fail | 不改变在线控制，不把数据完整性 PASS 当成跟踪质量 PASS |
| OCP solver/wrapper | 消费上述模块输出，求解并输出 solver command、预测轨迹和可追溯快照 | 不在内部重新构造第二套曲率、速度上限、延迟状态、安全门或 terminal 逻辑 |

#### 单一执行时刻契约

线速度延迟 `0.15 s`、角速度延迟 `0.22 s` 是两个执行通道的动态参数，不是两个可以分别交给 OCP 的状态时刻。每个控制周期必须只定义一个 `t_exec`，最终的 `[x,y,yaw,v,omega]` 和 slosh 模态状态都带同一个时间戳。

预测时应在同一积分时间轴上分别查询：

```text
v_applied(t)     = cmd_v_history(t - delay_v)
omega_applied(t) = cmd_omega_history(t - delay_omega)
state_exec       = integrate(state_raw, raw_stamp -> t_exec,
                             v_applied(t), omega_applied(t))
```

若积分查询落到尚未发布的未来命令区间，必须由 Stage 2A 明确采用 zero-order hold、候选命令二次预测或显式输入延迟模型；不得静默当零，也不得伪称为完整历史。

`t_exec` 的选择策略必须在配置和诊断中显式冻结；可从“新 Twist 的两个通道都已生效”的时刻开始验证，但不得把 `v` 预测到 `t+0.15 s`、把 `omega` 预测到 `t+0.22 s` 后拼成一个不存在的机器人状态。输出还必须记录 raw stamp、`t_exec`、两通道延迟、历史完整性、预测跨度、未来命令假设和降级原因。正式 slosh 模式下，机器人和液体状态也必须对齐到该共同 epoch。

#### 独立速度安全上限契约

必须区分三种量：

```text
v_ref                  期望速度，允许优化器偏离
v_safe_max             独立、可审计的运动安全硬上限
v_feasible_profile(s)  受曲率、alpha、加速度和制动距离约束的动态参考
```

必须满足 `v_feasible_profile(s) <= v_safe_max <= platform_v_max`。`v_safe_max` 必须进入 OCP 硬边界和 effective config，并在最终发布层做独立断言。若最后一道保护不得不截断命令，该周期必须留下明确诊断并使 execution/quality gate 失败，不能把隐藏截断后的结果计为 OCP 成功跟踪。

#### OCP 实际参考的跨语言契约

`ReferenceGeometry` 必须提供一个可版本化的只读快照，至少包含：路径 SHA/geometry ID、表示类型、`s0/s_end`、stage 的 `s/x/y/yaw/kappa/kappa_prime` 或能精确重建这些量的系数、拟合误差、端点降级标记和 cycle ID。

C++ 中的 OCP、warm start、speed profile 和在线诊断必须消费同一实例；Python quality validator 必须读取该实例的序列化快照，不得再从原始路径用另一种 Menger/有限差分算法冒充“OCP 实际曲率”。原始路径几何仍可作为输入质量对照，但字段名和报告必须明确区分。

### 5.6 代码级解耦验收标准

目标依赖方向固定为：

```text
odom + command history -> ExecutionStatePredictor -> execution_state(t_exec)
frozen path -----------> ReferenceGeometry -------> geometry(path_id, version)
execution_state + geometry -> ProgressProjector --> progress_s / segment_id
geometry + progress_s + MotionLimitContract ------> FeasibleSpeedProfile

execution_state + geometry horizon + speed profile + effective limits
    -> OCP solver -> solver command
    -> TerminalController -> terminal command
    -> TrackingSafetyGate -> publish/stop decision

上述只读快照 -> diagnostics/bag -> TrackingQualityValidator
```

代码审查必须同时满足：

1. 核心算法模块有独立头文件、实现文件和单元测试；ROS 参数读取、消息转换和发布留在 adapter/orchestrator，不能塞进算法类。
2. 配置只解析一次并转为带版本的 typed config；模块不得各自读取 YAML/parameter server 后形成不同 effective value。
3. execution state、geometry、speed profile 和 motion limits 分别带 `epoch/id/version`；OCP wrapper 发现身份不匹配时拒绝求解，不能自动混用。
4. diagnostics 只能复制模块输出，不能为了“显示方便”重新计算另一套 yaw/kappa/speed。
5. Python 只读取版本化快照；若需要计算原始路径 Menger 曲率，只能作为明确命名的输入质量指标。
6. 模块之间不允许循环依赖。`ReferenceGeometry` 不依赖 speed profile，speed profile 不依赖 OCP，safety/terminal 不反向修改 geometry。
7. 每次“提取模块”先做行为保持提交，以冻结 cycle fixture 证明 solver 输入和发布命令未变；随后才允许单独修该模块的行为。
8. 上层 orchestrator 只负责调用顺序、ID/时间戳一致性检查和故障传播，不重新实现任何模块算法。

## 6. 按模块拆分的实施方案

以下 Stage 是验收门，不是提交单位。强制规则是：一个提交只改变一个模块的一条行为假设；行为修改前的失败测试必须先落地；不得在同一提交中同时改路径、速度上限、delay mode、`alpha_max` 和 cost。

规范顺序为：

```text
Stage 0  证据/质量检查
Stage 1  硬速度上限与参数契约
Stage 2  延迟补偿
Stage 3  tracking safety
Stage 4  统一参考几何
Stage 5  可实现速度规划
Stage 6  转向代价
Stage 7  路径投影
Stage 8  终点控制
Stage 9  B0/slosh 验证
```

### Stage 0：冻结测试数据、诊断格式和质量检查，不改控制行为

**状态：`TO_IMPLEMENT`。**

必须拆成至少三个独立提交：

#### 0A. 冻结证据与最小路径 corpus

- 为 a01/a02 固定 bag、路径 SHA、有效配置、binary/solver 身份和当前指标提取结果；
- 冻结直线、定曲率圆弧、类 clothoid、快速换向 S 弯、回头/近平行/自交和终点弯；
- 每条 fixture 记录长度、`kappa_max`、`kappa_prime` 和理论 `omega/alpha` 需求，不依赖可变外部路径文件。

#### 0B. 冻结跨语言诊断 schema

- 先让现有 `PreSolveSnapshot` 多项式系数可由 Python 精确重建，建立当前行为基线；
- 增加带 schema version、path/geometry ID 和 cycle ID 的 OCP 实际参考快照契约；
- 此提交只加诊断/解析测试，不改变 solver 输入或命令。

#### 0C. 独立 `TrackingQualityValidator`

- 保留现有 acquisition/data-integrity validator 的语义；
- 独立检查速度硬上限、contour/yaw、停滞、饱和、delay applied、terminal 段和安全介入；
- 固化“a02 acquisition pass、tracking-quality fail”的回归，防止以后仅凭 `GOAL_REACHED` 放行。

Stage 0 或对应模块的前置测试必须覆盖：

1. `SAFE-01` 合法圆弧回归：`r=0.4 m, v=0.25 m/s, 90 deg`，持续角速度超过 2 s 时不得触发 spin fail。
2. 真正原地旋转回归：高 `omega`、低 `v`、低 progress 持续超时必须触发并锁存。
3. `TRK-01` 纯延迟 plant 回归：线/角延迟 `0.15/0.22 s`，检查饱和 `a/alpha` 下命令建立速度，并显式失败于“每拍从滞后测量重锚定”的旧行为。
4. S 弯换向时序回归：保存 `kappa_poly/omega_ref/u0_alpha/solver_cmd/published_cmd/plant_omega`，命令换向滞后不得被底盘延迟指标掩盖。
5. `REF-03` 任意地图朝向直线的首/尾曲率必须为 0。
6. `REF-04` 故意构造无法由单个三次多项式精确表示的路径，现有 fit-error gate 必须先显示为假阴性。
7. `REF-06` 端点回归：`s0 -> path_length` 时参考切向/曲率必须有定义，不得出现零导数和 `pi` 航向翻转。
8. `REF-07` 曲率契约回归：质量 validator、speed profile、OCP parameter 和 stage-0 诊断必须指向同一参考几何身份。
9. `REF-02` 回头弯、平行近距离段和自交路径投影回归。
10. `CFG-01` 运行时 `omega_max=0.75` 与 codegen `1.2` 不一致的契约测试。
11. `SPD-01` 速度契约回归：低速 runner 的最终发布速度不得超过冻结硬上限，且配置/有效值/审计报告一致。
12. `VAL-01` 质量门回归：构造数据完整但 contour/yaw/速度超限的 trial，acquisition pass 与 tracking-quality fail 必须同时被正确表达。
13. `TERM-01` 命令分层回归：尾弯中 solver/terminal/published 三层必须各自可见，且 tracking-quality gate 必须检查 terminal 弯道而不是排除它。

这些测试可以按模块分批落地，但每一个行为修复提交之前，关联的旧行为必须已经稳定失败。

### Stage 1：建立硬速度上限和参数契约

**状态：`TO_IMPLEMENT`。**

#### 1A. `MotionLimitContract`（先做，不改变控制行为）

独立提交完成以下契约：

1. 明确 `platform_v_max`、`v_safe_max`、运行时 effective bounds 和 generated bounds 的字段语义；
2. 启动时核对 solver metadata/config hash/运行时 override，发现不一致则 fail closed；
3. `/spmpc/debug/effective_config` 和审计消息发布同一份带身份的硬约束；
4. 先用 `omega_max=0.75`、generated `1.2` 的 fixture 固化旧版静默分裂。

cost normalization 和 curvature-speed 所需 motion limits 优先改成运行时参数；若保留多套 generated solver，则必须一套 profile 对应一个明确身份，不能自动猜测。

#### 1B. 独立 `v_safe_max`（单独行为提交）

1. `v_ref` 保持软目标，不再承担“低速安全”含义；
2. `v_safe_max` 同时进入 OCP 硬边界、warm start/profile 上界和 effective config；
3. 最终发布层只做独立契约检查。若需要最后一道安全截断，必须报告差值并让该 trial 失败，不能静默修饰 solver 输出；
4. 用 a02 的 `V_REF=0.10`、实际约 `0.36 m/s` 复现旧失败，再证明新硬上限不可突破。

`1A` 和 `1B` 不得合并：前者建立配置/身份契约，后者才改变速度行为。

### Stage 2：只修延迟补偿和 execution-state 一致性

**状态：`TO_IMPLEMENT`。**

必须拆成以下提交：

1. **2A 时间语义 ADR + 失败测试（不改行为）：**冻结唯一 `t_exec` 的定义、raw state 所属时刻、分通道 delay-line 查询规则，以及预测区间中尚无历史命令时采用 hold/两次求解/显式输入延迟模型中的哪一种。该决定未完成前禁止改闭环；无论选择哪种算法，都不得拼接两个状态时刻。
2. **2B predictor core：**只修改 `ExecutionStatePredictor`，按第 5.5 节的分通道延迟历史把完整机器人状态推到同一 `t_exec`，并覆盖历史缺失、stale、时钟回退和预测跨度超限测试。
3. **2C B0 闭环接线：**让 OCP x0、投影输入、第一步命令语义和诊断都引用同一 execution-state ID；用纯延迟 plant 和冻结 S 弯检查命令建立相位。
4. **2D slosh common epoch：**在 B0 接线通过后，把液体状态传播到同一 epoch；`fixed_robot_only` 只能作诊断消融，不得进入正式 matched 结论。
5. **2E profile/故障策略：**仿真和实物使用不同 profile；零延迟仿真不伪装成 `0.22 s`，已识别延迟的实物入口不能只开 `shadow`。所有降级/fail-closed 原因进入 effective config 和 cycle audit。

不建议只把出口改成 `last_cmd + alpha*dt`，同时仍用 raw measured omega 作为 OCP x0；这会制造新的状态/命令分裂。

`2A~2E` 不得与 safety、参考几何、速度 profile 或 cost 修改合并。完成标准是纯延迟 plant 和 S 弯命令建立时序改善，且关闭补偿时仍可稳定复现旧问题。

### Stage 3：只提取并修复 `TrackingSafetyGate`

**状态：`TO_IMPLEMENT`。**

至少拆成两个提交：

1. **3A 行为保持提取：**把 ROS 类内 tracking projection/spin 的计时、滞回和锁存搬入可单测模块，输出每个判据和失败原因，保证命令逐周期不变；
2. **3B 判据修复：**在失败 fixture 已存在后，把 spin 条件改成：

```text
high_omega
AND low_linear_motion
AND low_progress_rate
AND persists_for_timeout
```

投影距离、cmd/measured 一致性可作为附加证据。不得把“有持续正向 progress 的合法高曲率转弯”视为失控，也不得删除真正原地自旋时的 fail-closed。terminal spin 不在本 Stage 修改，留给 Stage 8。

### Stage 4：只建立统一 `ReferenceGeometry`

**状态：`TO_IMPLEMENT`。**

依次使用独立提交：

1. **4A 行为保持提取：**把当前局部多项式构造从 OCP solver 内移到 `ReferenceGeometry`，先证明 solver 参数和命令逐周期等价；
2. **4B 统一快照：**让 OCP、warm start、在线诊断和 Python 使用同一 geometry ID/序列化对象，不再混用 spline kappa 与 polynomial yaw；
3. **4C 端点修复：**修复首尾单边差分和 `s0 -> path_length` 拟合退化，禁止零导数和 `pi` 航向翻转；
4. **4D 拟合契约：**明确 `lookahead_distance`，并修复全局-s 单三次拟合。优先使用分段/逐 stage 参考；若暂时保留多项式，必须使用 `sigma=s-s0`、锚定当前位置/切向、限制为实际需要区间，并检查位置、切向和曲率误差；
5. **4E 真 fit-error gate：**直接比较 OCP 实际参考与原始路径几何，不再比较 warm start 与自身。

本 Stage 不改速度参考或转向 cost。每次几何行为变化都必须在同一冻结路径 corpus 上独立回归，并产生新的 geometry schema/version 或明确兼容说明。

### Stage 5：只建立 `FeasibleSpeedProfile`

**状态：`TO_IMPLEMENT`。**

该模块只消费 Stage 1 的硬约束和 Stage 4 的统一几何，显式满足：

```text
v <= v_safe_max
abs(v*kappa) <= omega_max * margin_omega
abs(a*kappa + v^2*kappa_prime) <= alpha_max * margin_alpha
abs(a) <= a_max
```

拆分为：

1. **5A 离线/单元模块：**在 horizon 样本上做前向/后向 speed pass，证明弯前具有足够制动距离；
2. **5B OCP 接线：**把同一 profile 作为 stage 参考/边界输入，并让快照、warm start 和 Python 报告同一 profile ID；
3. **5C anti-creep 语义：**只惩罚“在可行 profile 下无原因停滞”，不惩罚为满足 `alpha` 约束所需的合法减速。

`5A/5B/5C` 不得与 yaw/omega cost 修改合并。

### Stage 6：加入航向/曲率前馈，重新整理转向代价语义

**状态：`TO_IMPLEMENT`。**

只有 Stage 4 的 geometry contract 和 Stage 5 的 feasible profile 均通过后才允许开始。至少拆成参数接线、yaw cost、omega cost 三个独立提交；每个行为提交都必须同时重生成并验证 B0/slosh。

按顺序增加：

1. **6A 参数/符号测试：**先接通 reference yaw/kappa/profile 参数和 cost 对照测试，不改变有效权重；
2. **6B yaw tracking：**使用 `1-cos(yaw-phi_ref)` 或等价周期平滑形式，避免 `+-pi` 不连续；
3. **6C omega tracking：**加入 `omega_ref=v*kappa`，让 contour error 出现前就有建立角速度的收益；
4. **6D 可选 alpha 前馈：**只有 6B/6C 仍不足且证据明确时，才加入 `alpha_ref=d(v*kappa)/dt`，并使用与 speed profile 同一套 `kappa/kappa_prime/a/v`。

同时把当前含混语义拆开：

- `w_omega_reg`：角速度幅值正则；
- `w_omega_track`：对 `omega_ref` 的跟踪；
- `w_alpha_reg`：角加速度幅值正则；
- 若存在 `alpha_ref`，再独立定义 tracking 权重。

不得直接把旧 `w_omega/w_alpha` 从 0.1 调成 0 就宣布修复。那只是减少阻尼，没有建立可验证的转向参考。

### Stage 7：只修复 `ProgressProjector`

**状态：`TO_IMPLEMENT`。**

投影候选应至少同时考虑：

- 上一路段索引/局部弧长窗口；
- 按 `v_max*dt`、定位不确定性和延迟给出的最大前跳；
- 车体 yaw 与路段切向的一致性；
- 连通路段优先；
- 小范围回退或显式 re-acquire 状态机。

全局重定位只能在局部投影失败后进入显式 recovery，不能在每拍普通 tracking 中默认发生。必须诊断 `delta_s`、segment index、heading mismatch 和 re-acquire reason。

先以行为保持提交补齐当前 projector 的候选/选择诊断，再以单独行为提交增加窗口、最大前跳和 re-acquire 状态机。本 Stage 不允许修改 terminal 条件或命令。

### Stage 8：只修复 `TerminalController`

**状态：`TO_IMPLEMENT`。**

1. 保留 goal reached 的欧式位置判定。
2. slowdown/capture/clamp 进入要同时确认 tail progress/remaining arc length，防止空间靠近终点但实际还在早期路段。
3. `omega` 夹限必须与尾段 `v*kappa` 一致：若角速度必须更小，就应在 OCP 内同步降低可行速度，不得只在出口截断。
4. 进入 terminal 时不得让未完成的尾弯从 OCP 跟踪责任中消失；必须持续评估 tail contour/yaw/progress，并报告 solver-to-terminal 改命令的周期数和最大差值。
5. 终点大曲率 fixture 必须既不误触发 `TERMINAL_SPIN_FAIL`，也不因隐藏 omega clamp 偏离。

终点进入条件、速度 envelope、omega clamp 和 terminal spin 判据应分别有失败测试；若一次提交需要改变其中两项，必须说明不可分割原因，否则继续拆分。不得在本 Stage 顺手修改 projector 或通用 tracking safety。

### Stage 9：B0 基线通过后，再做 slosh 对齐和正式验证

**状态：`TO_VALIDATE`。**

顺序不得颠倒：

1. B0 + 零延迟理想 plant；
2. B0 + 线/角分通道延迟 plant；
3. B0 低速实物 N=1 safety run；
4. B0 固定路径 N=3；
5. slosh solver 中 `w_slosh=0` 的机器人链对齐；
6. matched slosh pair；
7. 最后才能对 `w_slosh`、hard constraint 或 risk governor 作方法学结论。

## 7. 必须建立的自动回归门

### 7.1 单元/符号测试

| 编号 | 必须保证的性质 |
|---|---|
| UT-REF-01 | 任意朝向直线首尾 `kappa=0` |
| UT-REF-02 | OCP reference fit 误差直接对真 spline 计算，差几何必须被 gate 抓住 |
| UT-REF-03 | `s0=path_length` 仍有有限、正确的尾点切向/曲率，无 `pi` 翻转 |
| UT-REF-04 | OCP、speed profile、warm start 和 stage diagnostic 对同一参考实例给出同一 `kappa` |
| UT-PROJ-01 | 自交/平行段不会无界前跳，单周期 `delta_s` 受约束 |
| UT-SAFE-01 | 合法持续圆弧不触发 spin fail |
| UT-SAFE-02 | 高 omega + 低 v + 低 progress 持续超时必须 fail closed |
| UT-EXEC-01 | 延迟 plant 中 `alpha` 饱和可持续建立 execution-epoch `omega`，不从同一滞后测量重置 |
| UT-EXEC-02 | `delay_v != delay_omega` 时，输出的 `x/y/yaw/v/omega` 和 slosh state 仍共享唯一 `t_exec`；禁止拼接双时刻状态 |
| UT-SPD-01 | 任意 `v_ref` 和 progress 权重下，solver/published command 都不能超过独立 `v_safe_max` |
| UT-COST-01 | 同一路径点上，正确 yaw/omega 的 cost 必须低于错误 yaw/omega |
| UT-COST-02 | 车仍在中心线上但前方有弯时，最优转向方向必须与 `kappa` 符号一致 |
| UT-FEAS-01 | 生成的 speed profile 在离散容差内满足 omega/alpha/a 限制 |
| UT-CFG-01 | runtime motion limits 与 cost/solver metadata 不一致时不得静默启动 |
| UT-MODE-01 | B0/slosh 共享参数前缀、维度和生成 metadata 同步 |
| UT-VAL-01 | 同一 trial 可同时得到 acquisition PASS 和 tracking-quality FAIL，二者不得互相覆盖 |

| 场景 | 关键判据 |
|---|---|

建议最低标准，后续冻结实验时可收紧但不得临时放宽：

- B0 同一冻结路径 N=3 全部 `GOAL_REACHED`；

### 8.1 已有证据

### 8.2 不能过度外推的结论

- B0 不是所有路径都失败；较平滑 S 路径的实物 N=3 曾稳定到点。
- 问题主要随 `kappa_prime`、延迟、路径拓扑、终点位置和安全门持续时间触发。
- 静态代码审查能确认因果机制，但无具体 bag 时不能断言某一次失败是哪个 gate 最先触发。必须根据 status 和 cycle audit 分流。a01/a02 已有具体 bag，其首要现象是命令建立滞后/停滞，不是 solver 或 safety gate 先失败。
